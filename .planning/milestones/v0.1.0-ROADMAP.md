# Roadmap: gbkt Compiler Pipeline Rebuild

## Overview

The rebuild transforms gbkt from a fragile, string-concatenating prototype into a clean compiler pipeline: a Kotlin DSL records games into a sealed IR, nine ordered analysis passes annotate that IR with hardware resource assignments, and a structured C AST codegen layer emits bank-split C files for GBDK lcc. Five phases deliver the complete pipeline: IR and DSL stabilization, structured codegen with migration cut, asset pipeline and JVM test runner, analysis passes (the "GC for hardware" differentiator), and full integration validation across all three example games.

**Goal**: The sealed IR hierarchy is complete and stable; all game-domain concepts expressible without RPG-specific nodes; DSL builders record into IR; example games produce valid IR
**Depends on**: Nothing (first phase)
**Requirements**: IR-01, IR-02, IR-03, IR-04, DSL-01, DSL-02, DSL-03, DSL-04

  3. `ref()` calls to nonexistent targets fail the build with a clear error message

  5. `when(irNode)` exhaustive matching compiles without `else` branches across all IR node types

### Phase 06.12: Embedded Emulator Core and Debug Loop (INSERTED)

**Goal:** Embed a Game Boy emulator as a JVM library (`gbkt-emulator` module) to close the developer debug loop. Replace the fire-and-forget `runEmulator` Gradle task with an integrated emulator that captures `EMU_printf` debug output to a log file in real-time. This enables Claude-assisted debugging (read `build/gbkt/logs/debug.log`) and lays the foundation for the IntelliJ-embedded emulator (Phase 09).
**Depends on:** Phase 06.11
**Requirements**: EMU-01, EMU-02, EMU-03, EMU-04, EMU-05, EMU-06, EMU-07

**Technical Decisions (from research):**

**Primary emulator core: Coffee-GB** (`eu.rekawek.coffeegb:core` on Maven Central)

- Pure Java 16, zero native code, zero GUI deps in core module
- MIT license, 1,149 stars, actively maintained (Feb 2026)
- Passes all Blargg test suites (cpu_instrs, instr_timing, mem_timing-2, cgb_sound, halt_bug)
- Full GB + GBC support, MBC1-MBC7 (MBC5 critical for GBDK banking)
- Proven headless API: `GameboyConfiguration` → `Gameboy.tick()` → `EventBus` frame events
- Memory access: `getAddressSpace().getByte(addr)` / `setByte(addr, val)`
- CPU access: `getCpu().getRegisters()` (PC, SP, AF, BC, DE, HL)
- Frame stepping: `tick()` returns per T-cycle, `TICKS_PER_FRAME = 69,905`
- Input: `ButtonPressEvent`/`ButtonReleaseEvent` via EventBus

**Fallback/upgrade path: SameBoy** (via JNI/FFM if accuracy insufficient)

- C11, MIT license, gold standard accuracy (99.9%+ on ~2,800 games)
- Native `GB_set_execution_callback` — per-instruction opcode delivery (zero overhead)
- Native `GB_set_write_memory_callback` / `GB_set_read_memory_callback`
- `GB_get_direct_access` — raw pointers to ROM, WRAM, VRAM, SRAM, OAM, IO, HRAM
- Requires JNI/FFM bridge (~09-20 functions) + platform-specific native libs
- Reserve this path for Phase 09 IDE embedding if Coffee-GB proves insufficient

**`ld d,d` trap (EMU_printf) implementation with Coffee-GB:**

- GBDK `EMU_printf` emits opcode 0x52 (`ld d,d`) + magic signature `0x6464` + message payload
- Coffee-GB approach: poll `getCpu().getCurrentOpcode()` after each `tick()`, or fork CPU class to add callback
- AddressSpace decorator pattern (proven by `Genie` class) enables memory write hooks

**Architecture:**

```
gbkt-emulator/                    # New module
  GbEmulator.kt                   # Interface (swappable backend)
  CoffeeGbEmulator.kt             # Coffee-GB implementation
  DebugMessageParser.kt           # ld d,d trap → structured log events
  EmulatorSession.kt              # Run loop, input handling, frame capture

gbkt-gradle-plugin/
  RunEmulatorTask.kt              # Updated: use embedded emulator, capture logs
                                  # Log output: build/gbkt/logs/debug.log
                                  # Framebuffer: render to Swing window (160x144)
```

  6. All existing example ROMs (Pong, Breakout, Explorer, Platformer) boot and run in the embedded emulator

### Phase 13: framework primitives surfaced by example ports (rolling)

**Goal:** Add the framework-level DSL/codegen primitives that the reference-port phases (9, 10, 11, 12) collectively surfaced as gaps too wide for port-local fixes. This phase is a **rolling collector** — initial requirements come from the Phase 09.3 audit of simple-physics; phases 10/11/12 are expected to add more requirements via `/gsd-phase --edit 13` as ports surface new gaps. The phase is intentionally placed at the end of v1.0 so cross-port patterns can be identified before committing to API shapes. **SPLIT 2026-06-03:** divided into five subsystem sub-phases (13.1–13.5, by-subsystem grouping); this umbrella section is the canonical Req #1–#18 catalog and the sub-phase sections below are the execution units.

**Initial requirements (from Phase 09.3 simple-physics audit):**

1. **Type-safe `Cartridge` enum/type** for `config { cartridge = ... }` — eliminate the string-typed `"ROM_ONLY"` / `"MBC1"` / `"MBC5"` magic strings currently used across examples. Should be the canonical reference for valid cartridge types and lower cleanly to the GBDK `cart` config without runtime string parsing.
2. **Single-frame conditional primitive (`if` / `unless`)** to replace overloaded nested `whenever` blocks. Current usage (e.g., SimplePhysics.kt:77-83) nests `whenever` inside `whenever` to express "if speed went past clamp, snap it back" — semantically an `if` inside a frame handler, not a reactive trigger. Frame handlers need a real `if {} else {}` or `unless {}` primitive that lowers to a direct C `if`.
3. **Fixed-point sub-pixel abstraction** (`i16FixedVar` / `subpixel { }`) — hide the manual `shr 4` and the magic literal `1024` (= 64 pixels × 16 sub-pixels). Should support arithmetic, comparison, and pixel-coordinate extraction with no shift leaking into user code.

**Additional requirements (from Phase 10 metasprites audit — 2026-05-18):**

4. **`MetaspriteBuilder.sprite()` method** — declarative asset binding inside `metasprite { }` blocks. Currently `sprite(asset("sprites/elephant.png"))` cannot be compiled inside a `metasprite { }` block; the asset PNG is loaded implicitly at the pipeline level by matching the metasprite ID to a resource file. An explicit `sprite()` builder method would make the asset loading intent visible in DSL, enable IDE navigation from DSL → asset file, and align `metasprite { }` with the existing `actor { sprite(...) { } }` pattern. Surfaced at `Metasprites.kt:130` (`// PHASE-13: MetaspriteBuilder.sprite() not yet implemented`). Confirmed across the metasprites CLAUDE.md §"PHASE-13 TODOs" item 1.
5. **Explicit-slot `palette()` DSL for multi-palette scenes** — `SceneBuilder.palette(p)` (and the related `GameBuilder` actor-palette path) currently uses an auto-increment slot counter when no explicit slot is provided. While this is functionally correct for sequential declarations, authors loading palettes into specific GBC OBP slots (e.g., always load the "enemy" palette into slot 3) need a `palette(p, slot = 3)` or `palette(p).intoSlot(3)` API. The auto-increment fix in Plan 16 (`else paletteOps.size`) resolved the runtime bug, but the DSL gap (no way to specify explicit slot from user code) remains. Surfaced at `Metasprites.kt:92, 317` (`// PHASE-13: slot assignment — all palette() calls default to slot 0 until explicit-slot DSL lands`). Confirmed across the metasprites CLAUDE.md §"PHASE-13 TODOs" item 2.

**Additional requirements (from Phase 10 metasprites deeper audit — 2026-05-19):**

The Phase 10 close (item #4 + #5 above) captured the most egregious gaps but missed four primitives that together account for ~40% of the `Metasprites.kt` line count and most of the "this reads like a thin C wrapper, not a Compose-like DSL" feel. Each is surfaced by a concrete `Metasprites.kt` line citation and has an inline `PHASE-13` annotation pre-seeded in the source file.

6. **Asset-driven metasprite frame import** — declarative `metasprite(asset("sprites/elephant.png"))` or `metasprite { sprite(asset(...)); fromPng2Asset() }` that walks the `png2asset` output at build time and synthesises the `frame { tile(dy, dx, dtile) }` blocks. Currently, tile **data** is auto-loaded from PNG via the asset pipeline, but per-frame **tile layouts** are hand-transcribed line-by-line from `png2asset`'s `sprite.c` output — 159 lines of `tile(8, 0, baseId)` (39% of `Metasprites.kt`). The asset pipeline integration is half-finished: data without layout. An author should never see `METASPR_ITEM(dy, dx, dtile, attr)` shapes in their Kotlin source. Surfaced at `Metasprites.kt:134–309`. Combined with item #4 (`MetaspriteBuilder.sprite()`), the entire 5-frame declaration should collapse to a single asset-binding line.
7. **`Color.rgb888()` / `Color.rgb555()` palette helpers** — hide the GBC `>>= 3` RGB888→RGB555 conversion math currently leaking into user palette declarations. Each of the four `spritePalette { }` blocks in `Metasprites.kt` ships with arithmetic-in-comments (e.g., `// 170 → 21`, `// 255 → 31`, `// >>= 3`) because the author had to convert the reference's RGB888 constants by hand and use the resulting `gbc(31, 0, 31)` magic triples. Both `Color.rgb888(255, 0, 255)` (auto-converting) and a `Color.gbc555(...)` raw form (for authors who want 0..31 directly) should be available; the helper hides which model the framework targets, and a single named constant (`Color.MAGENTA`) for primaries would absorb the most common values. Surfaced at `Metasprites.kt:95–122`. Eliminates ~28 lines of comment-arithmetic across just this one file.
8. **`damp(v)` / `easeToZero(v)` decay primitive** — replace hand-rolled "ease toward zero" ladders. `Metasprites.kt:397–401` writes the pattern four times: `whenever(spdY isBelow 0) { spdY++ } whenever(spdY isAbove 0) { spdY-- }` (then again for `spdX`). The file's own inline annotation at line 397 names this requirement: `// PHASE-13: candidate primitive — ladder pattern abstraction`. The primitive should be expressible as `damp(spdY)` or `spdY.easeToZero(by = 1)` in the frame handler and lower to the same generated C as today's expansion. Required by virtually every input-driven mover (simple-physics has the same pattern). Surfaced at `Metasprites.kt:397–401`.
9. **Wrap/cycle primitive for `u8Var` / `i8Var`** — eliminate hand-rolled modulo arithmetic on byte variables. `Metasprites.kt:366` (`whenever(idx isAtLeast NUM_FRAMES) { idx set 0 }`) and `Metasprites.kt:376` (`rot set (rot and 0xF)`) both express "wrap at N" by hand, and the author's defensive comment at `Metasprites.kt:81–83` documents **Pitfall 6** ("`idx` and `rot` MUST be `u8Var` (NOT `i8Var`) — unsigned context for wrap comparisons") — a piece of pitfall folklore that should be made impossible by the type system, not memorialised in comments. Two delivery options: declarative (`u8Var(0, wrapAt = NUM_FRAMES)` / `u8Var(0, wrapAtMask = 0xF)`) or fluent (`idx.cycle(NUM_FRAMES)` / `rot.cycleMasked(0xF)`). The declarative form is preferred because it pushes the wrap invariant into the variable's type, making "out-of-wrap" states unrepresentable. Surfaced at `Metasprites.kt:81–83, 366, 376`. Subsumes the Pitfall 6 documentation issue inherited from Phase 05.05.3 ergonomics work.

**Additional requirements (from Phase 12.2 close audit of banks + platformer-template — 2026-05-23):**

After Phase 12.2 closed terminally with `verdict=passed`, an audit of `Banks.kt` (111 lines) and `PlatformerTemplate.kt` (416 lines) surfaced 7 cross-port primitives — 4 with 3+-port reach (Tier 1) and 3 with 2-port reach (Tier 2). `PlatformerTemplate.kt` alone ships **16 `@Suppress("UNUSED_VARIABLE")` annotations** + 1 `cEmit()` escape hatch that emits a stderr WARNING at ROM-build time — neither is consistent with the "poster child for gbkt" framing. Inline citations below.

**Tier 1 — 3+ port reach:**

10. **`by zone { }` delegate** — eliminate the property-name-duplicated-as-magic-string in `val play = zone("play") { … }`. The DSL today lacks a `ZoneDelegate` analogous to `MetaspriteDelegate` (which exists). Surfaced at `Banks.kt:67` (`zone("play_zone") { … }`) and `PlatformerTemplate.kt:222-265` (5 zones, all string-form). Phase 12-16 SUMMARY explicitly defers this: "by zone { } delegate not yet implemented in gbkt-lang (no ZoneDelegate)". Confirmed cross-port — every existing and future port that declares a zone benefits. Subsumes SEED-014 Phase 11.1 substrate.

11. **Auto-sized `romBanks` / `ramBanks` from analyzed usage** — eliminate the magic `romBanks = N` value and its accompanying multi-paragraph allocation-math comment block. The framework already runs `BankingAnalysisPass` (gbkt-analysis), which knows how many zone banks, scene banks, and metasprite banks the game will need; the value should be derived, not hand-computed. Surfaced at `Banks.kt:42-46` (`romBanks = 4` with a 4-line rationale comment citing RESEARCH §BankingAnalysisPass on Small Games) and `PlatformerTemplate.kt:59-65` (`romBanks = 8` with a comment computing "HOME(0) + scenes(1) + zone banks 2..6 + title-card(7) margin"). Cross-port: every example today either hand-computes or undersizes. **Sister gap:** `CartridgeConfig.ramBanks` is currently NOT propagated to `gbkt-build.properties`, so authors must declare `ramBanks` in BOTH `build.gradle.kts` AND the DSL `config { }` block (`Banks.kt:45` + `banks/build.gradle.kts:40`) — the propagation fix is in-scope for this primitive.

12. **Delegate-unused-warning fix for `val/var by …`** — eliminate the `@Suppress("UNUSED_VARIABLE")` ceremony required on every property delegate that registers state via side effect (the delegate adds the var to the active builder, but the Kotlin compiler only sees an unread local). The delegate pattern exists to remove ceremony; currently it adds more. Surfaced at `PlatformerTemplate.kt` (16 instances across `var x by u8Var(...)`, `val z by metasprite { … }`, `val zone = zone("…") { … }`, scene refs, etc.) and `Banks.kt` (2 instances). Two delivery options: (a) `provideDelegate` returning a value the compiler treats as used, or (b) ship a custom `@MustBeDocumented` annotation that suppresses the warning class globally for the gbkt DSL package. The current state is the #1 ergonomic blocker for any port over ~100 lines.

13. **Unified `navigate(scene)` API** — eliminate the string-vs-ref inconsistency. **Tier 2 — 2-port reach:**

14. **Smart default `size(...)` for zones** — eliminate the dangerous `size(32, 32)` default that overwrites the tile array when the underlying tileset is smaller. `Banks.kt:67-73` declares `zone("play_zone") { tileset(asset("tiles/checker.png")); size(20, 18) }` — the explicit `size(20, 18)` is required because, per PATTERNS gotcha #6, the default 32×32 would write 1024 tile indices over the 4-byte checker tile array. ### Phase 13.6: sprite-pipeline transparency — route non-zero PNG tRNS color to GB OBJ index 0 in ConvertSpritesTask (INSERTED)

**Goal:** Make the sprite asset pipeline correctly honor a PNG's declared transparent color (tRNS) when it is NOT at palette index 0. Game Boy hardware forces 2bpp index 0 to be the transparent OBJ slot; `ConvertSpritesTask.buildPng2AssetArgs()` passes `-keep_palette_order` (Phase 12.9 D2a) which silently assumes the source PNG already has its transparent/background color at index 0. When a PNG declares tRNS on a non-zero index (e.g. `metasprites/res/sprites/elephant.png`: tRNS=4 white, outline at index 0), the outline color collapses into the transparent slot and renders see-through → the sprite loses its outline/border. The framework must route the tRNS color to GB index 0 regardless of source palette order, so a developer dropping in a normally-authored indexed PNG gets a correct sprite (core value prop: framework manages GB hardware, not the author).

**Origin:** Surfaced during Phase 13.3 post-close UAT. Full root-cause + proof experiment in `.planning/seeds/SEED-PHASE-13-SPRITE-OUTLINE-LOST-NONZERO-TRNS-INDEX.md` (PROVEN: reordering the palette so transparent→index 0 moves the outline to a visible index 1 at 17.9% of pixels). Compatible with — and must NOT revert — the 13.3-22/24 sprite-palette index-polarity fix (ascending ramps).

**Requirements**: NEW framework gap (not in the original Req #1–#18 catalog). Add to the Phase 13 umbrella catalog during spec/discuss.

**Depends on:** Phase 13 (and runs after 13.3/13.4/13.5 in the 13.x sequence — NOT urgent-next; 13.3 still owns terminal close).
