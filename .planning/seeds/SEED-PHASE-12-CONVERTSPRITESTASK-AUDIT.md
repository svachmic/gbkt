## Confirmed Defect (2026-05-24)

Phase 12.3-15 anchor 4 re-shoot surfaced the concrete defect this SEED preventively flagged:

**Symptom:** Player metasprite renders as a uniform dark checkerboard square in the platformer-template ROM; walk-cycle and hflip emission both work internally (walkFrameIdx cycles 0/1/2, facingRot=3 triggers OAMF_HFLIP) but no visible animation reaches the screen.

**Root cause:** `gbkt-examples/platformer-template/build/gbkt/generated/sprites/player.c` contains:
```c
/* Stub sprite data — generated by gbkt ConvertSpritesTask */
/* Replace with a valid PNG to get real sprite graphics */
const uint8_t player_tiles[64] = {
    /* placeholder tiles (4x 8x8 tiles, checkerboard pattern) */
    0xAA, 0xAA, 0x55, 0x55, ...  // checkerboard repeats
};
```

The PNG asset `gbkt-examples/platformer-template/res/graphics/player-character-gbapduck-sprites.png` IS valid duck art (visually verified — 12 frames of asymmetric duck poses), but `ConvertSpritesTask` emits the 64-byte stub instead of running png2asset on the PNG. The "Replace with a valid PNG" comment is misleading — the PNG is valid; the task isn't actually invoking the toolchain.

**Phase 12.3 emission impact:** ZERO. Phase 12.3's PlatformerVisitor walk-cycle + cameraOffsetX wiring + Phase 10.1-05 hflip emission all generate correct C. The bug is entirely downstream in the sprite asset pipeline.

**Evidence:** `.planning/phases/12.3-platformer-visitor-auto-emission-wiring-wire-input-playervx-/evidence/uat-screenshots/anchor4-*.png` show the checkerboard placeholder; the 4 MD5s are distinct but the visual content is indistinguishable to a human reviewer.

## Context

`ConvertSpritesTask` is the sister class to `ConvertZoneTilesetsTask`. They share the
same authoring style and were introduced in adjacent phases:

- `ConvertZoneTilesetsTask` — Phase 11.2 (tileset PNG → bank-2 byte array via png2asset)
- `ConvertSpritesTask` — earlier, parallel evolution (sprite PNG → metasprite byte array
  via png2asset, with related dedup / mirror modes)

The Defect 7 antipattern that Phase 12.2 removed was a synthetic-fallback emission
path: when no real tilemap PNG was supplied, `ConvertZoneTilesetsTask` modulo-tiled the
png2asset `_tileset_map` dedup table across a hardcoded 32×32 grid (
`gbkt-gradle-plugin/.../ConvertZoneTilesetsTask.kt` lines 432-439, pre-12.2). That
synthetic data shipped as if it were real tilemap bytes — silently producing wrong
output.

`ConvertSpritesTask` MAY carry an analogous synthesis-fallback antipattern (e.g., a
modulo-tiled byte producer when the sprite asset is absent or malformed). No defect is
known today, but the structural similarity warrants an audit.

## What's Deferred

Read `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt`
end-to-end and identify any synthesis-style fallback code paths. Heuristics for the
audit:

- Search for `% (?:mapTileW|mapTileH|spriteW|spriteH)` style modulo arithmetic that
  fabricates byte data.
- Search for hardcoded fallback grids (`for (y in 0 until X) for (x in 0 until X)
  byteArray += ...`).
- Search for branches that emit "default" or "placeholder" sprite data when an asset
  is missing instead of throwing a Gradle exception.

If a synthesis path is found:

- Confirm whether it produces CORRECT output for all known fixtures (Pong, Breakout,
  Banks, Explorer, platformer-template, simple-physics, metasprites, metasprites-stress).
- If correct: document the rationale inline with a KDoc and add a sentinel test (mirror
  Phase 11.2's `INV-8` pattern).
- If incorrect: either DELETE the synthesis path (mirror Phase 12.2's full-delete) and
  add a fail-fast diagnostic, OR replace with a real png2asset extraction path.
