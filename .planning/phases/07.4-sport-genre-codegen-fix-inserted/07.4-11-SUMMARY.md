# Phase 07.4 Plan 11: SportVisitor enterOps emission — pool spawn, track tileset+tilemap, camera bind Summary

**Extends `SportVisitor.visitRacingNew` to populate `GenreVisitorResult.enterOps` for the bound race scene with three op groups closing GAP-A (AI pool spawn), GAP-B (track tileset + tilemap load + sentinel), and GAP-D (camera target bind). ## Accomplishments

### Op groups emitted into enterOps[raceSceneId]

For each `Vehicle` in `resolvedAiVehicles`, the rival actor's `position(...)` from `gameIR.actors` flows into `pool_<aiVehicleId>_spawn(<rivalX>u, <rivalY>u);`. The existing pool spawn helper (already shipped by Plan 07.3 via `GBDKSystemVisitor.buildActorPoolFunctions`) sets `_active[i]=1u`, writes `_x[i]/_y[i]`, and calls `move_sprite()` — so one RawOp per AI slot is sufficient (D-13 — no helper duplication).

Tileset+tilemap load:
- `set_bkg_data(0, 3, _racing_<id>_tileset);` — DMA the 3 builtin tiles into VRAM bg slots 0..2.
- `set_bkg_tiles(0, 0, <mapW>u, <mapH>u, _zone_<id>_tiles);` — paint the synthesized tilemap (already exists in `zone_bank2.c` per Plan 04) onto the BG layer at origin. Dimensions read from `gameIR.zones.firstOrNull { it.id == racingId }.mapWidth/mapHeight` — no hard-coded 19/20.
- `_current_tileset_id = 1u;` — sentinel matching the dungeon path's tileset-loaded convention (see Decisions §1 below for why this is kept, not redundant).

Camera target bind:
- `_camera_target = <playerActorIdx>u;` where `playerActorIdx = gameIR.actors.indexOfFirst { it.id == playerActorId }`. The `_camera_target` global is declared by `GBDKSystemVisitor`'s camera codegen but was never assigned previously — this RawOp closes the D-06 contract.

### Builtin track tileset constant

48-byte hand-tuned 3-tile tileset emitted as `const UINT8 _racing_<id>_tileset[48]`:
- Tile 0 — WALL: 16 bytes of 0xFF (solid black square).
- Tile 1 — DRIVABLE: 16 bytes of 0x00 (open white/light square).
- Tile 2 — GRASS: alternating 0x55 / 0xAA per row (visually distinct dotted pattern).

Tile indices match TrackSynthesizer's constants (Plan 07.4-04). The CVarDecl uses `CArray(CConst(CU8), 48)` so GBDK places the constant in ROM, not RAM.

### Op ordering (asserted by Test 7)

Within `enterOps[raceSceneId]`:

```
_camera_target = 0u;                                               (GAP-D)
set_bkg_data(0, 3, _racing_track1_tileset);                        (GAP-B)
set_bkg_tiles(0, 0, 19u, 19u, _zone_track1_tiles);                 (GAP-B)
_current_tileset_id = 1u;                                          (GAP-B sentinel)
pool_carAi_spawn(80u, 96u);                                        (GAP-A)
```

Camera bind first → tileset/tilemap → AI spawn. VRAM is correct before any sprite becomes visible, and the camera knows its target before the first frame tick reads `_camera_target`.

## Decisions Made

1. **Kept `_current_tileset_id = 1u;` RawOp — NOT dropped.** Per the plan's read_first instruction, executor confirmed by reading `GBDKPipelineV2.addTilesetGuardToEnterFunction` (lines 1303-1326). The guard fires only when `scene.tilesetRef` is non-null on the SceneIR (`val tilesetId = scene.tilesetRef?.let { tilesetIdMap[it.path] }; if (tilesetId != null) addTilesetGuardToEnterFunction(...)` at line 1232-1234). Racer.kt:134-154 declares the race scene with no `tileset(...)` call, so `scene.tilesetRef` is null and the guard does NOT inject the sentinel write. Without Plan 11's RawOp, `_current_tileset_id` stays at its initial `0xFF` after race_enter, and the next scene transition to results would re-evaluate the tileset state with stale info. Value `1u` mirrors the dungeon path's convention where `buildTilesetIdMap` assigns sequential ids starting at 1 (with 0xFF reserved for "no tileset loaded"). If a future plan adds `tileset(asset(...))` to the race scene's DSL, the guard will fire and Plan 11's sentinel write becomes redundant — but for Plan 07.4 it is load-bearing.
2. **No new ScriptOp type added.** Used `RawOp` for all five RawOp emissions (camera, set_bkg_data, set_bkg_tiles, sentinel, pool_spawn). Per D-01, no new IR nodes. Per Plan 05's pattern for `racing_tick_<id>();`, RawOp is the documented escape hatch for literal C call sites that don't have a typed ScriptOp.
3. **Op ordering: camera → tileset → pool spawn.** Camera target is set first because the camera follow logic reads `_camera_target` once per frame; if the AI spawns first, the OAM would briefly show the AI sprite at its initial position before the camera correctly centers on the player. Tileset/tilemap loads precede pool spawns so the BG layer is correct before sprites become visible. The plan's `<must_haves.truths>` block specified this exact order ("emitted in this order so the runtime VRAM is correct before any sprites become visible") — Plan 11 honors it, and Test 7 locks it.
4. **`CArray(CConst(CU8), 48)` for the builtin tileset.** Required for GBDK to place the 48-byte constant in ROM (not scarce 8KB RAM). Without `CConst`, the array would land in `_DATA` segment and consume RAM.
5. **playerActorIdx via `indexOfFirst`, not a hard-coded 0.** Plan 03's RacingDelegate currently leaves the actor list in declaration order, so for Racer.kt (where car is declared before rival) playerActorIdx == 0. But the codegen reads the index dynamically so any future analysis pass that re-orders actors (e.g. for OAM allocation grouping) will still produce a correct `_camera_target` write.
6. **Multi-AI declared order preserved by iteration order.** `for (aiVehicle in resolvedAiVehicles)` iterates the resolved list from Plan 03's RacingDelegate, which itself preserves the order of `aiOpponents(...)` calls. Test 2 explicitly asserts `idxA in 0 until idxB` for two AI vehicles to lock this against future changes.
