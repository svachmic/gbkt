### Why the lap-completion test legitimately keeps seeding

The lap-completion test is a focused probe of the lap-completion bookkeeping inside `racing_tick_track1` (D-15 invariant: lap counter advances iff visited bitmap holds the all-checkpoints-set value AND the car is within the 8 px proximity box of CP 0). Driving the car through every checkpoint in declared order across the corridor would require ~80-100 emulator frames per test — every wall-time second of the JVM-tier test suite is a multiplier on developer iteration cost.

Plan 07.4-12's wall-collision guard would in principle make a long-form natural-play test feasible — the car can now drive the corridor without underflowing — but that does not change the cost-benefit analysis: the contract under test is the bitmap state machine, not the throttle integrator.

The seeding now touches only 3 variables instead of 5 (LAP_COUNT and CHECKPOINT_IDX were redundant no-ops because main.c's initialiser already sets `_racing_lap_count_track1 = 0u;` and `_racing_checkpoint_idx_track1 = 0u;`). Each remaining seed is annotated inline with a `SEEDING JUSTIFICATION:` comment.

@Test

    game.bootToScene("race")
    val before = game.readVariable(CAR_Y)

Both tests reach assertions with zero seeding — the natural ROM execution path drives the precondition.

## Decisions Made

1. **Did NOT delete the existing 4 tests.** Only test 4 (lap-completion) had writeVariable seeding; tests 1-3 were already natural-play. The plan's `Tests that should NOW be reachable from natural play` heuristic does not require deleting clean tests — it requires that previously-seeded preconditions become natural-play assertions, which is achieved by ADDING new tests.

2. **Added 4 NEW natural-play tests instead of refactoring.** The 4 NEW tests precisely target the runtime preconditions established by Plans 07.4-11 (AI pool / tileset / camera) and 07.4-12 (held-UP bound check). These were not assertions in the original 4-test net; they are now first-class assertions.

3. **Dropped 2 redundant writeVariable seeds (LAP_COUNT, CHECKPOINT_IDX).** Both initialise to 0u in main.c — the seeds were no-ops. This is `quality over shortcuts` taken further than the plan strictly requires: not just removing seeds that became natural, but also removing seeds that were never necessary.

4. **Inline `SEEDING JUSTIFICATION:` comments.** The plan's machine check (`writeVariable count <= JUSTIFICATION count`) is strict. To pass it cleanly AND make the file maximally readable, each remaining writeVariable call has its own one-line annotation immediately above it, in addition to the multi-paragraph block at the top of the test method.

5. **Used uppercase Kotlin consts for the new symbol names.** Matches the existing const-companion convention (SPEED_CUR, CAMERA_X, LAP_COUNT). Avoids inline magic strings — every variable name is a named constant.

6. **Did NOT regenerate Racer.kt or production sources.** Plan acceptance criteria explicitly require 0 production-code drift. Confirmed via `git diff --name-only` against gbkt-examples/racer/src/main/, gbkt-genre-sport/, gbkt-backend-api/, gbkt-backend-gbdk/ — all return 0 lines.
