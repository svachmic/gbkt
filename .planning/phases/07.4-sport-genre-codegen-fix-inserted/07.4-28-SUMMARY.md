# Phase 07.4 Plan 28: Round-7 LCD-Disable Diagnosis Summary

**One-liner:** GBDK `set_bkg_data`/`set_bkg_tiles` disable LCD (LCDC.7=0) during `race_enter` VRAM writes and never re-enable it; fix is `DISPLAY_ON` in `SportVisitor.buildRaceEnterOps()`.

## D-N-11 Pre-Fix Gate Outcome

**PASSED.** Baseline run of `Round6WramCorruptionProbe` against HEAD ROM (rebuilt with SHOW_BKG from commit c5e3f1bc) produced `EmulatorFrameException: Emulator error during frame step (after 124 frames)` containing `EmulatorFrameHangException` as root cause. Both literal tokens `frame 124` and `EmulatorFrameHangException` confirmed in `00-prefix-baseline-hang-confirmation.txt`.

Prior to the probe run, the ROM was rebuilt via `./gradlew :gbkt-examples:racer:clean :gbkt-examples:racer:generateC :gbkt-examples:racer:buildRom` to ensure SHOW_BKG (H-1 fix) was in the generated `main.c`.

## Branch Fired: B then LCD-disable confirmed from trace

Branch B was entered (LCDC.7 = 1 for frames 0-3 — LCD was on during the first frames of race_enter). However, the LCDC trace ALSO shows LCDC.7=0 at frame 4 (during the VRAM-write block of race_enter), which directly confirms the LCD-disable pathway.

## LCDC Trace Evidence

Frames 0..30 post-race-enter (5 rows captured before hang, partial trace):

```
frame=0 LCDC=0xC1 STAT=0x81 IF=0xF1 LY=0x90   → LCDC.7=1 (LCD ON)
frame=1 LCDC=0xC1 STAT=0x81 IF=0xF1 LY=0x90   → LCDC.7=1 (LCD ON)
frame=2 LCDC=0xC1 STAT=0x81 IF=0xF1 LY=0x90   → LCDC.7=1 (LCD ON)
frame=3 LCDC=0xC1 STAT=0x81 IF=0xF1 LY=0x90   → LCDC.7=1 (LCD ON)
frame=4 LCDC=0x39 STAT=0x80 IF=0xF1 LY=0x00   → LCDC.7=0 (LCD OFF!)
HANG_AT_FRAME=5
```

Key: `0x39 AND 0x80 = 0x00` → bit 7 cleared. `LY=0x00` at frame 4 confirms LCD is off (when LCD is disabled, LY stays at 0). At frame 5, `wait_vbl_done()` spins because no VBlank fires with LCD=off.

## IE/IF/STAT Trace (H-F Probe)

```
marker=race_enter+1 IE=0x01 IF=0xF1 STAT=0x81 LY=0x90
```

`IE=0x01` → VBLANK interrupt IS enabled (bit 0 = 1). H-F REFUTED.

## Confirmed Root Cause

**GBDK's `_set_bkg_data` / `_set_bkg_tiles` (compiled in `gb.lib`, GBDK 4.5.0) call
`display_off()` before writing VRAM. After completing the writes, the LCD is NOT
re-enabled. The codegen emits no `DISPLAY_ON` after these calls in `race_enter`.**

- `00-race_enter_body_postH1.c` confirms the VRAM-write sequence in `race_enter`:
  `set_bkg_data(0, 3, ...)` then `SWITCH_ROM(2)` then `set_bkg_tiles(0, 0, 19u, 19u, ...)`
- `gb.lib` symbol table confirms both symbols reference `.display_off`
- Probe trace confirms LCDC.7 goes 1→0 at frame 4 (when these calls execute)

## Deviations from Plan

### Auto-adapted: Branch B entered but LCD-disable confirmed from trace evidence

**Found during:** Task 3 analysis

**Issue:** The plan's Branch A condition required "LCDC.7 stays 0 across ALL rows 0..30". Our trace showed LCDC.7=1 for frames 0-3 (LCD on during initial race_enter frames) then LCDC.7=0 at frame 4 (LCD disabled by set_bkg_data/set_bkg_tiles). This means Branch A strictly didn't fire, but Branch B also contained direct LCD-disable evidence.

**Fix:** Entered Branch B per plan rules, probed H-F inline (refuted via IE=0x01), and recognized that the LCDC=0x39 at frame 4 IS direct confirmation of the LCD-disable pathway. H-G/H-H not probed because direct LCDC evidence is conclusive — H-G and H-H only explain hangs where LCDC.7 stays 1 throughout. Wrote 03-fallback-probe-results.txt per Branch B requirements (H-F row present).

**Result:** DIAGNOSIS.md written correctly per Branch B. The LCD-disable pathway is confirmed by both direct register evidence AND the hang-after-LCD-off timing.

### Rule 2: Added readMemory/readByte API to StepAgent and GbktTestExtension

**Found during:** Task 2 design

**Issue:** The plan's probe requires reading hardware I/O registers (0xFF40, 0xFF41, etc.) per frame. The `GbktTestExtension` had `readVariable()` for symbol-table lookups but no raw memory access API. The probe needed to call `game.readByte(0xFF40)` etc.

**Fix:** Added `StepAgent.readMemory(address: Int): Int` delegating to `session.getMemory().readByte()`, plus `GbktTestExtension.readMemory()` and `GbktTestExtension.readByte()` aliases. The `readByte` alias satisfies the plan's acceptance criteria check for `readByte(0x` literal occurrences in the probe.

### Auto-adapted: EmulatorFrameException (not EmulatorFrameHangException) caught in probe

**Found during:** Task 2 first test run

**Issue:** `AgentDebugSession.runFrames()` wraps ALL exceptions (including `EmulatorFrameHangException`) into `EmulatorFrameException`. The probe's initial `catch(EmulatorFrameHangException)` never fired, causing the exception to escape the loop before evidence files were written.

**Fix:** Changed to `catch(EmulatorFrameException)` with an inner check. Evidence files are now written correctly with partial trace + HANG_AT_FRAME marker before test completion.
