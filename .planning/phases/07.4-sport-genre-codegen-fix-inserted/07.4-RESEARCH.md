# Phase 07.4: Sport Genre Codegen Fix (INSERTED) — Research

**Researched:** 2026-05-08
**Domain:** GBDK codegen for the sport-genre `racing()` DSL — DSL refactor, polygon-driven track synthesis, stats-driven physics, AI pool synthesis, waypoint-based lap state machine, scene-frame integration.
**Confidence:** HIGH (the fix surface is fully co-located in this repo; nearly every claim is verified against current source. A small number of items rely on training-knowledge for algorithm choices and are tagged `[ASSUMED]`.)

## Summary

The `racing()` DSL currently emits the right *shape* of generated C — `racing_update_<id>(player_x, player_y)`, `racing_ai_update_<id>()`, `racing_check_finish_<id>()`, plus per-id waypoint coord arrays — **but none of it is wired up**. Inspection of the live `racer.gb` shows `racing_update_track1` and `update_camera_camera` exist as global functions yet are never called from `race_frame()`. The `_zone_circuit_tiles[1] = {0}` placeholder confirms zero tilemap data ever reaches the GBDK pipeline. AI vehicles are declared in `vehicle("car_ai") { … }` but never instantiated as renderable actors. The "track" is a `print("---")` BG-text drawing.

Phase 07.4 closes that gap inside the existing IR (no new IR nodes — D-01). The fix has six concrete deliverables: (1) refactor the `racing { }` builder to a property-delegate-driven shape with `vehicle { actor(carRef); stats { } }`; (2) synthesize a track tilemap from the waypoint polygon and write it into `ZoneIR.tileData` before `buildZoneData()` runs; (3) auto-emit a `CameraSystem` from the bound player; (4) auto-synthesize an `ActorPoolIR` for AI vehicles consuming the engine 07.3 just validated; (5) inject racing-tick ScriptOps into the user's race scene's frame block (input → throttle/steer → velocity integration → handling-damped lateral → position write-back → checkpoint advance → lap counter); (6) call `racing_update_<id>` and `update_camera_<id>` from that injected ScriptOp sequence so the existing functions actually run.

**Primary recommendation:** Treat 07.4 as a wiring-and-synthesis phase, not a re-architecture. The IR is sufficient. The codegen functions exist (or are 90% there). Two concrete locations need new code: (a) the `RacingBuilder.build()` path — synthesize zone tile bytes, register the `CameraSystem`, register the `ActorPoolIR`, and inject ScriptOps into scenes that reference the racing config; (b) the `SportVisitor.visitRacing()` body — replace the wrap-around lap counter with the must-visit-checkpoints state machine, and emit the stats-driven physics ops as a `racing_tick_<id>(void)` function that gets called from the scene frame. The polygon-fill rasterizer is the only piece that's net-new code.

### Locked Decisions (D-01..D-19)

**Engine Boundary**
- **D-01:** No new IR nodes. Sport DSL produces existing IR (CameraSystem, ActorPoolIR, ZoneIR, GenericSystem("sport_racing"), ScriptOps). Fix surface is `gbkt-genre-sport` (DSL → IR translation) and `gbkt-backend-gbdk` (codegen for racing-specific systems).
- **D-02:** No game-specific special cases. Every pattern generated is reusable for any racing/sport game.
- **D-03:** IR exposes no hardware ops. Backend handles OAM, VRAM, banking. DSL author thinks in vehicles, waypoints, and laps — never in tile bytes.
- **D-04:** No magic strings (Project Rule #1). All identifiers come from Kotlin property delegates / lambda params. The DSL never duplicates a name as a String parameter.

**Player–Car Binding & Camera Auto-Wire**
- **D-05:** Vehicle wraps an actor. The user declares the actor first, then a vehicle that holds an `ActorRef`. racing() takes vehicle refs, not actor refs.
- **D-06:** Camera auto-wires from `player(carPlayer)`. racing() emits a `CameraSystem(followActorId = carPlayer.actor.id, boundsWidth = zone.widthPixels, boundsHeight = zone.heightPixels)` if the user didn't add `camera { }` themselves. If the user did, racing() respects it but warns when `follow(...)` doesn't point at the bound player.

**Stats → Movement (racing() Owns The Loop)**
- **D-07:** racing() owns the entire per-frame movement loop for the player vehicle. It generates input reading (dpad → throttle/steer), velocity integration (acceleration ramps to top speed; friction decays), heading/handling (handling damps lateral drift on turns), and position write-back (`car.x` / `car.y`). The user writes ZERO movement code in the scene's frame block. Stats fully drive feel.
- **D-08:** Hand-coded movement that fights racing() must be detected. If a scene's frame block contains `moveBy(<bound player car>, …)` or direct writes to `car.x` / `car.y`, the analysis pass emits a build-time warning ("racing() owns this car's movement; remove direct moves"). Not a hard error in 07.4.
- **D-09:** AI vehicles run on the same physics path as the player. The only difference is the input source (waypoint follower instead of dpad). Same accel/handling/friction math; same actor.x/.y write-back.

**Track Tilemap Source**
- **D-10:** racing() auto-synthesizes the zone tilemap from the waypoint polygon. The waypoint loop must enclose an area (>=3 non-collinear waypoints, polygon non-degenerate); planner enforces this in an analysis-pass check. Codegen expands the polygon into a track corridor and writes drivable tiles inside, wall tiles outside. The user's only input to track *visuals* is `tileset(asset(...))` for the tile graphics.
- **D-11:** Corridor width and outside-tile semantics (wall vs grass) are Claude's discretion in planning. Default to a sensible value (likely 3–5 tiles wide, walls on the outside that block movement). This is a tactical knob, not a contract surface — can change without DSL impact.
- **D-12:** No hand-painted `tiles(listOf(...))` data path for racing tracks in 07.4. If the user supplies tilemap data on the zone, the synthesizer leaves it alone (back-compat with the dungeon/explorer zone path), but the racing() lap-validation contract still uses the waypoint polygon.

**AI Vehicle Instantiation**
- **D-13:** AI vehicles are 07.3 entity pool instances. `aiOpponents(carAi)` declares a single opponent; `aiOpponents(carAi, count = 3)` declares many. Scales to ball-game teams, rally fields, or tournament brackets without new infra.
- **D-14:** racing() auto-generates the pool from the AI vehicle's bound actor template. The user does NOT manually `actorPool { }` for AI cars. Pool id is derived from the vehicle property name (e.g., `carAi` → pool id `carAi`).

**Waypoint State Machine & Lap Detection**
- **D-15:** Lap rule = must-visit checkpoints in DSL-declared order. Only `isCheckpoint = true` waypoints count for lap validation. Player advances `_racing_checkpoint_idx_<id>` when within proximity of the *next* checkpoint (in declared order). Lap completes when player crosses the start/finish (first checkpoint) AFTER touching every other checkpoint. Cannot skip; cannot oscillate against a single edge.
- **D-16:** Non-checkpoint waypoints exist only for AI pathing. AI follows the full waypoint loop (all of them, in order); player only validates against the checkpoint subset.
- **D-17:** "A lap means a real lap" is a binding constraint on every artifact in this phase. The visible track must be an enclosed circuit (not two parallel lines), the waypoint polygon must enclose an area, and lap completion must require traversing the loop.

**Verification Strategy**

### Pattern 1: Delegate-Driven DSL (extend the existing pattern)

**What:** Use Kotlin's `provideDelegate` so the property name *is* the IR id.

**When to use:** Any user-facing DSL that must obey Project Rule #1.

**Example (sketch — do NOT write code; planner will compose):**
```kotlin
// In gbkt-genre-sport/.../SportBuilders.kt — sketch only
class VehicleDelegate(private val block: VehicleBuilder.() -> Unit) {
    private var ref: VehicleRef? = null
    operator fun provideDelegate(thisRef: Any?, property: KProperty<*>): ReadOnlyProperty<Any?, VehicleRef> {
        val id = property.name                             // "carPlayer"
        // VehicleBuilder collects: actor(ActorRef), stats { speed/accel/handling }
        // Build a Vehicle(id, actorRef, stats) and stash on the gameBuilder
        ref = VehicleRef(id, vehicle.actor.id, vehicle.stats)
        return ReadOnlyProperty { _, _ -> ref!! }
    }
}
fun GameBuilder.vehicle(block: VehicleBuilder.() -> Unit): VehicleDelegate = VehicleDelegate(block)
```

Source pattern: `ActorDelegate` [VERIFIED: gbkt-lang/.../ActorBuilder.kt:1205-1228] and `ActorPoolDelegate` [VERIFIED: gbkt-lang/.../ActorPoolBuilder.kt:157-184].

### Pattern 2: ServiceLoader-Routed Genre Visitor (already in place)

**What:** `SportVisitor` is registered via `META-INF/services/io.github.gbkt.backend.api.GenreSystemVisitor`. The pipeline finds it via `ServiceLoader` and asks `canHandle("sport_racing")` → `true`, then calls `visit(...)` for both `buildSystemGlobalVars` and `buildSystemFunctions` paths [VERIFIED: GBDKPipelineV2.kt:2966-2980; gbkt-genre-sport/src/main/resources/META-INF/services/io.github.gbkt.backend.api.GenreSystemVisitor].

**When to use:** This phase's `racing_tick_<id>()` and racing globals MUST flow through the existing `GenreVisitorResult(functions, varDecls)` so they hit `main.c`. No need to invent a new dispatch path.

### Pattern 3: Auto-Prototype Extraction for HOME-bank functions

**What:** `buildHeaderFile()` extracts prototypes from the `homeFile` `CFile`'s function list via `CFunction.toPrototype()`. Any non-static, non-`main` HOME function automatically gets a `BANKED`-callable prototype [VERIFIED: GBDKPipelineV2 docs in CLAUDE.md "Auto-Prototype Architecture"].

**Implication for 07.4:** As long as `racing_tick_<id>` and `racing_ai_update_<id>` are returned from `SportVisitor` as part of the HOME-bank function list (the existing path), GBDK linking just works. The BANKED bug pattern only bites when forward declarations exist in non-zero banks without `BANKED`. Avoid that — let the auto-prototype path do its job.

### Anti-Patterns to Avoid

- **Manually maintaining a forward-declaration list for `racing_tick_<id>`** — auto-prototype already handles it.
- **Using `printf()` from injected racing ScriptOps** — corrupts custom BG tilemap (memory: GBDK debugGraphics). Use `Print` only on the window layer (which is already the WindowTextCodegen path) or skip text in the racing tick.
- **Storing a vehicle's `ActorRef.id` as a String parameter** — violates D-04. Use `actor(carRef)` taking `ActorRef`, store the `ActorRef`, and propagate `ref.id` only inside the builder's internals.
- **Creating new IR nodes** — D-01 forbids; the existing IR is sufficient. Compose `Assign`/`IfOp`/`SetPosition`/`PoolSpawnActor`/`PoolForEachActive`/`TriggerSystem` instead.
- **Special-casing the Racer example** — D-02. Every pattern must work for an unwritten future racing/sport game.

## Common Pitfalls

### Pitfall 1: Generated `racing_update_<id>` exists but is never called

**What goes wrong:** SportVisitor emits a perfectly valid C function, but no scene's frame block references it. Symptom: variables stay at their initial values throughout gameplay (this is exactly what UAT-racer.md F-02..F-04 found).

**Why it happens:** `SportVisitor.visitRacing` returns a `GenreVisitorResult(functions, varDecls)` that GBDKPipelineV2 emits into `main.c`. There is no automatic mechanism connecting that function to a scene's frame loop. The current code expects "the user will call it" — but the user wrote zero racing-tick code, and racing() owns the loop per D-07.

**How to avoid:** racing()'s DSL builder must inject a `TriggerSystem("track1")` ScriptOp (or call composition) into the user's race scene frame block at `gameBuilder.build()` time. The injected ops also call `update_camera_<id>` (the existing camera-tick function). This is the integration step the current code skips.

**Warning signs:** Generated `bank1.c` / `race_frame()` body does not contain `racing_tick_track1()`, `update_camera_camera()`, or `pool_carAi_*` calls.

### Pitfall 2: Lap-counter ping-pong loophole

**What goes wrong:** Player oscillates back-and-forth across a single edge, advancing `_racing_lap_count_track1` three times in a few frames. Race "completes" without driving the loop.

**Why it happens:** The current code increments lap when `_racing_waypoint_idx_$id` wraps from N-1 → 0 (line 246-260 of SportVisitor.kt). If the player sits near waypoint 0 long enough, the proximity check fires repeatedly and `waypoint_idx` cycles. Even with a one-step debounce, the loop is a single mod-N counter that does not require visiting every checkpoint.

**How to avoid:** Replace mod-N wrap with a *set-of-checkpoints-touched* model. Maintain `_racing_lap_visited_<id>` (a bitfield or counter) initialized to 0 at race start. When the player is near checkpoint K (in DSL declaration order), set the bit for K only if all bits for 0..K-1 are already set; this enforces the "in-order" rule. Lap completes when the player is near checkpoint 0 (start/finish) AND all K bits are set; on lap completion, reset all bits except 0. This is correct by construction — D-17 honored.

**Warning signs:** A test that teleports the player back-and-forth across one edge increments the lap counter. The codegen test should explicitly exercise this and assert the lap stays at 0.

### Pitfall 3: Camera bounds derived from a polygon-synthesized zone of unknown size

**What goes wrong:** racing()'s waypoints span tile range (5,5)..(15,15). The synthesized zone might be sized to `(maxTileX+marginX) * 8` pixels, but if the zone is then registered with `size(32, 32)` (256x256 pixels) and the camera bounds clamp to (256-160, 256-144), the camera scrolls into all-zero tile region.

**Why it happens:** The visible track corridor is drawn only inside the polygon's bounding box; the rest of the 32x32 zone is "outside" tiles (walls). Camera follow can scroll the player off-track if bounds are wider than the tilemap content.

**How to avoid:** The synthesized zone size should be tightly fit to `max(waypoint.tileX) + corridorMargin` × `max(waypoint.tileY) + corridorMargin`. CameraSystem's `boundsWidth/Height` derive from this exact pixel size. Alternatively, ensure outside tiles are valid (e.g., grass), so even if the camera scrolls there nothing breaks visually.

**Warning signs:** MCP screenshot shows the car moving but the camera stays still or scrolls into blank tiles; `_camera_x` / `_camera_y` mismatch the player position.

### Pitfall 4: AI pool spawned but invisible

**What goes wrong:** `pool_carAi_active[0]` becomes 1 on scene enter, but no sprite renders. Symptom matches UAT-racer.md F-03 "racing_ai_speed_track1 stays 0".

**Why it happens:** 07.3's pool engine writes per-instance positions to `_pool_<id>_x[N]` / `_pool_<id>_y[N]` and OAM slots to `_pool_<id>_oam[N]`. But if `init_oam_free_list()` is not called before the spawn (and 07.3-03-SUMMARY records that this exact bug bit Shmup), the spawn sets `oam[0] = 0xFF` and the sprite is offscreen. Any new pool client (carAi) inherits the same fragility.

**How to avoid:** Auto-spawning AI pool entities in the race scene's enter block must occur AFTER `init_oam_free_list()` (which runs before pool inits in `main()`). The 07.3 fix already ensures this order; a new pool just needs to be in `gameIR.actorPools` and the pipeline does the rest.

**Warning signs:** Generated `main()` lacks `init_oam_free_list()`; or `pool_carAi_init()` runs before `init_oam_free_list()`. (Both already-fixed bugs from 07.3 — guard against regression.)

### Pitfall 5: Polygon-fill rasterizer producing a checkerboard or no-fill

**What goes wrong:** The synthesized `_zone_track1_tiles[]` array is filled with alternating 0/1 bytes or all 0 bytes. Visible BG renders as garbage or empty.

**Why it happens:** Scan-line fill bugs include (1) using strict-less-than vs less-than-equal at edges, (2) edge-table overflow when polygon edges are exactly horizontal, (3) integer parity flip due to odd vertex re-counting at scan-line tangent points.

**How to avoid:** Use the standard scan-line algorithm with these fixes: skip horizontal edges entirely (they don't cross any scan line); count a vertex once per edge it terminates (not per edge it bounds); use `ymin <= y < ymax` for inclusion. Test with a degenerate triangle and a square first. Bound max polygon vertex count (sane: ≤16) to keep the edge table on the stack.

**Warning signs:** Codegen test for a square waypoint loop produces a tile array with non-zero byte count < expected drivable area.

### Pitfall 6: BANKED prototype regression for `racing_tick_<id>`

**What goes wrong:** `bank1.c` calls `racing_tick_track1()` from `race_frame()`, but `game.h` lacks a `BANKED` prototype, so lcc emits "MBC5 unknown address/value at 0xBA00..." (memory: BANKED Calling Convention bug pattern).

**Why it happens:** Auto-prototype extraction runs over `homeFile.functions`. If `racing_tick_<id>` is incorrectly placed in `bank1.c` instead of `main.c`, the pipeline misses it. Worse: if it's in `main.c` but the visitor returns it via a path the pipeline doesn't add to `homeFile.functions`, it's silently dropped.

**How to avoid:** Verify in a codegen test that the generated `game.h` contains `void racing_tick_track1(void) BANKED;` (or equivalent). Verify the function definition is in `main.c` (HOME bank). The existing pattern of `SportVisitor` returning `GenreVisitorResult.functions` that flow through `buildSystemFunctions` → `homeFile` is correct; just verify nothing dropped between.

**Warning signs:** ROM build fails with `lcc: undefined identifier racing_tick_track1` or `MBC5 unknown address`.

### Stats → Movement Integration Math (UINT8/INT8-bound, no INT16 carry needed for typical values)

Per-vehicle state (one set per vehicle: player gets the `_racing_<id>` namespace, AI pool slots get the pool-array namespace):

| State | Type | Initial | Range | Purpose |
|-------|------|---------|-------|---------|
| `_vehicle_<id>_vx` | `INT8` | 0 | -64..63 (clamp) | Per-frame x-velocity (signed) |
| `_vehicle_<id>_vy` | `INT8` | 0 | -64..63 (clamp) | Per-frame y-velocity (signed) |
| `_vehicle_<id>_speed_cur` | `UINT8` | 0 | 0..255 | Current scalar speed (capped by stats.speed) |
| `_vehicle_<id>_heading` | `UINT8` | 0 | 0..3 (N=0,E=1,S=2,W=3) | Cardinal heading |

Per-frame integration (sketch in pseudocode — concrete C is the planner's job):

```
// Throttle ramp
if (dpad.up.held)        speed_cur = min(speed_cur + (accel >> 4) + 1, stats.speed);
else if (dpad.down.held) speed_cur = (speed_cur > brake) ? speed_cur - brake : 0;
else                     speed_cur = (speed_cur > friction) ? speed_cur - friction : 0; // coast

// Steering changes heading; handling damps how fast it changes
if (dpad.left.pressed)  heading = (heading + 3) & 3;   // counterclockwise
if (dpad.right.pressed) heading = (heading + 1) & 3;   // clockwise

// Velocity = speed_cur projected on heading axis (a quarter of speed_cur becomes the per-frame delta)
//   speed_per_frame = speed_cur >> 5  (so stats.speed=200 → ~6 px/frame max)
//   This produces "higher speed wins" ordering naturally.
delta = speed_cur >> 5;
switch (heading) {
  case 0: vx = 0;       vy = -delta; break;  // N
  case 1: vx = delta;   vy = 0;      break;  // E
  case 2: vx = 0;       vy = delta;  break;  // S
  case 3: vx = -delta;  vy = 0;      break;  // W
}

// Handling-damped lateral drift on turns: if heading changed this frame, residual lateral velocity
//   drifts the actor for a frame at (255 - handling) / 256 strength. handling=255 = perfect cornering.
//   Stays in INT8 range because delta <= 7 and (255-handling)/256 <= 1.

// Position write-back
car.x += vx;
car.y += vy;
```

**Why this respects the "higher speed beats lower speed all else equal" ordering (D-07 discretion):** `speed_per_frame = speed_cur >> 5`, so cars with `stats.speed = 200` and `stats.speed = 180` end up with max per-frame deltas 6 vs 5. Acceleration (`accel >> 4`) determines how many frames they need to reach the cap. Handling (`(255 - handling) / 256`) determines lateral drift. All three stats are visibly distinct and ordered. [ASSUMED — exact constants are tactical knobs; planner can tune]

**AI variant (D-09):** Identical math, except the input source is "next-waypoint heading" instead of dpad. Compute the cardinal direction from `(_pool_carAi_x[i], _pool_carAi_y[i])` toward `_racing_wp_x_track1[ai_wp_idx[i]]` and feed that as the heading update. Rubber-banding boosts `speed_cur` by `(rubber_band_strength * stats.speed / 100)` when the AI is behind the player on the waypoint loop. Same physics path, identical write-back.

### Polygon → Tilemap Rasterization (scan-line fill with corridor)

Algorithm choice: **standard scan-line polygon fill, with a post-pass that erodes the inside to leave a corridor of width W tiles.** Rationale:
- Single pass over polygon edges → output array of `mapHeight` byte rows, `mapWidth` cols each.
- Output size = `mapWidth * mapHeight` bytes, fits in one `_zone_<id>_tiles` array (32x32 = 1024 bytes; bank limit is 16 KB per bank, so safe).
- Erosion to corridor is straightforward with a 4-neighbor distance-from-boundary pass: tile is "drivable" if `min_distance_to_polygon_boundary >= corridor_width`.

**Wait — re-read D-10.** Spec says "expand polygon into a track corridor and writes drivable tiles inside, wall tiles outside." That's actually the **inverse** of fill+erode for a thick *outline*. Two valid readings:
- **Reading A (filled track):** Inside the polygon = drivable; outside = wall. Track is the entire enclosed area.
- **Reading B (outlined track):** Only a corridor near the polygon boundary is drivable; far inside = grass; outside = wall. Track is a loop, not a filled shape.

[ASSUMED] — D-10 wording slightly ambiguous; D-11 says "Default to a sensible value (likely 3–5 tiles wide, walls on the outside that block movement)" which matches **Reading B** (corridor near boundary). Reading B is also the only one that matches a real-world racing-game shape (closed loop). **Recommend Reading B.**

Implementation (sketch):
```
// Step 1: Compute polygon bounding box → mapWidth, mapHeight (with margin = corridorWidth + 1).
// Step 2: Scan-line fill into a temporary List<Boolean>: true = inside polygon.
// Step 3: For each tile (x, y), compute min distance to any polygon edge (in tile units).
//         drivable = (insidePolygon[x,y] && distToEdge[x,y] < corridorWidth/2)  // Reading B
//         wall     = !insidePolygon[x,y]
//         grass    = (insidePolygon[x,y] && distToEdge[x,y] >= corridorWidth/2)
// Step 4: Map (drivable, grass, wall) → tile indices (1, 2, 3) — concrete indices match the user's
//         tileset(asset(...)) tile layout (Claude's discretion).
```

**Output:** A `List<Int>` of length `mapWidth * mapHeight`, written to `ZoneIR.tileData`. The existing `buildZoneData()` consumes it unchanged.

[ASSUMED] — corridor width = 4 tiles is a reasonable default; can be tuned during plan-check.

### Waypoint State Machine (in SportVisitor.visitRacing — replace the wrap-around)

```c
// Generated C (sketch)
// Player frame tick — replaces existing wrap-around lap counter
if (_racing_checkpoint_idx_track1 < 4u) {
    UINT8 cp_x = _racing_cp_x_track1[_racing_checkpoint_idx_track1];
    UINT8 cp_y = _racing_cp_y_track1[_racing_checkpoint_idx_track1];
    UINT8 dx = (_car_x > cp_x) ? _car_x - cp_x : cp_x - _car_x;
    UINT8 dy = (_car_y > cp_y) ? _car_y - cp_y : cp_y - _car_y;
    if (dx < 8u && dy < 8u) {
        // Touched checkpoint K. Set bit K only if all bits 0..K-1 are set.
        UINT8 mask_below = (1u << _racing_checkpoint_idx_track1) - 1u;
        if ((_racing_visited_track1 & mask_below) == mask_below) {
            _racing_visited_track1 |= (1u << _racing_checkpoint_idx_track1);
            // Was this the final checkpoint AND we're back near checkpoint 0?
            // Check separately: K == numCheckpoints-1 doesn't auto-complete a lap;
            // the lap completes when player re-touches CP 0 with full visited bitmap.
        }
    }
}
// Lap completion: near CP 0 AND all bits set.
{
    UINT8 cp0_x = _racing_cp_x_track1[0];
    UINT8 cp0_y = _racing_cp_y_track1[0];
    UINT8 dx0 = (_car_x > cp0_x) ? _car_x - cp0_x : cp0_x - _car_x;
    UINT8 dy0 = (_car_y > cp0_y) ? _car_y - cp0_y : cp0_y - _car_y;
    UINT8 all_set = (1u << NUM_CHECKPOINTS_TRACK1) - 1u;
    if (dx0 < 8u && dy0 < 8u && _racing_visited_track1 == all_set) {
        _racing_lap_count_track1 += 1u;
        _racing_visited_track1 = 1u;   // reset, but keep CP 0 set so we don't immediately re-complete
    }
}
```

**Key insight:** The bitmap `_racing_visited_track1` makes ping-pong impossible. To complete a lap from CP 0 to CP 0, every intermediate CP must be visited in order. Going backwards across a single edge does not advance the bitmap. [VERIFIED: this construction by inspection — no source to cite, deduced from D-17 binding constraint.]

Constraint: `NUM_CHECKPOINTS_TRACK1 ≤ 8` so the bitmap fits in `UINT8`. If a future game has >8 checkpoints, switch to `UINT16`. [ASSUMED — sport-genre racing rarely has >8 checkpoints; can be relaxed later.]

## Risks & Landmines

### R1: Bank Overflow

Synthesized 32x32 zone tilemap = 1024 bytes. Plus `_racing_wp_x_<id>[]` + `_racing_wp_y_<id>[]` + `_racing_cp_x_<id>[]` + `_racing_cp_y_<id>[]` ≈ ~50 bytes. Plus camera state ~6 bytes. Plus per-AI-instance arrays (one pool with N=1..3) ~40 bytes. Total well within 16 KB bank limit. **Risk: LOW.** Banking pass already handles dungeon zones of similar size (Explorer / Dungeon).
**Counter-test:** `./gradlew :gbkt-examples:racer:buildRom` succeeds; `BudgetAuditPass` does not flag overflow.

### R2: BANKED Calling Convention Regression

Memory: prior bug pattern. If `racing_tick_<id>` ends up with a forward declaration in `bank1.c` without `BANKED`, lcc errors at 0xBA00+. **Risk: MEDIUM** — auto-prototype path mostly handles this, but a new function in a less-trodden code path can still slip through.
**Counter-test:** Codegen test asserts `racing_tick_<id>` is in `homeFile.functions` (HOME bank); a separate test asserts `game.h` contains a matching `BANKED`-suffixed prototype.

### R3: Stats-Driven Movement Indistinguishable from MovementStyle.SMOOTH

If the new physics math feels visually identical to the old `MovementStyle.SMOOTH` (or to the hand-coded `moveBy`), SC-2 fails the user-visible criterion. **Risk: MEDIUM** — not an algorithmic issue but a perceptual one.
**Counter-test:** MCP comparison: Racer with stats.speed=200 vs stats.speed=100; assert measurable lap-time difference. JVM unit test on the math: feed two stats configs, run 100 simulated frames, assert pixel delta differs.

### R4: Polygon-Fill Bugs (Checkerboard / Off-By-One)

If scan-line fill produces a non-uniform tile array, the generated track is unrenderable. **Risk: MEDIUM** for first-time-implementing-from-scratch.
**Counter-test:** `TrackSynthesizerTest` cases — square (4 vertices), triangle (3 vertices), pentagon (5 vertices). For each, assert (a) total drivable-tile count matches expected polygon area minus erosion, (b) no row contains alternating drivable/wall tiles (checkerboard signature), (c) walls are contiguous on the outside.

### R5: Lap-Counter Ping-Pong Loophole Slips Through

D-17 binding constraint — the ONE thing that absolutely must hold. If the bitmap construction is buggy (wrong `mask_below` math; wrong reset on lap completion), ping-pong might still register a lap. **Risk: HIGH** if not explicitly tested; LOW once tested.
**Counter-test:** MCP scripted path — drive across edge between CP 0 and CP 1 six times in a row, assert `_lap == 0`. Also: drive CP 0 → CP 1 → CP 0 (skipping CP 2 and CP 3), assert `_lap == 0`. Also: drive full loop CP 0 → 1 → 2 → 3 → 0, assert `_lap == 1`.

### R6: Camera scrolls into uninitialized BG tile region

If the synthesized zone is sized 256x256 (default `zone size(32,32)`) but the polygon only fills a 128x128 region, the camera will scroll into all-zero tiles when the player drives toward the edge. **Risk: LOW** because the polygon itself bounds where the player can drive (walls outside).
**Counter-test:** MCP play-through holds RIGHT for 60 frames; screenshot the result; assert no blank BG region appears in viewport.

### R7: Old goldens fail tests they shouldn't

Existing `racer-{title,race,results}.png` were captured against the FAIL baseline. After the fix, tests comparing against them will fail. **Risk: HIGH but expected.**
**Counter-test:** Regenerate goldens as part of plan-04 (or whatever the final task is). UAT-racer.md explicitly notes: "Goldens captured 2026-05-07 are torn up and regenerated against the new track + AI sprite + scrolling camera."

### R8: Auto-injected scene-frame ScriptOps interfere with user's frame logic

If racing() prepends ops that mutate `car.x`/`car.y`, but the user's frame block reads `car.x` for HUD or sound, the user's reads see the post-tick values. **Risk: LOW** — this is exactly the design (D-07: racing() owns the loop). But document the prepend semantic in the rewritten PLAYBOOK.md so users know.
