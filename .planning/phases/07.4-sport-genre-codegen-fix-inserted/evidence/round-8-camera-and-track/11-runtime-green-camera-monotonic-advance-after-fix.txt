## Root cause: signed-vs-unsigned literal comparison (NEW gap)

GBDKSystemVisitor.visitCameraSystem builds the inner comparisons as
CBinaryExpr(CVar("rawY"), "<", CLiteral(0)) and CBinaryExpr(CVar("rawY"),
">", CLiteral(8)). CEmitter renders every non-negative CLiteral with a
`u` suffix (CEmitter.kt:421 — `"${expr.value}u"` when value >= 0). So
the emitted comparisons are `rawY < 0u` and `rawY > 8u`.

rawY is INT16 (signed). In C, comparing a signed short to an unsigned int
triggers "usual arithmetic conversions" (C11 §6.3.1.8):

  1. The INT16 is promoted to int.
  2. int and unsigned int → both converted to unsigned int (because they
     have the same rank and unsigned wins).
  3. A negative int value, when converted to unsigned int, becomes a
     LARGE positive value (e.g. -63 → 0xFFFFFFC1 ≈ 4.29e9).
  4. The comparison then runs in unsigned domain.

Concrete: _car_y=5 → rawY = (int16_t)5 - 72u = -63.

  - rawY < 0u   →  (unsigned)-63 < 0u   →  0xFFFFFFC1 < 0  →  FALSE
  - rawY > 8u   →  (unsigned)-63 > 8u   →  0xFFFFFFC1 > 8  →  TRUE

So the C output for rawY=-63 evaluates:
  _camera_y = (UINT8)(FALSE ? 0u : (TRUE ? 8u : rawY)) = (UINT8)8 = 8

_camera_y is permanently clamped to maxY (8) for any _car_y < 72.
