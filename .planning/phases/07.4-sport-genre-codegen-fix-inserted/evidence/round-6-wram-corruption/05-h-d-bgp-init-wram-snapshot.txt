# Rationale (from 26-PLAN26-FOLLOWUP.md H-D): "GBDK VBlank/STAT interrupt
# handler writes stack-relative garbage when SHOW_BKG is on but BGP is
# uninitialised". 0xE4 = standard 3,2,1,0 grayscale BGP byte. The watchdog
# message itself hints at this: "Check LCDC, BGP, and the most recent
# scene-enter."
#
# Probe result: Round6WramCorruptionProbe FAILED. Identical hang signature
# at frame 124. EmulatorFrameHangException identical to baseline.
#
# 0xC0xx canaries: probe could not read them; hang occurred before the

## verdict
#
# H-D REFUTED. Initialising BGP_REG to 0xE4 before SHOW_BKG did NOT
# prevent the hang. The frame count is identical (124), proving the
# hang occurs at the same code path. Palette uninitialisation is NOT
# the upstream cause of the corruption.
#
# Note: BGP_REG is undefined on GBC mode (GBC uses BCPS/BCPD register
# pair instead of BGP), so the H-D write may be a no-op on the GBC
# Coffee-GB target. However, the racer is configured GBC_COMPATIBLE,
# which means BGP_REG IS the active palette register at boot until
# the GBC palette upload happens — so this write is meaningful in
# DMG-compatible boot. The hang still occurring suggests the BG palette
# is not the upstream cause; either:
#   (a) the BGP write happens too late (after a frame has been rendered
#       with corrupt state), or
#   (b) the corruption is unrelated to palette state.
