## Decisions Made

- **Fix at the emitter, not the visitor.** Plan 32's executor diagnosis confirmed the visitor's AST shape (`CCast(CU8, CTernary(...))`) was already correct — the bug lived exclusively in text emission where `is CCast -> "(${emitType(expr.type)})${emitExpr(expr.expr)}"` dropped parens. Fixing at the visitor would have addressed only the camera site; fixing at the emitter (Option A from plan Task 1 step 2) is the structural fix that benefits every present and future CCast call site.
- **Defensive parenthesisation extends beyond CTernary.** `emitCastInner()` also wraps `CBinaryExpr` and `CUnaryExpr`. Cast and unary share precedence rank in C so unary-prefix wrapping is strictly defensive (no behaviour change), but a future cast site that builds `CCast(_, CBinaryExpr(_,"+",_))` would otherwise hit the same precedence-fragility class. Cheap belt-and-suspenders.
- **Partial-closure documented, scope respected.** When Task 3's runtime probe surfaced a NEW gap (signed-vs-unsigned literal comparison) that the precedence fix cannot address, I stopped per plan threat T-07.4-34-01 rather than expanding into either the visitor or the CLiteral emission policy. The new gap is documented in evidence file 11 with three viable architectural options for the planner; this honours the plan's stated scope (CEmitter.kt:430 CCast handler) and T-07.4-34-03 (no scope-creep tampering).

## Issues Encountered

### 1. Runtime monotonicity probe RED — root cause is NOT zone size

**Symptom:** `_camera_y = 8, 8, 8` at baseline / +30 / +60 frame snapshots despite `_car_y` decreasing from 80 → 5 (UP input reached engine, precondition met).

**Initial hypothesis (from plan Task 3 step 3):** zone size too small for camera scroll — would imply Plan 35 (track-fix) dependency.

**Actual root cause (discovered during diagnosis):** the visitor's `CBinaryExpr(rawY, "<", CLiteral(0))` emits as `rawY < 0u` because CEmitter renders every non-negative `CLiteral` with a `u` suffix (CEmitter.kt:421). C's usual-arithmetic-conversion promotes the signed INT16 to unsigned int for the comparison, reinterpreting negative values as huge positives. So `rawY < 0u` is always false for negative rawY, and `rawY > 8u` is always true → `_camera_y` permanently clamped to `maxY=8` whenever `_car_y < 72`.

**Resolution:** documented as Layer 2 gap in evidence 11; surfaced to planner per Rule 4. Three architectural options proposed (visitor literal-cast, type-aware emitter literals, CLiteral signed/unsigned AST split). Not fixed in this plan — would violate T-07.4-34-03 scope (no GBDKSystemVisitor edits; no literal-emission policy changes).

### 2. Pre-existing GAP-TRACK-CIRCUIT failures in `:gbkt-genre-sport:test`
