# Phase 07.4 Plan 03: SportBuilders / SportExtensions Delegate Refactor Summary

**Refactored the `gbkt-genre-sport` racing DSL from String-id `racing("track1")` / `vehicle("car_player")` factories to property-delegate-driven `val track1 by racing { … }` / `val carPlayer by vehicle { … }` factories (D-04 Project Rule #1). RacingDelegate now wires TrackSynthesizer (Plan 04) into ZoneIR.tileData with a D-12 user-zone bypass, auto-emits a CameraSystem following the bound player vehicle's actor (D-06), synthesizes one ActorPoolIR per AI vehicle slot (D-13, D-14 — pool id from the AI vehicle property name), and registers a `sport_racing` GenericSystem carrying the canonical per-game config map that Plans 05 and 06 consume read-only.**

## Decisions Made

1. **Cross-module API expansion in `gbkt-lang`** — `GameBuilderContext` made public; `GameBuilder.registerActorPool` promoted from internal to public; new public methods `registerZone`, `currentSystems`, `currentZones`. Required because Kotlin's `internal` is per-module and the genre package cannot reach `internal` symbols across the module boundary. Surface kept to the bare minimum: read-only snapshots return defensive copies (no mutation possible from outside `gbkt-lang`); the only mutating addition is `registerZone`, which mirrors the existing public `registerSystem` pattern. Treated as a Rule 3 deviation; see Deviations section for the full justification.
2. **`System.identityHashCode`-keyed VehicleRegistry** instead of a thread-local. Thread-locals require explicit `clear()` to avoid bleeding state across `game { }` invocations in the same thread (e.g., back-to-back tests). Identity-hash keying is automatically per-builder and self-scopes to the GameBuilder lifetime. `snapshot()` and `clear()` are provided for completeness.
3. **Two atomic commits even though Task 1's intermediate state does not compile** — preserving the plan's two-task boundary in the audit trail. The intermediate non-compiling commit window exists only between the two commits; both land together within Plan 03's single execution wave so the project history never observes a broken main branch tip. Documented in the deviations section.
4. **SportBuildersTest fixture migration** — the eight pre-existing racing tests were ported to the new delegate API rather than preserving back-compat factories. Plan Step K explicitly authorizes this (and D-04's contract demands it: magic strings are gone permanently). One semantic shift: vehicle bindings live in the GenericSystem config map under `registeredVehicles` instead of `RacingConfig.vehicles` (the legacy VehicleDef list, intentionally empty in the new flow).
5. **`racing defaults laps to 1 and mode to AI_OPPONENT`** — the renamed `defaults_test` test reflects the new RacingBuilder defaults. The legacy builder defaulted to `(laps=3, mode=TIME_TRIAL)`; the new one defaults to `(laps=1, mode=AI_OPPONENT)` because the racing-meta-context expects users to explicitly call `laps()` for non-trivial races and AI_OPPONENT is the more common default for a genre-meta engine. The test name change documents the shift.
6. **`RacingPolygonRasterTest` flipped to GREEN here** — the user prompt's success criteria explicitly listed this as a Plan 03 GREEN target. Plan 04's SUMMARY noted that Plan 03 is responsible for the integrated outcome (TrackSynthesizer is callable from Plan 03's RacingDelegate, which writes the result into ZoneIR.tileData). The plan body's stale `<verification>` block listing RacingPolygonRasterTest under "Plan 05 owns those" was inherited from the planning template before Plan 04's split was finalized; the user prompt's success criteria takes precedence.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] Cross-module API expansion in gbkt-lang**

- **Found during:** Task 1 first compile attempt
- **Issue:** `GameBuilderContext` was `internal object` in gbkt-lang; `GameBuilder.registerActorPool` was `internal fun`. Kotlin `internal` is module-scoped, so gbkt-genre-sport's `RacingDelegate.provideDelegate` could not call `GameBuilderContext.current` to obtain the active GameBuilder, nor could it call `gameBuilder.registerActorPool(...)` to synthesize per-AI-vehicle pools. Without these, the delegate body cannot complete the racing-system synthesis the plan requires.
- **Fix:** Promoted `GameBuilderContext` from `internal object` to public `object`; promoted `registerActorPool` from `internal fun` to `fun`. Added new public methods `registerZone(zone: ZoneIR)`, `currentZones(): List<ZoneIR>`, `currentSystems(): List<SystemIR>` to GameBuilder. Surface is minimal: the read-only snapshots return defensive copies (no mutation possible); the only new mutating method is `registerZone`, which mirrors the existing public `registerSystem` pattern. The other genre packages (gbkt-genre-rpg, etc.) already access `registerSystem` publicly for their delegate-driven extensions.
- **Files modified:** `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/GameBuilder.kt`, `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/VariableBuilders.kt`
