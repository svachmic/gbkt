<objective>
Lock GAP-CAMERA-NO-FOLLOW at the JVM codegen-shape tier AND the runtime monotonicity tier via two RED tests that FAIL against HEAD. These tests become the GREEN contract Plan 07.4-34 must satisfy.

The round-7 false-positive class: SC-3-VISUAL passed on `_camera_y > 0` after a 60-frame UP hold, but the value (8) came from the 152x152-zone-clamp upper bound, not from camera-follow tracking. The user's manual UAT then showed camera stuck at world origin. The structural lesson (D-N-12, codified here): visual SCs whose verdict depends on a VARIABLE TRAJECTORY require multi-snapshot monotonicity assertions, not single-snapshot thresholds.

This plan codifies D-N-12 by writing the first such monotonicity probe. The JVM RED test additionally locks the codegen-shape contract one level below the visual: the cast-wraps-ternary expression structure that the current visitor emits incorrectly.

The current bug surface (line ~255 of generated main.c):

`_camera_x = (UINT8)(rawX < 0u) ? 0u : (rawX > 0u) ? 0u : rawX;`

C operator precedence binds the (UINT8) cast to `(rawX < 0u)` ALONE, yielding 0 or 1. Then the ternary fires on that 0/1 value, NEVER on rawX. So _camera_x is permanently 0. Same for _camera_y with maxY=8 — the ternary upper bound is the only path that produces 8.

The fix Plan 07.4-34 lands re-parenthesises the emitted CExpr so the cast wraps the ENTIRE ternary, plus addresses the underlying zone-too-small constraint (152x152 zone < 160-wide screen → camera cannot scroll X at all; this is a TrackSynthesizer concern handled in Plan 07.4-35).
</objective>
