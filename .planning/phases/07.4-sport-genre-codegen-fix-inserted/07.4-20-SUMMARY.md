# Phase 07.4 Plan 20: Path C Scene-Aware ScreenClear + PrintOp Summary

JWT-style two-part fix lands the architectural rule "the DSL `clear()` and `print()` keywords MUST NOT corrupt a loaded BG tilemap" via a single one-line DSL routing change in `gbkt-lang` plus scene-aware codegen lowering in `gbkt-backend-gbdk`. No new IR node, no game-specific carve-out, no DSL surface change from the user's perspective. Plan 19's 4 RED tests flip to GREEN; the 1 staged @Ignore test is un-disabled and locks the back-compat-preserving shape.

## What Got Built

### Part 1 — DSL Routing Fix (gbkt-lang, one-line change)

`ScriptBuilder.clear()` body changed from:
```kotlin
ops += RawOp("cls();", sourceLocation = captureV2Location())
```
to:
```kotlin
ops += ScreenClear(sourceLocation = captureV2Location())
```

This routes DSL `clear()` through the existing `ScreenClear` IR node and into the existing `visitScreenClear` codegen hook. Without this change, the visitor's scene-aware lowering would be dead code for the racer's actual code path (the `RawOp("cls();")` flowed directly to `CRawCode("cls();")` via `visitRawOp`, bypassing `visitScreenClear` entirely). This is the load-bearing finding Plan 19 forwarded as CRITICAL.

### Part 2a — Scene Context Threading (GBDKPipelineV2)

`buildSceneFile()` now wraps each scene's op lowering in:
```kotlin
val hasBg = sceneHasBgTilemap(scene.id, gameIR, genreEnterOps)
ScriptOpVisitor.setSceneContext(scene.id, hasBg)
try {
    // ... existing SceneVisitor / addMovementAndAnimationCalls / addGenreFrameOps /
    // addGenreEnterOps / hud / tileset guard pipeline ...
} finally {
    ScriptOpVisitor.setSceneContext(null, false)
}
```

The new private predicate `sceneHasBgTilemap(...)` returns TRUE iff EITHER:
- `SceneIR.tilesetRef != null` (scene was authored with `tileset(...)` DSL), OR
- The genre `enterOps` splice for the scene paints the BG via GBDK's `set_bkg_data` / `set_bkg_tiles` (e.g. `racing { track }` causes `SportVisitor.enterOps` to splice these RawOps into `race_enter`).

The try/finally guarantees the scene context is cleared even if a downstream visitor throws — leaking the flag would taint the next scene's codegen.

### Part 2b — Scene-Aware visitScreenClear (ScriptOpVisitor)

```kotlin
override fun visitScreenClear(op: ScreenClear): CStatement =
    if (currentSceneHasBgTilemapContext.get()) {
        // BG scene: non-destructive clear preserves the painted tilemap
        CBlock(
            listOf(
                CRawCode("HIDE_SPRITES;"),                                    // OAM wipe
                CExprStatement(CCall("_win_clear_region",
                    listOf(CLiteral(0), CLiteral(0), CLiteral(20), CLiteral(18)))),   // window/HUD wipe
            ),
            sourceLocation = op.sourceLocation,
        )
    } else {
        // Non-BG scene: existing back-compat shape
        CExprStatement(CCall("cls", emptyList()), sourceLocation = op.sourceLocation)
    }
```

`HIDE_SPRITES` is emitted via `CRawCode` (NOT `CCall`) because it is a GBDK macro, not a function — `CCall("hide_sprites", ...)` would link-fail across all 6 ROMs. Mirrors the existing `RawOp("HIDE_SPRITES;")` pattern in `ScriptBuilder.hideSprites()`.

### Part 2c — Scene-Aware visitPrintOp (ScriptOpVisitor)

When `currentSceneHasBgTilemap` is TRUE, the visitor delegates to `buildWindowLayerPrint(op)`:
- **Literal print** (`op.values.isEmpty()`): direct call `_win_print_at(x, y, "<text>", <len>)`.
- **Formatted print**: `sprintf` into a 20-byte stack buffer, then `_win_print_at(x, y, _print_buf, strlen(_print_buf))`. Verified `sprintf` IS available in GBDK-2020 at `/Users/michalsvacha/gbdk/include/stdio.h:55`. No example game today exercises the formatted-print BG-scene path; it exists for forward-compat correctness.

When FALSE: byte-for-byte preserves the existing `gotoxy + printf` lowering.

### Part 3 — Test Lock (PrintOpSceneAwareTest)

Plan 19's Test #3 was staged via `@Ignore` for the RED phase. Plan 20 un-disables it and replaces the placeholder body with three locking assertions on `title_enter` (a non-BG scene):
- MUST contain `gotoxy(`
- MUST contain `printf(`
- MUST NOT contain `_win_print_at(`

This is the JVM-tier forcing function against accidental scope expansion: if a future change widens the BG-scene swap to ALL scenes, this test fails loudly before any cross-ROM regression hits the example games.

## REVISED Back-Compat Decision (Why Option (a))

The plan's `<decision>` block originally proposed option (b) — universal `_win_print_at` swap. Plan 20 adopted the REVISED choice (option (a) — scene-aware) for the following reasons:

1. **`sprintf` IS available in GBDK-2020.** Verified at `/Users/michalsvacha/gbdk/include/stdio.h:55` (`void sprintf(char *str, const char *format, ...);`). The universal-swap path is technically feasible — sprintf-into-buffer + `_win_print_at` would compile.
2. **HOWEVER**, exercising the sprintf+`_win_print_at` codegen path across the 5 non-racer example games' actual `print(format, ...args)` shapes has not been validated. The risk class is regression-by-untested-rewrite across 5 ROMs.
3. The original Plan 20 acknowledged this risk by reserving a `FIXME(07.4-20-FOLLOWUP)` escape hatch — that escape would have shipped literal format strings (e.g. `"SCORE: %d"`) on screen across 5 games. That violates `feedback_quality_over_shortcuts.md` ("no smoke and mirrors").
4. CLAUDE.md "Window-Layer UI" applies most stringently to scenes WITH a custom BG tilemap (where text on the BG layer would corrupt graphics). For BG-less scenes (title, results, gameover), `gotoxy + printf` writes to the BG tile layer but the BG is empty — there's nothing to corrupt. The architectural-purity argument for (b) is real but the regression-risk-vs-purity tradeoff favors (a) for this phase.

**Net for Plan 20:**
- BG scenes (race; any scene with `tilesetRef` or genre BG splice) → `print(...)` lowers to `_win_print_at(...)`. Window-layer UI honored where it matters most.
- Non-BG scenes (title, results, gameover) → `print(...)` keeps the existing `gotoxy + printf` lowering. Zero behavioral change for the 5 non-racer example games.

**Future direction (NOT this plan):** A follow-up phase can pursue universal `_win_print_at` lowering after the dynamic-print path (sprintf-into-buffer with formatted args) is exercised across all 5 games' actual `print(format, ...args)` shapes. Out of scope for 07.4.
