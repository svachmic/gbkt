<domain>
## Phase Boundary

Wire `gbkt-genre-sport`'s `racing()` DSL to working generated C so the block produces a real racing game — drivable car with stats-driven physics, AI opponents on a real circuit tilemap, camera that follows, and lap detection that requires actually driving the loop. The DSL must be reusable for any racing/sport game (rally, ball sports, tournaments), not Racer-specific.

The Racer example (`gbkt-examples/racer/Racer.kt`) is the validation target. Hand-coded `whenever(dpad.X.held) { moveBy(car, …) }` workarounds and the two-line "track" disappear after the fix.

**Scope includes:**
- `vehicle { actor(...); stats { ... } }` and `racing { player(...); aiOpponents(...); track { waypoint(...) } }` DSL → working IR + C
- Track tilemap synthesis from waypoint polygon (drivable corridor inside, walls outside)
- AI vehicle as a real renderable actor via 07.3 entity pools (uniform path for 1..N opponents)
- Camera follow auto-wired from the racing()→player binding
- Stats-driven movement: racing() owns the entire input → velocity → position loop
- Waypoint state machine + checkpoint-based lap counting (real circuit, not coordinate strip)
- Codegen-level regression tests + MCP play-through verification

**Scope excludes:**
- New IR nodes (fix lives in `gbkt-genre-sport` codegen + GBDK backend; existing IR sufficient)
- GBC palette init (separate phase 07.7)
- Other genre fixes (platformer 07.5, RPG 07.6)
- Game-specific shortcuts — every codegen pattern must be reusable per the engine contract from 07.3

## Implementation Decisions

These supersede the six placeholder D-? items in the previous CONTEXT.md stub.

### Engine Boundary (carried from 07.3)
- **D-01:** IR stays minimal — no new IR nodes. Sport DSL produces existing IR (CameraSystem, ActorPoolIR, ZoneIR, GenericSystem("sport_racing"), ScriptOps). Fix surface is `gbkt-genre-sport` (DSL → IR translation) and `gbkt-backend-gbdk` (codegen for racing-specific systems).
- **D-02:** No game-specific special cases. Every pattern generated is reusable for any racing/sport game.
- **D-03:** IR exposes no hardware ops. Backend handles OAM, VRAM, banking. DSL author thinks in vehicles, waypoints, and laps — never in tile bytes.
- **D-04:** No magic strings (Project Rule #1). All identifiers come from Kotlin property delegates / lambda params. The DSL never duplicates a name as a String parameter.

### Player–Car Binding & Camera Auto-Wire
- **D-05:** Vehicle wraps an actor. The user declares the actor first, then a vehicle that holds an `ActorRef`:

  ```kotlin
  val car by actor {
      position(80, 80)
      sprite(asset("sprites/car.png")) { size(8, 16); hitbox(0, 0, 8, 16) }
  }
  val rival by actor {
      sprite(asset("sprites/rival.png")) { size(8, 16); hitbox(0, 0, 8, 16) }
  }

  val carPlayer by vehicle {
      actor(car)
      stats { speed(200); acceleration(160); handling(180) }
  }
  val carAi by vehicle {
      actor(rival)
      stats { speed(180); acceleration(150); handling(200) }
  }

  val track1 by racing {
      laps(3)
      player(carPlayer)
      aiOpponents(carAi)
      track {
          waypoint(x = 5, y = 5, checkpoint = true)
          waypoint(x = 15, y = 5)
          waypoint(x = 15, y = 15, checkpoint = true)
          waypoint(x = 5, y = 15)
      }
  }
  ```

  The vehicle keeps the on-screen actor a separate, customizable entity (movement style, animationStates, custom props all still available). racing() takes vehicle refs, not actor refs.

- **D-06:** Camera auto-wires from `player(carPlayer)`. racing() emits a `CameraSystem(followActorId = carPlayer.actor.id, boundsWidth = zone.widthPixels, boundsHeight = zone.heightPixels)` if the user didn't add `camera { }` themselves. If the user did, racing() respects it but warns when `follow(...)` doesn't point at the bound player. Existing camera codegen (`GBDKSystemVisitor.visitCameraSystem`) already handles bounded follow.

### Stats → Movement (racing() Owns The Loop)
- **D-07:** racing() owns the entire per-frame movement loop for the player vehicle. It generates input reading (dpad → throttle/steer), velocity integration (acceleration ramps to top speed; friction decays), heading/handling (handling damps lateral drift on turns), and position write-back (`car.x` / `car.y`). The user writes ZERO movement code in the scene's frame block. Stats fully drive feel.
- **D-08:** Hand-coded movement that fights racing() must be detected. If a scene's frame block contains `moveBy(<bound player car>, …)` or direct writes to `car.x` / `car.y`, the analysis pass emits a build-time warning ("racing() owns this car's movement; remove direct moves"). Not a hard error in 07.4 — Racer.kt sheds the workarounds first, then we revisit.
- **D-09:** AI vehicles run on the same physics path as the player. The only difference is the input source (waypoint follower instead of dpad). Same accel/handling/friction math; same actor.x/.y write-back. This keeps "every codegen pattern reusable" honest — no separate AI movement code.

### Track Tilemap Source
- **D-10:** racing() auto-synthesizes the zone tilemap from the waypoint polygon. The waypoint loop must enclose an area (>=3 non-collinear waypoints, polygon non-degenerate); planner enforces this in an analysis-pass check. Codegen expands the polygon into a track corridor and writes drivable tiles inside, wall tiles outside. The user's only input to track *visuals* is `tileset(asset(...))` for the tile graphics.
- **D-11:** Corridor width and outside-tile semantics (wall vs grass) are Claude's discretion in planning. Default to a sensible value (likely 3–5 tiles wide, walls on the outside that block movement). This is a tactical knob, not a contract surface — can change without DSL impact.
- **D-12:** No hand-painted `tiles(listOf(...))` data path for racing tracks in 07.4. If the user supplies tilemap data on the zone, the synthesizer leaves it alone (back-compat with the dungeon/explorer zone path), but the racing() lap-validation contract still uses the waypoint polygon. Keeping these decoupled avoids the "asset says one thing, polygon says another" overfit risk.

### AI Vehicle Instantiation
- **D-13:** AI vehicles are 07.3 entity pool instances. `aiOpponents(carAi)` declares a single opponent; `aiOpponents(carAi, count = 3)` declares many. Same per-instance arrays / OAM allocator that 07.3 validated. Scales to ball-game teams, rally fields, or tournament brackets without new infra.
- **D-14:** racing() auto-generates the pool from the AI vehicle's bound actor template. The user does NOT manually `actorPool { }` for AI cars. Pool id is derived from the vehicle property name (e.g., `carAi` → pool id `carAi`). All identifiers from delegates.

### Waypoint State Machine & Lap Detection
- **D-15:** Lap rule = must-visit checkpoints in DSL-declared order. Only `isCheckpoint = true` waypoints count for lap validation. Player advances `_racing_checkpoint_idx_<id>` when within proximity of the *next* checkpoint (in declared order). Lap completes when player crosses the start/finish (first checkpoint) AFTER touching every other checkpoint. Cannot skip; cannot oscillate against a single edge.
- **D-16:** Non-checkpoint waypoints exist only for AI pathing. AI follows the full waypoint loop (all of them, in order); player only validates against the checkpoint subset. This decouples driving line from lap contract.
- **D-17:** "A lap means a real lap" is a binding constraint on every artifact in this phase. The visible track must be an enclosed circuit (not two parallel lines), the waypoint polygon must enclose an area, and lap completion must require traversing the loop. No completing 3 laps by ping-ponging.

## Existing Code Insights

### Reusable Assets
- **CameraSystem codegen** — `GBDKSystemVisitor.visitCameraSystem` already implements bounded follow with INT16 clamp. racing() just needs to emit a CameraSystem with `followActorId = car.id` and `boundsWidth/Height = zone.size_in_pixels`. No new camera code.
- **ActorPool engine** — 07.3 validated pools end-to-end. AI vehicles plug straight in via the same pool IR + per-instance arrays + OAM free-list path.
- **ZoneIR tile pipeline** — `_zone_<id>_tiles[]` array generation already works for dungeon zones. racing() writes synthesized tile bytes into `ZoneIR.tileData` at DSL build time; the GBDK pipeline consumes them unchanged.
- **SportVisitor.visitRacing** — already generates `racing_update`, `racing_ai_update`, `racing_check_finish`, waypoint coord arrays. Most of the structure is there; the gap is calling these from the scene frame loop and tying them to a real player/AI actor pair.
- **MovementStyle.SMOOTH actor movement** — exists, applies friction/acceleration. Useful as a reference but racing() will own its own per-frame loop (D-07) rather than configuring this.

### Established Patterns
- **Property delegates → IR ids** (`val foo by character { … }` → id="foo") — extend the same pattern to `vehicle { }` and `racing { }` for D-04. No string id parameters.
- **GenericSystem("sport_racing", config)** — sport DSL stores domain types in a generic config map; SportVisitor reads them out. Continues unchanged; the new player/aiOpponents/track block contents go in the same config.
- **Pipeline GameIR injection** (`ScriptOpVisitor.setGameIR(gameIR)` from 07.3) — required if racing() body codegen needs context about pools or actors. Already wired in `buildSceneFile()`.
- **Polygon → tile rasterization** — not yet in the codebase. Could borrow scan-line fill from any standard polygon-fill source; output is the byte array consumed by `buildZoneData`.

### Integration Points
- **DSL → IR:** `racing { }` builder must emit (a) updated `RacingConfig` with player/ai/track-polygon, (b) a `CameraSystem` (if no user camera), (c) zero-or-more `ActorPoolIR` for AI vehicles, (d) populate `ZoneIR.tileData` for the track zone, (e) install per-frame ScriptOps in the scene frame block that reference the bound player car.
- **Scene frame loop:** racing() needs to inject input-reading + physics-integration + checkpoint-advance + lap-counter ScriptOps into the user's race scene frame block. Likely path: a new `RacingTickOp` ScriptOp (or composition of existing ops) emitted by the racing() builder when it sees the user's scene reference. Alternative: an analysis pass that walks scenes and inserts the tick.
- **Zone <→ track binding:** racing()'s `track { waypoint(...) }` block must associate with a zone. Either the user names a zone (`track(circuitZone) { … }`) or racing() auto-creates a zone from the property name. Tactical detail; planner picks per D-04 + D-12 constraints (no magic strings; no asset-vs-polygon ambiguity).
- **Pool AI lifecycle:** AI pools spawn in scene `enter` (one instance per declared opponent or up to `count`), get destroyed on scene exit, and tick inside the same per-frame loop racing() owns.
