<objective>
Close the secondary issue surfaced in `07.4-UAT.md`: camera bounds clamp underflows to UINT8(-8)=248 when the zone is smaller than the GB screen (160×144). Racer's auto-synthesized 19×19-tile zone (152×152 px) triggers this — `maxX = boundsWidth - 160 = -8` is then cast to UINT8, yielding `SCX_REG = 248` and pushing the BG off-screen.

Per D-02 (no game-specific special cases), the fix lives in the GENERIC camera codegen, not the racing genre. ALL `CameraSystem`s benefit, including future puzzle/RPG zones smaller than the screen.

This plan must land BEFORE Plan 23 (re-verification) — otherwise even with Plan 20's BG-render fix in place, the camera would still mis-scroll the painted track off-screen.

Purpose: Make camera bounds defensible against zones smaller than the screen. A zone smaller than the screen has no scroll range — the camera simply locks at (0,0).

Output:
- `GBDKSystemVisitor.visitCameraSystem` clamps `maxX = max(0, boundsWidth - 160)` and `maxY = max(0, boundsHeight - 144)`.
- New `CameraBoundsUnderflowTest` covers: sub-screen X bound, sub-screen Y bound (genuinely negative — see W-4 fix below), exact-screen bounds, supra-screen bounds, no-bounds (back-compat).
- Existing GBDKSystemVisitor camera tests still GREEN.

```kotlin
override fun visitCameraSystem(system: CameraSystem): List<CFunction> {
    val sanitizedId = system.id.replace('-', '_').replace(' ', '_')
    val followActorId: String? = system.followActorId
    val boundsWidth: Int? = system.boundsWidth
    val boundsHeight: Int? = system.boundsHeight

    val body = buildList<CStatement> {
        if (followActorId != null) {
            // INT16 rawX = (INT16)_<actor>_x - 80;
            // INT16 rawY = (INT16)_<actor>_y - 72;
            ...
            if (boundsWidth != null && boundsHeight != null) {
                val maxX = boundsWidth - 160         // <-- BUG: negative when boundsWidth < 160
                val maxY = boundsHeight - 144        // <-- BUG: negative when boundsHeight < 144
                // _camera_x = (UINT8)(rawX < 0 ? 0 : (rawX > maxX ? maxX : rawX));
                // _camera_y = (UINT8)(rawY < 0 ? 0 : (rawY > maxY ? maxY : rawY));
                ...
            } else {
                // No bounds — clamp to 0..255 (UINT8 range)
                ...
            }
        }
    }
}
```

The fix is two lines:
```kotlin
val maxX = kotlin.math.max(0, boundsWidth - 160)
val maxY = kotlin.math.max(0, boundsHeight - 144)
```

When `boundsWidth < 160`, `maxX` becomes 0; the resulting clamp `(rawX > 0 ? 0 : rawX)` keeps `_camera_x` at 0 whenever rawX > 0 (the player is past the screen midpoint of the small zone), and the leading `(rawX < 0 ? 0 : ...)` already keeps it at 0 when rawX < 0. Net result: `_camera_x` is permanently 0 for sub-screen zones — camera locked at zone origin, no scroll, no underflow.

**Racer's actual numbers (sanity check for tests):**
- Zone is 19×19 tiles = 152×152 px.
- `boundsWidth = 152` → `maxX = 152 - 160 = -8` (UNDERFLOWS — RED test #1 target).
- `boundsHeight = 152` → `maxY = 152 - 144 = +8` (POSITIVE — does NOT underflow). Therefore a sub-screen Y test using boundsHeight=152 would NOT be RED at HEAD. Closes W-4: Test #2 below uses `boundsHeight = 100` (genuinely sub-screen) so `maxY = 100 - 144 = -44` (genuinely negative; RED at HEAD).
