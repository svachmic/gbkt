# Phase 07.4 Plan 19: Lock the Path C Bug at the JVM Tier (TDD-RED) Summary

Plan 14's round-2 verification false-positive (variable-state evidence accepted in lieu of visual evidence) hid the racer's BG-tilemap-wipe bug for 5 plans. This plan locks the bug at the JVM tier with two new RED test files (4 failing tests, 1 passing back-compat, 1 staged @Ignore) so the bug cannot regress silently again.

## What Got Locked

The architectural rule: **the DSL `clear()` and `print()` keywords, when invoked inside a scene that has a background tilemap (via `tilesetRef` OR via a genre plugin's `enterOps` splice), MUST NOT lower to bare `cls()` / `gotoxy() + printf()` in the generated C — those calls wipe / corrupt the BG tilemap.**

Test #2 in each file exercises the **EXACT racer code path**: actor + vehicle + racing { laps; player; aiOpponents; track } DSL → SportVisitor.visitRacing emits `enterOps` map → GBDKPipelineV2.addGenreEnterOps splices `set_bkg_data + set_bkg_tiles` into `race_enter` → user's `clear()` and `print("LAP:", ...)` follow → bug is observable in `race_enter` body.

## CRITICAL DSL Routing Finding (Forwarded to Plan 20)

At HEAD, **`ScriptBuilder.clear()` (gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/ScriptBuilder.kt:432) emits `RawOp("cls();")` — NOT `ScreenClear` IR.** This is a load-bearing fact for Plan 20:

- DSL `clear()` → `RawOp("cls();")` → `visitRawOp` → `CRawCode("cls();")` (verbatim text). `visitScreenClear` is **never called from this path**.
- The namespaced `screen.clear()` (UIBuilders.kt:826) is a **different DSL surface** and DOES emit `ScreenClear` IR — but the racer calls plain `clear()`, not `screen.clear()`.

**Plan 20 MUST fix BOTH halves:**
1. **DSL routing:** change `ScriptBuilder.clear()` to emit `ScreenClear` IR (one-line change in ScriptBuilder.kt). Otherwise the scene-aware `visitScreenClear` is dead code.
2. **Visitor lowering:** make `visitScreenClear` scene-aware (skip `cls()` for scenes that have a BG tilemap — `tilesetRef != null` OR a genre `enterOps` splice).

If Plan 20 changes only (2) and not (1), the RED Test #2 (`dsl_clear_in_race_scene_with_genre_splice_does_not_emit_bare_cls`) will STILL FAIL — because `clear()` still emits `RawOp("cls();")` which lowers verbatim regardless of how `visitScreenClear` behaves. **The RED test #2 is the forcing function for the DSL routing fix.**

For `print(...)` the routing is already correct: DSL `print(...)` → `PrintOp` → `visitPrintOp`. Plan 20 only needs to make `visitPrintOp` scene-aware (or universally route through `_win_print_at`).

## Verification Methodology Gap This Plan Closes

Plan 14's round-2 verification accepted that `_racing_lap_count_track1 = 3` (a variable-state truth) implied the race had visually completed (a visual truth). It hadn't — the BG was wiped immediately after the genre painted it, and the variable advanced because frame logic ran independently of rendering. The methodology gap was: **visual truths were not expressible at the JVM tier, so verifiers fell back to variable-state proxies that did not constrain the bug.**

These two test files turn the visual truth ("BG tilemap is intact in `race_enter`") into a **JVM-tier text-grep on the generated C** — observable without an MCP play-through, observable in CI, observable on the developer's machine in 1–2 seconds. Future regressions of this exact class are now caught **before** any MCP run.
