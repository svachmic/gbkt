correctly fixtures a 2-scene authored GameIR where one scene is a zero-op
stub (`sceneWithOps("stub", 0)`) and the other is a real scene with 30 ops.
Before Plan 06, the D-10 filter stripped the stub from `codeUnits`, so
`codeUnits.size == 1` matched and the real scene incorrectly landed in bank
0. After Plan 06 the dual guard rejects this shape via the
`game.scenes.size == 1` clause (since `game.scenes.size == 2`) and the
real scene correctly routes through the FFD bin-packer to bank ≥ 1. The
test asserts `slot.bank >= 1` and would fail loudly on a regression to the
pre-fix single-clause gate.

One narrow note on the Plan 06 fix that does NOT rise to a finding but is
worth flagging for follow-up tightening: the dual guard at line 91 now
expresses an invariant — `game.scenes.size == 1` implies `codeUnits.size <= 1`
(a single authored scene can produce at most one code unit; the D-10 filter
can only reduce, not multiply). The `codeUnits.size == 1` clause is therefore
strictly an optimization to short-circuit the `codeUnits[0]` access when the
single scene happens to be zero-op. Either keep both clauses (defense in
depth, current state — acceptable) or simplify to
`game.scenes.size == 1 && codeUnits.isNotEmpty() && codeUnits[0].estimatedBytes <= HOME_BANK_SCENE_BUDGET`
(matches the spec language more directly). The current form is correct; the
choice is stylistic.

## Critical Issues

### CR-02: Unconditional `SHOW_BKG;` in main() risks visible BG artifacts for games without a tilemap

**Status:** unchanged from prior review (Plan 06 did not address this)

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:3544`
**Issue:** `buildMainFunction()` unconditionally adds
`CRawCode("SHOW_BKG;")` immediately after `DISPLAY_ON`. The leading comment
explains the fix is needed for `set_bkg_tiles` (sport_racing genre, Plan
07.4-25), but the emission is unconditional — every game now enables the BG
tilemap layer at boot, including pong, breakout, platformer, and
simple-physics, none of which paint the BG.

Before this change, the BG plane was implicitly disabled (LCDC.BG_ENABLE = 0
at boot). With `SHOW_BKG` unconditionally on, games without a `set_bkg_tiles`
call display whatever VRAM tile-data 0 happens to be — typically all-zero on
cold boot, but not guaranteed across emulators or after a soft reset. This
is a regression risk for every game in `gbkt-examples` that does not paint
the BG.

The diff annotates the emission as "Re-introduced here after the Plan 26
attempt was rolled back; see evidence/round-6-wram-corruption/DIAGNOSIS.md
for the round-6 WRAM-corruption follow-up", suggesting the unconditional
emission is intentional but its blast-radius onto BG-less games was not
considered.

The cross-bank helper at `GBDKPipelineV2.kt:957` correctly gates on
`hasSportRacing && bankAllocation.values.any { it > 1 }`. `SHOW_BKG` should
be similarly gated on "any scene paints a BG tilemap" — it is a globally
scoped fix for a domain-specific (sport_racing / dungeon tilemap) need.

**Fix:** Gate `SHOW_BKG` on the same predicate used for `sceneHasBgTilemap`
at the game level — emit it only when at least one scene either has
`scene.tilesetRef != null` OR has genre enterOps containing `set_bkg_tiles`
/ `set_bkg_data`:

```kotlin
val anySceneHasBg = gameIR.scenes.any { sceneHasBgTilemap(it.id, gameIR, genreEnterOps) }
if (anySceneHasBg) {
    add(CRawCode("SHOW_BKG;"))
}
```

(Hoist `genreEnterOps` from `buildSceneFile` to a shared computation in
`buildCFiles`, or thread it through to `buildMainFunction`.)

Add a JVM-tier regression test: simple-physics's `main.c` MUST NOT contain
`SHOW_BKG;`. The visual-evidence rule (project CLAUDE.md) applies — once
the gate is implemented, a runtime screenshot of pong/simple-physics on
boot is required to confirm no BG garbage is rendered.

## Warnings

### WR-01: Fast-path `mergedHome.copy()` drops `typedefs`, `variables`, `rawSections` from `sceneFile`

**Status:** unchanged from prior review

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:525-529`
**Issue:** The fast-path merge composes `mergedHome` by overriding only three
`CFile` fields:

```kotlin
val mergedHome = homeFile.copy(
    functions = homeFile.functions + sceneFile.functions,
    defines = homeFile.defines + sceneFile.defines,
    includes = (homeFile.includes + sceneFile.includes).distinct(),
)
```

This silently drops `sceneFile.typedefs`, `sceneFile.variables`, and
`sceneFile.rawSections`. Today `buildSceneFile` does not populate those
fields (the returned `CFile` constructor only sets `name`, `bank`,
`includes`, `defines`, `functions`) — so the bug is latent. But this is a
fragile coupling: any future visitor that adds a `CVarDecl` or
`rawSections` to bank1.c would silently lose those declarations on the
fast-path, producing an "undefined-identifier" lcc error that would only
surface for single-scene HOME games (an obscure conditional path).

**Fix:** Merge all `CFile` fields explicitly, or assert they are empty:

```kotlin
require(sceneFile.typedefs.isEmpty()) { "Fast-path merge: sceneFile.typedefs must be empty" }
require(sceneFile.variables.isEmpty()) { "Fast-path merge: sceneFile.variables must be empty" }
require(sceneFile.rawSections.isEmpty()) { "Fast-path merge: sceneFile.rawSections must be empty" }
val mergedHome = homeFile.copy(
    functions = homeFile.functions + sceneFile.functions,
    defines = homeFile.defines + sceneFile.defines,
    typedefs = homeFile.typedefs + sceneFile.typedefs,
    variables = homeFile.variables + sceneFile.variables,
    rawSections = homeFile.rawSections + sceneFile.rawSections,
    includes = (homeFile.includes + sceneFile.includes).distinct(),
)
```

The `require` documents the invariant and fails loudly if a future visitor
adds data without updating the merge.

### WR-02: `guardCrossBankBgTilemapAccess` and `buildBkgTilesLoadBankedHelper` are gated by different predicates → potential linker error

**Status:** unchanged from prior review

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:953-961, 1646-1704`
**Issue:** The helper emission (`crossBankHelper`) is gated on:

```kotlin
hasSportRacing && bankAllocation.values.any { it > 1 }
```

But the call-site transformation (`guardCrossBankBgTilemapAccess`) only
checks:

```kotlin
if (bank > 1) { emit "_bkg_tiles_load_banked(...)" }
```

The transformation fires whenever the matched zone is in bank > 1,
regardless of `hasSportRacing`. If a non-sport genre ever emits a
`set_bkg_tiles(..., _zone_<id>_tiles)` RawOp (e.g. a future RPG or puzzle
genre using the same zone-tilemap naming convention) and a zone is
allocated to bank > 1, the guard emits `_bkg_tiles_load_banked(...)` but
the helper is never emitted → undefined-reference linker error.

Today this is masked because only SportVisitor emits these RawOps. But the
documentation comments in both functions explicitly anticipate other
genres adopting the convention ("Future direction: when a structured
`LoadBackgroundTilemap` ScriptOp lands"), so the latent bug is on the
planned roadmap.

**Fix:** Unify the predicate. Either gate both on `hasSportRacing`, or
gate both on "does any RawOp in any scene's genre enterOps contain
`set_bkg_tiles(..., _zone_..._tiles)`" — the latter is more robust and
matches the actual condition the helper needs to be available for:

```kotlin
val needsCrossBankHelper = bankAllocation.values.any { it > 1 } &&
    gameIR.scenes.any { scene ->
        (genreEnterOps[scene.id] ?: emptyList()).any { op ->
            op is RawOp && op.code.contains("set_bkg_tiles") && op.code.contains("_zone_")
        }
    }
val crossBankHelper = if (needsCrossBankHelper) listOf(buildBkgTilesLoadBankedHelper()) else emptyList()
```

### WR-03: Cross-bank guard regex-parse fallback silently emits the known-buggy form

**Status:** unchanged from prior review

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:1683-1695`
**Issue:** When the args-parsing regex (`bkgTilesArgsPattern`) fails to
match a `set_bkg_tiles(...)` RawOp, the fallback emits `op.code` unchanged:

```kotlin
val callRaw = if (argsMatch != null) {
    "_bkg_tiles_load_banked(${bank}u, $x, $y, $w, $h, $tiles);"
} else {
    // Fallback: can't parse args — emit original op unguarded.
    // This should not happen for well-formed set_bkg_tiles RawOps.
    op.code
}
```

The comment says "This should not happen for well-formed set_bkg_tiles
RawOps" but the recovery path emits the very form the helper is designed
to fix — i.e. an unguarded cross-bank `set_bkg_tiles` from a BANKED scene,
which is the known-broken pattern documented in the surrounding code as
causing `EmulatorFrameHangException` (line 1712). The fallback silently
re-introduces the bug instead of failing loudly.

If the regex ever fails (because a future SportVisitor change adds an extra
argument, uses a different whitespace pattern, or introduces a nested
function call), the build will silently regress to the round-7 broken
state.

**Fix:** Throw on regex-parse failure, or at minimum log a WARNING via the
Diagnostic pipeline. Failing loudly forces the developer to add a
regression test for the new shape:

```kotlin
val argsMatch = bkgTilesArgsPattern.find(op.code)
    ?: error("Failed to parse set_bkg_tiles args from RawOp: '${op.code}'. " +
            "Either fix the RawOp emission shape or update bkgTilesArgsPattern. " +
            "Falling back to unguarded emission would re-introduce the round-7 hang.")
```

### WR-04: Cross-bank guard regex is fragile against argument expressions containing commas

**Status:** unchanged from prior review

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:1654-1655`
**Issue:** The args regex captures the first four positional arguments
with `[^,]+`:

```kotlin
Regex("""set_bkg_tiles\s*\(\s*([^,]+),\s*([^,]+),\s*([^,]+),\s*([^,]+),\s*([^)]+)\s*\)""")
```

`[^,]+` rejects any argument that contains a literal comma. If a future
SportVisitor (or any RawOp emitter) ever produces something like:

```c
set_bkg_tiles(min(x, 19), 0u, 20u, 18u, _zone_track_tiles);
```

…the first argument matches up to the first `,` and the regex either fails
or matches in a way that produces a corrupted call. The fallback path
(WR-03) then silently emits the unguarded form.

**Fix:** Use a paren-balanced splitter rather than `[^,]+`. Better, drop
the text-parse entirely and emit the cross-bank wrapper at the
SportVisitor layer (where the structured arg list is still available) —
the RawOp text-match is explicitly called out as a stopgap in the
docstring ("Future direction: when a structured `LoadBackgroundTilemap`
ScriptOp lands, replace this text scan with a typed shape check").

### WR-05: `bankFillErrorThreshold` multiplied into `effectiveCapacity` without validation

**Status:** unchanged from prior review

**File:** `gbkt-analysis/src/main/kotlin/io/github/gbkt/analysis/passes/BankingAnalysisPass.kt:75`
**Issue:** The pass computes:

```kotlin
val effectiveCapacity = (ROM_BANK_SIZE * config.bankFillErrorThreshold).roundToInt()
```

No validation that `bankFillErrorThreshold ∈ (0.0, 1.0]`. If a user (or a
buggy upstream pass) supplies `0.0`, `effectiveCapacity == 0`, and
`findFirstFit` returns `null` for every code unit → bank overflow error on
a game that has sub-byte amounts of code. If supplied `> 1.0`, the
effective capacity exceeds the actual ROM bank size (16384 bytes) and the
bin-packer will pack code that will not fit on the hardware.

Today `AnalysisConfig` constructs with a sensible default, so the bug is
latent. But this is a configuration-injection path the pass should defend
against — the multiply-and-roundToInt happens silently.

**Fix:** Validate the threshold up-front:

```kotlin
require(config.bankFillErrorThreshold in 0.5..1.0) {
    "bankFillErrorThreshold must be in [0.5, 1.0], got ${config.bankFillErrorThreshold}"
}
val effectiveCapacity = (ROM_BANK_SIZE * config.bankFillErrorThreshold).roundToInt()
```

### WR-06: `_bkg_tiles_load_banked` helper-gate and call-site-gate predicates use implicit consistency

**Status:** unchanged from prior review

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:957-961, 1666`
**Issue:** The gate is split:

```kotlin
// Helper-emission site (line 957)
if (hasSportRacing && bankAllocation.values.any { it > 1 }) { listOf(buildBkgTilesLoadBankedHelper()) }

// Call-site (line 1666)
if (bank > 1) { /* emit _bkg_tiles_load_banked(...) */ }
```

The two predicates are consistent in practice today (the helper is emitted
if ANY zone is remote; the call-site fires for the specific zone that is
remote) but they live in two functions and could drift. WR-02 already
calls out the linker-error risk if `hasSportRacing == false` but a RawOp
says otherwise; this finding extends the concern to the inverse: if
dead-code elimination ever trims out the SportVisitor enterOps splice for
a scene, the helper is still emitted (wasting 8–16 bytes of HOME) but
never called.

**Fix:** Co-locate the helper emission with the call-site rewrite — when
`guardCrossBankBgTilemapAccess` actually emits a `_bkg_tiles_load_banked(...)`
call, mark a flag on the pipeline state, and emit the helper post-hoc only
if the flag was raised. This eliminates the predicate-drift risk and lets
dead-code elimination skip the helper entirely when no call site fires.
Alternative (cheaper): unify per WR-02's suggested fix.

### IN-01: Repeated magic number `6` (bytes/op) across test fixtures

**Status:** unchanged from prior review

**Issue:** Test docstrings and arithmetic repeatedly use `6 bytes/op`
literal: "30 ops * 6 bytes/op = 180 bytes", "1000 ops * 6 bytes/op = 6000
bytes", etc. This is the default `AnalysisConfig.bytesPerStatement` (= 6).
When the config default changes (or a future plan tunes the heuristic),
every test fixture arithmetic comment becomes stale, and the assertions
that depend on the arithmetic (e.g. "exceeds HOME_BANK_SCENE_BUDGET = 4096")

The Plan-06-added regression test at `BankingAnalysisPassTest.kt:260` also
hardcodes "30 enter ops * 6 bytes/op = 180 bytes — well under
HOME_BANK_SCENE_BUDGET (4096)" in its preamble — it inherits the same
trap.

**Fix:** Reference the constants by symbol in test docstrings, and
consider exposing `BYTES_PER_STATEMENT = 6` from `AnalysisConfig` as a
named constant that tests can import. Or extract the boundary calculation
into a helper: `private val bytesPerOp = AnalysisConfig().bytesPerStatement`.

### IN-02: Stale doc comment on `findPreferredBank` — does not specify iteration order

**Status:** unchanged from prior review

**File:** `gbkt-analysis/src/main/kotlin/io/github/gbkt/analysis/passes/BankingAnalysisPass.kt:174-198`
**Issue:** The docstring says:

> "Returns the preferred bank for [unit] based on scene locality: if any
> scene that [unit] transitions to is already assigned, prefer that bank.
> Also checks reverse edges (scenes that transition to this scene)."

The implementation iterates ALL forward edges before falling back to ALL
reverse edges, returning the FIRST match in each pass. The docstring does
not mention this ordering — a reader expects "any match returns its bank",
but the iteration order of `transitionGraph` is map-iteration-order
(insertion order for `LinkedHashMap`). Two callers with the same logical
input but different graph-construction order could get different
preferred banks.

This is more a documentation issue than a correctness bug (FFD with a
"first locality match" tie-breaker is reasonable), but the docstring
should say so.

**Fix:** Clarify the docstring to explicitly call out the precedence:
"forward-edge target first; if none, reverse-edge source; ties broken in
graph-iteration order (which mirrors scene declaration order in the IR)."

### IN-04: simple-physics `enter` block re-initializes posX/posY but does not sync the smiley sprite

**Status:** unchanged from prior review

**File:** `gbkt-examples/simple-physics/src/main/kotlin/io/github/gbkt/examples/simple_physics/SimplePhysics.kt:66-72`
**Issue:** The `enter` block sets `posX set 1024; posY set 1024; spdX set
0; spdY set 0;` but does not call `smiley.moveTo(posX shr 4, posY shr 4)`.
The sprite's `_smiley_x` / `_smiley_y` retain their previous values
(initially 64 from `actor { position(64, 64) }`) until the first
`frame { }` runs and emits the `moveTo` call.

For this game it is harmless — the first frame syncs the sprite to (64,
64), which matches the initial actor position anyway. But the pattern is a
trap for any reader extending the example: changing the initial `actor
position` without updating the `enter` block (or vice versa) would cause
the first frame to visibly snap the sprite to its new location.

**Fix:** Add `smiley.moveTo(posX shr 4, posY shr 4)` to the `enter` block
to make the initial sync explicit and the example more robust to
copy-paste modifications.
