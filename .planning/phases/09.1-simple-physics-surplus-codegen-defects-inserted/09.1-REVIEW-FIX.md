### BL-01: D-11 suggestion log emits non-existent DSL syntax and unknown cartridge name

**Files modified:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/CompileRomTask.kt`
**Commit:** `be7017fc`
**Applied fix:** Replaced the broken suggestion `config { cartridge(CartridgeType.ROM_MBC5) }` with the correct DSL property assignment. The new suggestion now reads `config { cartridge = "MBC5_RAM_BATTERY" }` when RAM banks are configured, or `config { cartridge = "MBC5" }` otherwise. ### CR-02: D-12 "per-example MBC regression contract" was vacuous

**Files modified:** `gbkt-backend-gbdk/src/test/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/MbcTypeProbeTest.kt`
**Commit:** `691975df`
**Status:** fixed: requires human verification

**Applied fix:** Replaced the zero-op `simplePhysicsLikeGameIR()` and `pongLikeGameIR()` fixtures with realistic per-example shapes (5 enter + 25 frame ops for simple-physics; 10 enter + 40 frame ops for pong). Extended `sceneWithOps` to take `enterN`, `frameN`, and `exitN` so future fixtures can mirror real DSL densities precisely.

**Revised assertion semantics.** With realistic op counts the single-scene games no longer "stay in bank 0" — FFD reserves bank 0 as HOME, so even a single-scene game gets assigned to bank 1. The old assertion `assignments.isEmpty() || all { bank == 0 }` was a tautology when fixtures had zero ops. The new assertion is `assignments.size == 1 && play.bank >= 1`, which actually pins the D-12 contract: a non-trivial single-scene game produces exactly ONE bank slot at bank >= 1, which is what triggers `CompileRomTask.readMbcType` to upgrade ROM_ONLY to MBC5.

**Why "requires human verification":** This is a logic-tier change (assertion semantics inverted from "stays bank 0" to "exactly one bank >= 1"). The new assertion passes against the current FFD implementation, and the test failure mode now actually catches regressions in the D-12 path, but a human should confirm that the inverted assertion accurately reflects the project's intent for ROM_ONLY single-scene games (the user-level question being: should simple-physics be silently MBC-upgraded, or should it stay in HOME via some currently-missing single-scene bank-0 fast-path?).

Also added a fourth test (`D-10 filter skips all-empty scenes`) that locks the actual semantics of the D-10 filter — namely that it only excludes scenes with ALL three op lists empty.

Removed the misleading "Mirrors the real simple-physics DSL ... was previously empty" comment.

### WR-02: `ScriptOpVisitor.visitSetPosition` does not sanitize actor IDs

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/visitor/ScriptOpVisitor.kt:605-617`
**Reason:** skipped: out-of-scope for phase 09.1 per orchestrator guidance.
**Verification:** `git blame -L 605,617` on `ScriptOpVisitor.kt` shows the function was last modified by commit `1493acb62` (2026-03-22) — well before phase 09.1. The review itself acknowledges this is "not introduced by Plan 01, but it is now exercised by the new `ActorRef.moveTo(Expr, Expr)` overload". The latent sanitization gap predates the phase and a fix would either need to sanitize at every ScriptOpVisitor site that constructs an actor-coordinate variable (broad surface, cross-cutting) or tighten the schema at `GameBuilder.registerActor` to forbid dots in actor IDs (effectively the same blast radius as a system-wide codegen change). Per the user-feedback rule on routing wide blast radius to a proper new phase, leaving the broader sanitization fix for a follow-up.

**Original issue:** `ActorVisitor.visit()` sanitizes actor IDs (`_${sanitizeId(actor.id)}_x/_y`) when declaring position variables, but `ScriptOpVisitor.visitSetPosition()` emits `_${op.actorId}_x` (no sanitization). Any actor ID containing a dot (or other sanitizer-mapped character) would produce a C variable name on the LHS that does not match the declared variable on the RHS, producing a compile error. No present example or test exercises this — the bug is latent.
