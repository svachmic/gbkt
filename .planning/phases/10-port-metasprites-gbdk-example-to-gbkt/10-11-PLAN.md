Three implementation options:
(a) Add a new DSL helper `bgFillCheckerboard()` callable from scene.enter { } that lowers to the two calls + the pattern[] declaration. Smallest user-facing addition; explicit intent.
(b) Use existing tilemap DSL with a 1-tile tilemap. Larger surface, less direct.
(c) Inline in port assembly via existing `raw()` escape hatch. Discouraged per D-overfitting-3 (raw is deprecated per CLAUDE.md "raw() is also deprecated").

Recommendation: option (a) — add `fun ScriptBuilder.bgFillCheckerboard()` (or `bgFill(pattern: ByteArray)`) as a thin DSL helper. Lowers via a new dedicated ScriptOp (e.g. `BgFillPattern(patternBytes: List<Int>)`) OR via a pipeline-level constant emission. Smallest viable shape: a new `BgFillPattern` ScriptOp in gbkt-ir + visitor handler. Pattern bytes are emitted as a `const uint8_t <name>_pattern[] = { ... }` at the top of the bank's C file, and the scene.enter { } call lowers to the two C call statements.

Alternative (simpler): emit the pattern constant + the two calls directly from `bgFillCheckerboard()` via CRawCode — no new ScriptOp needed. Less typed but minimal surface area. PICK THIS if the existing DSL/IR doesn't have a clean BgFill surface today (verify by grepping for `fill_bkg_rect` / `set_bkg_data` in existing visitors).
