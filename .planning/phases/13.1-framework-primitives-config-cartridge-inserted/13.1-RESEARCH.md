## Summary

Phase 13.1 replaces three categories of string-typed / hand-computed values in the gbkt `config { }` block with typed, analysis-derived primitives. The changes are strictly config-block scoped with no frame-logic or codegen-shape risk.

The key insight driving all three mechanisms is that the Gradle plugin's `GenerateCWorkAction` runs in a **classloader-isolated worker** whose `runtimeClasspath` includes `gbkt-ir` (since the game's compiled Kotlin classes transitively depend on it). This means the `Cartridge` enum class, once placed in `gbkt-ir`, is accessible by name to the reflective extraction code in `GenerateCTask.writeBuildMetadata()` — the enum's `getMbcByte()` method can be called reflectively without any static import. This settles D-04 in favor of the reflective accessor approach.

For D-05/D-06 (derive romBanks), the natural injection point is `GBDKBackend.generateV2()` at the exact point where `AnalysisConfig.fromCartridgeConfig(gameIR.config)` is called (line 88 of `GBDKBackend.kt`). When `CartridgeConfig.romBanks` is `null` (new optional sentinel), the backend derives the count by running a first-pass analysis to count how many banks the packer would need, then passing that count as `maxBanks`. When non-null and below the derived need, it hard-fails before the pipeline runs.

For D-13 (CompileRomTask auto-upgrade), the auto-upgrade logic currently guards against mismatches between DSL config and generated C. Under the typed enum + D-06 hard-error path, analysis already ensures `romBanks` is never undersized. The auto-upgrade becomes a dead-letter (no game will ever reach `CompileRomTask` with `mbcType=0x00` AND `#pragma bank N > 0` because D-06 kills the build earlier). The recommended disposition: keep the upgrade as a belt-and-suspenders fallback for non-gbkt C invocations but update its suggestion message to use typed DSL syntax.

**Primary recommendation:** Use the `gbkt-build.properties` channel for all three requirements — it already carries `cartridge`, `mbcType`, and `gbcMode`; adding `ramBanks` (D-07) and `romBanks` (D-05 derived value) is a natural extension of the existing pattern.

## Mechanism Findings (Claude's Discretion Items Resolved)

### D-04: Enum MBC Byte → Gradle Plugin — RECOMMENDED: Reflective Accessor

**Finding:** The `GenerateCWorkAction` runs with `workerExecutor.classLoaderIsolation { classpath.from(runtimeClasspath) }`. The `runtimeClasspath` is the full runtime classpath of the game Kotlin module, which transitively includes `gbkt-ir.jar`. Therefore the `Cartridge` enum class IS accessible to `Class.forName("io.github.gbkt.core.ir.Cartridge")` in the worker's classloader. [VERIFIED: direct code read of `GenerateCTask.kt:132`]

**Recommended Mechanism:** Add a `val mbcByte: Int` property (with `@JvmField` or a `getMbcByte()` companion function) directly on the `Cartridge` enum:

```kotlin
// In gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/Types.kt
enum class Cartridge(val mbcByte: Int) {
    ROM_ONLY(0x00),
    MBC1(0x01),
    MBC1_RAM(0x02),
    MBC1_RAM_BATTERY(0x03),
    MBC3_TIMER_BATTERY(0x10),
    MBC5(0x19),
    MBC5_RAM_BATTERY(0x1B),
}
```

In `writeBuildMetadata`, replace the `CARTRIDGE_MBC_MAP` lookup with:

```kotlin
// Replace:
//   val mbcType = CARTRIDGE_MBC_MAP[cartridgeName] ?: "0x00"
// With:
val mbcByteMethod = cartridge::class.java.getMethod("getMbcByte")
val mbcByteInt = mbcByteMethod.invoke(cartridge) as Int
val mbcType = "0x%02X".format(mbcByteInt)
```

Kotlin enum properties compile to `getPropertyName()` getter methods on the JVM. The enum value returned by `getCartridge()` on the config object IS a `Cartridge` instance (not a String), so `cartridge::class.java.getMethod("getMbcByte")` resolves correctly via the same isolated classloader. [VERIFIED: Kotlin enum JVM compilation contract; confirmed via `GbcTarget` precedent which is already read reflectively by the same method pattern for `gbcMode`.]

**Why not the serializer-resolved path?** The `gbkt-build.properties` write occurs in `writeBuildMetadata()` in `GenerateCWorkAction` which already has direct access to the live config object. Routing through the serializer would require serializing the IR to JSON and deserializing it in the plugin — a round-trip that adds complexity and a dependency on the JSON format. The reflective accessor is cleaner and consistent with how `gbcMode` is already handled. [ASSUMED: no additional classloader constraints block this based on how `gbcMode` reflective read already works]

**Delete:** `CARTRIDGE_MBC_MAP` companion object in `GenerateCTask.kt` lines 672-682. [VERIFIED: direct code read]

### D-13: CompileRomTask Auto-Upgrade — RECOMMENDED: Keep as Belt-and-Suspenders, Update Message

**Finding:** `CompileRomTask.readMbcType()` triggers the ROM_ONLY→MBC5 upgrade when `mbcType == "0x00"` AND `detectMaxBank(sourceFiles) > 0` (banking present in generated C). Under the typed enum + D-06 hard-error path:

- If the author declares `cartridge(Cartridge.ROM_ONLY)` with actual banked zones, the build fails at analysis time (D-06) before any C is generated — `CompileRomTask` never runs.
- If the author omits `cartridge()` (defaults to `Cartridge.ROM_ONLY`), the D-05 romBanks derivation in `GBDKBackend.generateV2()` will detect the need for banking and either auto-upgrade the MBC type (raising to MBC5 when derivation shows more than 2 banks needed) or fail with an error if the user explicitly specified `romBanks` too small.

**Recommended Disposition:** Keep the auto-upgrade code in `CompileRomTask.readMbcType()` as a belt-and-suspenders fallback (it guards against edge cases like hand-crafted C or future backend extensions that bypass analysis). Update the suggestion message to reference typed DSL:

```kotlin
// Before: "set `config { cartridge = \"MBC5_RAM_BATTERY\" }` to silence"
// After:  "set `config { cartridge(Cartridge.MBC5_RAM_BATTERY) }` to silence"
```

Additionally, the `ramBanks.getOrElse(0)` check at line 268 currently reads from the Gradle extension (`extension.ramBanks`). Under D-07, `ramBanks` flows from `gbkt-build.properties`, so update `readMbcType()` to first check `props.getProperty("ramBanks")` from the same properties file before falling back to the Gradle extension. [ASSUMED: this is the correct sequencing — needs planner to verify the property file is always written before CompileRomTask reads it]

**Constraint honored:** No string parsing of free cartridge strings. The suggestion message now references `Cartridge.*` enum, but the upgrade decision itself is based on the numeric `mbcType` byte, not a string. [VERIFIED: direct code read of `CompileRomTask.kt:259-283`]

### D-05/D-06: BankingAnalysisPass Derived Count — RECOMMENDED: `CartridgeConfig.romBanks` becomes `Int?`

**Finding:** `AnalysisConfig` is constructed from `CartridgeConfig` in `GBDKBackend.generateV2()` at line 88 via `AnalysisConfig.fromCartridgeConfig(gameIR.config)`. The factory method currently uses `config.cartridge.startsWith("ROM_ONLY")` etc. — string matching. [VERIFIED: direct code read of `AnalysisConfig.kt:85-97`]

**Recommended Mechanism:**

1. Change `CartridgeConfig.romBanks: Int = 2` to `CartridgeConfig.romBanks: Int? = null` — null means "derive from analysis." [ASSUMED: null sentinel is clean for Kotlin; no existing serialized JSON will break because `optInt("romBanks", 2)` in deserializer safely returns `2` for old JSON]

2. In `GBDKBackend.generateV2()`, before constructing `AnalysisConfig`, add a derivation step:

```kotlin
// D-05/D-06: Derive or validate romBanks
val effectiveRomBanks: Int = when (val declared = gameIR.config.romBanks) {
    null -> {
        // Derive: run a pass with unconstrained maxBanks (cartridge type max),
        // count the highest bank assigned, round up to a valid rom bank count.
        val typeMax = Cartridge.maxBanksFor(gameIR.config.cartridge)
        val probeConfig = AnalysisConfig.fromCartridgeConfig(gameIR.config.copy(romBanks = typeMax))
        val probeResult = DefaultPipeline.create().execute(PassContext(game = gameIR, profile = profile, config = probeConfig))
        val maxAssigned = (probeResult as? PassResult.Success)
            ?.context?.bankAssignments?.values?.maxOfOrNull { it.bank } ?: 0
        nextPowerOfTwo(maxAssigned + 1).coerceAtLeast(2)
    }
    else -> {
        // Validate: run derivation above; fail if declared < derived
        val derived = /* same as null branch */ ...
        if (declared < derived) {
            throw GradleException(
                "romBanks=$declared too small; banking analysis needs $derived. " +
                "Set romBanks >= $derived or remove romBanks to auto-derive."
            )
        }
        declared
    }
}
val analysisConfig = AnalysisConfig.fromCartridgeConfig(gameIR.config.copy(romBanks = effectiveRomBanks))
```

3. Update `AnalysisConfig.fromCartridgeConfig()` to accept `Cartridge` enum instead of `config.cartridge.startsWith("MBC5")` string matching:

```kotlin
fun fromCartridgeConfig(config: CartridgeConfig): AnalysisConfig {
    val typeMax = when (config.cartridge) {
        Cartridge.ROM_ONLY                       -> 2
        Cartridge.MBC1, Cartridge.MBC1_RAM,
        Cartridge.MBC1_RAM_BATTERY               -> 32
        Cartridge.MBC3_TIMER_BATTERY             -> 128
        Cartridge.MBC5, Cartridge.MBC5_RAM_BATTERY -> 256
    }
    val effectiveMax = minOf(typeMax, config.romBanks ?: typeMax)
    return AnalysisConfig(maxBanks = effectiveMax)
}
```

**No new accessor on `PassContext` needed.** The derived count comes from reading `bankAssignments.values.maxOfOrNull { it.bank }` on the probe result, then passing it to the main `AnalysisConfig`. The `PassContext.bankAssignments` already holds this information after `BankingAnalysisPass.run()`. [VERIFIED: direct code read of `PassContext.kt` and `BankingAnalysisPass.kt:140-153`]

**Note on double-run cost:** The probe run is a pure JVM operation with no I/O; for the 8 example games the probe completes in milliseconds. The double run is acceptable. [ASSUMED: performance acceptable at this scale]

## Common Pitfalls

### Pitfall 1: `AnalysisConfig.fromCartridgeConfig` Dual-Call During romBanks Derivation

**What goes wrong:** D-05 derivation runs the full analysis pipeline twice (once to derive romBanks, once as the real run). If the first run has side effects (file writes, non-determinism), the second run may diverge.

**Why it happens:** `BankingAnalysisPass` is a pure function of `PassContext` (immutable copy pattern) — no file I/O in the pass itself. The only file-writing passes are `BudgetAuditPass` (writes `optimization-report.json`) and `VRAMLayoutPass` (reads asset manifest). The probe run uses the same immutable IR but a different `AnalysisConfig.maxBanks`.

**How to avoid:** In the probe run, pass `outputDirectory = null` to prevent `BudgetAuditPass` from writing files. Also pass `assetManifest = null` if there is a risk of double-reading manifest state. This is a clean option since `PassContext` accepts both as nullable. [VERIFIED: `PassContext` fields `outputDirectory: File?` and `assetManifest: AssetManifest?` are both nullable]

**Warning signs:** `optimization-report.json` written twice with different bank counts in the same build.

---

### Pitfall 2: `gbkt { ramBanks }` Extension Deprecation Timing

**What goes wrong:** `banks/build.gradle.kts` sets `gbkt { ramBanks.set(2) }` (line 40). `CompileRomTask` reads `ramBanks` from this extension at line 134: `val ramBankCount = ramBanks.getOrElse(0)`. If the Gradle extension is deprecated without updating the CompileRomTask read path, the `banks` example will produce ROMs without the `-Wl-ya2` linker flag, breaking SRAM.

**Why it happens:** D-07 says DSL `config { ramBanks }` flows to `gbkt-build.properties`; `CompileRomTask` reads from there. But `CompileRomTask` currently reads the Gradle extension first, which overrides the properties file.

**How to avoid:** In `CompileRomTask.compile()`, change the read order: check `gbkt-build.properties` for `ramBanks` FIRST, then fall back to the Gradle extension. This preserves backward compatibility while making DSL the primary source. Add the `ramBanks` write in `GenerateCTask.writeBuildMetadata()` before this migration.

**Warning signs:** ROM builds without `-Wl-ya` flag after removing `ramBanks.set(2)` from `build.gradle.kts`.

---

### Pitfall 3: `null` romBanks Serialization Round-Trip

**What goes wrong:** `GameIRSerializer.deserializeCartridgeConfig` currently uses `json.optInt("romBanks", 2)` — so old serialized JSON files (with `"romBanks": 2`) deserialize to `romBanks = 2` (not null). After the change, newly serialized null is stored as `-1` (or absent key). Round-tripping old JSON with the new deserializer will give `romBanks = 2`, not `null` — meaning games that used to have explicit `romBanks = 2` will now have it overridden rather than auto-derived.

**Why it happens:** Backward compatibility between old-format and new-format serialized IR.

**How to avoid:** Use a JSON absent-key sentinel: serialize null as absent key (don't write the `"romBanks"` field), and deserialize with `if (json.has("romBanks")) json.getInt("romBanks") else null`. Old JSON that has `"romBanks": 2` will deserialize to explicit `2`; new null will deserialize to null. This is backward compatible.

**Warning signs:** Integration tests that use serialized GameIR fixtures fail because `romBanks` is unexpectedly `null` or `2` in wrong cases.

---

### Pitfall 4: `@Suppress("UNUSED_VARIABLE")` on Delegate in Game Block (D-09)

**What goes wrong:** `val saves by saveData { }` at game block scope triggers a Kotlin compiler warning: "Variable 'saves' is never used". Without `@Suppress("UNUSED_VARIABLE")`, the build may emit a warning that escalates to an error in strict mode.

**Why it happens:** The delegate pattern registers the system via side effect in `provideDelegate`, but Kotlin doesn't know `saves` is used inside scene blocks (it's a DSL-level reference, not a Kotlin local variable reference in the same scope).

**How to avoid:** Add `@Suppress("UNUSED_VARIABLE")` to the delegate declaration per D-09. This is the accepted temporary state until Phase 13.2.

**Warning signs:** Build warnings about unused variables on the `saves` binding.

---

### Pitfall 5: `AnalysisConfig.fromCartridgeConfig` Enum Exhaustiveness

**What goes wrong:** After changing `CartridgeConfig.cartridge` from `String` to `Cartridge`, the `when` block in `fromCartridgeConfig` must be exhaustive. If a new `Cartridge` enum entry is added in the future without updating `fromCartridgeConfig`, the Kotlin compiler will emit a warning (not an error for `when` on `else`-less non-sealed enums that is assigned to a val).

**How to avoid:** Write `fromCartridgeConfig`'s `when` block as an expression (returning from `val typeMax = when (config.cartridge) { ... }`) without an `else` branch. Kotlin requires exhaustive `when` when used as an expression on a sealed type or enum — this gives compile-time safety for all 7 enum variants. [VERIFIED: Kotlin exhaustive-when behavior for enums]

```kotlin
// Source: SystemBuilders.kt — mirrors MetaspriteDelegate pattern
@Suppress("UNUSED_VARIABLE")  // D-09: temporary until Phase 13.2 Req #12
class SaveDataDelegate(private val block: SaveDataBuilder.() -> Unit) :
    ReadOnlyProperty<Any?, SaveDataRef> {
    private var ref: SaveDataRef? = null

    operator fun provideDelegate(
        thisRef: Any?,
        property: KProperty<*>,
    ): ReadOnlyProperty<Any?, SaveDataRef> {
        val name = property.name
        val gameBuilder = GameBuilderContext.current
            ?: error("saveData {} must be called inside a game {} block")
        val builder = SaveDataBuilder(name)
        builder.block()
        val system = builder.build()
        gameBuilder.registerSaveData(system)
        ref = SaveDataRef(name)
        return this
    }

    override fun getValue(thisRef: Any?, property: KProperty<*>): SaveDataRef =
        ref ?: error("SaveDataDelegate not initialized — was provideDelegate called?")
}

fun saveData(block: SaveDataBuilder.() -> Unit): SaveDataDelegate = SaveDataDelegate(block)
```

## Open Questions (RESOLVED)

> All three resolved inline below (each carries a `Recommendation:`); plans 13.1-04/06/08 implement the resolutions. Retained for provenance.

1. **romBanks null sentinel in `PassContext.config.maxBanks`**
   - What we know: `AnalysisConfig.maxBanks: Int` (non-nullable) receives the derived count after the probe.
   - What's unclear: Should `AnalysisConfig` also become `maxBanks: Int?` to signal "unconstrained", or should the probe always resolve to a concrete int before constructing `AnalysisConfig`?
   - Recommendation: Resolve to concrete int before constructing (keep `AnalysisConfig` non-nullable; simpler).

2. **`platformer-template` explicit `romBanks = 8` — keep or remove?**
   - What we know: The comment explains "HOME(0) + scenes(1) + zone banks 2..6 + title-card(7) margin". The derivation should compute 7-8 naturally from 5 zones + 2 scene banks.
   - What's unclear: Whether the D-05 derivation will land on exactly 8 or a different value.
   - Recommendation: Remove explicit `romBanks` in `platformer-template` and let derivation run; add a PLAN comment noting the derived value should be confirmed against the original 8 via the migration smoke test.

3. **`SystemRef` in `gbkt-ir` or `gbkt-lang`?**
   - What we know: `TriggerSystem` ScriptOp lives in `gbkt-ir`. `ScriptBuilder.triggerSystem()` lives in `gbkt-lang`. The interface only needs to expose `systemId: String`.
   - What's unclear: If `SystemRef` lives in `gbkt-ir`, `SaveDataRef` (which implements it) must also live in `gbkt-ir` — but `SaveDataRef` is a DSL-level concept used in `ScriptBuilder`. Alternatively, `SystemRef` in `gbkt-ir`, `SaveDataRef` in `gbkt-lang`, with `TriggerSystem` keeping its `systemId: String` (no IR change) and the ref→id extraction happening in `ScriptBuilder`.
   - Recommendation: Keep `TriggerSystem.systemId: String` in IR. Put `SystemRef` interface and `SaveDataRef` both in `gbkt-lang`. The DSL overload `triggerSystem(ref: SystemRef)` simply calls `ops += TriggerSystem(ref.systemId, ...)`. This avoids any IR change and any `gbkt-ir` module boundary violation. [VERIFIED: module boundary rule — `gbkt-ir` must not depend on `gbkt-lang`]

## Project Constraints (from CLAUDE.md)

- **No magic strings (Project Rule #1):** The entire motivation for this phase. DSL must reflect names from property delegates / lambda params.
- **V2 visitor pattern:** IR changes that add new node types require updating all 3 visitor interfaces + all implementing visitors. However, this phase does NOT add new IR node types — `TriggerSystem` keeps `systemId: String`; `CartridgeConfig` fields change types but not the struct identity. No new visitor methods required.
- **Multi-module architecture:** `gbkt-ir` is a leaf module (zero deps). `SystemRef` interface must live in `gbkt-lang` (NOT `gbkt-ir`) unless `TriggerSystem` needs to hold a typed `SystemRef` at IR level — it does not (the DSL-time ref→id resolution removes the need).
- **ROM-build smoke test rule:** Phase touches `GenerateCTask`, `CompileRomTask`, `BankingAnalysisPass`. Verifier MUST run clean `buildRom` before declaring complete.
- **DSL Ergonomics over Code Metrics:** `SaveDataDelegate` may appear to have "too many functions" but follows the established pattern. Detekt exclusion already covers `**/dsl/**`.
- **No parallel gradle clean:** Never fan out two `./gradlew clean ...` against the same project root. ROM regression sweep must chain into a single `./gradlew clean :a:buildRom :b:buildRom ...` command.
