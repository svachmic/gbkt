# Phase 13.1: Code Review Report

**Reviewed:** 2026-06-03T11:23:38Z
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

Phase 13.1 introduces a typed `Cartridge` enum (replacing the previous String cartridge
config), makes `CartridgeConfig.romBanks` nullable with derive-when-null / hard-error-when-too-small
semantics, adds a `saveData` delegate plus a `triggerSystem(SystemRef)` typed reference, and
lowers the cartridge MBC byte through the Gradle plugin via reflection.

The DSL/delegate wiring (`SaveDataDelegate`, `SystemRef`, `BattleRef`, `triggerSystem`) is clean
and self-consistent. The D-05 derive path in `GBDKBackend.generateV2` is correctly structured to
avoid re-entering the D-06 validation branch. However, two correctness defects are present:

1. **The D-06 undersized-romBanks probe in `BankingAnalysisPass` can recurse without bound**
   (StackOverflowError) when a single scene's estimated code exceeds one full ROM bank and the
   author declared a small `romBanks` — the probe never escapes the same overflow branch it was
   spawned from.
2. **The cartridge-config deserializer crashes** on any legacy/unknown cartridge string via an
   unguarded `Cartridge.valueOf`, defeating the "warn and continue" contract documented for the
   serializer and breaking the very migration window this phase creates.

In addition, the `Cartridge` enum is missing MBC2/MBC3 variants that `AnalysisConfig`'s own
documentation table and `fromCartridgeConfig` mapping reference, a small power-of-two correctness
gap exists in `nextPowerOfTwo`, and `nextPowerOfTwo` is duplicated verbatim across two modules.

## Critical Issues

### CR-01: D-06 undersized-`romBanks` probe recurses unboundedly on an oversized single scene

**File:** `gbkt-analysis/src/main/kotlin/io/github/gbkt/analysis/passes/BankingAnalysisPass.kt:329-367`
**Issue:**
`bankOverflowError` handles the D-06 case (`declaredRomBanks != null && declaredRomBanks <= maxBanks`)
by spawning a fresh `BankingAnalysisPass().run(probeCtx)` with `maxBanks` bumped to `>= 256`. The
probe context copies the *AnalysisConfig* (`config = probeConfig`) but does **not** alter
`context.game.config.romBanks`, which stays at the small declared value.

If any single scene's `estimatedBytes` exceeds `effectiveCapacity` (≈16 KB, a full ROM bank),
`findFirstFit` returns null for *every* bank even at `maxBanks = 256`, so the probe's own packing
loop calls `bankOverflowError` again. In that nested call `declaredRomBanks` is unchanged and
`declaredRomBanks <= maxBanks (256)` is still true → it spawns yet another probe → infinite
recursion → `StackOverflowError`, crashing the build instead of emitting the actionable
"romBanks too small" diagnostic.

A scene whose op count × `bytesPerStatement` exceeds 16 KB is plausible for a large RPG scene
(2731 ops at the default 6 bytes/op), and the D-06 branch is precisely the path taken when the
author has set an explicit small `romBanks` — i.e. the exact configuration this phase added.

(Note: the parallel D-05 derive probe in `GBDKBackend.generateV2:96-117` is *not* affected — it
runs through `DefaultPipeline.create().execute()` with `romBanks = null`, so the nested pass's
`bankOverflowError` takes the generic non-D-06 branch and returns normally. Only the
in-pass probe here recurses.)

**Fix:** Make the probe path unable to re-enter the D-06 branch — either null out `romBanks` on
the probed game config (mirroring the D-05 path), or pass an explicit "is-probe" flag that
short-circuits the recursive branch:

```kotlin
val probeCtx = context.copy(
    game = context.game.copy(
        config = context.game.config.copy(romBanks = null) // probe must not re-enter D-06
    ),
    config = probeConfig,
    outputDirectory = null,
    bankAssignments = emptyMap(),
    diagnostics = emptyList(),
)
```

With `romBanks = null`, the nested `bankOverflowError` falls through to the generic branch and
returns a `PassResult.Failed` (so `derived` becomes `maxOf(2, nextPowerOfTwo(0 + 1)) = 2`). That
is still a poor derived number for a genuinely oversized scene, so additionally guard the
oversized-single-scene case up front in `run()` (a scene that cannot fit *any* bank should produce
a dedicated "scene too large to bank" error, not feed the derivation machinery).

### CR-02: `deserializeCartridgeConfig` crashes on unknown/legacy cartridge strings

**File:** `gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/GameIRSerializer.kt:564-572`
**Issue:**
```kotlin
cartridge = Cartridge.valueOf(json.optString("cartridge", "ROM_ONLY")),
```
`Cartridge.valueOf` throws `IllegalArgumentException` for any string that is not an exact enum
constant name. The class KDoc for `GameIRSerializer` explicitly promises unknown enum/subtype
values are handled by warning to `System.err` and continuing — and this phase is the one that
*replaced a free-form String cartridge field with the enum*. Any IR JSON produced before this
phase (or by an external tool) that carries a value like `"MBC5+RAM+BATTERY"`, `"MBC1+RAM"`, or
the lowercased `"rom_only"` will throw an uncaught exception out of `fromJson`, taking down the
caller rather than degrading gracefully. Other enum fields in this file that use `valueOf` have
the same latent issue, but cartridge is the one this phase newly converted from String, so it is
the regression.

**Fix:** Guard with a safe lookup and fall back to the default with a warning, matching the
documented contract:

```kotlin
val cartridgeName = json.optString("cartridge", "ROM_ONLY")
val cartridge = Cartridge.entries.firstOrNull { it.name == cartridgeName }
    ?: run {
        System.err.println(
            "WARNING: Unknown cartridge '$cartridgeName'; defaulting to ROM_ONLY"
        )
        Cartridge.ROM_ONLY
    }
```

## Warnings

### WR-01: `Cartridge` enum omits MBC2 and plain MBC3, contradicting `AnalysisConfig` docs and risking a no-branch `when`

**File:** `gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/Types.kt:142-150`
**Issue:**
The enum defines `ROM_ONLY, MBC1, MBC1_RAM, MBC1_RAM_BATTERY, MBC3_TIMER_BATTERY, MBC5,
MBC5_RAM_BATTERY`. The `AnalysisConfig.fromCartridgeConfig` KDoc table
(`AnalysisConfig.kt:74-84`) documents `MBC2` (16 banks) and `MBC3` (128 banks) rows that have no
corresponding enum constant, so they can never be selected — the documentation is misleading. More
importantly, the only MBC3 variant present is `MBC3_TIMER_BATTERY` (0x10); a game wanting plain
MBC3 (0x11) or MBC3+RAM+BATTERY (0x13) — the most common save-game cartridge — has no option, which
undercuts the `saveData` feature this same phase ships. The `when` in `fromCartridgeConfig` is
exhaustive over the *current* enum, but adding any future constant without updating that `when`
will be a compile error only if the `when` is used as an expression (it is, so this is safe today)
— flagging so the omission is a deliberate decision, not an oversight.
**Fix:** Either add the missing constants (`MBC2`, `MBC2_BATTERY`, `MBC3`, `MBC3_RAM_BATTERY`) with
their official MBC bytes and `when` branches, or correct the `AnalysisConfig` table to list only
the constants that actually exist.

### WR-02: `nextPowerOfTwo` returns a non-power-of-two for inputs > 2^31-... and is duplicated across modules

**File:** `gbkt-analysis/src/main/kotlin/io/github/gbkt/analysis/passes/BankingAnalysisPass.kt:391-400` and `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/GBDKBackend.kt:254-263`
**Issue:**
Two byte-identical copies of `nextPowerOfTwo` exist. Beyond the duplication (a maintenance
hazard — a fix to one will silently diverge), both share an edge case: for `n` that is already a
power of two the bit-twiddle returns `n` correctly, but `derived`/`maxBank` math feeds
`nextPowerOfTwo(maxAssigned + 1)`. When `maxAssigned + 1` is itself a power of two (e.g. a game
that exactly fills banks 0..7 → `maxAssigned = 7` → `nextPowerOfTwo(8) = 8`), the derived ROM bank
count is 8, which is correct; but when `maxAssigned = 8` (bank index 8 used) →
`nextPowerOfTwo(9) = 16` — also fine. The real concern is the duplication plus the fact that
neither copy clamps to the cartridge's actual `typeMax`: a derived value can exceed the cartridge's
maximum bank count (e.g. MBC1 caps at 32 but the derivation can return 64+), producing a `romBanks`
suggestion the hardware cannot honor.
**Fix:** Extract a single `nextPowerOfTwo` to a shared utility (e.g. `gbkt-ir` or `gbkt-analysis`)
and clamp the derived bank count to the cartridge type maximum before emitting it as a suggestion.

### WR-03: D-06 condition `declaredRomBanks <= maxBanks` mis-fires when the author set `romBanks` larger than the cartridge cap

**File:** `gbkt-analysis/src/main/kotlin/io/github/gbkt/analysis/passes/BankingAnalysisPass.kt:335`
**Issue:**
`maxBanks` here is the *effective* cap = `minOf(typeMax, declaredRomBanks)` (computed in
`AnalysisConfig.fromCartridgeConfig:94`). If an author declares `romBanks = 512` on an MBC1 cart
(`typeMax = 32`), `effectiveMax = 32`, and `declaredRomBanks (512) <= maxBanks (32)` is **false**,
so the code takes the generic overflow branch and emits "increase maxBanks in AnalysisConfig" —
unactionable, because the real problem is the cartridge type cannot address 512 banks. The D-06
actionable message is skipped exactly when the author most needs cartridge-type guidance.
**Fix:** Distinguish "declared romBanks exceeds cartridge type max" as its own diagnostic
("MBC1 supports at most 32 banks; you declared 512 — switch to a larger cartridge type or reduce
romBanks") rather than letting it fall into the generic message.

### WR-04: MBC auto-upgrade in `CompileRomTask` ignores the declared non-zero-but-RAM-less cartridge intent

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/CompileRomTask.kt:261-289`
**Issue:**
`readMbcType` only auto-upgrades when `mbcType == "0x00"` (ROM_ONLY). That is correct, but the
fallback at the end (`return if (hasRam) "0x1B" else "0x19"`) hardcodes MBC5 even when banking is
detected and `gbkt-build.properties` is entirely absent. With the new typed `Cartridge` enum and
reflective `getMbcByte` lowering (GenerateCTask:515-519), the metadata file *should* always carry
the correct byte; if `writeBuildMetadata` silently returns false (it has many silent-skip paths —
see GenerateCTask:495-571), the ROM is built as MBC5 regardless of the author's `config { cartridge(...) }`
selection, and the mismatch is invisible. The MBC byte is now owned by the enum (D-03), so a missing
metadata file represents a real lowering failure that is being papered over.
**Fix:** When banking is detected but no `mbcType` was found in metadata, log a WARNING that the
declared cartridge could not be read and the build is falling back to MBC5, so the silent override
is at least surfaced.

### WR-05: Reflective `getMbcByte` cast (`as Int`) can throw `NullPointerException`/`ClassCastException` swallowed as opaque metadata warning

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/GenerateCTask.kt:515-519`
**Issue:**
```kotlin
val mbcByteMethod = cartridge::class.java.getMethod("getMbcByte")
val mbcByteInt = mbcByteMethod.invoke(cartridge) as Int
```
`getMethod("getMbcByte")` is called *unguarded* (unlike `getRamBanks`/`getGbcTarget` below, which
wrap `getMethod` in a try/catch and null-check). For a legacy game whose `Cartridge` predates the
`mbcByte` property, this throws `NoSuchMethodException`, which is only caught by the outer
`catch (e: Exception)` at line 567 — collapsing the whole metadata write (cartridge, mbcType,
ramBanks, gbcMode) into a single "Could not extract build metadata" warning and producing *no*
`gbkt-build.properties`. That then triggers the silent MBC5 fallback in WR-04. Additionally
`invoke(...) as Int` will NPE if the reflective call returns null (it won't for the current enum,
but the cast is unsafe by construction in a reflection-across-classloaders context, which the rest
of this file is careful about — see the `!= null` Pitfall-3 comments at lines 832-834).
**Fix:** Mirror the guarded pattern used for `getRamBanks`/`getGbcTarget`: wrap `getMethod` in its
own try/catch, treat a missing method or null result as "MBC byte unavailable" and skip just the
`mbcType` property rather than aborting the entire metadata write; use `as? Int` with a fallback.

### WR-06: `SaveDataDelegate.getValue` can throw if Kotlin calls `getValue` before `provideDelegate` populated `ref`

**File:** `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/SystemBuilders.kt:630-659`
**Issue:**
`SaveDataDelegate` implements `ReadOnlyProperty` and stores `ref` as a nullable populated in
`provideDelegate`. `getValue` errors with "SaveDataDelegate not initialized" if `ref` is null. This
is correct for the normal `by` path, but the class is `ReadOnlyProperty` *and* exposes
`provideDelegate` returning `this`. If a caller constructs `SaveDataDelegate(block)` and uses it as
a property delegate **without** the `provideDelegate` hook firing (e.g. assigning the same delegate
instance to two properties, or any path where `provideDelegate` is skipped), `getValue` throws at
read time rather than registration time. The `SaveSystem` is also registered as a side effect inside
`provideDelegate`, so reusing one delegate instance across two `val`s would double-register the save
system under whichever property name fires last and silently drop the first. This is a fragility,
not a guaranteed bug.
**Fix:** Document that a `SaveDataDelegate` instance is single-use, and/or guard against
double-`provideDelegate` (throw if `ref != null` on a second `provideDelegate` call) so misuse fails
loudly at build time.

### WR-07: `triggerSystem(SystemRef)` performs no validation that the referenced system was registered

**File:** `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/ScriptBuilder.kt:270-272`
**Issue:**
`triggerSystem` lowers `ref.systemId` straight into a `TriggerSystem` IR node with no check that the
id corresponds to a registered system. The codebase already has a `RefRegistry` mechanism that
`GameBuilder.build()` resolves and fails on for unresolved refs (GameBuilder:694-714). For
`SoundRef`/`SceneRef` the registration is enforced; for the new `SystemRef` path it is not, so a
`triggerSystem(BattleRef("typo"))` or a `saveData` ref whose registration was skipped produces a
`TriggerSystem("typo")` that compiles to a call to a C function that does not exist, surfacing only
as an opaque `lcc` "undefined identifier" error at link time — the exact failure class this
project's typed-ref work aims to eliminate.
**Fix:** Register `SystemRef` usages (or at minimum validate `ref.systemId` against
`refRegistry.registeredIds(RefKind.SYSTEM)` at `build()`), consistent with the scene/sound ref
validation already in place.

## Info

### IN-01: `RpgRegistry` thread-local is never cleared, leaking registrations across builds in the same thread

**File:** `gbkt-genre-rpg/src/main/kotlin/io/github/gbkt/rpg/dsl/RpgExtensions.kt:56-83`
**Issue:**
`RpgRegistry.clear()` is defined and its KDoc says "call after the game-building lambda completes,"
but a repo-wide search finds **no call site**. In a long-lived JVM (Gradle daemon, test runner) that
builds multiple games on the same thread, character/monster defs from a prior `game {}` persist into
the next build's registry. The registry is keyed by id so collisions overwrite rather than
accumulate unboundedly, but stale entries from game A can be read while building game B.
**Fix:** Invoke `RpgRegistry.clear()` from the `game {}` lambda teardown (alongside the
`GameBuilderContext` restore), or remove the dead `clear()` if the registry is genuinely
build-scoped some other way.

### IN-02: `ConfigBuilder` exposes both a mutable `cartridge` property and a `cartridge(type)` setter, inviting inconsistent use

**File:** `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/SystemBuilders.kt:531-585`
**Issue:**
`ConfigBuilder` has `var cartridge` (and `var gbcTarget`) plus `cartridge(type)` / `target(mode)`
functions that set the same field. Two ways to set one value is a minor API smell; the `MagicNumber`
exemption notes the DSL prefers ergonomics, so this is informational. The `romBanks` and `ramBanks`
fields are only settable via direct property assignment (no setter function), so the API is
inconsistent about which style it offers per field.
**Fix:** Pick one convention per field (function setters for all, or `var` for all) for a uniform
config DSL.

### IN-03: `nextPowerOfTwo` KDoc example is wrong for n = 1

**File:** `gbkt-analysis/src/main/kotlin/io/github/gbkt/analysis/passes/BankingAnalysisPass.kt:386-390` and `gbkt-backend-gbdk/.../GBDKBackend.kt:246-253`
**Issue:**
Both KDoc blocks state `nextPowerOfTwo(1) = 1`. That is the actual return value, but ROM bank counts
are never 1 (minimum valid is 2), and every call site wraps the result in `maxOf(2, ...)`. The
example is harmless but documents a value that can never legitimately be used, which can mislead a
future maintainer into removing the `maxOf(2, ...)` guard.
**Fix:** Update the example to a value the function is actually used with, or note the `maxOf(2,...)`
caller contract.

### IN-04: Serializer omits `romBanks` key when null, but reader distinguishes absent-vs-present — verify external producers

**File:** `gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/GameIRSerializer.kt:556-572`
**Issue:**
`serializeCartridgeConfig` omits `romBanks` entirely when null (`config.romBanks?.let { put(...) }`)
and `deserializeCartridgeConfig` reconstructs null via `if (json.has("romBanks")) ... else null`.
This round-trips correctly within gbkt. However an external tool that emits `"romBanks": null`
(JSON null literal) rather than omitting the key will hit `json.has("romBanks") == true` →
`json.getInt("romBanks")` → `JSONException` on a null value. Given the serializer's stated purpose
is interop with non-JVM frontends, this asymmetry is worth hardening.
**Fix:** Use `json.isNull("romBanks")` in the guard: `romBanks = if (json.has("romBanks") &&
!json.isNull("romBanks")) json.getInt("romBanks") else null`.
