Turns GREEN when Plan 13.1-03 (nullable romBanks) + Plan 13.1-06 (derive+validate block) land and the D-06 message is emitted.

### Task 2: RomBanksDerivedTest

D-05 derivation contract: when `romBanks=null` (omitted), GBDKBackend.generateV2() derives:

- The derived count must satisfy the packer (generation succeeds)
- The derived count is a power of two >= 2

Turns GREEN when Plan 13.1-03 (nullable romBanks) + Plan 13.1-06 (probe + derive block) land.

### Task 3: CartridgeMbcByteEmissionTest

Cartridge enum MBC byte contract: the enum owns its hardware byte via `val mbcByte: Int` constructor parameter. The hex format is `"0x%02X".format(mbcByte)` (uppercase, zero-padded). Key assertion:
- `MBC5_RAM_BATTERY.mbcByte == 0x1B` → `"0x1B"` in gbkt-build.properties
- All 7 entries have distinct bytes

Turns GREEN when Plan 13.1-03 adds the Cartridge enum with `mbcByte: Int` to `gbkt-ir/Types.kt`.

## Deviations from Plan

**1. [Rule 1 - Architecture] RomBanksValidationTest module placement**

The plan says the test should "assert that the derive+validate path throws" — but the derive+validate block lives in `GBDKBackend`, which is in `gbkt-backend-gbdk`. The `gbkt-analysis` module cannot import `GBDKBackend` (would be circular: gbkt-backend-gbdk → gbkt-analysis → gbkt-backend-gbdk).

Resolution: The test asserts on the **analysis pipeline diagnostic output** (what the analysis layer emits) rather than catching a GradleException from GBDKBackend. This is the correct architectural placement — Plan 13.1-06 will emit the D-06 diagnostic from within the analysis flow, which is visible to this test. The GBDKBackend may re-wrap the diagnostic as a GradleException, but the root assertion is on the diagnostic message shape.

This is a no-impact deviation: the D-06 contract is still locked correctly; the test turns GREEN when the validation diagnostic is added in Plan 13.1-06.
