# Phase 06.1: V1 Feature Parity Port - Context

**Gathered:** 2026-02-21
**Status:** Ready for planning

<domain>
## Phase Boundary

Port ALL V1 capabilities to V2 pipeline. V2 is ~18% feature-complete vs V1 (deleted in 06-01). Complete feature parity is mandatory — V2 must be feature-equal AND better than V1. The bar is: "no purpose for V2 without everything."

This is organized as multiple 06.X sub-phases using bottom-up layering:
- **06.1** = Foundations (camera, movement, animation, save/load, physics, NPC pathfinding) + C AST cleanup (eliminate all CRawCode)
- **06.2** = UI layer (dialogs, menus, status bars, text rendering)
- **06.3** = World system (floors, zones, tilemaps, encounters, exploration)
- **06.4** = Combat mechanics + items/inventory (engine-level — NOT RPG-specific)
- **06.5** = RPG package (stats, leveling, abilities, status effects, monster AI, RPG battle logic)
- **06.6** = Example games (update Pong/Breakout/Explorer + new minimal platformer)
- **06.7** = LabyrinthOfTheDragon port (reference implementation, runs parallel with UAT)

Phase 06.1 specifically delivers: camera system, movement controller, sprite animation, save/load system, physics primitives, NPC pathfinding, and elimination of all CRawCode stubs from Phase 06.

V1 reference: git commit f82518e (last commit with V1 code).

</domain>

<decisions>
## Implementation Decisions

### Phase organization
- Bottom-up layering: foundations first, then UI, world, combat, RPG, examples, LotD
- Each 06.X phase builds on the previous — no skipping
- Not moving to Phase 07 (UAT) without complete feature parity across ALL subsystems
- LotD (06.7) runs parallel with UAT — does not block Phase 07

### RPG vs engine boundary
- Engine owns: generic combat state machine, turns, damage calculation, items/inventory
- gbkt-rpg owns: character stats, leveling, abilities, status effects, monster definitions, RPG-specific AI, RPG battle logic
- Combat mechanics (06.4) is engine-level — non-RPG games can use it too (Zelda-style interactions)

### 06.1 Foundation systems scope
- Camera: follow-target tracking, screen shake, AND camera bounds (map-edge clamping) — improvement over V1
- Movement controller: per-actor configuration (each actor can have different movement style in same scene)
- Sprite animation: simple frame sequences by default + opt-in condition-based state machines (idle→walk→attack with auto-transitions)
- Save/load: structured saves with versioned slots, automatic checksums, corruption detection. Opt-out pattern — all vars saved by default, mark `transient()` to exclude
- Physics: velocity, acceleration, gravity, bounce as actor-level properties — `actor { velocity(0, 0); gravity(1); bounce(0.8) }`
- NPC pathfinding: grid-based A* + optional waypoint-based patrol routes
- CRawCode elimination: replace ALL existing CRawCode stubs from Phase 06 with typed C AST nodes (zero raw code policy)

### DSL API style
- Full V2 style for ALL ported features — property delegates, operator overloads, type-safe builders
- V1 function/builder names may change to fit V2 patterns
- Camera uses delegate pattern: `val cam by camera { follow(hero); bounds(mapWidth, mapHeight) }`
- Save uses delegate pattern: `val save by saveSystem { slots(3); checksum(true) }`
- Physics as actor properties: `actor { velocity(0, 0); gravity(1) }`
- Animation state machines: condition-based transitions `transition(idle to walk) { whenever(dpad.any) }`

### Codegen approach
- Generated C must be BETTER than V1 — cleaner, fewer globals, better bank utilization
- CRITICAL: No LotD-specific hard-coded patterns. V1 codegen was heavily influenced by LotD porting — V2 must be general-purpose only
- Zero CRawCode policy — every C construct gets a typed AST node. No exceptions
- GBDK/lcc quirks (C89 compliance, etc.) abstracted in C AST layer, not visible in codegen
- Extend existing visitor pattern (ExprVisitor, ScriptOpVisitor, SceneVisitor) for new features — no dedicated codegen classes
- Correctness first, optimization later — don't let optimization concerns slow down porting

### Testing strategy
- Both unit codegen tests (IR in → C out) AND integration tests (full game → compilable C) for every ported feature
- Maximum coverage at both layers

### Claude's Discretion
- NPC pathfinding: Claude determines whether behavior-on-actor or centralized pathfinding system pattern is better
- Specific C AST node types needed to replace CRawCode stubs
- Internal implementation details of camera bounds, save serialization format, physics step function

</decisions>

<specifics>
## Specific Ideas

- "The bar is incredibly high — feature parity AND better"
- "V1 codegen was heavily influenced by LotD porting effort — there were parts that felt like they were almost hard-coded. This is to be avoided at all costs. We want a general purpose game engine, not tailor made framework to write LotD."
- i18n/localization is a first-class QoL feature of gbkt — "modern app development feel, not just LotD." The IntelliJ IDE plugin should have a string editor implementation similar to Android Studio's string resource editor.
- Camera bounds (map-edge clamping) is a V2 improvement over V1 — common need, small scope
- Animation state machines should be opt-in — simple games use frame sequences, complex games use condition-based transitions
- Per-actor movement configuration — player can be smooth while NPCs are grid-based in same scene
- Structured saves with opt-out pattern — minimal boilerplate for the common case

</specifics>

<deferred>
## Deferred Ideas

- IntelliJ string editor (Android Studio-style) for localization — belongs in IntelliJ plugin DX phase or a dedicated i18n tooling phase
- ROM size optimization pass (shared constant tables, function deduplication, dead code elimination in C output) — after correctness is achieved
- New example games beyond platformer — future consideration
- LotD game design improvements — V2 port uses same content, better code only

</deferred>

## Cross-Phase Decisions (apply to all 06.X phases)

These decisions apply across the entire 06.1–06.7 effort:

1. **Full V2 DSL style** — all ported features use delegates, operators, type-safe builders
2. **Zero CRawCode** — every C construct has typed AST nodes
3. **General-purpose engine** — no LotD-specific patterns anywhere
4. **GBDK quirks in C AST** — abstracted, not visible in codegen
5. **Extend visitors** — no dedicated codegen classes for subsystems
6. **Correctness first** — optimization is a later concern
7. **Both test layers** — unit codegen + integration tests
8. **Example updates in 06.6** — not phase-by-phase
9. **LotD as reference implementation** — well-documented, shows V2 best practices
10. **LotD content matches V1** — same gameplay, better DSL code, V2 improvements where visible
11. **LotD localization included** — PO-based i18n is part of the port
12. **LotD drives RPG fixes** — may surface gbkt-rpg issues, fix iteratively
13. **LotD parallel with UAT** — does not block Phase 07
