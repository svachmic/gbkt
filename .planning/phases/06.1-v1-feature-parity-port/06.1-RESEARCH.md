## Summary

Phase 06.1 ports six foundational V1 systems (camera, movement, animation, save/load, physics, NPC pathfinding) into the V2 pipeline while simultaneously eliminating all CRawCode stubs left by Phase 06. The V1 code was deleted in Phase 06-01 (commit `89e23cf`) but is available for reference at git commit `3fb5fa7`.

The V2 pipeline is significantly more complete than the Serena memory suggests — Phase 06 already implemented GBDKSystemVisitor (visitCameraSystem, visitSaveSystem, visitExplorationSystem), SpawnActor/DestroyActor OAM management, SimpleBattle state machine, and all 29 ScriptOp types in ScriptOpVisitor. What remains in Phase 06.1 is strictly additive: new IR nodes, new DSL builders, new SystemIR subtypes, and typed C AST nodes to replace CRawCode where it remains.

**Primary recommendation:** Work feature-by-feature in dependency order — camera bounds first (extends existing CameraSystem), then per-actor movement (new IR fields on ActorIR), then animation state machines (new IR + ScriptOp), then structured save (extend SaveSystem IR), then physics actor-properties (new ActorIR fields + new ScriptOp), then NPC pathfinding (new SystemIR subtype), then CRawCode elimination across all visitors and pipeline.

## Architecture Patterns

### Pattern 1: Extending Existing SystemIR (Camera, Save, Exploration)

The three systems that need enhancement (camera bounds, structured save, per-actor movement) already have SystemIR subtypes and GBDKSystemVisitor methods. The pattern is:

1. **Extend the SystemIR data class** to carry the new configuration fields
2. **Extend the DSL builder** to capture the new configuration
3. **Update the visitor method** in GBDKSystemVisitor to use the new fields
4. **Add new C AST node types** if needed (unlikely — current set is comprehensive)

Example for camera bounds:
```kotlin
// IR extension
data class CameraSystem(
    override val id: String,
    val followActorId: String? = null,   // NEW
    val boundsWidth: Int? = null,        // NEW — map width in pixels
    val boundsHeight: Int? = null,       // NEW — map height in pixels
    val smoothing: Float = 0.0f,        // NEW
    override val sourceLocation: SourceLocation? = null,
    ...
) : SystemIR

// DSL builder extension
class CameraBuilder {
    private var followTarget: String? = null
    private var boundsWidth: Int? = null
    private var boundsHeight: Int? = null

    fun follow(actor: ActorRef) { followTarget = actor.id }
    fun bounds(mapWidth: Int, mapHeight: Int) { boundsWidth = mapWidth; boundsHeight = mapHeight }

    // For delegate pattern: val cam by camera { follow(hero); bounds(256, 256) }
    internal fun build(): CameraSystem = CameraSystem(id = id, followActorId = followTarget, ...)
}
```

### Pattern 2: New SystemIR Subtype (NPC Pathfinding)

NPC pathfinding is a new system with no existing SystemIR subtype. Pattern:

1. **Add `PathfindingSystem` data class** to `gbkt-ir/SystemIR.kt`
2. **Add `visitPathfindingSystem()`** to `SystemIRVisitorI` interface
3. **Implement the visitor** in GBDKSystemVisitor
4. **Add DSL builder** in `gbkt-lang/SystemBuilders.kt`
5. **Wire into GameBuilder** with `pathfinding()` or `npcPathfinding()` method

Since SystemIRVisitorI is NOT sealed (it's an interface), adding a new `visitPathfindingSystem()` method requires updating all implementations. Only one implementation exists: GBDKSystemVisitor. Safe to add.

However, SystemIR itself uses `accept()` dispatch. Adding a new SystemIR subtype `PathfindingSystem` requires:
- `PathfindingSystem.accept()` calls `visitor.visitPathfindingSystem(this)`
- GBDKSystemVisitor must implement `visitPathfindingSystem()`
- SystemIRVisitorI gets a new method (breaking change for external implementors — acceptable since this is internal)

### Pattern 3: ActorIR Extension (Movement, Physics, Animation)

Movement style, physics properties, and animation state machines are per-actor. They belong as fields on ActorIR (or companion data classes referenced from ActorIR):

```kotlin
data class ActorIR(
    val id: String,
    val position: PositionDef,
    val sprite: SpriteDef? = null,
    val hitbox: HitboxDef? = null,
    val movementConfig: MovementConfig? = null,    // NEW
    val physicsConfig: PhysicsConfig? = null,      // NEW
    val animationStates: List<AnimationStateDef> = emptyList(),  // NEW
    val sourceLocation: SourceLocation? = null,
    ...
) : PlatformAnnotatable
```

The companion data classes would live in `gbkt-ir` since ActorIR lives there.

### Pattern 4: New ScriptOp Subtypes

Physics update (`PhysicsStep`), animation state transition (`SetAnimationState`), and pathfinding movement (`PathfindStep`) need new ScriptOp subtypes. Pattern:

1. Add the data class to `gbkt-ir/ScriptOp.kt` implementing `ScriptOp`
2. Add `visitXxx()` to `ScriptOpVisitorI`
3. Implement in `ScriptOpVisitor` (gbkt-backend-gbdk)
4. Add DSL method to `ScriptBuilder`

Since `ScriptOp` is an interface (unsealed), new subtypes require adding `visitXxx()` to `ScriptOpVisitorI`. The only implementation is `ScriptOpVisitor` in gbdk-backend. The simulation interpreter (`ScriptOpInterpreter`) also implements `ScriptOpVisitorI` — must update both.

### Pattern 5: DSL Delegate Pattern for Camera/Save

The CONTEXT.md specifies delegate syntax: `val cam by camera { follow(hero); bounds(mapWidth, mapHeight) }`. This is a property delegate returning a reference object (similar to ActorDelegate pattern from Phase 05.05.3).

Looking at the existing `camera()` GameBuilder method:
```kotlin
fun camera(block: CameraBuilder.() -> Unit) {
    // NOT a delegate — just registers the system
}
```

The delegate pattern requires `CameraBuilder` to implement `ReadOnlyProperty<Any?, CameraRef>` (similar to how `ActorDelegate` works). The `CameraRef` would provide typed access for DSL operations (`cam.shake(4, 10)`, etc.).

This is a DSL-only change — no IR changes needed, just how the DSL method returns a typed reference.

## Feature-by-Feature Implementation Plan

### Feature 1: Camera Bounds (map-edge clamping)

**What V1 had:**
V1 `Camera.kt` had `CameraBuilder` with `follow(entity)`, `bounds { minX, maxX, minY, maxY }`, and smooth-follow support. V1 codegen generated a per-frame camera update that clamps SCX_REG/SCY_REG to map bounds.

**V2 current state:**
- `CameraSystem` IR exists but carries no fields except `id`
- `visitCameraSystem` generates `update_camera_<id>()` with shake logic (using CRawCode)
- `visitCameraOp(FOLLOW)` sets `_camera_target` to actor index
- No follow tracking per-frame, no bounds clamping

**What to add:**
- `CameraSystem` IR: add `followActorId: String?`, `boundsWidth: Int?`, `boundsHeight: Int?`, `smoothing: Float`
- `visitCameraSystem`: generate update function that reads `_<actorId>_x/_y`, applies bounds clamp, writes SCX_REG/SCY_REG — all with typed C AST
- Bounds clamp formula: `clamp(_camera_x, 0, boundsWidth - 160)` — GBDK screen is 160px wide
- Replace CRawCode shake body with: `CIf(CBinaryExpr(CVar("_camera_shake_timer"), ">", CLiteral(0)), ...)`
- DSL: `CameraBuilder.follow(actor: ActorRef)`, `CameraBuilder.bounds(w: Int, h: Int)`

**C AST nodes needed (no new types needed):**
- `CIf` for shake condition and bounds check
- `CBinaryExpr` for clamp math: `max(0, min(targetX, boundsWidth - 160))`
- `CExprStatement(CBinaryExpr(CVar("SCX_REG"), "=", clampExpr))`
- `CUnaryExpr("--", CVar("_camera_shake_timer"))` for decrement

**GBDK hardware note:** SCX_REG / SCY_REG are GBDK globals. Game Boy screen is 160x144px. Map bounds clamping: `camera_x = max(0, min(actor_x - 80, mapWidth - 160))`. Use I16 (not U8) for intermediate math to avoid underflow.

### Feature 2: Per-Actor Movement Controller

**What V1 had:**
V1 had `MovementController` interface with `GridMovementController`, `PhysicsMovementController`, `FreeRoamMovementController`, `TopDownMovementController`. Registered at game level via `game.movementControllers`. V1 codegen generated movement type constants, config tables, and per-type update functions.

**V2 current state:**
- `ExplorationSystem` visitor generates `exploration_move()` with hard-coded grid movement (CRawCode, nx < 31 bounds)
- No per-actor movement configuration
- `ActorIR` has no movement fields

**V2 approach (per CONTEXT.md — "per-actor configuration in same scene"):**
The V1 approach of game-level movement controllers is too LotD-specific. V2 should attach movement config directly to ActorIR:

```kotlin
// New IR types (in gbkt-ir)
data class MovementConfig(
    val style: MovementStyle,  // GRID, SMOOTH, PHYSICS
    val speed: Int = 4,
    val tileSize: Int = 8,
)
enum class MovementStyle { GRID, SMOOTH, PHYSICS }
```

ActorIR gains `val movementConfig: MovementConfig? = null`.

**Codegen approach:**
The `ActorVisitor` gains a method `generateMovementFunction(actor: ActorIR)` that generates an `update_movement_<actorId>()` function. The scene frame function calls this per-actor.

Since movement is fundamentally about updating position variables (already exist as `_<actorId>_x` and `_<actorId>_y`), the codegen emits:
- Grid: read d-pad via `dpad_held(J_UP)` etc., check collision, update position
- Smooth: same but with fractional speed (sub-pixel as I16 variable)
- Physics: see Feature 5

**DSL:**
```kotlin
val player by actor {
    position(80, 72)
    sprite(asset("sprites/player.png")) { ... }
    movement { style(MovementStyle.GRID); speed(4); tileSize(8) }
}
val npc by actor {
    position(40, 40)
    movement { style(MovementStyle.SMOOTH); speed(2) }
}
```

### Feature 3: Sprite Animation State Machines

**What V1 had:**
V1 entities had `states { state("idle") { ... }; state("walking") { ... } }` with enter/exit/tick handlers and condition-based transitions. The codegen generated `STATE_ENTITY_IDLE`, `_entity_state` variable, `entity_update()` function with switch.

**V2 current state:**
- `AnimateOp(actorId, animation)` ScriptOp exists
- `visitAnimateOp` generates a simple frame counter increment (CRawCode)
- No concept of animation states, no condition transitions
- `ActorIR` has no animation state definition

**V2 approach:**

Simple frame sequences (opt-in `animation { frames(0..7); speed(8) }`):
- Add `frameSpeed: Int` to `SpriteDef` or as separate `AnimationDef` on ActorIR
- `visitAnimateOp` generates typed counter logic (replacing CRawCode)

State machines (opt-in):
```kotlin
// New IR types
data class AnimationStateDef(

data class AnimTransition(
```

**C AST nodes needed:** CSwitch (already exists), CSwitchCase (already exists), CIf, CExprStatement.

### Feature 4: Structured Save / Load

**What V1 had:**
V1 `SaveData` had `u16Field()`, `config { slots, checksum: Checksum.CRC8 }`, `save.load(0)`, `save.save(0)`, magic string header validation. Complex SRAM layout with slot offset arithmetic.

**V2 current state:**
- `SaveSystem` IR exists with `id` only — no slot count, no checksum flag
- `visitSaveSystem` saves ALL variables sequentially with 0xAB sentinel — no slots, no checksum, no transient exclusion
- `SaveDataBuilder` has `slots: Int = 1` and `checksum: Boolean = false` but these are NOT passed to `SaveSystem` IR

**V2 approach (per CONTEXT.md — "opt-out pattern, all vars saved by default, `transient()` to exclude"):**

1. Extend `SaveSystem` IR:
```kotlin
data class SaveSystem(
    override val id: String,
    val slots: Int = 1,
    val useChecksum: Boolean = false,
    val version: Int = 1,
    val transientVarNames: Set<String> = emptySet(),  // vars to exclude
    override val sourceLocation: SourceLocation? = null,
    ...
) : SystemIR
```

2. Mark variables as transient in DSL:
```kotlin
var lives by u8Var(3)
var tempFlag by u8Var(0)  { transient() }  // excluded from save
```

This requires `u8Var()` to return an object that has a `transient()` method that registers the variable name in the SaveDataBuilder's excluded list. Since `SaveDataBuilder` is defined at game-builder scope and `u8Var()` is at script scope, the simplest approach is to store transient markers in `GameBuilderContext` ThreadLocal alongside variable registration.

3. Save layout:
- Slot 0 at 0xA000, Slot 1 at 0xA000 + slot_size, etc.
- slot_size = (savedVarCount * 1 byte each) + 1 (sentinel/checksum)
- 8-bit simple checksum: sum all variable bytes, store last byte

4. Replace ALL CRawCode in visitSaveSystem with typed AST:
- `CVarDecl("sram", CPointer(CU8), CRawExpr("(volatile UINT8 *)0xA000"))` — CRawExpr is acceptable for type casts
- `CExprStatement(CCall("ENABLE_RAM", emptyList()))` — or keep as CRawCode since ENABLE_RAM is a GBDK macro with no typed alternative
- `CFor(...)` for slot offset arithmetic

**GBDK hardware note:** SRAM at 0xA000-0xBFFF (8KB per bank). Must call ENABLE_RAM before and DISABLE_RAM after. MBC5 required for SRAM.

### Feature 5: Physics Primitives (Actor-Level)

**What V1 had:**
V1 `PhysicsWorld` was a global physics world with per-entity physics components. Had gravity zones, collision response, friction. Codegen generated per-entity velocity variables, per-frame physics update function, gravity zone table.

**V2 approach (per CONTEXT.md — "actor-level properties, not global physics world"):**

```kotlin
val player by actor {
    position(80, 72)
    sprite(asset("sprites/player.png")) { ... }
    velocity(0, 0)   // dx, dy as I8 variables
    gravity(1)       // pixels per frame^2, applied to dy each frame
    bounce(0.8f)     // coefficient when hitting floor (0.0-1.0, stored as U8 0-255)
}
```

This translates to new ActorIR fields:
```kotlin
data class PhysicsConfig(
    val velocityX: Int = 0,
    val velocityY: Int = 0,
    val gravity: Int = 0,         // fixed-point or integer pixels/frame^2
    val bounce: Float = 0f,       // 0.0-1.0
    val maxFallSpeed: Int = 8,
)
```

**New ScriptOp:** `PhysicsStep(actorId: String)` — emitted by a `physicsUpdate(actor)` DSL call in the frame block. Generates inline per-frame physics application:
```c
// For actor "player":
_player_vy += GRAVITY_PLAYER;     // apply gravity
if (_player_vy > MAX_FALL_PLAYER) _player_vy = MAX_FALL_PLAYER;
_player_y += _player_vy;          // apply velocity
if (_player_y >= FLOOR_Y) {       // floor collision
    _player_y = FLOOR_Y;
    _player_vy = -(UINT8)(_player_vy * BOUNCE_PLAYER / 256);
}
_player_x += _player_vx;         // horizontal velocity
```

All variables: `_player_vx`, `_player_vy` as I8 (or I16 for sub-pixel). Constants: `GRAVITY_PLAYER`, `MAX_FALL_PLAYER`, `BOUNCE_PLAYER` as `#define` or `const UINT8`.

The `ActorVisitor` generates the velocity variable declarations when `physicsConfig != null`. The `ScriptOpVisitor/visitPhysicsStep` generates the per-frame update.

### Feature 6: NPC Pathfinding (Grid A* + Waypoints)

**What V1 had:**
V1 `Pathfinding.kt` (816 lines) had: `NavGrid` (walkable/blocked tiles, weights), `Path` object, `PathQuery` with A* options (heuristic, maxDepth, diagonal), `PathFollow` with callbacks. Many IR nodes: `IRPathFind`, `IRPathFollow`, `IRPathAdvance`, `IRPathAtWaypoint`, etc.

V1 codegen generated A* state tables, path arrays, per-step movement.

**Claude's Discretion: centralized pathfinding system vs behavior-on-actor**

Given V2's general-purpose direction and per-actor composition pattern, the recommendation is **centralized pathfinding system** (new `SystemIR` subtype `PathfindingSystem`) for the A* grid infrastructure, with DSL behavior attached at the actor level.

Rationale:
- A* grid infrastructure (open/closed sets, priority queue) is shared across all NPCs — wasteful to duplicate per-actor
- The nav-grid itself is map-global (references the collision data that is per-scene)
- Waypoint routes are per-NPC actor config

```kotlin
// System defines the A* infrastructure
val pathfinding by pathfindingSystem { gridSize(8); maxOpenNodes(32) }

// Per-NPC actor config
val guard by actor {
    position(40, 40)
    waypoints { point(40, 40); point(80, 40); point(80, 80) }  // patrol route
    // OR:
    followTarget(player)   // chase player
}
```

**New IR types:**
```kotlin
data class PathfindingSystem(
    override val id: String,
    val gridSize: Int = 8,
    val maxOpenNodes: Int = 32,
    val maxPathLength: Int = 32,
    override val sourceLocation: SourceLocation? = null,
    ...
) : SystemIR

data class WaypointRoute(val points: List<Pair<Int, Int>>)
// On ActorIR:
val waypointRoute: WaypointRoute? = null
val followTargetId: String? = null
```

**New ScriptOps:**
- `PathfindStep(npcActorId: String, targetActorId: String)` — compute one step of pathfinding from NPC toward target
- `WaypointStep(npcActorId: String)` — advance NPC along its waypoint route

**Codegen:**
`visitPathfindingSystem` generates:
- A* state tables: `_pf_open[maxOpenNodes]`, `_pf_closed[mapSize]` (UINT8 bitmask), `_pf_parent[mapSize]` (UINT8 index)
- `pf_find_path(startX, startY, endX, endY)` — A* implementation in C
- `pf_step_toward(actorId, targetX, targetY)` — one-step movement helper

`visitWaypointStep` in ScriptOpVisitor generates waypoint patrol advancement.

**Game Boy hardware constraint:** 8KB WRAM. A* for a 32x32 map needs open list (32 nodes × 4 bytes = 128 bytes), closed set (32×32/8 = 128 bytes bitmask), parent array (32×32 = 1024 bytes). Total: ~1.3KB. Acceptable for simple dungeons. For larger maps, reduce maxOpenNodes.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead / Note |
|---------|-------------|-------------------|
| SRAM enable/disable | Custom macro wrapper | `ENABLE_RAM`/`DISABLE_RAM` are GBDK macros — emit as `CRawCode` or `CCall` directly |
| Camera follow math | Custom lerp | Simple integer follow: `if (cam_x < target_x - 4) cam_x++; else if (cam_x > target_x + 4) cam_x--;` |
| A* priority queue | Heap | Use linear scan of small `maxOpenNodes` array — Game Boy WRAM is too small for a real heap; sorted linear scan is correct |
| Fixed-point math | Custom float | Fixed-point 8.8 (or just integer pixels) — no FPU on GB; same pattern V1 used |
| Animation state machine switch | Custom dispatch | Standard `CSwitch` with `CSwitchCase` — pattern already exists in SimpleBattle |

## Common Pitfalls

### Pitfall 1: CameraSystem IR Field Addition Breaks Existing Code
**What goes wrong:** Adding fields to `CameraSystem` data class (in gbkt-ir) breaks all call sites that use positional constructor syntax.
**Why it happens:** `data class CameraSystem(override val id: String, ...)` — any new non-default field breaks callers.
**How to avoid:** All new fields MUST have default values. Existing `CameraSystem(id = "camera")` call sites in tests remain valid.
**Warning signs:** Compilation errors in `GBDKSystemVisitorTest.kt` or `buildSystemGlobalVars()`.

### Pitfall 2: ScriptOpVisitorI Interface Extension Breaks ScriptOpInterpreter
**What goes wrong:** Adding `visitPhysicsStep()`, `visitPathfindStep()` to `ScriptOpVisitorI` requires implementing them in ALL implementations: `ScriptOpVisitor` (gbdk-backend) AND `ScriptOpInterpreter` (gbkt-core tests).
**Why it happens:** Interface methods have no default implementations.
**How to avoid:** Add both implementations simultaneously. `ScriptOpInterpreter` implementation can be a no-op or basic simulation for testing.
**Warning signs:** Compilation error in `gbkt-core/src/test/.../SimulationContextV2Test.kt`.

### Pitfall 3: ActorIR Extension Breaks All Test Fixtures
**What goes wrong:** Adding fields to `ActorIR` constructor invalidates test fixture code using positional args.
**Why it happens:** Data class constructor — all callers must be updated.
**How to avoid:** All new ActorIR fields MUST have default values (`= null` or `= emptyList()`). Verify by building `gbkt-core` tests.
**Warning signs:** Compilation errors in `PongPipelineTest.kt`, `SpriteRenderingTest.kt`, etc.

### Pitfall 4: Camera Bounds Integer Overflow on Game Boy
**What goes wrong:** `target_x - 80` underflows as UINT8 when target is near left edge.
**Why it happens:** GBDK UINT8 wraps at 0.
**How to avoid:** Use INT16 (I16) for camera intermediate calculations. Clamp AFTER converting: `_camera_x = (UINT8)max(0, min((INT16)actor_x - 80, mapWidth - 160))`.
**Warning signs:** Camera jitters to right edge when player is near left edge.

### Pitfall 5: SRAM Corruption Without DISABLE_RAM
**What goes wrong:** If save function throws or exits early (via navigation), SRAM remains enabled.
**Why it happens:** ENABLE_RAM / DISABLE_RAM must be paired.
**How to avoid:** Always generate DISABLE_RAM as the last statement in both save_game and load_game. Use CBlock to guarantee order.

### Pitfall 6: A* Stack Overflow on Embedded
**What goes wrong:** Recursive A* implementation blows the Game Boy's 128-byte call stack.
**Why it happens:** Game Boy has ~128 bytes of stack (HRAM-based).
**How to avoid:** Generate iterative A* (while loop with explicit open/closed arrays), not recursive. V1 also used iterative pattern.

### Pitfall 7: Transient Variable Registration Timing
**What goes wrong:** `u8Var { transient() }` called before SaveDataBuilder is created; or after game{} block, the transient set is stale.
**Why it happens:** DSL execution order — variables registered before save system.
**How to avoid:** Store transient markers in `GameBuilderContext` ThreadLocal alongside variable defs. SaveDataBuilder.build() reads from context at build time (same pattern as variable registration).

## Code Examples

### C AST: Camera Shake Logic (replacing CRawCode)

```kotlin
// BEFORE (CRawCode):
add(CRawCode("if (_camera_shake_timer > 0) {"))
add(CRawCode("    UINT8 offset = (_camera_shake_timer & 1) ? _camera_shake_intensity : 0;"))
...

// AFTER (typed C AST):
CIf(
    condition = CBinaryExpr(CVar("_camera_shake_timer"), ">", CLiteral(0)),
    then = CBlock(listOf(
        CVarDecl("offset", CU8, CTernary(
            CBinaryExpr(CBinaryExpr(CVar("_camera_shake_timer"), "&", CLiteral(1)), "!=", CLiteral(0)),
            CVar("_camera_shake_intensity"),
            CLiteral(0)
        )),
        CExprStatement(CBinaryExpr(CVar("SCX_REG"), "=", CBinaryExpr(CVar("_camera_x"), "+", CVar("offset")))),
        CExprStatement(CBinaryExpr(CVar("SCY_REG"), "=", CBinaryExpr(CVar("_camera_y"), "+", CVar("offset")))),
        CExprStatement(CUnaryExpr("--", CVar("_camera_shake_timer"))),
    )),
    else_ = CBlock(listOf(
        CExprStatement(CBinaryExpr(CVar("SCX_REG"), "=", CVar("_camera_x"))),
        CExprStatement(CBinaryExpr(CVar("SCY_REG"), "=", CVar("_camera_y"))),
    ))
)
```

### C AST: SRAM Read/Write (replacing CRawCode)

```kotlin
// SRAM pointer declaration
CVarDecl("sram", CPointer(CU8), CRawExpr("(volatile UINT8 *)0xA000"))
// ENABLE_RAM is a GBDK macro with no C equivalent — acceptable CRawExpr/CRawCode
CExprStatement(CCall("ENABLE_RAM", emptyList()))
// Variable write: sram[idx] = _score
CExprStatement(CBinaryExpr(CArrayAccess(CVar("sram"), CLiteral(idx)), "=", CVar("_${varDef.name}")))
// DISABLE_RAM
CExprStatement(CCall("DISABLE_RAM", emptyList()))
```

Note: `ENABLE_RAM` and `DISABLE_RAM` are C preprocessor macros, not functions. They expand to inline assembly. The cleanest approach is `CExprStatement(CCall("ENABLE_RAM", emptyList()))` since CCall will emit `ENABLE_RAM()` but GBDK's macros are written to work both as function-like calls and bare expressions. Alternatively, keep as `CRawCode("ENABLE_RAM;")` — this is a documented GBDK quirk (macro, not function), and the zero-CRawCode policy primarily targets structural/logic code, not GBDK hardware macros.

### Camera Bounds Clamp in Typed C AST

```kotlin
// Camera follow with bounds: clamp camera to map bounds
// Generated C: _camera_x = (UINT8)max(0, min((INT16)_hero_x - 80, mapWidth - 160));
val followUpdate = CExprStatement(
    CBinaryExpr(
        CVar("_camera_x"), "=",
        CCast(CU8, CCall("max", listOf(
            CLiteral(0),
            CCall("min", listOf(
                CBinaryExpr(CCast(CI16, CVar("_hero_x")), "-", CLiteral(80)),
                CLiteral(boundsWidth - 160)
            ))
        )))
    )
)
```

Note: `max` and `min` are not standard C89 functions. GBDK provides them or they need `#define max(a,b) ((a)>(b)?(a):(b))`. Use `CTernary` instead of `CCall("max")` for C89 safety:
```kotlin
val clampExpr = CTernary(
    CBinaryExpr(rawX, "<", CLiteral(0)), CLiteral(0),
    CTernary(CBinaryExpr(rawX, ">", CLiteral(mapWidth - 160)), CLiteral(mapWidth - 160), rawX)
)
```

### Animation State Machine: New ScriptOp and Visitor

```kotlin
// ScriptOp definition (gbkt-ir/ScriptOp.kt)
data class SetAnimationState(
    val actorId: String,
    val stateName: String,
    override val sourceLocation: SourceLocation? = null,
) : ScriptOp {
    override fun <T> accept(visitor: ScriptOpVisitorI<T>): T = visitor.visitSetAnimationState(this)
}

// Visitor implementation (ScriptOpVisitor.kt)
override fun visitSetAnimationState(op: SetAnimationState): CStatement {
    val stateConst = "ANIM_${op.actorId.uppercase()}_${op.stateName.uppercase()}"
    return CBlock(listOf(
        CExprStatement(CBinaryExpr(CVar("_${op.actorId}_anim_state"), "=", CVar(stateConst))),
        CExprStatement(CBinaryExpr(CVar("_${op.actorId}_anim_frame"), "=", CLiteral(0))),
    ), sourceLocation = op.sourceLocation)
}
```

## Open Questions

1. **ENABLE_RAM/DISABLE_RAM macro handling**
   - What we know: These are C preprocessor macros that expand to inline `__asm__` — cannot be represented as typed `CCall` without GBDK-specific handling
   - What's unclear: Does emitting `CCall("ENABLE_RAM", emptyList())` produce `ENABLE_RAM()` which works as a macro invocation? Or does GBDK macro require bare `ENABLE_RAM;`?
   - Recommendation: Test empirically with existing GBDK. If `ENABLE_RAM()` doesn't compile, use `CRawCode("ENABLE_RAM;")` — this is a legitimate exception to the zero-CRawCode rule (GBDK-specific macro).

2. **Fixed-point representation for physics**
   - What we know: Game Boy has no FPU; REQUIREMENTS.md explicitly forbids floats in ScriptOp
   - What's unclear: Should gravity/velocity use 8.8 fixed-point (INT16 with 8 fractional bits) or pure integer pixels/frame?
   - Recommendation: Use integer pixels/frame for simplicity (gravity = 1 means +1 pixel/frame/frame). Bounce coefficient stored as UINT8 0-255 (divide by 256 = 0.0-1.0). This is sufficient for Pong/Breakout physics; platformers may need 4.4 fixed-point.

3. **NPC pathfinding map size**
   - What we know: A* closed set for 32x32 map = 1024 bytes WRAM; WRAM is 8KB total
   - What's unclear: Should pathfinding support variable map sizes or fixed 32x32?
   - Recommendation: Fixed maxPathLength (default 32 nodes), variable map size configured in PathfindingSystem IR. The closed set uses bit-packing (1 bit/tile) to minimize WRAM.

4. **Animation state machine transition conditions**
   - What we know: CONTEXT.md says `transition(idle to walk) { whenever(dpad.any) }`
   - What's unclear: Does `whenever(dpad.any)` need to embed the condition in IR as an Expr, or is it a callback block?
   - Recommendation: Embed as Expr — `AnimTransition(toState = "walk", condition = DpadAnyExpr)`. This enables codegen without needing ScriptBuilder context for transitions.
