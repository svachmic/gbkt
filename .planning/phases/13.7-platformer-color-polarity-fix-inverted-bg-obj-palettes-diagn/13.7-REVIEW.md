# Phase 13.7: Code Review Report

**Reviewed:** 2026-06-06
**Depth:** standard
**Files Reviewed:** 9

## Summary

Phase 13.7 adds three deliverables to a build-time Game Boy ROM asset pipeline:
(1) a Spearman luminance-order palette-polarity comparator (`checkPalettePolarity` +
`spearmanRanks` + `spearmanCorrelation`) in `PngUtils.kt`; (2) a non-fatal, ASCII-only
build WARNING wired into both `ConvertZoneTilesetsTask` (BG) and `ConvertSpritesTask`
(OBJ); (3) an additive `set_sprite_palette` emission arm for asset-driven metasprites in
`GBDKPipelineV2.buildMetaspriteSpritePaletteStatements`.

**Scope note (review-method observation, not a code defect):** the `diff_base` supplied in
the config (`1ab2553922...^`) resolves to a Phase 12.7 commit. The true Phase 13.7
implementation lives in commits `980b505d`, `7a074a29`, `3716dd98`, `2142b5d1`, `097f6afd`.
I scoped the review to the genuine 13.7 additions (verified by `git log` per file). The
large unrelated GBDKPipelineV2 hunks in the wide diff (1193, 1597, 2403, 3023, …) belong to
phases 12.9/12.11/13.3/13.4/13.5 and were **not** reviewed as 13.7 work.

**Overall assessment:** The core architecture is sound. The `set_sprite_palette` arm
correctly preserves the 13.3-17 Direction B suppression (gated on `hasSpritePalette`) and
the 12.9 D2a `-keep_palette_order` flag set is untouched. No BLOCKER-class correctness or
security defects were found. The most significant issue is a **latent false-negative in the
polarity comparator** caused by zero-padded PLTE entries that mathematically neutralize the
strict −1.0 reversal threshold on the very BG asset the phase ships (`world1-tileset.png`),
which means the WARNING the phase advertises as a regression guard cannot actually fire for
that asset. Several quality defects (verbatim code duplication the phase's own `PngUtils.kt`
charter was meant to prevent) are also flagged.

## Warnings

### WR-01: Polarity comparator is neutralized by zero-padded PLTE entries — WARNING can never fire on the shipped BG asset

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/PngUtils.kt:249-307` (`checkPalettePolarity`)

**Issue:** The all-equal-luminance degenerate guard (line 282-284) compares the global
`min`/`max` luminance across the *entire* emitted-size window. But `world1-tileset.png` (the
exact BG asset this phase ships and `BgPaletteCShapeTest` exercises) has a 16-entry PLTE in
which only indices 0-3 carry real colors; indices 4-15 are all `RGB(0,0,0)` (verified by
decoding the PLTE chunk: 12 of 16 entries have lum=0). Because index 1 has lum≈236, the
`maxLum - minLum < EPSILON` guard does **not** trip, so the comparator runs over all 16
entries. `spearmanRanks` assigns the 12 tied zero-entries an identical averaged rank in BOTH
the source and emitted series, contributing `d=0` at those 12 positions. With 12 of 16
positions locked at d=0, a Spearman value of exactly −1.0 (strict full reversal) is
mathematically unreachable — so `checkPalettePolarity` returns `false` for this asset even if
the meaningful first-four colors were truly inverted.

Net effect: the BG polarity WARNING — which the phase advertises (and `BgPaletteCShapeTest`
KDoc describes) as the regression guard that "a future change cannot silently invert it" — is
a **false-negative on the one production BG asset in scope**. The guard the phase relies on
is dead for `world1-tileset.png`. (It does not currently misfire because BG is "already
correct", but it provides no real protection.)

**Fix:** Restrict the comparison to the *used* palette window (drop trailing/padding entries
with zero pixel usage, mirroring `countUsedVisibleColors`) before ranking, OR compare each
GBC sub-palette (4-entry group) independently and warn if any sub-palette is a strict
reversal. For example, exclude entries that are not referenced by any pixel and that
duplicate the lum of another entry:

```kotlin
// Before ranking, trim to the meaningful window — e.g. compare per 4-color sub-palette:
val subPaletteSize = 4
require(n % subPaletteSize == 0)
val inverted = (0 until n step subPaletteSize).any { base ->
    val srcGroup = sourceLum.subList(base, base + subPaletteSize)
    val emGroup  = emittedLum.subList(base, base + subPaletteSize)
    if (srcGroup.max() - srcGroup.min() < SPEARMAN_EPSILON) return@any false
    spearmanCorrelation(spearmanRanks(srcGroup), spearmanRanks(emGroup)) < -1.0 + SPEARMAN_EPSILON
}
return inverted
```

### WR-02: Flat 16-entry ranking crosses GBC sub-palette boundaries — semantically wrong baseline

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/PngUtils.kt:274-303`

**Issue:** A GBC background palette array of 16 entries is four *independent* 4-color
sub-palettes, not one 16-step luminance ramp. `checkPalettePolarity` ranks all 16 entries as
a single flat series. Even setting aside WR-01's padding problem, "is the concatenation of
four sub-palettes a strict reversal" is not the question the WARNING claims to answer ("is the
emitted palette luminance order the strict reverse of the source PLTE"). For a real 4×4
tileset palette this produces a baseline that does not correspond to any meaningful hardware
inversion, so the WARNING is both unable to fire on genuine per-sub-palette inversions and
liable to confuse a maintainer who reads the warning text. The OBJ path (sprites) is
single-sub-palette and not affected.

**Fix:** Same as WR-01 — rank per 4-entry sub-palette group rather than over the flat array.
The comparator should take (or infer) the sub-palette stride and evaluate inversion
per-sub-palette.

### WR-03: Palette-parse + RGB8→RGB555 logic duplicated verbatim across both tasks — defeats the PngUtils single-source charter

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertZoneTilesetsTask.kt:591-638` (`parsePaletteRgb555Values` + `parseRgb8OrIntValues`) and `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt:815-847` (`parseSpriteRgb555Values`)

**Issue:** The `palette_color_t <symbol>[N] = { ... }` regex parse, the RGB8 match loop, the
`r8 * 31 / 255` → `(b5<<10)|(g5<<5)|r5` packing, and the decimal/hex fallback are duplicated
near-verbatim between the two tasks (a `diff` of the two bodies shows identical RGB8
conversion). This is precisely the duplication that `PngUtils.kt`'s own header comment
("extracted here … both tasks share the same … parse via a single source of truth") and the
13.6 D2a refactor were created to eliminate (`isIndexedPngShared`, `getTransparentIndexShared`).
The new 13.7 parse helpers were added independently to each task instead of as a shared
`PngUtils` function. A future fix to the RGB8 conversion (e.g. the rounding in WR-04) must now
be made in two places, and the two copies already differ subtly in their empty-result handling
(`parseRgb8OrIntValues` may return an empty non-null list; `parseSpriteRgb555Values` coerces
empty → null).

**Fix:** Promote a single `internal fun parsePaletteRgb555Values(file: File, symbol: String):
List<Int>?` (and the RGB8→RGB555 helper) into `PngUtils.kt` and have both tasks delegate,
mirroring the existing `isIndexedPngShared` pattern.

### WR-04: RGB8→RGB555 conversion uses truncating division — asymmetric with png2asset/GBDK rounding, risks polarity mis-ranking near luminance ties

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt:831-834`, `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertZoneTilesetsTask.kt:622-624`, and the inverse decode `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/PngUtils.kt:291-293`

**Issue:** The parse path packs `r5 = r8 * 31 / 255` (integer truncation), and
`checkPalettePolarity` unpacks `r8 = r5 * 255 / 31` (also truncating). This double truncation
means the emitted-luminance value fed to the Spearman ranker is a lossy, non-round-tripping
approximation of the source RGB. For palettes whose entries are close in luminance (the
comparator's whole purpose is to detect *order*), truncation can swap the relative order of
two near-equal entries, flipping a rank and changing the Spearman result. The source side
(`checkPalettePolarity` lines 275-279) uses the *exact* 8-bit PLTE values, so the two series
are computed on different quantization grids — an apples-to-oranges luminance comparison that
can yield both false positives and false negatives at the margins.

**Fix:** Either (a) compare RGB555 luminance on both sides (quantize the source PLTE to RGB555
first, so both series live on the same 5-bit grid), or (b) carry the original RGB8 values
through to the comparator instead of round-tripping through RGB555. Option (a) is closest to
"what the hardware actually displays":

```kotlin
// quantize source PLTE to RGB555 before computing luminance, matching the emitted grid
fun to5(c: Int) = (c * 31 / 255) * 255 / 31
val sourceLum = (0 until n).map { i ->
    0.299 * to5(srcReds[i].toInt() and 0xFF) +
        0.587 * to5(srcGreens[i].toInt() and 0xFF) +
        0.114 * to5(srcBlues[i].toInt() and 0xFF)
}
```

### WR-05: `gameIR.palettes` SPRITE filter does not distinguish per-scene palette ownership — multi-scene games risk over- or under-suppression

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:5065-5074`

**Issue:** The new arm gates the entire asset-driven upload on a single game-global predicate
`gameIR.palettes.any { it.type == PaletteType.SPRITE }`. Because `spritePalette { }` registers
at the `GameBuilder` (game) level, not the scene level (confirmed in
`PaletteBuilder.SpritePaletteDelegate`), `hasSpritePalette` is global. In a game that declares
*any* sprite palette anywhere — even one used only by a single non-platformer scene — the
asset-driven player's auto-upload is suppressed game-wide. Conversely, a game with multiple
asset-driven metasprites and no `spritePalette{}` uploads each to a distinct OBJ slot
(`proceduralCount + idx`) with no check that those slots don't collide with OBJ palette slots
written by scene-level `spritePalette` uploads or actor-sprite palette code elsewhere. For the
two shipped shapes (platformer = no spritePalette; metasprites-example = has spritePalette) the
behavior is correct, but the predicate is coarser than the "scene is the sole OBJ palette
authority" invariant the Direction-B comment claims to preserve, so a future multi-scene game
can regress silently.

**Fix:** Document the game-global scope of the suppression explicitly in the KDoc, and add an
assertion or test for the mixed case (game with both an asset-driven metasprite AND a
scene-scoped sprite palette that is NOT meant to own that metasprite). Longer term, the
suppression decision should be scene-scoped if scene-level sprite palettes become possible.

## Info

### IN-01: Comparator computes full Spearman correlation when only the strict −1.0 extreme is consumed

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/PngUtils.kt:302-303`

**Issue:** `spearmanCorrelation` returns the full `[-1, 1]` correlation but the only consumer
compares against `-1.0 + EPSILON`. The `n <= 1 → 0.0` sentinel inside `spearmanCorrelation`
(line 181) is unreachable from `checkPalettePolarity` (the `n < 2` guard at line 263 already
returns false), so that branch is effectively dead for this call path. Not a bug, but the API
surface is broader than needed and invites misuse (a caller could treat the `0.0` sentinel as a
real correlation).

**Fix:** Either narrow the comparator to a boolean `isStrictFullReversal(...)` helper, or add a
KDoc note that `0.0` is a sentinel, not a computed correlation. No functional change required.

### IN-02: `parseRgb8OrIntValues` can return an empty (non-null) list, diverging from the sprite-side contract

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertZoneTilesetsTask.kt:613-638`

**Issue:** `parseRgb8OrIntValues` returns `result` directly; when `found` is true the list is
non-empty, but the fallback path can return an empty list if no token parses. `parsePaletteRgb555Values`
(its only caller) then maps empty → null, so the observable behavior is fine. But the
sprite-side twin (`parseSpriteRgb555Values`) folds the empty→null coercion inside the function.
The inconsistency is a maintenance trap (see WR-03).

**Fix:** Make both helpers return `null` for empty results consistently (folded into the shared
helper proposed in WR-03).

### IN-03: Hardcoded absolute path in test fixture reduces portability

**File:** `gbkt-gradle-plugin/src/test/kotlin/io/github/gbkt/gradle/tasks/PalettePolarityWarningTest.kt:336-339`

**Issue:** Test 8 hardcodes `/Users/michalsvacha/GitHub/personal/gbkt/gbkt-examples/metasprites/res/sprites/elephant.png`.
The test is skip-guarded (`if (!elephantSrc.isFile) return`), so it degrades to a silent skip
on any other machine/CI rather than failing — but it also means the test never actually runs
outside the author's checkout, providing zero CI coverage for the OBJ non-fatal path. The
sibling `findPlatformerTemplatePng` helper in the same file already demonstrates the portable
walk-up pattern that should be used here instead.

**Fix:** Replace the absolute path with a walk-up search mirroring `findPlatformerTemplatePng`
(search `gbkt-examples/metasprites/res/sprites/elephant.png` relative to the working dir),
so the test exercises the path in CI where the example is checked out.
