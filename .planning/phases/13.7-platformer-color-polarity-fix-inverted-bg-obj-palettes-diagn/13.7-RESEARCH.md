## Summary

Phase 13.7 fixes inverted GBC palette rendering in the platformer-template example. The investigation reveals two distinct root causes requiring different fixes.

**OBJ (player sprite) inversion is confirmed from static analysis.** The platformer-template player is an asset-driven metasprite (`spritePath != null`). Phase 13.3-17 (Direction B) deliberately excluded asset-driven metasprites from the automatic `set_sprite_palette` upload in `GBDKPipelineV2.buildMetaspriteSpritePaletteStatements()`. `PlatformerTemplate.kt` contains no `spritePalette{}` block in any scene. The result: `set_sprite_palette` is never called for the player, so it renders under the default GBC OBJ palette from `cgb_compatibility()` — a descending {0x7FFF, 0x56B5, 0x294A, 0x0000} palette. The player PNG's PLTE has index 2 = near-white (lum 248) mapping to 0x294A (dark gray) and index 3 = gray (lum 168) mapping to 0x0000 (black). This produces the dark body / light halo symptom.

**BG (zone tileset) inversion requires a live GBC MCP probe to confirm.** Static analysis shows that png2asset output for `world1-tileset.png` with gbkt's flags is IDENTICAL to the GBDK reference. The `set_bkg_palette` call arguments match the reference. The 13.3 Color migration does NOT affect the BG pipeline (it is png2asset-derived, not DSL Color-derived). If BG inversion is confirmed at runtime, the fix locus is not in the palette ORDER but in the GBC VRAM bank gate or some other runtime condition.

**Primary recommendation:** Wave 0 diagnostic plan: (1) build GBDK reference GBC ROM, (2) run GBC MCP probe on both gbkt and reference ROMs, (3) compare screenshots to confirm/deny BG inversion. Wave 1 fix plan: emit `set_sprite_palette` for asset-driven metasprites that lack `spritePalette{}` declarations. Wave 2 fix plan (conditional on BG confirmation): trace BG runtime path.

### Pattern 1: PngUtils.kt — Spearman Rank Correlation for Palette Polarity

**What:** Read the PNG PLTE via `IndexColorModel`, compute Rec.601 luminance per entry, rank entries by luminance, compare with the emitted RGB555 sequence's luminance ranks. If Spearman rank correlation = -1.0, the emission is fully inverted.

**When to use:** Called from both `ConvertZoneTilesetsTask` and `ConvertSpritesTask` after png2asset runs, before the output is committed.

**Example:**
```kotlin
// Source: codebase analysis — PngUtils.kt internal function pattern
// [ASSUMED] exact implementation sketch — verify against actual file structure at implementation time

internal fun checkPalettePolarity(sourcePng: File, emittedPaletteC: File, symbol: String): Boolean {
    // Step 1: read source PLTE luminances
    val image = ImageIO.read(sourcePng) ?: return true
    val colorModel = image.colorModel as? IndexColorModel ?: return true
    val n = colorModel.mapSize
    val reds = IntArray(n); colorModel.getReds(reds)
    val greens = IntArray(n); colorModel.getGreens(greens)
    val blues = IntArray(n); colorModel.getBlues(blues)
    val sourceLum = (0 until n).map { i ->
        0.299 * reds[i] + 0.587 * greens[i] + 0.114 * blues[i]
    }

    // Step 2: rank source lums (ties → equal rank = average rank)
    val sourceRanks = spearmanRanks(sourceLum)

    // Step 3: parse emitted RGB555 values from C file
    val emittedRgb555 = parsePaletteC(emittedPaletteC, symbol) // existing parsePaletteArrayDim helper
    val emittedLum = emittedRgb555.map { rgb555ToLuminance(it) }
    val emittedRanks = spearmanRanks(emittedLum)

    // Step 4: Spearman rank correlation
    val spearman = spearmanCorrelation(sourceRanks, emittedRanks)
    return spearman > -1.0 + EPSILON // true = not inverted, false = inverted
}

private fun rgb555ToLuminance(rgb555: Int): Double {
    val r5 = (rgb555 and 0x1F)
    val g5 = (rgb555 shr 5) and 0x1F
    val b5 = (rgb555 shr 10) and 0x1F
    val r8 = r5 * 255 / 31
    val g8 = g5 * 255 / 31
    val b8 = b5 * 255 / 31
    return 0.299 * r8 + 0.587 * g8 + 0.114 * b8
}
```

### Anti-Patterns to Avoid

- **Blind S_PAL remap:** Do not remap `S_PAL(N)` values to work around inversion. The 13.3-22/24 fix achieved correctness by fixing the SOURCE order, not by patching downstream slot assignments.
- **Hardcoding ascending order expectation:** The luminance comparator MUST use the source PNG's own PLTE as baseline (D-02), not a fixed ascending expectation. A designer may intentionally use a non-ascending palette for stylistic reasons.
- **Emitting set_sprite_palette in bank1.c (scene files):** Keep palette uploads in `buildHomeFile()` (HOME bank, always reachable without bank switching).
- **Re-running png2asset in reverse:** Do not add a post-processing step to reverse the palette array after png2asset runs. The correct fix is upstream (either the source PNG PLTE order, or ensuring the correct palette gets uploaded to GBC hardware).

## D-02c: Luminance Comparator Recommendation

### Predicate: Strict Full-Reversal via Spearman Rank Correlation

**Recommendation:** Use **Spearman rank correlation with threshold -1.0 (strict full reversal)**.

**Reasoning:**
- Neither the world1-tileset PLTE ([dark-teal lum=20, light-green lum=236, mid-green lum=166, dark-green lum=85]) nor the player PLTE ([orange lum=159, black lum=0, near-white lum=248, gray lum=168]) is monotonically ordered.
- A monotonicity check would give false positives for these palettes (they would fail "is ascending?" even when correctly rendered).
- Spearman rank correlation captures ONLY the full-reversal case (Spearman = -1.0) without penalizing non-monotonic but correctly ordered palettes.
- **Strict full-reversal** (Spearman = -1.0 exactly) is more specific than partial reversal detection; it matches the symptom (systematic full inversion, not partial scrambling).

**Luminance formula:** Rec.601: `lum = 0.299*R + 0.587*G + 0.114*B`

**Why Rec.601 over Rec.709 (`lum = 0.2126*R + 0.7152*G + 0.0722*B`):** Rec.601 is the standard for SD/CRT content. Game Boy Color targets a non-standard LCD whose color rendering is closer to CRT-era assumptions. Either formula is acceptable for rank correlation (rank ordering rarely changes between the two); Rec.601 is the existing convention in the gbkt metasprites test assertions.
[ASSUMED: Rec.601 is the existing convention — verify against `MetaspritesGrayPaletteEmissionTest.kt` before coding]

**Tie-handling:** If two entries have equal luminance, assign them equal rank = average of the tied ranks. In Spearman computation, treat tied ranks as equal fractional values. This prevents false positives from all-black padding entries (lum=0).

**RGB555 → Luminance conversion:**
```
r8 = (r5 * 255) / 31
g8 = (g5 * 255) / 31
b8 = (b5 * 255) / 31
lum = 0.299 * r8 + 0.587 * g8 + 0.114 * b8
```
[VERIFIED: bit layout confirmed from CoreTypes.kt: `rgb555 = (b5 shl 10) or (g5 shl 5) or r5`]

**PLTE → Luminance via IndexColorModel:**
```kotlin
val reds = IntArray(n); colorModel.getReds(reds)
val greens = IntArray(n); colorModel.getGreens(greens)
val blues = IntArray(n); colorModel.getBlues(blues)
```
Each component is 0-255 (8-bit). No scaling needed for source PLTE side. [VERIFIED: JVM stdlib docs]

**Epsilon for floating-point comparison:** Use `EPSILON = 1e-9` when testing `spearman < -1.0 + EPSILON`.

## Common Pitfalls

### Pitfall 1: Breaking Direction B (13.3-17) while fixing OBJ upload

**What goes wrong:** The fix adds `set_sprite_palette` for asset-driven metasprites. If done naively, it also uploads palettes for asset-driven metasprites that already have `spritePalette{}` blocks — causing triple-slot collision (Phase 13.3-17 specifically prevented this).

**Why it happens:** `buildMetaspriteSpritePaletteStatements()` operates on `GameIR.metasprites`. Checking only `it.spritePath != null` is insufficient — must also check if any scene contains a `spritePalette{}` for that metasprite.

**How to avoid:** Before emitting `set_sprite_palette` for an asset-driven metasprite, query `GameIR.scenes` for any `spritePalette{}` upload that references the metasprite's ID. Only emit if no scene upload is found.

**Warning signs:** `MetaspritesGrayPaletteEmissionTest` failing with unexpected `set_sprite_palette` duplicates.

### Pitfall 2: Using wrong sprite PNG for GBC reference comparison

**What goes wrong:** gbkt uses `player-character-gbapduck-sprites.png` but GBDK reference GBC build uses `player-character-gbc-sprites.png`. Comparing them directly produces a false discrepancy.

**Why it happens:** The GBDK cross-platform example has separate sprite sheets per platform variant.

**How to avoid:** For palette comparison, verify that both PNGs share the same PLTE order (same palette entries). If they differ, compare each ROM against its own reference, not cross-reference.

**Warning signs:** Player palette RGB values differ between gbkt and reference even before any fix.

### Pitfall 3: Spearman = -1.0 false positive on degenerate palettes

**What goes wrong:** A 2-color palette (all entries the same luminance) has undefined Spearman correlation. A 1-entry palette is trivially "inverted" by any definition.

**Why it happens:** Very small sprites or palettes with all-identical lum entries.

**How to avoid:** Guard `checkPalettePolarity`: if `n < 2` or all luminances are equal, return false (not inverted — cannot determine). Document this edge case in function kdoc.

**Warning signs:** Polarity warning fires for solid-color sprites or icon assets.

### Pitfall 4: pluginTest vs :gbkt-gradle-plugin:test confusion

**What goes wrong:** Running `./gradlew :gbkt-gradle-plugin:test` fails because it cannot resolve gbkt-core/backend-api from a stale `~/.m2`.

**Why it happens:** The plugin's IntegrationTest TestKit sandbox depends on mavenLocal() snapshots.

**How to avoid:** ALWAYS use `./gradlew pluginTest` for gradle-plugin tests in this project.

**Warning signs:** `Could not resolve io.github.gbkt:gbkt-core:0.1.0-SNAPSHOT` error.

### Pitfall 5: BG inversion may be transient (default palette flash)

**What goes wrong:** The `_gbkt_default_bg_pal` descending default is uploaded to BG palette slot 0 during `main()` init. If the zone-load `set_bkg_palette` call is delayed (e.g., issued after `cls()`), the default palette appears briefly in the first few frames.

**Why it happens:** GBC palette RAM retains the last uploaded palette. If zone-load is not atomic with scene-enter, a transient flash shows the descending default.

**How to avoid:** In the diagnostic plan, capture screenshots at frame 1 and frame 60 of gameplay. If they differ, it's a transient flash, not a persistent inversion. Persistent inversion = frame 60 still wrong.

**Warning signs:** Screenshot at first game frame shows inverted colors, but screenshot after 1 second looks correct.

### Spearman Rank Correlation (pure Kotlin stdlib)
```kotlin
// [ASSUMED] implementation sketch — no external lib needed
fun spearmanRanks(values: List<Double>): List<Double> {
    val sorted = values.mapIndexed { i, v -> v to i }
        .sortedBy { it.first }
    val ranks = DoubleArray(values.size)
    var i = 0
    while (i < sorted.size) {
        var j = i
        while (j < sorted.size && sorted[j].first == sorted[i].first) j++
        val avgRank = (i + 1 + j) / 2.0  // 1-indexed average
        for (k in i until j) ranks[sorted[k].second] = avgRank
        i = j
    }
    return ranks.toList()
}

fun spearmanCorrelation(ranksX: List<Double>, ranksY: List<Double>): Double {
    val n = ranksX.size
    val dSquaredSum = ranksX.zip(ranksY).sumOf { (rx, ry) -> (rx - ry) * (rx - ry) }
    return 1.0 - (6.0 * dSquaredSum) / (n * (n * n - 1))
}
```
