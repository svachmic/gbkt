# Phase 13.7: platformer color polarity — fix inverted BG + OBJ palettes (diagnose-first) — Specification

**Created:** 2026-06-05
**Ambiguity score:** 0.166 (gate: ≤ 0.20)
**Requirements:** 6 locked

## Goal

In GBC color mode, the gbkt-built `platformer-template` background (zone tilesets) and player metasprite render with light↔dark **inverted** palettes versus the compiled GBDK reference; this phase diagnoses the polarity defect in both pipelines and corrects it at the framework/codegen source so the rebuilt GBC ROM reads non-inverted (sky light, player body light), matching the compiled reference.

## Background

The platformer-template colors were APPROVED at Phase 12.9 (12.9-08h G3: user "all pictures are perfect"), so the inversion is a **Phase 13.x regression**, not a long-standing defect. Prime suspect is the Phase 13.3 "Color refactor" (`gbc()`/`GbcColor`/`gbcHex()` → `Color` namespace migration, plans 13.3-04/07/08/11). Plans 13.3-21/22/23 fixed the *metasprites-example* gray sprite palette (ascending-ramp polarity) but did not cover the platformer-template BG zone-tileset palettes or its player metasprite palette.

Symptom (GBC mode, evidence `.planning/seeds/evidence/platformer-gbc-inverted-colors-2026-06-04.png`): the world reads as a near-uniform dark-green/olive wash (sky tile should read LIGHT), foreground blocks are lighter than the sky (value relationship inverted), and the player metasprite is a dark body with a light halo (body should read light).

Two pipelines are implicated:
- **BG:** `gbkt-gradle-plugin` `ConvertZoneTilesetsTask` → per-zone `_zone_<id>_tileset_palettes[16]` arrays uploaded via `set_bkg_palette` (Phase 12.9 W5 wiring; `-keep_palette_order` gated by `isIndexedPng()` at `ConvertZoneTilesetsTask.kt:329`).
- **OBJ:** `gbkt-gradle-plugin` `ConvertSpritesTask` → player metasprite palette uploaded via `set_sprite_palette` (`GBDKPipelineV2.buildMetaspriteSpritePaletteStatements`, ~line 5047).

The correct-colors reference is the **compiled GBDK source material** at `/Users/michalsvacha/gbdk/examples/cross-platform/platformer_template/` (built via its Makefile, run in GBC mode). Phase 12.9 also retains approved reference PNGs at `.planning/phases/12.9-palette-inversion-asset-pipeline/evidence/reference/{00-last-gameplay,01-nextlevel-flip,02-nextlevel-card,03-level-2}.png`.

This phase is diagnose-first: lock ONE polarity root cause per affected pipeline before fixing, and fix at the asset-pipeline/codegen source — NOT by re-authoring each game's palette declarations.

## Requirements

1. **BG palette polarity diagnosed and resolved**: The background zone-tileset palette path is proven either inverted (and fixed) or already-correct (with evidence).
   - Current: `_zone_world1Area1Zone_tileset_palettes` (and world2/title/nextLevel zones) render inverted vs the source PNG PLTE luminance order in GBC mode; root cause not yet isolated
   - Target: codegen-read confirms the emitted RGB555 BG palette byte order matches the source PNG PLTE luminance order; if a code change is required, it is made in `ConvertZoneTilesetsTask`/BG-palette codegen (not in the example's DSL)
   - Acceptance: a DIAGNOSTIC artifact records the BG root cause (or proves BG already correct); the rebuilt GBC ROM's sky/ground reads light-where-the-reference-is-light under live GBC MCP probe + screenshot

2. **OBJ (player metasprite) palette polarity diagnosed and resolved**: The player sprite palette path is proven either inverted (and fixed) or already-correct (with evidence).
   - Current: the player metasprite renders as a dark body with a light halo in GBC mode; root cause not yet isolated; 13.3-22/24 ascending-ramp fix may not have reached the platformer player palette site
   - Target: codegen-read confirms the emitted player sprite palette byte order matches the source PNG PLTE luminance order; any code change is made at the framework/codegen source
   - Acceptance: a DIAGNOSTIC artifact records the OBJ root cause (or proves OBJ already correct); the rebuilt GBC ROM's player body reads light (non-inverted) under live GBC MCP probe + screenshot

3. **Emission test locks corrected byte order**: At least one RED→GREEN JVM-tier test locks the corrected BG and/or OBJ palette emission byte order for whichever pipeline(s) received a code change.
   - Current: no emission test guards the platformer-template BG/OBJ palette luminance order
   - Target: a JVM-tier emission test fails on the pre-fix (inverted) byte order and passes on the corrected order, for each pipeline that was changed
   - Acceptance: the test is RED at the pre-fix commit and GREEN at the fix commit; `./gradlew test` for the affected module(s) passes

4. **Build-time inverted-polarity warning (both pipelines, non-fatal)**: The build emits a non-fatal WARNING naming the asset when an emitted palette's luminance order is inverted versus the source PNG PLTE.
   - Current: no build-time diagnostic exists for inverted palette polarity in either `ConvertZoneTilesetsTask` (BG) or `ConvertSpritesTask` (OBJ)
   - Target: both tasks emit a non-fatal WARNING (analogous to the 13.6 D-06 warning) identifying the offending PNG when its emitted palette order is inverted vs the source PLTE; the build still succeeds (EXIT 0)
   - Acceptance: a deliberately-inverted fixture (or the pre-fix asset state) triggers exactly one WARNING per offending asset and the build still exits 0; the corrected assets emit zero such warnings

5. **No regression of prior color fixes**: The 13.3-22/24 ascending-ramp sprite-palette fix and the 12.9 D2a `-keep_palette_order` player-transparency fix are preserved.
   - Current: the metasprites elephant renders correctly non-inverted (13.3-22/24) and the platformer player sprite is transparent-correct (12.9 D2a)
   - Target: both remain true after this phase's changes
   - Acceptance: the metasprites elephant renders correctly non-inverted at rot=0 (regression guard); the platformer player sprite index-0 stays transparent (no `-keep_palette_order` revert); existing 13.3/12.9 emission tests stay GREEN

6. **Binding visual sign-off vs compiled reference + ROM-build sweep**: The fix is confirmed visually against the compiled GBDK reference, and the build pipeline stays green across targets.
   - Current: the only evidence of inversion is one GBC screenshot; no post-fix reshoot exists
   - Target: a live GBC MCP reshoot of gameplay (world + player) and title, captured against the freshly-rebuilt ROM, side-by-side with the compiled GBDK reference, receives a binding user APPROVED verdict; the 7-target `:buildRom` sweep stays EXIT 0
   - Acceptance: user binding APPROVED verdict recorded (Visual Evidence Rule); `:gbkt-examples:platformer-template:buildRom` EXIT 0; the 7-target buildRom sweep EXIT 0 (pong PASS*)

## Boundaries

**In scope:**
- Diagnose BG zone-tileset palette polarity (`ConvertZoneTilesetsTask` / BG-palette codegen) for the platformer-template
- Diagnose OBJ player-metasprite palette polarity (`ConvertSpritesTask` / `set_sprite_palette` codegen) for the platformer-template
- Fix the polarity at the framework/asset-pipeline/codegen source for whichever pipeline(s) the diagnosis proves inverted — BOTH BG and OBJ explicitly resolved (fixed OR proven correct with evidence)
- RED→GREEN JVM emission test(s) locking the corrected byte order
- A non-fatal build-time WARNING in BOTH `ConvertZoneTilesetsTask` and `ConvertSpritesTask` when emitted palette luminance order is inverted vs the source PNG PLTE
- Compile + run the GBDK reference (`/Users/michalsvacha/gbdk/examples/cross-platform/platformer_template/`) in GBC mode as the correct-colors reference
- Live GBC MCP reshoot + binding visual sign-off; 7-target `:buildRom` sweep

**Out of scope:**
- Sprite-pipeline non-zero-tRNS transparency routing — owned by Phase 13.6 (sprite-only; does NOT cover BG inversion)
- Re-authoring the platformer-template's own palette declarations to mask the symptom — the fix must be at the framework layer so any indexed PNG benefits
- Reverting or re-opening the 13.3-22/24 ascending-ramp fix or the 12.9 D2a `-keep_palette_order` fix — hard regression guards
- Non-color platformer defects (collision, spawn-Y, physics, sub-pixel sink) — separate seeds/phases
- Broadening the fix to non-platformer example games beyond what the regression-guard sweep requires
- An opt-in strict "fail the build on inverted polarity" flag — warning is non-fatal only this phase

## Constraints

- All visual verification MUST be in GBC mode with the `.noi` symFile (`emulator_start` `gbcMode=true`) — DMG-mode captures are green-tinted and read as a false palette regression (13.5 false-flag gotcha; see `learning_platformer_mcp_needs_gbc_mode`).
- The fix must NOT revert the 13.3-22/24 ascending-ramp sprite-palette polarity fix or the Phase 12.9 D2a `-keep_palette_order` player-transparency fix.
- The build-time warning MUST be non-fatal (build exits 0); strict-fail behavior is out of scope.
- Diagnose-first: ONE polarity root cause must be locked per affected pipeline (codegen-read + live GBC MCP probe) BEFORE any code change; no blind palette remap.
- The 7-target byte-identity / ROM-smoke sweep must stay green for non-platformer targets (pong PASS* per `project_pong_toolchain_nondeterminism`).
- Color-namespace byte-neutrality (from 13.3-21: `gbc(r,g,b)` ≡ `Color.rgb555(r,g,b)` same bit layout) must be re-confirmed for the platformer assets, not assumed.
