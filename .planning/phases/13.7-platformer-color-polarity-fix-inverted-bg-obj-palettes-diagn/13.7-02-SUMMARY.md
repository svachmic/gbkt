## What Was Built

### `PngUtils.checkPalettePolarity` (D-02 shared comparator)

Signature: `internal fun checkPalettePolarity(sourcePng: File, emittedRgb555Values: List<Int>): Boolean`

Returns `true` when the emitted GBC RGB555 palette sequence is a strict full reversal of the source PNG PLTE luminance order (Spearman rank correlation == -1.0, EPSILON=1e-9). Returns `false` for all degenerate/non-inverted cases.

Predicate (D-02c, locked):
- Source luminance: Rec.601 `0.299*r + 0.587*g + 0.114*b` on PLTE entries via `IndexColorModel.getReds/getGreens/getBlues`
- Emitted luminance: `r5 = v and 0x1F`, `g5 = (v shr 5) and 0x1F`, `b5 = (v shr 10) and 0x1F`, scale to 8-bit, Rec.601
- Ties: equal-rank averaging via `spearmanRanks`
- Strict threshold: `spearman < -1.0 + EPSILON`

Degenerate guards (all return false):
- Emitted list size < 2
- Emitted size > source PLTE map size
- All source PLTE luminances are equal (undefined rank order)
- Any exception (sentinel idiom, matching existing PngUtils shape)

### `spearmanRanks` and `spearmanCorrelation`

Both `internal` file-scope functions matching existing PngUtils visibility. Standard implementations using Kotlin stdlib only (no new dependencies). `spearmanCorrelation` uses `Long` arithmetic to prevent overflow for large palettes.

### `PalettePolarityTest.kt`

5 unit tests covering all 5 behaviors from the plan:
1. Ascending PLTE + ascending emitted → Spearman +1.0 → false
2. Ascending PLTE + fully-reversed emitted → Spearman -1.0 → true (RED gate)
3. Degenerate (all-equal-lum, n<2) → false (no false positive)
4. Non-monotonic PLTE + emitted matching source ranking → Spearman +1.0 → false
5. Partial reorder (not full reversal) → Spearman > -1.0 → false

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] JVM PLTE padding to 256 after ImageIO round-trip**
- **Found during:** Task 1 GREEN phase — Test 2 returning false instead of true
- **Issue:** `IndexColorModel.mapSize` returns 256 after `ImageIO.read` on a 4-entry indexed PNG (JVM pads to 256). The original guard `emittedRgb555Values.size != mapSize` (4 != 256) fired, returning false.
- **Fix:** Changed size guard to use `n = emittedRgb555Values.size` as the comparison count; uses first N entries from source PLTE. Guard fires only if `n > mapSize` (emitted larger than actual palette).
- **Files modified:** PngUtils.kt (guard logic), PalettePolarityTest.kt (degenerate Case B changed from single-entry PNG to single-emitted-value)
- **Commit:** 980b505d (inline in GREEN commit)

**2. [Rule 1 - Bug] ByteArray vs IntArray for IndexColorModel.getReds/getGreens/getBlues**
- **Found during:** Task 1 GREEN compile
- **Issue:** Initial implementation used `IntArray` for `cm.getReds(it)` — JVM API takes `ByteArray!`
- **Fix:** Changed to `ByteArray` with `toInt() and 0xFF` unsigned conversion
- **Files modified:** PngUtils.kt
- **Commit:** 980b505d (inline in GREEN compile)
