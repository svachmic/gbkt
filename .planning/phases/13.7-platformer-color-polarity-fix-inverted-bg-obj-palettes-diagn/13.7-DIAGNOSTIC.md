## OBJ root cause

**Verdict: INVERTED + FIX-NEEDED. Fix locus = `GBDKPipelineV2.buildMetaspriteSpritePaletteStatements` (D-04). Confirmed by codegen-read.**

Evidence (codegen-read of the freshly built gbkt ROM):

- `grep -rn "set_sprite_palette" <generated/>` → **0 calls** across the entire generated tree.
- `grep -c "player_palettes" main.c` → **0** references. The array IS generated
  (`sprites/player.c`: `const palette_color_t player_palettes[4] = { RGB8(255,128,64),
  RGB8(0,0,0), RGB8(248,248,248), RGB8(168,168,168) }`, png2asset `-keep_palette_order`) but
  is never uploaded to OBJ palette RAM.
- The GBDK reference **does** upload it: `player.c:85/88/91 →
  set_sprite_palette(baseProp, 1, PlayerCharacterSprites_palettes)`.
- `PlatformerTemplate.kt` (`val player by metasprite { sprite(asset("...player-character-gbapduck-sprites.png")) {...} posX/posY/rot/idx; frames(12) }`)
  has **no `spritePalette{}` block** → the player is asset-driven; the game declares no
  `GBCPalette(type=SPRITE)`.
- Root cause: 13.3-17 Direction B deliberately excluded ALL asset-driven metasprites from auto
  `set_sprite_palette` (to avoid triple-slot collision when a `spritePalette{}` is present).
  With no upload, the player renders under the `cgb_compatibility()` descending default
  (index0 = lightest) → **dark body / light halo inversion**.
- **Fix (Plan 03, additive):** emit `set_sprite_palette` for asset-driven metasprites ONLY
  when the game has no `GBCPalette(type=SPRITE)` — preserving Direction B when one is present.

## BG codegen-read

**Verdict (static): ALREADY-CORRECT (persistent palette byte-identical to reference). Only candidate for any inversion is a transient first-frame `_gbkt_default_bg_pal` flash. Frame≥60 GBC screenshot (Task 2) decides the binding verdict.**

Evidence:

- `_zone_world1Area1Zone_tileset_palettes[16]` first 4 entries:
  `RGB8(8,24,32), RGB8(224,248,207), RGB8(136,192,112), RGB8(48,104,80)`
  — **byte-identical** to the GBDK reference `World1Tileset_palettes[16]` (same conversion via
  `-keep_palette_order`; `PALETTE_COUNT = 4`). Re-confirmed against THIS build, not assumed.
- gbkt **does** upload the correct per-zone palette on every gameplay scene enter:
  `main.c:160 set_bkg_palette(0u, _zone_world1Area1Zone_tileset_PALETTE_COUNT, _zone_world1Area1Zone_tileset_palettes)`
  (and `:245`, `:330` for world1Area2 / world2Area1). The reference uploads the same array via
  `level.c → setBKGPalettes → set_bkg_palette(0, count, palettes)`.
- **Transient-flash candidate (Pitfall 5):** `main.c:68 const palette_color_t
  _gbkt_default_bg_pal[4] = {0x7FFF, 0x56B5, 0x294A, 0x0000}` (DESCENDING: index0 = white,
  index3 = black) is uploaded ONCE at init: `main.c:748 cgb_compatibility(); main.c:749
  set_bkg_palette(0u, 1u, _gbkt_default_bg_pal)`. This precedes the first gameplay scene enter,
  which immediately overwrites slot 0 with the correct ascending zone palette. So any inversion
  would be a first-frame flash only, NOT a persistent state at frame≥60.
- Per the SPEC / Plan 04: if frame≥60 reads correct, ship **no BG code change** (no blind
  remap, no DSL re-authoring) — Req 1 satisfied by evidence + a C-shape guard test.

## D-04b — Color-namespace byte-neutrality (Constraint)

Both palette paths are **png2asset-derived via `-keep_palette_order`** (see the "Conversion
args" comments: BG `world1-tileset.png ... -keep_palette_order`; OBJ
`player-character-gbapduck-sprites.png ... -keep_palette_order`), NOT DSL `Color.rgb555`. The
Phase 13.3 `Color` migration (`gbc()`/`GbcColor`→`Color`) does not touch these byte arrays —
it cannot be the cause, and the fix must not be a palette-value rewrite. (D-04b resolved.)
