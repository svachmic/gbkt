## Summary

This phase fixes 5 confirmed codegen/analysis bugs and performs a structured audit across all genre and analysis modules. The bugs were confirmed by reading the canonical source files referenced in CONTEXT.md. All 5 bugs are clear, localized fixes — none require architectural changes.

The most nuanced bug is F-077 (`checkPalettePrecision`). The IR stores `GBCColor` (rgb555, 5 bits/channel). The analysis pass receives already-quantized data. The current code expands rgb555 to rgb888 using a biased formula `(r5 << 3) | (r5 >> 2)` and then re-quantizes — this biased expansion introduces error for values like `r5=31` (WHITE), producing a false positive. The correct fix is to remove the biased round-trip entirely and instead guard the check on `paletteStrictMode` being enabled, while using `hasPrecisionLoss` on the original rgb888 at the DSL layer (where `gbcHex()` already prints to stderr). Alternatively, `GBCPalette` must store the original rgb888 hex alongside the rgb555 value. The existing test at line 225-246 (`SemanticValidationPassTest.kt`) explicitly documents that WHITE was causing a false positive, confirming the diagnosis.

The F-075 fix must convert from `AllocationResult.warnings` (currently returns a warning string) to a hard build error. `BankAllocator` lives in `gbkt-core/PoParser.kt` and does not have access to the analysis `PassResult` / `Diagnostic` pattern. The fix should change `AllocationResult` to distinguish overflows (new `errors: List<String>` field) from soft warnings, and the caller — currently only `PoParserTest.kt` — must check for errors.

**Primary recommendation:** Fix each bug in the exact function identified, add targeted unit tests, then run `./gradlew test` as the exit gate.

## Architecture Patterns

### Genre Visitor Pattern (sport, puzzle, platformer)

Genre visitors extend `GenreSystemVisitor` (from `gbkt-backend-api`). Each visitor generates C AST nodes — `CFunction`, `CVarDecl`, `CFor`, `CIf`, `CArrayAccess`, `CExprStatement`, `CBinaryExpr`, `CLiteral`, `CVar`, `CUnaryExpr`, `CBlock` — that are assembled into `GenreVisitorResult(functions, varDecls)`.

Unit tests for genre visitors use `GBDKPipelineV2().generate(gameIR)` and inspect the `output.files["main.c"]` string for expected patterns. Example from `SportCodegenTest.kt`:

```kotlin
val output = pipeline.generate(gameIR)
val mainC = output.files["main.c"] ?: error("main.c not generated")
assertTrue(mainC.contains("tournament_standings_"), "Expected standings function")
```

### Analysis Pass Pattern

Passes implement `AnalysisPass` (`fun interface { run(PassContext): PassResult }`). They receive an immutable `PassContext`, append `Diagnostic` objects, and return `PassResult.Success(ctx.withDiagnostics(...))` or `PassResult.Failed(diagnostics)`. Errors cause `BudgetAuditPass` to return `PassResult.Failed`, which halts the pipeline.

```kotlin
// Add a hard error diagnostic
diagnostics += Diagnostic(
    id = "ANLZ-XX",
    severity = Severity.ERROR,
    message = "Developer-friendly message",
    location = "relevant context",
    suggestion = "What the developer should do",
)
```

### BankAllocator Integration

`BankAllocator` lives in `gbkt-core/PoParser.kt` and returns `AllocationResult(namespaceToBank, bankToNamespaces, warnings)`. It is NOT called from within an analysis pass — it is a standalone utility. The overflow fix should:
1. Add an `errors: List<String>` field to `AllocationResult`
2. Populate `errors` instead of (or in addition to) `warnings` when overflow occurs
3. The caller must check `result.errors` and surface them as build errors

Currently `BankAllocator` is only called in `PoParserTest.kt` — the test at line 322-332 checks `bank in 0..7` but does NOT verify that an overflowing namespace produces an error rather than a silent fallback.

## Bug Analysis and Fix Patterns

### F-033: Tournament Standings — Incomplete Swap (SportVisitor.kt lines 757-859)

**Root cause:** The bubble sort in `tournament_standings_$id` swaps `_tournament_wins_$id[j]` and `_tournament_wins_$id[j+1]` (3 CExprStatement nodes) but does not swap the corresponding `_tournament_losses_$id` entries. Standings sort by wins, but if you sort wins without co-sorting losses, the losses array becomes misaligned — participant 0's win count no longer matches participant 0's loss count.

**Fix:** After the 3-statement wins swap block, add 3 parallel statements swapping `_tournament_losses_$id[j]` and `_tournament_losses_$id[j+1]` using the same `tmp` variable (or a second `tmp` if desired, but using the same tmp with sequential swaps is fine since wins swap completes before losses swap begins).

**Existing test file:** `SportCodegenTest.kt` — add a new test `tournament standings swaps losses array in sync with wins array` that inspects `mainC` for `_tournament_losses_` swap statements.

**Integration:** `gbkt-examples/racer/` is the closest example to sport (no tournament example exists in examples/). Unit test is sufficient for regression coverage.

### F-034: Puzzle Match Detection — Missing Cell Cleanup (PuzzleVisitor.kt lines 210-401)

**Root cause:** `buildCheckMatch()` scans horizontal and vertical runs, sets `found = 1` when a run of `minMatch` or more is detected, and returns `found`. It NEVER writes back to the grid: matched cells remain with their original non-zero values. The game loop calls `puzzle_check_match_$id()` every frame, it returns 1 forever, and the game cannot advance.

**Fix:** When `run >= minMatch` is detected, the code must also zero out the cells in that run. This requires tracking the start position of the run and emitting loop/assignment code to clear `_puzzle_grid_$id[r*width + c_start..c]` (horizontal) or `_puzzle_grid_$id[r_start..r * width + c]` (vertical) to 0.

**Complexity note:** The fix is non-trivial because the current scan doesn't track run start indices. The new code needs a `run_start` variable alongside `run` to mark where the current run began.

**Existing test file:** `PuzzleCodegenTest.kt` — existing test at line 64-80 verifies function names are generated; add a test that verifies the generated C contains `= 0` assignment inside the match-check function for matched cells.

### F-035: Puzzle Gravity DOWN — Single-Pass Algorithm (PuzzleVisitor.kt lines 418-548)

**Root cause:** `buildApplyGravity()` for `GravityDirection.DOWN` emits a `for c` outer loop (columns) and a `for r` inner loop (rows, from bottom-1 to 0). The inner loop finds `grid[r][c] == 0` (empty cell) and swaps it with `grid[r-1][c]` (the cell above). This single-pass correctly bubbles ONE empty cell down by one row per function call.

For a column like `[A, B, 0, 0]` (A at top), calling the function once produces `[A, 0, B, 0]`. The second call produces `[0, A, B, 0]`. Wait — actually the issue is different. The inner loop goes from `r = height-1` down to `r > 0`. When it finds `grid[r] == 0`, it swaps with `grid[r-1]`. But after the swap, `r` decrements, so the element that just moved down to `r` is not re-examined in this pass to see if it should keep falling. Each call to `puzzle_apply_gravity_id()` moves each piece down by at most 1 row.

**Fix:** Wrap the inner loop body in an outer "repeat until settled" while loop. For Game Boy C code generation, emit a `do { swapped=0; for(r=height-1; r>0; r--) { if grid[r]==0 && grid[r-1]!=0 { swap; swapped=1; } } } while(swapped)` pattern. This converges gravity in a single call.

**Existing test:** `PuzzleCodegenTest.kt` — add a test verifying the generated C for `puzzle_apply_gravity_` contains a convergence loop (e.g., contains `swapped` or a `do`/`while` pattern).

### F-075: BankAllocator — Silent Overflow (PoParser.kt lines 332-338)

**Root cause:** When no bank has room for a namespace, the fallback appends to `warnings` and sets `namespaceToBank[namespace] = maxBanks`. This silently assigns the namespace to a bank that is already full, producing a ROM that exceeds the allowed bank size — generating a broken binary without any build error.

**Fix:**
1. Add `errors: List<String>` to `AllocationResult` data class alongside existing `warnings`.
2. In the overflow path, populate `errors` instead of `warnings`.
3. Keep a developer-friendly message: `"Game content exceeds ROM capacity. Too many localized strings to fit in the available ROM banks. Consider reducing string content or splitting into fewer localization namespaces."` (not "bank overflow in bank 7").
4. The existing `PoParserTest.kt` test `bank allocator all banks are within valid range` asserts bank <= 7 — it will need updating to assert that overflow produces an error, not a silent fallback.

**Note:** `BankAllocator` does not integrate with `PassContext`/`Diagnostic` — it's a standalone utility. The error surface is `AllocationResult.errors`. The caller (Gradle plugin or pipeline) must check `result.errors` and surface them.

### F-077: checkPalettePrecision — Post-Quantization Check (SemanticValidationPass.kt lines 241-277)

**Root cause:** `GBCColor` stores only rgb555 (5 bits/channel). By the time `checkPalettePrecision` receives `game.palettes`, every color is already quantized. The code expands rgb555 back to rgb888 using the biased formula `r8 = (r5 shl 3) or (r5 shr 2)` — this is a standard "scale up" formula used for display, but it is NOT the inverse of the quantization `r5 = r8 >> 3`. The round-trip `r5 → r8_biased → r5_rt` can differ from the original r5 for many valid rgb555 values (e.g., r5=31: r8=(31<<3)|(31>>2) = 248+7 = 255, then r5_rt = 255>>3 = 31 — this specific case is fine, but for r5=1: r8=(1<<3)|(1>>2)=8+0=8, r5_rt=8>>3=1 — also fine). Actually the test comment (line 225-246) says WHITE was causing a false positive, which contradicts the math above.

**Re-examination:** The test at line 229 shows `GBCColor(0x7FFF)` — WHITE. `r5=31, g5=31, b5=31`. The biased expansion: `r8 = (31 shl 3) or (31 shr 2) = 248 or 7 = 255`. Re-quantize: `r5rt = (255 shr 3) and 0x1F = 31`. These match, so NO false positive should occur. But the test says it previously triggered a false positive, meaning there was a bug in the condition check that has since been partially addressed (or the test is aspirational). The real problem is that the check is logically impossible to do correctly on already-quantized data — the IR cannot tell you what the original rgb888 was.

**The correct fix:** The palette precision check cannot be meaningfully applied to rgb555 data. The check should be removed from `checkPalettePrecision` and moved entirely to the DSL layer (where `gbcHex()` in `GbcColor.kt` already calls `GBCColor.hasPrecisionLoss` and prints to stderr). Alternatively: remove the body of `checkPalettePrecision` and replace it with a no-op (always emit no diagnostics), since precision was already lost at DSL construction time. The existing test suite already has a correct test structure — the fix is to make `checkPalettePrecision` correct (not emit false positives, not attempt post-quantization checks).

**Concrete fix:** Replace the round-trip check with `GBCColor.hasPrecisionLoss(color.rgb555)` — but wait, `hasPrecisionLoss(hex: Int)` takes rgb888. For rgb555 data, every value is by definition already exactly representable in rgb555. So the function should emit zero warnings when operating on already-quantized `GBCColor` data. The fix: if `paletteStrictMode` is enabled and the game contains palettes, emit a single INFO diagnostic noting that precision was already applied at DSL construction time, and leave per-color checks to `gbcHex()`. OR: store the original rgb888 hex in `GBCPalette` alongside the rgb555 for use by this check.

**Recommended minimal fix:** Store `originalHex: Int? = null` in `GBCColor` or `GBCPalette`. When `gbcHex()` creates a color, populate `originalHex`. Then `checkPalettePrecision` uses `originalHex` when available. If `originalHex` is null (color created programmatically from rgb555), skip the check — it can't be done. This preserves the intent of the feature without false positives.

## Common Pitfalls

### Pitfall 1: Fixing DOWN but not UP gravity
**What goes wrong:** F-035 is documented for DOWN gravity. The UP gravity branch (lines 550-676) uses an identical single-pass loop structure — it has the same convergence bug.
**How to avoid:** Fix both DOWN and UP branches in the same change. Add tests for both directions.
**Warning signs:** Test for UP gravity settling only checks function name generated, not convergence behavior.

### Pitfall 2: Changing AllocationResult breaks PoParserTest
**What goes wrong:** Adding `errors: List<String>` to `AllocationResult` changes the data class constructor. The existing test at PoParserTest.kt line 322-332 creates the allocator and calls `allocateForStrings()` — the test checks `bank in 0..7`, which will still pass if the overflow uses `errors` instead of silently assigning to maxBanks (the assignment is removed). But the test needs updating to also verify `result.errors.isNotEmpty()` when overflow occurs.
**How to avoid:** Update PoParserTest.kt alongside PoParser.kt.

### Pitfall 3: F-077 fix scope confusion
**What goes wrong:** The check-after-quantization problem means the current code is simultaneously: (a) failing to warn about actual precision loss (since the loss already happened), and (b) potentially emitting false positives for valid colors due to biased expansion math. A naive fix that "adds the check back" still won't work correctly.
**How to avoid:** The minimal correct fix is to clear the body of `checkPalettePrecision` (make it a no-op) and rely on `gbcHex()` (which correctly checks before quantization at DSL construction time). The longer-term fix stores original rgb888 in `GBCPalette`. Choose based on phase scope — noop is fastest and eliminates false positives.

### Pitfall 4: C AST bubble-sort temporary variable reuse
**What goes wrong:** F-033 fix reuses the existing `tmp` CVarDecl to also swap losses. This is correct IF the wins swap fully completes before the losses swap begins (which it does — they're sequential statements). But if the planner generates code that interleaves wins/losses swap steps, the tmp value will be wrong.
**How to avoid:** Generate the swap as: save wins[j] to tmp, assign wins[j]=wins[j+1], assign wins[j+1]=tmp, THEN save losses[j] to tmp, assign losses[j]=losses[j+1], assign losses[j+1]=tmp. Use the same tmp variable sequentially.

### Pitfall 5: Match clearing changes function signature
**What goes wrong:** F-034 fix makes `buildCheckMatch()` modify the grid as a side effect. If callers expect a pure query (returns 1 or 0 without mutation), this changes semantics. However, game loops calling `puzzle_check_match_id()` currently see it return 1 forever (since nothing clears the match), so the current behavior is already broken. Changing to clear-on-match is the correct semantics.
**How to avoid:** Document the new semantics: `puzzle_check_match_$id()` returns 1 if matches were found AND clears them, returns 0 if no matches. Update the existing test to verify both the return value AND cell-clearing behavior.

### Pattern: Convergence loop for gravity (F-035)

Generated C pseudocode (to be expressed as C AST):
```c
uint8_t swapped;
do {
    swapped = 0;
    for (uint8_t c = 0; c < WIDTH; c++) {
        for (uint8_t r = HEIGHT - 1; r > 0; r--) {
            if (grid[r * WIDTH + c] == 0 && grid[(r-1) * WIDTH + c] != 0) {
                uint8_t tmp = grid[r * WIDTH + c];
                grid[r * WIDTH + c] = grid[(r-1) * WIDTH + c];
                grid[(r-1) * WIDTH + c] = tmp;
                swapped = 1;
            }
        }
    }
} while (swapped);
```

Key C AST nodes needed: `CVarDecl("swapped", CU8)`, `CDoWhile(body, condition)` (check if `CDoWhile` exists in the C AST — if not, use a `while(1) { ...; if(!swapped) break; }` pattern).
