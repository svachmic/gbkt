<domain>
## Phase Boundary

Fix 5 known codegen/analysis bugs producing broken C output, then perform a full module audit across all genre and analysis modules for the same classes of bugs. Any additional bugs found by the audit are fixed in this phase. This is the pre-UAT hardening gate — all fixes must land before interactive play-testing in Phase 07.2.

**Known bugs:**
- F-033: Tournament standings bubble sort swaps wins but not losses array (genre-sport)
- F-034: Puzzle match detection doesn't clear matched cells (genre-puzzle)
- F-035: Puzzle gravity DOWN single-pass only, pieces don't fully settle (genre-puzzle)
- F-075: BankAllocator overflow fallback assigns to maxBanks without capacity check (analysis)
- F-077: checkPalettePrecision checks after quantization instead of before (analysis)

</domain>

<decisions>
## Implementation Decisions

### Fix Scope & Audit
- **D-01:** Fix all 5 reported bugs AND perform a full module audit for the same classes of bugs
- **D-02:** Audit scope includes ALL genre modules (sport, puzzle, rpg, platformer) AND the analysis module (all 11 passes)
- **D-03:** Any additional bugs found by the audit are fixed in this phase, not deferred to UAT
- **D-04:** Four bug classes to audit for:
  1. **Incomplete operations** — operation updates one data structure but not its sibling (like F-033 sorting wins but not losses)
  2. **Missing state cleanup** — detection logic runs but never clears/resets detected state (like F-034 detecting matches but not clearing cells)
  3. **Single-pass algorithms** — algorithm needs multiple passes to converge but only runs once (like F-035 gravity doing one swap per call)
  4. **Silent overflow/fallback** — error path silently produces invalid output instead of failing (like F-075 assigning to overflowing bank)

### F-075 Error Behavior
- **D-05:** BankAllocator overflow must be a **hard build error** with an actionable, user-friendly message
- **D-06:** Error message must NOT require banking knowledge — phrased in terms the game developer understands (e.g., "Game content exceeds ROM capacity" not "bank overflow in bank 7")
- **D-07:** Consistent with gbkt's "compile-time over runtime" principle and "zero hardware knowledge required" philosophy

### Regression Testing
- **D-08:** All fixes verified with **both** unit tests on codegen output AND integration tests with real ROMs
- **D-09:** Unit tests verify the code generator produces correct C AST/output (fast, deterministic)
- **D-10:** Integration tests use **existing example games** in gbkt-examples/ (no new test fixtures)
- **D-11:** **Full `./gradlew test` must pass as phase exit gate** — all modules, all example games

### Delivery Ordering
- **D-12:** Work organized **by module** — one plan per module group
- **D-13:** **Wave 1: Analysis fixes** (F-075, F-077 + full analysis module audit) — analysis passes run before codegen, fix pipeline correctness first
- **D-14:** **Wave 2: Genre fixes** (F-033 sport, F-034/F-035 puzzle + sport/puzzle/rpg/platformer audit) — independent genre modules can run in parallel within wave 2

### Claude's Discretion
- Exact audit methodology and how to systematically scan each module
- How to structure unit tests for codegen output verification
- Which example games map to which bug fixes for integration testing
- Fix implementation details for each bug
- How to handle edge cases found during audit (severity triage)

</decisions>

<specifics>
## Specific Ideas

- F-075 error message should be developer-friendly: "Game content exceeds ROM capacity" not "bank 7 overflow" — the user doesn't know or care about banks
- Banking is fully automatic in gbkt — the allocator should either handle it silently or fail clearly, never produce a broken ROM without explanation
- The full module audit is a thorough hardening pass before UAT — better to find bugs now than during interactive play-testing where they're harder to diagnose
- Four bug classes (incomplete ops, missing cleanup, single-pass, silent overflow) provide a systematic audit checklist

</specifics>
