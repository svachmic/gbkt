## User Constraints (from CONTEXT.md)

### Locked Decisions

**Old API Removal (A6):**
- Delete outright — `assign()`, `varRef()`, `literal()` removed entirely, no deprecation ceremony (pre-v1 release)
- Full sweep + compiler — grep sweep to proactively find all call sites in tests/examples, then compiler verifies zero remain
- `raw()` renamed — keep as escape hatch, rename to signal danger (e.g., `unsafeRaw()` or `cEmit()`), emit build WARNING when used

**Input Enhancements (A1, A2):**
- `InputRef.released` — edge-triggered (true for one frame on release), matching `.pressed` semantics
- `dpad.x / dpad.y` — return full `Expr` values (-1/0/+1) composable with arithmetic: `player.x += dpad.x * speed`

**Array Safety (A3):**
- Compile-time bounds checking only — when index is a literal, validate at DSL record time; zero runtime overhead in generated C
- Best DX philosophy — proactively help the developer catch mistakes without GB CPU cost

**Struct Types (A5):**
- DSL construct — `struct("TileHashEntry") { field("key", u16); field("value", u8) }` — explicit definition mapping to C struct
- Reusable — define once, use in hashtable, pool, ring buffer, fixed slots, and standalone variables
- Dot syntax for field access — `entry.key set 5` / `whenever(entry.key isAbove 10)` via proxy objects
- Flat fields only — struct fields are primitives (u8, u16, i8, i16, bool); nested structs deferred

**Generic Collections (A4):**
- Reified generics — `val cache by hashtable<TileEntry>(64)` with compile-time type checking and IDE autocomplete
- Method-based access — `cache.put(key, entry)` / `cache.get(key)` / `cache.remove(key)` — clear intent, consistent verb style
- All four collection types support struct elements from the start (hashtable, pool, ring buffer, fixed slots)
- forEach iteration — `entityPool.forEach { entity -> entity.x += entity.dx }` generates C for-loop
- RAM validation — RAMPlanningPass calculates total collection memory; build error if total exceeds WRAM budget
- Pool acquire — returns null proxy + `exists` check when full: `val bullet = pool.acquire(); whenever(bullet.exists) { ... }`
- Ring buffer — full API: push/pop/peek, overwrite-oldest on full
- Fixed slots — both index access (`inv[3]`) and named keys (`equip.slot("weapon")`)

**GBC Color Helpers (B1, B2):**
- Multiple input formats — `gbc(r,g,b)` with 0-31 range, `gbcHex("#FF8800")` from 24-bit, and named constants; all compile to RGB555
- Lossy conversion warning — build warning with preview: `'#FF8800' maps to GBC (31,17,0)` showing original vs actual
- Explicit GBC opt-in — `config { target(GBC) }` or `config { target(GBC_COMPATIBLE) }` matching GBDK compiler flag distinction

**GBC Palette System (B3):**
- Builder DSL — `val forest by palette { color0(gbc(0,20,5)); color1(gbc(10,25,8)); ... }` auto-validates 4-color limit
- Curated preset library — ~15-20 presets: classic GB green, nature, fire/ice, ocean, dungeon, UI
- Scene-level default + actor override — `scene { palette(GbcPalette.NATURE) }` with per-actor `palette(GbcPalette.FIRE)` override
- Hardware validation — build error if scene uses more than 8 BG or 8 OBJ palettes (via analysis pass)

**Audio Driver (C1, C2, C3):**
- hUGEDriver — native .uge format, GBDK built-in support, active community
- Asset-based music — `val theme by music(asset("music/dungeon.uge"))` with asset pipeline conversion
- Gradle asset pipeline — .uge to C conversion in processAssets task alongside PNG/TMX
- Priority-based SFX mixing — HIGH/MEDIUM/LOW per sound; high-priority SFX temporarily steal music channels, auto-resume
- Fade transitions — `play(battleTheme, fadeIn = 30)` / `stopMusic(fadeOut = 15)` for smooth track changes

- Scene auto-manage — `scene { music(dungeonTheme) }` auto-plays on enter, auto-stops on exit; explicit play()/stop() can override

## Summary

This phase closes three categories of deferred framework gaps. The most important finding from codebase research is that **SC-10 (AudioMixer priority mixing) is already fully implemented** — the audit memory from phase 06.3 confirms all 8 audio mixer requirements are complete, including `audio_mixer_request_channel()` with priority preemption. This reduces the actual work significantly.

The remaining work splits cleanly into three tracks:

**Track A — DSL Ergonomics** is largely additive changes to existing files. `InputRef` gets a `released` property (same pattern as `pressed`/`held`). `dpad.x`/`dpad.y` are new properties on the existing `dpad` object. Array bounds checking is a DSL-time error, not a codegen change. The old API deletion (`assign()`, `varRef()`, `literal()`) requires a codebase sweep first, then hard deletion. Struct types and generic collections are the most complex new work — they need new IR nodes, new DSL builders, and codegen support.

**Track B — GBC Color** builds on existing infrastructure. `GBCColor` and `GBCPalette` types already exist in `gbkt-ir` with full RGB555 support, hex parsing, and precision loss detection. What's missing is the DSL-facing `gbc()` / `gbcHex()` helpers, the palette builder DSL, a preset library, and the `config { target(GBC) }` syntax. The analysis pass for 8-palette hardware validation doesn't exist yet.

**Track C — Audio** is the most externally-dependent track. The hUGEDriver integration (music playback via `MusicPlay`/`MusicStop` ScriptOps) is already implemented in the codegen — `visitMusicPlay()` emits `hUGE_init(&song_X)`. What's missing is the asset pipeline integration for `.uge` files (the `.uge → C` conversion step), the DSL-level `music(asset(...))` declaration, and scene-level music auto-management (`scene { music(theme) }` as syntactic sugar for play-on-enter / stop-on-exit).

**Primary recommendation:** Work in three parallel tracks (A, B, C). SC-10 is already done — mark it satisfied immediately. Start with A6 (API deletion) since it requires a codebase sweep that informs how many call sites exist.

## Architecture Patterns

### A1: InputRef.released

**What:** Add `released` property to `InputRef` class using a new `button_released` C helper.

**Pattern:** Mirror exact structure of `pressed` — edge-triggered (true for one frame when button transitions from held to not-held).

**DSL change** (`InputBuilders.kt`):
```kotlin
class InputRef(
    private val gbdkConstant: String,
    private val heldFn: String,
    private val pressedFn: String,
    private val releasedFn: String,  // NEW
) {
    val released: Expr
        get() = CallExpr(releasedFn, listOf(VarRef(gbdkConstant)))
}
```

**Codegen change** (`GBDKPipelineV2.kt` in `buildInputHelperFunctions()`):
```c
// button_released: falling edge = NOT held now AND held previous frame
// return (~__joypad & mask) & (__joypad_prev & mask)
UINT8 button_released(UINT8 mask) {
    return (~__joypad & mask) & (__joypad_prev & mask);
}
```

**Wire-up:** `dpad` and `buttons` objects pass `"button_released"` / `"dpad_released"` as `releasedFn`. Add `dpad_released` as alias for `button_released` (same implementation, same as `dpad_held` / `dpad_pressed` pattern).

### A2: dpad.x / dpad.y Axis Helpers

**What:** `dpad.x` returns an `Expr` with value -1 (left held), +1 (right held), or 0 (neither).

**Pattern:** Ternary expression chain — `dpad_held(J_LEFT) ? -1 : (dpad_held(J_RIGHT) ? 1 : 0)`.

**DSL change** (`dpad` object in `InputBuilders.kt`):
```kotlin
val x: Expr
    get() = TernaryExpr(
        CallExpr("dpad_held", listOf(VarRef("J_LEFT"))), Literal(-1),
        TernaryExpr(CallExpr("dpad_held", listOf(VarRef("J_RIGHT"))), Literal(1), Literal(0))
    )

val y: Expr
    get() = TernaryExpr(
        CallExpr("dpad_held", listOf(VarRef("J_UP"))), Literal(-1),
        TernaryExpr(CallExpr("dpad_held", listOf(VarRef("J_DOWN"))), Literal(1), Literal(0))
    )
```

**Note:** `TernaryExpr` already exists in `gbkt-ir/.../ir/Expr.kt` and is handled by `ExprVisitor`. No new IR or codegen needed.

### A3: Compile-Time Bounds Checking in ArrayVar.get()

**What:** When index is a literal `Int`, validate at DSL record time (not runtime).

**Pattern:** Add check in `ArrayVar.get(index: Int)`:
```kotlin
operator fun get(index: Int): Expr {
    require(index in 0 until arraySize) {
        "Array bounds error: index $index out of bounds for array '$name' (size=$arraySize)"
    }
    return ArrayAccessExpr(name, Literal(index))
}
```

**Constraint:** Only literal-index access gets the compile-time check. Dynamic index (`get(Expr)`) cannot be checked at record time — it falls through unchanged. The existing `exists()` method is the DSL-time guard for dynamic access.

**No codegen changes needed.**

### A5 + A4: Struct Types and Generic Collections

**What:** New `StructDef` IR node and generic collection delegates that accept struct element types.

**Complexity rating:** HIGH — requires new IR types, new DSL builders, new C codegen for struct declarations, and extending the existing 4 collection types.

**New IR node** (add to `gbkt-ir/.../ir/Types.kt` or new `StructIR.kt`):
```kotlin
data class StructFieldDef(val name: String, val type: VarType)

data class StructDef(
    val name: String,       // "TileHashEntry" — also becomes C typedef name
    val fields: List<StructFieldDef>,
    val sourceLocation: SourceLocation? = null,
) {
    val sizeBytes: Int get() = fields.sumOf { it.type.byteSize }
}
```

**GameIR extension** (add `structs: List<StructDef> = emptyList()` to `GameIR.kt`).

**C codegen for struct:** Emits `typedef struct { UINT8 value; UINT16 key; } TileHashEntry;` in home bank header section.

**DSL builder** (new `StructBuilder.kt` in `gbkt-lang/.../dsl/`):
```kotlin
fun struct(name: String, block: StructBuilder.() -> Unit): StructDef {
    // Records StructDef into GameIR
}
class StructBuilder(val name: String) {
    fun field(name: String, type: VarType): StructFieldDef
}
```

**Struct element type system for collections:** The current `IRCollHashTable(keyType: VarType, valueType: VarType)` only accepts primitive `VarType`. For struct support, the options are:
1. Add `StructDef` references alongside `VarType`: `keyType: VarType? = null, keyStruct: StructDef? = null` — messy
2. Create a sealed `ElementType` that wraps either a `VarType` or `StructDef` — clean, matches sealed IR style

**Recommended approach (sealed ElementType):**
```kotlin
sealed interface CollElementType {
    val sizeBytes: Int
    data class Primitive(val varType: VarType) : CollElementType { ... }
    data class Struct(val structDef: StructDef) : CollElementType { ... }
}
```

**Struct variable access proxy:** For `StructVar` (a variable of struct type), field access via `entry.key set 5` needs a proxy object:
```kotlin
class StructVar(val name: String, val structDef: StructDef) {
    operator fun get(fieldName: String): AssignableVar =
        AssignableVar("${name}.${fieldName}")  // Emits _entry.key in C
}
```

**Note:** The ExprVisitor already handles `PropertyAccessExpr` — check if this already emits `expr.field` syntax.

**Reified generic collection delegates:**
```kotlin
// In game builder context
inline fun <reified T> hashtable(size: Int): HashTableDelegate<T>
// T is StructDef at runtime via reified resolution
```

**Complexity note:** Reified generics require the StructDef to be discoverable from `T`. This means structs need to be registered in a global registry before collection delegates are created, OR the collection factory functions take the StructDef explicitly. Recommendation: support both — `hashtable<TileHashEntry>(64)` and `hashtable(tileHashEntry, 64)`.

### A6: Old API Deletion

**What:** Delete `assign()`, `varRef()`, `literal()` from DSL. Rename `raw()` to `cEmit()` with build WARNING.

**Files to modify:**
- `gbkt-lang/.../dsl/ScriptBuilder.kt` — delete `assign()`, `arrayAssign()`, `arrayRef()`, `buttonPressed()`, `buttonHeld()`, `dpadHeld()`, `dpadPressed()`, `dpadAny()` (all at WARNING level); rename `raw()` to `cEmit()`
- `gbkt-lang/.../dsl/ExprBuilder.kt` — delete `literal()`, `varRef()`

**Pre-deletion sweep required:** Search all test files and example files for calls to deleted functions. The codebase search showed zero usages in production code (the grep for `fun assign\|fun varRef` etc. returned nothing in calling code) — but tests for deprecated APIs may exist.

**Rename pattern for `raw()` → `cEmit()`:**
```kotlin
// Keep as escape hatch, emit build warning
@GbktDsl
fun cEmit(code: String) {
    // Emit a build-time warning (Gradle logger or println to stderr)
    System.err.println("WARNING: cEmit() used at ${captureV2Location()} — consider adding DSL support")
    ops += RawOp(code, sourceLocation = captureV2Location())
}
```

**Alternative names ranked:** `cEmit()` reads most clearly for a C code injection escape hatch. `unsafeRaw()` is also good (matches Kotlin naming for dangerous operations). Avoid `rawC()` — ambiguous whether it means "raw for C" or "C is raw".

### B1 + B2: GBC Color Helpers

**What:** Top-level DSL functions `gbc(r, g, b)` and `gbcHex("#FF8800")` that produce `GBCColor` values.

**Existing infrastructure (HIGH confidence):** `GBCColor` in `gbkt-ir/.../ir/CoreTypes.kt` already has:
- `fromRGB888(r, g, b)` — takes 0-255 each
- `fromHex(hex: Int)` — takes 0xRRGGBB
- `hasPrecisionLoss(r, g, b)` and `hasPrecisionLoss(hex)` — for warning generation

**DSL additions** (new `GbcColor.kt` in `gbkt-lang/.../dsl/` or extend `DmgColor.kt`):
```kotlin
/** GBC color from 5-bit components (0-31 each). Maps directly to RGB555. */
fun gbc(r: Int, g: Int, b: Int): GBCColor {
    require(r in 0..31 && g in 0..31 && b in 0..31) { ... }
    return GBCColor((b shl 10) or (g shl 5) or r)
}

/** GBC color from 24-bit hex string ("#FF8800" or "FF8800"). Emits build warning on lossy conversion. */
fun gbcHex(hex: String): GBCColor {
    val cleaned = hex.removePrefix("#")
    val value = cleaned.toInt(16)
    if (GBCColor.hasPrecisionLoss(value)) {
        val color = GBCColor.fromHex(value)
        System.err.println("WARNING: '$hex' → GBC (${color.red}, ${color.green}, ${color.blue}) (lossy)")
    }
    return GBCColor.fromHex(value)
}

/** Named GBC color constants */
object GbcColor {
    val WHITE = GBCColor(0x7FFF)
    val BLACK = GBCColor(0x0000)
    val RED = GBCColor.fromRGB888(255, 0, 0)
    // ...15-20 named constants
}
```

**Note:** Recommend keeping `gbc()` and `gbcHex()` as top-level functions (not on an object) to maximize DSL ergonomics — `color0(gbc(0, 20, 5))` reads better than `color0(GbcColor.from(0, 20, 5))`.

### C2: hUGETracker .uge Asset Pipeline Integration

**What:** `.uge` files in the asset directory get converted to C source during `ProcessAssetsTask`.

**Existing infrastructure:** `ProcessAssetsTask.dispatchFile()` in `gbkt-gradle-plugin` dispatches by file extension. The task processes PNG → 2bpp data and TMX → tilemap data.

**Integration approach:**
```kotlin
// In ProcessAssetsTask.dispatchFile():
"uge" -> processUge(file, relPath, outDir)
```

**The `.uge → C` conversion challenge:** hUGETracker exports C files via its CLI tool `uge2c` (part of the hUGEDriver distribution). Options:
1. **Shell out to `uge2c`** — requires hUGEDriver installed; fails if not found (same pattern as GBDK detection)
2. **Bundle a pure-Kotlin/JVM .uge parser** — more complex but no external dependency
3. **Copy .uge as-is and document that C export is done manually** — minimal scope

**Recommendation (based on CONTEXT.md decision):** Implement option 1 (shell out to `uge2c`), with graceful error message if not found. Document detection path in CLAUDE.md alongside GBDK detection. The Gradle plugin already has a `GbdkToolchain` pattern for external tool detection — reuse the same pattern for hUGEDriver detection.

**Output:** `processUge()` produces `song_<name>.c` + `song_<name>.h` in the output directory. The `MusicPlay(songId)` ScriptOp already references this symbol: `hUGE_init(&song_${songId})`.

### C3: Music DSL and Scene Auto-Management

**What:** DSL-level music declarations and scene-level auto-play/stop.

**Existing IR:** `MusicPlay`, `MusicStop`, `MusicPause`, `MusicResume` ScriptOps already exist. `visitMusicPlay()` emits `hUGE_init(&song_X)`. The codegen infrastructure is complete.

**Missing DSL layer:**

1. **Music declaration** (new `MusicDef` type or reference mechanism):
```kotlin
// In GameBuilder
val dungeonTheme by music(asset("music/dungeon.uge"))
// Returns a MusicRef with ID "dungeonTheme"
```

2. **Scene music auto-management** (extend `SceneBuilder`):
```kotlin
// Syntactic sugar: emits MusicPlay in enter ops, MusicStop in exit ops
scene("dungeon") {
    music(dungeonTheme)  // auto-play on enter, auto-stop on exit
    enter { /* other ops */ }
    frame { /* game logic */ }
}
```

3. **Explicit play/stop with options**:
```kotlin
scene("battle") {
    enter {
        play(battleTheme, fadeIn = 30)
    }
    exit {
        stopMusic(fadeOut = 15)
    }
}
```

**Fade and resume ScriptOps:** The existing `MusicPlay` has no `fadeIn` or `resume` parameters. Need to either:
- Extend `MusicPlay` with `fadeIn: Int = 0, resume: Boolean = false`
- Or create separate `MusicPlayFade` / `MusicPlayResume` ScriptOps

**Recommendation:** Extend `MusicPlay` with optional parameters (simpler, fewer IR types):
```kotlin
data class MusicPlay(
    val songId: String,
    val fadeInFrames: Int = 0,  // 0 = instant
    val resume: Boolean = false, // true = resume from saved position
    override val sourceLocation: SourceLocation? = null,
) : ScriptOp
```

**Codegen:** `visitMusicPlay()` needs to emit fade logic when `fadeInFrames > 0` and resume logic when `resume = true`. This requires the audio mixer's `fade_group()` function to be available.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| .uge → C conversion | Custom .uge parser | `uge2c` CLI from hUGEDriver | hUGEDriver format is undocumented binary; uge2c is the canonical exporter |

| Palette validation | Manual count in codegen | Analysis pass in `SemanticValidationPass` | Consistent with how OAM limits and RAM limits are enforced |
| Build warnings for cEmit() | Gradle API | `System.err.println()` or logger.warn() | Simple and works; no framework needed |

## Common Pitfalls

### Pitfall 1: SC-10 Already Done — Don't Re-Implement AudioMixer Priority

**What goes wrong:** Re-implementing `audio_mixer_request_channel()` when it already exists.
**Why it happens:** The phase description says "AudioMixer full priority mixing" as a gap item.
**How to avoid:** The Serena memory `phase_06.3_audiomixer_audit` confirms ALL 8 audio mixer requirements are implemented, including priority preemption (Gap 5), auto-ducking (Gap 6), save/load state (Gap 4), fade_group, and channel masks. **SC-10 is closed before the phase starts.**

### Pitfall 2: Struct Types Need Codegen in Multiple Places

**What goes wrong:** Adding `StructDef` to IR but forgetting to generate the `typedef struct` in the C header.
**Why it happens:** C requires struct type declarations before use in array and variable declarations.
**How to avoid:** `buildHeaderFile()` in `GBDKPipelineV2.kt` must emit `typedef struct { ... } Name;` for each `GameIR.structs` entry, before any collection data declarations that reference struct types.

### Pitfall 3: Reified Generic Collections Require Struct Registry

**What goes wrong:** `hashtable<TileHashEntry>(64)` can't find `TileHashEntry` struct at compile time.
**Why it happens:** Reified generics in Kotlin give you `T::class`, not a `StructDef` instance.
**How to avoid:** Two options:
- Register structs in a global `StructRegistry` singleton keyed by class name
- Make the generic syntax explicitly reference the StructDef: `hashtable(tileHashEntry, 64)` where `tileHashEntry` is the delegate result

**Recommendation:** Use explicit StructDef parameter for reliability; add `inline fun <reified T>` overload as syntactic sugar that looks up by class name from the builder-local registry.

### Pitfall 4: GBC Target Configuration Must Flow to Gradle Plugin

**What goes wrong:** `config { target(GBC) }` is recorded in `CartridgeConfig` but the Gradle plugin doesn't read it when invoking `lcc`.
**Why it happens:** The Gradle plugin runs as a separate process, reading the compiled game JAR.
**How to avoid:** The `GBDKPipelineV2` generates the C code — it can emit `#pragma GBDK_GBC` or similar directive, OR the `GenerateCTask` / `CompileRomTask` reads the IR's `config.gbcTarget` and adds the appropriate GBDK compiler flags (`-Wm-yc` or `-Wm-yC`).

### Pitfall 5: hUGEDriver .uge Pipeline Requires External Tool

**What goes wrong:** Build fails if hUGEDriver's `uge2c` is not installed.
**Why it happens:** Unlike GBDK (required for ROM building), hUGEDriver might not be on the user's PATH.
**How to avoid:** Make `.uge` processing fail gracefully with a clear error message pointing to the hUGEDriver installation instructions. Follow the same detection pattern as `GbdkToolchain.kt`. Skip `.uge` processing (not a build error) if `uge2c` isn't found, but emit a WARNING that music won't work.

### Pitfall 6: MusicPlay Fade Codegen Requires AudioMixer

**What goes wrong:** `play(theme, fadeIn = 30)` codegen assumes `fade_group()` function exists, but it only exists when `audioMixer { }` is configured.
**Why it happens:** `fade_group()` is generated by `buildAudioMixerFunctions()` in `GBDKSystemVisitor`, only when a `GenericSystem` with type=`audio_mixer` is in `GameIR.systems`.
**How to avoid:** If `fadeInFrames > 0` and no AudioMixer is configured, emit a build WARNING and fall back to instant-start. The `hasMusicOps()` check in `GBDKPipelineV2` can be extended to also check for fade ops.

### Pitfall 7: Old API Deletion Must Sweep Tests

**What goes wrong:** Deleting `assign()`, `varRef()`, `literal()` breaks test files that use them.
**Why it happens:** The deprecated functions have WARNING level — callers in tests may still use them.
**How to avoid:** Run the codebase sweep FIRST (grep for all call sites in `src/test/**` and `gbkt-examples/**`), fix all call sites, then delete the functions.

## Open Questions

1. **Reified generic collection syntax — registry approach**
   - What we know: Kotlin `reified` gives `T::class` but not a `StructDef` instance
   - What's unclear: Whether to use a global registry singleton or explicit StructDef parameter
   - Recommendation: Explicit parameter first (`hashtable(tileEntry, 64)`), then add `inline fun <reified T>` sugar that resolves from a `GameBuilder`-local registry

2. **`cEmit()` warning mechanism**
   - What we know: DSL runs at build time (JVM); Gradle logger is available in Gradle tasks but not in DSL code itself
   - What's unclear: Is `System.err.println()` acceptable or should there be a proper diagnostic channel?
   - Recommendation: Add a `DiagnosticCollector` singleton (similar to `ScriptBuilderContext`) that accumulates warnings; the Gradle task drains it and logs via `logger.warn()`

3. **hUGEDriver detection path**
   - What we know: `uge2c` is included with hUGEDriver distribution; `GbdkToolchain.kt` pattern exists for external tool detection
   - What's unclear: Whether `uge2c` is commonly on PATH or in a known install location
   - Recommendation: Search same locations as GBDK (`HUGHE_HOME` env, `/opt/hughe`, `~/hughe`, etc.); document in CLAUDE.md

4. **Music fade codegen without AudioMixer dependency**
   - What we know: `fade_group()` is generated only when `audioMixer { }` is in the game DSL
   - What's unclear: Should `play(theme, fadeIn = 30)` implicitly require AudioMixer, or implement its own fade?
   - Recommendation: `play(theme, fadeIn = 30)` requires explicit `audioMixer { }` in the game; emit build ERROR if not present. This makes the dependency explicit.

5. **Palette preset naming and color values**
   - What we know: ~15-20 presets needed; user explicitly delegated exact names/values to Claude's discretion
   - Recommendation: Use descriptive names matching common game genres — CLASSIC_GREEN, NATURE, FIRE, ICE, OCEAN, DUNGEON, CAVERN, SUNSET, NIGHT, PASTEL, SEPIA, NEON, MONOCHROME_BLUE, WARM_GRAY, UI_LIGHT, UI_DARK (16 presets)
