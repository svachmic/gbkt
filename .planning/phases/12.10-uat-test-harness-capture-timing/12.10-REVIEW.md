# Phase 12.10: Code Review Report

**Reviewed:** 2026-06-02
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

Phase 12.10 adds `StepAgent.settle()` / `captureScreenshotSettled()` (capture-timing
primitive) and `VisualDiff.compareRegion()` (region-confined pixel diff, with the shared
pixel loop refactored into `diffPixels`). I reviewed the settle loop's frame-cap,
held-button preservation, and never-throws contract, plus the region-crop clamp/diff math.

No BLOCKER-class defects were found: the settle loop honours its documented
2-consecutive-identical / cap-30 / never-throws contract, held-button preservation is
correct (it advances via `runFrames`, not `step`), and the region clamp math is sound and
well tested (clamp, zero-area, out-of-bounds all covered). The `getSubimage`→`drawImage`
diff-image path does NOT mutate the source image (it copies into a fresh `BufferedImage`),
so that aliasing trap is avoided.

The findings below are correctness-adjacent robustness gaps and quality issues. The two
that matter most: (WR-01) `settle()` silently inflates `frameCount` by up to 30 frames,
desynchronising the agent's frame accounting from wall-clock frames and from any held
input-edge logic; and (WR-02) `settle()` reads the frame buffer once *before* advancing,
so a frame buffer that is already stable on entry still costs a minimum of
`SETTLE_STABLE_FRAMES` advanced frames before it can return — it never returns the
on-entry frame.

Per scope note: the `@Disabled` on `anchor5LevelSwitch` is an intentional, documented
routing to Phase 12.11 and is NOT flagged.

## Warnings

### WR-01: `settle()` silently inflates `frameCount`, desyncing agent frame accounting

**File:** `gbkt-emulator/src/main/kotlin/io/github/gbkt/emulator/agent/StepAgent.kt:214-232`
**Issue:** `settle()` calls `session.runFrames(1)` up to `SETTLE_FRAME_CAP` (30) times.
`AgentDebugSession.runFrames` does `frameCount += n` (AgentDebugSession.kt:179), so every
settle advances `StepAgent.frameCount` / `Observation.frame` by 1–30 frames that the caller
never requested. The KDoc contract documents held-button preservation and the cap, but says
nothing about the frame-count side effect. Consequences:
- A subsequent `Observation.frame` no longer equals "frames the test asked for", so any
  frame-correlated evidence (e.g. anchor5's `lastGameplayFrame`, anchor4's cadence sampling)
  drifts by an unbounded-within-cap amount after each settled capture.
- `captureScreenshotSettled` writes a JSON sidecar whose `frameNumber` (from
  `frameCount`, AgentDebugSession.kt:209-211) reflects the post-settle count, not the
  logical capture point — the sidecar misattributes the frame.
- Worst case in `anchor4`, four `captureSettledAndRename` calls can each add up to 30
  frames, silently advancing the walk by up to 120 extra frames beyond what the explicit
  `step`/`stepN` calls imply — affecting where the player ends up and thus the OAM box.

**Fix:** Either document the side effect explicitly in the `settle()` KDoc contract
(frame-count is advanced by the number of frames settled), or — preferable — have `settle()`
not advance the public frame counter for settling frames (settling is a render-stabilisation
detail, not game progression). E.g. expose a `session.runFramesNoCount(n)` for the settle
loop, or snapshot/restore `frameCount` around the loop:
```kotlin
fun settle(): IntArray {
    val frameBefore = session.frameCount   // if a restore API exists
    // ... existing loop ...
    // optionally restore: settling frames are render-warmup, not gameplay frames
}
```
At minimum, add to the KDoc `Contract:` block: "**Frame count:** advances `frameCount`
by the number of frames settled (1..SETTLE_FRAME_CAP)."

### WR-02: `settle()` cannot return the on-entry frame; always advances ≥ SETTLE_STABLE_FRAMES

**File:** `gbkt-emulator/src/main/kotlin/io/github/gbkt/emulator/agent/StepAgent.kt:215-229`
**Issue:** The loop reads `prev = session.getFrameBuffer()` once, then *advances a frame
before its first comparison*. If the frame buffer is already fully rendered and stable at
the moment `settle()` is entered, the function still steps at least `SETTLE_STABLE_FRAMES`
(2) frames before two consecutive reads can match and it returns. There is no early-out for
"already stable". This is a minor correctness wrinkle for the "held-input mid-hold pose"
use case: settling an already-stable held pose nudges the simulation 2+ frames further into
the hold, changing the captured pose from the one the caller intended to capture. Combined
with WR-01, the minimum cost of every settled capture is 2 advanced frames even in the best
case.
**Fix:** Compare against the on-entry frame inside the loop so a pre-stable buffer can be
detected without forcing extra advances, or accept the floor and document it. A
zero-advance early-out:
```kotlin
fun settle(): IntArray {
    var prev = session.getFrameBuffer()
    var consecutiveMatch = 0
    repeat(SETTLE_FRAME_CAP) {
        session.runFrames(1)
        val current = session.getFrameBuffer()
        if (prev.contentEquals(current)) {
            // count the on-entry equality too: an already-stable buffer needs only
            // SETTLE_STABLE_FRAMES-1 *additional* identical reads
            consecutiveMatch++
            if (consecutiveMatch >= SETTLE_STABLE_FRAMES) return current
        } else {
            consecutiveMatch = 0
        }
        prev = current
    }
    return prev
}
```
If the 2-frame floor is intentional (give the PPU time to latch even when entry looks
stable), state that rationale in the KDoc; right now the contract reads as if an
already-stable frame returns immediately, which it does not.

### WR-03: `compareRegion` swallows `tolerance` rounding at small crops — a 1-pixel diff can pass a "pixel-perfect" intent

**File:** `gbkt-emulator/src/main/kotlin/io/github/gbkt/emulator/agent/VisualDiff.kt:158-162`
**Issue:** `compareRegion` computes `diffRatio = diffCount.toDouble() / totalPixels` and
`isMatch = diffRatio <= tolerance`, identical to `compare`. With the default
`tolerance = 0.0` this is exact (any diff fails), which is correct. But the anchor4 gate
relies on the *ratio* semantics over a 768-px crop, and a caller passing a small non-zero
tolerance (say `0.001`) over a 768-px crop silently rounds to "0 pixels allowed" only by
luck of the arithmetic (0.001 * 768 ≈ 0.77 → still fails on 1 px). The behaviour is correct
but the asymmetry between a crop ratio and a full-frame ratio for the *same tolerance value*
is a footgun: a 5% tolerance means "~38 px" on the 768-px box but "~1152 px" full-frame.
This is documented in the KDoc ("in-region ratio"), so it is a WARNING not a BLOCKER, but
callers migrating a tolerance constant from `compare` to `compareRegion` will get a silently
much stricter (in absolute pixels) gate.
**Fix:** No code change strictly required, but add an explicit caution to the KDoc that a
tolerance value is reinterpreted against the crop area, so a tolerance tuned for full-frame
is far stricter in absolute pixels when applied to a small crop. Consider exposing an
absolute-pixel-budget overload for region gates if that semantic is wanted.

### WR-04: anchor4 region gate reads the live OAM box at walk-frame-0 but applies it to the facing-left capture — camera-relative assumption is undocumented-fragile

**File:** `gbkt-examples/platformer-template/.../PlatformerTemplateUatTest.kt:632, 726-735`
**Issue:** `metaspriteBox` is captured once at the walk-frame-0 settle point (line 632) and
then reused as the crop rect for the facing-left frame (lines 727-735). Between those two
captures the test releases RIGHT, holds LEFT for 10 frames, and settles
(lines 663-671) — during which the camera follows the player and, more importantly, the
player physically moves left. The inline comment claims "the duck stays in the same
camera-relative screen region", but nothing enforces that: 10 frames of LEFT plus a settle
(WR-01: +up to 30 more frames) can shift the sprite far enough that the walk-frame-0 box no
longer fully contains the facing-left sprite. If the sprite drifts partly out of the box,
the HIGH ratio drops toward the LOW floor and the gate can flake RED for a reason unrelated
to the hflip. The test does not re-derive the box for the facing-left frame, nor assert that
the facing-left sprite still falls within the walk-frame-0 box.
**Fix:** Either (a) re-derive the bounding box at the facing-left capture point and use the
union (or intersection) of the two boxes for both region diffs, or (b) add an assertion that
the facing-left OAM extents are contained within `metaspriteBox` before running the region
diff, so a camera/position drift fails loudly with a clear message instead of producing a
misleadingly-low HIGH ratio. At minimum, shorten/eliminate the LEFT-hold-then-settle gap or
capture the box immediately adjacent to the facing-left capture.

## Info

### IN-01: Dead/no-op assertion in `compareRegion totalPixels` test

**File:** `gbkt-emulator/src/test/kotlin/io/github/gbkt/emulator/agent/VisualDiffTest.kt:270`
**Issue:** `assertEquals(160 * 144, 23040)` compares two compile-time constants and can
never fail; it documents the full-frame count but is a no-op assertion. The following line
(271) does the real work (`region.totalPixels != 23040`).
**Fix:** Replace the no-op with a comment, or fold the constant into the line-271 message,
e.g. `assertTrue(region.totalPixels != 23040, "Region totalPixels (${region.totalPixels}) must not be the full frame 23040")`.

### IN-02: `settleComparesContentNotIdentity` assigns `firstRendered` but never asserts it is non-null

**File:** `gbkt-emulator/src/test/kotlin/io/github/gbkt/emulator/agent/SettleCaptureTest.kt:192-209`
**Issue:** `firstRendered` is captured via `.also { if (firstRendered == null) firstRendered = it }`
and then passed to `assertNotSame(firstRendered, settled, ...)`. If the stub progression
ever changed such that the rendered branch were never hit, `firstRendered` would be null and
`assertNotSame(null, settled)` would still pass (settled is non-null), giving a false GREEN.
The test's intent ("latched a *later* instance than the first rendered one") is only
meaningful when `firstRendered` is the genuine first rendered instance.
**Fix:** Add `assertNotNull(firstRendered, "stub must have produced a first rendered frame")`
before the `assertNotSame`, so the identity-vs-content guarantee is anchored on a real first
instance.

### IN-03: Magic literals `160`/`144`/`8` repeated in OAM bounding-box math

**File:** `gbkt-examples/platformer-template/.../PlatformerTemplateUatTest.kt:181-185`
**Issue:** `metaspriteBoundingBox` hardcodes the LCD dimensions (`160`, `144`) and the
hardware sprite width (`8`) inline. These are duplicated from the Game Boy LCD spec already
encoded elsewhere in the emulator module (frame buffer is 160×144). A drift between this
test's clamp bounds and the actual frame dimensions would silently mis-clamp the crop.
**Fix:** Reference shared constants (the emulator already knows the LCD dimensions) rather
than re-literalising 160/144/8 in test math. Low priority since the values are stable
hardware constants.

### IN-04: `captureScreenshotSettled` discards the settled buffer it just computed, re-reads via `captureScreenshot`

**File:** `gbkt-emulator/src/main/kotlin/io/github/gbkt/emulator/agent/StepAgent.kt:248-251`
**Issue:** `settle()` returns the stabilised `IntArray`, but `captureScreenshotSettled`
ignores that return value and calls `session.captureScreenshot(label)`, which reads
`emu.getFrameBuffer()` again. Because no frames are advanced between `settle()` returning and
the re-read, the buffers are content-equal, so this is correct — but it relies on the
implicit invariant "no frame advances between settle and capture". A future edit that
advanced a frame in between would silently capture a different frame than the one `settle()`
proved stable. The double read is also a (negligible) wasted copy.
**Fix:** Acceptable as-is, but consider a one-line comment noting the invariant
("captureScreenshot re-reads the now-stable buffer; safe only because no frame is advanced
between settle() and here"), so the coupling is explicit.
