<domain>
## Phase Boundary

Phase 12.10 is a **test-harness / emulator-tooling phase only** — it touches
ZERO codegen (proven by Requirement 5's byte-identical ROM sweep). It bundles
two UAT-harness defects surfaced during the Phase 12.6 debug cycles:

1. **Settle-before-capture primitive.** A reusable capture path that waits for
   the emulator frame to stabilize before reading the frame buffer, so
   post-scene-transition screenshots latch the rendered frame instead of
   stale/blank PPU state (the 413-byte blank PNGs from 11.1-08; the reason
   12.6 fell back to direct-MCP capture).
2. **anchor4 threshold retune.** Recalibrate `anchor4MetaspriteAnimation`'s
   pixel-diff gate from the wrap-corruption-inflated `>10%` (now removed by
   12.6) to a method the genuine ~6.60% facing-right/left diff clears
   deterministically while still proving the hflip occurred.

The direct-MCP capture workflow REMAINS the source-of-truth for user-gated
visual SCs (per CLAUDE.md Visual Evidence Rule). The harness settle primitive
serves **automated regression only**.

<decisions>
## Implementation Decisions

### Area 1 — Settle mechanism design

- **D-01: Settle rule = frame-buffer stability.** The primitive steps frames
  and captures only when consecutive `getFrameBuffer()` snapshots are
  pixel-identical. This proves the PPU latched the new scene (deterministic in
  headless Coffee-GB). Rejected: fixed N-frame settle (magic number, doesn't
  prove stability); rejected: stability + non-blank guard (extra logic; the
  stale-frame bug is a stable-but-wrong scene, not a blank — see D-04 model
  and the Known Limitation below).

- **D-02: Stability params = 2 consecutive identical frames, cap=30,
  best-effort capture on cap (never throws).** Capture once 2 consecutive
  frames are pixel-identical; if 30 frames (≈0.5s) elapse without 2 identical,
  capture the last frame anyway and never throw. Rejected: throw-on-cap (risks
  flakiness on legitimately-animated scenes); rejected: fully-configurable
  `stableFrames`/`maxFrames`/`onTimeout` params (more API surface than this
  phase needs — the 2/30/best-effort defaults are the locked contract; the
  planner MAY expose params with these defaults if a clean signature emerges,
  but it is not required).

- **D-03: Preserve currently-held buttons while settling.** The settle-stepping
  continues holding whatever buttons the caller currently holds, so a held-input
  scene (anchor4's RIGHT/LEFT holds) settles to the real mid-hold pose the
  player sees — not an idle pose. This is why the primitive lives on `StepAgent`
  (D-05): `StepAgent.heldButtons` is the held-state owner. Rejected: release-all
  during settle (wrong pose for anchor4); rejected: explicit `buttons` param
  (unnecessary — held state already lives on StepAgent).

### Area 2 — API placement & surface

- **D-04: Primitive lives on `StepAgent` (not AgentDebugSession, not a
  standalone helper).** `StepAgent` already owns `heldButtons` (required by D-03
  to preserve input) and wraps `session`. `UatRunner` can call through its own
  agent. Lowest-friction; matches where the held-button state lives. Rejected:
  `AgentDebugSession` (doesn't track held buttons — D-03 would need plumbing);
  rejected: standalone `FrameSettle` object (more isolated but needs emulator +
  frame-step callbacks threaded in).

- **D-05: Two public methods on `StepAgent`:**
  - `settle(): IntArray` — low-level; steps until stable per D-01/D-02 and
    returns the stabilized frame buffer. The RED→GREEN test asserts
    immediate-vs-settled buffers **directly** (no PNG round-trip).
  - `captureScreenshotSettled(label: String): File` — settles then writes the
    PNG (settle + existing `captureScreenshot` composition) for UAT use.

  Rejected: capture-only single method (forces the RED→GREEN test through PNG
  VisualDiff ceremony); rejected: `settle()` returning a frame-count (less
  direct RED signal than comparing buffers). Method names are a suggestion —
  planner may rename per `feedback_no_magic_strings` / convention.

- **D-06: anchor4 is the single UAT consumer this phase (SPEC R-01 ≥1 test).**
  anchor4's labeled captures route through `captureScreenshotSettled`. Other
  anchors (1–3, 5) stay on the existing `captureAndRename` path — out of scope
  per SPEC (blast-radius containment).

### Area 3 — anchor4 retune (sprite-region diff)

- **D-07: Retune method = OAM-derived sprite-region diff, NOT a full-frame
  threshold tweak.** Add a region-aware compare that diffs only the ~24×32
  metasprite bounding box. Within that box an hflip flips most pixels → a high,
  meaningful diff % independent of incidental BG-scroll noise. The gate then
  truly measures the sprite, not the camera. Rejected: lowering the full-frame
  threshold to ~4% (diff still mostly BG scroll — weak hflip proof); rejected:
  banded full-frame 4–12% (still entangles BG scroll with the sprite signal).

- **D-08: Region located via `OamSpriteReader` at capture time.** Read the
  visible-sprite OAM extents and build the bounding box dynamically. Robust to
  centering/camera nuances and self-documenting. Rejected: hardcoded screen rect
  (magic rect, brittle if spawn/centering changes — violates no-magic-strings);
  rejected: actor-metadata + world→screen camera mapping (more moving parts than
  OAM extents).

- **D-09: Integrity enforced by an in-code control comparison (NOT prose, NOT a
  separate negative test).** The same test also region-diffs two SAME-facing
  frames (e.g. two facing-right walk frames) and asserts that control diff is
  LOW (below threshold), while facing-right vs facing-left is HIGH. The
  high/low contrast proves the region-diff responds to hflip specifically — a
  no-op gate could not satisfy both assertions. This satisfies SPEC's "gate must
  still FAIL if hflip removed" without needing to synthesize a no-hflip runtime
  state (which would require an out-of-scope codegen change). Rejected:
  documented-threshold-rationale (integrity asserted by prose, not code);
  rejected: separate negative @Test (driving no-hflip at runtime is awkward
  without codegen change).

### Area 4 — RED→GREEN capture-timing test

- **D-10: Test driver = stub emulator (blank/stale → rendered), in the
  `gbkt-emulator` suite.** Inject a stub `GbEmulator` via the existing
  `StepAgent.stubEmulatorFactory` hook whose `getFrameBuffer()` returns
  stale/in-progress buffers early then a stable rendered buffer. Fully
  deterministic, no ROM dependency, runs in CI — and lands IN the
  `gbkt-emulator` suite per SPEC R-02. Rejected: real platformer-template ROM
  (ROM-dependent + would live outside gbkt-emulator); the real-ROM consumption
  proof is already covered by anchor4 (D-06).

- **D-11: Stub frame progression = DISTINCT rendering-in-progress frames →
  repeated identical rendered frame.** The stub returns several distinct
  "rendering-in-progress" buffers for the first few `stepFrame`s, then repeats
  one identical "rendered" buffer. The immediate capture grabs the first
  (stale, mid-render) frame = RED; `settle()` (D-01/D-02) steps until the
  repeats fire = GREEN. The test asserts immediate ≠ settled. This faithfully
  models a real transition AND avoids the identical-blank false positive that
  would occur if the stub held identical blanks (which 2-consecutive-identical
  would wrongly latch on). Rejected: blank-held → rendered (would require the
  non-blank guard we declined in D-01).

### Claude's Discretion

- **Method names** (`settle`, `captureScreenshotSettled`) — D-05 names are
  suggestions; planner may rename to fit convention.
- **Region-compare API shape** — D-07 region diff: planner picks whether it's a
  `VisualDiff.compare(..., region: Rectangle)` overload, a new
  `VisualDiff.compareRegion(...)`, or a small region-crop helper feeding the
  existing `compare`. Any keeps the full-frame `compare` intact.
- **Region threshold value** — the concrete HIGH/LOW thresholds for D-09's
  contrast assertion. Planner calibrates from a real anchor4 run; document the
  rationale in the test per SPEC R-03.
- **Stub buffer contents** — D-11 "distinct" vs "rendered" buffers: planner
  picks concrete pixel patterns (e.g. incrementing fill values) as long as the
  early frames differ from each other and the late frames repeat.
- **Plan-wave structure** — JVM-first RED→GREEN cadence per 12.7/12.8/12.9;
  planner sizes waves (settle primitive + RED→GREEN test → anchor4 region-diff +
  control → suite GREEN → 7-target sweep).

## Known Limitation (researcher note)

Pure 2-consecutive-identical stability (D-01) has a theoretical false-positive
in the real **stale-previous-scene** case: if the OLD scene's frame is itself
stable for ≥2 frames at the very start of a transition (before the new scene's
VRAM writes land), `settle()` could latch the old scene. The D-11 stub model
sidesteps this for the regression test by emitting changing frames. This is an
ACCEPTED limitation because the harness primitive is automated-regression-only
and direct-MCP capture stays the source-of-truth for visual SCs (SPEC boundary).
Researcher should note it; planner need not guard against it unless a cheap
guard (e.g. a minimum-settle-floor of a few frames before stability counts)
falls out naturally.

<specifics>
## Specific Ideas

- **Direct buffer comparison is the RED signal** — D-05's `settle(): IntArray`
  exists specifically so the D-10 test asserts `immediateBuffer != settledBuffer`
  on raw IntArrays, avoiding PNG-encode/decode flakiness in the regression proof.
- **Control comparison is the integrity proof** — D-09's same-facing LOW vs
  facing-flip HIGH is the mechanism that satisfies SPEC's "still fails if hflip
  removed" WITHOUT an out-of-scope codegen change to disable hflip. Two
  facing-right walk frames (already captured in anchor4's 01–03 sequence) are
  the natural control pair.
- **The 6.60% number is full-frame** — the real measured diff that soft-fails
  today is a FULL-FRAME ratio dominated by BG scroll. After D-07's region diff,
  the in-region facing-flip ratio will be MUCH higher (most of a 24×32 box
  flips), so the retuned threshold is calibrated against the region, not 6.60%.

</specifics>

<deferred>
## Deferred Ideas

### Migrate anchors 1–3, 5 onto the settle primitive

Only anchor4 consumes `captureScreenshotSettled` this phase (SPEC blast-radius
containment). If the other anchors show capture-timing flakiness later, migrate
them in a follow-up — not pre-planned.

### Stale-previous-scene settle guard

The D-01 known limitation (old scene stable ≥2 frames could false-latch). If a
real UAT test trips this, add a minimum-settle-floor or a scene-change-detect
guard. Deferred — accepted limitation because the harness is regression-only.

### Region-diff API generalization

If multiple future tests need region diffs, promote D-07's region path to a
first-class `VisualDiff` API with named regions. For now it serves anchor4 only.

### Configurable settle params

D-02 locks 2/30/best-effort. If a future animated-scene test needs different
tuning, expose `stableFrames`/`maxFrames`/`onTimeout`. Deferred unless a
concrete need surfaces.

### UatRunner settle integration

`UatRunner.checkpoint()` could route through the settle primitive for golden
comparisons. Out of scope (only anchor4 / StepAgent consumes it this phase).

</deferred>
