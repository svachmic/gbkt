## Summary

Phase 12.10 is a pure test-harness fix — zero codegen. Two defects surfaced during Phase 12.6 debug cycles are bundled: (1) `StepAgent.captureScreenshot()` reads whatever frame the PPU holds at call time, which is stale/blank immediately post-scene-transition; (2) `anchor4MetaspriteAnimation` pixel-diff gate (`>10%` full-frame) was calibrated against now-removed wrap-corruption BG inflation and soft-fails at the real 6.60% diff.

The design is fully locked in CONTEXT.md (D-01..D-11). Research confirms that all referenced line numbers and API shapes match the live code. The planner's job is implementation only — no design decisions remain open except the discretionary items listed in Claude's Discretion.

**Primary recommendation:** Implement `StepAgent.settle(): IntArray` (stability loop using `session.runFrames(1)` + `session.getFrameBuffer()` comparison, holding `heldButtons`), then `captureScreenshotSettled` composing settle + existing `session.captureScreenshot`. For anchor4, add a `VisualDiff.compareRegion` (or crop-then-compare helper) using `OamSpriteReader.readVisible(session.getMemory())` to derive the metasprite bounding box. Write the D-10 stub test first (JVM-first RED→GREEN cadence).

## Architecture Patterns

### Settle Loop Pattern (D-01/D-02/D-03)

```kotlin
// Source: CONTEXT.md D-01/D-02/D-03 + CoffeeGbEmulator.getFrameBuffer() copy semantics [VERIFIED]
fun settle(): IntArray {
    var prev = session.getFrameBuffer()
    var consecutiveMatch = 0
    for (frame in 0 until 30) {  // cap = 30
        session.runFrames(1)     // advance 1 frame; held buttons remain pressed in emulator
        val current = session.getFrameBuffer()
        if (prev.contentEquals(current)) {
            consecutiveMatch++
            if (consecutiveMatch >= 2) return current  // stable for 2 consecutive frames
        } else {
            consecutiveMatch = 0
        }
        prev = current
    }
    return prev  // best-effort: cap reached, return last frame (never throws)
}
```

**Key constraint:** `session.runFrames(1)` advances frames without re-dispatching input events. The buttons pressed via `session.executeInputScript(hold(b))` in the prior `step()` call remain in the emulator's physical input state. This satisfies D-03 (preserve held buttons) without reading `heldButtons` inside the settle loop.

**Note:** `session` is `private val` in StepAgent. Both `settle()` and `captureScreenshotSettled()` live ON `StepAgent`, so they access `session` directly — no visibility change needed.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Frame buffer copy semantics | Manual frame buffer caching | `CoffeeGbEmulator.getFrameBuffer()` (already returns `copyOf()`) | Copy is guaranteed per the synchronized block; two calls to `getFrameBuffer()` AFTER the same frame will always be contentEquals — no stale reference risk |

## Common Pitfalls

### Pitfall 1: Settle loop calls `step()` instead of `session.runFrames(1)`
**What goes wrong:** `step()` inside the settle loop recomputes a button delta. If `step(emptySet())` is called, it emits RELEASE events for all held buttons (dpad-right/left in anchor4's mid-hold pose), changing the emulator's input state mid-settle and producing the wrong pose.
**Why it happens:** `settle()` needs to advance frames, and `step()` is the obvious public method.
**How to avoid:** Call `session.runFrames(1)` directly inside `settle()`. Buttons remain pressed in the emulator from the prior `session.executeInputScript(hold(b))` call made by `step()`.
**Warning signs:** anchor4 settle produces idle-pose frames instead of mid-hold walk frames.

### Pitfall 2: `captureScreenshotSettled` calls `ScreenshotCapture.capture` directly
**What goes wrong:** Bypasses the variable snapshot (VariableInspector.readAll) that `session.captureScreenshot` writes to the JSON sidecar. UAT tests that read the JSON sidecar for variable assertions get stale data.
**How to avoid:** `captureScreenshotSettled(label)` calls `settle()` first, then `session.captureScreenshot(label)` (not `captureFrameBuffer()` + manual PNG encode).

### Pitfall 3: Stub `getFrameBuffer()` returns the SAME OBJECT across calls
**What goes wrong:** If the stub returns the same IntArray object for all "stale" calls, D-11's progression is correct BUT the D-10 test may have false contentEquals depending on mutation. More critically: if the "rendered" buffer IS the same IntArray reference, `contentEquals` will be true trivially even if the settle logic is broken.
**How to avoid:** Use distinct IntArray instances for each stale frame AND the rendered frame. The two rendered frames should be `contentEquals` but NOT the same reference (to prove the logic compares content, not identity).

### Pitfall 4: `OamSpriteReader.readVisible` called with wrong memory
**What goes wrong:** In anchor4, the test uses `agent.readMemory(addr)` for individual memory reads. But `OamSpriteReader.readVisible` requires a `MemoryAccess` object. If the test constructs a `mockMemory()` (from test helpers) instead of the live emulator memory, OAM will be all-zeros and `readVisible` returns an empty list → bounding box calculation panics.
**How to avoid:** Build the `MemoryAccess` adapter from `agent.readMemory` / `agent.writeMemory` to access the live emulator's OAM at the moment of capture (after the frame where sprites are visible on screen).

### Pitfall 5: Region crop `BufferedImage.getSubimage` with negative or out-of-bounds coordinates
**What goes wrong:** `OamSpriteReader.screenX`/`screenY` can be negative (sprites partially off-screen). `getSubimage(x, y, w, h)` throws if x < 0 or x+w > imageWidth.
**How to avoid:** Clamp the bounding box: `minX = max(0, minX)`, `minY = max(0, minY)`, `maxX = min(160, maxX)`, `maxY = min(144, maxY)` before cropping.

### Pitfall 6: D-09 control pair uses screenshots from DIFFERENT frames with BG scroll
**What goes wrong:** If the two "same-facing" control frames (e.g., walk-frame-0 and walk-frame-2) happen to have significantly different BG scroll positions, the IN-REGION diff may be non-zero due to BG bleeding through the sprite layer, producing a spuriously HIGH control diff and defeating the high/low contrast assertion.
**How to avoid:** The control pair should be two frames with the SAME BG scroll position (same camera position) but different walk animation frames — or the region should be verified to contain only sprite pixels. In anchor4's existing setup, the 3 walk frames are captured 6 frames apart while scrolling, so BG may differ slightly. Alternatively: use the facing-right frame 0 TWICE as the control pair (exact same file → 0% diff) to prove the floor. Simplest: `walk0Screenshot == walk0Screenshot` control diff must be 0%.

### Pitfall 7: `./gradlew clean :a:buildRom :b:buildRom` with too-long chains on low-memory CI
**What goes wrong:** The 7-target sweep runs as one Gradle invocation. If the chain includes `clean` before a long series of `:buildRom` targets, the Gradle daemon may exhaust heap on heavy targets.
**How to avoid:** Per `feedback_no_parallel_gradle_clean.md` the rule is ONE invocation not ONE PER TARGET. The existing pattern from 12.9 is `./gradlew clean :pong:buildRom :breakout:buildRom ...` — Gradle serializes per-target internally. This is verified as the correct pattern.

## Open Questions

1. **Memory access shape for OamSpriteReader in anchor4**
   - What we know: `StepAgent.readMemory(addr)` exposes individual byte reads; `OamSpriteReader.readVisible(memory: MemoryAccess)` requires the full interface
   - What's unclear: Planner must choose between (a) adding `fun getMemory(): MemoryAccess` thin wrapper on `StepAgent`, or (b) building an inline `MemoryAccess` adapter in the anchor4 test
   - Recommendation: Option (a) is cleaner and consistent with the "harness layer" principle; option (b) keeps StepAgent's API smaller. Both are within Claude's Discretion.

2. **D-09 control pair identity: which two "same-facing" frames to use?**
   - What we know: Walk frames 01–03 are facing-right; they're captured 6 frames apart with active scrolling
   - What's unclear: Do the 3 walk frames have enough BG-scroll position variation to produce a non-zero in-region control diff?
   - Recommendation: Use walk-frame-0 vs walk-frame-0 (same file) as the LOW control pair — guarantees 0% in-region diff, maximally strong control assertion. Then HIGH = walk-frame-0 vs facing-left (facing-flip). The 0%/HIGH contrast satisfies D-09 without any BG-scroll concern.

3. **Concrete threshold values for D-09 HIGH/LOW**
   - What we know: Full-frame diff is ~6.60%; in-region diff for a 24×32 box where most pixels flip will be much higher (plausibly 50-80%)
   - What's unclear: Exact value depends on duck art; planner must run one real anchor4 capture to calibrate
   - Recommendation: Run `./gradlew :gbkt-examples:platformer-template:buildRom` then a one-shot test that prints `diffCount/totalPixels` for the in-region comparison. Lock the threshold 10pp below the measured value for repeatability margin.
