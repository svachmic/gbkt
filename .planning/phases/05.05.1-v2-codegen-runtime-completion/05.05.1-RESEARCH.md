## Summary

The v2 codegen pipeline currently generates compilable ROMs that boot into a blank screen during gameplay. The root cause is threefold: (1) `ScriptOpVisitor` only handles 7 of 20+ `ScriptOp` types — all others emit `/* TODO */` comments; (2) `ActorVisitor` generates only position variable declarations with no OAM initialization or per-frame `move_sprite()` calls; and (3) the sprite helper functions (`hide_sprites_range`, `show_sprites_range`) are empty stubs. The game logic variables update correctly each frame but sprites are never written to hardware OAM, so the screen stays blank.

This phase has two parallel tracks: (A) make the three example games playable by implementing sprite rendering, sound, and the remaining ScriptOp handlers; and (B) unseal the v2 IR interfaces and restructure into the layered module architecture. Track B must happen before Track A scales up, because building more codegen on top of sealed interfaces creates rework debt that would need unwinding before BOM publishing.

**Primary recommendation:** Implement in three sequential waves — (1) unseal IR + module restructure, (2) sprite rendering + OAM management + asset include integration, (3) remaining ScriptOp handlers + sound driver. Each wave produces testable, committed C output.

## Architecture Patterns

### Current V2 Pipeline Architecture

```
GameIR
  ├── GBDKPipelineV2.buildCFiles()
  │     ├── buildHomeFile()    → CFile("main.c", bank=0)
  │     │     ├── SceneVisitor.generateSceneEnum()  → defines
  │     │     ├── ActorVisitor.visit()               → position vars only (GAP)
  │     │     ├── globalVars + joypadVars
  │     │     ├── buildInputHelperFunctions()         → implemented
  │     │     ├── buildSpriteHelperStubs()            → STUB (GAP)
  │     │     ├── buildTrampolineStubs()              → implemented
  │     │     ├── buildNavigateToSceneFunction()      → implemented
  │     │     └── buildMainFunction()                 → implemented
  │     ├── buildSceneFile()   → CFile("bank1.c", bank=1)
  │     │     └── SceneVisitor.visit() per scene
  │     │           └── ScriptOpVisitor.visit() per op  (7/20+ handled)
  │     └── buildHeaderFile()  → CFile("game.h", isHeader=true)
  └── CEmitter.emit() → String per CFile
```

### What "Playable" Means at the C Level

For Pong to show sprites on screen, the generated C must:

1. **At game init (main.c init section or scene enter):** Load sprite tile data into VRAM:
```c
// Load paddle tile (8x16 = 2 tiles)
set_sprite_data(0, 2, paddle_tiles);
// Load ball tile (8x8 = 1 tile)
set_sprite_data(2, 1, ball_tiles);
```

2. **At game enter (scene enter):** Set OAM entries to initial positions:
```c
// paddle1 at OAM slot 0 (8x16 composite = slots 0,1)
set_sprite_tile(0, 0); move_sprite(0, 16+8, 64+16);  // GBDK +8,+16 hardware offset
set_sprite_tile(1, 1); move_sprite(1, 16+8, 72+16);
// paddle2 at OAM slot 2 (slots 2,3)
set_sprite_tile(2, 0); move_sprite(2, 152+8, 64+16);
set_sprite_tile(3, 1); move_sprite(3, 152+8, 72+16);
// ball at OAM slot 4
set_sprite_tile(4, 2); move_sprite(4, 80+8, 72+16);
```

3. **Each frame (in `update_sprites()` called from scene frame):** Sync position variables to OAM:
```c
void update_sprites(void) {
    move_sprite(0, _paddle1_x + 8, _paddle1_y + 16);
    move_sprite(1, _paddle1_x + 8, _paddle1_y + 24);
    move_sprite(2, _paddle2_x + 8, _paddle2_y + 16);
    move_sprite(3, _paddle2_x + 8, _paddle2_y + 24);
    move_sprite(4, _ball_x + 8, _ball_y + 16);
}
```

The GBDK hardware coordinate system adds 8 to x and 16 to y because OAM position 0,0 is off-screen (hardware quirk — tiles at x<8 or y<16 are clipped).

### Pattern 1: Inline Sprite Manager (Claude's Discretion Resolved)

**Recommendation:** Emit a thin inline `update_sprites()` function that syncs position variables to OAM every frame. This avoids per-operation move_sprite calls scattered through scene code and makes the generated C easy to read.

```c
// Generated in main.c for Pong:
void update_sprites(void) {
    // paddle1: OAM slots 0-1 (8x16 = 2 tiles tall)
    move_sprite(0, _paddle1_x + 8, _paddle1_y + 16);
    move_sprite(1, _paddle1_x + 8, _paddle1_y + 24);
    // paddle2: OAM slots 2-3
    move_sprite(2, _paddle2_x + 8, _paddle2_y + 16);
    move_sprite(3, _paddle2_x + 8, _paddle2_y + 24);
    // ball: OAM slot 4
    move_sprite(4, _ball_x + 8, _ball_y + 16);
}
```

`update_sprites()` is called from main game loop (in `buildMainFunction()`) after `update_joypad()` and before `wait_vbl_done()`.

**Why this over per-call approach:** `SetPosition` and `MoveBy` update Kotlin-side position variables. The OAM sync happens once per frame, avoiding redundant hardware writes when multiple `MoveBy` ops touch the same actor in one frame (e.g., Pong AI does two paddle movements).

### Pattern 2: Asset Include Integration

Locked decision: `png2asset` outputs are `#include`d directly. This means the generated C adds:
```c
#include "sprites/paddle.h"    // declares: const unsigned char paddle_tiles[]
#include "sprites/ball.h"
```

The asset pipeline's `png2asset` invocation must produce `.h` and `.c` files with tile data. The generated `main.c` includes the `.h` files and calls `set_sprite_data()` using the declared arrays. The `.c` files are compiled separately by lcc.

### Pattern 3: ScriptOp Visitor Pattern (BOM-01 unlock)

Current: `sealed interface ScriptOp`
Required: `interface ScriptOp` + `ScriptOpVisitor` interface

```kotlin
// In gbkt-core/ir/v2/ScriptOp.kt (after unsealing):
interface ScriptOp {
    val sourceLocation: SourceLocation?
    fun <T> accept(visitor: ScriptOpVisitorI<T>): T
}

// Visitor interface:
interface ScriptOpVisitorI<T> {
    fun visitAssign(op: Assign): T
    fun visitIfOp(op: IfOp): T
    // ... all 20+ op types
}
```

The existing `ScriptOpVisitor` object becomes an implementation of this interface.

### Pattern 4: Sound Preset System

Sound presets map named presets to register sequences:

```c
// Generated inline sound driver for Breakout:
void play_sound_hit(void) {
    // CH1: Square wave, short burst
    NR10_REG = 0x16;   // Frequency sweep
    NR11_REG = 0x40;   // Duty 50%, length 0
    NR12_REG = 0xF3;   // Envelope: max volume, decreasing
    NR13_REG = 0x83;   // Frequency lo
    NR14_REG = 0xC7;   // Frequency hi + trigger + use length
}

void play_sound_score(void) { /* COIN preset */ }
void play_sound_lose(void) { /* EXPLOSION preset */ }
void play_sound_win(void) { /* POWERUP preset */ }
```

The `PlaySound` ScriptOp emits `CExprStatement(CCall("play_sound_${soundId}", emptyList()))`. The sound functions are generated in `main.c` by a new `buildSoundFunctions()` method in `GBDKPipelineV2`.

### Anti-Patterns to Avoid

- **TODO stubs left in generated C**: Any `/* TODO */` comment in generated output means a broken game. Zero stubs after this phase.
- **Busy-wait for WaitFrames**: Do NOT emit a `for (i=0; i<frames; i++) wait_vbl_done()` loop. Use state machine pattern with frame counter variable.
- **Direct BANKED calls from HOME**: `navigate_to_scene` is in HOME bank; sound functions and sprite manager must also be HOME-resident or callable via trampoline.
- **Forgetting GBDK coordinate offset**: GBDK sprite positions have +8x, +16y hardware offset. Forgetting this makes sprites appear 8px left and 16px up from expected position.
- **printf in game scene**: PrintOp uses `printf()` which writes to background tile layer — corrupts sprite backgrounds. Use only in title/menu scenes or use window layer for in-game HUD.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| PNG to 2bpp conversion | Custom Java ImageIO parser | `png2asset` (GBDK bundled) | Locked decision. png2asset handles palette ordering, tile deduplication, metasprites correctly. |
| Sound register values | Calculate from frequency/envelope math | Preset table with verified register values | GBDK sound registers are finicky; wrong values cause no sound or harsh noise. Verified presets from GBDK examples are reliable. |
| OAM slot allocation algorithm | Custom bin-packing | Use OAM slot from `ActorIR.oamSlot` annotation (filled by analysis pass) | Analysis pass (OAMAllocationPass) already assigns slots. Don't duplicate the allocation logic. |

**Key insight:** The analysis passes (Phase 4) already annotate `ActorIR.oamSlot` with hardware slot assignments. The codegen layer just needs to read `actor.oamSlot?.slot` and emit the corresponding `move_sprite(slot, x, y)` calls. This is already done for bank slots — the same pattern applies to OAM slots.

## Common Pitfalls

### Pitfall 1: OAM Slot Annotation May Be Null

**What goes wrong:** `ActorIR.oamSlot` is null when the analysis pipeline hasn't run (e.g., in unit tests with inline `GameIR` fixtures). Codegen crashes with NPE or emits wrong slot numbers.

**Why it happens:** Analysis passes are optional — the v2 pipeline runs without them in tests. `OAMAllocationPass` fills `oamSlot`, but tests bypass the full pass pipeline.

**How to avoid:** Use fallback slot assignment when `oamSlot` is null: assign OAM slots sequentially based on actor order in `gameIR.actors`. Document that slot numbers are analysis-assigned when present and index-fallback otherwise.

**Warning signs:** `actor.oamSlot == null` in the codegen — indicates analysis didn't run or actor is new.

### Pitfall 2: Metasprite Tile Calculation

**What goes wrong:** A 4x16 paddle sprite requires 2 OAM slots (two 8x8 tiles stacked vertically). Emitting only one `move_sprite()` call shows only half the sprite.

**Why it happens:** GBDK sprites are always 8x8. Multi-tile sprites need multiple OAM entries. The `SpriteDef.size` field carries the logical size (e.g., `SizeDef(4, 16)`) but the actual OAM count is `ceil(width/8) * ceil(height/8)`.

**How to avoid:** Calculate OAM slots per actor as `tilesWide * tilesHigh` where `tilesWide = ceil(width/8)` and `tilesHigh = ceil(height/8)`. The paddle (4x16) needs `1 * 2 = 2` OAM slots. The ball (4x4) needs `1 * 1 = 1` OAM slot.

**Warning signs:** Sprites that look half-cut vertically or appear as a single tile where a taller sprite was expected.

### Pitfall 3: Module Restructure Breaks Sealed Exhaustiveness

**What goes wrong:** After unsealing `ScriptOp`, `when(op)` expressions in existing code no longer enforce exhaustiveness. New `ScriptOp` implementations added in genre modules are invisible to `when(op)` — they fall through to the visitor `else` branch silently.

**Why it happens:** Kotlin's sealed interface exhaustiveness is compile-time only within the defining module. Once you break the seal, `when` becomes non-exhaustive. The visitor pattern is the correct replacement but requires adding a method to the visitor interface for each new op type.

**How to avoid:** Replace every `when(op)` in codegen with `op.accept(visitor)`. Implement the visitor interface with an `abstract` base class that throws `UnsupportedOperationException` for unknown ops — new ops fail loudly at runtime rather than silently.

**Warning signs:** Adding a new `ScriptOp` subtype and the compiler doesn't error anywhere — that's the sign sealed enforcement is gone and visitors need to be updated manually.

### Pitfall 4: Sound Functions in BANKED Code

**What goes wrong:** Scene functions are in `bank1.c` (BANKED). Calling `play_sound_hit()` from a scene function works in HOME bank but fails from BANKED scene functions if the sound function is also BANKED.

**Why it happens:** GBDK's BANKED calling convention requires trampolines for calls between different banks. Sound functions called from scene code must be in HOME bank (or have trampolines).

**How to avoid:** Generate all sound functions in `main.c` (HOME bank, bank 0). Add prototype declarations to `game.h`. Scene functions in `bank1.c` can then call HOME-resident sound functions directly without trampolines — HOME bank is always accessible.

**Warning signs:** Build succeeds but sound doesn't play in-game (symptom: BANKED function called without bank switch).

### Pitfall 5: WaitFrames Breaks the Game Loop

**What goes wrong:** Implementing `WaitFrames` as a busy-wait loop (`for (i=0; i<frames; i++) wait_vbl_done()`) blocks the entire game loop for the duration. Input is unread, sprites don't update.

**Why it happens:** Naive implementation treats WaitFrames as a synchronous delay.

**How to avoid:** WaitFrames requires state machine approach: emit a frame counter variable and return from the scene frame function if the counter isn't zero. Locked decision specifies "state machine approach (frame counter + resume), not busy-wait loop."

**Implementation approach:** `WaitFrames(5)` emits:
```c
if (_wait_counter > 0) { _wait_counter--; return; }
// ... rest of scene frame body
```
The `_wait_counter` is set to N at the `WaitFrames` insertion point and decremented each frame until zero.

## Code Examples

### Example 1: ActorVisitor with OAM Initialization

```kotlin
// ActorVisitor.kt — extended to generate OAM init
fun generateSpriteInit(actor: ActorIR): List<CStatement> {
    val sprite = actor.sprite ?: return emptyList()
    val oamSlot = actor.oamSlot?.slot ?: fallbackSlot(actor)
    val tilesWide = (sprite.size.width + 7) / 8
    val tilesHigh = (sprite.size.height + 7) / 8
    val statements = mutableListOf<CStatement>()
    var slot = oamSlot
    for (row in 0 until tilesHigh) {
        for (col in 0 until tilesWide) {
            val tileIndex = row * tilesWide + col
            statements += CExprStatement(CCall("set_sprite_tile", listOf(CLiteral(slot), CLiteral(tileIndex))))
            val xOffset = col * 8
            val yOffset = row * 8
            statements += CExprStatement(CCall("move_sprite", listOf(
                CLiteral(slot),
                CBinaryExpr(CVar("_${actor.id}_x"), "+", CLiteral(8 + xOffset)),
                CBinaryExpr(CVar("_${actor.id}_y"), "+", CLiteral(16 + yOffset))
            )))
            slot++
        }
    }
    return statements
}
```

### Example 2: update_sprites() Generation

```kotlin
// In GBDKPipelineV2.buildSpriteUpdateFunction():
private fun buildSpriteUpdateFunction(gameIR: GameIR): CFunction {
    val statements = mutableListOf<CStatement>()
    var currentSlot = 0
    for (actor in gameIR.actors) {
        val sprite = actor.sprite ?: continue
        val oamSlot = actor.oamSlot?.slot ?: currentSlot
        val tilesWide = (sprite.size.width + 7) / 8
        val tilesHigh = (sprite.size.height + 7) / 8
        for (row in 0 until tilesHigh) {
            for (col in 0 until tilesWide) {
                val slot = oamSlot + row * tilesWide + col
                val xExpr = CBinaryExpr(CVar("_${actor.id}_x"), "+", CLiteral(8 + col * 8))
                val yExpr = CBinaryExpr(CVar("_${actor.id}_y"), "+", CLiteral(16 + row * 8))
                statements += CExprStatement(CCall("move_sprite", listOf(CLiteral(slot), xExpr, yExpr)))
            }
        }
        currentSlot = oamSlot + tilesWide * tilesHigh
    }
    return CFunction(
        name = "update_sprites",
        returnType = CVoid,
        body = statements,
        sectionComment = "Sprite OAM sync (called every frame)"
    )
}
```

private fun buildSoundFunctions(gameIR: GameIR): List<CFunction> {

private fun buildSoundFunction(id: String, preset: String): CFunction {
    val body = when (preset) {
        "HIT" -> listOf(
            CRawCode("NR10_REG = 0x16;"),
            CRawCode("NR11_REG = 0x40;"),
            CRawCode("NR12_REG = 0xF3;"),
            CRawCode("NR13_REG = 0x83;"),
            CRawCode("NR14_REG = 0xC7;")

        "COIN" -> listOf(/* COIN register sequence */)
        "EXPLOSION" -> listOf(/* EXPLOSION register sequence */)
        "POWERUP" -> listOf(/* POWERUP register sequence */)
        "TICK" -> listOf(/* TICK register sequence */)
        "SELECT" -> listOf(/* SELECT register sequence */)
        else -> listOf(CRawCode("/* Unknown preset: $preset */"))
    }
    return CFunction(name = "play_sound_$id", returnType = CVoid, body = body)
}

## Open Questions

1. **OAM slot allocation when analysis hasn't run**
   - What we know: `ActorIR.oamSlot` is filled by `OAMAllocationPass`. Tests often bypass analysis.
   - What's unclear: Should the codegen synthesize sequential fallback slots, or require analysis to have run?
   - Recommendation: Use sequential fallback (actor index → slot) with a build warning if `oamSlot` is null. Tests pass; real builds use analysis slots.

2. **png2asset integration timing**
   - What we know: Locked decision is to shell out to `png2asset` at build time; outputs are `#include`d
   - What's unclear: Does `png2asset` need to run before codegen, or can codegen emit `#include "sprites/X.h"` regardless and let the build system ensure the file exists?
   - Recommendation: Emit the `#include` unconditionally; the Gradle plugin task ordering ensures `png2asset` runs before `generateC`. No codegen change needed for the `#include` itself — just add the include directive to `buildHomeFile()`.

3. **ShowDialog/ShowMenu scope for this phase**
   - What we know: Locked decision is "production quality, not printf placeholders"
   - What's unclear: Does "production quality" for Explorer require full window layer rendering, or is a printf-based approximation acceptable for the initial playable milestone while a follow-up polishes the UI?
   - Recommendation: Implement window layer dialog (GBDK `SHOW_WIN` / `move_win` / `set_win_tiles`) matching GBDK-2020 example patterns. The window layer is the correct approach (prevents text from corrupting the background tilemap layer).

4. **Module restructure scope per phase**
   - What we know: CONTEXT.md says "IR unsealing + module restructure must happen BEFORE building more codegen on top"
   - What's unclear: Does the full AndroidX-style Gradle module split happen in 05.05.1, or is unsealing sufficient for now with file moves deferred to 5.1?
   - Recommendation: Unseal IR interfaces (required) + create new Gradle module stubs + move files to correct packages. Full BOM/version alignment is Phase 5.2 (BOM publishing) not this phase.
