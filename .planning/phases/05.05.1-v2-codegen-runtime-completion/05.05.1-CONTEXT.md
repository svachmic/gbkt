# Phase 05.05.1: V2 Codegen Runtime Completion - Context

**Gathered:** 2026-02-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Complete the v2 codegen pipeline so it produces fully playable ROMs — not just compilable ones. This includes:
1. Porting all ScriptOp handlers, sprite rendering, OAM management, and sound from v1 concepts to v2's typed C AST pipeline
2. Full DSL surface coverage — every documented DSL construct produces working C code
3. Unsealing the v2 IR and restructuring into the layered module architecture (gbkt-ir → gbkt-lang → gbkt-engine → genre extensions)

The reference standard is pixel-perfect parity with the original GBDK-2020 example games. V1 never produced working games — v2 is the first real implementation.

**Expanded scope from original roadmap:** Originally scoped to three example games; expanded to full DSL coverage and module restructuring because building on sealed IR would require rework later.

</domain>

<decisions>
## Implementation Decisions

### Sprite Rendering Approach
- V2 generates its own inline sprite manager per game (not a shared library file)
- Generated C mirrors GBDK-2020 example patterns (direct set_sprite_data/move_sprite/set_sprite_tile calls) for debuggability via side-by-side comparison
- Build-time PNG → 2bpp conversion using GBDK's `png2asset` tool (shell out at build time)
- png2asset outputs are `#include`d directly — not parsed and re-emitted through the typed C AST
- Support all sprite complexity from the start: simple 8x8, composite metasprites (16x16 = 4 OAM slots), GBC color palettes
- Sprite assets ship in the gbkt repo (gbkt-examples/) — self-contained, no dependency on GBDK install paths for assets
- GBC palette support from day one

### Claude's Discretion: Sprite Manager
- Whether to keep a thin inline sprite manager for OAM slot tracking or emit direct GBDK calls — Claude decides based on what integrates best with `#include` approach and GBDK-style C output

### Playable Definition Per Game
- **Pong:** Full gameplay loop — paddles move, ball bounces, scoring works, game-over transition, restart. Pixel-perfect match to GBDK-2020 pong example
- **Breakout:** Full feature parity — paddle, ball, brick grid, brick destruction, sound effects on collision, lives, scoring. Pixel-perfect match to GBDK-2020 breakout example
- **Explorer:** Showcase gbkt capabilities — full dungeon crawl with grid movement, scene transitions, dungeon floors, random encounters, battle screen, inventory, menus. Goes beyond basic GBDK explorer example to demonstrate the DSL's power

### ScriptOp Coverage
- Port ALL 20+ ScriptOp types — not just what the three examples need
- ShowDialog: Full windowed text box rendering with borders (production quality, not printf placeholders)
- ShowMenu: Full selectable menu rendering (production quality)
- WaitFrames: State machine approach (frame counter + resume), not busy-wait loop. Non-blocking during gameplay
- CallOp/ReturnOp: Inline at call site (expand called script's body). Faster at runtime, avoids call overhead on GB CPU
- No ScriptOps left as TODO stubs after this phase

### Sound System
- Sound driver layer (not direct register writes) — handles channel allocation and priority for multiple simultaneous sounds
- Inline per game (consistent with sprite approach — no shared library files)
- Both predefined presets AND custom waveform definitions in DSL
- Music + SFX support — background music tracks using tracker format plus short sound effects

### Module Architecture (CRITICAL)
- **Unseal v2 IR interfaces** (ScriptOp, Expr, SystemIR) — replace sealed with visitor pattern
- IR is an active design goal for alternative frontends (visual editors, JSON definitions, etc.) — not just Kotlin DSL
- JVM-only for now (no JSON/protobuf IR serialization in this phase)

**Layered module structure (AndroidX-style coordinates):**

| Group ID | Artifact ID | Contains |
|----------|-------------|----------|
| io.github.gbkt.core | ir | IR types + visitor interfaces |
| io.github.gbkt.core | lang | DSL recording, variables, expressions |
| io.github.gbkt.engine | engine | Entities, scenes, input, graphics, collision, movement, camera, tweens, sound, UI basics |
| io.github.gbkt.rpg | rpg | Characters, battles, abilities, items, stats |
| io.github.gbkt.world | world | Floors, encounters, flags, maps |
| io.github.gbkt.exploration | exploration | Dungeon crawling, gauges, keys |
| io.github.gbkt.backend | api | Backend contract interface |
| io.github.gbkt.backend | gbdk | GBDK/Game Boy codegen |
| io.github.gbkt | gbkt-all | Meta-dependency: everything |
| io.github.gbkt | gbkt-bom | Version alignment |
| io.github.gbkt.tools | gradle-plugin | Build infrastructure (like AGP — does NOT pull libraries) |
| io.github.gbkt.tools | cli | Command-line tool |
| io.github.gbkt.tools | intellij-plugin | IDE support |

**Developer consumption:**
- `gbkt-all`: One import gets everything (beginners)
- `gbkt-bom` + individual imports: Version alignment with explicit feature selection (power users)
- Gradle plugin is build infrastructure only — does not pull library dependencies (like AGP doesn't pull AndroidX)

### Project Vision & Quality Bar
- **Pipeline:** Complete v2 codegen → UAT validation → LabyrinthOfTheDragon port → publishable v1 of gbkt
- **Approach:** Careful and deliberate, not quick wins
- **Generated C quality:** Production quality — readable, well-structured, well-commented. Something you'd be proud to show
- **Testing:** JVM AST tests + ROM compilation verification (requires GBDK in CI)
- **Error handling:** Configurable — default fail-fast with clear errors, `--lenient` flag for partial output during development

### Example Games Strategy
- Extend existing three games (Pong, Breakout, Explorer) to full feature parity
- Create additional targeted showcase-quality examples that exercise specific subsystems (RPG battle demo, menu demo, etc.)
- Examples are documentation/tutorial material — part of the publishable v1 vision

### LotD (LabyrinthOfTheDragon)
- This phase is about generic DSL coverage, NOT LotD-specific
- LotD is a separate phase after initial UAT of the three games
- LotD will most likely need a full rewrite of the gbkt-rpg package

</decisions>

<specifics>
## Specific Ideas

- Generated C should read like the GBDK-2020 example C code — debuggable by comparing side-by-side
- V1 codegen never produced working games — v2 is the first real implementation, targeting GBDK example parity
- The IR unsealing + module restructure must happen BEFORE building more codegen on top — prevents building on a foundation that needs rewriting
- Module naming follows AndroidX conventions (group-per-domain: io.github.gbkt.core, io.github.gbkt.engine, io.github.gbkt.rpg)
- Separating gbkt-lang from gbkt-ir is an active design goal to support alternative frontends to the Kotlin DSL

</specifics>

<deferred>
## Deferred Ideas

- IR serialization format (JSON/protobuf) for non-JVM frontends — future phase after v1 launch
- LabyrinthOfTheDragon port — separate phase after UAT, likely requires gbkt-rpg rewrite
- Headless emulator tests (ROM behavior verification) — considered but JVM + compilation testing is sufficient for now

</deferred>
