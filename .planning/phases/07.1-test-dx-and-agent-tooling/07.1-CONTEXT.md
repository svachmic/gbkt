# Phase 07.1: Test DX and Agent Tooling - Context

**Gathered:** 2026-03-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Eliminate test boilerplate, simplify UatRunner DSL, create game playbook format for LLM agents, enrich game_metadata.json, expand MCP server capabilities. Tests feel like describing gameplay in Kotlin, not wiring infrastructure. LLM agents get a natural-language playbook and enriched tools to play-test games autonomously.

**Scope includes:**
- New `gbkt-test` module with JUnit5 extension and test recipes
- Metadata enrichment (controls, transitions, variable semantics)
- Markdown playbook format per game with auto-scaffold task
- MCP server expansion (save/load state, batch assert, playbook, game discovery)
- GameConstants enrichment (Controls, Transitions objects)
- Migration of all 9 existing StepAgentTests to new extension
- `context/TESTING.md` documentation

**Scope excludes:**
- Interactive play-testing (Phase 07.2)
- End-user documentation site (may materialize after implementation)
- Multi-session MCP server
- LotD-specific testing

</domain>

<decisions>
## Implementation Decisions

### Test Boilerplate Elimination
- **JUnit5 extension** (`GbktTestExtension`) as the primary test API — `@RegisterExtension val game = GbktTestExtension("pong")`
- **Convention-based discovery** with override: extension infers ROM/sym/metadata paths from game name using standard Gradle layout. Individual paths can be overridden for non-standard layouts
- **Auto-managed lifecycle**: extension creates StepAgent in `@BeforeEach`, closes in `@AfterEach`. No `.use { }` blocks needed. Fresh agent per test
- **Fluent assertion DSL**: `game.assertScene()`, `game.assertVariable()`, `game.assertActorVisible()`, `game.assertTextOnScreen()` — wraps UatRunner assertions with cleaner API
- **Auto-screenshot on failure**: extension captures screenshot + variable dump on any assertion failure. Saved to `build/gbkt/test-failures/{TestClass}_{testName}_frame{N}.png` + `.json` sidecar
- **bootToScene() method**: StepAgent gets `bootToScene(sceneName)` that auto-navigates using metadata. Games with complex flows (RPG-Lite, Dungeon) can provide custom boot scripts that override the default
- **No magic strings**: all tests use `GameConstants` (Scenes.TITLE, Variables.SCORE, etc.) — never raw string literals for game identifiers

### New gbkt-test Module
- Dedicated module for test infrastructure — NOT in gbkt-emulator testFixtures
- Dependencies: gbkt-emulator, JUnit5
- Contains: `GbktTestExtension`, fluent assertion helpers, test recipes, game-aware test reporter
- Example games add `testImplementation(project(":gbkt-test"))` dependency

### Test Migration
- All 9 existing StepAgentTests migrated to use `GbktTestExtension` + `GameConstants`
- Proves the new DX works end-to-end and eliminates all boilerplate

### Test Tiers (Naming Convention)
- **Tier 1: Simulation** — `*SimTest` / `*GameTest` (fast, no ROM, uses `SimulationContext`)
- **Tier 2: Emulator** — `*EmulatorTest` / `*IntegrationTest` (real ROM, uses `GbktTestExtension`)
- Both tiers coexist in same test source set, clearly differentiated by naming

### Test Recipes
- Pre-built composable patterns: `game.verifyTitleScreen()`, `game.verifyAllSceneTransitions()`, `game.verifyInputResponds(scene, button, variable, expectDecrease)`, `game.verifySpriteVisibility(scene, actors)`
- Recipes use metadata-driven logic — work across any game without game-specific code

### Game-Aware Test Output
- After tests, print per-game summary: scenes tested, assertions passed/failed, screenshots captured
- Formatted console output alongside standard JUnit results

### Game Playbook Format
- **Markdown per game** (`PLAYBOOK.md`) co-located in each example's directory (e.g., `gbkt-examples/pong/PLAYBOOK.md`)
- **Natural language**, NOT deterministic test scripts — describes what the game IS, how it's played, what winning/losing looks like, known quirks
- **For LLM agents**: agent reads playbook to understand the game, then uses MCP tools to play-test. Agent figures out the details (variable names, button sequences) from metadata
- **For CI**: deterministic testing is handled by Kotlin emulator tests, NOT playbooks
- **Auto-scaffold**: `./gradlew generatePlaybook` task generates PLAYBOOK.md skeleton from game_metadata.json (scenes, actors, variables). Developer adds gameplay prose

### Metadata Enrichment
- **Control mappings per scene**: extracted from DSL input handlers (e.g., `whenever(dpad.up.held) { moveBy(paddle1, ...) }` → `{ "game": { "UP": "moves paddle1" } }`)
- **Scene transition graph**: extracted from `navigate()` calls (e.g., `{ from: "title", to: "game", trigger: "START" }`)
- **Variable semantics**: categories (score, position, velocity, state, counter, flag) + description field, auto-detected from variable names heuristically
- **Auto-extracted from DSL/IR**: pipeline analyzes input handlers, navigate calls, and variable declarations. No manual annotations needed
- **emulator_describe_game** returns full enriched metadata automatically

### GameConstants Enrichment
- Add `Controls` object (e.g., `Controls.GAME_UP = "UP"`) and `Transitions` object (e.g., `Transitions.TITLE_TO_GAME = "title->game"`)
- `generateGameConstants` task auto-wired: `generateC → generateGameConstants → compileTestKotlin`. Zero manual setup

### MCP Server Expansion
- **New tools:**
  - `emulator_save_state(label)` → `{ stateFile, frame, scene }`
  - `emulator_load_state(label)` → `{ restored, frame, scene }`
  - `emulator_get_playbook()` → `{ content: "# Pong\n..." }`
  - `emulator_assert(checks: [...])` → `{ passed, failed, results }` (batch assertions)
  - `emulator_list_games()` → list of available games with build status
- **Assert types**: variable_equals, variable_in_range, scene_is, text_on_screen, actor_visible, sprite_count
- **Game name loading**: `emulator_start` accepts `game: "pong"` for convention-based discovery OR explicit file paths. Both work
- **Game discovery**: scans project for built ROMs. Works for both multi-game projects (gbkt-examples/) AND single-game standalone projects (user's own game with gbkt plugin)
- **Single session**: one game at a time, matching current architecture

### Documentation
- New `context/TESTING.md` guide covering: test tiers, GbktTestExtension API, test recipes, GameConstants, playbook format, troubleshooting
- Module `gbkt-test/CLAUDE.md` for developer reference
- End-user documentation site may come later after full implementation

- Test reporter formatting details
- Playbook scaffold template structure
- MCP game discovery scan implementation details

<code_context>
## Existing Code Insights

### Reusable Assets
- `StepAgent`: Full agent API (step, stepN, readVariable, writeVariable, waitForScene, captureScreenshot) — extension wraps this
- `UatRunner`: Assertion framework (assertVariable, assertScene, assertTextOnScreen, checkpoint) — extension delegates to this
- `GameMetadata`: Parses game_metadata.json (scenes, actors, variables, texts) — extend with controls/transitions/semantics
- `GenerateGameConstantsTask`: Generates type-safe GameConstants.kt from metadata — extend with Controls/Transitions
- `AgentSessionConfig.discoverFiles()`: Auto-discovers sym/metadata from ROM file — reuse in extension discovery
- `SavestateManager`: Save/load emulator state — expose via MCP tools
- `ScreenshotCapture`: PNG capture from frame buffer — reuse for failure screenshots
- `VramTextVerifier`: Text detection on screen — powers assertTextOnScreen
- `OamSpriteReader`: Sprite position reading — powers assertActorVisible

### Established Patterns
- Gradle plugin registers tasks via `GbktPlugin.kt` with task dependencies in `afterEvaluate`
- MCP tools registered in `ToolHandlers.kt` via `Server.registerEmulatorTools()`
- GameConstants generated from game_metadata.json using `toConstantName()` + collision resolution
- Per-game tests use `Assumptions.assumeTrue(ROM_FILE.exists())` for graceful skip when ROM not built

### Integration Points
- New `gbkt-test` module added to multi-module build (settings.gradle.kts)
- `GbktTestExtension` wraps `StepAgent` + `GameMetadata` + `AgentSessionConfig`
- `generateGameConstants` task wired between `generateC` and `compileTestKotlin`
- `generatePlaybook` task reads game_metadata.json, writes PLAYBOOK.md
- MCP `ToolHandlers.kt` gets 5 new tool registrations
- Metadata enrichment happens in `GBDKPipelineV2.buildMetadataFile()`

</code_context>

<specifics>
## Specific Ideas

- "Avoid magic strings as much as possible — for variables we have a codegen object. If it's not good enough, fix it. Don't carry over magic strings from the project, it's a recipe for disaster."
- Playbooks are NOT deterministic test plans — they're "here's the game, here's how it's played, you figure it out" descriptions for LLM agents. CI testing uses Kotlin integration tests.
- MCP game discovery must work for both multi-game repos (gbkt-examples/) AND single-game standalone projects (user's game with the gbkt plugin running in their IDE)
- End-user documentation may materialize after full implementation — for now, `context/TESTING.md` is the developer guide
- Test boilerplate is in gbkt-test module (not in gbkt-emulator) — be mindful of module boundaries

</specifics>

## Deferred Ideas

- **End-user documentation site** — may come after full implementation, separate from developer docs
- **Multi-session MCP server** — named sessions for switching between games. Current architecture is single-session
- **GIF sequence capture** — multi-frame animations for motion/transition validation via MCP
- **Visual diff MCP tool** — compare screenshots programmatically via MCP (exists in emulator but not exposed as MCP tool)
