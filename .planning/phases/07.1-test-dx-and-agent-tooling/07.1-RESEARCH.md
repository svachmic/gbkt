## Summary

Phase 07.1 is a developer-experience and tooling phase that builds on top of the complete Phase 07 UAT infrastructure. The existing codebase has all building blocks: `StepAgent`, `UatRunner`, `GameMetadata`, `AgentSessionConfig`, `SavestateManager`, `ScreenshotCapture`, and 11 MCP tools. The work is additive — creating the `gbkt-test` JUnit5 extension module, enriching metadata with controls/transitions/variable semantics, expanding GameConstants to include Controls and Transitions objects, adding 5 new MCP tools, and establishing the PLAYBOOK.md format.

The boilerplate problem is concrete: all 9 `*StepAgentTest.kt` files contain the same companion object with hardcoded paths, same `Assumptions.assumeTrue(ROM_FILE.exists(), ...)` pattern, same `GameMetadata.fromJsonFile()` + `AgentSessionConfig()` + `StepAgent(config, metadata).use {}` setup. A JUnit5 extension with `@RegisterExtension` eliminates all of this in one annotation.

Metadata enrichment requires extending `GBDKPipelineV2.buildMetadataFile()` to walk the IR and extract: `NavigateTo` ops (for transition graph), `CallExpr` nodes whose function is `dpad_held`/`button_pressed`/`dpad_pressed` (for control mappings), and variable name heuristics (for semantics). All extraction happens at codegen time from the already-analyzed IR — no runtime or emulator involvement.

**Primary recommendation:** Build gbkt-test as the thin JUnit5 wrapper layer; keep all game-driving logic in StepAgent/UatRunner; extend metadata enrichment in GBDKPipelineV2; expand MCP ToolHandlers with 5 new tools that delegate to SavestateManager and game discovery utilities already present in the codebase.

### Pattern 1: JUnit5 Extension Lifecycle

The `GbktTestExtension` implements three JUnit5 interfaces:
- `BeforeEachCallback` — creates `StepAgent`, calls `start()`
- `AfterEachCallback` — calls `close()` on agent
- `TestExecutionExceptionHandler` — captures screenshot + variable dump on any test failure before re-throwing

```kotlin
// Source: JUnit5 docs / project convention
class GbktTestExtension(
    private val gameName: String,
    private val customRomFile: File? = null,
) : BeforeEachCallback, AfterEachCallback, TestExecutionExceptionHandler {

    private lateinit var _agent: StepAgent

    val agent: StepAgent get() = _agent

    override fun beforeEach(context: ExtensionContext) {
        val config = if (customRomFile != null) {
            AgentSessionConfig.discoverFiles(customRomFile)
        } else {
            GameDiscovery.configForGame(gameName)
        }
        // Assumptions.assumeTrue equivalent — skip gracefully if ROM missing
        _agent = StepAgent(config)
        _agent.start()
    }

    override fun afterEach(context: ExtensionContext) {
        if (::_agent.isInitialized) _agent.close()
    }

    override fun handleTestExecutionException(context: ExtensionContext, throwable: Throwable) {
        // Capture failure screenshot before rethrowing
        if (::_agent.isInitialized) {
            val testName = "${context.requiredTestClass.simpleName}_${context.requiredTestMethod.name}"
            _agent.captureScreenshot("failure_$testName")
            // Also dump variables to JSON sidecar (ScreenshotCapture already does this)
        }
        throw throwable
    }
}
```

**Migration pattern** (what existing tests look like vs. new pattern):
```kotlin
// BEFORE (75+ lines of boilerplate per test class)

    private val ROM_FILE = File("build/gbkt/output/pong.gb")
```

### Pattern 3: Metadata Enrichment in GBDKPipelineV2

`buildMetadataFile(GameIR)` must be extended to walk the IR and emit three new JSON sections. The IR walk is already available — this is a matter of adding extraction logic.

**Control mapping extraction**: Walk each `SceneIR.frameScript` (a list of `ScriptOp`). Find `IfOp` nodes whose condition is a `CallExpr` with function name matching `dpad_held`, `dpad_pressed`, `button_held`, `button_pressed`. The argument is a `VarRef` with the GBDK constant name (`J_UP`, `J_A`, etc.). Map these to a per-scene controls JSON object.

**Transition extraction**: Walk every `ScriptOp` recursively; find `NavigateTo` ops. Record `{from: sceneName, to: sceneId, context: "frame|enter|exit"}`. These form an edge list in the metadata.

**Variable semantics**: For each `VariableDef`, apply name-based heuristics. This is a pure string-matching function in the pipeline with no IR dependency.

```kotlin
// Variable semantic heuristic (Claude's discretion implementation)
internal fun inferVariableSemantic(name: String): VariableSemantic {
    val lower = name.lowercase()
    return when {
        lower.contains("score") || lower.contains("point") -> VariableSemantic.SCORE
        lower.endsWith("_x") || lower.endsWith("_y") -> VariableSemantic.POSITION
        lower.contains("dx") || lower.contains("dy") || lower.contains("vel") || lower.contains("speed") -> VariableSemantic.VELOCITY
        lower.contains("hp") || lower.contains("health") || lower.contains("mp") || lower.contains("sp") -> VariableSemantic.STAT
        lower.contains("flag") || lower.contains("met") || lower.contains("has_") || lower.contains("is_") -> VariableSemantic.FLAG
        lower.contains("step") || lower.contains("count") || lower.contains("frame") || lower.contains("timer") -> VariableSemantic.COUNTER
        lower == "current_scene" -> VariableSemantic.STATE
        else -> VariableSemantic.UNKNOWN
    }
}
```

### Pattern 5: MCP Tool Registration

New tools follow the exact pattern established in `ToolHandlers.kt`. Each tool is a `addTool()` call in `Server.registerEmulatorTools()` with a JSON schema and a handler that delegates to `McpEmulatorSession`.

```kotlin
// Source: existing ToolHandlers.kt pattern
server.addTool(
    name = "emulator_save_state",
    description = "Save current emulator memory state with a label for later restore",
    inputSchema = buildJsonObject {
        put("type", "object")
        putJsonObject("properties") {
            putJsonObject("label") {
                put("type", "string")
                put("description", "Label for this savestate (used as filename)")
            }
        }
        putJsonArray("required") { add(JsonPrimitive("label")) }

    val label = args?.get("label")?.jsonPrimitive?.content
```

The `McpEmulatorSession` gets corresponding `saveState(label)`, `loadState(label)`, `getPlaybook()`, `batchAssert(checks)`, `listGames()` methods that delegate to `SavestateManager` and `GameDiscovery`.

### Anti-Patterns to Avoid

- **Magic strings in test code**: All scene names, variable names, actor names MUST come from `GameConstants`. The existing `PongStepAgentTest` already follows this — the new extension reinforces it.
- **ROM path hardcoding in test class body**: Path resolution belongs in `GbktTestExtension`/`GameDiscovery`, not in test class companions.
- **Checking ROM existence in every test**: The extension handles this once in `beforeEach`; individual tests should not duplicate `Assumptions.assumeTrue(romFile.exists())`.
- **Metadata enrichment through annotations**: Enrichment must be auto-extracted from IR, not via `@ControlMapping` annotations in DSL code. Zero user annotation burden.
- **MCP save state exposing internal file paths**: `emulator_save_state(label)` should return `{label, frame, scene}` — not internal file paths. The session manages storage.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| ROM file existence check + skip | Custom skip logic | `Assumptions.assumeTrue()` (JUnit5) | Already the project pattern; JUnit5 assumption failures show as "skipped" not "failed" |
| Agent lifecycle | Manual `.use { }` blocks | `GbktTestExtension` `@RegisterExtension` | That's the entire point of the extension |
| Screenshot on failure | Custom test listener | `TestExecutionExceptionHandler` | JUnit5 extension interface specifically for this |
| Save/load emulator state | New save format | `SavestateManager` (already exists in gbkt-emulator) | Already implemented: saves WRAM+OAM+HRAM to binary file with magic bytes |
| Control mapping extraction | New IR visitor | Direct walk in `GBDKPipelineV2.buildMetadataFile()` | IR walk already happening there; IfOp + CallExpr nodes are already in the existing IR walk |
| Variable name→semantic mapping | ML model or config file | Pure string heuristics function | Simple and sufficient; the patterns (suffixes like `_x`, `_y`, contains `score`) are high-confidence |

**Key insight:** 80% of this phase is wiring existing code together, not building new algorithms. `SavestateManager`, `ScreenshotCapture`, `AgentSessionConfig.discoverFiles()`, `VramTextVerifier`, `OamSpriteReader` are all complete. The extension and MCP tools are thin delegation layers.

## Common Pitfalls

### Pitfall 1: JUnit5 Extension Instance Scope

**What goes wrong:** Creating the extension with `@ExtendWith` at class level means one instance per test class, not per test. If agent state leaks between tests, assertions fail unexpectedly.
**Why it happens:** `@ExtendWith` and `@RegisterExtension` have different instance lifetimes.
**How to avoid:** Use `@RegisterExtension` (instance field) which creates a fresh extension per test class. The extension's `beforeEach`/`afterEach` callbacks handle per-test agent lifecycle.
**Warning signs:** Tests pass in isolation but fail when run together.

### Pitfall 2: AgentSessionConfig.discoverFiles() Requires Existing ROM

**What goes wrong:** `AgentSessionConfig` constructor has `require(romFile.exists())` — calling it before checking existence throws `IllegalArgumentException` not a JUnit5 assumption failure.
**Why it happens:** The existing API requires the ROM to exist at construction time.
**How to avoid:** In `GbktTestExtension.beforeEach()`, check ROM existence with `File(...).exists()` BEFORE constructing `AgentSessionConfig`. Call `Assumptions.assumeTrue(romFile.exists(), "ROM not found — run buildRom first")` to produce a proper skip.

### Pitfall 3: GameConstants Package Mismatch

**What goes wrong:** `GenerateGameConstantsTask` derives the package name from the game's `mainClass` setting (e.g., `io.github.gbkt.examples.pong`). If Controls/Transitions are added to the same `GameConstants` object, they must use the same package — no separate file.
**Why it happens:** The generated file path is `$packagePath/GameConstants.kt` under the build directory.
**How to avoid:** Add Controls and Transitions as nested objects inside the existing GameConstants generation, not as separate files.

### Pitfall 4: Metadata Enrichment IR Walk Completeness

**What goes wrong:** Control mapping extraction may miss input handlers inside nested `IfOp` blocks (e.g., `whenever(cond1) { whenever(dpad.up.held) { ... } }`).
**Why it happens:** A shallow walk of `SceneIR.frameScript` misses nested scripts.
**How to avoid:** Use recursive ScriptOp walk (depth-first traversal) when extracting NavigateTo and input CallExpr nodes. The IR already contains a `body` list in `IfOp` — walk it recursively.

### Pitfall 5: bootToScene() Navigation Assumptions

**What goes wrong:** A `bootToScene("game")` implementation that presses START and waits for the scene may fail on games with complex intro sequences (RPG-Lite has a character select screen, Dungeon has cutscene text).
**Why it happens:** The simple navigation path (title → press START → gameplay) doesn't generalize.
**How to avoid:** `bootToScene()` uses metadata's transition graph to find navigation path, but also allows games to register custom boot scripts. The extension checks if a custom boot script exists first; falls back to metadata-driven navigation.

### Pitfall 6: MCP emulator_list_games() in Standalone Projects

**What goes wrong:** Scanning `gbkt-examples/` for ROMs doesn't work in a user's standalone project where their game is at `build/gbkt/output/mygame.gb`.
**Why it happens:** The multi-game project layout assumption is baked in.
**How to avoid:** `GameDiscovery.scanForBuiltRoms()` scans two locations: `./build/gbkt/output/` (standalone) AND `./gbkt-examples/*/build/gbkt/output/` (multi-game repo). Returns union with game name inferred from ROM filename.

### Pitfall 7: Variable Semantic Heuristics — False Positives

**What goes wrong:** Variable named `playerState` gets classified as `POSITION` because it ends with a common suffix, or `scoreMultiplier` as `COUNTER` due to false match.
**Why it happens:** Simple string matching can overlap.
**How to avoid:** Order checks from most-specific to least-specific. Check exact suffix patterns (`_x`, `_y`) before broader substring matches (`score`). Default to `UNKNOWN` rather than guessing.

## Open Questions

1. **bootToScene() for complex game flows**
   - What we know: Simple games (Pong, Breakout) go title → press START → gameplay in ~180 frames
   - What's unclear: RPG-Lite has character select; Dungeon has multi-step intro cutscene. Does metadata's transition graph contain enough info to auto-navigate, or does each game need a custom boot script?
   - Recommendation: Implement metadata-driven navigation as the default (title → find START transition → first non-title scene). Provide an override hook `GbktTestExtension("rpg-lite") { bootScript = { agent.stepN(120); agent.step(setOf(Button.START)); agent.stepN(60) } }`. Start with this for all 9 games and see which ones need custom scripts.

2. **Controls JSON structure in metadata**
   - What we know: Input handlers are `CallExpr("dpad_held", [VarRef("J_UP")])` inside `IfOp` in scene frame scripts
   - What's unclear: The extracted "effect" (what the input does) requires understanding the IfOp body — which may be complex IR. A simple heuristic (the first `ScriptOp` in the body, e.g. `MoveBy(actor, dx, dy)`) may be sufficient.
   - Recommendation: For the first pass, record `{scene, button, firstOp}` and let `GenerateGameConstantsTask` emit `Controls.GAME_UP = "UP"` constants. Skip "effect description" extraction — the PLAYBOOK.md developer adds prose descriptions anyway.

3. **gbkt-test module build.gradle.kts dependency scoping**
   - What we know: `gbkt-test` needs `gbkt-emulator` and JUnit5. Both are `api` dependencies (consumers of `gbkt-test` need them too).
   - What's unclear: Should JUnit5 be `api` or `compileOnly`? Example games already have JUnit5 in their test dependencies. Making it `api` might cause version conflicts.
   - Recommendation: Use `compileOnly(platform("org.junit:junit-bom:5.11.x"))` + `compileOnly("org.junit.jupiter:junit-jupiter-api")` so consumers bring their own JUnit5 version. `gbkt-emulator` should be `api`.
