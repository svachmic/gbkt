## User Constraints (from CONTEXT.md)

### Locked Decisions

**Overall Vision & Philosophy**
- **v1-inspired, v2-native**: Use v1 conventions where they fit, let v2's script-op model shape the DSL naturally where it diverges
- **No magic strings**: Variable/actor/scene names inferred from Kotlin property names. No dual naming with string parameters. Optional string override for rare edge cases (C name conflicts)
- **Declarative, not imperative**: Game code should describe WHAT happens, not step-by-step HOW
- **Both reactive rules AND lifecycle**: `whenever(condition) { effect }` for behavior, `enter/frame/exit` for structure — both are first-class
- **Compose-like scalability**: Must work with thousands of LOC. Proper subpackages, imports, domain-organized builders
- **Error quality matters**: Two layers — Kotlin compiler catches type errors at compile time, DSL validation catches semantic errors at build time. IntelliJ plugin provides live feedback (plugin enhancements may extend beyond this phase, but type system design must enable it)
- **Example games are the spec**: If Pong, Breakout, and Explorer look clean and natural, the DSL is good enough
- **IDE discoverability**: Type system should guide developers via autocomplete

**Variable Delegate Syntax**
- **Delegate-based (`var x by ...`)**: Natural Kotlin `=`, `+=`, `-=` via `getValue`/`setValue` delegates
- **Name inference**: Kotlin property name IS the C identifier. `var score by u8Var(0)` → C: `uint8_t score = 0;`
- **Optional name override**: `var hp by u8Var(100, "hitPts")` for rare cases
- **Full arithmetic operators**: `+`, `-`, `*`, `/`, `%` on variables and expressions. All compound assignments (`+=`, `-=`, `*=`, `/=`, `%=`)
- **Comparison operators**: Both standard Kotlin (`>=`, `<=`, `>`, `<`, `==`) AND infix names (`isAbove`, `isBelow`, `isAtLeast`) — user's choice per expression
- **Logical operators**: Both `&&`/`||`/`!` AND `and`/`or`/`not` — both styles supported
- **Unary operators**: Negation (`-x`), increment (`++x`, `x++`), decrement (`--x`, `x--`)
- **Bitwise operators**: Available but not front-and-center. DSL surface exposes friendly high-level operations. Bitwise is an escape hatch for advanced users only
- **Explicit type casting**: Mixed type expressions (u8 + u16) require explicit cast: `score.toU16() + timer`. No implicit widening

**Array Syntax**
- **Both `[]` operator AND `get()`/`set()` methods** available
- **`get()` returns an optional** — leverage Kotlin's nullable types
- **Rich array API**: `exists`, `size`, and other collection-like helpers
- Declaration: `val bricks by u8Array(30)`

**Actor Property Access**
- **Actors as typed objects**: Actor definition bundles position, sprite, hitbox, and custom properties into a typed object
- **Direct property access**: `ball.x`, `ball.y`, `ball.visible` are real assignable properties
- **Both mutation AND methods**: `ball.x += 2` for quick mutations, `ball.moveTo(80, 72)` for semantic operations
- **Custom properties via extension**: Actors can define custom properties in their builder (`var dx by i8Prop(1)`) accessible as `ball.dx`
- **Collision syntax**: Method-based: `whenever(ball.collides(paddle)) { }` instead of infix `collidesWith`

**Color Definition**
- **DMG**: Preset constants (`WHITE`, `LIGHT_GRAY`, `DARK_GRAY`, `BLACK`) for 4-shade palettes
- **GBC**: Hex literals with helpers, plus builder support. Compile-time warnings when color won't match developer's intent on actual hardware (RGB555 fidelity)
- **Helpful presets**: Modifiable preset palettes for common GBC color schemes

**Literal Auto-Wrapping**
- **Full wrapping everywhere**: Both `score + 5` AND `5 + score` work. Extension functions on Int/Long to support left-side operations
- **String auto-wrap**: `showDialog("Hello!")`, `print("Score: " + score)` — plain Kotlin strings work in DSL functions
- **Boolean auto-wrap**: `ball.visible = true`, `flag = false` — Kotlin booleans work directly
- **raw() kept but discouraged**: `raw("c_code")` exists as escape hatch but generates a compiler warning. Signals DSL should eventually cover the case

**Migration & API Strategy**
- **New layer on top of ScriptBuilder**: ScriptBuilder stays as internal workhorse (used by codegen/tests). New DSL layer wraps it with delegate syntax. Game authors use the DSL layer — ScriptBuilder is the engine under the hood
- **Old syntax removed from public API**: `assign()`, `varRef()`, `literal()` become internal/private. Only Kotlin-idiomatic syntax is public
- **All example games migrated at once**: Pong, Breakout, and Explorer all rewritten together
- **Acceptance: equivalent behavior**: C output can differ structurally, but ROMs must be functionally identical
- **Test strategy**: All existing tests pass + new DSL-specific tests + ROM behavioral equivalence
- **Docs updated inline**: Each code change that modifies syntax also updates the relevant doc section (CLAUDE.md, DSL_REFERENCE.md, examples)

## Summary

Phase 05.05.2 is a pure DSL ergonomics refactor — no new IR nodes, no new codegen features. The existing IR and backend are already correct. The goal is to replace the assembly-style surface syntax in the three example games with natural Kotlin idioms so that developers write `ball.x += ballDx` instead of `assign("ball.x", varRef("ball.x") + varRef("ballDx"))`.

The key technical challenge is making Kotlin's property delegate and operator overload systems bridge into IR-recording side effects. This is a solved pattern in the codebase (the v1 `ExpressionWrapper` class and `AssignableVar` delegate already demonstrate it), and the v2 IR already has the right shape (`PropertyAccessExpr`, `VarRef`, `Assign` with `AssignOp`). The work is primarily in the DSL layer (`gbkt-lang`), not in IR or backend.

The three examples reveal exactly what needs to change: (1) `varRef("score")` → `score` (where `score` is the `AssignableVar` delegate result), (2) `assign("score", varRef("score") + literal(1))` → `score += 1`, (3) `varRef("ball.x")` → `ball.x` (ActorRef property), (4) `literal(5)` auto-wrapping from `Int` directly, and (5) `assign("ball.x", ...)` → actor property setter syntax.

**Primary recommendation:** Implement `AssignableVar` as a full expression type with operator overloads, add `set`/`+=`/`-=`/`*=` methods that emit ScriptOp into the active `ScriptBuilder`, give `ActorRef` typed property accessors (`ActorPropertyRef`) that work the same way, and make `Int` extension functions wrap into `Expr` for left-side arithmetic.

## Current State (What Exists)

### What Already Works

**`AssignableVar` already exists** (`VariableBuilders.kt`) and returns the variable name. Delegates (`u8Var`, `i8Var`, `u16Var`, `i16Var`, `u8Array`) already register `VariableDef` with `GameBuilder`.

**`ExprBuilder.kt` already has** operator extensions on `Expr`:
- Arithmetic: `plus`, `minus`, `times`, `div`, `rem`, `unaryMinus` (right-side Int versions already exist: `Expr.plus(Int)`)
- Bitwise: `and`, `or`, `xor`, `shl`, `shr`, `inv`
- Comparison: `isAbove`, `isBelow`, `isAtLeast`, `isAtMost`, `isEqualTo`, `isNotEqualTo`
- Logical: `logicalAnd`, `logicalOr`, `not`

**`PropertyAccessExpr` already exists** in `Expr.kt` as an IR node. `ExprVisitor.visitPropertyAccessExpr()` already emits `CVar(sanitizeVarName("${objectId}.${property}"))` → `_ball_x` in C. This is the same output as `varRef("ball.x")` produces today.

**`VarRef("ball.x")` and `varRef("ball.y")` already produce correct C** — the `sanitizeVarName` logic replaces dots with underscores and adds a leading underscore prefix. So the C output is already correct for actor properties; it's only the DSL syntax that is verbose.

**`ScriptBuilder` is the IR recorder** — it has all the `assign()`, `arrayAssign()`, `arrayRef()`, `whenever()`, etc. methods that need to be called as the backend. The new DSL layer must route through these.

### What Is Missing (What Needs to Be Built)

The ergonomic gap between current and target state, organized by feature:

**1. Variable `set`/compound assignment operators**

Current (assembly-style):
```kotlin
assign("score", literal(0))
assign("score", varRef("score") + literal(1))
```

Target (Kotlin-idiomatic):
```kotlin
score set 0
score += 1
```

`AssignableVar` is the delegate result. It needs:
- `set(value: Expr)` — emits `Assign(name, value, AssignOp.SET)` into the active `ScriptBuilder`
- `set(value: Int)` — auto-wraps `Literal(value)`
- `plusAssign(value: Expr)` / `plusAssign(value: Int)` — emits `AssignOp.ADD`
- `minusAssign`, `timesAssign`, `divAssign`, `remAssign` — same pattern
- Inherits all `Expr` operator extensions via the existing `toExpr()` delegation

Problem: ScriptBuilder methods must be called — but `AssignableVar` doesn't have a reference to the active `ScriptBuilder`. The solution (see Architecture Patterns below) is a `ScriptBuilderContext` thread-local, analogous to the existing `GameBuilderContext`.

**2. Actor property access as Expr**

Current:
```kotlin
varRef("ball.x")                          // as expression
assign("ball.x", varRef("ball.x") + 1)   // as assignment target
```

Target:
```kotlin
ball.x                    // as expression → PropertyAccessExpr("ball", "x")
ball.x += 1              // as assignment target → Assign("ball.x", ...)
```

`ActorRef` currently has only `id: String`. It needs:
- `val x: ActorPropertyRef` — property returning an `ActorPropertyRef` delegate
- `val y: ActorPropertyRef` — same
- `val visible: ActorBoolPropertyRef` — special boolean property
- `ActorPropertyRef` is expression-capable (like `AssignableVar`) and records mutations via `ScriptBuilderContext`

**3. Int literal auto-wrapping (left-side)**

Current:
```kotlin
score isAbove literal(5)        // requires literal() wrapper
5 + score                        // FAILS — Int.plus(AssignableVar) doesn't exist
```

Target:
```kotlin
score isAbove 5                  // Int overload on isAbove already exists ✓ (just need AssignableVar to extend Expr)
5 + score                        // needs: operator fun Int.plus(other: AssignableVar): Expr
```

The right-side `Int` overloads already exist on `Expr` (`Expr.plus(Int: Expr)`). The missing pieces are:
- Left-side extension functions: `operator fun Int.plus(other: Expr): Expr`, `operator fun Int.minus(other: Expr): Expr`, etc.
- `AssignableVar` needs to implement `Expr` (or expose a compatible interface) so it can be used in comparison infix functions without calling `.toExpr()`.

**4. Array ergonomics**

Current:
```kotlin
val bricks by u8Array("bricks", 30)   // requires explicit name string
arrayAssign("bricks", varRef("bi"), literal(1))
arrayRef("bricks", varRef("bidx"))
```

Target:
```kotlin
val bricks by u8Array(30)    // name inferred from property name
bricks[bi] = 1               // operator set, bi is AssignableVar
bricks[bidx]                 // operator get, bidx is AssignableVar
```

The `ArrayDelegate` already has `provideDelegate` but currently requires explicit name. Name inference via `property.name` (as `VarDelegate` does it) is the fix.

**5. ScriptBuilder context access from property actions**

The critical architectural insight: `AssignableVar.set(value)` needs to call `ScriptBuilder.assign(...)`. But `set()` is called inside a `ScriptBuilder` lambda (e.g., `frame { score += 1 }`). The ScriptBuilder is the receiver of that lambda, but the `AssignableVar` delegate itself has no reference to it.

The solution pattern is a thread-local context — exactly how `GameBuilderContext` already works. A `ScriptBuilderContext` thread-local set at the beginning of each `ScriptBuilder.{enter,frame,exit,whenever}` block would allow `AssignableVar.set()` to find the active `ScriptBuilder`.

**6. `varRef()`/`literal()`/`assign()` access control**

These three functions currently live in `ExprBuilder.kt` (top-level) and `ScriptBuilder` respectively. Making them `internal` removes them from game author code. The migration: any existing test that uses them directly will still compile (same module), but example games and user code will lose access.

## Architecture Patterns

### Pattern 1: ScriptBuilderContext Thread-Local

The active `ScriptBuilder` must be accessible from `AssignableVar.set()`, `ActorPropertyRef` setters, and array indexing. The proven solution is a `ThreadLocal`:

```kotlin
// In gbkt-lang: dsl/v2/ScriptBuilderContext.kt (new file)
internal object ScriptBuilderContext {
    private val holder = ThreadLocal<ScriptBuilder?>()

    val current: ScriptBuilder? get() = holder.get()

    fun <T> with(builder: ScriptBuilder, block: () -> T): T {
        val previous = holder.get()
        holder.set(builder)
        return try { block() } finally { holder.set(previous) }
    }
}
```

`ScriptBuilder` must set this context before executing each user-provided block:

```kotlin
// Modified ScriptBuilder.whenever() — same pattern for all block-producing methods
fun whenever(condition: Expr, block: ScriptBuilder.() -> Unit) {
    val loc = captureV2Location()
    val bodyBuilder = ScriptBuilder()
    ScriptBuilderContext.with(bodyBuilder) { bodyBuilder.block() }  // ← set context
    ops += IfOp(condition, bodyBuilder.build(), emptyList(), sourceLocation = loc)
}
```

The same applies to `SceneBuilder.enter {}`, `frame {}`, and `exit {}` blocks — wherever a `ScriptBuilder` lambda executes.

**Precedent:** `GameBuilderContext` in `VariableBuilders.kt` is exactly this pattern and is already used by `VarDelegate.provideDelegate()`.

### Pattern 2: AssignableVar as Expr Participant

`AssignableVar` currently wraps a name string and has a `toExpr()` method. For the new ergonomics, it should behave like an `Expr` in most contexts. Two design options:

**Option A: AssignableVar implements Expr directly** — Cannot do this because `Expr` is an interface in the `ir.v2` package and `AssignableVar` is in `dsl.v2`. The `Expr` interface is non-sealed, so technically implementable cross-package, but it would pollute the IR type hierarchy with a DSL type.

**Option B (recommended): AssignableVar is an Expr wrapper class with all operator extensions** — Keep `AssignableVar` as a DSL-layer type, but make all operator functions from `ExprBuilder.kt` available on it by delegating through `toExpr()`:

```kotlin
// AssignableVar gains all Expr operators by delegation
operator fun AssignableVar.plus(other: AssignableVar): Expr = this.toExpr() + other.toExpr()
operator fun AssignableVar.plus(other: Expr): Expr = this.toExpr() + other
operator fun AssignableVar.plus(other: Int): Expr = this.toExpr() + other
infix fun AssignableVar.isAbove(other: Int): Expr = this.toExpr() isAbove other
infix fun AssignableVar.isAbove(other: AssignableVar): Expr = this.toExpr() isAbove other.toExpr()
// ... all comparison operators
```

And the assignment-recording methods:

```kotlin
infix fun AssignableVar.set(value: Expr) {
    ScriptBuilderContext.current?.assign(name, value)
        ?: error("set() called outside a ScriptBuilder block")
}
infix fun AssignableVar.set(value: Int) = set(Literal(value))
infix fun AssignableVar.set(value: AssignableVar) = set(value.toExpr())

operator fun AssignableVar.plusAssign(value: Expr) {
    ScriptBuilderContext.current?.assign(name, value, AssignOp.ADD)
        ?: error("+= called outside a ScriptBuilder block")
}
operator fun AssignableVar.plusAssign(value: Int) = plusAssign(Literal(value))
// ... minusAssign, timesAssign, divAssign, remAssign
```

This keeps `AssignableVar` in the DSL package as a pure DSL concept, with IR conversion happening via `toExpr()`.

### Pattern 3: ActorPropertyRef for Typed Actor Properties

`ActorRef` gets typed property accessors that return `ActorPropertyRef`:

```kotlin
// In ActorBuilder.kt (expanded)
data class ActorRef(val id: String) {
    val x: ActorPropertyRef get() = ActorPropertyRef(id, "x")
    val y: ActorPropertyRef get() = ActorPropertyRef(id, "y")
    val visible: ActorBoolPropertyRef get() = ActorBoolPropertyRef(id, "visible")
}

class ActorPropertyRef(val objectId: String, val property: String) {
    fun toExpr(): Expr = PropertyAccessExpr(objectId, property)  // → emits _ball_x in C
    val name: String get() = "$objectId.$property"               // → "ball.x" as assign target
}

// Operator extensions on ActorPropertyRef (same pattern as AssignableVar):
infix fun ActorPropertyRef.set(value: Expr) {
    ScriptBuilderContext.current?.assign(name, value)
        ?: error("set() called outside a ScriptBuilder block")
}
infix fun ActorPropertyRef.set(value: Int) = set(Literal(value))

operator fun ActorPropertyRef.plusAssign(value: Expr) {
    ScriptBuilderContext.current?.assign(name, value, AssignOp.ADD)
}
operator fun ActorPropertyRef.plusAssign(value: Int) = plusAssign(Literal(value))
// ... minus, times, div

// Arithmetic as Expr:
operator fun ActorPropertyRef.plus(other: Expr): Expr = this.toExpr() + other
operator fun ActorPropertyRef.plus(other: Int): Expr = this.toExpr() + other
operator fun ActorPropertyRef.plus(other: AssignableVar): Expr = this.toExpr() + other.toExpr()
infix fun ActorPropertyRef.isAbove(other: Int): Expr = this.toExpr() isAbove other
// ... all comparison infix functions
```

The IR for `ball.x += ballDx` becomes:
```
Assign(target="ball.x", value=VarRef("ballDx"), op=AssignOp.ADD)
```
The `ExprVisitor` already handles this correctly — it sanitizes "ball.x" to "_ball_x" in the C output.

### Pattern 4: Int Left-Side Extension Functions

For `5 + score` to work, `Int` needs extension functions that return `Expr`:

```kotlin
// In ExprBuilder.kt — left-side Int extensions
operator fun Int.plus(other: Expr): Expr = BinaryExpr(Literal(this), BinaryOp.ADD, other)
operator fun Int.plus(other: AssignableVar): Expr = BinaryExpr(Literal(this), BinaryOp.ADD, other.toExpr())
operator fun Int.minus(other: Expr): Expr = BinaryExpr(Literal(this), BinaryOp.SUB, other)
operator fun Int.times(other: Expr): Expr = BinaryExpr(Literal(this), BinaryOp.MUL, other)
// ... div, rem
```

**Kotlin collision concern:** Kotlin's stdlib already defines `Int.plus(Int)`, `Int.plus(Long)`, etc. Adding `Int.plus(Expr)` in a DSL-scoped file is fine — it only resolves when `Expr` is the right-side type, which is unambiguous.

### Pattern 5: Array Name Inference

The current `u8Array("bricks", 30)` requires an explicit name string. With delegate-based name inference:

```kotlin
class ArrayDelegate(
    private val elementType: VarType,
    private val size: Int,
    private val nameOverride: String? = null,  // optional explicit name
) : ReadWriteProperty<Any?, ArrayVar> {
    operator fun provideDelegate(thisRef: Any?, property: KProperty<*>): ReadWriteProperty<Any?, ArrayVar> {
        val name = nameOverride ?: property.name
        GameBuilderContext.current?.registerArray(ArrayDef(name, elementType, size))
        return BoundArrayDelegate(name, elementType, size)
    }
}

fun u8Array(size: Int, name: String? = null) = ArrayDelegate(VarType.U8, size, name)
```

The `ArrayVar` (returned value type) supports bracket syntax:

```kotlin
class ArrayVar(val name: String, val elementType: VarType, val size: Int) {
    operator fun get(index: AssignableVar): Expr = ArrayAccessExpr(name, index.toExpr())
    operator fun get(index: Expr): Expr = ArrayAccessExpr(name, index)
    operator fun get(index: Int): Expr = ArrayAccessExpr(name, Literal(index))

    operator fun set(index: AssignableVar, value: Expr) {
        ScriptBuilderContext.current?.arrayAssign(name, index.toExpr(), value)
    }
    operator fun set(index: AssignableVar, value: Int) = set(index, Literal(value))
    operator fun set(index: Expr, value: Expr) { ScriptBuilderContext.current?.arrayAssign(name, index, value) }
    // ... Int index variants
}
```

### Pattern 6: SceneBuilder Context Propagation

`SceneBuilder.enter {}`, `frame {}`, `exit {}` blocks create new `ScriptBuilder` instances. They must also set the `ScriptBuilderContext`:

```kotlin
// Current SceneBuilder — needs ScriptBuilderContext.with() wrapping
fun enter(block: ScriptBuilder.() -> Unit) {
    val builder = ScriptBuilder()
    ScriptBuilderContext.with(builder) { builder.block() }  // ← add this
    enterOps = builder.build()
}
```

This same change is needed for `whenever()`, `ifOp()`, `whileOp()`, `forOp()`, and `elseOp()` in `ScriptBuilder` itself (they create nested `ScriptBuilder` instances).

### Anti-Patterns to Avoid

- **Making AssignableVar implement Expr directly**: Pollutes the IR type hierarchy with a DSL type. Keep the IR/DSL boundary clean.
- **Static thread-local in ScriptBuilder itself**: Creates circular dependency. A separate `ScriptBuilderContext` object (like `GameBuilderContext`) is the clean solution.
- **Overloading Kotlin standard operators on base types globally**: Extension functions on `Int` must be limited to the `dsl.v2` package. The wildcard import `import io.github.gbkt.core.dsl.v2.*` already required for operator functions (documented in STATE.md) handles this correctly.
- **Changing `assign()`/`varRef()`/`literal()` visibility in ScriptBuilder before example games compile**: Migrate examples first, then make them internal. Don't break the compile mid-migration.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead |
|---------|-------------|-------------|
| Thread-local active builder tracking | Custom synchronization | `ThreadLocal<T>` — already used in `GameBuilderContext` |
| Property name capture | Reflection-based lookup | `KProperty.name` in `provideDelegate` — already used in `VarDelegate` |
| Operator-to-AssignOp mapping | Custom enum dispatch | `AssignOp` enum already in IR (`SET`, `ADD`, `SUB`, `MUL`, `DIV`, `MOD`) |
| Actor property C naming | Custom name sanitizer | `ExprVisitor.sanitizeVarName("ball.x")` already produces `_ball_x` |
| Left-side literal wrapping | Parser magic | Extension functions on `Int` returning `Expr` |

## Common Pitfalls

### Pitfall 1: Nested ScriptBuilder Blocks Must Each Set Context

**What goes wrong:** A `whenever()` inside `frame {}` creates a new inner `ScriptBuilder`. If only `frame {}` sets `ScriptBuilderContext`, then inside `whenever {}`, `ScriptBuilderContext.current` refers to the outer builder — ops get recorded in the wrong builder.

**Why it happens:** Each `whenever`/`ifOp`/`whileOp`/`forOp`/`elseOp` call creates a fresh `ScriptBuilder` and executes the body block in it. The context must be swapped to the inner builder before executing the body.

**How to avoid:** Every method in `ScriptBuilder` that accepts a `block: ScriptBuilder.() -> Unit` must wrap the block execution with `ScriptBuilderContext.with(bodyBuilder) { bodyBuilder.block() }`. This includes `whenever`, `ifOp`, `elseOp`, `whileOp`, `forOp`, and `fade`.

**Warning signs:** Ops appearing in the wrong scene lifecycle handler, or `set()` calls silently failing (if using `?.` null-safe access instead of `!!`).

### Pitfall 2: AssignableVar Cannot Implement Expr Without IR Pollution

**What goes wrong:** Making `AssignableVar : Expr` is tempting (then all existing `Expr` extensions work directly). But `Expr` is in `io.github.gbkt.core.ir.v2` — the IR package. A DSL-layer type implementing it crosses the DSL/IR boundary.

**Why it matters:** The backend (`ScriptOpVisitor`, `ExprVisitor`) does `when (expr) { is VarRef -> ..., is Literal -> ..., ... }` — not sealed, but the visitor pattern assumes only "IR types" implement `Expr`. A DSL wrapper would never appear in IR (it should be converted to `VarRef` first), but the risk of accidental leakage into IR is high.

**How to avoid:** Keep `AssignableVar` as a DSL-layer type with a `toExpr(): VarRef` method. Add all operators as extension functions that call `toExpr()`. The tradeoff is more boilerplate extension functions, but clean separation.

### Pitfall 3: `set` as an Infix Function vs Operator Assignment

**What goes wrong:** `score = literal(0)` looks natural but won't work — Kotlin won't accept `AssignableVar = Expr` because `setValue` on the delegate is a no-op (by design, since delegates live at game scope, not script scope).

**The correct syntax:** `score set 0` (infix) or via operator overload implicitly through the `set()` method. The `set` infix naming matches v1 DSL (`score set 0` is the v1 pattern from `AssignableExpr`).

**Warning signs:** Developers writing `score = 0` expecting it to emit a script assign op. The Kotlin compiler will compile it (calling the delegate's `setValue()`), but nothing will happen at game-logic level.

**How to avoid:** Document clearly in KDoc that `set` is the assignment operator. Consider making the delegate `setValue` throw an error with a helpful message pointing to `set`.

### Pitfall 4: Actor Property Name Must Match C Variable Convention

**What goes wrong:** `ball.x` in DSL maps to `ball.x` as the `Assign` target string. The `ScriptOpVisitor.visitAssign()` sanitizes this via `ExprVisitor.sanitizeVarName("ball.x")` → `_ball_x`. But the `ActorVisitor` declares `CVarDecl("_ball_x", CU8, ...)`. Both must agree on the naming.

**Verified:** The current pipeline already handles `assign("ball.x", ...)` correctly via `sanitizeVarName`. The `ActorPropertyRef.name` returning `"$objectId.$property"` (e.g., `"ball.x"`) will produce the same C output as the current `assign("ball.x", ...)` calls.

**Warning signs:** C compilation errors like `undefined identifier '_ball_x'` or duplicate declarations.

### Pitfall 5: `u8Array` Name Override Breaks Existing Tests

**What goes wrong:** Changing `u8Array("bricks", 30)` signature to `u8Array(30)` will break existing uses that pass the name explicitly. The `ArrayDef.name` in the IR must still match the name used in `arrayAssign`/`arrayRef` calls.

**How to avoid:** Keep backward compatibility by accepting an optional name override. The `property.name` is used when no override is provided. For Breakout's `val bricks by u8Array("bricks", 30)` → after migration: `val bricks by u8Array(30)` where name is inferred as "bricks".

### Pitfall 6: ScriptBuilderContext Must Be Set in SceneBuilder Too

**What goes wrong:** The `SceneBuilder.enter {}` block is not itself a `ScriptBuilder` lambda — it creates a `ScriptBuilder` internally. If `SceneBuilder.enter` doesn't set `ScriptBuilderContext`, then any `AssignableVar.set()` calls at the top of `enter {}` won't find an active builder.

**How to avoid:** `SceneBuilder.enter`, `frame`, and `exit` must all set `ScriptBuilderContext.with(builder) { builder.block() }`.

## Code Examples

### Before/After: Pong Game Scene (Illustrative)

```kotlin
// BEFORE (current assembly-style v2)
scene("game") {
    enter {
        assign("ballDx", literal(1))
        assign("ball.x", literal(80))
    }
    frame {
        assign("ball.x", varRef("ball.x") + varRef("ballDx"))
        whenever(varRef("ball.y") isBelow literal(16)) {
            assign("ballDy", literal(1))
        }
        whenever(varRef("p1Score") isAtLeast literal(5)) { navigate("gameover") }
    }
}

// AFTER (target Kotlin-idiomatic v2)
scene("game") {
    enter {
        ballDx set 1
        ball.x set 80
    }
    frame {
        ball.x += ballDx
        whenever(ball.y isBelow 16) {
            ballDy set 1
        }
        whenever(p1Score isAtLeast 5) { navigate("gameover") }
    }
}
```

### Before/After: Array Operations (Breakout)

// BEFORE

## Migration Strategy

The CONTEXT.md specifies "old syntax removed from public API." The safest migration order:

1. **Add new ergonomic layer** (new files, new extensions) without removing old API.
2. **Migrate all three example games** to new syntax — they should compile and produce identical C output.
3. **Deprecate then internalize** `assign()`, `varRef()`, `literal()`, `arrayAssign()`, `arrayRef()` in `ScriptBuilder`.
4. **Run all tests** — backend tests use IR directly and are unaffected. Any DSL tests that use old syntax will need updating.
5. **Remove `@Suppress("UNUSED_VARIABLE")`** from variable declarations (they're used now via their delegate values).

The `@Suppress("UNUSED_VARIABLE")` suppression in example games is a strong signal: Kotlin's compiler sees `var score by u8Var(0)` as unused because `score` (the `AssignableVar`) is never read — instead `varRef("score")` is used as a magic string. Once `score` is used directly in `score += 1`, the suppression is no longer needed.

## Open Questions

1. **`forOp` loop variable as delegate or string?**
   - Current: `forOp("bi", literal(0), literal(29)) { ... }` — string name, literal bounds
   - Target options: `forOp(bi, 0, 29) { ... }` where `bi` is declared as `var bi by u8Var(0)` first, OR `for (bi in 0..29) { ... }` (not possible, since Kotlin `for` range iteration isn't interceptable as IR recording)
   - Recommendation: Keep `forOp` as a ScriptBuilder method with either a string or an `AssignableVar` parameter for the loop variable. The loop variable name just needs to be a valid C identifier. The Kotlin `for` keyword cannot be overridden.
   - The Int overloads for bounds already handle `literal()` removal: `forOp("bi", 0, 29) { ... }`.

2. **`BinaryOp.SHR` in Breakout — should it use `shr` infix?**
   - Current Breakout uses `BinaryExpr(varRef("ball.x") - literal(40), BinaryOp.SHR, literal(3))` directly (a manual IR construct leaking into game code).
   - Target: `(ball.x - 40) shr 3` — the `shr` infix already exists on `Expr`.
   - Once `ball.x` returns `ActorPropertyRef` with `minus(Int): Expr`, then `(ball.x - 40) shr 3` works naturally.
   - This is a case where `BinaryExpr`/`BinaryOp` are public IR types leaking into game code — they should not be needed after this phase.

3. **`raw()` compile-time warning — how exactly?**
   - Options: `@Deprecated("raw() is an escape hatch. Consider adding DSL support instead.", level = DeprecationLevel.WARNING)` on the `raw()` method in `ScriptBuilder`.
   - Kotlin `@Deprecated` with `DeprecationLevel.WARNING` causes yellow underline in IntelliJ and a compile-time warning (not error). This is exactly the right behavior.
   - Claude's discretion per CONTEXT.md.

4. **`setPosition(ball.id, 80, 72)` → `ball.moveTo(80, 72)` or `ball.position set (80, 72)`?**
   - CONTEXT.md locks: "Both mutation AND methods: `ball.x += 2` for quick mutations, `ball.moveTo(80, 72)` for semantic operations"
   - `ActorRef.moveTo(x: Int, y: Int)` emitting `SetPosition` is straightforward.
   - Implementation: `fun ActorRef.moveTo(x: Int, y: Int) { ScriptBuilderContext.current?.setPosition(id, x, y) }`
