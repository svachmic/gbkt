# Phase 12.1: Code Review Report — Defect 6 Gap-Closure (Plans 11/12/13/14)

**Reviewed:** 2026-05-22T17:00:00Z
**Depth:** standard
**Files Reviewed:** 2

## Summary

Reviewed the Plan 12.1-11..14 gap-closure changes against the documented contract
(`option c-prime` literal-bank substitution). The production change in
`buildSetupCurrentLevelFunctionIfNeeded` is structurally correct and the new JVM
emission-invariant tests lock the new shape adequately. However, several issues
warrant attention:

- The fallback bank value (`?: 1`) is documented as "safe HOME-adjacent" but bank 1
  is reserved for SCENE CODE (`bank1.c`), not data; if the fallback ever fires at
  runtime the `is_tile_solid` / `_bkg_set_level_submap_banked` helpers will read
  scene code bytes as tilemap collision data, producing nonsense (not a crash, but
  not "safe" either). The fallback is defensive against a "shouldn't happen" map
  miss, but the comment overstates safety.
- The sibling test (`setupCurrentLevel helper function definition is emitted at
  column 0 of main_c`) was NOT updated to reflect the new emission shape — its
  comments and the contract-claim it documents still reference the retired
  `_current_area_bank = BANK(_zone_<id>_tilemap)` shape. Future maintainers will
  see contradictory documentation in the same test file.
- A latent issue (NOT introduced by this gap-closure but surfaced by the
  changed code path): the per-case `threshold` STUB hardcodes `17` and reads ONLY
  `zone.platformerPhysicsOverride[solidThreshold]`, never falling back to the
  game-level `platformer_physics` system threshold; this is documented as
  Plan 12-18 territory, but the per-game `platformerPhysics { solidThreshold(N) }`
  config is silently ignored by the per-case emit.

No CRITICAL findings — the changed code does not introduce data loss, security
risk, or a guaranteed runtime crash. The fallback bank-1 issue would only fire
on an invariant-broken bankAllocation map, which the upstream allocator
(`allocateZoneBanks`) never produces for in-game zones.

## Warnings

### WR-01: Fallback bank `1u` is NOT safe — bank 1 holds scene code, not data

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:2313-2315`

**Issue:** The `?: 1` fallback labels bank 1 as "safe HOME-adjacent" in both the
production comment and the test docstring (LevelSwitchEmissionTest.kt:527-534).
This is misleading. Bank 1 is documented as reserved for SCENE CODE (`bank1.c`)
at multiple places in the same file:
- Line 144: `Bank 1: bank1.c — scene lifecycle functions (all BANKED)`
- Line 605: `Bank 0 (HOME) and bank 1 (scenes) are reserved and never used for tilemap data.`
- Line 615: `val tilemapBankStart = 2 // Banks 0 (HOME) and 1 (scenes) are reserved`

If `_current_area_bank = 1u` ever fires at runtime, the helpers `is_tile_solid`
(line 2160) and `_bkg_set_level_submap_banked` (line 2215) will `SWITCH_ROM(1)`
and read scene-code bytes as tilemap data. The behavior is not a crash (bank 1
is always physically present, no page fault) but it is also NOT "safe" — the
collision verdict and submap copy will operate on whatever opcodes/data happen
to live at the bank-1 byte offsets. That is a silent correctness bug, not a
defensive fallback.

The fallback is structurally observable (the inline `/* fallback: ... */` C
comment + the Plan 12.1-11 SUMMARY docs), so a developer inspecting the
generated C would notice. But a runtime probe (MCP / UAT) reading garbage
collisions would chase a phantom physics bug.

**Fix:**

Option A — change the fallback to `0u` (HOME bank) and document explicitly that
this routes reads to main.c's HOME data, with the same `garbage but not
crashing` semantics — but with the upside that HOME data is mostly DSL-author
controlled globals (rather than codegen-emitted scene jumptables), so a debug
session has a fighting chance:

```kotlin
val bank = bankAllocation[zone.id] ?: 0  // HOME bank — reads return globals data, observable in symbol map
val bankFallbackComment = if (bankAllocation[zone.id] == null) {
    " /* fallback: bankAllocation missing zoneId; routes is_tile_solid to HOME (garbage but observable in .sym) */"
} else { "" }
```

Option B — make the fallback fatal by throwing at codegen time, since a missing
zone id in `bankAllocation` indicates a pipeline-orchestration bug:

```kotlin
val bank = bankAllocation[zone.id]
    ?: error("bankAllocation map missing entry for zone '${zone.id}' — pipeline-orchestration bug")
```

Option B is preferable per CLAUDE.md §"Quality over shortcuts" memory:
the `?: 1` silently masks a pipeline contract violation, while a hard fail
surfaces the violation at the earliest possible point (JVM-tier codegen
exception). Option A keeps the defensive philosophy but corrects the misleading
"safe HOME-adjacent" claim.

If the team prefers to keep the defensive `?: 1` shape (e.g., because emission
must never fail for any reason in mid-build), at minimum update the inline
comment to remove the "safe" claim:

```kotlin
" /* fallback: bankAllocation missing zoneId; bank-1 routes to scene code — collision verdicts will be garbage */"
```

### WR-03: Per-case `threshold` STUB silently ignores game-level platformer_physics solidThreshold

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:2319-2324`

**Issue:** The per-case body computes `threshold` as:

```kotlin
val threshold = (zone.platformerPhysicsOverride?.get("solidThreshold") as? Int) ?: 17
```

This reads ONLY from the per-zone override. If the DSL author wrote
`platformerPhysics { solidThreshold(42) }` at the GAME level (NOT per-zone), the
emission still hardcodes `17u` for every case body. The fixture
`buildTilemapCollisionGameDsl` in the test file calls
`platformerPhysics { solidThreshold(17) }` precisely because that's what the
hardcoded STUB returns — so the test would PASS even if a future DSL author set
`solidThreshold(42)` and reasonably expected `_current_level_non_solid_tile_count = 42u`
in the emission.

The inline comment at line 2319-2322 acknowledges this is a STUB:

```kotlin
// Per-zone solidThreshold override falls back to game-level (handled by Plan 12-07).
// For the Plan 12-17 STUB shape we emit a placeholder threshold of 17 (matches
// PlatformerTemplate.kt's game-level default); Plan 12-18 will source the threshold
// from `zone.platformerPhysicsOverride["solidThreshold"]` falling back to game-level.
```

But the comment promises Plan 12-18 will fix this — and yet Plan 12-18 has
shipped (Phase 12 is "completed" per the recent commits; Phase 12.1 just closed
Defect 6 within Phase 12.1). If the deferral is still valid for Phase 12.1's
scope (gap-closure for Defect 6 only), at minimum the comment should be
updated to reflect the actual deferral target (a future phase, or "out of scope
for Phase 12.1 — tracked separately").

This is NOT a regression introduced by Plans 11-14, but the Defect 6 fix
TOUCHES this code path — the literal-bank substitution sits 5 lines above the
threshold STUB. A reviewer auditing the diff would see the STUB and reasonably
ask whether the Defect 6 closure scope included it.

**Fix:** Either (a) extend the threshold lookup to fall back to the game-level
platformer_physics system config, OR (b) update the deferral comment to
identify the actual future-phase target:

```kotlin
// Option (a) — full fallback chain
val threshold = (zone.platformerPhysicsOverride?.get("solidThreshold") as? Int)
    ?: gameIR.systems.filterIsInstance<GenericSystem>()
        .firstOrNull { (it.config["type"] as? String) == "platformer_physics" }
        ?.let { sys ->
            val physicsConfig = sys.config["physicsConfig"] ?: return@let null
            try {
                val field = physicsConfig.javaClass.getDeclaredField("solidThreshold")
                field.isAccessible = true
                field.get(physicsConfig) as? Int
            } catch (_: Exception) { null }
        }
    ?: 17

// Option (b) — update comment only (lowest-risk, preserves Plan 12.1-11 scope)
// Per-zone solidThreshold override falls back to game-level (DEFERRED — see
// 12.1-VERIFICATION.md §"Future Work" for the planned phase that wires this).
// For the current Phase 12.1 scope we emit a placeholder threshold of 17 ...
```

### WR-04: Redundant `bankAllocation[zone.id]` map lookup

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:2313-2318`

**Issue:** The map lookup happens twice — once for the value, once for the
null-check that drives the fallback comment:

```kotlin
val bank = bankAllocation[zone.id] ?: 1
val bankFallbackComment = if (bankAllocation[zone.id] == null) {
    " /* fallback: bankAllocation missing zoneId; safe HOME-adjacent */"
} else {
    ""
}
```

This pattern is fragile against `Map<String, Int?>` (if the type ever widens
to allow null values), because the `?: 1` would treat a stored-null as "not
present" while the `== null` check would treat it as "present-with-null" — two
slightly different semantics from the same map. The current
`Map<String, Int>` type guarantees no null values so the discrepancy doesn't
fire today, but the pattern duplicates intent.

The double lookup is not a real performance issue (HashMap lookup is O(1)) but
the code reads as if the author wanted to avoid recomputation.

**Fix:** Hoist the lookup to a single binding, then derive both values from it:

```kotlin
val allocatedBank: Int? = bankAllocation[zone.id]
val bank = allocatedBank ?: 1
val bankFallbackComment = if (allocatedBank == null) {
    " /* fallback: bankAllocation missing zoneId; safe HOME-adjacent */"
} else {
    ""
}
```

### IN-01: Fixture-tied bank-2 assertion masks fixture fragility

**File:** `gbkt-backend-gbdk/src/test/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/LevelSwitchEmissionTest.kt:499-506`

**Issue:** The positive test asserts `helperBody.contains("_current_area_bank = 2u;")`.
The reasoning in the comment claims the fixture's two gameplay zones have
"~1024 tilemap bytes each" so the bin-packer packs both into bank 2. But the
fixture's PNG paths (`res/graphics/level1.png`, `res/graphics/level2.png`)
likely do NOT exist as actual resources — `zoneTileDataSize` (kt:592) returns
1 for empty tileData. So all 4 zones (titleZone, gameplayZone1, gameplayZone2,
nextLevelZone) are size 1 each, and the bin-packer trivially packs all 4 into
bank 2.

This means the comment's calculation (`2 × 1024 << 16384 cap`) is technically
wrong — it's actually `4 × 1 << 16384 cap`. The test still passes, but for the
wrong reason. A reviewer who reads the comment and trusts it would have a
mistaken mental model of why the assertion holds.

**Fix:** Either (a) load actual PNG bytes in the fixture so the comment is
true, or (b) update the comment to reflect that empty-tileData zones default to
size 1 and the bin-packer trivially packs them:

```kotlin
// Both gameplay zones in the fixture have empty tileData (PNG paths are
// placeholders that resolve to size 1 via zoneTileDataSize fallback at
// kt:592-593). The bin-packer therefore packs all 4 zones into bank 2
// (4 × 1 << 16384 cap). If the packer changed (e.g., spread one per bank),
// this assertion would catch the upstream-allocation drift before it ships.
```

### IN-03: Counter regex pattern uses non-default `count()` instead of `findAll().count()` consistency

**File:** `gbkt-backend-gbdk/src/test/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/LevelSwitchEmissionTest.kt:470`

**Issue:** The new test counts literal-bank assignments via:

```kotlin
val literalBankAssignments = Regex("_current_area_bank = \\d+u;").findAll(helperBody).count()
```

Stylistically, the sibling test at line 400 uses:

```kotlin
val caseCount = "case ".toRegex().findAll(helperBody).count()
```

The two patterns differ trivially (`Regex(...)` vs `"...".toRegex()`). Either
is fine; consistency would slightly improve readability.

**Fix:** Use the sibling test's `"...".toRegex()` form for consistency:

```kotlin
val literalBankAssignments = "_current_area_bank = \\d+u;".toRegex().findAll(helperBody).count()
```
