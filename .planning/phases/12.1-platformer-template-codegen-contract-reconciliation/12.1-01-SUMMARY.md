### Bank numbers assigned to each platformer-template zone

From `gbkt-examples/platformer-template/build/gbkt/generated/game_metadata.json`:

| Zone | tilesetPath | bank |
| --- | --- | --- |
| world1Area1Zone | graphics/world1-tileset.png | 2 |
| world1Area2Zone | graphics/world1-tileset.png | 2 |
| world2Area1Zone | graphics/world2-tileset.png | 2 |
| titleZone | graphics/title-screen.png | 2 |
| nextLevelZone | graphics/next-level.png | 2 |

All 5 zones receive bank 2 because each zone's tileData is small (FFD bin-packer fits them all into the first available tilemap bank). This is correct behavior — the FFD allocation strategy minimizes ROM-bank usage by packing zones until a bank is full, then opens the next bank. With the platformer-template's modest data sizes, one bank suffices.

### `__bank__zone_*_tilemap` error count before/after

Before this plan (per `.planning/phases/12-port-platformer-template-gbdk-example-to-gbkt/evidence/first-buildrom.md` Defect 2): 3 zones reporting `error 20: Undefined identifier '__bank__zone_<id>_tilemap'` (world1Area1Zone, world1Area2Zone, world2Area1Zone — title + nextLevel zones not reached by `setup_current_level()`).

After this plan: **3 errors STILL appear during `:compileRom`**, but their root cause is now CHAINED downstream:

- The synthesized `_zone_<id>_tilemap.c` files DO carry `#pragma bank N`, so SDCC IS able to synthesize the `__bank__zone_<id>_tilemap` companion symbol at .c compile time.
- However, `main.c` does not `#include "_zone_<id>_tileset.h"` (where the `extern const uint8_t _zone_<id>_tilemap[...]` lives). So SDCC compiling `main.c` cannot parse `BANK(_zone_<id>_tilemap)` because the underlying variable is unknown — SDCC reports both `_zone_<id>_tilemap` AND `__bank__zone_<id>_tilemap` as undefined identifiers at parse time.
- The header-visibility half belongs to Plan 12.1-03 (see plan boundary: "Do NOT alter `synthesizeHeader` (that owns tileset.h, addressed by Plan 12.1-03)").

**Pragma-emission half of Defect 2 is now in place.** Plan 12.1-03 will resolve the header visibility, which together with this plan's pragma emission will make `__bank__zone_<id>_tilemap` fully link-resolvable.

### Option-b confirmation (per RESEARCH §Risks #3)

`allocateZoneBanks(gameIR)` is called inside `buildMetadataFile`, side-effect-free (option b in 12.1-CONTEXT.md). `generate()` was NOT restructured (option a). The allocation map is computed once at the top of the zoneTilesets-building loop and consumed per-zone; the legacy `buildTilemapBankFiles` call site (inside `buildCFiles`) continues to receive a separate allocation from its own `allocateZoneBanks(gameIR)` call (idempotent — both produce identical maps).

## Decisions Made

- **D-01 option (b) over option (a):** Picked Gradle-task-emits-pragma (b) over codegen-restructure (a) per CONTEXT.md decision. Preserves existing pipeline shape; new code is strictly additive.
- **`allocateZoneBanks` called inside `buildMetadataFile`** (not threaded as a parameter): keeps the existing call-site contract of `buildMetadataFile(gameIR)` and avoids touching the `generate()` orchestration layer. The function is documented side-effect-free, so the duplicate call (also invoked inside `buildCFiles` for the legacy path) is idempotent and cheap.
- **Updated pre-existing test fixtures rather than introducing a sibling fixture set:** parallel to Plan 11.1-17's strategy when it added `mapWidth`/`mapHeight`. Minimizes test-file proliferation; new fixtures live in dedicated `*PragmaBankTest.kt` / `*BankFieldTest.kt` files for the new contract.
