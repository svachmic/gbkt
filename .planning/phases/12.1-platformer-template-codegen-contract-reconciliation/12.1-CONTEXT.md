## Implementation Decisions

### Defect 2 — BANK() macro path

- **D-01: Lock option (b) — `#pragma bank N` on tilemap arrays via
  `ConvertZoneTilesetsTask`.** The task emits `#pragma bank N` at the top of
  each `_zone_<id>_tilemap.c`; `BankingAnalysisPass` picks N; SDCC synthesizes
  `__bank_<sym>` natively; `BANK(_zone_<id>_tilemap)` resolves at link time
  without further intervention.
  - **Rejected (a) literal `1u` substitution:** locks tilemap data into HOME
    bank forever; HOME is ~16 KB shared with main loop + scene dispatch + all
    helpers; Phase 12 has 5 zone tilemaps and risks blowing the 16 KB-per-bank
    cap (Phase 11 D-15) the phase exists to verify. Also makes the existing
    `SWITCH_ROM(_current_area_bank)` machinery vestigial (always switches to
    bank 1 = no-op). Vestigial code is a smell.
  - **Rejected (c) explicit `_zone_<id>_tilemap_BANK #define`:** parallel
    symbol convention competing with SDCC's native `__bank_<sym>`. Redundant
    when (b) does the job.
  - **Composition:** activates the existing Plan 07.4-30 HOME-bank
    SWITCH_ROM wrapper for its intended purpose (cross-bank tilemap access).
    Matches the established dungeon-zone pattern (`zone_bank2.c` with
    bank-2 tilemap arrays).
  - **Regression test surface:** Requirement 5 — the 5 existing example
    ROMs continue to build GREEN. BankingAnalysisPass either finds a bank
    for the existing examples' tilemaps (silent success) or fails loud
    (caught immediately, not a silent regression).

### Defect 3 — Tilemap WIDTH / HEIGHT symbol source

- **D-02: Lock option (a) — `#define _zone_<id>_tilemap_WIDTH/_HEIGHT` in
  `_zone_<id>_tileset.h` via `ConvertZoneTilesetsTask`.** Same task as D-01;
  PNG dimensions are known at conversion time (the task already validates
  multiples of 8 — `gbkt-gradle-plugin/.../ConvertZoneTilesetsTaskTest.kt`
  "fails fast when PNG dimensions not multiple of 8" test).
  - **Rejected (b) literal substitution from `game_metadata.json`:** creates
    a metadata→codegen data-flow loop. `game_metadata.json` is currently
    pipeline OUTPUT, not input; routing metadata back into `GBDKPipelineV2`
    introduces a new ordering constraint. (a) keeps the symbol contract
    symbolic and debuggable — a developer inspecting tileset.h sees
    `#define _zone_world1Area1Zone_tilemap_WIDTH 32` with full provenance.
  - **Composition with D-01:** symmetric with the `#pragma bank` emission —
    both defects scoped to ConvertZoneTilesetsTask, both produced into the
    tileset.h / tilemap.c headers, both verified by the same emission test
    plan (test pair after the fix pair).

### Defects 4 + 5 — Player position symbol convention (COUPLED)

- **D-03: Lock option (ii) — user-declared `playerX` / `playerY` i16Vars +
  metasprite `pos(playerX, playerY)` binding + PlatformerVisitor rewrite to
  use the user's property names.** The cleanest reconciliation of the
  Defect-4 physics-update symbol convention with the Defect-5 metasprite
  render symbol convention is to give the user a single declaration site:
  ```kotlin
  var playerX by i16Var(80 shl 4)    // sub-pixel: pixel * 16
  var playerY by i16Var(72 shl 4)

  val player by metasprite {
      // existing 6-frame + hflip declaration (D-04 from Phase 12 CONTEXT)
      // unchanged; ADD:
      pos(playerX, playerY)            // binds posXVar/posYVar on MetaspriteIR
      idx(walkFrameIdx)                // already wired in Plan 12-17
      rot(facingRot)                   // already wired
  }
  ```
  `MetaspriteVisitor` already reads `posXVar` / `posYVar` from `MetaspriteIR`
  (set via `pos(varRef)` at `MetaspriteBuilder.kt:140-145`) and emits
  `_<varName>` instead of the magic `_posX` / `_posY` fallback. The magic
  fallback remains as a back-compat path for unbound metasprites (Phase 10).
  `PlatformerVisitor.buildTilemapPhysicsUpdateFunction` rewrites every
  `_player_x` / `_player_y` reference to `_playerX` / `_playerY` (and every
  `_player_vx` / `_player_vy` / `_grounded` to `_playerVx` / `_playerVy` /
  `_grounded` — TBD per D-claude-1).

  - **Rejected (i) `val player by actor { position(); hitbox() }`:** matches
    Phase 12 D-12b's "hitbox-driven probe" intent but requires verifying
    that an actor + a standalone metasprite descriptor coexist on the same
    logical entity, which is unverified composition. Actor uses sprite slot;
    metasprite uses descriptor render; the two paths don't naturally
    converge. Would force additional codegen wiring (actor's metasprite
    slot, or actor symbols read by MetaspriteVisitor) that isn't required
    by option (ii).
  - **Rejected (iii) pipeline-emitted `_plat_x` / `_plat_y` globals:** hides
    player position from user DSL — user can't write `playerX set 80` from
    a scene script. Forces magic binding from metasprite to pipeline
    globals. Violates the declarative-over-imperative principle and the
    `feedback_no_magic_strings.md` rule (player-position symbols would be
    derived from internal naming, not from a user property delegate).
  - **Composition:** the 5-point bounding-box probe (Phase 12 D-12b)
    becomes explicit configuration on `tilemapCollision`:
    ```kotlin
    tilemapCollision {
        position(playerX, playerY)   // explicit position-var binding
        hitbox(0, 0, 8, 24)            // explicit hitbox-rect
        solidThreshold(17)
    }
    ```
    More explicit than "actor.hitbox → implicit derivation"; easier to
    test; doesn't depend on actor+metasprite composition.
  - **DSL gap:** verify whether `tilemapCollision` (the per-genre builder
    introduced in Phase 12) accepts a `position(varRef, varRef)` setter
    or whether it needs to be added. Planner's task — could be the D4a
    fix plan's scope or split into a sub-task.

### Claude's Discretion

- **D-claude-1: Exact symbol naming for physics rewrite.** Decision D-03
  locks the user-DSL property names (`playerX` / `playerY`) and the
  metasprite binding. The physics-path rewrites `_player_x` →
  `_playerX` (and siblings) per the user-property naming convention. If
  research finds an existing in-pipeline symbol-mangling convention
  (e.g., camelCase preserved, underscore-prefix added), the planner
  follows the existing convention; if not, the planner picks the most
  consistent shape with existing examples and locks it in the D4a
  plan SUMMARY.md.

- **D-claude-2: Whether `tilemapCollision` builder needs a
  `position(varRef, varRef)` setter.** Research / planner check: does
  the existing builder accept position-var binding? If yes, D-03's
  PlatformerTemplate.kt change just uses it. If no, the planner adds
  the setter as part of plan 5 (D4a) — single-line builder extension
  scoped to `gbkt-genre-platformer/.../PlatformerExtensions.kt`. If the
  builder doesn't exist at all (only inferred from actor.hitbox per
  D-12b's intent), this becomes a small new builder surface — still in
  scope per the SPEC's "any minimal DSL-side change required" clause.

- **D-claude-3: Whether Defect 5 needs a code change or only a test.**
  Research check: with PlatformerTemplate.kt updated to bind
  `pos(playerX, playerY)` on the metasprite, does the existing
  `MetaspriteVisitor.lowerToMoveMetasprite` (or equivalent emit
  site) correctly propagate the binding to the lowering? If yes,
  Defect 5 is test-only (plan 9 is the only plan; plan 8 collapses).
  If no — the binding is only honored under specific DSL composition —
  plan 8 is a visitor fix to make the binding always-honored. Planner
  decides after the D4a / D4b plans complete.

- **D-claude-4: Where the `position(varRef, varRef)` setter on
  `tilemapCollision` lives architecturally.** Inside the
  `tilemapCollision` builder block (preferred — explicit per-collision
  position binding) vs on the scene's `tilemapCollision` extension
  (less explicit) vs inferred from a `with(actor)` pattern (rejected
  per D-03's rationale against actor-coupling). Planner picks; default
  is "inside the `tilemapCollision` builder block".

- **D-claude-5: Whether the JVM emission tests reuse Phase 12's
  per-function awk brace-walk helper or duplicate the pattern.** Phase
  12 D-16's invariants used awk-extracted function bodies before grep.
  If a shared helper exists in `gbkt-test` or `gbkt-backend-gbdk` test
  utilities, reuse it; otherwise inline the awk pattern per-test
  (matches Phase 12's plans). Either way, the test pattern is awk-then-grep,
  NOT file-level grep.
