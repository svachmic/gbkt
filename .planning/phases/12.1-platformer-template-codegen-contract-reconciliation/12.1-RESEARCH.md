## D-claude-4 — Architectural home for `position(varRef, varRef)` on `tilemapCollision`

**Locked:** **INSIDE the `tilemapCollision { ... }` builder block, mirroring the Option A surface from D-claude-2.**

Recommended shape:
```kotlin
tilemapCollision {
    position(playerX, playerY)   // ← inside the builder block
    hitbox(0, 0, 8, 24)
    solidThreshold(17)
}
```

**Why not on the scene's `tilemapCollision` extension?** Scene-level extensions exist for things tied to per-scene lifecycle (e.g., scene-zone-binding). Tilemap collision is GAME-LEVEL state (one player, one hitbox, one solid threshold) — it doesn't vary by scene. Putting it on a per-scene extension would invite the misconception that the threshold can vary per scene (which it can via `platformerPhysicsOverride` already — separate concern).

**Why not derive from `with(actor)` / actor-hitbox?** Rejected per D-03's rationale: actor + metasprite composition is unverified. Also PlatformerTemplate.kt currently has no actor — the auto-derivation falls back to the default `(0, 0, 8, 24)` which is the SAME as the explicit hitbox the user would write. Explicit > implicit for testability.

**File:line for the recommendation:** `gbkt-genre-platformer/src/main/kotlin/io/github/gbkt/genre/platformer/dsl/PlatformerExtensions.kt:168` (alongside the other builder extensions).

## splitByBank `#pragma bank N` handling

**Locked:** **No `splitByBank` function exists in the codebase.** The CONTEXT.md's instruction to "verify that splitByBank correctly handles #pragma bank N directives on data files" is moot — there is no such function. The actual mechanism is:

- **In-pipeline CFiles**: `CEmitter.emit(file)` writes `#pragma bank ${file.bank}` at the top of the file when `file.bank > 0` ([VERIFIED] CEmitter.kt:106-108).
- **Out-of-pipeline files** (like `_zone_<id>_tilemap.c` written by ConvertZoneTilesetsTask): the task writes the file directly to disk; D-01 must add the `#pragma bank N` directive to the task's own emission code (file:line `ConvertZoneTilesetsTask.kt:430-453`).
- **Compile-time scan**: `CompileRomTask.detectMaxBank` (line 305-320) scans ALL source files in the source set for `#pragma bank \d+` regex matches — no file is special-cased. So once the tilemap file carries the directive, it participates in MBC-level promotion automatically.

**Risk flagged:** **NONE.** Data declarations with `#pragma bank N` and an `extern` reference from HOME bank are the GBDK-canonical pattern (dungeon's `zone_bank2.c` does exactly this today). The pragma routes the file to a non-HOME bank; the SDCC linker synthesizes the `__bank_<sym>` symbol that `BANK(<sym>)` expands to; cross-bank reads from HOME use `_bkg_tiles_load_banked` which auto-handles the bank switch.

**One caveat for the planner:** when adding `#pragma bank N` to `_zone_<id>_tilemap.c`, do NOT also place the file in the `CFile` pipeline (it's not currently a `CFile`; it's a raw text file from a Gradle task). Mixing the two would double-emit the pragma and confuse `CompileRomTask`. Keep ConvertZoneTilesetsTask's emission separate.

## Risks and gotchas

1. **`_jump_increase_timer` cross-path leakage.** The rect-physics path (PlatformerVisitor.kt:149 area per CONTEXT) declares `_jump_increase_timer` as a pipeline-emitted global. The tilemap-physics path references the same symbol (broken main.c line 350). If both paths emit declarations, SDCC will report duplicate symbol; if neither path declares it under the tilemap-physics gate, link fails. Plan 6 must verify the declaration is gated appropriately OR introduce `var jumpIncreaseTimer by u8Var(0)` in PlatformerTemplate.kt (with the `_jumpIncreaseTimer` rewrite — but that breaks `_jump_increase_timer` callers in main.c). RECOMMENDATION: keep `_jump_increase_timer` exactly as emitted today; only rewrite the 4 player position/velocity symbols + `_grounded`.

2. **`_grounded` symbol naming.** The current emission uses bare `_grounded` (no namespace). User-declared `var grounded by u8Var(0)` emits `_grounded` (single underscore + property name). The two coincide — the rewrite is a no-op for this one symbol. BUT: if `_grounded` is currently pipeline-emitted (declared in `buildTilemapCollisionGlobals` or sibling), AND user adds `var grounded by u8Var(0)`, SDCC reports duplicate declaration. Plan 5 must check and either (a) drop the user-declaration if pipeline already emits it, or (b) drop the pipeline-emission. RECOMMENDATION: verify in plan 5 via `grep -n '_grounded' build/gbkt/generated/main.c` BEFORE adding `var grounded` to the DSL; if pipeline emits it, skip the DSL declaration and let the existing pipeline path stay intact.

3. **Bank-allocation timing dependency.** `buildMetadataFile` is called at line 188 of GBDKPipelineV2.generate; `allocateZoneBanks` at line 521. Reading bank assignments into metadata requires reorganizing so `allocateZoneBanks` runs FIRST or the bank map is computed on-demand inside `buildMetadataFile`. The simpler fix: compute `bankAllocation` once at the top of `generate()`, thread it into both `buildMetadataFile` and the rest. Plan 1 must restructure `generate()` slightly. Risk: this restructure touches a hot path used by every example — regression sweep in Plan 9 is the catch-net.

4. **MBC1 vs MBC5 bank-count.** PlatformerTemplate.kt declares `cartridge = "MBC1"; romBanks = 8`. MBC1 supports up to 16 banks; placing tilemaps in banks 2-3 fits. But the GBDK BANKED-call mechanism uses MBC5-style switching (per `feedback` memory entry on MBC5 calling convention). CompileRomTask's `detectMaxBank` may auto-promote MBC1 → MBC5 — verify this in plan 10's terminal smoke. If promotion doesn't fire, the player may need to switch to MBC5 explicitly.

5. **MetaspriteVisitor's bound-vs-unbound dispatch.** Per D-claude-3 the visitor handles both paths today via parameter defaults (line 237-242: `posXVar: String = "_posX"`).
