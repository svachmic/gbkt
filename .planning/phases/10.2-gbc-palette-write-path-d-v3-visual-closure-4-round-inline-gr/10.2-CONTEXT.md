## Phase Boundary

Phase 10.2 closes the **single visual defect** that Phase 10.1's 4 inline rounds couldn't close: **GBC behavior3 (sub-palette cycle) renders literal RGB(0,0,0) every pixel** despite Plan 10.1-22's codegen-shape fix (explicit `set_bkg_palette(0u, 1u, _gbkt_default_bg_pal)` + `bgFillCheckerboard` hoist into `main()` pre-`DISPLAY_ON`) landing GREEN at the JVM tier (`DV3VisualV2DiagnosticTest` 2/2, `DV3GbcPaletteWriteDiagnosticTest` 3/3).

**The critical evidence (resurrected from SEED-013):** the pre-Plan-19 ROM (commit `cbe81d29`) rendered **cyan sprite on black BG** — the sprite-palette path was demonstrably working. The post-Plan-22 ROM renders **solid black everywhere**. Therefore: **one of Plans 10.1-19/20/22 introduced a regression** that killed sprite-palette rendering that was previously working. The fix in this phase must (a) restore visible sprite-palette rendering AND (b) close the BG visibility while keeping all 5 locked codegen-shape tests GREEN.

**In scope:**

- Build SEED-012 MCP tool `emulator_read_memory(address, count)` (general 0x0000–0xFFFF range, count ≤ 256) — unlocks runtime BCPD/OCPD/LCDC/OAM inspection at frame 60+. Includes one MCP sanity test (LCDC bit 7 transitions across DISPLAY_ON).
- Revert-bisect diagnostic against pre-Plan-19 baseline (`cbe81d29`) in a detached scratch worktree (`git worktree add scratch/bisect cbe81d29`). Each bisect probe = a small diagnostic plan: re-apply one of Plans 10.1-19 / 10.1-20 / 10.1-22 fix-commit deltas (cherry-pick or selective file restore), `:gbkt-examples:metasprites:clean buildRom` in the scratch worktree, capture behavior3 PNG via MCP emulator, dump BCPD + OCPD palette RAM at frame 60 via the new memory-read tool, log pixel-decode (distinct color count, whether cyan present, whether checker visible) into Phase 10.2 `evidence/bisect-probe-N/`.
- Named-cause finding: a markdown artifact (analogous to `d-v3-visual-finding-v2.md`) under `evidence/` that names the regression site identified by the bisect and the proposed minimal fix shape.
- Fix plan that applies the named cause's minimal-scope correction. The fix must preserve all 5 currently-GREEN tests: `DV3GbcPaletteWriteDiagnosticTest` (3) + `DV3VisualV2DiagnosticTest` (2). New locking tests may be added (e.g., for emission order, additional emission, or removed emission).
- Cross-phase UAT re-shoot (D-04 reprise from 10.1): re-capture the 3 behavior PNGs into `.planning/phases/10-port-metasprites-gbdk-example-to-gbkt/evidence/uat-screenshots/`. behavior3 must go from 147-byte all-black to a visible cyan-elephant + checker-BG image with ≥4 distinct colors in the pixel decode. behavior1/2 (DMG path) must not regress.
- ROM-build smoke gate: clean `:gbkt-examples:metasprites:buildRom` is mandatory; `:gbkt-examples:metasprites-stress:buildRom` is in-scope IFF the bisect-named regression touches code locked by 10.1's D-21 stress gate (planner decides at fix-plan time).
- Phase close: scratch worktree torn down (`git worktree remove scratch/bisect`); branch left intact for traceability per `feedback_claude_code_worktree_drift_quirks.md` (never `git branch -D` until merge is visible — and we are NOT merging from this worktree).

**Out of scope:**

- DSL surface changes (no new IR fields, no new visitor methods, no DSL helpers).
- Real-hardware (flash cart) and BGB / SameBoy cross-emulator confirmation. Coffee-GB is the binding ground truth for this phase; real-hardware divergence is a future-phase concern.
- New gameplay behaviors on the metasprites ROM. The 3 anchor behaviors (animation-advance, flip-cycle, subpalette-cycle) are locked.
- A 4th UAT anchor or new behavior PNG.
- Refactoring `GBDKPipelineV2.buildMainFunction()` beyond the minimal surgical change needed to close D-V3. Cleanup PRs are a Phase 13 concern.
- Investigations into other visual defects (D-V1, D-V2 are already CLOSED with visible PNGs from Phase 10.1).

The named cause emerges from the table.

### Diagnostic tooling prerequisite

- **D-08: SEED-012 MCP `emulator_read_memory(address, count)` is Plan 10.2-01.** General signature per the seed (raw 0x0000–0xFFFF address, count ≤ 256 bytes, returns hex-formatted byte array). Single-method addition to `gbkt-mcp-server` tool registry + thin pass-through to `StepAgent.readMemory(Int): Byte` (probably already exists internally for the sym-file lookup). Sanity test: read `LCDC_REG` (0xFF40) at boot vs post-DISPLAY_ON, assert bit 7 transitions from 0 → 1.
- **D-09: Why MCP-tool-first and not inline-only:** the 4-round 10.1 grind failed via static deduction. Static analysis correctly named "Coffee-GB's cgb_compatibility doesn't reach BCPD" as a hypothesis, but the static path had no way to confirm "did our explicit `set_bkg_palette(0u, 1u, _gbkt_default_bg_pal)` write actually land in BCPD palette RAM, or is something resetting it?" — that question can only be answered by reading the runtime register state. This phase MUST be able to answer it.
- **D-10: MCP tool surface = general, NOT palette-specific.** Per user decision. The general `emulator_read_memory(address, count)` unlocks future audio/banking/OAM diagnostics in addition to the immediate palette use case. Marginal cost over a palette-only helper is negligible.
