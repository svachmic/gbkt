# Phase 10.2: GBC palette write path — D-V3 visual closure - Research

**Researched:** 2026-05-19
**Domain:** GBDK codegen pipeline (palette write path) + MCP emulator memory-read tool + revert-bisect diagnostic
**Confidence:** HIGH (codebase verified, source files cited at file:line)

## Summary

Phase 10.2 closes ONE visual defect that Phase 10.1's 4 inline rounds (Plans 19/20/21/22) couldn't close: GBC behavior3 (sub-palette cycle) renders a 147-byte all-black PNG despite all 5 codegen-shape contracts (10 locked test methods) being GREEN. The phase's first move is a **revert-bisect** against the known-good commit `cbe81d29` (which rendered cyan elephant on black BG) using a `git worktree add scratch/bisect` workflow, gated by a new MCP `emulator_read_memory` tool (SEED-012) so each bisect probe captures BCPD/OCPD palette RAM dumps alongside the behavior3 PNG.

Research confirms: (1) `StepAgent.readMemory(Int): Int` already exists at `StepAgent.kt:218` — SEED-012 is a pure pass-through at the MCP boundary; (2) `cbe81d29` is reachable from current HEAD and three GBDKPipelineV2.kt commits exist between it and HEAD (`7b86049f` Plan 20, `0976e08b` Plan 22, plus the `1ad0664a` SPRITES_8x8 emit and `20fdd8e8` metasprites.h include); (3) the 3 Plan 22 emissions are independently applicable — each is gated by a separate `gameIR.config.gbcTarget != GbcTarget.DMG` block at distinct line ranges (1013–1018 for constant, 3779–3784 for `set_bkg_palette` statement list, 3762–3768 for bgFillCheckerboard hoist filter); (4) the 5 locked tests + their 10 @Test methods have narrow contract surfaces that allow additive/reorder/inline-replacement fix shapes but block bare removal of `set_sprite_palette`, `set_bkg_palette`, or LCDC-bit ordering.

**Primary recommendation:** Structure Phase 10.2 as **Wave 1: SEED-012 MCP tool (1 plan) → Wave 2: scratch worktree setup + cyan baseline (1 plan) → Wave 3: bisect probes A/B/C (3 sequential plans, each per-probe; Plan 22 sub-splittable into 3 sub-probes if needed) → Wave 4: named-cause finding writeup + RED test (1 plan, Plan 21→22 decoupling pattern) → Wave 5: 1-task atomic fix (1 plan) → Wave 6: UAT re-shoot + cross-phase Phase 10 evidence update (1 plan) → Wave 7: phase close + ROM-build smoke + worktree teardown verification (1 plan)**. Total: 8 minimum plans (D-03 lower bound); 12 ideal (each probe split into sub-probes if Plan 22 sub-splitting needed; D-03 ideal target).

### Pattern 1: Plan 21→22 Diagnostic→Fix Decoupling (D-19)

**What:** Diagnostic plan writes the finding markdown AND commits the RED test. Execution plan is 1-task atomic.
**When to use:** The named-cause-and-fix pair at end of Phase 10.2 (Wave 4 → Wave 5).
**Example:** Plan 21 (`10.1-21-SUMMARY.md`) committed `DV3VisualV2DiagnosticTest` RED and wrote `d-v3-visual-finding-v2.md` with exact insertion points. Plan 22 (`10.1-22-SUMMARY.md`) was 1 task: apply the 3 emissions verbatim. Total Plan 22 duration: ~20 min.

### Pattern 2: Duplication-not-Relocation (Plan 20 + Plan 22)

**What:** Hoist an emission into `main()` while preserving the original in `{start}_enter` (idempotent palette/VRAM writes mean duplication is runtime-neutral).
**When to use:** If the named fix requires moving an emission earlier in the bootstrap sequence.
**Example:** GBDKPipelineV2.kt lines 3737–3744 (`hoistedStartPaletteStatements`) and lines 3762–3768 (`hoistedBgFillCheckerboardStatements`). The filter-and-map idiom: `startScene?.enterOps?.filterIsInstance<SetPalette>()?.map { it.accept(ScriptOpVisitor) }`. Note: the filter identifies but does NOT remove.

### Pattern 3: GBC-Conditional Emission Gate

**What:** Wrap any non-DMG-safe emission in `if (gameIR.config.gbcTarget != GbcTarget.DMG)`.
**When to use:** Any new register write or hoist the fix introduces.
**Example:** Lines 1014, 3780, 3798 — three existing sites using the identical negative-of-DMG gate pattern. Future enum additions (hypothetical `SGB`) default to emitting the gated content (safer than silent drop).

### Pattern 4: Awk Brace-Walk Before Grep (D-18)

**What:** Extract a function body via brace-walk before grepping for emission shape; prevents file-level false positives where another function happens to contain the same substring.
**When to use:** Any new RED test in this phase that asserts an invariant about main() or play_enter() contents.
**Example:** All 5 locked tests use the identical Kotlin brace-walk helper (`extractFunctionBody`/`extractFunctionBodyForDv3`/`extractFunctionBodyForDv3V2`/`extractFunctionBodyBgTest`/`extractFunctionBodyForSlotTest`) — see `DV3GbcPaletteWriteDiagnosticTest.kt:72-90`. Phase 10.2's new RED test MUST follow this idiom.

### Anti-Patterns to Avoid

- **File-level grep for per-function invariants:** A `mainC.contains("set_bkg_palette")` test will pass even if the call lives in `play_enter()` instead of `main()`. Always brace-walk.
- **Force-deleting the worktree branch at phase close:** Per `feedback_claude_code_worktree_drift_quirks.md` §3 + D-20, NEVER `git branch -D worktree-*` until a merge commit is visible — and Phase 10.2 is NOT merging from the worktree (it's a read-only diagnostic). Keep the branch for traceability.
- **Multiple emission additions in one bisect probe:** D-06 specifies chronological probes. If Plan 22's 3 emissions need to be narrowed, do 3 sub-probes (C-1/C-2/C-3) — don't combine.
- **Test deletion to make the fix easier:** D-12 — if a locked test contracts the regression itself, AskUser before deleting; default to find an additive/order-tweaked fix.
- **5th speculative fix on top of the existing stack:** The whole phase exists to avoid this. Bisect MUST name the regression site before any fix is applied.

## Common Pitfalls

### Pitfall 1: Probe rebuild without clean

**What goes wrong:** A probe shows "cyan still visible" not because the regression isn't introduced but because `build/gbkt/generated/main.c` is stale from the previous probe.
**Why it happens:** Gradle's up-to-date check on `generateC` can think nothing changed if file mtimes are deceptive.
**How to avoid:** ALWAYS `:clean buildRom` between probes. Pin this in every probe plan's task description per D-16.
**Warning signs:** Two consecutive probes with identical `behavior3-*.png` byte sizes despite source diff between them.

### Pitfall 2: Worktree commit leakage to main branch

**What goes wrong:** A bisect probe's commit (cherry-pick) lands on `feat/d_and_d_gaps` instead of the bisect branch (1 in 3 worktree agents per the memory feedback).
**Why it happens:** `Agent(isolation="worktree")` quirk — see `feedback_claude_code_worktree_drift_quirks.md` §1.
**How to avoid:** Per D-20, check `git reflog feat/d_and_d_gaps | head -50` AFTER each probe wave. If a probe commit shows up on the parent branch instead of the worktree, the probe still ran correctly — but the worktree's tip is unchanged.
**Warning signs:** `git log scratch/bisect` shows the cherry-pick reverted at HEAD; `git reflog feat/d_and_d_gaps` shows the cherry-pick.

### Pitfall 3: Test-deletion temptation

**What goes wrong:** Fix shape requires removing one of the 5 locked tests' contracts (e.g., bisect proves Plan 19's SHOW_BKG-before-DISPLAY_ON ordering itself is what kills cyan, but `DV3GbcPaletteWriteDiagnosticTest` test 3 locks SHOW_BKG-before-DISPLAY_ON).
**Why it happens:** It's the easy way out.
**How to avoid:** Per D-11 + D-12 — try every additive/order-tweaked fix first. If after exhaustive search a test MUST be deleted, AskUser. Most "fix needs test removal" situations are actually "fix needs to be done differently".
**Warning signs:** Fix candidate's diff is just a `@Disabled` annotation on an existing test.

### Pitfall 4: BCPD palette RAM read via wrong address pattern

**What goes wrong:** Probe reads `0xFF69` (BCPD data port) directly without setting `0xFF68` (BCPS index register), gets garbage that doesn't match palette RAM layout.
**Why it happens:** Coffee-GB's `ColorPalette.setByte` only mutates `palettes[index/8][(index%8)/2]` when address == dataAddr (the data port). The reverse — reading the data port — requires writing BCPS first to address the slot. This is the standard Game Boy CGB protocol per `d-v3-visual-finding-v2.md:120-135`.
**How to avoid:** Probe reads must use a `(write BCPS to address, read BCPD)` pair loop, NOT a single-address read.
**Warning signs:** Palette-RAM dumps are uniform (all `0xFF` or all `0x00` regardless of probe state) — that means the dump pattern is wrong, not that the palette state is wrong.

### Pitfall 5: Coffee-GB `gbcMode=true` ambiguity at boot

**What goes wrong:** The emulator boots in GBC mode but the ROM's cgb_compatibility byte is wrong, so Coffee-GB interprets it as DMG mode.
**Why it happens:** The CGB compatibility byte in the ROM header (`0x0143`) must be 0x80 (GBC backward-compatible) or 0xC0 (GBC only). gbkt sets this correctly per Plan 17, but a corrupted ROM build could regress this.
**How to avoid:** Wave 2's cyan-baseline probe MUST sanity-check the ROM header byte (read 0x0143). If the value is 0x00, the bisect is testing DMG, not GBC.

   - **RESOLVED (canonical bytes, no static decode bug):** The constant at `GBDKPipelineV2.kt:1015` is
     `const palette_color_t _gbkt_default_bg_pal[4] = {0x7FFF, 0x56B5, 0x294A, 0x0000};`. As a little-endian

     of `GBDKPipelineV2.kt:1015` at planning time (2026-05-19).

## Security Domain

> Phase 10.2 is a developer-tool / codegen / diagnostic phase. No production user data, no auth surface, no network endpoint. The SEED-012 MCP tool exposes `read` (not `write`) of emulator memory in a development-only stdio MCP server context. ASVS scope is minimal.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | MCP stdio is local-only; no auth boundary |
| V3 Session Management | no | One session per stdio process — lifecycle is the process itself |
| V4 Access Control | no | The emulator runs the developer's own ROM; no resource-access policy needed |
| V5 Input Validation | yes | `emulator_read_memory` MUST validate `address` is in 0x0000–0xFFFF and `count` ≤ 256. Already specified in SEED-012 + Pitfall 1 mitigations. |
| V6 Cryptography | no | No keys, no secrets, no certificates in scope |

### Known Threat Patterns for the touched surface

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Out-of-range memory read (e.g., `count=10000`) | Denial of Service (server hang) | `count.coerceIn(1, 256)` per SEED-012 |
| Address-parse failure (`address="garbage"`) | Tampering / Denial | Try/catch around `toInt(16)` parse + `errorResult` per `handleReadVariable`/`handleStart` patterns |
| Address out of address space (`-1`, `0x10000`) | Tampering | Range check `address !in 0..0xFFFF` |
| Coffee-GB MMU side-effect on read (rare — most reads are side-effect-free) | Tampering of emulator state | `MemoryAccess.readByte` documents "I/O register WRITES trigger hardware side-effects" (line 98 of GbEmulator.kt). Reads are inert. No mitigation needed. |
| `System.err.println` leaking sensitive info on exception | Information Disclosure | Already established pattern — exceptions are logged with class name + message; no stack trace exposure. Acceptable for developer-local stdio. |
