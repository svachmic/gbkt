# Phase 10.2 Plan 01: MCP read_memory / write_memory tool pair

**SEED-012 EXTENDED MCP tool pair — emulator_read_memory + emulator_write_memory — unlock the 64-byte BCPD/OCPD palette-RAM dump protocol that Plan 03+ bisect probes consume.**

## Performance

- **Duration:** ~8 min
- **Completed:** 2026-05-19
- **Tasks:** 2
- **Files modified:** 3

## Accomplishments

- `StepAgent.writeMemory(address: Int, value: Int)` added as sibling to existing `readMemory(Int)`; masks value via `and 0xFF` for Int→Byte safety.
- `McpEmulatorSession.readMemory(address, count)` returns `List<Int>` of N consecutive bytes; `writeMemory(address, value)` is single-byte. Both mutex-guarded suspend.
- `ToolHandlerLogic.handleReadMemory` and `handleWriteMemory` added in the ToolHandlers object — accept JSON `{address: hex|decimal string, count?: 1..256}` / `{address, value: 0..255}`, return JSON `{address: "0x%04X", count, bytes: ["0xNN", ...]}` / `{success, address, value}`.
- Two new `addTool(...)` registrations placed between `emulator_get_playbook` and `emulator_list_games` — both follow the existing error-handler boilerplate (System.err logging; class-name + message only; no stack traces).

## Decisions Made

- Used `inline-duplicated` address parsing in both handlers rather than factoring a `parseAddress` helper — keeps the surgical patch tight and avoids introducing a new private function across the handler file.
- Write tool tolerates out-of-byte-range values by silent `and 0xFF` masking (mirrors `emulator_write_variable`); does NOT errorResult — accepted per the plan's threat model T-10.2-01w disposition.
- Did NOT enable BCPS/OCPS auto-increment in the tool itself — each Plan 03+ probe writes a fresh index byte per iteration. Plan 03's `palette-dump-protocol.md` documents this explicitly.
