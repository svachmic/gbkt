# Phase 10.2: Code Review Report

**Reviewed:** 2026-05-19
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Phase 10.2 delivers three distinct changes: (1) a 1-line `addAll` order swap in `GBDKPipelineV2.kt`
that fixes a VRAM write-ordering regression (checker bytes overwrote sprite tile 0 when
`set_bkg_data` fired after `set_sprite_data`); (2) the SEED-012 EXTENDED MCP tool pair
(`emulator_read_memory` + `emulator_write_memory`) wired through `ToolHandlers.kt` →
`McpEmulatorSession.kt` → `StepAgent.kt`; and (3) a new JVM-tier diagnostic test
`DV3VisualV3DiagnosticTest` that locks the relative-order invariant.

The order swap itself is correct and its logic is well-documented. The MCP tool pair introduces two
security and correctness issues that are BLOCKER-class: `readMemory` performs no upper-bound
overflow guard when `count > 1` (address + count - 1 can exceed 0xFFFF), and `writeMemory` at
the `ToolHandlers` layer silently masks values outside 0..255 with no error to the caller.
Additional warnings exist in the capture-only test files (hardcoded absolute paths, resource
leak on exception path, dead variables) and a gap in `handleReadMemory` test coverage.

## Critical Issues

### CR-01: Multi-byte readMemory overflows the 16-bit address space without bounds check

**File:** `gbkt-mcp-server/src/main/kotlin/io/github/gbkt/mcp/McpEmulatorSession.kt:249`
**Issue:** `readMemory(address, count)` maps over `(0 until count)` and calls
`a.readMemory(address + i)` for each byte. The address range is validated to `0..0xFFFF` at the
`ToolHandlers` layer for `address` alone, but the combined end address `address + count - 1` is
never checked. With a maximally-large count of 256 (the `coerceIn(1, 256)` cap in
`handleReadMemory`) and `address = 0xFF01`, the last read is from `0xFF01 + 255 = 0x10000`, which
is outside the 16-bit address space. The underlying `StepAgent.readMemory` calls through to
Coffee-GB's `MemoryAccess.readByte(address)`. Depending on the emulator's bounds behaviour this
either wraps silently (wrong data returned) or throws an `ArrayIndexOutOfBoundsException` (since
the mock in `ToolHandlersTest` allocates `IntArray(0x10000)`). In the live Coffee-GB path this
will throw an uncaught exception, propagating through the coroutine and producing an unstructured
500-class error to the MCP client.

**Fix:**
```kotlin
// In handleReadMemory (ToolHandlers.kt), after parsing count:
val endAddress = address + count - 1
if (endAddress > 0xFFFF) {
    return errorResult(
        "address + count - 1 (0x${"%04X".format(endAddress)}) exceeds 0xFFFF. " +
            "Reduce count or use a lower start address."
    )
}
```

### CR-02: Evidence-capture tests use machine-specific absolute paths that are committed to the repo

**File:** `gbkt-examples/metasprites/src/test/kotlin/io/github/gbkt/examples/metasprites/BaselineCaptureTest.kt:28-35`
**File:** `gbkt-examples/metasprites/src/test/kotlin/io/github/gbkt/examples/metasprites/ProbeACaptureTest.kt:28-36`
**Issue:** `WORKTREE_ROM` and `EVIDENCE_DIR` are hardcoded to absolute paths under
`/Users/michalsvacha/GitHub/personal/gbkt/`. These paths are committed to the repository. Any
developer or CI runner that checks out the repository will see compile-clean tests that skip
(because `WORKTREE_ROM.exists()` is false), silently masking whether the test infra is broken or
correctly skipped. More importantly, these tests write evidence files to planning directories via
`EVIDENCE_DIR.mkdirs()` and `File(EVIDENCE_DIR, ...).writeText(...)` — if `EVIDENCE_DIR` somehow
resolves on another machine (e.g. a CI agent running as the same user), evidence files from
foreign ROMs would silently pollute the canonical evidence directory, invalidating the bisect
record. The absolute paths also make the tests unrunnable by anyone other than the original author
without source edits.

The tests are explicitly documented as "one-shot evidence capture" and gated by `assumeTrue`, but
that does not remove the security/integrity risk of hardcoded path writes to planning artifacts.

**Fix:**
- Convert `WORKTREE_ROM` and `EVIDENCE_DIR` to be resolved from a system property or environment
  variable, with `Assumptions.assumeTrue(false, "...")` when the property is absent:
```kotlin
private val WORKTREE_ROM: File? = System.getProperty("gbkt.bisect.rom")?.let { File(it) }
private val EVIDENCE_DIR: File? = System.getProperty("gbkt.bisect.evidenceDir")?.let { File(it) }

@Test
fun `capture baseline evidence`() {
    Assumptions.assumeTrue(WORKTREE_ROM != null && WORKTREE_ROM.exists(), "gbkt.bisect.rom not set")
    ...
}
```
This keeps the skip-by-default behaviour while removing hardcoded paths and the associated
integrity risk.

## Warnings

### WR-01: handleWriteMemory silently accepts out-of-range integer values from callers that pass non-JSON integers

**File:** `gbkt-mcp-server/src/main/kotlin/io/github/gbkt/mcp/ToolHandlers.kt:284`
**Issue:** `handleWriteMemory` reads `value` as `args["value"]?.jsonPrimitive?.intOrNull`. If the
caller passes a large integer (e.g. `256`, `512`, `65535`, or a negative value like `-1`), the
handler silently masks it with `value and 0xFF` and returns `success: true` with the masked value
in the response JSON. The caller receives no error and may not notice the truncation. The doc says
"Value is masked to a byte (0..255); higher bits masked off", but a negative value like `-1`
becomes `0xFF` via bitwise AND without any indication that the input was invalid. This inconsistency
— silent success with mutation — is surprising to API consumers and differs from the approach taken
for `frames` (which returns an explicit error when out of range).

**Fix:**
```kotlin
if (value !in 0..255) {
    return errorResult("value $value is out of range (0..255). " +
        "emulator_write_memory writes exactly one byte.")
}
```
Alternatively, document the masking behaviour clearly in the MCP schema description and accept it as
intentional. The current description only says "higher bits masked off", which is insufficient to
explain that negative values wrap to 0x01..0xFF.

### WR-02: BaselineCaptureTest and ProbeACaptureTest have a resource leak on the exception path

**File:** `gbkt-examples/metasprites/src/test/kotlin/io/github/gbkt/examples/metasprites/BaselineCaptureTest.kt:182-187`
**File:** `gbkt-examples/metasprites/src/test/kotlin/io/github/gbkt/examples/metasprites/ProbeACaptureTest.kt:180-186`
**Issue:** The `StepAgent` is created outside the try/catch block (`val agent = StepAgent(...)`),
then `agent.start()` is called. If `agent.start()` throws, the outer `catch (e: Exception)` block
calls `try { agent.close() } catch (_: Exception) {}`, which is correct. However, the agent is
also closed mid-try with `agent.close()` on line 107/111 (inside the try body, before the file
writes), and then the `catch` block unconditionally calls `agent.close()` again. If the first
`agent.close()` inside the try succeeds but a subsequent file write throws, the catch calls
`agent.close()` on an already-closed agent. While `AutoCloseable.close()` called twice is
typically safe, it is nevertheless incorrect structure: `StepAgent` should either be wrapped in
`use {}` (with no manual `close()` inside the try body) or the mid-try `agent.close()` should be
eliminated. The current mixed approach is error-prone and misleading.

**Fix:** Use `agent.use { ... }` and remove the manual `agent.close()` from inside the try body:
```kotlin
StepAgent(config, metadata = null).use { agent ->
    agent.start()
    // ... rest of test body without agent.close()
}
```

### WR-03: DV3VisualV3DiagnosticTest uses indexOf for ordering but does not guard against the first token being absent from the body before asserting ordering

**File:** `gbkt-backend-gbdk/src/test/kotlin/io/github/gbkt/backend/gbdk/codegen/visitor/DV3VisualV3DiagnosticTest.kt:198-230`
**Issue:** Test 1 uses `assertTrue(fillBkgRectIdx >= 0, ...)` to assert presence before the
ordering assertion `assertTrue(fillBkgRectIdx < setSpriteDataIdx, ...)`. However, if
`setSpriteDataIdx == -1` (i.e., `set_sprite_data` is absent from `main()` because the pipeline
did not emit a sprite data load for the `dummySprite`), the ordering assertion
`fillBkgRectIdx < setSpriteDataIdx` becomes `N < -1`, which is **false** regardless of actual
ordering — the test would fail with a misleading VRAM-ordering message when the real problem is
that `set_sprite_data` was never emitted at all.

The same pattern applies in Test 2: if `setSpriteDataIdx == -1`, the assertion
`setBkgDataIdx < setSpriteDataIdx` fails as a false negative with a confusing error message. There
is no `require(setSpriteDataIdx >= 0)` guard analogous to the `require(displayOnIdx >= 0)` guard
that was added for DISPLAY_ON.

**Fix:** Add a precondition guard for `set_sprite_data` analogous to the DISPLAY_ON guard:
```kotlin
require(setSpriteDataIdx >= 0) {
    "main() body missing set_sprite_data — dummySprite did not trigger sprite data load. " +
        "Check buildAllSpriteDataLoadStatements() for metasprite support.\nmain() body:\n$mainBody"
}
```

### WR-04: handleReadMemory test coverage gap — multi-byte overflow edge case is untested

**File:** `gbkt-mcp-server/src/test/kotlin/io/github/gbkt/mcp/ToolHandlersTest.kt`
**Issue:** `ToolHandlersTest` tests `handleReadMemory` with `address=0xFF40, count=3` (a safe
range) and with a two-phase LCDC scenario. There is no test that exercises the overflow boundary
identified in CR-01: `address=0xFF01, count=256` (end address = 0x10000). Until CR-01 is fixed,
this test cannot be written (the behaviour is undefined), but once CR-01 is fixed the boundary
condition must be covered by a test that verifies an error result is returned. Without it the
regression protection for CR-01 is structural only (the fix code) with no executable guard.

**Fix:** After implementing the CR-01 fix, add:
```kotlin
@Test
fun `handleReadMemory rejects address plus count exceeding 0xFFFF`() = runTest {
    val session = makeSession()
    startSession(session)
    val args = buildJsonObject {
        put("address", "0xFF01")
        put("count", 256)  // end = 0x10100
    }
    val result = ToolHandlerLogic.handleReadMemory(session, args)
    assertTrue(result.isError == true)
    assertTrue(resultText(result).contains("exceeds 0xFFFF"))
    session.stop()
}
```

**Fix:** Add a `@Tag("evidence-capture")` annotation at the class level and configure `./gradlew

### IN-04: cyanPresent logic in BaselineCaptureTest uses overly broad OR — ocpdSlot2NonZero alone treats all non-zero OCPD as cyan

**File:** `gbkt-examples/metasprites/src/test/kotlin/io/github/gbkt/examples/metasprites/BaselineCaptureTest.kt:305`
**Issue:** `val cyanPresent = cyanInOcpd || cyanInPixels || ocpdSlot2NonZero`. The third term
`ocpdSlot2NonZero` is true whenever *any* byte in OCPD slot 2 (indices 16–23) is non-zero,
regardless of whether it represents a cyan colour. This means if a non-cyan palette is written to
OBJ slot 2 (e.g. a white palette with value 0x7FFF for color 0), `cyanPresent` evaluates to
`true` even if no actual cyan is visible. Combined with the assertion at the bottom
(`if (!cyanPresent) throw AssertionError(...)`), this could mask a real regression where the
sprite is rendered with the wrong palette. The same issue exists in ProbeACaptureTest (line 303).

This is present in both files identically (copy-paste).

**Fix:** Narrow the OR: `ocpdSlot2NonZero` is already covered by `cyanInOcpd` (which checks the
specific cyan 15-bit values). If `cyanInOcpd` is false, `ocpdSlot2NonZero` being true just means
some unknown palette is written — that should not count as "cyan present":
```kotlin
val cyanPresent = cyanInOcpd || cyanInPixels
// Drop ocpdSlot2NonZero — a non-zero but non-cyan palette must not satisfy the cyan test
```

### IN-05: DV3VisualV3DiagnosticTest Test 1 and Test 2 both generate the full pipeline output independently — expensive duplication

**File:** `gbkt-backend-gbdk/src/test/kotlin/io/github/gbkt/backend/gbdk/codegen/visitor/DV3VisualV3DiagnosticTest.kt:192-307`
**Issue:** Both `@Test` methods call `buildDv3V3GbcGame()` and `pipeline.generate(gameIR)` in
full, each independently generating the complete C output. The pipeline is stateless so this
is not incorrect, but it doubles the JVM test execution time for these two tests, which are
exercising the same generated `main.c` with different substrings checked. Given the pipeline is
not cheap (metasprite visitor, codegen, emission), both checks could be asserted in a single test
or extracted into a `@BeforeEach` fixture.

**Fix:** Extract shared setup:
```kotlin
private lateinit var mainBody: String

@BeforeEach
fun generateMainBody() {
    val gameIR = buildDv3V3GbcGame()
    val mainC = pipeline.generate(gameIR).files["main.c"] ?: error("main.c not generated")
    mainBody = extractFunctionBodyForDv3V3(mainC, "void main(void)")
        ?: error("Could not extract main() body")
}
```
This keeps both tests as separate `@Test` methods (preserving independent failure reporting) while
running the pipeline only once.
