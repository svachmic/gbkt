  <action>Write `evidence/bisect-probe-0-baseline/palette-dump-protocol.md`. The doc has THREE sections:

(1) **Protocol selection — Direct BCPS/OCPS pre-write + BCPD/OCPD read.** Per the 2026-05-19 user decision, SEED-012 is extended with `emulator_write_memory`, enabling this protocol. Per-byte dump loop (executed once for BCPD, once for OCPD):
```
for index in 0..63:
    emulator_write_memory(BCPS_or_OCPS_addr, index)   // bit 7 (auto-increment) OFF; explicit index per byte
    byte = emulator_read_memory(BCPD_or_OCPD_addr, 1)
    dump[index] = byte
```
- BCPS = 0xFF68, BCPD = 0xFF69. OCPS = 0xFF6A, OCPD = 0xFF6B.
- 64 indexes cover 8 palettes × 4 colors × 2 LE bytes per palette = full palette RAM per port.
- Bit 7 (auto-increment) is intentionally LEFT CLEAR for each write — we want deterministic per-iteration addressing, not relying on Coffee-GB's increment behavior under read (which Pitfall 4 / Assumption A8 flag as unverified). If a Wave 1 spike shows auto-increment is deterministic, future probes MAY switch to a single bit-7-set BCPS write + 64 sequential reads as a small optimization. Not required for closure.

(2) **JSON shape (the dump file contract — used by Plans 04/05/06).** Each dump JSON file has:
```json
{
  "address_port": "0xFF69",
  "index_port": "0xFF68",
  "auto_increment_used": false,
  "byte_count": 64,
  "bytes_hex": ["0xNN", "0xNN", ..., "0xNN"],
  "palettes": [
    {"slot": 0, "colors_15bit": ["0xNNNN", "0xNNNN", "0xNNNN", "0xNNNN"], "interpretation": "<e.g., 'all zero — BCPD slot 0 not written'>"},
    {"slot": 1, "colors_15bit": ["0xNNNN", ...], "interpretation": "..."},
    ...
    {"slot": 7, "colors_15bit": ["0xNNNN", ...], "interpretation": "..."}
  ],
  "summary": {
    "any_slot_non_zero": true|false,
    "slot_0_non_zero": true|false,
    "slot_2_non_zero": true|false,
    "notes": "<one-line interpretation>"
  }
}
```
- `palettes[i].colors_15bit[j]` = the 15-bit GBC color = `(bytes_hex[i*8 + j*2 + 1] << 8) | bytes_hex[i*8 + j*2]` (little-endian pair → 16-bit, then ignore high bit which is unused per GBC spec).
- The dump-loop helper script (kotlin scratch or python ad-hoc) reads the 64-hex-byte array and emits this enriched JSON.

(3) **Slot semantics for the bisect.** For sprite-palette-cycle behavior3:
- BCPD slot 0 = the default BG palette emitted by `set_bkg_palette(0u, 1u, _gbkt_default_bg_pal)` (Plan 22 emission). Non-zero proves the BG write reached palette RAM.
- OCPD slot 2 = the cyan palette emitted by `set_sprite_palette(2u, 1u, cyan_pal)` (Plan 20 emission). Non-zero with cyan-bit-pattern proves the sprite write reached palette RAM.
- These two slots are the bisect's binding signals. The full 64-byte dump captures them PLUS the rest of palette RAM for additional context (e.g., did the metasprite's S_PAL selector touch a different slot than expected?).

(4) **Fall-back protocol (16-byte minimum)** — if the Wave 1 spike (Plan 02 + a manual MCP test) shows the write-then-read round-trip fails on real Coffee-GB (different from the JVM stub), degrade to writing index 0 only for each of the 8 slots = 16 bytes (8 slots × 2 bytes = first color of each palette). This still matches the D-07 minimum "16 bytes, slots 0..7" phrasing. Document the degradation cause in the SUMMARY.md.
