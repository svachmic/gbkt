## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Engine vs RPG boundary
- **Damage model**: Engine provides pluggable formula framework (hooks for source, target, amount). RPG layer configures formulas for its domain (elemental, stat-based, etc.)
- **Combatants**: Engine defines abstract Combatant interface (ID, side, canAct). RPG adds HP, stats, abilities on top
- **Combat types in engine**: Turn-based + real-time only. ATB, tactical, wave-survival go in RPG or future genre packages
- **Turn order**: Entirely RPG concern. Engine just says "next turn happens"
- **Equipment**: RPG only. Engine items are data + effects, not equippable
- **Drop/loot tables**: Engine feature (weighted random item selection is genre-agnostic)
- **All 5 V1 combat types must exist** for parity, but placement differs: 2 in engine, 3 in RPG

#### Combat state machine
- **Core states simple**: Engine provides minimal states (INIT, PLAYER_TURN, ENEMY_TURN, VICTORY, DEFEAT). Extensibility interfaces let genres add their own states
- **Fully extensible**: Typed interface for states (not enum, not string). Game authors can define custom states (e.g., NEGOTIATION). Engine provides core states, game/RPG extends with custom ones
- **State objects with update()**: Each state is an object with its own `update()` method. Engine calls current state's update() each frame
- **Deferred transitions**: State changes queue and apply at start of next frame. Prevents mid-frame state conflicts
- **Hierarchical**: States can have sub-states (e.g., PLAYER_TURN.SELECTING_TARGET). Engine manages the hierarchy
- **Common base, separate impls**: Shared CombatEngine interface with lifecycle methods. Turn-based and real-time implement differently
- **Declarative conditions**: Game author defines win/lose in DSL: `onVictoryWhen { allEnemiesDead() }`, `onDefeatWhen { partyWiped() }`

#### Item & inventory model
- **Effect types**: Claude's discretion — keep minimal and generic (heal, buff, script as escape hatch). RPG extends the ItemEffect interface with domain-specific effects
- **Containers**: Typed and extensible. Engine provides container interface; game authors define the container types they need (bag, key items, etc.)
- **Categories**: Extensible. Engine provides the category mechanism; game authors define their own categories (CONSUMABLE, AMMO, RECIPE, etc.)
- **Stacking**: Category provides default stacking rules, per-item definitions can override. Both layers work together

#### DSL surface design
- **Combat**: New `combatEngine()` delegate pattern — `val combat by combatEngine("name") { type(TURN_BASED); ... }`. Clearly "engine level"; RPG wraps with its own `battle()` that configures combatEngine internally
- **Inventory**: Container-first — `val bag by container("bag") { slots(16) }; val keys by container("keys") { slots(8) }`. Multiple containers from the start
- **Items**: Catalog + references — `items { val potion by item { ... } }` in a catalog block. Inventories reference items from catalog
- **Integration**: Combat and inventory are independent systems. Extensible enough that RPG module can build custom battle actions (use item in combat) without engine coupling

#### Module structure & BoM
- **IR already extracted**: `gbkt-ir` exists with visitor interfaces (ScriptOpVisitorI, ExprVisitorI, SystemIRVisitorI). Non-sealed, extensible
- **Combat & inventory placement**: Everything in `gbkt-engine` (types AND implementations). Not split into separate modules — engine is the common denominator for all GB/GBC game genres
- **Codegen**: New CombatVisitor and InventoryVisitor in `gbkt-backend-gbdk` alongside existing SceneVisitor, ActorVisitor, etc.
- **CLAUDE.md updates**: Rewrite old combat/rpg CLAUDE.md files in gbkt-core to reflect V2 architecture
- **BoM/gbkt-all**: Update as part of this phase to include new combat/inventory in gbkt-engine

## Summary

Phase 06.4 ports engine-level combat and inventory systems to the V2 pipeline. The primary deliverables are: (1) a generic `CombatEngineSystem` in `gbkt-engine` with turn-based and real-time variants using extensible typed state objects, (2) an `ItemCatalog` + `ContainerSystem` for inventory management in `gbkt-engine`, and (3) new codegen visitors `CombatVisitor` and `InventoryVisitor` in `gbkt-backend-gbdk`. Both systems integrate with the existing `GenericSystem` IR node pattern — the combat engine becomes a new `SystemIR` subtype (or extended `GenericSystem`) and inventory containers become IR types in `gbkt-ir`.

The codebase already has the skeletal `simpleBattle` system in `gbkt-rpg` that generates a basic 5-state COMBAT_STATE machine. Phase 06.4 promotes this to a proper engine-level `CombatEngineSystem` with extensibility interfaces, removes the RPG coupling, and adds the `real-time` combat mode. The existing codegen patterns from `GBDKSystemVisitor.buildSimpleBattleFunctions()` and `GBDKPipelineV2.buildSystemGlobalVars()` form the reference implementation template.

**Primary recommendation:** Model combat as a new sealed `SystemIR` subtype `CombatEngineSystem` (alongside `DialogSystem`, `SaveSystem`, etc.) and add `ItemCatalogIR` + `ContainerIR` as new IR data types in `gbkt-ir`. Wire them into `GameIR` as new list fields (`items`, `containers`). Add `CombatVisitor` and `InventoryVisitor` as new visitor classes in `gbkt-backend-gbdk/codegen/visitor/`. Follow the `WorldIR` + `WorldBuilders` + `GBDKSystemVisitor` pattern established in Phase 06.3.

### Pattern 1: New SystemIR Subtype (Preferred for Combat)

The existing `SystemIR` interface is non-sealed (allows external implementors). The cleanest approach for phase 06.4 is to add `CombatEngineSystem` as a new concrete implementor alongside `DialogSystem`, `SaveSystem`, etc.

```kotlin
// Source: gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/CombatEngineIR.kt
data class CombatEngineSystem(
    override val id: String,
    val combatType: CombatType,                         // TURN_BASED | REAL_TIME
    val combatants: List<CombatantDef> = emptyList(),   // abstract combatant slots
    val onVictoryOps: List<ScriptOp> = emptyList(),
    val onDefeatOps: List<ScriptOp> = emptyList(),
    val customStates: List<CombatStateId> = emptyList(), // extensibility hook
    val damageFormula: DamageFormulaRef? = null,         // optional formula ref
    override val sourceLocation: SourceLocation? = null,
    override val bankSlot: BankSlot? = null,
    override val vramRange: VRAMRange? = null,
    override val oamSlot: OAMSlot? = null,
) : SystemIR {
    override fun <T> accept(visitor: SystemIRVisitorI<T>): T =
        visitor.visitCombatEngineSystem(this)
}

enum class CombatType { TURN_BASED, REAL_TIME }

// Typed state identifier — replaces magic strings
@JvmInline value class CombatStateId(val id: String)

// Abstract combatant slot
data class CombatantDef(
    val id: String,
    val side: CombatantSide,  // PLAYER | ENEMY
)

enum class CombatantSide { PLAYER, ENEMY }

// Opaque reference to a damage formula function
@JvmInline value class DamageFormulaRef(val functionName: String)
```

**Why this pattern:** Maintains visitor exhaustiveness. The `SystemIRVisitorI.kt` adds one more method. `GBDKSystemVisitor` dispatches to `CombatVisitor`. This follows how `ExplorationSystem`, `CameraSystem`, etc. are handled.

**Alternative:** Keep using `GenericSystem(type="combat_engine")` and dispatch in `visitGenericSystem`. This avoids modifying the visitor interface. Use this if the visitor interface change is considered too invasive. The CONTEXT.md says "codegen: new CombatVisitor and InventoryVisitor" which implies proper visitor dispatch.

### Pattern 3: DSL Builder Pattern (Follows Phase 06.3 WorldBuilders Style)

```kotlin
// Source: gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/CombatEngineBuilder.kt
class CombatEngineBuilder(val id: String) {
    private var combatType = CombatType.TURN_BASED
    private val combatants = mutableListOf<CombatantDef>()
    private var onVictoryOps: List<ScriptOp> = emptyList()
    private var onDefeatOps: List<ScriptOp> = emptyList()

    fun type(t: CombatType) { combatType = t }
    fun combatant(id: String, side: CombatantSide) { combatants += CombatantDef(id, side) }
    fun onVictory(block: ScriptBuilder.() -> Unit) {
        onVictoryOps = ScriptBuilder().apply(block).build()
    }
    fun onDefeat(block: ScriptBuilder.() -> Unit) {
        onDefeatOps = ScriptBuilder().apply(block).build()
    }
    fun build() = CombatEngineSystem(id, combatType, combatants, onVictoryOps, onDefeatOps)
}

// In GameBuilder.kt — combatEngine() method added alongside camera(), saveData(), etc.:
fun GameBuilder.combatEngine(id: String, block: CombatEngineBuilder.() -> Unit): CombatEngineRef {
    val builder = CombatEngineBuilder(id)
    builder.block()
    val system = builder.build()
    refRegistry.register(id, RefKind.SYSTEM)
    registerSystem(system)
    return CombatEngineRef(id)
}

// Delegate variant (matches CONTEXT.md "val combat by combatEngine(...) { }" DSL):
class CombatEngineDelegate(val id: String, val block: CombatEngineBuilder.() -> Unit) :
    ReadOnlyProperty<Any?, CombatEngineRef> {
    operator fun provideDelegate(thisRef: GameBuilder, prop: KProperty<*>): CombatEngineDelegate {
        thisRef.combatEngine(id.ifEmpty { prop.name }, block)
        return this
    }
    override fun getValue(thisRef: Any?, property: KProperty<*>) = CombatEngineRef(...)
}
```

### Pattern 4: Codegen — CombatVisitor (New File, Mirrors GBDKSystemVisitor)

```kotlin
// Source: gbkt-backend-gbdk/.../visitor/CombatVisitor.kt
//
// Generated C for TURN_BASED CombatEngineSystem:
//
// // Globals (in buildSystemGlobalVars):
// UINT8 _combat_state_<id> = 0;   // INIT=0, PLAYER_TURN=1, ENEMY_TURN=2, VICTORY=3, DEFEAT=4
// UINT8 _pending_state_<id> = 0xFF;  // deferred transition — 0xFF = no pending transition
//
// // Functions:
// void combat_request_state_<id>(UINT8 s) { _pending_state_<id> = s; }
//
// void update_combat_<id>(void) {
//     // Apply deferred transition first (start-of-frame)
//     if (_pending_state_<id> != 0xFF) {
//         _combat_state_<id> = _pending_state_<id>;
//         _pending_state_<id> = 0xFF;
//     }
//     switch (_combat_state_<id>) {
//         case 0: /* INIT */ _combat_state_<id> = 1; break;
//         case 1: /* PLAYER_TURN */ if (button_pressed(J_A)) { combat_request_state_<id>(2u); } break;
//         case 2: /* ENEMY_TURN */ combat_request_state_<id>(1u); break;
//         case 3: /* VICTORY */ <onVictoryOps> break;
//         case 4: /* DEFEAT */ <onDefeatOps> break;
//         // custom states (5, 6, ...) dispatch here
//     }
// }
//
// UINT8 combat_is_in_state_<id>(UINT8 state) {
//     return _combat_state_<id> == state;
// }
// void trigger_<id>(void) { _combat_state_<id> = 0; _pending_state_<id> = 0xFF; }
//
// REAL_TIME variant: case 1 runs every frame (no J_A wait), enemy AI runs every N frames
```

The key improvement over existing `buildSimpleBattleFunctions()`: deferred transitions via `_pending_state_<id>` prevent mid-frame conflicts. The existing code transitions immediately; the V2 engine model queues the transition.

### Anti-Patterns to Avoid

- **Using `GenericSystem` config map for CombatEngineSystem**: The config map is `Map<String, Any>` — no type safety, requires `@Suppress(UNCHECKED_CAST)` everywhere. Given that the CONTEXT.md explicitly names "CombatVisitor" as separate from `GBDKSystemVisitor`, a proper `SystemIR` subtype is preferred. The visitor interface addition is the right call.
- **Sealed ItemEffectIR in gbkt-ir**: Do NOT make `ItemEffectIR` sealed in `gbkt-ir` — that would prevent RPG module from extending it. Use a non-sealed interface (same pattern as `SystemIR`, `ScriptOp`, `Expr`).
- **Placing combat/inventory in `gbkt-engine` source files**: The CONTEXT.md says "Everything in `gbkt-engine` (types AND implementations)." However, the module hierarchy is `gbkt-ir ← gbkt-lang ← gbkt-engine`. IR types go in `gbkt-ir`. DSL builders go in `gbkt-lang`. The `gbkt-engine` module adds the engine-level Kotlin interface types that straddle DSL and IR (like `CombatState` interface, `ItemEffect` interface). This is consistent with how `gbkt-engine` already contains `InputTypes.kt`, `EntityTypes.kt`, `SceneTypes.kt`, `GraphicsTypes.kt`.
- **Duplicating `buildSimpleBattleFunctions` in CombatVisitor**: Delete or deprecate the existing `buildSimpleBattleFunctions` in `GBDKSystemVisitor` once `CombatVisitor` covers the same functionality. Or keep it for RPG backward compat — but add a TODO.
- **Missing `_pending_state` global in `buildSystemGlobalVars`**: The deferred transition requires two globals per combat engine (`_combat_state_<id>` and `_pending_state_<id>`). Don't forget `_pending_state` in the global variable generation.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead |
|---------|-------------|-------------|
| Inventory slot management | Custom allocator | Parallel arrays: `_inv_<id>_items[slots]` + `_inv_<id>_counts[slots]` with linear scan — Game Boy has no heap, fixed-size arrays are the only option |
| Item use effect dispatch | Function pointers (C89 incompatible naming) | `switch(item_id)` dispatch — same pattern as `_map_collision()` dispatcher in Zone codegen |
| State machine | Recursive state hierarchy | Flat `switch(_combat_state_<id>)` + `_pending_state_<id>` for deferred transitions — Game Boy stack is ~128 bytes, recursion overflow risk |
| Damage formula evaluation | Runtime formula parser | Compile-time function call: formula is a C function name `damage_formula_<id>()` — game author writes the formula in DSL which becomes a generated C function |
| CombatEngineRef delegate | Custom property delegation | Follow `ArrayDelegate`/`ActorDelegate`/`ZoneRef` pattern — `ReadOnlyProperty<Any?, CombatEngineRef>` with `provideDelegate` |

**Key insight:** Game Boy constraints (no heap, small stack, C89 compiler) make all "smart" runtime approaches wrong. Every runtime data structure must be a compile-time fixed-size array. Every dispatch must be a switch statement.

## Common Pitfalls

### Pitfall 1: Visitor Interface Modification
**What goes wrong:** Adding `visitCombatEngineSystem()` to `SystemIRVisitorI` breaks all existing visitor implementations that don't implement the new method.
**Why it happens:** The interface requires all methods to be implemented.
**How to avoid:** Add a default `fun visitCombatEngineSystem(system: CombatEngineSystem): T = visitGenericSystem(GenericSystem(system.id))` fallback — or add a `default` implementation using a GenericSystem stub. Check all existing `SystemIRVisitorI` implementors: `GBDKSystemVisitor` in `gbkt-backend-gbdk` (must implement) and any analysis pass visitors.
**Warning signs:** Compilation failure "Class 'X' is not abstract and does not implement abstract member."

### Pitfall 2: Mid-Frame State Transition Conflicts
**What goes wrong:** Transitioning combat state mid-frame causes the same frame's remaining logic to run against the new state.
**Why it happens:** Direct assignment `_combat_state_<id> = newState` takes effect immediately within the same `update_combat_<id>()` call.
**How to avoid:** Use `_pending_state_<id>` deferred transitions — set pending at end of case, apply at start of next update call. The generated C for PLAYER_TURN should call `combat_request_state_<id>(2u)` not directly assign.
**Warning signs:** Victory/defeat ops running on the same frame as state detection.

### Pitfall 3: GameIR Backward Compatibility
**What goes wrong:** Adding `items` and `containers` fields to `GameIR` with non-default values breaks all existing `GameIR(...)` constructor call sites.
**Why it happens:** `GameIR` is a data class — any new non-defaulted constructor parameters require all callers to update.
**How to avoid:** Always add new `GameIR` fields with `= emptyList()` defaults. Study existing examples: `zones: List<ZoneIR> = emptyList()` and `flags: List<GlobalFlagsIR> = emptyList()` were added this way in Phase 06.3.
**Warning signs:** Mass compilation failures in test fixtures creating `GameIR(...)` directly.

### Pitfall 4: CombatEngineSystem vs simpleBattle Duplication
**What goes wrong:** Phase 06.4 creates `CombatEngineSystem` while `gbkt-rpg` still uses `GenericSystem(type="simple_battle")`. Both paths generate combat code. Double-generation in game output.
**Why it happens:** `buildSimpleBattleFunctions()` in `GBDKSystemVisitor` remains active for `simple_battle` systems while `CombatVisitor` generates for `CombatEngineSystem` — two separate code paths.
**How to avoid:** The simpleBattle RPG path should eventually delegate to `CombatEngineSystem`. For this phase, they coexist. Add a code comment in `buildSimpleBattleFunctions()`: "TODO 06.5: migrate to CombatEngineSystem". No deletion yet.
**Warning signs:** Explorer example generating both `update_combat_combat` and `update_combat_engine_combat` functions.

### Pitfall 5: C89 Compatibility for Inventory Loops
**What goes wrong:** Using `for (int i = 0; i < slots; i++)` inside inventory functions causes "mixed declarations and code" C89 error on GBDK's `lcc` compiler.
**Why it happens:** C89 requires variable declarations before any statements in a block. The GBDK lcc compiler is strict C89.
**How to avoid:** Follow the `hide_sprites_range` pattern — use `CVarDecl` before the loop, then `CFor` with `init=null`. Or use `CRawCode` for loop body (pre-approved for C89 workarounds). Reference: Phase 05.05.1 decision "hide_sprites_range uses CRawCode for loop body — avoids C89 mixed-declaration issue."

### Pitfall 6: `SystemIRVisitorI` in `gbkt-analysis`
**What goes wrong:** The analysis passes (resource inventory, constraint check, RAM planning) may implement `SystemIRVisitorI` and fail to compile after adding `visitCombatEngineSystem()`.
**Why it happens:** Analysis passes may have catch-all visitors that need updating.
**How to avoid:** Grep for all `SystemIRVisitorI` implementors before modifying the interface. Add default no-op implementations if appropriate.

### Example 3: Generated C (CombatEngineSystem TURN_BASED)

```c
// Generated main.c globals:
UINT8 _combat_state_main_combat = 0u;    /* INIT */
UINT8 _pending_state_main_combat = 0xFF; /* no pending */

// Generated functions:
void combat_request_state_main_combat(UINT8 s) {
    _pending_state_main_combat = s;
}

void update_combat_main_combat(void) {
    /* Apply deferred transition */
    if (_pending_state_main_combat != 0xFF) {
        _combat_state_main_combat = _pending_state_main_combat;
        _pending_state_main_combat = 0xFF;
    }
    switch (_combat_state_main_combat) {
        case 0: /* INIT */
            _combat_state_main_combat = 1u;
            break;
        case 1: /* PLAYER_TURN */
            if (button_pressed(J_A)) {
                combat_request_state_main_combat(2u);
            }
            break;
        case 2: /* ENEMY_TURN */
```

### Module Hierarchy (Critical for Import Decisions)

```
gbkt-ir       ← pure IR data (no DSL deps)
   ↑ api()
gbkt-lang     ← DSL builders (GameBuilder, ScriptBuilder, etc.)
   ↑ api()
gbkt-engine   ← engine-level types (Kotlin interfaces for DSL surface)
   ↑ (not a dep of gbkt-lang; gbkt-engine gets gbkt-lang transitively)
gbkt-core     ← meta-module re-exporting gbkt-ir + gbkt-lang + gbkt-engine
   ↑
gbkt-rpg      ← genre package (implementation(":gbkt-core"))
gbkt-backend-gbdk ← codegen (gets everything via gbkt-core)
```

**Decision for `CombatEngineSystem` placement:** IR type goes in `gbkt-ir`. Builder goes in `gbkt-lang`. Kotlin interface types (`CombatState`, `ItemEffect`) go in `gbkt-engine`. This matches how `InputTypes.kt`, `EntityTypes.kt`, `GraphicsTypes.kt` are placed in `gbkt-engine`.

### Existing CRawCode Approvals to Be Aware Of

Per project decisions, the following patterns are approved escape hatches:
- GBDK hardware macros (`ENABLE_RAM`, `SCX_REG`, `NR50_REG`, etc.) — remain CRawCode
- C89 loop variable declarations (`CVarDecl` before `CFor` with `init=null`)
- `CRawExpr` for volatile pointer casts

For inventory/combat codegen: avoid CRawCode for anything representable in typed C AST. The loop body pattern for inventory operations can use `CRawCode` only if C89 variable scoping makes the typed version impossible (same as `hide_sprites_range`).

## Open Questions

1. **Should `visitCombatEngineSystem()` be added to `SystemIRVisitorI` or handled in `visitGenericSystem()`?**
   - What we know: `GBDKSystemVisitor` already dispatches on `"simple_battle"` type string inside `visitGenericSystem()`. Both approaches work.
   - What's unclear: Adding to `SystemIRVisitorI` is cleaner but requires all visitor implementors to update. Using `GenericSystem` avoids the interface change but loses type safety.
   - Recommendation: Add to `SystemIRVisitorI`. This matches the locked CONTEXT.md decision ("new CombatVisitor"). Find all implementors first with `mcp__serena__search_for_pattern("SystemIRVisitorI")` and add `override fun visitCombatEngineSystem() = emptyList()` defaults where appropriate.

2. **How does `RPGExtensions.simpleBattle()` relate to `CombatEngineSystem`?**
   - What we know: `simpleBattle()` in gbkt-rpg currently creates a `GenericSystem(type="simple_battle")`. Phase 06.4 creates `CombatEngineSystem` as the engine-level type.
   - What's unclear: Should `simpleBattle()` be refactored to create `CombatEngineSystem` internally in this phase, or just coexist?
   - Recommendation: For Phase 06.4, coexist. In Phase 06.5 (RPG), `simpleBattle()` should delegate to `CombatEngineSystem` and add RPG-specific fields on top. Add a TODO comment.

3. **How does `InventoryDataSource` in `MenuDef` connect to `ContainerIR`?**
   - What we know: `InventoryDataSource(inventoryId: String)` in `UITypes.kt` already exists. The menu codegen generates a loop over `_inventory_<id>_count` and `_inventory_<id>_names[i]`. The new `ContainerIR` would replace the string-based ref with a typed reference.
   - What's unclear: Whether `_inventory_<id>_count` naming aligns with the new `_inv_<id>_size` naming used in this research.
   - Recommendation: Use `_inv_<id>_size` and `_inv_<id>_items[]` consistently. Update the menu codegen that generates `_inventory_${invId}_count` to use `_inv_${invId}_size` once `ContainerIR` exists. Flag this as a codegen alignment task in the plan.

4. **Drop/loot table codegen scope?**
   - What we know: CONTEXT.md says "Drop/loot tables: Engine feature (weighted random item selection is genre-agnostic)."
   - What's unclear: How deep does loot table codegen go? Weighted random selection on Game Boy requires a pseudo-random function and weight table.
   - Recommendation: Scope to `DropTableIR` (list of weighted `ItemDef` refs) in `InventoryIR.kt`. Codegen generates a `roll_drop_table_<id>()` function using a simple LCG PRNG (deterministic, no stdlib). If this is too complex for 06.4, defer to 06.5 — CONTEXT.md marks it as engine feature but doesn't put it in the success criteria explicitly.
