# Phase 09.2: Fix generateC stale-output sync (INSERTED) — Context

**Gathered:** 2026-05-17
**Status:** Ready for planning
**Trigger:** Surfaced during Phase 09.1 closeout (2026-05-15) — a clean `./gradlew :gbkt-examples:simple-physics:buildRom` produced duplicate `_play_enter` / `_play_frame` link errors against a stale `bank1.c` left over from a prior MBC5 build. Plan 09.1-05 had folded `bank1.c` into `main.c` for single-scene-fits-HOME games, but `GenerateCTask` only ever WRITES the current emission set — it never DELETES files dropped from the set. Phase 09.1 was wrongly marked complete (15/15 truths verified) because the JVM-tier verifier never exercised the build pipeline end-to-end. Phase 09.2 closes that gap.

---

<domain>
## Phase Boundary

Phase 09.2 ships two surgical deliverables — no surplus.

**In scope:**
- **Deliverable 1 — GenerateCTask output sync.** `GenerateCTask` (gbkt-gradle-plugin) must reconcile its `outputDir` to exactly the file set the pipeline returns each run. Stale files (e.g. `bank1.c` left over after Plan 09.1-05's fold removed it for single-scene-fits-HOME games) MUST be deleted before `compileRom` globs the directory. Mechanism: diff-and-delete at end of `@TaskAction`, applied via a shared helper to both v1 and v2 paths.
- **Deliverable 2 — ROM-build smoke recipe + verifier gate.** Add a `buildRom` integration test in `gbkt-gradle-plugin/.../IntegrationTest.kt` that exercises `simple-physics` end-to-end (skipped gracefully when GBDK is unavailable). Wire it into the gsd-verifier as a phase-level gate that fires automatically whenever a phase touches codegen-pipeline paths (via a maintained glob list in `.planning/verifier-gates.md`). Failure = BLOCKER finding in `*-VERIFICATION.md`, phase status `gaps_found`.

**Out of scope:**
- Per-file `@OutputFile` declarations on `GenerateCTask` (rejected — file set is dynamic).
- Wipe-then-write semantics that discard incrementality (rejected — diff-and-delete is more conservative).
- Multi-example smoke variants (breakout, all-examples) — surplus per hard scope cap; can be added later if staleness recurs on the MBC5 path.
- Smoke recipe living in `gbkt-test/GbktTestRecipes.kt` + manifest-driven verifier integration — rejected as spanning two systems for no immediate gain.
- Standalone `romSmokeAll` Gradle task — rejected (forces GBDK on every contributor).
- Opt-in smoke gate via phase manifest — rejected (the WHOLE POINT is that 09.1 was wrongly complete because nobody opted in; the gate must be automatic).
- Auto-spawning a `<phase>-SMOKE-GAP.md` stub on failure — defer to planner agent territory.
- Refactor of `BankingConfig` defaults or `BankingAnalysisPass` fast-path (Plan 09.1-06 already locked this; 09.2 does not re-open).
- Promoting any 09.1 deferred items — closed phase.

</domain>

<decisions>
## Implementation Decisions

### Sync mechanism (Deliverable 1)
- **S-01 mechanism:** **Diff-and-delete at end of `@TaskAction`.** Enumerate files currently in `outputDir`, compute `emittedSet` from the pipeline `files.keys` plus the known sidecars, delete anything not in the union. Chosen over per-file `@OutputFile` (file set is dynamic — bank labels and counts vary per game) and over wipe-then-write (would invalidate downstream input fingerprints unnecessarily).
- **S-02 protected set:** **Whitelist + dotfile exemption.** Surviving set = pipeline `files.keys` ∪ {`main.c.gbkt.map` (v1), per-file `*.gbkt.map` (v2), `gbkt-build.properties`, `game_metadata.json`} ∪ anything starting with `.` (defensive against `.gitkeep`, IDE markers).
- **S-03 sync site:** **Shared helper `syncOutputDir(outputDir, emittedSet)` invoked at the END of both `executeV2Path()` and the v1 execute path.** Same contract everywhere — if any path emits to `outputDir`, it syncs.
- **S-04 logging:** **`println("Removed stale: $name")` per deletion at lifecycle level**, matching the existing `Generated: $name` format. The log makes the staleness bug self-evident in build output; negligible noise for the common 0-stale case. Rejected the silent variant because it would mask future regressions.

### Smoke recipe shape (Deliverable 2 — test)
- **K-01 location:** **Gradle-plugin TestKit integration test.** Extend `gbkt-gradle-plugin/src/test/kotlin/io/github/gbkt/gradle/IntegrationTest.kt` (the existing GradleRunner-based `buildRom` fixture at line 115 is the skeleton). Same module as the bug fix; same CI run that exercises the rest of plugin-tier behavior.
- **K-02 example set:** **`simple-physics` only.** It IS the bug surface. Tightest signal-to-cost ratio; one ROM build per test run. Other examples are still covered by the existing D-04 multi-example `buildRom` smoke when humans run it.
- **K-03 GBDK gating:** **Graceful skip via `@EnabledIfEnvironmentVariable(named = "GBDK_HOME", matches = ".+")` or `Assumptions.assumeTrue(gbdkFound)`.** Same pattern as `EmulatorTestTaskTest`. Test reports SKIPPED on machines without GBDK; CI machines that DO have it run it for real. Mock `lcc` rejected — it cannot validate the link-error class that 09.1 missed.
- **K-04 pass bar:** **`result.task(":buildRom")?.outcome == SUCCESS` AND `simple-physics.gb` exists at `build/gbkt/output/`.** Two assertions. Catches the actual bug class (link failure surfaces as `buildRom` FAILED). Byte-level invariants (`0x0147 == 0x00`, size caps) are left to `MbcTypeProbeTest` — no duplication.

### Staleness regression test (Deliverable 2 — focused regression)
- **R-01 layering:** **Both — unit test on `syncOutputDir` helper AND Gradle TestKit double-build via GradleRunner.** Two layers. The unit test is fast and locks the helper contract independently of `@TaskAction` wiring; the TestKit test exercises end-to-end wiring.
- **R-02 repro strategy:** **Hand-staged stale file.** In the TestKit test: (1) synthetic gbkt project that emits 1 file; (2) manually write a stub `bank1.c` to `outputDir` BEFORE running generateC; (3) run generateC via GradleRunner; (4) assert `bank1.c` is gone. Deterministic; doesn't depend on banking-config-flip semantics that could shift in future plans.
- **R-03 test locale:** **Two new files.** Unit-tier → new `OutputDirSyncTest.kt` in `gbkt-gradle-plugin/src/test/kotlin/io/github/gbkt/gradle/tasks/`. Integration-tier → new `@Test` methods appended to existing `IntegrationTest.kt` (covers both the Area-3 double-build AND the Area-2 smoke). Convention-compliant — integration tests live in `IntegrationTest.kt` by name; unit tests live alongside the task they cover.
- **R-04 edge coverage:** **Six unit-tier `@Test` cases on the helper:**
  1. Basic — stale file is deleted, emitted file survives.
  2. Dotfile exemption — `.gitkeep` survives even when not in `emittedSet`.
  3. Sidecar whitelist — `gbkt-build.properties` survives even when not in the pipeline `files` map.
  4. Idempotency — calling sync twice on the same state is a no-op (no errors, no spurious deletions).
  5. Read-only file failure mode — what does sync do if `delete()` returns false? (Pick: skip with warning, or fail the task; planner picks the friendlier option but locks the choice with a test.)
  6. Missing `outputDir` — does sync create it, skip silently, or crash? (Pick the safest default and lock it.)

### Verifier-gate trigger (Deliverable 2 — gate semantics)
- **V-01 trigger:** **Touched-path heuristic.** gsd-verifier inspects the phase's git diff. If ANY file matches a known codegen-pipeline path glob, the smoke gate fires automatically. Automatic; one place to maintain the rule. Rejected opt-in (the entire phase exists because nobody opted into a build-tier check in 09.1) and always-on (penalizes non-codegen phases for no benefit).
- **V-02 glob list home:** **`.planning/verifier-gates.md`** — a new project-level rule file. Markdown, sectioned by gate (initially just `rom-build`), each path entry has a short comment explaining what it covers. Versioned with the rest of `.planning`, visible in code review, doesn't require touching agent code. Initial path entries should at minimum include: `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/GenerateCTask.kt`, `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/CompileRomTask.kt`, `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt`, `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/visitor/**`, `gbkt-analysis/src/main/kotlin/io/github/gbkt/analysis/passes/BankingAnalysisPass.kt`. Planner expands.
- **V-03 failure blast radius:** **BLOCKER finding in `*-VERIFICATION.md`, phase status = `gaps_found`.** Symmetric with how the verifier treats other BLOCKER truths today. Soft-warning rejected — the phase exists precisely because 09.1 was wrongly marked complete. Phase author runs a gap-closure plan or routes to a new phase via the standard 09.1 pattern.
- **V-04 GBDK-missing behavior on verifier machine:** **SKIPPED row with a structured note that flags the smoke for the next human-UAT loop.** Note text MUST explicitly say: `ROM-build smoke SKIPPED — GBDK not available on verifier machine; human MUST run :gbkt-examples:simple-physics:buildRom locally before sign-off.` Doesn't block the verifier run; the human-UAT loop catches it. Aligns with the existing Human-UAT pattern from 09.1. Silent skip rejected — that IS the 09.1 failure mode.

### Plan ordering recommendation
Suggested by risk-and-blast-radius: **Plan 1 = sync helper + unit tests (smallest, no GBDK dependency, locks the helper contract)**. **Plan 2 = wire helper into `GenerateCTask` v1 + v2 paths + TestKit double-build + smoke recipe + per-deletion log (extends `IntegrationTest.kt`, exercises end-to-end)**. **Plan 3 = verifier-gates.md + gsd-verifier touched-path heuristic + BLOCKER+SKIP semantics**. Planner decides final order and split granularity; this is a recommendation, not a constraint.

### Claude's Discretion
- **TDD ordering** (RED-GREEN-REFACTOR) within each plan — planner picks. The 6 unit-tier `@Test` cases on the helper especially benefit from RED-first authoring.
- **Whether the TestKit double-build test should use `--rerun-tasks`** or a fresh project tmpdir per build — planner picks based on Gradle TestKit ergonomics.
- **Whether to use a real `gbkt-examples:simple-physics` reference via `includeBuild`** for the smoke test, or a synthesized `GameBuilder` fixture — planner picks (real example exercises asset pipeline + DSL discovery; synthesized fixture is faster but less integration-like). Recommendation: synthesized fixture for the staleness test (locks behavior), real example for the smoke (locks end-to-end).
- **`verifier-gates.md` format** — markdown table vs YAML frontmatter + bullet list. Planner picks based on what's easiest for gsd-verifier to parse.
- **Whether 09.2's own verifier run should self-host the new gate** (eat its own dog food) or whether the gate goes live for the NEXT codegen-pipeline phase — planner's call. Self-hosting is the more honest signal but the rule file would have to land before final verifier run.

<specifics>
## Specific Ideas

- **The structural lesson 09.2 makes permanent:** "JVM-tier GREEN ≠ buildRom GREEN". The user-feedback memory said it; 09.1 was wrongly marked complete despite the memory; 09.2 converts the memory into a verifier-enforced gate (V-01 + V-03). After 09.2, future phases CANNOT silently bypass the ROM-build check when they touch codegen-pipeline paths.
- **Phase 09.2 self-hosting is the honest test** of the verifier gate. The phase touches `GenerateCTask.kt` — which IS on the V-02 glob list — so the gate should fire on 09.2's own verifier run, exercise the new TestKit smoke, and (assuming the fix works) report PASS. If the gate goes live ONLY for the NEXT codegen-pipeline phase, 09.2 ships the gate untested in its full pipeline. Planner picks whether self-hosting fits the plan sequencing.
- **The whitelist + dotfile exemption is deliberately generous** (S-02). The risk surface of "deleted something I shouldn't have" exceeds the cost of "left one stale file behind" — the latter shows up as a broken build that the smoke catches; the former is silent data loss. Bias toward leaving files alone unless we're confident they're stale.
- **Six edge cases on the helper is more than 09.1's pattern** (one invariant per fix). The reason: a sync helper has more sharp edges than a one-shot codegen fix (filesystem semantics, whitelist edges, idempotency, error paths). Tightening here pays off because every future codegen phase rides on this code.
- **`simple-physics` is the right smoke example**, not just for its history. It's the only example whose single-scene-fits-HOME emission DIFFERS by file set from the MBC5 emission (one file vs many). The stale-file failure mode is specifically a "file set shrunk" failure; simple-physics is where shrinkage happens.
