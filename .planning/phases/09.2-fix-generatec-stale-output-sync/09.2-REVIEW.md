nits carried forward from the prior review.

## Critical Issues

### CR-01: `emittedSet` lists sidecars unconditionally — failed sidecar writes leave prior-run stale files protected

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/GenerateCTask.kt:321-328` (v1) and `:418-425` (v2)

**Issue:**

Both call sites build `emittedSet` by *intent* rather than by *evidence of write*:

```kotlin
// v1, lines 321-328
val emittedSet = buildSet<String> {
    addAll(files.keys)
    add("main.c.gbkt.map")          // unconditional — but the actual write is in a try-catch
    add("gbkt-build.properties")    // unconditional — but writeBuildMetadata swallows all exceptions
    add("game_metadata.json")       // unconditional — and v1 doesn't even write this file
}
syncOutputDir(outputDir, emittedSet)
```

```kotlin
// v2, lines 418-425
val emittedSet = buildSet<String> {
    addAll(files.keys)
    files.keys.forEach { add("$it.gbkt.map") }   // unconditional — actual write at 399-404 is conditional on sourceMapJson != null
    add("gbkt-build.properties")                 // unconditional — writeBuildMetadata at 410 wrapped in silent try-catch
    add("game_metadata.json")                    // unconditional (likely written inside `files` for v2, but listed defensively)
}
syncOutputDir(outputDir, emittedSet)
```

Now trace the failure mode for v1's source map:

1. Build N completes successfully → `build/gbkt/generated/main.c.gbkt.map` describes build N's
   line mappings. Good.
2. Build N+1: the v1 codegen runs, `files.keys` updates, but the `try { ... }` at lines
   285-308 throws (any reason: reflection mismatch from a refactor, GBDKCodeGenerator
   constructor signature change, OutOfMemoryError during JSON serialization, etc.). The
   `catch` at line 302-307 logs `"WARNING: Source map not generated"` and continues —
   **the file `main.c.gbkt.map` is NOT rewritten this run**.
3. The unconditional `add("main.c.gbkt.map")` at line 324 means `isProtected("main.c.gbkt.map",
   emittedSet)` returns `true`, so `syncOutputDir` does NOT delete it.
4. `lcc` compilation runs against build N+1's C output. Errors flow through
   `SourceMapLoader.kt` + `ErrorEnhancer.kt`. The loader reads the **stale** map from build N
   and confidently maps `bank0.c:142` to whatever Kotlin line that *used to* correspond to in
   build N — likely garbage in build N+1.

The same pattern repeats for `gbkt-build.properties` (silently caught at
`writeBuildMetadata` lines 538-540) and for `game_metadata.json` (v1 doesn't write it but
adds it to emittedSet, so a hand-placed or leftover file persists; v2 presumably writes it
via `files.keys` from `GBDKPipelineV2.buildMetadataFile()` but the defensive `add(...)` is
still write-blind).

This is **the same class of bug as the original CR-01** (stale sidecars survive across runs
and misroute downstream tooling), just one indirection deeper. The headline CR-01 fix locks
in the contract "isProtected does not protect map files by suffix"; this finding shows the
contract "emittedSet reflects what was actually emitted this run" is broken at both call
sites.

The risk is non-hypothetical: the v1 source-map path goes through extensive reflection
(`Class.forName("io.github.gbkt.backend.gbdk.codegen.GBDKCodeGenerator")`, `getMethod("generateWithSourceMap")`, an unchecked `as Pair<String, Any>` cast at line 293). Any one of those failing on a future refactor lands silently in the catch block, and the next several builds will compile against new C with old maps until someone notices.

**Fix:**

Track each sidecar's actual write outcome and only add to `emittedSet` on success. For v1:

```kotlin
val writtenSidecars = mutableSetOf<String>()

// Source map block — record success
try {
    // ... existing reflection ...
    val sourceMapFile = File(outputDir, "main.c.gbkt.map")
    sourceMapFile.writeText(sourceMapJson)
    writtenSidecars += "main.c.gbkt.map"
    println("Generated source map: ${sourceMapFile.absolutePath}")
} catch (e: Exception) {
    System.err.println("WARNING: Source map not generated: ${e.message}")
    System.err.println("WARNING: Compiler errors will reference C line numbers, not Kotlin source.")
}

// Build metadata — change writeBuildMetadata to return Boolean (true if written)
if (writeBuildMetadata(game, outputDir)) {
    writtenSidecars += "gbkt-build.properties"
}

// game_metadata.json — v1 doesn't write this; drop the unconditional add.
// If a future v1 path emits it, follow the same pattern.

val emittedSet = files.keys + writtenSidecars
syncOutputDir(outputDir, emittedSet)
```

And symmetrically for v2 (track the conditional `sourceMapJson != null` branch inside the
`files.forEach` loop). Update `writeBuildMetadata` to return `true` on success / `false` on
the silent-skip paths (the `return` at line 494, the `return` at line 502, the catch at line
538).

Alternatively — and probably cleaner long term — push the sidecar manifest into the codegen
result itself: `GenerationResult` already carries `files`; add a `writtenSidecars: Set<String>`
field that the codegen populates. The Gradle task then just calls
`syncOutputDir(outputDir, files.keys + result.writtenSidecars)` with no enumeration in the
plugin at all. That eliminates the "two-place-truth" smell flagged in WR-04 of the prior
review.

Add a regression test:

```kotlin
@Test
fun `sidecar not written this run does not protect prior-run stale copy`() {
    // Simulate: build N wrote main.c + main.c.gbkt.map
    File(outputDir, "main.c").writeText("// new build\n")
    File(outputDir, "main.c.gbkt.map").writeText("{\"stale\": true}\n")

    // Build N+1: main.c was rewritten but source-map generation FAILED this run.
    // emittedSet must NOT include "main.c.gbkt.map".
    val deleted = syncOutputDir(outputDir, setOf("main.c"))

    assertFalse(
        File(outputDir, "main.c.gbkt.map").exists(),
        "Stale sidecar from prior build must be deleted when this run did not write a new one"
    )
    assertEquals(listOf("main.c.gbkt.map"), deleted)
}
```

## Warnings

### WR-01: `SIDECAR_WHITELIST` asymmetrically defends v1's source map but not v2's per-file maps

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/GenerateCTask.kt:679-690`

**Issue:**

The whitelist contains `"main.c.gbkt.map"` and its doc comment explains the intent as
"defensive single-source-of-truth so a future call-site refactor cannot accidentally drop
the v1 source map." Fine. But this defense is asymmetric:

- v1 path emits exactly one map (`main.c.gbkt.map`) → defended in `SIDECAR_WHITELIST`.
- v2 path emits N per-file maps (`main.c.gbkt.map`, `bank1.c.gbkt.map`, ...) → defended
  ONLY by the call site's `files.keys.forEach { add("$it.gbkt.map") }`. If a refactor breaks
  the v2 call site (the very scenario the v1 defense was added for), the v2 maps are deleted
  and ROM debugging breaks.

The asymmetry is acknowledged in the doc comment ("The v2 path enumerates per-file maps
dynamically ... and does NOT rely on this whitelist for any specific map file") but no
rationale is given for why v1 deserves defense-in-depth while v2 does not. Both paths
have the same risk surface: a future refactor that drops the sidecar enumeration leaves
downstream tooling pointed at stale maps.

This becomes more pointed once CR-01 is fixed: with sidecars tracked from actual write
outcomes, the v1 whitelist entry for `main.c.gbkt.map` should be deleted entirely
(otherwise CR-01's "stale survives when write fails" reappears via the whitelist clause).

**Fix:**

Either (a) drop `"main.c.gbkt.map"` from `SIDECAR_WHITELIST` as part of the CR-01 fix —
when each call site tracks actual writes, the whitelist's defense-in-depth becomes the
exact bug it was trying to prevent; or (b) generalize the defense — change the codegen
contract to return its sidecar manifest, so the plugin doesn't need to know what files
exist at all.

### Round 3 Findings

#### New Findings in Plan 05 Scope

##### WARNING WR-05: `writtenSidecars` tracking for `gbkt-build.properties` is logically bypassed by `SIDECAR_WHITELIST`

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/GenerateCTask.kt:314-316` (v1) and `:411-414` (v2); `SIDECAR_WHITELIST` at `:694-697`

**Issue:**

Plan 05's stated objective includes making the `gbkt-build.properties` emission write-outcome-aware by gating `writtenSidecars += "gbkt-build.properties"` on `writeBuildMetadata`'s Boolean return value. The code correctly does this at both call sites. However, `gbkt-build.properties` is simultaneously listed in `SIDECAR_WHITELIST` (line 695), and `isProtected` checks the whitelist independently of `emittedSet`:

```kotlin
private fun isProtected(name: String, emittedSet: Set<String>): Boolean =
    name in emittedSet ||
        name in SIDECAR_WHITELIST ||  // <-- fires regardless of writtenSidecars
        name.startsWith(".")
```

This means `isProtected("gbkt-build.properties", emittedSet)` returns `true` whether or not `writeBuildMetadata` succeeded — the whitelist short-circuits the write-outcome check. A stale `gbkt-build.properties` from a prior run (e.g., with a different cartridge type) will survive a build where `writeBuildMetadata` returns `false`, because the whitelist protects it before the `emittedSet` check even matters for this specific file.

The net result: the write-outcome-aware tracking for `gbkt-build.properties` at both call sites is effective only for `emittedSet` completeness but has no effect on deletion behavior for that specific file. The `SIDECAR_WHITELIST` KDoc explicitly acknowledges this intent ("tolerated when missing this run"), so this is a design choice, not an inadvertent gap. However, it means plan 05's claim that "both v1 and v2 paths are now write-outcome-aware" is overstated: the fix is fully write-outcome-aware for `*.gbkt.map` files, but `gbkt-build.properties` remains always-protected regardless of write outcome.

This was pre-existing behavior before plan 05 (the whitelist already protected `gbkt-build.properties` in rounds 1+2). Plan 05 does not introduce a regression; it adds tracking on top of the whitelist without changing the net deletion behavior for this file.

**Practical risk:** If `writeBuildMetadata` fails silently (e.g., the v1 `Game` class lacks `getConfig`), a prior-run `gbkt-build.properties` with stale cartridge metadata survives. `CompileRomTask` reads this file to determine MBC type and GBC flags. A stale cartridge type could cause the wrong GBDK `-Wm-yt` flag to be passed to `lcc`, silently producing a ROM with the wrong cartridge header. This is the same class of symptom as the original CR-01 (stale file misroutes downstream tooling), though limited to the cartridge-metadata path rather than the source-map path.

**Fix:**

Remove `"gbkt-build.properties"` from `SIDECAR_WHITELIST` and rely entirely on `writtenSidecars` tracking to protect it. This is symmetric with the treatment of `*.gbkt.map` files after plan 05. If removing it from the whitelist is considered too aggressive (breaking compatibility with older output dirs), at minimum update the KDoc of `SIDECAR_WHITELIST` to acknowledge that `gbkt-build.properties` protection is currently unconditional regardless of write outcome, so future maintainers understand the design intent is tolerance, not write-outcome-awareness.
