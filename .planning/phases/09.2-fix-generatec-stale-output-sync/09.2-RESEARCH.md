## Summary

Phase 09.2 closes a structural gap exposed during Phase 09.1 closeout (2026-05-15): `GenerateCTask`
writes the file set the pipeline emits but never deletes files dropped from that set, so a clean
`./gradlew :gbkt-examples:simple-physics:buildRom` after Plan 09.1-05's `allScenesInHome` fold
re-linked a stale `bank1.c` from a previous MBC5 build and produced duplicate
`_play_enter`/`_play_frame` symbol errors. The 09.1 verifier passed 15/15 truths because it only
exercised JVM-tier invariants — the on-disk `build/gbkt/generated/` directory was never inspected.

The phase ships two deliverables, both already specified by CONTEXT.md and not subject to
re-derivation here:

1. **GenerateCTask output sync** — a shared `syncOutputDir(outputDir, emittedSet)` helper invoked
   at the end of both `executeV2Path()` and the v1 execute path, applying diff-and-delete with a
   whitelist + dotfile exemption. Per-deletion log: `println("Removed stale: $name")` matching the
   existing `Generated: $name` style.
2. **ROM-build smoke recipe + verifier gate** — a `simple-physics` `buildRom` test in
   `IntegrationTest.kt` (GBDK-gated via `@EnabledIfEnvironmentVariable`), plus a new
   `.planning/verifier-gates.md` rule file that the gsd-verifier reads to fire the smoke
   automatically whenever the phase's git diff touches codegen-pipeline paths. Failure becomes a
   BLOCKER truth in `*-VERIFICATION.md`; missing GBDK becomes a SKIPPED row whose note flags the
   smoke for the next human-UAT loop.

**Primary recommendation:** Plan in three slices per CONTEXT.md's recommended ordering (sync
helper + 6 unit-tier @Test cases → wire into GenerateCTask v1/v2 paths + TestKit double-build +
smoke recipe + per-deletion log → verifier-gates.md schema + gsd-verifier touched-path heuristic +
BLOCKER/SKIP semantics). Use the existing TestKit GradleRunner fixture in `IntegrationTest.kt`
(synthesized minimal-game project) for the staleness test; use a tmpdir + plain `buildRom`
invocation for the smoke (the existing `end-to-end game compiles to ROM when GBDK is available`
test at line 121 is the template — extend with `result.task(":buildRom")?.outcome == SUCCESS`
assertion and `simple-physics.gb`-style ROM-file existence check). Verifier wiring goes into
`$HOME/.claude/get-shit-done/workflows/verify-phase.md` between `behavioral_verification` and
`scan_antipatterns` as a new `step name="build_smoke_gates"`.

## Domain Background

### The staleness failure mode

`GenerateCTask` declares `outputDir` as a `@get:OutputDirectory` (line 49) and runs inside a
`GenerateCWorkAction` with classloader isolation (line 132-153). For each file the pipeline emits,
the worker writes via `outputFile.writeText(content)` — explicitly visible at:

| Path | Loop | Loop body |
|------|------|-----------|
| v1 path | GenerateCTask.kt lines 277-282 | `files.forEach { (filename, content) -> outputFile.writeText(content); println("Generated: $filename (...)") }` |
| v2 path | GenerateCTask.kt lines 383-396 | Same shape, also writes `${filename}.gbkt.map` per file when source map JSON is available |

**Critical gap:** neither loop deletes anything. When the pipeline's file set shrinks
(`bank1.c` folded into `main.c` for single-scene-fits-HOME games per Plan 09.1-05), the old
`bank1.c` from the previous build remains on disk. `CompileRomTask` then globs the directory and
hands the stale file to `lcc`, which produces duplicate-symbol link errors against the symbols
also present in the new `main.c`.

### The 09.1 closeout incident

On 2026-05-15 the 09.1 verifier passed 15/15 truths and re-verification PASSED (see
`.planning/phases/09.1-simple-physics-surplus-codegen-defects-inserted/09.1-VERIFICATION.md`).
The user then ran a clean `./gradlew :gbkt-examples:simple-physics:buildRom` and it FAILED with
duplicate `_play_enter` / `_play_frame` link errors. The 15 verified truths covered:
- BankingAnalysisPass invariants (truths 9, 10, 14, 15 — JVM-tier @Test cases)
- GBDKPipelineV2 fold contract (truth 13 — ROM byte probe via `od`, but ONLY the byte at
  0x0147, not the link state)
- MbcTypeProbeTest assertions (truth 11 — 8 @Test functions)
- D-04 multi-example smoke (truth 12 — "7/10 build successfully; 3 pre-existing SDCC-91")

The D-04 smoke at truth 12 SHOULD have caught it. Why didn't it? Because Plan 05's smoke ran the
multi-example sweep AFTER its own clean — it never hit the staleness condition. Staleness is
reachable only when a build runs with the OLD emission set still on disk and then re-runs with
the NEW (shrunk) emission set without a `clean` in between. The 09.1 smoke order accidentally
masked the bug it was supposed to surface.

### Why JVM-tier verification missed it

Per Plan 09.1's D-03 doctrine (`Done signal = JVM-tier invariant per fix`), each fix landed a
JVM-tier @Test that locked the in-process output. The pipeline returns a `Map<String, String>` of
filename → content; the JVM tests assert against this in-memory map. They have ZERO visibility
into `build/gbkt/generated/` on disk. The disk state can drift arbitrarily (stale files, partial
writes, manual edits) and no JVM test fires.

The structural lesson — **"JVM-tier GREEN ≠ buildRom GREEN"** — was already captured in the
user-memory file `feedback_rom_build_smoke_test_for_codegen_phases.md` (which says: "the verifier
MUST run a clean `:gbkt-examples:<game>:buildRom` before declaring the phase complete"). 09.1
shipped 15/15 GREEN with a broken `buildRom`. The memory was not enforced. **09.2 converts the
memory into a verifier-enforced gate via V-01 + V-03.**

## Technical Architecture

### Sync helper API surface

**Signature (recommended):**

```kotlin
/**
 * Reconcile [outputDir] to exactly [emittedSet]. Files present in [outputDir] but absent
 * from [emittedSet] are deleted; surviving sidecars (whitelisted) and dotfiles are exempt.
 *
 * Lifecycle log: `Removed stale: $name` per deletion.
 *
 * @return List of deleted filenames (may be empty).
 */
internal fun syncOutputDir(outputDir: File, emittedSet: Set<String>): List<String>
```

**Whitelist (S-02):**

```kotlin
private val SIDECAR_WHITELIST = setOf(
    "main.c.gbkt.map",         // v1 source map (single file)
    "gbkt-build.properties",   // build metadata read by CompileRomTask
    "game_metadata.json",      // emulator/agent metadata
    // v2 per-file source maps match the pattern `*.gbkt.map` and are protected via:
    //   filename.endsWith(".gbkt.map") || filename.startsWith(".")
)

private fun isProtected(name: String, emittedSet: Set<String>): Boolean =
    name in emittedSet ||
    name in SIDECAR_WHITELIST ||
    name.endsWith(".gbkt.map") ||  // v2 sidecars (per filename pattern)
    name.startsWith(".")           // .gitkeep, IDE markers
```

**Location (S-03):** Place as a top-level private function in `GenerateCTask.kt` immediately
after `GenerateCWorkAction.execute()`. Both `executeV2Path()` and the v1 path execute inside the
worker, so the helper is reachable from both sites via the file's package scope. Alternative:
nest as `private fun` on `GenerateCWorkAction`. Either works; top-level is preferred because
unit tests (R-04) can call it without instantiating the worker.

**Insertion sites (S-03):**

| Path | Insertion point | Existing line |
|------|----------------|---------------|
| v1 | After line 313 (`println("Generated ${files.size} C files (...)")` ) AND after `writeBuildMetadata()` on line 311 — both write to outputDir. The helper goes after `runAssetOptimization()` on line 319 to ensure all writes are complete. | The cleanest insertion is AFTER line 318 (`runAssetOptimization()` call) but BEFORE the closing `}` of the try block on line 320. |
| v2 | After line 407 (`println("Output directory: ${outputDir.absolutePath}")` ). The v2 path's last write is the metadata try block on lines 400-404. | Insert helper call as line 408 (before the final implicit return). |

**emittedSet construction:**

```kotlin
// v1 path — after the writes complete:
val emittedSet = buildSet<String> {
    addAll(files.keys)             // C files from pipeline
    add("main.c.gbkt.map")         // v1 source map
    add("gbkt-build.properties")   // build metadata
    add("game_metadata.json")      // emulator metadata (if pipeline emits it)
}
syncOutputDir(outputDir, emittedSet)

// v2 path — same shape:
val emittedSet = buildSet<String> {
    addAll(files.keys)
    files.keys.forEach { add("$it.gbkt.map") }  // per-file sidecars
    add("gbkt-build.properties")
    add("game_metadata.json")
}
syncOutputDir(outputDir, emittedSet)
```

The dotfile exemption + `.gbkt.map`-suffix check inside `isProtected()` means the planner does
not have to enumerate every per-file map explicitly. Belt-and-suspenders: add them to
`emittedSet` anyway so the log message in `isProtected = false` cases doesn't surprise a
reviewer.

### `@CacheableTask` interaction

`GenerateCTask` is annotated `@CacheableTask` (line 32) and declares `outputDir` as
`@get:OutputDirectory` (line 49). Gradle's `@OutputDirectory` semantics:

- The directory is tracked as a build output for incremental builds and the build cache.
- Gradle records a fingerprint of the directory contents at task end.
- On subsequent runs, if inputs are unchanged AND the cached output snapshot matches, the task
  is marked UP-TO-DATE and the cached directory is restored.

**Diff-and-delete safety:** The helper runs at the END of `@TaskAction`, AFTER all `writeText`
calls complete and BEFORE Gradle snapshots the directory. Deletion is a normal filesystem
operation; Gradle's output snapshot is computed AFTER `@TaskAction` returns. The snapshot
correctly reflects the post-sync state.

**Cache restore safety:** When Gradle restores a cached output, it writes the snapshot's exact
file set into the directory. If a stale file existed pre-restore, Gradle DOES delete it as part
of `Restoring cached output`. This is documented Gradle behavior — the build cache is
authoritative for `@OutputDirectory` contents.

**The case that staleness actually reaches:** Local (non-cached) builds without `clean`. The
build cache lookup misses (because the build classpath, source files, or `gameSpec` changed in a
way that invalidated the input fingerprint), the task re-runs, the new file set is written, and
no one cleans up the dropped files. This is exactly the case S-01 fixes.

**Citation:** Gradle 9.0 `@OutputDirectory` contract is documented at
<https://docs.gradle.org/current/userguide/incremental_build.html#sec:task_outputs> [CITED:
docs.gradle.org/current/userguide/incremental_build.html]. The diff-and-delete pattern is
specifically called out as the safe approach when the file set is dynamic (vs. the
`@OutputFiles` collection registration approach that requires knowing files at configuration
time).

**Recommended belt: `outputs.upToDateWhen { false }` is NOT required.** The helper preserves
incrementality because the input fingerprint hasn't changed — Gradle's cache key is computed
from `@Input`s, `@Classpath`, and `@InputDirectory`. Deletion at end-of-action doesn't affect
those.

## Implementation Patterns

### TestKit double-build pattern (R-02)

Existing pattern in `IntegrationTest.kt`. The structural setup is at lines 29-60 (`@TempDir` +
`settingsFile.writeText(...)`) and each test calls `createMinimalGameFixture()` /
`createBasicBuildFile()` / `GradleRunner.create().withProjectDir(testProjectDir).withArguments(...).build()`.

**Recommended pattern for the staleness regression:**

```kotlin
@Test
fun `generateC deletes stale files dropped from the emission set`() {
    createMinimalGameFixture()
    createBasicBuildFile()

    // Pre-stage a stale bank1.c in the output directory BEFORE the first generateC
    // (simulates the 09.1 failure mode: previous build emitted bank1.c, current build does not)
    val outputDir = File(testProjectDir, "build/gbkt/generated")
    outputDir.mkdirs()
    val staleBank1 = File(outputDir, "bank1.c")
    staleBank1.writeText("// stale content from prior build — must be deleted by sync\n")

    val result =
        GradleRunner.create()
            .withProjectDir(testProjectDir)
            .withArguments("generateC", "--stacktrace")
            .withPluginClasspath()
            .build()

    assertEquals(TaskOutcome.SUCCESS, result.task(":generateC")?.outcome)
    assertFalse(staleBank1.exists(), "stale bank1.c should be deleted by syncOutputDir")
    assertTrue(
        result.output.contains("Removed stale: bank1.c"),
        "S-04 lifecycle log must announce the deletion",
    )
}
```

**`--rerun-tasks` vs fresh tmpdir:** Use a **fresh tmpdir per test** (the `@TempDir` already
does this). This is simpler than `--rerun-tasks` and avoids interaction with Gradle's build
cache. `@TempDir` is per-test via JUnit5 lifecycle — each test gets its own clean directory by
default. The hand-staged `bank1.c` is the only "previous build artifact" the test needs.

**Why not `--rerun-tasks`:** It forces re-execution but does NOT clear `@OutputDirectory`
contents. Stale files would persist. The hand-staged approach gives precise control over the
pre-state.

## Verifier-Gate Wiring

### Where gsd-verifier behavior lives

**Location:** `$HOME/.claude/get-shit-done/workflows/verify-phase.md`. This is the workflow file
executed by `/gsd:verify-phase`. It is NOT a `.claude/agents/*.md` file (the agents directory at
`$HOME/.claude/get-shit-done/agents/` is empty) and NOT a `.claude/skills/*/SKILL.md`. CONTEXT.md
guessed `.claude/skills/gsd-ns-review/` — incorrect; the actual home is the workflows dir.

**The verifier behavior is encoded as a sequence of `<step name="...">` blocks**, executed in
order by `/gsd:verify-phase`. Confirmed steps (in order):

1. `load_context` — reads phase dir, ROADMAP entry, requirements, all milestone phases
2. `establish_must_haves` — pulls truths/artifacts/key_links from PLAN frontmatter OR Success Criteria OR derived from goal
3. `verify_truths` — each truth gets ✓ VERIFIED / ✗ FAILED / ? UNCERTAIN
4. `verify_artifacts` — Levels 1–3 (exists, substantive, wired)
5. `verify_wiring` — key-link verification via `gsd-sdk query verify.key-links`
6. `verify_requirements` — REQ-IDs from REQUIREMENTS.md
7. `verify_decisions` — non-blocking warning gate (CONTEXT decisions vs shipped artifacts)
8. `behavioral_verification` — runs project test suite via auto-detected command (gradle/just/make/etc.)
9. `scan_antipatterns` — grep for TBD/FIXME/XXX without issue references
10. `audit_test_quality` — disabled tests, circular tests, assertion strength
11. `identify_human_verification` — surface Human-UAT items
12. `determine_status` — `passed` / `gaps_found` / `human_needed`
13. `filter_deferred_items` — defer gaps that match later-phase scope
14. `generate_fix_plans` — fix plans per cluster if gaps_found
15. `create_report` — write `*-VERIFICATION.md`
16. `return_to_orchestrator` — emit status

### Wiring site for V-01 / V-03 / V-04

**Insert as a NEW step between `behavioral_verification` and `scan_antipatterns`.** Suggested
name: `step name="build_smoke_gates"`.

**Why this position:** `behavioral_verification` already runs the project test suite (auto-resolves to `./gradlew test` or similar). The smoke gate is the SAME class of evidence (runtime, not static) but conditional on a touched-path trigger — it belongs immediately after the unconditional test run, before the static anti-pattern scan.

**Pseudocode for the new step:**

```markdown
<step name="build_smoke_gates">
**Touched-path gate evaluation.**

Skip if `.planning/verifier-gates.md` does not exist (project hasn't adopted the gate yet) or
if `workflow.build_smoke_gates` is explicitly `false`.

1. Read `.planning/verifier-gates.md` — parse gate definitions (initial gate: `rom-build`).
2. Compute the phase's diff path set:
   ```bash
   PHASE_BASE=$(gsd-sdk query phase.base-commit "${phase_number}")  # commit at phase creation
   PHASE_FILES=$(git diff --name-only "${PHASE_BASE}..HEAD")
   ```
3. For each gate: glob-match each PHASE_FILE against the gate's path list.
4. On match → invoke the gate's smoke command. For `rom-build`:
   ```bash
   timeout 600 ./gradlew :gbkt-examples:simple-physics:clean :gbkt-examples:simple-physics:buildRom 2>&1
   ```
5. Record outcome:
   - **Exit 0** → ✓ PASS row in VERIFICATION.md "Build Smoke Gates" table.
   - **Exit non-zero** → ✗ BLOCKER row; append to gaps; phase status downgrades to `gaps_found`.
   - **GBDK not available** (`GBDK_HOME` unset or `lcc` missing) → ⊘ SKIPPED row with
     structured note: `ROM-build smoke SKIPPED — GBDK not available on verifier machine; human
     MUST run :gbkt-examples:simple-physics:buildRom locally before sign-off.` Does NOT block;
     human-UAT loop catches it.

6. Append the table to VERIFICATION.md under a new section:
   ```markdown
   ### Build Smoke Gates

   | Gate | Trigger | Outcome | Evidence |
   |------|---------|---------|----------|
   | rom-build | GenerateCTask.kt modified | ✓ PASS | `./gradlew :gbkt-examples:simple-physics:clean :gbkt-examples:simple-physics:buildRom` exit 0 |
   ```
</step>
```

### V-02 schema recommendation: markdown table

The verifier reads multiple `.planning/*.md` files today (ROADMAP, REQUIREMENTS, STATE,
CONTEXT, VERIFICATION, HUMAN-UAT). All are markdown with structured tables or sectioned
headings. No `.planning/` file is currently YAML-fronted with bullet-list bodies.

**Existing markdown-table parse precedent:** verify-phase.md already greps REQUIREMENTS.md with
patterns like `grep -E "^| ${phase_number}" .planning/REQUIREMENTS.md`. A markdown table is the
path of least new parsing code.

**Recommended schema for `.planning/verifier-gates.md`:**

```markdown

Project-level gates the gsd-verifier runs automatically when a phase's diff touches matching
paths. Each gate has a name, a trigger path list, and a smoke command.

## Gate: rom-build

**Purpose:** Catch codegen-pipeline regressions that JVM-tier tests cannot see — staleness in
`build/gbkt/generated/`, link errors against dropped bank files, MBC byte drift, etc. See
Phase 09.1 closeout incident for the precedent failure mode.

**Trigger paths (any match fires the gate):**

| Path glob | Reason |
|-----------|--------|
| `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/GenerateCTask.kt` | Owns the file-emission write loop |
| `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/CompileRomTask.kt` | Owns the lcc invocation + MBC upgrade logic |
| `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt` | Owns the file-set decision (fold or split) |
| `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/visitor/**` | Any visitor change can shift emission shape |
| `gbkt-analysis/src/main/kotlin/io/github/gbkt/analysis/passes/BankingAnalysisPass.kt` | Owns the bank-assignment fast-path |

**Smoke command:**

```bash
./gradlew :gbkt-examples:simple-physics:clean :gbkt-examples:simple-physics:buildRom
```

**Pass criteria:** Exit code 0 AND `gbkt-examples/simple-physics/build/gbkt/output/simple-physics.gb` exists with size > 0.

**Skip behavior:** When `GBDK_HOME` is unset or `lcc` is not on `PATH`, mark the gate SKIPPED
with the structured note `ROM-build smoke SKIPPED — GBDK not available on verifier machine;
human MUST run :gbkt-examples:simple-physics:buildRom locally before sign-off.`
```

**Why markdown table over YAML frontmatter + bullet list:**

1. The verifier already parses markdown tables (REQUIREMENTS.md, ROADMAP.md). YAML frontmatter
   would require pulling a YAML parser into the verifier's grep-based toolchain.
2. Code review of `.planning/verifier-gates.md` reads naturally — each glob row has its
   "Reason" cell explaining WHY the gate fires for that file.
3. Multiple gates (rom-build today, possibly future `webExport-smoke`, `intellij-plugin-smoke`)
   each get their own `## Gate: <name>` section with the same shape — discoverable, paste-able.

**Why NOT YAML frontmatter:** YAML would force every gate's globs into a flat list with no
inline rationale, making future drift (e.g., adding `LocalizationPipeline.kt` later) less
self-documenting.

### Anti-patterns to avoid

- **Don't wipe-then-write.** S-01 explicitly rejected this — it invalidates downstream input
  fingerprints (CompileRomTask globs the dir; wiping forces re-glob even when content is
  identical) and is irreversibly destructive on bugs in the helper.
- **Don't move the sync to a separate Gradle task.** A dedicated `syncOutputDir` task would
  need its own `@TaskAction`, dependency wiring, lifecycle. The helper inside `@TaskAction`
  composes with the existing emission and respects Gradle's incremental contract.
- **Don't reference real `:gbkt-examples:simple-physics` directly from the smoke test via
  `withProjectDir(File("gbkt-examples/simple-physics"))`.** Breaks TestKit's hermeticity and
  ties the test to the project layout. Use a synthesized fixture inside `@TempDir`.
- **Don't use `Runtime.getRuntime().exec("./gradlew ...")`** from the smoke test. TestKit's
  `GradleRunner` is the correct integration boundary — it spawns a Gradle daemon, captures
  output, returns `TaskOutcome`. Direct `exec` bypasses all of that.
- **Don't grep stdout for "Removed stale:" as the SOLE assertion that the helper ran.** Assert
  the file is gone first (`assertFalse(staleBank1.exists())`); the log assertion is secondary
  confirmation that the lifecycle log shape is right.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Directory enumeration | `outputDir.walk().toList()` | `outputDir.listFiles()?.filter { it.isFile }` | `walk()` recurses; the helper only cares about top-level files. Recursing risks deleting nested generated trees (e.g., processed-assets) the planner forgot to whitelist. |
| Atomic delete | `Files.delete(path)` + try/catch | `File.delete()` returning Boolean | The R-04 case 5 (read-only failure mode) requires inspecting the return value to decide warn-vs-fail. `Files.delete` throws; `File.delete` returns false on failure — easier to test. |
| Glob matching in the verifier-gates step | Hand-rolled string `startsWith()` / `contains()` | Java `PathMatcher` (`FileSystems.getDefault().getPathMatcher("glob:...")`) | Handles `**`, `?`, `[...]` correctly per POSIX glob semantics. The V-02 glob list uses `**` (visitor directory) — must match correctly. |
| Git diff path enumeration in the verifier-gates step | Parsing `git diff` output line-by-line | `git diff --name-only "${PHASE_BASE}..HEAD"` | Returns a clean newline-separated path list; trivially split into a `List<String>`. |
| TestKit fixture authoring | Inline `buildFile.writeText("plugins { ... }")` per test | The existing `createBasicBuildFile()` + `createMinimalGameFixture()` helpers in IntegrationTest.kt | The factory pattern is already established (5 fixture helpers); add `createSimplePhysicsLikeFixture()` to match. |

## Common Pitfalls

### Pitfall 1: `outputDir.listFiles()` returns null when dir doesn't exist
**What goes wrong:** R-04 case 6 (missing outputDir) — `listFiles()` returns `null` on a
non-existent or non-readable directory.
**Why it happens:** Java `File.listFiles()` contract — returns null instead of throwing.
**How to avoid:** `outputDir.listFiles()?.filter { ... } ?: emptyList()`. The helper should
handle the null case as a no-op (no files to sync ≠ error).
**Warning signs:** R-04 case 6's @Test exercises this directly.

### Pitfall 2: `File.delete()` silently fails on locked / read-only files
**What goes wrong:** R-04 case 5 (read-only failure mode) — delete returns false, file remains.
**Why it happens:** OS file lock, permissions, antivirus on Windows. Java doesn't throw.
**How to avoid:** Inspect return value; emit `println("WARNING: Could not delete stale: $name
— file may be locked or read-only")`. CONTEXT.md says "planner picks the friendlier option but
locks the choice with a test" — recommend warn-and-continue over fail-the-task. Bias matches
S-02's "deliberately generous" stance.
**Warning signs:** Test asserts the warning message appears in `println` capture.

### Pitfall 3: Sync helper accidentally deletes the `.gradle` lockfiles or `build` cache markers
**What goes wrong:** Future `outputDir` reuse (e.g., a `processed-assets` subdir added to the
same dir).
**Why it happens:** Dotfile exemption ONLY covers files starting with `.`; subdirectories named
without a leading dot would be enumerated by `listFiles()`.
**How to avoid:** The helper MUST filter `it.isFile` before considering for deletion — never
delete a subdirectory. The `OutputDirSyncTest` should have a case asserting that a
sub-directory survives even when not in the whitelist.
**Warning signs:** Subdir disappearing from `build/gbkt/generated/` after a clean build.
(Suggest planner add a 7th case for this, or extend case 2 to also stage a subdir.)

### Pitfall 4: TestKit fixture leaks state between tests
**What goes wrong:** Two tests in `IntegrationTest.kt` share `@TempDir testProjectDir`.
**Why it happens:** This is NOT how JUnit5 `@TempDir` works — each `@Test` gets its own dir by
default when `@TempDir` is on a `lateinit` field with no `factory` configured. Confirmed: the
existing 13 IntegrationTest tests already use the same pattern without leakage.
**How to avoid:** Don't change the `@TempDir` lifecycle.
**Warning signs:** Tests passing individually but failing in sequence.

### Pitfall 5: V-01 touched-path gate fires for unrelated paths
**What goes wrong:** A phase that only edits documentation under `gbkt-backend-gbdk/CLAUDE.md`
matches the `gbkt-backend-gbdk/.../codegen/visitor/**` glob (it doesn't — the glob is
restricted to `src/main/kotlin/...`) but a similarly-broad future glob might.
**Why it happens:** Glob carelessness.
**How to avoid:** Keep V-02 globs anchored to `src/main/kotlin/...` paths. The initial list
already does this.
**Warning signs:** Verifier reports unexpected gate fires; planner needs to tighten the glob.

### Pitfall 6: V-03 BLOCKER finding doesn't propagate into `determine_status`
**What goes wrong:** The new `build_smoke_gates` step records a FAIL but `determine_status`
doesn't know about the new section.
**Why it happens:** `determine_status`'s decision tree explicitly enumerates the truth-shaped
conditions (line 1: "IF any truth FAILED, artifact MISSING/STUB, key link NOT_WIRED, blocker
found...").
**How to avoid:** Plan 3 MUST patch `determine_status` to add a new disjunct: `OR
build_smoke_gates.*.outcome == "FAIL"`. The patch is one line of pseudocode in the workflow
file.
**Warning signs:** Verifier shows ✗ BLOCKER row in the report but exits with status `passed`.

### Sync helper skeleton

```kotlin
// gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/GenerateCTask.kt
// Add as top-level private fun in the same file as GenerateCWorkAction.

/**
 * Reconcile [outputDir] to exactly [emittedSet]. Files in [outputDir] not protected by the
 * whitelist or dotfile exemption are deleted; survivors are silent.
 *
 * Emits `println("Removed stale: $name")` per deletion at lifecycle level (matches the
 * existing `Generated: $name` log style on lines 281, 387).
 *
 * @return List of deleted filenames (empty if no staleness).
 */
internal fun syncOutputDir(outputDir: File, emittedSet: Set<String>): List<String> {
    if (!outputDir.exists() || !outputDir.isDirectory) return emptyList()

    val deleted = mutableListOf<String>()
    outputDir.listFiles()?.filter { it.isFile }?.forEach { file ->
        val name = file.name
        if (isProtected(name, emittedSet)) return@forEach
        if (file.delete()) {
            println("Removed stale: $name")
            deleted += name
        } else {
            println("WARNING: Could not delete stale: $name — file may be locked or read-only")
        }
    }
    return deleted
}

private val SIDECAR_WHITELIST = setOf(
    "main.c.gbkt.map",
    "gbkt-build.properties",
    "game_metadata.json",
)

private fun isProtected(name: String, emittedSet: Set<String>): Boolean =
    name in emittedSet ||
    name in SIDECAR_WHITELIST ||
    name.endsWith(".gbkt.map") ||
    name.startsWith(".")
```

## Open Questions (RESOLVED)

1. **Should `syncOutputDir` be invoked even on the v1 path's source-map exception path?**
   - What we know: v1 source-map generation is wrapped in try/catch (lines 285-308) and skips
     silently if `GBDKCodeGenerator` is unavailable. The sync helper runs AFTER the try block.
   - What's unclear: if `writeBuildMetadata` also fails (try/catch on lines 468-522), does sync
     still need to run?
   - **RESOLVED:** YES — sync always runs. Even when source-map or metadata write fails,
     `files` were written successfully and stale files must be deleted. The sync helper's
     reading of `outputDir.listFiles()` is independent of whether sidecars wrote successfully.

2. **Should the verifier-gates.md schema support per-gate `skip_when` predicates?**
   - What we know: V-04 hardcodes `GBDK_HOME` as the only skip condition.
   - What's unclear: a future gate (e.g., `webExport-smoke`) might need a different skip
     condition (Node.js missing, npm registry unreachable, etc.).
   - **RESOLVED:** defer. The schema starts minimal (just trigger paths + smoke command);
     skip conditions are gate-specific and can be encoded inline in the smoke command (`if !
     command -v lcc; then exit 0; fi`).

3. **What happens if a stale file deletion causes a subsequent `compileRom` cache invalidation
   that takes too long?**
   - What we know: `CompileRomTask` has its own `@OutputFile romFile` declaration; its inputs
     are the C source files. Deleting `bank1.c` would re-trigger `compileRom` if it was
     previously cached.
   - What's unclear: is the cache invalidation expected behavior or a regression?
   - **RESOLVED:** This IS expected. The whole point is that the previous (broken) build's
     cache should NOT be reused. Plan 2's smoke validates this by running `clean` before
     `buildRom`.
