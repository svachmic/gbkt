# Phase 06.3: V1 Feature Parity Port — World System - Context

**Gathered:** 2026-02-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Port V1 world/dungeon subsystems to V2 pipeline: floor navigation, zone loading, tilemap rendering, random encounter system, exploration state machine. Full V2 DSL style with typed C AST (zero CRawCode). Also close two inherited gaps: entity obstacle detection (Directive G3) and AudioMixer real implementation (Directive A5).

The world system is an **engine-level** feature — it must work standalone without the RPG package. RPG-specific behavior (party stats, monster definitions, abilities) plugs in via interfaces in Phase 06.4/06.5.

</domain>

<decisions>
## Implementation Decisions

### Entity Obstacle Detection (Directive G3)

- **Blocking feedback**: Bump feedback on blocked movement (short sound/visual nudge), not silent
- **Per-entity collision modes**: Configurable per entity — block, passthrough, blockAndTrigger, overlapTrigger
  - blockAndTrigger: player stops on adjacent tile, trigger fires (entity remains wall)
  - overlapTrigger: player moves onto entity tile, trigger fires (floor trigger / pressure plate)
- **Entity-aware callbacks**: onBlocked receives the blocking entity reference — game can react differently per NPC
- **Player-only collision**: Only the player checks entity collisions. NPC-to-NPC collision is not supported
- **Runtime changeable modes**: Collision mode set at definition time by default, but a runtime setter is available for dynamic cases (e.g., doors that unlock)
- **Dual collision shapes**: Both tile-based (full grid tile) and pixel-based (hitbox) available — programmer chooses per entity
- **Auto-clear on remove**: Removing/destroying an entity automatically clears its collision
- **Multi-tile entities**: Entities can occupy multiple tiles (e.g., 2x2 boulders)
- **Pushable entities**: Included in this phase as a collision mode
  - Push direction is configurable per entity (any direction, horizontal-only, specific directions)
  - onPushed callback fires with entity reference and push direction — enables puzzle mechanics
  - Push only succeeds if destination tile is free

### AudioMixer Implementation (Directive A5)

- **Channel groups**: Predefined defaults (music, sfx, ui) plus custom group definitions
- **Volume control**: Both mute/unmute (quick toggle) and gradual volume (0-100%) supported
- **Master volume**: Global master volume control that scales all group volumes — useful for settings menus
- **Configurable channel mapping**: DSL lets game author assign Game Boy's 4 channels (2 pulse, 1 wave, 1 noise) to groups
- **Built-in fade support**: fadeGroup(group, targetVolume, frames) generates per-frame interpolation
- **Persistable state**: Audio settings (volume levels, mute state) saveable/restorable as part of game save data
- **Priority system**: Each sound has a priority level. Higher priority can interrupt lower when channels are full
- **Auto-ducking**: Music volume automatically reduces during important SFX or dialog playback

### Zone Transitions

- **Configurable transition style**: Per-zone transition type (cut, fade, scroll) — not one global style
- **Auto tileset reuse detection**: Engine compares tileset IDs and skips VRAM reload when adjacent zones share the same tileset. Invisible to DSL author
- **Player position mapping**: Edge-based auto-mapping as default (exit right → enter left at same Y), with override to named entry points when needed
- **Zone lifecycle callbacks**: Both onEnter and onExit callbacks available — enables music changes, cutscenes, flag setting during transitions

### Encounter System

- **Rate model**: Safe steps + random range (N guaranteed safe steps, then random chance within a range) — classic JRPG model
- **Per-zone rates**: Each zone has its own encounter configuration — enables safe rooms, dangerous corridors, boss areas with no random encounters
- **Explicit safe zone flag**: Zones can be marked as encounter-free with a dedicated flag (not just rate=0)
- **Conditional encounter entries**: Encounter table entries can have conditions (e.g., different monsters after story flags) — enables story progression affecting encounters

### Engine/RPG Architecture Boundary

- **Interface pattern throughout**: All world system extension points (encounters, zone events, floor logic, movement) use pluggable interfaces. RPG and other game genres plug in uniformly
- **Generic combat trigger**: Encounters fire a generic 'start combat' event with encounter data. Engine doesn't know about RPG systems — Phase 06.4/06.5 plugs in
- **Encounter data as interfaces**: Encounter entries define contracts, not concrete types. RPG package provides typed implementations that feel idiomatic — no visible seams to the developer
- **Standalone world system**: World system works independently without RPG package — enables action-adventure, puzzle, horror games with dungeon-like structures but no RPG stats
- **Pluggable movement**: Movement style is an interface. Grid movement is the default implementation. Smooth/free movement could be added later
- **Separated state ownership**: Engine owns world state (position, zone, steps, flags). RPG owns party/inventory/quests. Clear boundary
- **Fully pluggable save/load**: Save system is fully interface-based. Both world state and RPG state are save interfaces — maximum flexibility
- **Presets with overrides**: World system provides preset configurations (e.g., DUNGEON_CRAWLER) as convenient starting points, but every setting is individually overridable

### Claude's Discretion
- Exact bump sound/animation implementation for entity blocking
- Internal grid-to-pixel collision resolution details
- Fade interpolation algorithm (linear vs eased)
- GBDK NRxx register manipulation details for audio
- Zone transition frame budgets
- Encounter random number generation approach
- Interface naming conventions and Kotlin sealed/open hierarchy choices

</decisions>

<specifics>
## Specific Ideas

- "The developer should have an idiomatic experience and not feel like they are shoe-horning things in" — the engine/RPG interface boundary must be invisible in normal use. When using RPG features, it should feel native, not like adapting generic APIs
- Presets should be "good starter, but flexible config" — a sensible default that doesn't lock you in
- The overall design philosophy: engine provides contracts, game-genre packages provide implementations, DSL author sees a unified experience

</specifics>

<deferred>
## Deferred Ideas

- NPC-to-NPC collision — could be a future enhancement if pathfinding is added
- Smooth/free movement implementation — interface exists in 06.3, concrete smooth impl is a future feature
- Advanced puzzle mechanics beyond pushables (switches, pressure plates, timed blocks) — could be its own phase

</deferred>
