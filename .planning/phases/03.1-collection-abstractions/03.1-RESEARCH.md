## User Constraints (from CONTEXT.md)

### Locked Decisions

**IR Design Approach**
- Hybrid: Collection IR + backend traits — Collections are first-class IR nodes representing platform-agnostic concepts ("a hashtable of 64 entries"), and each backend decides how to implement them (GBDK uses static arrays + linear probing; a hypothetical GBA backend might use different alignment or DMA-friendly layouts)
- IR knows exact byte counts at compile time for all collections
- Every collection compiles to fully static C — runtime indices over fixed memory, no heap

**Collection Types**
- `IRHashTable(keyType, valueType, size)` — static array + generated hash/probe/insert/lookup/clear functions
- `IRPool(elementType, capacity)` — static array + free-list index tracking
- `IRRingBuffer(elementType, capacity)` — static array + head/tail indices
- `IRFixedSlots(elementType, count)` — array + active/inactive bitfield

**DSL Sugar**
- `val objectTable by hashtable<TileHashEntry>(64)`
- `val monsterSlots by fixedSlots<Monster>(3)`
- `val messageBuffer by ringBuffer<Char>(128)`

**Backend Contract**
- Each backend implements collection codegen through traits/interfaces
- GBDK backend: static arrays + linear probing for hashtables, bitfield tracking for fixed slots
- Backend portability is a design goal — same IR works across targets

### Claude's Discretion
None specified — all major decisions locked.

## Summary

Phase 3.1 adds first-class collection IR nodes to gbkt-core and a corresponding GBDK codegen implementation. The codebase already has a clear, well-exercised pattern for this exact kind of addition: the entity Pool system. Pool follows the identical three-layer architecture (IR nodes in `SystemIR.kt` / `PathfindingIR.kt`, DSL wrapper class in `entity/`, GBDK codegen in `codegen/core/PoolCodegen.kt`). New collection types map directly onto that pattern.

The critical insight is that "collection IR" in this codebase is not a new concept. Each collection will be:
1. A **data class in gbkt-core/ir/** implementing `IRStatement`/`IRExpression` (sealed — no else branch means every when in IRWalker, IRSubstitution, RecordingContext must be updated for each new type)
2. A **domain class in gbkt-core/** (like `Pool`) that the DSL delegate returns, which calls `RecordingContext.require().emit(IR...)` to record operations
3. A **GBDK codegen function** in `gbkt-backend-gbdk/codegen/core/` called from `GBDKCodeGenerator.generate()`
4. A **collection descriptor** added to `Game` (like `pools: List<Pool>`) and wired through `GameBuilder`

The backend trait contract (locked decision) requires a new interface that `GBDKBackend` implements, giving future backends a hook to substitute their own implementation. This is the one genuinely new architectural element; everything else is established pattern.

**Primary recommendation:** Follow the Pool pattern exactly for each collection type. The four files to update for each new IR type are predictable: `IRWalker.kt`, `IRSubstitution.kt`, `RecordingContext.kt` (source-location tag), and `StatementCodegen.kt` → `generateDelegatedStatement`. The backend trait interface is a thin wrapper that can be introduced once and reused for all four collection types.

```kotlin
fun <V> hashtable(size: Int) = HashTableDelegate<V>(size)
```

### Naming Collision Warning: `IRPool` vs Entity `Pool`

There is an **existing entity `Pool`** system in `gbkt-core/entity/Pool.kt` with IR nodes called `IRPoolUpdate`, `IRPoolSpawn`, etc. The new `IRPool(elementType, capacity)` decided in CONTEXT.md conflicts with this namespace.

**Resolution (HIGH confidence — must be addressed in plan):** Use unambiguous names:
- `IRCollection` as the sealed interface grouping the four collection types, OR
- Use prefix `IRColl` to distinguish: `IRCollPool`, `IRCollHashTable`, `IRCollRingBuffer`, `IRCollFixedSlots`
- The domain class wrapping `IRCollPool` should be named `PoolCollection` or `DataPool` to avoid collision with `Pool` (entity pool)

### New IR Nodes Must Update Six Files

Every new `IRStatement` subtype requires updating six existing files (HIGH confidence — verified in IRWalker.kt):

| File | What to add | Reason |
|------|-------------|--------|
| `ir/IRWalker.kt` — `childStatementLists()` | New `is IR... -> emptyList()` branch | Sealed exhaustive when — compiler error without it |
| `ir/IRSubstitution.kt` — `deepCopy()` | New `is IR... -> this` or copy branch | Same exhaustive constraint |
| `dsl/RecordingContext.kt` — `withSourceLocation()` | New `is IR... -> this` branch | Same exhaustive constraint |
| `StatementCodegen.kt` — `generateDelegatedStatement()` | Call to `generateCollectionStatement()` | Routes new IR to handler |
| `StatementCodegen.kt` — new `generateCollectionStatement()` | `is IRCollHashTable... -> ...` | Actual C output |
| `validation/IRReferenceValidation.kt` | Pool-style name validation | Consistent error messages |

For new `IRExpression` subtypes:
| File | What to add |
|------|-------------|
| `ir/IRWalker.kt` — `childExpressions()` | New `is IR... -> emptyList()` |
| `ir/IRSubstitution.kt` — `deepCopy()` (expr branch) | New `is IR... -> this` |
| `ExpressionCodegen.kt` | Expression-to-C string |

### Backend Trait Interface (New Element)

The locked decision requires a backend trait interface for collection codegen. Based on the existing `CodegenBackend` pattern:

```kotlin
// New file: gbkt-backend-api/src/main/kotlin/io/github/gbkt/backend/api/CollectionCodegen.kt
interface CollectionCodegen {
    /** Generate all declarations (static arrays, #define sizes) for one hash table. */
    fun generateHashTable(name: String, keyType: CollectionKeyType, valueType: CollectionValueType, size: Int): String
    fun generatePool(name: String, elementType: CollectionValueType, capacity: Int): String
    fun generateRingBuffer(name: String, elementType: CollectionValueType, capacity: Int): String
    fun generateFixedSlots(name: String, elementType: CollectionValueType, count: Int): String
}
```

`GBDKBackend` implements `CollectionCodegen`. `GBDKCodeGenerator` receives a `CollectionCodegen` reference and delegates generation to it. This is the portability hook.

**Alternative simpler approach:** Place the trait in `gbkt-backend-gbdk` as a local interface and just make `GBDKCodeGenerator` pluggable — backend portability is a design goal but the trait-in-api-module approach is cleaner for the declared goal.

### Byte Size Calculation

IR nodes must expose compile-time byte counts (locked decision: "IR knows exact byte counts at compile time").

```kotlin
// Example for IRCollHashTable
data class IRCollHashTable(
    val name: String,
    val keyType: GBVar.VarType,
    val valueType: GBVar.VarType,
    val size: Int,
) {
    /** Static WRAM bytes: keys array + values array + probe count */
    val sizeBytes: Int
        get() = size * keyType.size + size * valueType.size + size * 1 // probe/used byte
}
```

The pattern already exists on `BalanceColumn.sizeBytes` and `CompositeTable.sizeBytes` in `TablesIR.kt` — same property naming convention.

### GBDK Static C Pattern for Each Collection Type

**HashTable (static linear probing):**
```c
// Generated by generateHashTableData()
#define TILE_TABLE_SIZE 64
static UINT16 tile_table_keys[TILE_TABLE_SIZE];
static UINT8  tile_table_values[TILE_TABLE_SIZE];
static UINT8  tile_table_used[TILE_TABLE_SIZE];  // 0=empty, 1=occupied

// Generated by generateHashTableFunctions()
static UINT8 tile_table_hash(UINT16 key) { return (UINT8)(key % TILE_TABLE_SIZE); }
static void tile_table_insert(UINT16 key, UINT8 value) { ... }
static UINT8 tile_table_lookup(UINT16 key, UINT8* out) { ... }
static void tile_table_clear(void) { ... }
```

**Pool (free-list index):**
```c
#define ITEM_POOL_CAPACITY 16
static UINT8 item_pool_data[ITEM_POOL_CAPACITY];
static UINT8 item_pool_free[ITEM_POOL_CAPACITY];  // free-list bitmap
static UINT8 item_pool_count;

static INT8 item_pool_alloc(void) { ... }  // returns index or -1
static void item_pool_free_slot(UINT8 idx) { ... }
```

**RingBuffer (head/tail):**
```c
#define MSG_BUFFER_CAPACITY 128
static UINT8 msg_buffer_data[MSG_BUFFER_CAPACITY];
static UINT8 msg_buffer_head;
static UINT8 msg_buffer_tail;
static UINT8 msg_buffer_count;

static void msg_buffer_push(UINT8 val) { ... }
static UINT8 msg_buffer_pop(void) { ... }
static UINT8 msg_buffer_peek(void) { ... }
```

**FixedSlots (bitfield active tracking):**
```c
#define ENEMY_SLOTS_COUNT 3
static Enemy enemy_slots_data[ENEMY_SLOTS_COUNT];
```

### GameScope Registration Pattern

Collections must register with `GameScopeContext` (identical to how `GBArray` registers via `GameScopeContext.current?.registerArray(arr)`). The `GameScope` abstract class needs a new `registerCollection()` method:

```kotlin
// In GameScope.kt
abstract class GameScope {
    internal val variables = mutableListOf<GBVar<*>>()
    internal val arrays = mutableListOf<GBArray>()
    internal val collections = mutableListOf<CollectionIR>()  // NEW

    fun registerCollection(c: CollectionIR) {
        if (collections.none { it.name == c.name }) collections.add(c)
    }
}
```

`GameBuilder` (which extends `GameScope`) already collects variables and arrays in `build()` — same pattern for collections.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Hash function for GBDK | Custom prime-based hash | Simple modulo `key % size` | Game Boy is 4MHz; modulo is fast enough for small tables (≤64 entries); prime-based hash is overkill and generates more C code |
| Dynamic resizing | Grow-on-insert | Fixed compile-time size only | No heap; locked design decision |
| Generic type system | Kotlin generics passed to C | `GBVar.VarType` enum maps to C types | Already exists; `VarType.cType` gives `UINT8`, `UINT16`, etc. |
| C code templating | String interpolation in codegen | Direct `line("...")` calls in `GBDKCodeGenerator` | All existing codegen uses this pattern; consistency matters |

## Common Pitfalls

### Pitfall 1: Name Collision with Existing Entity Pool
**What goes wrong:** Naming the new general-purpose pool IR `IRPool` collides with `IRPoolSpawn`, `IRPoolUpdate`, etc. which belong to the entity Pool (sprites, OAM, despawn conditions).
**Why it happens:** The CONTEXT.md says `IRPool(elementType, capacity)` but entity Pool IR uses `IRPool*` prefix throughout SystemIR.kt.
**How to avoid:** Use a distinguishing prefix or namespace. Recommended: `IRCollPool` for the collection-typed pool, or group all four under `IRCollection` sealed interface with subtypes.
**Warning signs:** Kotlin compiler "ambiguous reference" or "duplicate class" errors.

### Pitfall 2: Missing Branches in Sealed When Expressions
**What goes wrong:** Adding a new `IRStatement` subtype without adding it to all six exhaustive `when` expressions causes compile errors.
**Why it happens:** `IRWalker.kt` explicitly has NO `else` branch — this is intentional and documented.
**How to avoid:** After adding any new IR data class, run `./gradlew :gbkt-core:build` — the compiler will enumerate all missing branches. Fix them in order: IRWalker, IRSubstitution, RecordingContext, then StatementCodegen.
**Warning signs:** Compile error "when expression must be exhaustive" in IRWalker.kt.

### Pitfall 3: Forgetting `generateDelegatedStatement` Registration
**What goes wrong:** New collection IR statement types get emitted but `generateStatement()` hits `error("Unhandled IR statement type: ...")` at runtime.
**Why it happens:** `generateStatement()` has an explicit `else -> generateDelegatedStatement(stmt)` chain; new categories must register via `if (generateCollectionStatement(stmt)) return`.
**How to avoid:** Add `generateCollectionStatement()` handler to `generateDelegatedStatement()` in `StatementCodegen.kt`.
**Warning signs:** Runtime exception in codegen with "Unhandled IR statement type: IRCollHashTableInsert".

### Pitfall 4: Game.build() Not Forwarding Collections
**What goes wrong:** Collection definitions in DSL are silently dropped — no codegen output.
**Why it happens:** `GameBuilder.build()` explicitly maps each field. Collections added to `GameScope` but not forwarded in `build()` are lost.
**How to avoid:** Add collections to both `Game` constructor parameters AND `GameBuilder.build()` return statement, matching the `variables`/`arrays` pattern exactly.
**Warning signs:** `game.hashTables.isEmpty()` even after `val x by hashtable(64)` in DSL.

### Pitfall 5: Byte Count Off-By-One in sizeBytes
**What goes wrong:** Downstream Phase 4 RAM planning gets wrong budgets.
**Why it happens:** Hash table internal bookkeeping (probe byte, used byte) is easy to forget.
**How to avoid:** Define `sizeBytes` conservatively (include all hidden overhead arrays). For hashtable: `size * (keyType.size + valueType.size + 1)` where +1 is the `used` byte array.
**Warning signs:** Actual C array size doesn't match `sizeBytes` property.

### Pitfall 6: GBDKCodeGenerator.generate() Call Order
**What goes wrong:** Collection data referenced before declaration; C compiler error "undefined symbol".
**Why it happens:** `generate()` has strict ordering (variables first, then functions that use them).
**How to avoid:** Add `generateCollectionData()` immediately after `generateVariables()` (before scene functions). Add `generateCollectionFunctions()` after data but before scenes. See existing call order in `GBDKCodeGenerator.generate()` lines 294-436.
**Warning signs:** GBDK lcc compilation errors about undeclared variables.

## Key Architectural Facts

### Where IR nodes live (HIGH confidence — verified)

All IR nodes in `gbkt-core` must implement `IRStatement` or `IRExpression` from `CoreIR.kt`. The sealed constraint means all subtypes must be in the same module. New collection IR nodes go in `gbkt-core/src/main/kotlin/io/github/gbkt/core/ir/CollectionsIR.kt` (new file).

### How Game model receives collections (HIGH confidence — verified)

`Game.kt` is a constructor with ~60 named parameters. Each new domain list (e.g., `hashTables`) is:
1. Added as a parameter to `Game` constructor with default `emptyList()`
2. Added to `GameBuilder._collections` mutable list
3. Forwarded in `GameBuilder.build()` return

`GameScope` gets `registerCollection()`. `GameScopeContext.current?.registerCollection()` is called from the DSL delegate's `getValue`.

### How `GBDKCodeGenerator` accesses `game` (HIGH confidence — verified)

`GBDKCodeGenerator` holds `val game: Game`. All codegen extension functions use `GBDKCodeGenerator` as receiver (e.g., `internal fun GBDKCodeGenerator.generatePoolData()`). They access `game.pools`, `game.variables`, etc. directly. New collection codegen follows this exact pattern: `game.hashTables`, `game.collPools`, etc.

### Backend trait placement (MEDIUM confidence — design decision)

The locked decision says "each backend implements collection codegen through traits/interfaces." The natural placement is:
- Interface in `gbkt-backend-api` (alongside `CodegenBackend`) so future backends can implement it
- `GBDKBackend` implements `CollectionCodegen`
- `GBDKCodeGenerator` receives `CollectionCodegen` in constructor or calls backend directly

The existing `GBDKBackend` delegates to `GBDKCodeGenerator` via `generate()`. The backend trait can be: `GBDKCodeGenerator(game, collectionCodegen: CollectionCodegen)` where GBDK provides its own default implementation.

### VarType for collection element types (HIGH confidence — verified)

`GBVar.VarType` (U8/U16/I8/I16) with `.cType` and `.size` properties covers all primitive types needed. For struct-like element types (e.g., `Monster`, `TileHashEntry`), the DSL phase must resolve these to either a GBVar type or a struct name string. Phase 3.1 scope likely covers primitive element types; struct types may be deferred.

## Open Questions

1. **TypeParam resolution for `<V>` in DSL**
   - What we know: DSL sugar uses Kotlin generics (`hashtable<TileHashEntry>(64)`) but GBDK output is typed C
   - What's unclear: How does `V` map to a C type? For primitives, `GBVar.VarType` works. For structs (like `Monster`), we need a struct name string
   - Recommendation: In Phase 3.1, restrict `V` to `GBVar.VarType` equivalent types (u8, u16, i8, i16) and represent as a type parameter bound. Struct element types can be added in a follow-on.

2. **IRPool naming collision resolution**
   - What we know: `IRPool*` prefix is fully occupied by entity Pool IR (IRPoolSpawn, IRPoolUpdate, etc.)
   - What's unclear: The planner needs to pick the final naming convention
   - Recommendation: Use `IRCollPool`, `IRCollHashTable`, `IRCollRingBuffer`, `IRCollFixedSlots` throughout. The collection domain class wrapping `IRCollPool` can be named `DataPool` or `CollectionPool`.

3. **Backend trait interface scope**
   - What we know: Interface goes in `gbkt-backend-api`; GBDK implements it
   - What's unclear: Whether `GBDKCodeGenerator` should accept `CollectionCodegen` in constructor or whether the interface is at the `GBDKBackend.generate()` level
   - Recommendation: Keep simple — place the interface as a nested default implementation inside `GBDKBackend` for now. Extract to API if a second backend materializes.
