# Phase 3.1: Collection Abstractions - Context

**Gathered:** 2026-02-18
**Status:** Ready for planning

<domain>
## Phase Boundary

First-class IR nodes for static collection patterns (hashtable, pool, ring buffer, fixed slots) that compile to fully static C — no heap, no dynamic allocation. Each backend chooses optimal implementation. This phase adds IR types, DSL sugar, and codegen visitors; Phase 4's RAM planning then naturally accounts for collection memory budgets.

</domain>

<decisions>
## Implementation Decisions

### IR Design Approach
- **Hybrid: Collection IR + backend traits** — Collections are first-class IR nodes representing platform-agnostic concepts ("a hashtable of 64 entries"), and each backend decides how to implement them (GBDK uses static arrays + linear probing; a hypothetical GBA backend might use different alignment or DMA-friendly layouts)
- IR knows exact byte counts at compile time for all collections
- Every collection compiles to fully static C — runtime indices over fixed memory, no heap

### Collection Types
- `IRHashTable(keyType, valueType, size)` — static array + generated hash/probe/insert/lookup/clear functions
- `IRPool(elementType, capacity)` — static array + free-list index tracking
- `IRRingBuffer(elementType, capacity)` — static array + head/tail indices
- `IRFixedSlots(elementType, count)` — array + active/inactive bitfield

### DSL Sugar
- `val objectTable by hashtable<TileHashEntry>(64)`
- `val monsterSlots by fixedSlots<Monster>(3)`
- `val messageBuffer by ringBuffer<Char>(128)`

### Backend Contract
- Each backend implements collection codegen through traits/interfaces
- GBDK backend: static arrays + linear probing for hashtables, bitfield tracking for fixed slots
- Backend portability is a design goal — same IR works across targets

</decisions>

<specifics>
## Specific Ideas

- The LabyrinthOfTheDragon "dynamic memory allocation" use case is actually static arrays with runtime bookkeeping — a well-known embedded pattern
- gbkt doesn't need a heap; it needs collection abstractions in IR that compile to deterministic, statically-sized C
- This strengthens the C AST direction: IR validates at compile time that e.g. a hashtable of 64 entries fits in the target's WRAM budget

</specifics>
