## Summary

The shmup UAT failure (Phase 07.2) is explained by seven distinct codegen bugs that interact to make pooled entities invisible and non-functional. The bugs were verified by reading the generated `main.c` and `bank1.c` files directly against the codegen source in `GBDKSystemVisitor`, `ActorVisitor`, `GBDKPipelineV2`, and `ScriptOpVisitor`.

The root problem is that `GBDKSystemVisitor.buildActorPoolStateVars()` generates only an active-bitmap array and an `oam_base` scalar per pool — it does not generate per-instance position arrays. Without those arrays, `forEachActive` loop bodies have no per-instance state to read or write, so they fall back to the template actor's single global position variable. Additionally, `update_sprites()` re-syncs the template actor positions to OAM every frame, overwriting any position the pool spawn set. The pool `oam_base` is initialized to 0 (the same slot range used by template actors), and pool `_init()` functions are never called from `main()`. Collision detection uses template variable AABB checks rather than per-active-instance iteration.

All seven bugs are fixes to the GBDK backend layer only. No IR changes are required. The existing `PoolSpawnActor`, `PoolForEachActive`, `PoolDestroyActor`, and `PoolDestroyAll` IR ops carry all the information the backend needs.

**Primary recommendation:** Fix the seven bugs in sequence (state vars → OAM allocation → spawn → forEachActive → update_sprites exclusion → main init → collision), with a JVM codegen regression test per fix, then MCP play-through of shmup for runtime validation.

## Bug Inventory

All bugs were verified against `/gbkt-examples/shmup/build/gbkt/generated/main.c` and `bank1.c`.

### Bug 1: Missing per-instance position arrays (CRITICAL)

**Location:** `GBDKSystemVisitor.buildActorPoolStateVars()` (line 4379)

**Current behavior:** For each pool, generates only:
```c
UINT8 _pool_bulletPool_active[8];
UINT8 _pool_bulletPool_oam_base = 0u;  // BUG: initialized to 0, never updated
```

**Required behavior:** Must also generate:
```c
UINT8 _pool_bulletPool_x[8];   // per-instance x positions
UINT8 _pool_bulletPool_y[8];   // per-instance y positions
UINT8 _pool_bulletPool_oam[8]; // per-instance OAM slot mapping (D-03)
```

**Impact:** Without position arrays, `forEachActive` bodies cannot read/write per-instance positions. All collision and movement checks fall back to the single template variable.

### Bug 2: `oam_base` initialized to 0, never assigned a post-actor offset (CRITICAL)

**Location:** `GBDKSystemVisitor.buildActorPoolStateVars()` initializer + `GBDKPipelineV2.buildMainFunction()`

**Current behavior:** `_pool_bulletPool_oam_base = 0u` — hardcoded, never overwritten at startup. The shmup has actors bullet (1 OAM slot), enemy (4 OAM slots), player (4 OAM slots) = 9 total slots used by `update_sprites()`. The bulletPool's `oam_base` also starts at 0, so pool spawn calls collide with template actor OAM slots.

**Required behavior with D-03 (dynamic allocation):** Remove `oam_base` entirely. Replace with a per-instance `_pool_<id>_oam[N]` array. Pool `spawn()` allocates an OAM slot from the shared free list (same `spawn_actor()` free stack used by non-pooled actors). Pool `destroy()` returns the slot to the free stack via `destroy_actor()`.

**OAM budget for shmup:** bullet=1 slot, enemy=4 slots, player=4 slots = 9 non-pool slots. bulletPool(max=8) + enemyPool(max=4) = 12 pool slots. Total = 21 of 40 available OAM slots. Dynamic allocation avoids all conflicts.

### Bug 3: `pool_<id>_init()` functions never called from `main()` (CRITICAL)

**Location:** `GBDKPipelineV2.buildMainFunction()` (line 3003)

**Current behavior:** `buildMainFunction()` calls `spriteDataLoads`, `spriteOAMInits`, and `startEnterCall`, but never calls `pool_<id>_init()`. The active bitmaps are uninitialized C globals (GBDK zero-initializes BSS, so active[] starts as zero, which is technically correct — but `oam_base` and the new `oam[]` array need runtime initialization).

**Required behavior:** Add `pool_<id>_init()` call for each pool in `buildMainFunction()`, before the start-scene enter call. With the D-03 dynamic-allocation design, `pool_<id>_init()` zeroes the active bitmap and sets all `oam[]` entries to `0xFF` (invalid). No OAM slot pre-allocation.

### Bug 4: `forEachActive` body accesses template variable, not per-instance array (CRITICAL)

**Location:** `ScriptOpVisitor.visitPoolForEachActive()` (line 787) + ExprVisitor actor property resolution

**Current behavior:** Inside `forEachActive(bulletPool, "bi") { bi -> ... }`, any reference to `bullet.y` emits `_bullet_y` (the template actor's global scalar). The generated C is:
```c
UINT8 _bi;
for (_bi = 0u; _bi < 8u; _bi++) {
    if (_pool_bulletPool_active[_bi]) {
        if (_bullet_y < 4u) {  // BUG: uses template var, not instance
            pool_bulletPool_destroy(_bi);
        }
    }
}
```

**Required behavior:** The backend must detect that a `forEachActive` body is being compiled and redirect `_bullet_y` reads to `_pool_bulletPool_y[_bi]` and writes to `_pool_bulletPool_y[_bi] = ...`. This is a context-injection problem: `ScriptOpVisitor.visitPoolForEachActive()` must set an active-pool context that `ExprVisitor` and `ScriptOpVisitor.visitMoveBy()` consult to redirect actor property accesses.

**Context injection design (Claude's discretion):** A thread-local or parameter-passed `PoolContext(poolId, slotVar)` that `visitPoolForEachActive` sets before compiling body ops. `ExprVisitor.visitActorPropertyRef()` checks for active pool context; if the referenced actor is the pool's template actor, redirects to array access. `ScriptOpVisitor.visitMoveBy()` does the same for position mutation.

### Bug 5: `update_sprites()` syncs template actor OAM slots every frame (CRITICAL)

**Location:** `ActorVisitor.generateUpdateSprites()` (line 178) — called by `GBDKPipelineV2`

**Current behavior:** `update_sprites()` is called from `main()` game loop. It iterates `gameIR.actors` — which includes the `bullet` and `enemy` template actors — and emits:
```c
void update_sprites(void) {
    move_sprite(0u, _bullet_x + 8u, _bullet_y + 16u);  // OAM slot 0 = bullet template
    move_sprite(1u, _enemy_x + 8u, _enemy_y + 16u);    // OAM slots 1-4 = enemy template
    ...
    move_sprite(5u, _player_x + 8u, _player_y + 16u);  // OAM slots 5-8 = player
    ...
}
```

This means even if pool spawn correctly positions a bullet sprite at the player's location, `update_sprites()` immediately overwrites it back to `_bullet_x + 8u` (the template's initial position 248, 248 in hardware coords).

**Required behavior:** `generateUpdateSprites()` must exclude actors that are used as pool templates. An actor used as `actorTemplateId` in any `ActorPoolIR` should not appear in `update_sprites()`. Pool sprite sync happens via the post-body `move_sprite` calls inside `forEachActive`.

**Template actor exclusion:** `GBDKPipelineV2` can compute the set of pool template actor IDs: `gameIR.actorPools.map { it.actorTemplateId }.toSet()`. Pass this set to `generateUpdateSprites()` to skip template actors.

### Bug 6: No display sync in `forEachActive` after body execution (CRITICAL)

**Location:** `ScriptOpVisitor.visitPoolForEachActive()` — body is compiled but no `move_sprite` call follows

**Current behavior:** The `forEachActive` loop body executes script ops but never calls `move_sprite` to commit the updated position to OAM. Even if Bug 4 is fixed and body ops write to `_pool_bulletPool_y[_bi]`, the sprite's OAM position stays stale until something explicitly moves it.

**Required behavior:** After the body block executes (still inside the active-guard `if`), emit:
```c
if (_pool_bulletPool_active[_bi]) {
    // ... body ops here (position array reads/writes)
    move_sprite(_pool_bulletPool_oam[_bi],
                _pool_bulletPool_x[_bi] + 8u,
                _pool_bulletPool_y[_bi] + 16u);
}
```

Note: The `+8`/`+16` hardware offset is the standard GBDK convention used everywhere (verified in `ActorVisitor.generateUpdateSprites()`, `generateOAMInit()`).

**Variant for multi-tile sprites:** Pool template actors can be 8x8 (bullet: 1 tile), 16x16 (enemy: 4 tiles), etc. The `forEachActive` sync must handle multi-tile metasprites. For max=8 bulletPool with 1-tile bullets, one `move_sprite` per iteration. For 4-tile enemy sprites, four `move_sprite` calls per iteration (with column/row offsets matching the sprite grid).

**Key insight:** `ActorPoolIR.actorTemplateId` gives the template actor ID. The template actor's `sprite.size` gives the tile grid dimensions. The `_pool_<id>_oam[N]` array holds the base OAM slot for each instance; additional slots for multi-tile sprites are consecutive (`oam[i]+1`, `oam[i]+2`, etc.). Allocate `tilesWide * tilesHigh` consecutive slots per instance at spawn time.

### Bug 7: Collision between pools uses template variable AABB (ARCHITECTURAL)

**Location:** `ExprVisitor` collision expression generation — `whenever(bullet.collides(enemy))`

**Current behavior:** `bullet.collides(enemy)` is compiled as a single AABB check using template scalar vars:
```c
if (_bullet_x < _enemy_x + 16u && _bullet_x + 4u > _enemy_x && ...)
```

This is a single boolean check, not an iteration over all active pool pairs. Semantically `bullet.collides(enemy)` when both are pool templates should mean "any active bullet collides with any active enemy."

**Required behavior (D-06 scope):** Cross-pool collision must be restructured as nested `forEachActive` loops. This is an IR-level semantic question: does `whenever(bullet.collides(enemy))` mean "for any pair" or "for the singleton template"?

**Decision implication:** The Shmup DSL currently writes `whenever(bullet.collides(enemy))` outside any `forEachActive`, expecting the backend to synthesize the nested iteration. This requires either (a) a new `PoolCollision` ScriptOp in IR or (b) backend detection that both operands are pool templates and auto-wrapping in nested loops.

**Per D-07 (IR stays minimal):** The backend should detect that both collision operands reference pool template actors and synthesize the nested iteration. This is backend-level inference from existing IR, not a new IR node.

**Generated C target:**
```c
// whenever(bullet.collides(enemy)) with both as pool templates
{
    UINT8 _pool_bi;
    for (_pool_bi = 0u; _pool_bi < 8u; _pool_bi++) {
        if (_pool_bulletPool_active[_pool_bi]) {
            UINT8 _pool_ei;
            for (_pool_ei = 0u; _pool_ei < 4u; _pool_ei++) {
                if (_pool_enemyPool_active[_pool_ei]) {
                    if (_pool_bulletPool_x[_pool_bi] < _pool_enemyPool_x[_pool_ei] + 16u &&
                        _pool_bulletPool_x[_pool_bi] + 4u > _pool_enemyPool_x[_pool_ei] &&
                        _pool_bulletPool_y[_pool_bi] < _pool_enemyPool_y[_pool_ei] + 16u &&
                        _pool_bulletPool_y[_pool_bi] + 8u > _pool_enemyPool_y[_pool_ei]) {
                        // body ops
                    }
                }
            }
        }
    }
}
```

**Note:** This requires `GBDKPipelineV2` or `ScriptOpVisitor` to have access to `gameIR.actorPools` to resolve template actor IDs back to pool IDs and maxSizes. `ScriptOpVisitor` currently receives pool context implicitly — this lookup needs to be threaded through.

**Scope concern:** Bug 7 (pool-pool collision) is the hardest bug and requires the most architectural change to `ScriptOpVisitor`. Bugs 1-6 are independent and address the core rendering failure. Bug 7 is needed for scoring to work in shmup. Recommend fixing 1-6 first, then 7.

### Dynamic OAM Allocator Design (D-03)

The existing non-pooled actor system uses `spawn_actor(hash)` / `destroy_actor(slot)` functions (generated by `GBDKSystemVisitor.buildSpawnActorFunction()`). Pool spawn should use the same free stack.

Pool `spawn()` change:
```c
UINT8 pool_bulletPool_spawn(UINT8 x, UINT8 y) {
    UINT8 i;
    UINT8 oam_slot;
    // Find free pool slot
    for (i = 0u; i < 8u; i++) {
        if (_pool_bulletPool_active[i] == 0u) {
            goto pool_bulletPool_found;
        }
    }
    return 0xFF;  // pool full
    pool_bulletPool_found:
    // Allocate OAM slot from shared free stack (1 slot for 8x8 bullet)
    oam_slot = spawn_actor(ACTOR_HASH_BULLET);
    if (oam_slot == 0xFF) { return 0xFF; }  // no OAM slots available
    _pool_bulletPool_active[i] = 1u;
    _pool_bulletPool_oam[i] = oam_slot;
    _pool_bulletPool_x[i] = x;
    _pool_bulletPool_y[i] = y;
    move_sprite(oam_slot, x + 8u, y + 16u);
    return i;  // return pool slot index (not OAM slot)
}
```

Key change: `spawn()` now returns the pool slot index `i` (0..maxSize-1), not the OAM slot. This is the index used in `forEachActive` as the slot variable. The OAM slot is stored in `_pool_<id>_oam[i]`.

Pool `destroy()` change:
```c
void pool_bulletPool_destroy(UINT8 i) {
    if (i == 0xFF) { return; }
    if (i >= 8u) { return; }
    if (!_pool_bulletPool_active[i]) { return; }
    destroy_actor(_pool_bulletPool_oam[i]);  // return OAM slot to free stack
    _pool_bulletPool_active[i] = 0u;
    _pool_bulletPool_oam[i] = 0xFF;
}
```

Pool `init()` change:
```c
void pool_bulletPool_init(void) {
    UINT8 i;
    for (i = 0u; i < 8u; i++) {
        _pool_bulletPool_active[i] = 0u;
        _pool_bulletPool_oam[i] = 0xFF;  // OAM not yet allocated
    }
}
```

### Pool Context Injection for `forEachActive` Body (Bug 4 + Bug 6)

`ScriptOpVisitor` is a Kotlin `object` (stateless). Context injection must be thread-safe. The existing pattern for similar problems: thread-local context variables (e.g., `hasAudioMixerContext` in `ScriptOpVisitor.kt` line ~341).

Design: Add a thread-local `activePoolContext: ThreadLocal<PoolCodegenContext?>` to `ScriptOpVisitor`, where:
```kotlin
data class PoolCodegenContext(
    val poolId: String,
    val templateActorId: String,
    val slotVarName: String,
    val tilesWide: Int,
    val tilesHigh: Int,
)
```

`visitPoolForEachActive` sets this context before compiling body ops, clears it after. `ExprVisitor.visitActorPropertyRef()` and `ScriptOpVisitor.visitMoveBy()` check the context: if the actor ID matches `templateActorId`, redirect to per-instance array access. After body ops, emit the `move_sprite` display sync while context is still set.

`ExprVisitor` needs to be aware of the pool context to redirect reads. Currently `ExprVisitor` is a `class` instantiated with `GameIR.actors`. Pass `ScriptOpVisitor.activePoolContext` access to `ExprVisitor`.

### Template Actor Exclusion in `update_sprites()` (Bug 5)

```kotlin
// In GBDKPipelineV2.buildHomeFile()
val poolTemplateActorIds = gameIR.actorPools.map { it.actorTemplateId }.toSet()
val updateSpritesFn = ActorVisitor.generateUpdateSprites(
    actors = gameIR.actors,
    excludeIds = poolTemplateActorIds,  // new parameter
)
```

`ActorVisitor.generateUpdateSprites()` signature change: add `excludeIds: Set<String> = emptySet()` parameter. Skip actors whose sanitized ID is in `excludeIds`.

OAM slot numbering consequence: current code assigns slots sequentially by actor position in `gameIR.actors`. If template actors are excluded from `update_sprites()` but still in `gameIR.actors`, their OAM slots are no longer statically assigned. Template actors used as pool templates should also be excluded from `buildOAMInitStatements()` — their OAM slots are allocated dynamically by the pool.

### Multi-Tile Pool Sprites

For pool templates with metasprites (e.g., 16x16 enemy = 4 tiles in a 2x2 grid):
- `spawn()` must allocate `tilesWide * tilesHigh` consecutive OAM slots from the free stack.
- `_pool_<id>_oam[i]` stores the base slot; remaining slots are `oam[i]+1`, `oam[i]+2`, etc.
- Post-body display sync emits one `move_sprite` per tile with appropriate x/y offsets.
- `destroy()` must free all `tilesWide * tilesHigh` consecutive slots.

For simplicity and correctness, the pipeline can pass `tilesWide` and `tilesHigh` to `buildActorPoolFunctions()` by looking up the template actor's sprite dimensions in `gameIR.actors`.

## Common Pitfalls

### Pitfall 1: spawn() returns OAM slot vs pool index confusion

**What goes wrong:** Current `pool_<id>_spawn()` returns the OAM slot number. After the fix, it should return the pool index `i` (0..maxSize-1). `PoolSpawnActor` IR op discards the return value (the call is a statement, not an expression), so existing DSL callers aren't broken. But `PoolDestroyActor` takes `slotExpr` which was previously the OAM slot — it must now be the pool index `i`. The `forEachActive` iterator variable `_bi` is already the pool index. Verify: `destroy(bulletPool, bi.toExpr())` passes `_bi` (pool index) to `pool_bulletPool_destroy(_bi)` — this is correct after the fix.

**How to avoid:** Rename function parameter from `slot` to `i` in `pool_<id>_destroy()` to make the semantics clear. The destroy function receives a pool array index, not an OAM slot.

### Pitfall 2: OAM init statements including template actors

**What goes wrong:** `buildOAMInitStatements()` assigns static OAM slots to all actors. If pool template actors remain in this call, they get pre-assigned static OAM slots which the dynamic allocator will re-use, causing corruption.

**How to avoid:** Apply the same `poolTemplateActorIds` exclusion set to `buildOAMInitStatements()` as to `generateUpdateSprites()`. Template actors should have no static OAM slot — their tile data is loaded (sprite VRAM), but no OAM entry is reserved.

**Consequence:** Pool template actors need sprite VRAM loaded (`set_sprite_data()` still runs) but NOT `set_sprite_tile()` or initial `move_sprite()`. This requires splitting `buildOAMInitStatements()` or adding an exclusion parameter there too.

### Pitfall 3: `_pool_<id>_x[N]` and `_pool_<id>_y[N]` are `UINT8` — signed movement breaks

**What goes wrong:** `bullet.y -= 4` emits `_pool_bulletPool_y[_bi] -= 4u`. If `_bi_y` is `UINT8` and wraps below 0, the < 4 despawn check won't catch negative-wraparound bullets. Same for `i8Var` template actor props.

**How to avoid:** Match the type of `_pool_<id>_x[N]` and `_pool_<id>_y[N]` to the template actor's position variable type (`UINT8` for actors defined with default u8 position). In the current DSL, actor position is always `UINT8`. This is an existing constraint — movement-with-clamp via `whenever(bullet.y isAbove 4)` guards in the DSL are the correct pattern. No change needed here, but document it.

### Pitfall 4: Multi-tile pool sprites and consecutive OAM allocation

**What goes wrong:** `spawn_actor()` pops one slot from the free stack. A 16x16 sprite needs 4 consecutive OAM slots. The current free stack pops one at a time.

**How to avoid for phase 07.3:** Multi-tile pool sprites require allocating `tilesWide * tilesHigh` consecutive slots. For shmup: bullet is 8x8 (1 tile, 1 slot), so no issue. Enemy is 16x16 (4 tiles, needs 4 consecutive slots). Options: (a) pop `N` slots and only proceed if all N are available, (b) pre-reserve a contiguous block for multi-tile pool templates. Simplest: pop N individual slots — they may not be consecutive on the hardware OAM table, but each `move_sprite(slot, x, y)` call is independent. For metasprites, consecutive OAM slots are a convention but not a hardware requirement. Each tile in a 16x16 sprite is an independent OAM entry.

**Verified:** In current shmup generated C, enemy template slots 1-4 are assigned consecutively. The pool can allocate 4 independent OAM slots (not necessarily consecutive) and call `move_sprite` for each. Store all N slot IDs in `_pool_<id>_oam[i]` as the base, plus allocate and store offsets in `_pool_<id>_oam1[i]`, `_pool_<id>_oam2[i]`, etc. for multi-tile. **Simpler approach for Phase 07.3:** Only support 1-tile (8x8) pool templates for now — enemy sprites can be reduced to 8x8, or multi-tile support can be deferred. Check shmup template sizes: bullet=8x8 (1 tile), enemy=16x16 (4 tiles). If multi-tile is needed for enemy pool, must address.

### Pitfall 5: Pool collision body context not cleared on exception

**What goes wrong:** If `visitPoolForEachActive` throws during body compilation, the thread-local `activePoolContext` is left set, and subsequent ops outside the loop mistakenly redirect to pool arrays.

**How to avoid:** Use a try/finally block to always clear the thread-local after body compilation completes (or throws).

### Pitfall 6: `forEachActive` body in shmup has NO position-modifying ops

**What goes wrong:** The shmup DSL `forEachActive(bulletPool, "bi") { bi -> whenever(bullet.y isBelow 4) { destroy(bulletPool, bi.toExpr()) } }` contains only a despawn check — it does NOT contain `bullet.y -= 4` (the upward movement).

**Root cause:** Looking at the Shmup.kt source, the comment says "Bullets fly upward at 4px/frame" but the actual `bullet.y -= 4` op is **missing from the forEachActive body**. The PLAYBOOK.md says "bullets fly upward at 4px/frame" but the DSL has no such line inside the `forEachActive` body.

**Implication:** This is a DSL bug in Shmup.kt, not just a codegen bug. After the codegen fix, `bullet.y -= 4` needs to be added inside the `forEachActive(bulletPool, "bi")` body, and similarly `enemy.y += 1` inside `forEachActive(enemyPool, "ei")`. The planner must include a task to fix Shmup.kt.

**Verification:** `bank1.c` gameplay_frame confirms: the `forEachActive` for bulletPool only contains `if (_bullet_y < 4u) { pool_bulletPool_destroy(_bi); }` — no position update op exists. The PLAYBOOK says bullets fly upward, but Shmup.kt never wrote `bullet.y -= 4` inside the loop.

### Pitfall 7: ExprVisitor and ScriptOpVisitor coupling for pool context

**What goes wrong:** `ExprVisitor` is instantiated with `GameIR.actors` and has no knowledge of pool context. Actor property refs (`ActorPropertyRef`) go through `ExprVisitor.visitActorPropertyRef()`. For pool template actors inside a `forEachActive` body, these must be redirected to array accesses. But `ExprVisitor` is a separate class from `ScriptOpVisitor`.

**How to avoid:** Thread pool context through `ev()` (the `ExprVisitor` factory call in `ScriptOpVisitor`). `ScriptOpVisitor.ev()` creates/returns an `ExprVisitor`. Extend `ExprVisitor` constructor to accept an optional `PoolCodegenContext?`. `ScriptOpVisitor.visitPoolForEachActive()` passes the active context to `ev()` when compiling body ops.

## Open Questions

1. **Multi-tile pool sprite OAM allocation**
   - What we know: Enemy pool template is 16x16 (4 tiles). The dynamic allocator pops one slot at a time. 4 consecutive slots may not be available.
   - What's unclear: Whether multi-tile pool sprites need consecutive OAM slots or if each tile's OAM slot is fully independent.
   - Recommendation: Verify GBDK constraint. In standard GBDK sprite rendering, each OAM entry is independent — a 16x16 sprite is four 8x8 OAM entries, each with its own slot. Consecutive slots are a convention, not a hardware requirement. Plan can allocate 4 independent slots and store them in `_pool_<id>_oam0[N]`, `_pool_<id>_oam1[N]`, etc.

2. **Shmup DSL fix scope**
   - What we know: `forEachActive(bulletPool, "bi")` body is missing `bullet.y -= 4` (movement op). `forEachActive(enemyPool, "ei")` body is missing `enemy.y += 1`. These are DSL authoring omissions in `Shmup.kt`.
   - Recommendation: Phase 07.3 planner must include a task to add these missing ops to `Shmup.kt`. Without them, bullets are stationary even after all codegen fixes.

3. **Pool-pool collision scope for Phase 07.3 vs. deferred**
   - What we know: Bug 7 (pool-pool collision) is architecturally distinct from Bugs 1-6 (rendering/state). Fixing 1-6 gives visible sprites; fixing 7 enables scoring.
   - Recommendation: Fix Bug 7 in Phase 07.3. Shmup's core gameplay (score increments on enemy hit, lives decrement on player hit) requires it. Without cross-pool collision, the shmup UAT will still fail on collision checks.

4. **`spawn_actor()` hash parameter**
   - What we know: Non-pooled actor spawn uses `spawn_actor(hash)` where hash is computed from the actor ID string. Pool spawn must also call `spawn_actor(hash)`.
   - What's unclear: The hash for pool template actors — should it use the template actor's ID hash, or a pool-specific hash?
   - Recommendation: Use the template actor's ID hash (same as if the template were spawned directly). This is consistent and requires no new hash mechanism.
