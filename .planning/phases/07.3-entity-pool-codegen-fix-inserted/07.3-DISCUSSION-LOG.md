## Per-Instance State Model

| Option | Description | Selected |
|--------|-------------|----------|
| Parallel arrays | Generate _pool_<id>_x[N] and _pool_<id>_y[N] arrays. spawn() writes initial position, forEachActive reads/writes, then move_sprite syncs to OAM | ✓ |
| OAM-direct writes | No position arrays — read/write sprite positions directly through OAM shadow memory. Saves RAM but couples to hardware | |
| Template actor rewrite | forEachActive temporarily overwrites template actor's x/y, runs body, then syncs to OAM | |

**User's choice:** Parallel arrays
**Notes:** Clean separation between state (arrays) and display (OAM sync).

---

## OAM Slot Allocation

| Option | Description | Selected |
|--------|-------------|----------|
| Static ranges | Each pool gets a dedicated OAM range at codegen time. Simple but wastes slots when pools aren't full | |
| Dynamic allocation | Pool entities grab OAM slots from shared allocator at spawn, release on destroy. More flexible and scalable | ✓ |

**User's choice:** Dynamic allocation
**Notes:** User pushed back on static recommendation: "This looks like the more scaleable option, why is it not the recommended one? Static seems usually incorrect." Valid point — static ranges waste precious OAM slots (GB has only 40) and don't scale.

## Backend Boundary ("Overtraining"/"Overfitting" non-codegen to GBDK)

| Option | Description | Selected |
|--------|-------------|----------|
| IR has position ops, backend maps | New IR nodes for pool position sync, backend translates per platform | |
| IR stays minimal, codegen infers | No new IR nodes. Backend is smart enough to infer position arrays + display sync from existing ops | ✓ |

**User's choice:** IR stays minimal, codegen infers sync
**Notes:** User raised this as a custom area. Key quotes:
- "The aim is to have a true engine, not just overoptimized set of codebase that works only for written games and nothing else"
- "The idea is that the developer at worst case scenario uses IR to write quite custom operations, but should never worry about the actual hardware operations"
- "I don't want to remove that possibility [of other backends] at the inception of gbkt"
- "I don't want to overfit the codegen, because that could also result in overfitted loads of code in codegen package"
