# Phase 07.3: Entity Pool Codegen Fix (INSERTED) - Context

**Gathered:** 2026-03-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix entity pool code generation so pooled entities produce working gameplay — per-instance positions, per-frame movement, OAM rendering, and collision detection. The shmup example is the primary validation target, but the fix must work as a general-purpose entity pool engine for any game.

**Scope includes:**
- Diagnosing and fixing pool codegen in the GBDK backend (ScriptOpVisitor, GBDKSystemVisitor)
- Per-instance parallel position arrays (x[N], y[N]) generated by pool codegen
- Dynamic OAM slot allocation for pooled entities
- Display sync (move_sprite) inferred by backend from existing IR ops
- Codegen-level regression tests + MCP play-through verification
- Generic pool codegen test beyond shmup-specific patterns

**Scope excludes:**
- New IR nodes (fix is entirely in the GBDK backend layer)
- Analysis pass changes
- Other game fixes (racer, platformer — those have their own phases)
- Game-specific workarounds

</domain>

<decisions>
## Implementation Decisions

### Diagnosis Approach
- **D-01:** Code-first analysis — read generated C from shmup, trace back through codegen visitors to find where position writes and move_sprite calls are missing. No MCP emulator debugging for diagnosis.

### Per-Instance State Model
- **D-02:** Parallel arrays — generate `_pool_<id>_x[N]` and `_pool_<id>_y[N]` arrays for position tracking. `spawn()` writes initial position to arrays and syncs to display. `forEachActive` body reads/writes arrays, then syncs to display after body executes. Clean separation: state arrays → display sync.

### OAM Slot Allocation
- **D-03:** Dynamic allocation — pool entities grab OAM slots from a shared allocator at spawn time, release on destroy. Each pool stores per-instance OAM slot mapping (`_pool_<id>_oam[N]`). Static ranges waste precious OAM slots (GB only has 40) when pools aren't full.

### Verification Strategy
- **D-04:** Belt and suspenders — JVM-level codegen tests verify generated C contains correct arrays/loops/move_sprite patterns, THEN MCP play-through of shmup confirms runtime behavior (bullets fly, enemies descend, collisions work, game over triggers).
- **D-05:** Add a generic pool codegen test that exercises spawn/move/destroy/collision patterns independent of any specific game. Validates the engine contract, not shmup-specific patterns.
- **D-06:** Shmup is the primary validation target, but pool patterns must be general enough for future consumers (racer AI vehicles in Phase 07.4, platformer projectiles in 07.5).

### Backend Boundary (CRITICAL DESIGN PRINCIPLE)
- **D-07:** IR stays minimal — no new IR nodes for pool position sync. The existing `PoolSpawnActor`, `PoolForEachActive`, `PoolDestroyActor` ops are sufficient. The backend is smart enough to infer that spawn implies position init + display sync, and that forEachActive bodies writing to template actor properties need per-instance array reads/writes + display sync.
- **D-08:** The fix is ENTIRELY contained in the GBDK backend layer (`gbkt-backend-gbdk`). No changes to `gbkt-ir`, `gbkt-lang`, or `gbkt-analysis`. This preserves the backend-agnostic architecture — a future GBA backend would translate the same IR to different display primitives.
- **D-09:** Avoid overfitting — the codegen must not accumulate game-specific special cases. Every pattern generated must be reusable for any game that uses entity pools, not just the shmup. The framework is a true engine, not an optimized set of code that works only for written examples.
- **D-10:** IR is the developer's lowest escape hatch but never exposes hardware operations. Developers can write custom IR ops for unusual behavior, but should never need to think about OAM, VRAM, or platform-specific primitives. The backend handles all hardware translation.

### Bug Handling (carried forward from Phase 07)
- Fix inline immediately, generic framework fixes only
- One atomic commit per bug with regression test
- All ROMs must build at all times

### Claude's Discretion
- Exact codegen implementation details (how the backend infers display sync from body analysis)
- Dynamic OAM allocator design (free list, bitmap, or linear scan)
- Test structure and assertion patterns for generic pool tests
- MCP play-through sequence and checkpoint strategy

## Existing Code Insights

### Reusable Assets
- **ActorPoolIR** — Complete IR type with id, actorTemplateId, config, instanceProperties, deathCallback
- **Pool ScriptOps** — PoolSpawnActor, PoolDestroyActor, PoolForEachActive, PoolDestroyAll all exist with proper fields
- **ActorPoolBuilder DSL** — `pool()`, `spawn()`, `destroy()`, `forEachActive()`, `destroyAll()` all working
- **GBDKSystemVisitor** — Already generates `_pool_<id>_active[N]` arrays and init/spawn/destroy/active_count functions — needs extension for position arrays and display sync
- **ScriptOpVisitor** — Already handles pool ops but doesn't generate position writes or move_sprite calls in forEachActive bodies

### Established Patterns
- Non-pooled actors use `move_sprite(actor_oam_slot, actor_x, actor_y)` for display sync — pooled entities should follow the same pattern but indexed
- `GBDKCollectionCodegen` has generic pool data/function generation for `IRCollPool` — may overlap or complement ActorPool codegen
- Visitor codegen pattern: IR op → C AST node → pretty-printer → C string

### Integration Points
- `GBDKSystemVisitor.buildActorPoolStateVars()` — Where position arrays should be generated alongside existing active arrays
- `GBDKSystemVisitor.buildActorPoolFunctions()` — Where spawn/destroy functions need position array init and display sync
- `ScriptOpVisitor.visitPoolForEachActive()` — Where the loop body needs position array reads/writes and post-body display sync
- OAM slot allocation needs coordination with non-pooled actor slot assignment (existing in actor codegen visitors)

<specifics>
## Specific Ideas

- The framework should be a **true engine**, not an optimized codebase that only works for written examples. Every codegen pattern must be reusable for any game using entity pools.
- IR is the developer's lowest escape hatch but never exposes hardware. "I don't want to remove the possibility of plugging in other backends at the inception of gbkt."
- Don't "overfit the codegen" — avoid accumulating game-specific special cases that result in "overfitted loads of code in the codegen package."
- Dynamic OAM allocation chosen specifically because static ranges are "usually incorrect" — they waste slots and don't scale across diverse game types.

</specifics>
