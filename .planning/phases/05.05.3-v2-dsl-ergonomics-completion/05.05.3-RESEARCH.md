## User Constraints (from CONTEXT.md)

### Locked Decisions

**Overall Vision & Philosophy**
- v1-inspired, v2-native: Use v1 conventions where they fit, let v2's script-op model shape the DSL naturally where it diverges
- No magic strings: Variable/actor/scene names inferred from Kotlin property names. No dual naming with string parameters. Optional string override for rare edge cases (C name conflicts)
- Declarative, not imperative: Game code should describe WHAT happens, not step-by-step HOW
- Both reactive rules AND lifecycle: `whenever(condition) { effect }` for behavior, `enter/frame/exit` for structure — both are first-class
- Compose-like scalability: Must work with thousands of LOC. Proper subpackages, imports, domain-organized builders
- Error quality matters: Two layers — Kotlin compiler catches type errors at compile time, DSL validation catches semantic errors at build time
- Example games are the spec: If Pong, Breakout, and Explorer look clean and natural, the DSL is good enough
- IDE discoverability: Type system should guide developers via autocomplete

**Input API**
- Type-safe input objects: `dpad.up.held`, `dpad.left.pressed`, `buttons.a.pressed` returning v2 `Expr`
- These replace `dpadHeld("up")`, `dpadPressed("up")`, `buttonPressed("a")`, `buttonHeld("a")` string-based calls

**Type-safe Scene References**
- `scene()` already returns `SceneRef` and `navigate(SceneRef)` already exists
- The gap: examples still use `navigate("game")` string literals throughout
- Fix: migrate all example games to use `navigate(sceneRef)` where sceneRef is captured from `scene()` return value

**Actor Name Inference**
- `actor()` currently requires a string ID: `actor("paddle1") { ... }`
- Need delegate-based syntax: `val paddle1 by actorDef { ... }` to infer name from property
- Same `provideDelegate` pattern as `VarDelegate` and `ArrayDelegate`

**Collision DSL in Examples**
- `collides()` method EXISTS on `ActorRef`: `fun ActorRef.collides(other: ActorRef): Expr`
- The gap: examples still use 4-deep nested `whenever` blocks for collision
- Fix: replace nested wheneevers with `whenever(ball.collides(paddle)) { }` in all three games

**Color Definitions**

**Variable Delegate Syntax (Already Done — do NOT re-implement)**

- Operator extensions on AssignableVar, ActorPropertyRef, ArrayVar — COMPLETE

## Summary

Phase 05.05.3 closes six specific ergonomic gaps that were written into the 05.05.2 CONTEXT.md but dropped during planning. All gaps are DSL-layer additions in `gbkt-lang` — no IR node types need to be added and no codegen changes are required for most gaps.

The largest new feature is **type-safe input API**: typed `dpad` and `buttons` objects (analogous to v1's `Input.kt` but producing v2 `Expr` instead of v1 `Condition`). The second significant feature is **actor name inference** via a delegate pattern analogous to `VarDelegate`. The other four gaps — type-safe scene refs, collision DSL in examples, custom actor properties, and DMG color constants — are small additive changes to existing files.

Custom actor properties (`i8Prop`) require careful design because they are scoped to an `ActorBuilder` block but need to participate in the global VariableDef list. The cleanest implementation is to store them as prefixed variables (`ball_dx`) in `GameIR.variables`, with `ActorBuilder` accumulating prop defs and the `ActorRef` exposing them as `ActorPropertyRef` accessors.

**Primary recommendation:** Implement in order: (1) type-safe input API as a new file `InputBuilders.kt` in gbkt-lang, (2) actor delegate (`actorDef`), (3) migrate examples to use both, (4) add `i8Prop`/`u8Prop` to `ActorBuilder`, (5) add DMG color constants. This ordering minimizes coupling and lets example migration serve as integration tests.

## Architecture Patterns

### Pattern 1: V2 Input API Design

**What:** New singleton objects `dpad` and `buttons` that expose typed direction/button accessors returning `Expr` (v2).

**Key insight:** The v2 `ScriptBuilder.dpadHeld("up")` already emits `CallExpr("dpad_held", listOf(VarRef("J_UP")))`. The new type-safe API must produce identical IR expressions — it is purely a DSL surface change.

**The GBDK constant mapping** in `buttonToGbdkConstant()` is private to `ScriptBuilder`. It must be extracted or duplicated for the new input objects.

**Recommended design:**
```kotlin
// gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/v2/InputBuilders.kt

/** Typed reference to a single d-pad direction or button. */
class InputRef(private val gdbkConstant: String, private val heldFn: String, private val pressedFn: String) {
    /** True while this input is held. */
    val held: Expr get() = CallExpr(heldFn, listOf(VarRef(gdbkConstant)))
    /** True on the frame this input was first pressed (edge-triggered). */
    val pressed: Expr get() = CallExpr(pressedFn, listOf(VarRef(gdbkConstant)))
    /** True on the frame this input was released. */
    val released: Expr get() = CallExpr("button_released", listOf(VarRef(gdbkConstant)))
}

@Suppress("ClassNaming") // DSL convention: lowercase singleton
object dpad {
    val up    = InputRef("J_UP",    "dpad_held", "dpad_pressed")
    val down  = InputRef("J_DOWN",  "dpad_held", "dpad_pressed")
    val left  = InputRef("J_LEFT",  "dpad_held", "dpad_pressed")
    val right = InputRef("J_RIGHT", "dpad_held", "dpad_pressed")
    /** True when any d-pad direction is held. */
    val any: Expr get() = CallExpr("dpad_any", emptyList())
    /** True when no d-pad direction is held. */
    val none: Expr get() = ... // BinaryExpr NOT(dpad_any())
}

@Suppress("ClassNaming")
object buttons {
    val a      = InputRef("J_A",      "button_held", "button_pressed")
    val b      = InputRef("J_B",      "button_held", "button_pressed")
    val start  = InputRef("J_START",  "button_held", "button_pressed")
    val select = InputRef("J_SELECT", "button_held", "button_pressed")
}
```

**Backward compatibility:** `dpadHeld("up")`, `buttonPressed("a")` remain in `ScriptBuilder` but get `@Deprecated(WARNING)` annotations pointing to the new API.

**Naming conflict with v1:** The v1 module (`gbkt-core`) already has `object dpad` and `object buttons` in `io.github.gbkt.core.input.Input`. The v2 DSL lives in `io.github.gbkt.core.dsl.v2` — these are different packages and there is no conflict for v2 game authors who import `io.github.gbkt.core.dsl.v2.*`. The existing wildcard import in example games covers it.

**Missing C helper `button_released`:** The current `GBDKPipelineV2.kt` generates `button_pressed()` and `button_held()` C helpers, but NOT `button_released()`. If we expose `.released` in the DSL, codegen must also generate the helper. Check `GBDKPipelineV2.kt` lines ~358-370, ~631-667 before implementing. RECOMMENDATION: Defer `.released` to reduce scope, or add the C helper in the same plan.

**Confidence:** HIGH — pattern is identical to existing `dpadHeld` implementation.

### Pattern 2: Actor Delegate (`actorDef`)

**What:** A `provideDelegate`-based factory that infers the actor's string ID from the Kotlin property name. Returns `ActorRef` just like the current `actor(id, block)` call.

**Current state:** `actor("paddle1") { ... }` requires the string. The CONTEXT decision says `val paddle1 = actor { }` should infer.

**Key consideration:** `actor()` currently returns `ActorRef` directly (not a delegate). To support inference without breaking existing code, two approaches are possible:

**Option A (recommended): Add overload `actor(block)` returning `ActorDelegate`**
```kotlin
// New overload — no name param, returns delegate
fun actor(block: ActorBuilder.() -> Unit): ActorDelegate = ActorDelegate(null, block)

// Existing overload unchanged (backward compat)
fun actor(id: String, block: ActorBuilder.() -> Unit): ActorRef { ... }

class ActorDelegate(private val nameOverride: String?, private val block: ActorBuilder.() -> Unit) :
    ReadOnlyProperty<Any?, ActorRef> {
    private var ref: ActorRef? = null
    operator fun provideDelegate(thisRef: Any?, property: KProperty<*>): ReadOnlyProperty<Any?, ActorRef> {
        val name = nameOverride ?: property.name
        // Register with current GameBuilder
        val gameBuilder = GameBuilderContext.current ?: error("actor {} must be called inside game {}")
        ref = gameBuilder.registerActor(name, block)
        return this
    }
    override fun getValue(thisRef: Any?, property: KProperty<*>): ActorRef = ref!!
}
```

This allows: `val paddle1 by actor { position(16, 64); sprite(...) }` — name inferred as "paddle1".

**Option B: Rename to `actorDef` for the delegate version**
Less disruptive but less discoverable. CONTEXT says "val paddle1 = actor { }" which implies the same function name.

**RECOMMENDED: Option A** — overload `actor()` with no-name variant returning `ActorDelegate`.

**Interaction with `setPosition(actor.id, ...)` calls in examples:** Once actors use delegates, `setPosition(paddle.id, ...)` still works (ActorRef.id is still the inferred name). Breakout and Explorer each have one `setPosition(actor.id, ...)` call — these can optionally be migrated to `actor.moveTo(x, y)` in the same pass.

**Confidence:** HIGH — same pattern as VarDelegate/ArrayDelegate; provideDelegate is well-established.

### Pattern 3: Type-Safe Scene References (Migration)

**What:** `scene()` already returns `SceneRef`. `navigate(SceneRef)` already exists. The gap is that all three example games still use `navigate("game")` string literals.

**Required change:** No new code in `ScriptBuilder` or `SceneBuilder`. Pure example game migration.

**Pattern:**
```kotlin
// Before (working but magic string)
scene("game") { ... }
// ...
whenever(buttonPressed("start")) { navigate("game") }

// After (type-safe)
val gameScene = scene("game") { ... }
// ...
whenever(buttons.start.pressed) { navigate(gameScene) }
```

**Ordering constraint:** Scene definition must come BEFORE use in the DSL lambda. In all three example games, scenes are defined in order (title → game → gameover), then navigated to from within later-defined scenes' frame blocks. Since the outer `game { }` lambda runs top-to-bottom, `val gameScene = scene("game") { ... }` produces the SceneRef before the navigation is called. This pattern works correctly.

**Exception:** In `PongV2.kt`, the `navigate("game")` inside the `title` scene's `frame` block references the `game` scene, which is defined AFTER the title scene. This is fine — the frame block lambda runs at game-time (not at DSL build time), so the SceneRef captured in the surrounding closure is already resolved.

Wait — this is a closure capture issue. Let me re-check: in Kotlin, `val gameScene = scene("game") { ... }` is called during the `game { }` lambda execution. The order is:
1. `val titleScene = scene("title") { frame { whenever(...) { navigate(???) } } }` — frame block is a lambda stored, not executed yet
2. `val gameScene = scene("game") { ... }` — returns SceneRef("game")

If `navigate(gameScene)` is used inside the title scene's frame block, the `gameScene` variable must be declared before the title scene (since Kotlin local variables are not forward-declared). This is a real ordering constraint.

**Solution options:**
1. Reorder scenes so referenced scenes are declared first — forces reverse dependency order (gameover before game, game before title). Awkward.
2. Use late-init `lateinit var gameScene: SceneRef` — not `lateinit` for non-null value types; requires `var` instead of `val`.
3. Keep string-based `navigate("game")` for cross-scene navigation while using SceneRef for same-scene self-reference patterns.
4. Use `var` declarations: `var gameScene = SceneRef(""); scene("game") { gameScene = SceneRef("game") ... }` — hacky.
5. Simply define all scenes first (as properties), then reference them.

**Actual recommended approach:** Declare a `val` for each scene BEFORE filling its body, using a two-pass pattern that Kotlin doesn't naturally support. The cleanest is to capture the SceneRef after definition:

```kotlin
// Works because navigate(gameScene) is inside a lambda captured at frame time
val titleScene: SceneRef
val gameScene: SceneRef
val gameoverScene: SceneRef

// PROBLEM: Kotlin doesn't support late-binding of val like this
```

Actually, the simplest solution that works: since all three example games are small and cross-navigation only goes one direction (title→game→gameover→title), we can just define scenes in reverse dependency order. The CONTEXT says this is valid. OR we can keep `navigate("gameover")` as strings for cross-scene refs and only switch to `navigate(sceneRef)` when the scene is already declared above.

**Confidence:** MEDIUM — The ordering constraint is real. The planner needs to decide: full SceneRef migration with reordering OR partial (same-scene refs only). RECOMMENDATION: Migrate what's naturally easy (forward references), keep strings where reordering would harm readability.

### Pattern 4: Collision DSL in Examples

**What:** `ActorRef.collides(other: ActorRef): Expr` already exists in `ActorBuilder.kt` line ~319. The examples just don't use it.

**Current collision pattern in Pong:**
```kotlin
whenever(ball.x isBelow 20) {
    whenever(ball.x isAtLeast 4) {
        whenever(ball.y isAtLeast paddle1.y) {
            whenever(ball.y isBelow (paddle1.y + 16)) { ballDx set 1 }
        }
    }
}
```

**The `collides()` function** emits `CallExpr("collides", [VarRef(ball.id), VarRef(paddle1.id)])`. The backend C codegen must handle this `CallExpr`. Let me verify this is implemented in GBDKPipelineV2.

**Action required:** Verify that `CallExpr("collides", ...)` is handled in the ExprVisitor codegen. If not, the nested `whenever` pattern is the only working approach and collides() cannot be used until codegen supports it.

Check: `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/visitor/ExprVisitor.kt` for `collides` handling.

**If codegen handles it:** Migrate pong paddle collision, breakout paddle collision. Note these use AABB-style position math that `collides()` may not replicate exactly (hitbox vs position math). The `collides()` IR produces a C function call `collides(ball, paddle)` — verify what C function that maps to and whether it matches the hand-coded logic.

**If codegen does NOT handle it:** Two choices: (a) add codegen support in the same phase, or (b) leave examples as-is. RECOMMENDATION: If codegen support is trivial to add, add it. If complex, leave examples with nested `whenever` and document why.

**Confidence:** MEDIUM — Depends on codegen support status. Research the ExprVisitor implementation before planning tasks.

### Pattern 5: Custom Actor Properties (`i8Prop`/`u8Prop`)

**What:** Inside an `actor { }` builder block, allow declaring per-actor variables:
```kotlin
val ball = actor("ball") {
    position(80, 72)
    sprite(...)
    var dx by i8Prop(1)   // per-actor custom property
    var dy by i8Prop(1)
}
// Later: ball.dx += ballDx
```

**Implementation design:**
- `i8Prop(initial)` returns an `ActorPropDelegate` (analogous to `I8VarDelegate`)
- `provideDelegate` captures property name, registers a `VariableDef` with name `"${actorId}_${propName}"` in the GameBuilder
- `getValue` returns an `ActorPropertyRef(actorId, propName)`
- `ActorPropertyRef` operators already exist — no new operators needed
- `ActorBuilder` needs to accumulate prop defs and pass them to `GameBuilder` on `build()`

**IR storage:** Custom props are global variables with prefixed names (`ball_dx`). They are stored in `GameIR.variables`. No new IR types needed. The `PropertyAccessExpr(actorId, propName)` in the DSL maps to `VarRef("${actorId}_${propName}")` at codegen — or the ExprVisitor needs to handle PropertyAccessExpr with custom props differently from built-in props (x, y, visible).

**Codegen impact:** Check how `ExprVisitor.visitPropertyAccessExpr()` handles `ball.x` vs a hypothetical `ball.dx`. Built-in props (x, y, visible) likely map to GBDK actor state structs. Custom props should map to prefixed globals. This requires codegen to know which props are built-in vs custom — either by convention or by passing the prop list to the visitor.

**Complexity assessment:** MEDIUM. The DSL side is straightforward (delegate pattern). The codegen side needs verification. RECOMMENDATION: Implement DSL delegate only, emit custom props as prefixed globals, and verify codegen handles PropertyAccessExpr for custom names.

**Confidence:** MEDIUM — DSL pattern is clear; codegen implications need investigation.

### Pattern 6: DMG Color Constants

**What:** DMG preset constants for 4-shade palettes: `WHITE`, `LIGHT_GRAY`, `DARK_GRAY`, `BLACK`. GBC hex helpers with RGB555 fidelity warning.

**Existing:** `gbkt-core/src/main/kotlin/io/github/gbkt/core/graphics/Palette.kt` has `PalettePreset` enum and `PaletteBuilder` — but these are v1 types.

**Scope for this phase:** Add constants/helpers to the v2 DSL layer (`gbkt-lang`). Minimal implementation: a `DmgPalette` object or top-level constants. GBC is deferred per CONTEXT.

**Recommended design:**
```kotlin
// gbkt-lang/.../dsl/v2/ColorConstants.kt

/** DMG (4-shade grayscale) palette indices */
object DmgColor {
    const val WHITE      = 0
    const val LIGHT_GRAY = 1
    const val DARK_GRAY  = 2

```

These are compile-time constants used in palette builder calls, not IR expressions. No codegen impact.

**GBC color helpers (if in scope):** A `gbc(r, g, b)` function converting 0-255 RGB to RGB555 with a build-time warning if the conversion loses precision. Deferred per CONTEXT.

**Confidence:** HIGH — pure Kotlin constants, zero risk.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Input type IR | New ScriptOp/Expr subtypes for input | `CallExpr("button_pressed", ...)` / `CallExpr("dpad_held", ...)` | Codegen already handles these function calls; no new IR needed |
| Actor prop storage | New IR field `ActorIR.customProps` | `GameIR.variables` with prefixed names | GameIR is a data class in gbkt-ir (sealed hierarchy); adding fields requires updating all consumers |

| Collision codegen | New CollisionOp IR type | `CallExpr("collides", ...)` | Already the pattern; backend generates C `collides()` function |

## Common Pitfalls

### Pitfall 1: Naming Conflict Between v1 and v2 `dpad`/`buttons`

**What goes wrong:** If a game imports both `io.github.gbkt.core.input.*` (v1) and `io.github.gbkt.core.dsl.v2.*` (v2), there will be two `dpad` objects.
**Why it happens:** v1 has `object dpad` in `io.github.gbkt.core.input.Input`; new v2 will have `object dpad` in `io.github.gbkt.core.dsl.v2.InputBuilders`.
**How to avoid:** Example games only import `io.github.gbkt.core.dsl.v2.*` — the v1 input types are not in scope. No conflict in practice. The potential issue is for advanced users who might import both.
**Warning signs:** Compile error "ambiguous reference to dpad" in game files that import both packages.

### Pitfall 2: `button_released` C Helper Missing from Codegen

**What goes wrong:** Exposing `.released` property on `InputRef` without the corresponding `button_released()` C helper in `GBDKPipelineV2.kt`.
**Why it happens:** Only `button_pressed` and `button_held` helpers are currently generated.
**How to avoid:** Either add the C helper before exposing `.released`, or omit `.released` from this phase.
**Warning signs:** Compilation of generated C fails with "undefined: button_released".

### Pitfall 3: Actor Delegate vs `GameBuilderContext` Scope

**What goes wrong:** `val paddle by actor { }` called outside a `game { }` block.
**Why it happens:** `GameBuilderContext.current` is null outside the game builder lambda.
**How to avoid:** Add explicit null check in `ActorDelegate.provideDelegate` with helpful error message (same as `DSLValidationError` pattern used elsewhere).
**Warning signs:** NullPointerException or silent failure (actor not registered) instead of clear error.

### Pitfall 4: Custom Actor Property Naming Collision

**What goes wrong:** Two actors both declare `var dx by i8Prop(1)` — both generate a global `"dx"` VariableDef.
**Why it happens:** If prop names aren't prefixed with actor ID.
**How to avoid:** Always prefix: `"${actorId}_${propName}"` → `"ball_dx"`, `"paddle_dx"`. Enforce in `ActorPropDelegate.provideDelegate`.
**Warning signs:** C compile error "redefinition of _dx" or silent variable sharing between actors.

### Pitfall 5: Scene Reference Forward-Declaration Ordering

**What goes wrong:** `val titleScene = scene("title") { frame { whenever(dpad.up.held) { navigate(gameScene) } } }` where `gameScene` is declared after `titleScene`.
**Why it happens:** Kotlin local variable `gameScene` is captured by the frame lambda closure. Since `gameScene` is declared after `titleScene` in source, it's uninitialized when the closure is created.
**How to avoid:** Declare `SceneRef` variables before the scenes that reference them, OR keep string literals for forward-navigation (`navigate("game")`) and only use `navigate(sceneRef)` for backward/self-navigation.
**Warning signs:** Kotlin compile error "Variable 'gameScene' must be initialized before use" or runtime NPE.

## Key Investigation: Custom Props IR Storage Strategy

Two options for custom actor properties:

**Option A: Store as prefixed globals in `GameIR.variables`**
- `ActorBuilder` accumulates prop definitions
- On `GameBuilder.build()`, prefix all props with actor ID and add to `variables` list
- `PropertyAccessExpr("ball", "dx")` in IR → codegen converts to `_ball_dx` variable access
- ExprVisitor must distinguish built-in props (x, y, visible → GBDK actor struct) from custom props (→ global var)
- Codegen needs a lookup: "is this prop custom?" — requires passing prop name list to ExprVisitor

**Option B: Add `customProps: List<VariableDef>` to `ActorIR`**
- Cleaner IR semantics
- Requires updating `ActorIR` data class (in `gbkt-ir`) and all consumers
- `ActorIR` is in `gbkt-ir` module which is a shared module — changes propagate

**RECOMMENDATION: Option A (prefixed globals)** — fewer IR changes, ExprVisitor already handles `PropertyAccessExpr`, just needs a check for custom vs built-in. The "is custom" lookup is a Map built from `GameIR.variables` filtered by `actorId` prefix.
