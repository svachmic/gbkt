## Summary

Phase 09.4 is a pure cross-tier token rename — `smiley` → `ball` — within one Gradle subproject (`gbkt-examples/simple-physics/`). No framework code changes. No new IR nodes. No new packages.

The rename propagates from a single source truth: the Kotlin property declaration `val smiley by actor { ... }` at `SimplePhysics.kt:64`. The `ActorDelegate.provideDelegate` mechanism derives the actor-ID `"ball"` from the new property name automatically (Project Rule #1 / `feedback_no_magic_strings`). The codegen pipeline (`GBDKPipelineV2`) derives every `_smiley_*` symbol in generated C from the actor-ID in the IR — so the rename ripples through `build/gbkt/generated/main.c` (eight smiley sites) and `build/gbkt/generated/sprites/smiley.c|h` with no manual codegen edits required.

The evidence artifacts (UAT screenshot re-baseline + `rename-diff.md`) are the most mechanical-yet-critical tasks: they provide the verifier's proof that (a) the renamed ROM still renders the sprite and (b) the generated-C rename is shape-preserving (identical structure, only symbol tokens changed).

**Primary recommendation:** Rename DSL property first; then tests; then docs; then produce evidence artifacts in a final gated wave. The docs wave is independent of tests but should merge after tests are GREEN to prevent a reviewer seeing stale test names alongside the updated docs.

## Q2: Asset pipeline implications of renaming `smiley.png` → `ball.png`

[VERIFIED from `ConvertSpritesTask.kt` and `GenerateCTask.kt` source; VERIFIED from `GbktPlugin.kt` task wiring]

**How the pipeline reads assets:**

1. `GenerateCTask` has `@InputDirectory @PathSensitive(RELATIVE) assetDirectory`. When `res/sprites/ball.png` replaces `res/sprites/smiley.png`, Gradle's incremental build detects the input directory change and re-runs `generateC` automatically.

2. `ConvertSpritesTask` at `ConvertSpritesTask.kt:99-122` scans the generated `main.c` for `#include "sprites/ball.h"` (after the Kotlin rename updates the codegen path). It then looks up `res/sprites/ball.png` by removing `.h` suffix and appending `.png` — i.e., `includePath.removeSuffix(".h") + ".png"` at L111. This is fully name-driven.

3. Array naming in generated sprites: `ConvertSpritesTask.kt:174` — native array name is `${stemName}_tiles` (= `ball_tiles`). Path-based alias at L177-178 is `sprites_ball_tiles`. The generated `main.c` will call `set_sprite_data(0u, 1u, sprites_ball_tiles)`.

**Stale build artifact risk (CRITICAL):**

After asset rename, `build/gbkt/generated/sprites/` will still contain `smiley.c` and `smiley.h` from the prior build. These files are in the `@OutputDirectory` of `ConvertSpritesTask` and are NOT automatically deleted when the input changes — Gradle only adds new outputs, it does not remove stale ones from prior runs.

**Without `clean`:** `lcc` will compile both `smiley.c` (stale, now unreferenced) and `ball.c` (new). The stale `smiley.c` may or may not cause linker conflicts, but it creates ghost symbol entries (`sprites_smiley_tiles` defined but unreferenced). At minimum this inflates the ROM — at worst, symbol name collisions could cause link errors if `BANKREF(smiley)` and `BANKREF(ball)` clash.

**Mitigation:** The roadmap success criterion already mandates a `clean` step: `./gradlew :gbkt-examples:simple-physics:clean :gbkt-examples:simple-physics:buildRom`. Running `clean` removes `build/gbkt/generated/sprites/smiley.c|h` before the new build produces `ball.c|h`. This is non-negotiable.

**Gradle task input tracking:** The `assetDirectory` property is `@PathSensitive(PathSensitivity.RELATIVE)`, meaning Gradle tracks the relative paths of files within the directory. A rename from `smiley.png` to `ball.png` IS detected as an input change. However, since `ConvertSpritesTask` is `@CacheableTask`, Gradle may restore a stale `smiley.c` from the build cache if the cache entry predates the rename. `clean` before `buildRom` eliminates this risk entirely.

## Q6: PLAYBOOK ↔ MCP-agent grep contract

[VERIFIED from `VariableInspector.kt:62-99`, `.noi` file content, and `game_metadata.json` content]

**How variable names flow from code to MCP:**

1. `GBDKPipelineV2` emits `__ball_x` / `__ball_y` in `.noi` (GBDK double-underscore convention; confirmed by current `__smiley_x 0xC0B1` entry in live `.noi`).

3. `VariableInspector.readAll()` produces `{"ball_x": N, "ball_y": N, ...}` in the Observation `variables` map.

**How actor names flow:**

1. `game_metadata.json` (emitted by `GBDKPipelineV2.buildMetadataFile()`) will contain:

**PLAYBOOK script contracts are position-variable agnostic:** Every `emulator_read_variable` in PLAYBOOK reads `spdX`, `spdY`, `posX`, `posY` — these are DSL-declared variables, not actor-position variables. ## Q9: Anti-patterns and pitfalls drawn from 09.3 closeout

### Pitfall 1: Forgetting to update `EVIDENCE_DIR` in `SimplePhysicsUatTest.kt`
**What goes wrong:** UAT screenshots from the re-baseline overwrite the frozen 09.3 `behavior2-jump-impulse.png`. The 09.3 evidence file changes content (now showing `_ball_x`/`_ball_y` in the JSON sidecar), which violates D-A2-01.
**How to avoid:** Update `EVIDENCE_DIR` at `SimplePhysicsUatTest.kt:47-51` as part of Wave 2. This is not in CONTEXT.md's explicit footprint but is essential.
**Warning signs:** After Wave 2, running the UAT test without updating `EVIDENCE_DIR` writes into `…/09.3-polish-…/evidence/uat-screenshots/`.

### Pitfall 2: Skipping `clean` before `buildRom`
**What goes wrong:** `build/gbkt/generated/sprites/smiley.c|h` from the prior build lingers. The `lcc` linker compiles both `smiley.c` (stale, now unreferenced by `main.c`) and `ball.c`. The stale sprite C file may cause: (a) duplicate BANKREF symbols, (b) ghost tile data arrays in the ROM, (c) inflated ROM size, or (d) link errors.
**How to avoid:** Always run `:clean` before `:buildRom` in the smoke gate task. The roadmap success criterion already mandates this.
**Warning signs:** `ls build/gbkt/generated/sprites/` shows both `smiley.c` and `ball.c` after buildRom.

### Pitfall 3: Partial rename leaving `smiley` in PLAYBOOK's "Bug B workaround" section
**What goes wrong:** PLAYBOOK L43-48 contains 2 `smiley` refs (L45 and L48). If only L5 and L11 are renamed, MCP agents reading the PLAYBOOK for code-reference patterns see `smiley.x set` / `smiley.moveTo` — contradicting the Kotlin source.
**How to avoid:** CONTEXT.md D-A3-01 explicitly lists "all 4 refs (L5, L11, L45, L48)". The planner must not conflate the L41 anti-overfitting carve-out (preserved, no `smiley` there) with the L45/L48 code refs (renamed).

### Pitfall 4: Treating `rename-diff.md` as documentation (violates D-A4-01/D-A4-02)
**What goes wrong:** Adding a pointer to `rename-diff.md` from README, CLAUDE.md, or a `09.4-evidence/README.md` "for discoverability."
**How to avoid:** The artifact lives in `.planning/` (planning-internal), is read by `gsd-verifier`, and requires no doc-tier anchor. Git log + CONTEXT.md are the full trail.

### Pitfall 5: Forgetting the todo lifecycle step
**What goes wrong:** `.planning/todos/pending/simple-physics-rename-smiley-to-ball.md` remains in `pending/` after phase completion, showing up in future `/gsd:discuss-phase` scans as unresolved.
**How to avoid:** Move to `.planning/todos/completed/` (not `done/` — CONTEXT.md has a typo; the actual directory is `completed/`).
**Warning signs:** `ls .planning/todos/pending/` still shows `simple-physics-rename-smiley-to-ball.md` after final commit.

### Pitfall 6: Touching historical artifacts
**What goes wrong:** Renaming `smiley` → `ball` in `.planning/phases/09-port-simple-physics-gbdk-example-to-gbkt/` evidence files, `09.3-…/evidence/post-09.3-main.c`, or the 09.3 UAT screenshots.
**How to avoid:** Explicitly scope all edits to `gbkt-examples/simple-physics/` (non-build subdirs) and the new 09.4 planning artifacts. The grep gate in Wave 4 excludes historical planning dirs from scope.

### Pitfall 7: Running `SimplePhysicsEmissionTest` after Wave 1 (before Wave 4 clean buildRom)
**What goes wrong:** `SimplePhysicsEmissionTest` calls `GBDKPipelineV2().generate(simplePhysics.build())` in-memory and checks the generated C shape. After the Kotlin rename (Wave 1), the in-memory pipeline produces `_ball_x`/`_ball_y`. The `SimplePhysicsEmissionTest` assertions check for patterns like `"_spdY = -$JUMP_ACCELERATION_IN_SUBPIXELS"` — these still pass. BUT: the test's `EVIDENCE_DIR` points to `09-port-simple-physics-gbdk-example-to-gbkt/evidence/tier1-shape/` (hardcoded). The evidence files written there will now show `_ball_*` symbols. This is acceptable (the emission test doesn't assert on actor variable names), but the executor should be aware that the tier1-shape evidence files in Phase 09's evidence dir will be overwritten with post-rename content. This is a cosmetic issue, not a functional one.
