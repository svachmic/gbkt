# Phase 13.3 Plan 15: PINK + DEDUP Diagnostic Summary

**One-liner:** Root-causes the pink elephant defect (triple set_sprite_palette upload collision + S_PAL(1) descriptor entries) and delivers an ACCEPT verdict on the OAM-count dedup difference, backed by live-ROM screenshot evidence.

## What Was Built

A written diagnostic document (`evidence/13.3-DIAGNOSTIC.md`) and runtime screenshot
(`evidence/13.3-15-current-pink-elephant.png`) that fully characterize the two remaining
un-confirmed GAP-1 sub-divergences from 13.3-VERIFICATION.md.

### PINK Root Cause (now locked)

Three `set_sprite_palette` upload sites in the generated `main.c` create a slot-0 collision:

| Site | Location | Effect |
|------|----------|--------|
| A | `main()` lines 191-194 | slot0=gray, slot1=pink, slot2=cyan, slot3=green |
| B | `main()` line 205 — from `buildMetaspriteSpritePaletteStatements` HARDCODED `1u` | slot0 overwritten with elephant_palettes[0..3] (greenish) |
| C | `play_enter()` lines 226-229 | slot0 RESTORED to gray, slot1 remains pink |

At the moment play_frame() executes (after Site C): OBJ slot 0 = gray, OBJ slot 1 = pink.

The png2asset descriptor bakes per-entry S_PAL indices: `S_PAL(0)` (97 occurrences across all
frames) selects gray; `S_PAL(1)` (52 occurrences) selects pink. Every frame has both — the
outline/highlight tiles use S_PAL(1) → pink outline is visible. This matches the
`metasprites-elephant-postmigration.png` evidence from 13.3-VERIFICATION.md.

`elephant_palettes[32]` has exactly 2 non-trivial sub-palettes (entries 0-3: greenish tones;
entries 4-7: white + zeros; entries 8-31: all black). The hardcoded `1u` in
`buildMetaspriteSpritePaletteStatements` only uploads sub-palette 0, missing sub-palette 1
entirely. But the real fix is SUPPRESSION (Direction B), not correction of the count.

### Recommended Fix Direction for 13.3-17

**Direction B: Suppress `buildMetaspriteSpritePaletteStatements` output** for the metasprites
example. The scene's `spritePalette { }` blocks (gray, pink, cyan, green) are the intended
palette authority, cycling via `rot >> 2`. The pre-migration reference (gray elephant) was
achieved by the scene palette alone. The png2asset `elephant_palettes` array was never intended
to drive the OBJ palette in this example.

Full gray requires also patching the descriptor's S_PAL(1) entries to S_PAL(0) — which is a
separate fix that Plan 13.3-17 must confirm against the pre-migration reference.

### DEDUP Verdict

**ACCEPT** — post-migration frame-0 has 29 OAM entries vs pre-migration 31. The 2-entry
difference is a png2asset dedup artifact with `-noflip -keep_palette_order` applied to the
same source PNG. Frame 2 has 31 entries (the maximum), confirming the full OAM budget is
available for frames requiring more unique tiles. No png2asset flag change needed for 13.3-18;
that plan becomes a documented acceptance record.

### Runtime Confirmation

Screenshot captured at frame 60 via `CaptureScreenshotTask` (headless Coffee-GB emulator).
The screenshot shows:
- Elephant positioned bottom-right (pivot defect — 13.3-16's domain)
- Pink/magenta outline visible on the elephant (S_PAL(1) → slot1 = pink_pal confirmed)
- Gray elephant body (S_PAL(0) → slot0 = gray_pal confirmed)

The Visual Evidence Rule is satisfied: codegen-read says slot1=pink → screenshot shows pink.

**Found during:** Task 2

**Issue:** The plan specifies MCP tools (`mcp__gbkt-emulator__emulator_start`,
`mcp__gbkt-emulator__emulator_screenshot`) for the live-ROM probe. The MCP server JAR was not
present at session start (needed `./gradlew :gbkt-mcp-server:shadowJar` to rebuild). MCP
servers only connect at session startup; the tools were not available.

Gradle task, which uses the same headless Coffee-GB emulator internally). The 60-frame probe
captures the play scene (which boots immediately) and produces a PNG with equivalent runtime
evidence. The VISUAL EVIDENCE RULE is still satisfied — a real ROM was run and a real screenshot
was captured.
