## G2 — D-07 png2asset Frame-Count + Native Array Output Format

**VERIFIED from live build output at `gbkt-examples/metasprites/build/gbkt/generated/sprites/elephant.c`.**

### Array name patterns (CONFIRMED)

png2asset emits per-frame arrays and a pointer array with these exact name patterns:
```c
const metasprite_t elephant_metasprite0[] = { METASPR_ITEM(...), ..., METASPR_TERM };
const metasprite_t elephant_metasprite1[] = { ... };
...
const metasprite_t elephant_metasprite4[] = { ... };
const metasprite_t* const elephant_metasprites[5] = {
    elephant_metasprite0, elephant_metasprite1, elephant_metasprite2,
    elephant_metasprite3, elephant_metasprite4
};
```

Pattern: `<stemName>_metasprites[N]` where `stemName` comes from the output `.c` file stem (which is the metasprite `id` for Path A, since `includePath = "sprites/${ms.id}.h"` → `outputC = "${stemName}.c"` → `stemName = ms.id`).

### CRITICAL NAMING DISTINCTION

The CONTEXT.md describes these as `<id>_metasprites[]`. The current `MetaspriteVisitor.generateMetaspriteDescriptor()` emits `sprite_<id>_frames[]` (DIFFERENT namespace). Path A means:

- **Old (keep for escape-hatch):** `sprite_elephant_frames[idx]` (gbkt-generated)
- **New (Path A):** `elephant_metasprites[idx]` (png2asset-native)

The `game.h` extern currently says `extern const metasprite_t* const sprite_${ms.id}_frames[];`. For Path A, a NEW extern `extern const metasprite_t* const ${ms.id}_metasprites[];` is needed (and the old one removed for asset-driven metasprites).

### Frame count parse strategy (D-07 concrete approach)

The frame count is directly readable from the pointer-array declaration line:
```
const metasprite_t* const elephant_metasprites[5] = {
```
Parse strategy: regex `val frameCount = Regex("""${Regex.escape(stemName)}_metasprites\[(\d+)\]""").find(content)?.groupValues?.get(1)?.toInt()`

This is O(1), robust, and does NOT require parsing METASPR_ITEM entries. The array size is explicitly declared by png2asset. A NULL-terminated pointer array (`{…, nullptr}`) does NOT apply here — png2asset emits an explicit size.

Alternative fallback: count `const metasprite_t ${stemName}_metasprite\d+\[\]` definitions.

### D-02 confirmation (CONFIRMED)

`generateC` (JVM) does NOT need png2asset output. The sidecar `game_metadata.json` sprites[] is written by `GBDKPipelineV2.buildMetadataFile()` during `generateC` and contains `spritePath`/`includePath` for ConvertSpritesTask to read. `ConvertSpritesTask` runs AFTER `generateC` (per `CLAUDE.md` task graph: `generateC → convertSprites → compileRom`). D-07 validation runs inside `ConvertSpritesTask.convertSprite()` after png2asset succeeds — it reads the output `.c` file to extract the frame count, then can compare against a count parameter the planner threads through.

**Open sub-question for planner (D-07):** Where does the "author-declared count" come from at `ConvertSpritesTask` time? Options:
- (a) Add a `frameCount` field to the sidecar entry (written by `GBDKPipelineV2.buildMetadataFile()` from `MetaspriteIR`). This requires the IR to hold a declared count — which it currently does NOT for asset-driven metasprites (frames list is empty if only `sprite()` was called).
- (b) `ConvertSpritesTask` always derives the authoritative count from png2asset output and writes it back as a Gradle-property or to a sidecar; `generateC` (IR validation) reads it in a subsequent run. But this is cyclic with D-02's ordering.
- (c) The author declares `frameCount` in the DSL (e.g. a `frames(5)` call or via `wrapAt = N` on the `idx` variable), which flows to the sidecar as a declared-count field that `ConvertSpritesTask` validates against the parsed png2asset output.

Option (c) is cleanest — it keeps `generateC` → `convertSprites` ordering, puts the declared count in the sidecar, and `ConvertSpritesTask` fails loudly if `declaredCount != parsedCount`. `wrapAt = NUM_FRAMES` on the `idx` variable is already the user's source of truth for the frame count in Metasprites.kt. The planner should decide which DSL surface carries the declaration (explicit `frames(N)` on the metasprite block, or cross-reference `wrapAt` from the idx variable).

## G4 — D-09/D-11 Explicit-Slot Palette Plumbing

### GBCPalette.slot field (CONFIRMED)

```kotlin
// gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/CoreTypes.kt:327-335
data class GBCPalette(
    val name: String,
    val colors: List<GBCColor>,
    val slot: Int = -1, // -1 = auto-assign, 0-7 = explicit slot
    val type: PaletteType = PaletteType.BACKGROUND,
) {
    init { require(slot in -1..7) { "Palette slot must be -1 (auto) or 0-7, got $slot" } }
}
```

### SceneBuilder.palette() auto-increment (CONFIRMED at :172-178)

```kotlin
fun palette(palette: GBCPalette) {
    val slot = if (palette.slot >= 0) palette.slot else paletteOps.size
    paletteOps += SetPalette(palette.name, slot, palette.type)
}
```

The `GBCPalette.slot` field already supports explicit slots — it just requires the palette to be declared with `slot = N`. D-09's change is a DSL-level additive: allow `palette(gray, slot = 2)` at the scene call site. This means:

**Option A (builder-level override):** Add overload `fun palette(palette: GBCPalette, slot: Int)` in `SceneBuilder` that creates a temporary `SetPalette` with the explicit slot, ignoring `palette.slot`. This keeps the scene-load semantics clean (same palette can load into different slots in different scenes).

**Option B (copy-with):** `palette(gray.copy(slot = 2))`. Already works given `GBCPalette` is a `data class`! No new DSL surface needed — but it's less ergonomic than `palette(gray, slot = 2)`.

Option A is recommended per D-09 intent. It does NOT require changing `GBCPalette` declaration site (where `spritePalette { }` produces `slot = -1` by default).

### D-11 validation site

`SceneBuilder.build()` method (`:181`) runs after all `palette()` calls are accumulated in `paletteOps`. This is where:
1. **Range check:** All `SetPalette.slot` values must be in `0..7` (the `GBCPalette.slot` init check already validates `0..7` at declaration time, but the scene-load overload must also validate).
2. **Duplicate-slot check:** `paletteOps.groupBy { (it as? SetPalette)?.slot }.any { (_, ops) -> ops.size > 1 }` → fail with message.

Both checks live naturally in `SceneBuilder.build()` post-accumulation — consistent with where other IR-build-time validations are placed.

## Common Pitfalls

### Pitfall 1: Naming collision between png2asset arrays and gbkt arrays

**What goes wrong:** Path A uses `elephant_metasprites[]` (png2asset); the existing escape-hatch code uses `sprite_elephant_frames[]` (gbkt-generated). If both are emitted in the same compile unit, SDCC will have a duplicate-symbol or ambiguous-reference error.
**Why it happens:** The branch on `spritePath != null` must be enforced in BOTH `MetaspriteVisitor.generateMetaspriteDescriptor()` call sites AND in the game.h extern generation in `GBDKPipelineV2`.
**How to avoid:** The branch must be in ONE location — `GBDKPipelineV2` calling the visitor. Gate `generateMetaspriteDescriptor()` call AND the old `sprite_${ms.id}_frames` extern on `ms.spritePath == null`. Gate the new `${ms.id}_metasprites` extern on `ms.spritePath != null`.
**Warning signs:** SDCC linker error "duplicate symbol" or "undefined identifier" for `_metasprites` or `_frames` arrays.

### Pitfall 2: D-08 exactly-one guard leaves existing metasprites-stress in broken state

**What goes wrong:** If D-08 is enforced BEFORE metasprites-stress `frame {}` stubs are deleted, the `metasprites-stress:buildRom` will fail.
**Why it happens:** metasprites-stress currently has BOTH `sprite(asset(...))` AND `frame { tile(0,0,0) }` on each metasprite.
**How to avoid:** Plan ordering: migrate metasprites-stress (delete `frame {}` stubs) in the same plan or before the plan that adds D-08 validation.
**Warning signs:** Build failure: "metasprite 'elephant' must use exactly one of sprite(asset) or frame{}, not both".

### Pitfall 3: `Color` object in gbkt-lang references `GBCColor` from gbkt-ir — verify import chain

**What goes wrong:** If `Color` is placed in a package that doesn't have `gbkt-ir` as a compile dependency, import fails.
**Why it happens:** `GBCColor` is in `gbkt-ir`; `gbkt-lang` already depends on `gbkt-ir`. This is fine — no new dependency needed.
**How to avoid:** Place `Color.kt` in `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/` (same package as `GbcColor.kt`). Keep import `io.github.gbkt.core.ir.GBCColor` as is.

### Pitfall 4: MetaspriteIRTest tile-count assertions become stale after migration

**What goes wrong:** `MetaspriteIRTest` has 5 tests asserting `frames[0..4].tiles.size ≈ 31-33`. After Path A migration, `metasprites` has no `frame {}` blocks, so `frames.isEmpty()`. Tests fail.
**Why it happens:** Tests were written for the escape-hatch form; Path A moves tile data to png2asset.
**How to avoid:** Update `MetaspriteIRTest` to assert the new IR shape: `frames.isEmpty()` + `spritePath == "sprites/elephant.png"`. Create new assertions for the cutting flags (`spriteMode == SpriteMode.SPR8x8`, `frameWidth == 64`, `frameHeight == 48`).

### Pitfall 5: Byte-identity test fails until baseline re-pinned

**What goes wrong:** `MetaspritesGeneratedSpriteByteIdentityTest` is already RED (stale from 12.8). After Path A, it will remain RED until the baseline is regenerated with `-keep_palette_order` output.
**Why it happens:** The current baseline (size 10270) was captured before `-keep_palette_order` was added (current output: 10453 bytes). Path A does NOT change the png2asset invocation flags, so the baseline re-pin is purely about the staleness from 12.8.
**How to avoid:** Include baseline re-pin as an explicit plan step. Run `./gradlew :metasprites:convertSprites` + copy + commit.

### Pitfall 6: `Color.rgb888()` warning via `System.err` may surprise CI

**What goes wrong:** D-15 warning via `System.err.println()` at DSL-eval time (during `generateC`). In CI, this appears as unexpected stderr output.
**Why it happens:** `gbc()` currently delegates to `GBCColor.fromRGB888()` without any warning; the new `Color.rgb888()` adds one.
**How to avoid:** All metasprites palette values (`gbc(31, 31, 31)`, etc.) are exact multiples of 8 → no warning fires. GbcPresets values are also small integers (0-31) so they are RGB555 values directly → migrate to `Color.rgb555()`, NOT `Color.rgb888()`, to avoid false-positive warnings.
