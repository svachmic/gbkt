<decisions>
## Implementation Decisions

### Req #6 — asset-driven frame import (Path A)
- **D-01:** **Path A — reference png2asset's native metasprite arrays.**
  `MetaspriteVisitor` STOPS emitting frame-layout arrays for asset-driven
  metasprites. Instead it externs / `#include`s png2asset's own
  `<id>_metasprites[]` (array of `metasprite_t*` per frame) and emits
  `move_metasprite(<id>_metasprites[idx], x, y)`. The `frame { tile() }` blocks
  AND the baseId transcription disappear from the example DSL entirely. Single
  source of truth (png2asset), smaller `main.c`, maximal line-count win. NOT
  Path B (parse → sidecar → reconstruct IR frames → re-emit byte-identical
  arrays) — Path B keeps C byte-identical but needs gradle task reordering
  (png2asset before generateC) + a parser brittle to png2asset's output format.
- **D-02:** **No gradle task reordering required.** Path A references the arrays
  via `extern` / `#include` exactly like today's tile-data path
  (`ConvertSpritesTask` runs after `generateC`; the reference resolves at
  compile/link). `generateC` (JVM) does not need png2asset output — only the
  compile step does. This is a concrete advantage of Path A over Path B.
- **D-03:** **Generated-C shape for frames CHANGES by design** — the frame
  arrays move from gbkt's `main.c` to png2asset's `#include`d `.c`, and the
  metasprites codegen oracle (`MetaspriteIRTest`, the byte-identity golden) is
  **re-pinned to the new shape**. The SC "generated C unchanged in shape or
  smaller" is satisfied via *smaller* (`main.c` shrinks; transcription gone), not
  *unchanged shape*. This is the deliberate trade for the headline win. Verify
  via clean `:gbkt-examples:metasprites:buildRom` + re-pinned oracle.
- **D-04:** **`frame { tile(x, y, id) }` is KEPT as a documented escape hatch**
  for procedural / non-PNG metasprites (it is the only way to build a metasprite
  NOT from a PNG). The migrated examples stop using it; the hard-replace rule
  (13.1 D-11 / 13.2 D-17) applies to the EXAMPLE transcription, not to removing a
  still-useful lower-level primitive. The old hand-rolled `MetaspriteVisitor`
  layout path stays alive for the escape-hatch case; the new native-array path is
  added for the asset-driven case (visitor branches on `spritePath` presence).
- **D-05 (Claude's discretion → planner):** Whether **metasprites-stress** also
  migrates to the asset-driven form or stays on hand-transcribed `frame {}` as
  living coverage of the kept primitive — planner's call based on how stress is
  structured and what coverage the escape hatch needs.

### Req #4 — sprite() residual (verify + contract)
- **D-06:** Req #4 is **done + verify only**. `sprite(asset(...)) { mode/pivot/
  frameSize }` shipped in 12.4; this phase verifies it, composes it with Path A,
  and keeps `mode`/`pivot`/`frameSize` **explicit** (png2asset needs
  `-sw/-sh/-px/-py`; no reliable auto-derive). No new `sprite()` surface.
- **D-07:** **Build-time derive + validate frame count.** `ConvertSpritesTask`
  (or `GenerateCTask`) learns the real frame count from png2asset output and
  **FAILS the build** if the author-declared count disagrees (compile-time over
  runtime, per PROJECT). The author still declares the count (e.g.
  `NUM_FRAMES = 5`, driving `idx`'s `wrapAt`) because png2asset's count is NOT
  known at DSL-eval time (Path A build ordering) — but it is now *verified*, not
  *trusted*. (Researcher confirms png2asset's frame count is cheaply parseable
  from its output.)
- **D-08:** **Enforce exactly-one of { `sprite(asset)`, `frame {}` }** at build
  time. A metasprite must use EITHER the asset-driven form (png2asset owns frames)
  OR the procedural `frame { tile() }` escape hatch — never both, never neither.
  Fails loudly on misuse; resolves the 12.4 "migration window" optionality
  (`MetaspriteBuilder.kt:106,261` — `spriteAssetPath`/cutting-flag defaults null).

### Req #5 — explicit-slot palette
- **D-09:** **`palette(p, slot = N)`** — optional slot param on the *scene-load*
  call (`SceneBuilder.palette`). Slot lives at the load site (scene enter) where
  the load happens, so the same palette can load into different OBP slots in
  different scenes. NOT `palette(p).intoSlot(N)` (extra handle type) and NOT slot
  at the `spritePalette { }` declaration (wrongly binds a palette to one fixed
  slot forever). Reuses the existing `GBCPalette.slot` plumbing.
- **D-10:** **Auto-increment stays the default** when `slot` is omitted
  (sequential 0,1,2,3 — current Plan-16 behavior, byte-identical). Explicit slot
  is purely additive (e.g. "always load the enemy palette into slot 3").
  metasprites' four palettes already get 0,1,2,3 from auto-increment, so its #5
  migration is mainly **deleting the stale PHASE-13 comments**
  (`Metasprites.kt:86,322`) — optionally making the slots explicit for clarity.
- **D-11:** **Validate range + duplicates at build time.** Fail loudly on slot
  outside `0..7` (GBC OBP) or two palettes claiming the same slot within one
  scene (compile-time over runtime; catches the "always slot 3" footgun).

### Req #7 — unified Color namespace
- **D-12:** **Introduce a unified `Color` namespace** — `Color.rgb888(255,0,255)`
  (auto `>>= 3` convert), `Color.rgb555(31,0,31)` (raw 0–31), and named constants
  `Color.MAGENTA` / `WHITE` / `BLACK` / etc. One discoverable entry point matching
  the ROADMAP #7 phrasing. NOT free functions alone.
- **D-13:** **Hard-replace `gbc()` / `GbcColor.*` / `gbcHex()` everywhere** — fold
  all three into `Color`, delete the old surfaces, migrate **every** palette/UI
  call site across the whole codebase (NOT just the four reference ports). This is
  a deliberately **wider blast radius** than the 13.1/13.2 bounded-migration
  pattern — the user chose maximal cleanliness here. **Researcher MUST enumerate
  all `gbc()` / `GbcColor` / `gbcHex` call sites** (palettes, `UIBuilders.kt`,
  `GbcPresets`, genre code, tests) before planning; the planner sizes plans to the
  full sweep.
- **D-14:** **`gbcHex(string)` callers need a string→component path.** `gbcHex`
  takes a hex STRING; `Color.rgb888` takes int components. Replacement is either
  decompose-hex-to-components at each call site or a kept `Color.hex("#RRGGBB")`
  form. Researcher/planner picks; do not silently drop the hex-string ergonomics.
- **D-15:** **`Color.rgb888()` warns on precision loss** (any channel's low 3
  bits non-zero → stderr WARNING), matching the existing `gbcHex` behavior. The
  metasprites reference values are all exact multiples of 8, so they convert
  warning-free; arbitrary RGB888 (e.g. `(255,0,128)`) gets a build-time heads-up.
  (Consistent with 13.5's later "zero shipped stderr WARNINGs" SC for exact-value
  palettes.)

### Migration / verification policy (cross-cutting, carried from 13.1/13.2)
- **D-16:** **Hard-replace, no `@Deprecated` aliases** for the new primitives
  (13.1 D-11 / 13.2 D-17). For #6 the "old form" is hand-transcribed
  *patterns* (`frame { tile() }` transcription) — migration = delete the example
  blocks. For #7 the old form is *deletable functions* (`gbc`/`GbcColor`/`gbcHex`)
  — hard-replaced per D-13. `frame {}` itself survives as a primitive (D-04), not
  as a deprecated alias.
- **D-17:** **`metasprites` is a codegen oracle** (`MetaspriteIRTest` pins IR
  shape; the elephant byte-identity golden). #6 re-pins it (D-03). The verifier
  MUST run clean `:gbkt-examples:<game>:buildRom` for the regression sweep
  targets (per CLAUDE.md "ROM-build smoke test for codegen phases" — JVM tests
  can't see staleness in `build/gbkt/generated/`). Regression targets (per
  ROADMAP): pong, breakout, simple-physics, metasprites, metasprites-stress,
  banks, racer.
- **D-18:** New primitives documented in **DSL_REFERENCE.md** with worked
  examples (success criterion).

<specifics>
## Specific Ideas

- The headline: the elephant declaration should read as
  `val elephant by metasprite { sprite(asset("sprites/elephant.png")) { mode(...);
  pivot(...); frameSize(...) } }` — and nothing else. No `frame {}`, no
  `METASPR_ITEM` shapes, no baseId transcription. "An author should never see
  `METASPR_ITEM` shapes in their Kotlin source" (ROADMAP #6).
- Colors should read as intent, not arithmetic: `Color.rgb888(255, 0, 255)` or
  `Color.MAGENTA` — never `gbc(31, 0, 31) // 255 → 31, >>= 3`. The `>>= 3` math and
  the comment-arithmetic disappear (ROADMAP #7).
- The user accepted a **generated-C shape change** for #6 (Path A) in exchange for
  the maximal line-count win, and a **wider-than-usual blast radius** for #7
  (hard-replace `gbc`/`GbcColor`/`gbcHex` everywhere) for a single clean color
  surface — both deliberate, both stricter than the 13.1/13.2 bounded-migration
  default.
- Build-time *verification* over *trust* for the frame count (D-07) and the
  sprite-vs-frame contract (D-08) — compile-time-over-runtime, fail loudly.

### Accepted: metasprite OAM composition (29 vs 31) — 2026-06-03

**Decision:** ACCEPT — the post-migration png2asset descriptor for frame 0 produces
29 OAM entries; the pre-migration hand-authored descriptor enumerated 31. This
difference is ACCEPTED as a png2asset deduplication artifact, NOT a visual fidelity
regression.

**Root cause of the count difference:**
The png2asset args `-spr8x8 -px 0 -py 0 -sw 64 -sh 48 -noflip -keep_palette_order`
produce 29 METASPR_ITEM entries in frame 0. The pre-migration hand-authored descriptor
listed 31 explicit tile positions. The 2-entry difference represents tiles that are
transparent or identically covered by adjacent tiles in the elephant PNG at rest
(frame 0). png2asset omits these from the descriptor; the hand-authored version
included them explicitly.

**Evidence of visual faithfulness:**
- The 64×48 frame boundary is fully covered by the 29 OAM entries (spanning the same
  pixel area as the 31-entry pre-migration frame).
- Frame 2 of the post-migration descriptor already reaches 31 METASPR_ITEM entries —
  proving the OAM budget for the full frame is available when animation content
  requires it (walking/animation frames with more unique tile content).
- `evidence/13.3-DIAGNOSTIC.md` DEDUP verdict (Plan 13.3-15): "the 2-entry
  difference represents tiles that are transparent or identically covered by adjacent
  tiles — not missing visual content."
- Pre-migration reference screenshot: `evidence/elephant-PRE-migration-reference.png`
  shows the elephant at the correct position and scale; the 29-entry frame 0 covers
  the same visual area.
- Binding visual confirmation: Plan 13.3-19 reshoot (terminal visual-evidence
  sign-off vs `evidence/elephant-PRE-migration-reference.png`) is the binding
  confirmation that the 29-entry composition renders faithfully after pivot + palette
  corrections.

**What was NOT done (and why):**
No png2asset flag change was made (e.g., dropping `-noflip` to force 31-entry frame 0).
Such a change would alter the tile encoding scheme for ALL frames and could introduce
new discrepancies in frames 1-4 (e.g., frame 2 currently at 31 entries would change
unpredictably). OAM-count parity with the hand-authored pre-migration descriptor is
NOT required — visual fidelity of the rendered elephant is the requirement.

**This is a documented decision, NOT a silent scope reduction.** The 29-vs-31
difference is on record per the plan's `scope_reduction_prohibition`. The cluster
(Plans 13.3-15..19) closes this axis here; the reshoot in 13.3-19 provides the
binding screenshot evidence.

### LOCKED: elephant COLOR target — uniform gray (sub-palette cycling intent) — 2026-06-03

**Decision (D-19, binding user sign-off via `/gsd-plan-phase 13.3 --gaps`):** The
elephant's correct render at rest (rot=0) is **uniform gray**, honoring the documented
metasprites sub-palette cycling design (gray→pink→cyan→green via `rot >> 2`, gray at
rest — see `gbkt-examples/metasprites/CLAUDE.md` §"Sub-Palette Cycling"). The elephant
must be a **single-sub-palette** sprite so the cycling selects one uniform palette per
`rot` value.

**Why this is the oracle now:** GAP-1 (13.3-VERIFICATION.md) was stuck because the only
color reference (`evidence/elephant-PRE-migration-reference.png`) was itself
color-imperfect per the user ("Pre-migration was incorrect in color as well, but there
was no pink"). The pre-migration screenshot is **NOT a valid color oracle.** This locked
decision replaces it: the target is uniform gray with **zero pink**, judged against the
documented cycling design — not against the pre-migration screenshot.

**Concrete codegen target (the fix for 13.3-20):** Remap every `S_PAL(1)` descriptor
entry in `elephant.c` (52 occurrences across frames; 10 in frame 0) to `S_PAL(0)`, so all
OAM entries select OBJ slot 0. At rest slot 0 = `gray_pal` → the whole elephant renders
gray; no OAM entry selects slot 1 (pink) anymore. Source: `evidence/13.3-DIAGNOSTIC.md`
step (b), "Full fix requires also rewriting the descriptor indices."

**Rejected alternatives (recorded, not silently dropped):**
- **Native green** (upload png2asset's `elephant_palettes` so the elephant shows its real
  green source tones) — rejected; would drop the documented `rot >> 2` gray-cycling story.
- **Re-author the asset** (single-palette indexed `elephant.png` so png2asset emits clean
  all-`S_PAL(0)`) — rejected for 13.3-20; keep the fix in the codegen/descriptor path, not
  the source art.

**Verification bar:** RED→GREEN codegen test locking the all-`S_PAL(0)` descriptor shape,
