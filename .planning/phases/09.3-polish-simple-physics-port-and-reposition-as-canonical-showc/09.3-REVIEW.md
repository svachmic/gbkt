## Summary

Phase 09.3 is a low-risk, documentation-and-refactor phase touching only the
`simple-physics` example module. The substantive code change is small and well-justified:
a single oracle correction (`spdY set -512` → `spdY set -JUMP_ACCELERATION_IN_SUBPIXELS`)
plus extraction of seven `internal const val` constants and five `// PHASE-13:`
breadcrumbs. The test re-baseline is mechanical and matches the source delta.

No correctness or security defects were found. The framework code, IR, codegen, and DSL
are untouched. All 24 simple-physics tests are GREEN (per Plan 02 / Plan 04 SUMMARYs).

The findings below are mostly **internal-doc consistency drift** — both the explicitly
SURFACED PLAYBOOK `-512` deviations (acknowledged by the phase as intentional carve-out
deferrals) and several adjacent stale-doc strings the SUMMARYs did not call out (e.g. the
PLAYBOOK "Bug B workaround" paragraph at L43-L48 which contradicts SimplePhysics.kt's
post-09.1 use of `smiley.moveTo(...)`). These are NOT regressions caused by Phase 09.3 —
several pre-date the phase — but Phase 09.3's stated goal is "reframe as canonical
showcase", which raises the bar on doc accuracy, and reviewers/future readers are likely
to trip on them.

Two warnings cite **functional correctness drift** worth fixing before this phase is
considered complete:
- WR-01: `SimplePhysicsEmissionTest.EVIDENCE_DIR` still writes tier1-shape artifacts into
  the Phase 09 dir (`09-port-simple-physics-gbdk-example-to-gbkt/.../tier1-shape`), but
  the comment block in `SimplePhysics.kt` L129 still references "Bug A site" / decel
  comparisons as if Plan 04 of Phase 09 has not yet run.
- WR-02: Comment at `SimplePhysics.kt:129` describes a pre-Plan-04 design decision
  (`Positive-literal 0 in upper branch is a Bug A site`) that is meaningless to a reader
  arriving at this file as the "canonical showcase".

Note: Per `09.3-03-SUMMARY.md` § "Discrepancy SURFACED" and `09.3-04-SUMMARY.md`
§ "Accepted Deviation", the three known-stale `-512` references in PLAYBOOK.md
(L25, L59, L103) are intentional deviations under the D-12 minimum-touch carve-out.
They are **NOT** flagged below. The findings below are NEW issues this reviewer
discovered that are NOT covered by either deviation list.

### WR-01: Stale "Plan 04 will fix" / "RED at HEAD" framing throughout SimplePhysicsEmissionTest header is misleading post-Phase-09

**File:** `gbkt-examples/simple-physics/src/test/kotlin/io/github/gbkt/examples/simple_physics/SimplePhysicsEmissionTest.kt:15-48`

**Issue:** The header comment block (and matching per-test KDoc at L114-L118 / L188-L195
/ L225) repeatedly claims:
- `Phase 09 Plan 03 (locks the codegen surface that Plan 04 will fix)`
- `Expected at HEAD: D-11.1 RED ... Plan 04 target`
- `D-11.3 RED ... Plan 04 target`
- `All three tests are designed so Plan 04 ... flips D-11.1 and D-11.3 to GREEN without touching D-11.2`

But the tests are factually GREEN at HEAD (per `09.3-02-SUMMARY.md` Test Results
section: EmissionTest 3/3 PASS). The "RED at HEAD / Plan 04 will fix" framing is
self-contradictory and creates ambiguity about whether this test class is currently
locked or pending. A future reader will not know whether the assertions are gates that
are presently RED (waiting for a fix) or pinned contracts (currently GREEN).

This is exacerbated because Phase 09.3 is explicitly the "canonical showcase" phase —
the doc-vs-reality drift is precisely the kind of polish the phase is supposed to
remove. Plan 02 re-baselined the D-11.2 jump assertion against
`JUMP_ACCELERATION_IN_SUBPIXELS` but did NOT update the surrounding "RED at HEAD"
narrative. Same for the per-test KDocs.

**Fix:** Rewrite the header to reflect post-fix reality. Suggested replacement:

```kotlin
// =============================================================================
// SIMPLE-PHYSICS C EMISSION INVARIANTS — pinned post Phase 09 Plan 04 / Phase 09.3
//
// All three tests are GREEN at HEAD. They lock the generated C shape for play_frame:
// - D-11.1: spdX/spdY upper-bound clamp comparisons emit bare `> 64` (signed,
//   no `u` suffix). Routes through CIntLiteral per the Plan 04 signed-comparison
//   RHS fix.
// - D-11.2: jump impulse emits `_spdY = -$JUMP_ACCELERATION_IN_SUBPIXELS` and
//   `button_pressed(J_A)` (edge-detect). Post-09.3 D-01 oracle fix.
// - D-11.3: decel-ladder comparisons against 0 emit signed (`_spdX < 0`, etc.).
//
// Any regression that re-introduces a `u` suffix on a signed-context literal will
// flip the relevant test RED.
// =============================================================================
```

Update the three per-test KDocs (L114-L118, L188-L195, L225) to drop the
"GREEN target (Plan 04)" framing and replace with "Locked contract". Assertion failure
messages on L129/134/141/150/228/234/239/244 can keep "Plan 04 contract" if desired but
"Locked contract" is clearer for present-day readers.

### WR-02: Stale "Bug A site" comment in SimplePhysics.kt references a no-longer-relevant pre-Plan-04 hazard

**File:** `gbkt-examples/simple-physics/src/main/kotlin/io/github/gbkt/examples/simple_physics/SimplePhysics.kt:128-129`

**Issue:** The comment block above the decel ladder reads:
```kotlin
// Mutually exclusive — no else-if needed (Pitfall 4).
// Positive-literal `0` in upper branch is a Bug A site.
```

"Bug A" is an internal Phase 09 codename for the SDCC unsigned-suffix codegen bug.
Per `09.3-CONTEXT.md` and `09.3-03-SUMMARY.md`, that bug was fixed in Phase 09 Plan 04,
so by the time a reader arrives at SimplePhysics.kt in the "canonical showcase" phase,
the comment is referencing a hazard that no longer applies. Worse, this is the only
remaining `Bug A` reference in the source file (CLAUDE.md cleaned up the analogous
references in Plan 03 of Phase 09.3) so the term is now orphaned — the reader has no
way to look up what "Bug A" means without spelunking through the Phase 09 plan history.

Phase 09.3's stated mission is "reframe as canonical showcase". An undefined,
implementation-history-leaking term in the canonical-showcase file undercuts that goal.

**Fix:** Replace with a comment that explains the present-day rationale without the
historical codename:

```kotlin
// Mutually exclusive — no else-if needed (the two `whenever`s cannot both fire
// in the same frame since `spdY isBelow 0` and `spdY isAbove 0` are disjoint).
// Comparisons against `0` emit as signed (no `u` suffix) — locked by
// SimplePhysicsEmissionTest D-11.3.
```

Same treatment for the `Pitfall 4` reference (similar internal codename).

### WR-03: PLAYBOOK.md "Bug B workaround" paragraph (L43-L48) contradicts current SimplePhysics.kt source

**File:** `gbkt-examples/simple-physics/PLAYBOOK.md:43-48`

**Issue:** PLAYBOOK.md L43-L48 reads:
```
- **Bug B workaround for position sync** — `ActorRef.moveTo(Expr, Expr)` does not exist
  in the current DSL surface (`moveTo` only accepts `Int`). The port uses
  `smiley.x set (posX shr 4)` and `smiley.y set (posY shr 4)` via the `ActorPropertyRef`
  set-with-Expr API. The reference uses `move_sprite(0, SUBPIXELS_TO_PIXELS(PosX), ...)`
  inline. Functionally equivalent; if Bug B is named as the Plan 04 codegen fix, this
  workaround is replaced with the idiomatic `smiley.moveTo(posX shr 4, posY shr 4)`.
```

But SimplePhysics.kt:124 uses `smiley.moveTo(posX shr 4, posY shr 4)` — i.e., the
post-fix idiomatic call — and SimplePhysics.kt's own KDoc (L35-L37) describes
`ActorRef.moveTo(Expr, Expr)` as the Phase-9.1-Plan-01 SEED-002 addition. The
PLAYBOOK paragraph is factually obsolete: there is no workaround in the current source.
This was cleaned up in the CLAUDE.md "Sub-Pixel to Pixel Conversion" section
(per `09.3-03-SUMMARY.md`) but PLAYBOOK.md was left stale because of the strict D-12
minimum-touch carve-out.

The D-12 carve-out specifically permitted ONLY the L14-L15 math typo fix in this phase.
However, this paragraph (L43-L48) is now factually incorrect — it asserts a moveTo
overload does not exist when it demonstrably does, and the source file uses it. This
is more harmful than the SURFACED `-512` references because (a) it is not a documented
deviation, and (b) it actively misinforms the reader about the DSL surface.

**Fix:** Either widen the carve-out and clean up this paragraph in a follow-up plan,
OR add it to the existing "Discrepancy SURFACED" list in `09.3-03-SUMMARY.md` so it is
tracked alongside the L25/L59/L103 deviations. Suggested replacement:

```
- **Sub-pixel → pixel rendering uses `smiley.moveTo(Expr, Expr)`** (Phase 9.1
  Plan 01 SEED-002 overload). Lowers to a single `SetPosition` op per frame.
  Matches the reference's `move_sprite(0, SUBPIXELS_TO_PIXELS(PosX), ...)` shape.
```

### WR-04: SimplePhysicsEmissionTest.EVIDENCE_DIR writes evidence into the Phase 09 dir, opposite of the Plan 02 redirect pattern applied to UatTest

**File:** `gbkt-examples/simple-physics/src/test/kotlin/io/github/gbkt/examples/simple_physics/SimplePhysicsEmissionTest.kt:62-66`

**Issue:** `SimplePhysicsEmissionTest.EVIDENCE_DIR` resolves to:
```
../../.planning/phases/09-port-simple-physics-gbdk-example-to-gbkt/evidence/tier1-shape
```

But `SimplePhysicsUatTest.EVIDENCE_DIR` was explicitly redirected in Plan 02 to:
```
../../.planning/phases/09.3-polish-simple-physics-port-and-reposition-as-canonical-showc/evidence/uat-screenshots
```

…with the explicit rationale (per Plan 02 SUMMARY § "Phase-history-protection pattern")
that "when a plan re-baselines a test that writes screenshots into a prior phase's
evidence dir, redirect EVIDENCE_DIR to the current phase's evidence dir IN THE TEST
SOURCE itself, so the prior phase's historical artifact survives intact".

EmissionTest exhibits exactly the same pattern — Plan 02 caused
`01-accel-clamp-upper-bound.txt`, `02-jump-impulse.txt`, `03-decel-ladder.txt` to be
re-written under the Phase 09 path with post-09.3 content (the jump-impulse artifact
now contains `_spdY = -32;`, overwriting the prior `_spdY = -512;` historical
baseline). The "phase-history-protection pattern" was not applied consistently — the
Phase 09 tier1-shape historical artifacts have been silently re-baselined inside the
Phase 09 evidence dir, which contradicts the Plan 02 SUMMARY's claim that the pattern
protects prior-phase evidence.

This is a process-consistency defect: either the EmissionTest evidence should also be
redirected to Phase 09.3, OR the Plan 02 SUMMARY's "phase-history-protection pattern"
claim should be scoped to UAT screenshots only. As-is, a future verifier looking at
`09-port-simple-physics-gbdk-example-to-gbkt/evidence/tier1-shape/02-jump-impulse.txt`
will see post-09.3 content but believe it is Phase 09 baseline content.

**Fix:** Mirror the Plan 02 UatTest redirect on EmissionTest, e.g.:

```kotlin
val EVIDENCE_DIR = File(
    System.getProperty("user.dir"),
).resolve(
    "../../.planning/phases/" +
        "09.3-polish-simple-physics-port-and-reposition-as-canonical-showc/" +
        "evidence/tier1-shape"
).normalize()
```

Then copy the post-09.3 tier1-shape `.txt` artifacts to the new Phase 09.3 path and
restore the Phase 09 originals from git history (`git show <pre-09.3-commit>:.planning/.../tier1-shape/02-jump-impulse.txt > ...`).

### IN-03: SimplePhysics.kt cartridge `romBanks = 2` may not match `CARTRIDGE_ROM_ONLY` semantics

**File:** `gbkt-examples/simple-physics/src/main/kotlin/io/github/gbkt/examples/simple_physics/SimplePhysics.kt:45-46`

**Issue:** `cartridge = CARTRIDGE_ROM_ONLY` ("ROM_ONLY", a 32KiB cart with no banking)
is paired with `romBanks = 2` (which implies a banked cartridge). Whether this is a
real defect depends on the gbkt config plumbing — `romBanks = 2` may be inert when
`cartridge = "ROM_ONLY"`, OR it may force a different cartridge type. The ROM-size
evidence (32768 bytes both pre and post) suggests it's inert in practice. But this
configuration is precisely the kind of thing a canonical-showcase example should NOT
contain — a reader copying this idiom may end up with a mismatched cart header.

**Fix:** Either drop `romBanks = 2` (since ROM_ONLY implies a single bank) or change
the cartridge type to one that actually requires two banks. Recommend dropping
`romBanks = 2` since the pre-09.3 baseline already builds a 32KiB ROM.

Alternatively, document why `romBanks = 2` is needed alongside ROM_ONLY (the PHASE-13
breadcrumb at L44 could be expanded with this rationale).
