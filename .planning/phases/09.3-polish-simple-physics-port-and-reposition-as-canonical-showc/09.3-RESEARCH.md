### F. ROM Byte-Comparison Mechanics

**Pre-09.3 ROM baseline:** `build/gbkt/output/simple-physics.gb` = **32768 bytes** (confirmed by `wc -c`). This matches the Phase 09 `rom-size-comparison.md` finding.

**JUMP-immediate-site localization strategy:**
The generated C at `main.c:234` currently reads `_spdY = -512;`. After 09.3, it will read `_spdY = -32;`. This is a constant value change in a single assignment statement. The byte-level impact in the ROM depends on how SDCC encodes 16-bit immediate values:
- `-512` in little-endian INT16 = `0x00 0xFE` (two bytes: 0x00 and -2 as signed byte)
- `-32` in little-endian INT16 = `0xE0 0xFF` (two bytes: -32 as signed, 0xFF as sign extension)

Both are different two-byte sequences but still two bytes — so the ROM size stays at 32768 bytes (padded to cartridge boundary regardless). The diff in the ROM binary will show only the bytes corresponding to this one assignment. For the verifier, a binary diff (`cmp -l pre.gb post.gb` or `xxd` comparison) at the exact offset can confirm localization.

**Practical approach for the verifier:** Rather than byte-level binary diff (which requires GBDK to be installed), the plan can cross-validate via the JVM-tier emission test: the `SimplePhysicsEmissionTest.D-11_2` test asserts `_spdY = -$JUMP_ACCELERATION_IN_SUBPIXELS` (i.e., `-32`), and its absence of the `-512` form confirms the change is confined to the JUMP site. The ROM byte-size check (`wc -c simple-physics.gb` = 32768) provides the size assertion. Together these satisfy D-14 without requiring a byte-level binary diff tool.

## Common Pitfalls

### Pitfall 1: Line-Number Drift in Breadcrumbs
**What goes wrong:** Planner/executor places PHASE-13 breadcrumbs at CONTEXT.md's pre-edit line numbers, which shift after the constants block is inserted.
**Why it happens:** CONTEXT.md was written against the pre-edit file; inserting ~8 lines of constants at the top shifts every subsequent line.
**How to avoid:** Always apply the constants-extraction edit FIRST, then place breadcrumbs at the post-edit line positions.
**Warning signs:** Breadcrumb comments appear inside the config block or on wrong statements.

### Pitfall 2: Forgetting SimplePhysicsIRTest
**What goes wrong:** Plan re-baselines 3 tests but breaks IR tests because a renamed/restructured DSL construct changes the IR shape.
**Why it happens:** `SimplePhysicsIRTest` is not mentioned in CONTEXT.md but it exists and will fail if the DSL structure changes.
**How to avoid:** Run the full test suite (`./gradlew :gbkt-examples:simple-physics:test`) after edits to catch `SimplePhysicsIRTest` regressions. D-03 constant extraction does NOT change DSL structure, so this test should remain GREEN.
**Warning signs:** `SimplePhysicsIRTest` fails on scene count, variable count, or actor position assertions.

### Pitfall 3: UAT Screenshot Path Collision
**What goes wrong:** `SimplePhysicsUatTest` writes behavior-2 screenshot to Phase 09's evidence directory, overwriting the historical Phase 09 UAT evidence.
**Why it happens:** `EVIDENCE_DIR` in the test class points to `09-port-simple-physics-gbdk-example-to-gbkt/evidence/uat-screenshots/`.
**How to avoid:** Either (a) update `EVIDENCE_DIR` to point to the Phase 09.3 evidence directory before running the re-baseline, or (b) copy the new screenshot to the Phase 09.3 evidence directory as a post-step.
**Warning signs:** Phase 09's `behavior2-jump-impulse.png` size changes from 436 bytes (pre-09.3) to a different value.

### Pitfall 4: ROM Smoke Skip on No-GBDK Environment
**What goes wrong:** D-14 ROM smoke step is marked as "auto-inherited from 09.2 gate" and skipped because `GBDK_HOME` is not set.
**Why it happens:** The IntegrationTest.kt gate is explicitly `@EnabledIfEnvironmentVariable(named = "GBDK_HOME")`. Without GBDK installed, `buildRom` cannot run.
**How to avoid:** The plan must document that D-14 ROM smoke requires GBDK installed. If GBDK is absent, the verifier should note the skip with a human-verify checkpoint.
**Warning signs:** `./gradlew :gbkt-examples:simple-physics:buildRom` exits with "lcc not found."

### Pitfall 5: EmissionTest Uses In-Memory Pipeline (Not On-Disk main.c)
**What goes wrong:** Plan assumes updating `main.c` on disk is sufficient for the emission tests to pass.
**Why it happens:** `SimplePhysicsEmissionTest` uses `GBDKPipelineV2().generate(simplePhysics.build())` — it runs the pipeline in memory against the compiled Kotlin source. The on-disk `main.c` is irrelevant to the test.
**How to avoid:** The emission tests pass when the Kotlin source (`SimplePhysics.kt`) has the correct value. No separate `generateC` step is needed for tests to pass.

### Pitfall 6: PLAYBOOK `(-JUMP_ACCEL × 16)` Spans Two Lines
**What goes wrong:** Planner targets only L15 for the PLAYBOOK math-typo fix, leaving a dangling `-512` on L14.
**Why it happens:** CONTEXT.md says "L15 math-typo fix" but the actual sentence reads across L14-15.
**How to avoid:** Fix both L14 (`-512` → `-JUMP_ACCELERATION_IN_SUBPIXELS`) and L15 (remove the `(-JUMP_ACCEL × 16)` parenthetical).
