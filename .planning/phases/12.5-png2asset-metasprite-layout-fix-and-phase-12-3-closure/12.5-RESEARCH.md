## Summary

Phase 12.5 fixes the png2asset metasprite layout misconfiguration that caused the platformer-template player sprite to render as a malformed blob rather than recognizable duck art. The root cause is confirmed: `ConvertSpritesTask.convertSprite()` currently passes only `-spr8x8`/`-noflip` heuristics to png2asset, completely omitting the `-px 12 -py 6 -sw 24 -sh 32 -spr8x16` cutting flags documented in `res/README.md` and encoded in the GBDK reference Makefile. The Plan 12.4-08 evidence file (`player-tiles-ordering.md`) already contains png2asset output generated with the correct flags — confirming the fix is flag exposure, not binary patching.

The solution is a load-bearing DSL refactor: expose `mode()`, `pivot()`, `frameSize()` as typed builder methods on the `sprite()` block inside `metasprite { }`, propagate them as 5 additive nullable fields through `MetaspriteIR`, emit them into `game_metadata.json sprites[]`, and have `ConvertSpritesTask` build its png2asset command entirely from the sidecar. All 7 sprite-using games must be migrated to declare the full flag set explicitly (required, not optional). Three code-review warnings from Phase 12.4 (WR-01 path separators, WR-02 JSON diagnostic, WR-03 actor-sprite test) ship as three final small plans. The phase ends by re-shooting anchor 4, passing both the mechanical VisualDiff gate (tolerance=0.10) and the human-verify gate, then closing Phase 12.3.

**Primary recommendation:** The diagnostic step (REQ-1) is fast confirmation, not exploration — the smoking gun is already confirmed in `ConvertSpritesTask.kt:235-244`. The planner should treat REQ-1 as a verification step and structure plans 2–7 around the DSL refactor + migration work, which is the phase's core value.

### Pattern 1: Typed Builder Block on sprite() — how mode()/pivot()/frameSize() land

The existing `sprite(asset: AssetRef)` method (line 198 in MetaspriteBuilder.kt) currently just captures `asset.path` into `spriteAssetPath`. Phase 12.5 evolves it to accept an optional lambda block:

```kotlin
// CURRENT (Phase 12.4):
fun sprite(asset: AssetRef) {
    spriteAssetPath = asset.path
}

// PHASE 12.5 TARGET:
fun sprite(asset: AssetRef, block: SpriteConfigBuilder.() -> Unit = {}) {
    spriteAssetPath = asset.path
    val config = SpriteConfigBuilder().apply(block)
    spriteModeValue = config.spriteModeValue
    pivotXValue = config.pivotXValue
    pivotYValue = config.pivotYValue
    frameWidthValue = config.frameWidthValue
    frameHeightValue = config.frameHeightValue
}
```

OR alternatively, a new inner builder class at the `sprite { }` block level (planner decides the exact shape):

```kotlin
val player by metasprite {
    sprite(asset("graphics/player-character-gbapduck-sprites.png")) {
        mode(SpriteMode.SPR8x16)   // -spr8x16
        pivot(12, 6)               // -px 12 -py 6
        frameSize(24, 32)          // -sw 24 -sh 32
    }
    posX(playerX); posY(playerY)
    rot(facingRot); idx(walkFrameIdx)
    frame { tile(-6, -12, 0); tile(0, 8, 2); tile(0, 8, 4); tile(16, -16, 6); tile(0, 8, 8); tile(0, 8, 10) }
    // ...5 more frames...
}
```

**Structural siblings (for reference):** `posX(varRef: AssignableVar)` at line 147 captures a String name; the new `SpriteConfigBuilder` captures Int + enum. Structural pattern is the same — DSL builder method captures into a field, `build()` passes to `MetaspriteIR`.

### Anti-Patterns to Avoid

- **Height-heuristic for sprite mode:** `spriteModeFromHeight(pngFile)` reads the PNG and guesses SPR8x8 vs SPR8x16 from height. This is the bug class Phase 12.5 fixes — DELETE it.
- **Mixed string interpolation in error messages:** `"${assetDir}/${spritePath}"` produces mixed separators on Windows (WR-01). Use `pngFile.absolutePath` instead.
- **Unguarded JSONObject parse:** `JSONObject(metaFile.readText())` at line 97 throws a raw `JSONException` on corrupt JSON (WR-02). Wrap in try/catch.
- **Tolerance confusion:** `VisualDiff.compare(tolerance=0.05)` means "match if ≤5% differ"; the anchor4 test's assertion is `!diffResult.match` (images MUST differ by >5%). The Phase 12.4-15 comment at line 535 explains this. Phase 12.5 tightens to 0.10 (must differ by >10%).

## Common Pitfalls

### Pitfall 1: Tile() Coordinates Are Already Correct — Don't Re-author Them

**What goes wrong:** CONTEXT.md D-07a says "replace 36 tile() calls from reference-derived values." The existing PlatformerTemplate.kt tile() calls were ALREADY authored from the Plan 12.4-08 evidence, which ran png2asset with the correct flags. Re-authoring them from scratch risks introducing errors.

**Why it happens:** D-07a was written before it was confirmed that the existing tile() calls already match the correct flags output.

**How to avoid:** Verify the existing tile() calls against the `player-tiles-ordering.md` lookup table (already embedded in this RESEARCH.md). If they match, the platformer-template migration plan is: (1) add `mode(SPR8x16), pivot(12,6), frameSize(24,32)` to the sprite() block — no tile() changes needed.

**Warning signs:** If the geometry test (D-08a) fails after only adding the flag builders (no tile() changes), investigate whether the flags change the tile-array layout in an unexpected way.

### Pitfall 2: `banks` Game Has No Sprite Assets — Skip It

**What goes wrong:** D-07 says "all 7 games migrate." The `banks` example uses only a zone tileset (`tiles/checker.png`), not any sprite actors or metasprites. Attempting to add `mode()/pivot()/frameSize()` to it will cause a compilation error (no `sprite()` block exists).

**Why it happens:** "7 sprite-using games" was stated in CONTEXT.md but `banks` uses no sprite PNG assets — only a tileset PNG for zone rendering.

**How to avoid:** Verify each game's `sprite(asset(...))` usage before migration. `banks` has ZERO `sprite()` blocks. Skip the `banks` migration. The actual count is 6 games with sprite() blocks that need migration (pong × 3 sprites, breakout × 3 sprites, simple-physics × 1 sprite, metasprites × 1 metasprite, metasprites-stress × 2 metasprites + 1 actor, platformer-template × 1 metasprite).

**Warning signs:** If `Banks.kt` has no `metasprite { }` and no `actor { sprite(asset(...)) }` declarations, skip it.

### Pitfall 3: SpriteMode Enum Visibility After Move to gbkt-ir

**What goes wrong:** Moving `SpriteMode` from `ConvertSpritesTask`'s `internal` inner enum to `gbkt-ir` top-level requires adding an import in `ConvertSpritesTask.kt` and `MetaspriteBuilder.kt`. If the import path changes, the plugin worker's classloader-isolated context may fail to resolve `SpriteMode` via reflection.

**Why it happens:** The validation gate in `GenerateCTask.kt` accesses `MetaspriteIR.spriteMode` via reflection (`ms.javaClass.getMethod("getSpriteMode").invoke(ms)`). The return type is `SpriteMode?`, but in the reflection context it returns `Object`. The reflection cast (`as SpriteMode?`) won't work across classloader boundaries.

**How to avoid:** The reflection-based gate should check for null by comparing against null (not by type-checking against `SpriteMode`). Use `invoke(ms) != null` rather than `invoke(ms) as SpriteMode?` in the null-check. The actual enum value is read by `ConvertSpritesTask` from the JSON sidecar string (`entry.getString("spriteMode")`) and parsed via `SpriteMode.valueOf(...)` — this works because `ConvertSpritesTask` and `gbkt-ir` share the same classloader (both are in the Gradle plugin classpath).

### Pitfall 4: Byte-Identity Baseline Updates for metasprites + metasprites-stress

**What goes wrong:** Adding `pivot(0,0) frameSize(8,16)` to the elephant/tiger metasprites changes the png2asset invocation from `png2asset elephant.png -spr8x16 -noflip` to `png2asset elephant.png -spr8x16 -px 0 -py 0 -sw 8 -sh 16 -noflip`. If `-px 0 -py 0 -sw 8 -sh 16` are the DEFAULTS for png2asset (i.e., `(0,0)` pivot and full-image frame size produce identical output), the byte-identity baselines won't change.

**Why it matters:** If the flags change output, baselines MUST be refreshed atomically in the same commit. If they DON'T change output, the baselines stay identical (no commit needed).

**How to avoid:** Run png2asset twice — once with the current flags and once with the new explicit flags — and compare outputs. If they're identical, skip baseline refresh. The planner should include a step to verify this in the metasprites migration plan.

### Pitfall 5: VisualDiff Tolerance Semantics

**What goes wrong:** Misunderstanding `tolerance=0.10` — this means "images MATCH if ≤10% of pixels differ." The test asserts `!diffResult.match`, meaning images must differ by MORE than 10%. For a 160×144 = 23040-pixel Game Boy screen, the 24×32 player sprite covers only ~768 pixels (3.3%). A perfectly rendered hflip affecting only the sprite region would change <4% of pixels — below the 10% threshold, and the test would fail even with correct rendering.

**Why it happens:** The 10% threshold is stated in SPEC REQ-3b but may be too strict for a 24×32 sprite on a 160×144 screen.

**How to avoid:** The SPEC says "stricter than 12.4-15's threshold of 5%." But the 12.4-15 test was asserting `> 5%` diff (not 5% match). The correct interpretation: Phase 12.5 requires `> 10%` of FULL FRAME pixels to differ between facing-right and facing-left screenshots. This requires either: (a) the background to differ (e.g., scrolling, different tiles under the duck), or (b) the duck to cover a larger portion of the screen than 3.3%. The planner should be aware that REQ-3b at tolerance=0.10 may need careful capture conditions (hold dpad during capture so camera scroll accumulates background differences).

**Warning signs:** If the VisualDiff assertion fails even though the duck looks correct visually, the background content may be identical between the two captures. Restructure the capture to accumulate visual differences (e.g., hold RIGHT for 30 frames to scroll background, then hold LEFT briefly for facing-left capture — more background tiles will differ).

### Pitfall 6: ConvertSpritesTask Sidecar Read Path for New Fields

**What goes wrong:** When reading the 5 new fields from the sidecar, using `entry.getString("spriteMode")` throws `JSONException` if the field is missing (older sidecar without 5 new fields). This breaks backward compatibility for any cached sidecar from a prior build.

**Why it happens:** The D-04b validation gate ensures the fields are non-null when codegen runs, but a stale `game_metadata.json` from a prior `generateC` run (before the migration) won't have the new fields.

**How to avoid:** Use `optString("spriteMode", "SPR8x16")`, `optInt("pivotX", 0)`, etc. for reading from ConvertSpritesTask. After migration, all codegen runs will produce sidecars with the new fields — the opt* fallbacks are just safety nets for stale builds. Add a `:clean` recommendation to migration plan summaries.
