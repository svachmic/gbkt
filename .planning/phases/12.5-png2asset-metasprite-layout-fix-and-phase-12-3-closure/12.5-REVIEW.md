# Phase 12.5 Code Review

## Summary

Phase 12.5 correctly implements the five png2asset cutting-flag fields (`spriteMode`, `pivotX`, `pivotY`, `frameWidth`, `frameHeight`) through the full pipeline: `SpriteMode` enum in `gbkt-ir`, `MetaspriteIR` nullable fields, `SpriteConfigBuilder` inner DSL, sidecar emission in `GBDKPipelineV2.buildMetadataFile()`, validation gate in `GenerateCTask.validateMetaspriteSpritePaths()`, and CLI arg builder in `ConvertSpritesTask.buildPng2AssetArgs()`. The dead `spriteModeFromHeight` heuristic is confirmed gone. The three inline debug fixes (E-02/E-03/E-04) are correct and well-guarded by tests. No hardcoded secrets or injection risks exist in the new code.

Two issues stand out as quality/correctness risks. The most important is a silent-skip logic hole in `validateMetaspriteSpritePaths()`: a `NoSuchMethodException` on `getSpriteMode` silently skips ALL remaining D-04b checks for that metasprite (via `continue`), meaning a legacy IR class that predates Phase 12.5 would bypass the pivot and frameSize checks entirely — a gap the comment text says it is guarding against. The second notable issue is that `injectBankPragma` writes the modified file using Unix-only `\n` line endings, potentially corrupting Windows-authored output files (a platform-portability regression). Four additional warnings cover defensive gaps in the sidecar reader, the oamCount metadata calculation for 8x16 actors, a test gap for the mixed SPR8x8+SPR8x16 hardware-mode selection edge case, and a CLAUDE.md stale reference.

## Findings

### Critical

#### CR-01: `validateMetaspriteSpritePaths` silently skips D-04b checks when `getSpriteMode` is absent

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/GenerateCTask.kt:831-836`

**Issue:** When `getSpriteMode` throws `NoSuchMethodException` (legacy IR class predating Phase 12.5), the catch block executes `continue`, which exits the entire per-metasprite loop iteration. This skips the `pivotX`, `pivotY`, `frameWidth`, and `frameHeight` checks that follow. A metasprite on a pre-12.5 IR can have `spriteMode == null` reflected via the missing method, yet the pivot and frameSize checks are never reached. The stated intent (comment at line 828: "classloader isolation makes casting across boundaries unsafe") is correct, but the error-handling branches for `pivotX`, `pivotY`, `frameWidth`, and `frameHeight` return `null` on `NoSuchMethodException` (lines 847-853) while the spriteMode branch uses `continue`. The inconsistency means the three strongest invariants (pivot, frameSize) are silently skipped whenever the spriteMode method is absent — the exact gap `continue` was meant to close for the spriteMode-absent legacy case instead opens a broader skip.

**Fix:** Change the `NoSuchMethodException` catch for `getSpriteMode` to assign `null` (matching the pivot/frameSize pattern) instead of `continue`, and then let the `if (spriteMode == null)` gate throw. Alternatively, if the intent is truly "legacy IR → skip all D-04b checks," add an explicit comment and do not have the pivot/frameSize catches use a different strategy:

```kotlin
val spriteMode =
    try {
        ms.javaClass.getMethod("getSpriteMode").invoke(ms)
    } catch (_: NoSuchMethodException) {
        null  // legacy IR — treat same as not-set; gate below throws
    }
if (spriteMode == null)
    throw GradleException(
        "Metasprite '$id' missing mode() — declare mode(SpriteMode.SPR8x16) or " +
            "mode(SpriteMode.SPR8x8) inside sprite() { ... } block. (Phase 12.5 D-04b)"
    )
```

### Warning

#### WR-01: `injectBankPragma` uses `\n`-only line endings — corrupts files on Windows

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt:374`

**Issue:** `outputC.writeText(lines.joinToString("\n"))` unconditionally writes Unix newlines regardless of the host OS. On Windows, `outputC.readText()` → `content.lines()` produces CRLF-split lines but `joinToString("\n")` re-joins them with LF only, stripping the `\r` from every line. The result is a CRLF→LF file rewrite on every task invocation on Windows, dirtying the file unnecessarily and potentially conflicting with `lcc`'s line-ending expectations if the project is on Windows.

**Fix:** Use `System.lineSeparator()` or read/write the file as bytes:

```kotlin
outputC.writeText(lines.joinToString(System.lineSeparator()))
```

#### WR-02: `buildMetadataFile` `oamCount` is wrong for 8x16 hardware sprite mode actors

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:220-227`

**Issue:** The actor OAM-count calculation in `buildMetadataFile()` is:

```kotlin
val tilesWide = (sprite.size.width + 7) / 8
val tilesHigh = (sprite.size.height + 7) / 8
val oamCount = tilesWide * tilesHigh
```

For an 8×16 actor sprite in `SPRITES_8x16` hardware mode, the OAM hardware uses ONE slot per 8×16 pair. An 8×16 sprite is `tilesWide=1`, `tilesHigh=2` → `oamCount=2`, but the hardware allocates only 1 OAM entry (each entry covers both 8-pixel rows). The emulator agent's OAM-slot assertions driven by `game_metadata.json` will be wrong for 16px-tall actors, causing false failures or missed regressions in emulator integration tests. This is not a ROM-correctness issue but a metadata fidelity issue.

**Fix:** Apply the same actor-level `spriteMode` derivation used in the sidecar emission loop (line 396) to the metadata oamCount:

```kotlin
val oamSlotHeight = if (tileHeight <= 8) 8 else 16
val oamCount = tilesWide * ((sprite.size.height + oamSlotHeight - 1) / oamSlotHeight)
```

#### WR-03: Mixed SPR8x8 + SPR8x16 game would emit `SPRITES_8x16` but actors with 8px sprites are still cut as SPR8x8 — no guard exists for this illegal combination

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:4680-4688`

**Issue:** The `SPRITES_8x16` / `SPRITES_8x8` selection at line 4682 looks only at metasprites. If a game has both an SPR8x8 metasprite (e.g., elephant) and an SPR8x16 metasprite (e.g., player duck), the `any { it.spriteMode == SpriteMode.SPR8x16 }` check emits `SPRITES_8x16`. The actor sprites and SPR8x8 metasprites are then rendered in 8x16 hardware mode, halving their tile height rendering. GBDK hardware sprite mode is a global LCDC bit — all sprites share it. The validation gate in `validateMetaspriteSpritePaths()` does not check for this incompatible combination, nor does any analysis pass.

This is a latent defect that would become active the moment a game author mixes a large (SPR8x16) player metasprite and a small (SPR8x8) enemy metasprite in the same game.

**Fix:** Add a validation check in `validateMetaspriteSpritePaths()` (or a dedicated analysis pass) that throws `GradleException` when the game mixes SPR8x8 and SPR8x16 metasprites:

```kotlin
val modes = metasprites.mapNotNull { getSpriteMode(it) }.distinct()
if (modes.size > 1) {
    throw GradleException(
        "All metasprites in a game must use the same SpriteMode (hardware LCDC.SPRITE_SIZE " +
            "is global). Found both SPR8x8 and SPR8x16. (Phase 12.5 D-04b)"
    )
}
```

#### WR-04: `ConvertSpritesTask` sidecar reader uses `SpriteMode.valueOf()` on untrusted JSON — throws `IllegalArgumentException` instead of `GradleException` on invalid value

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt:145`

**Issue:** `SpriteMode.valueOf(entry.optString("spriteMode", "SPR8x16"))` will throw `java.lang.IllegalArgumentException` (not `GradleException`) if the sidecar contains a `spriteMode` value that is not `"SPR8x8"` or `"SPR8x16"` (e.g., a typo like `"SPR_8x16"` or a value from a future enum entry). The task wraps the `JSONException` case (malformed sidecar) but not enum valueOf failures. This results in an unhelpful Gradle task failure without a link to the sidecar or any fix suggestion.

**Fix:**

```kotlin
val spriteModeStr = entry.optString("spriteMode", "SPR8x16")
val spriteMode = try {
    SpriteMode.valueOf(spriteModeStr)
} catch (_: IllegalArgumentException) {
    throw GradleException(
        "Invalid spriteMode '$spriteModeStr' in game_metadata.json for sprite '${entry.optString("id")}'. " +
            "Expected SPR8x8 or SPR8x16. Re-run :generateC to regenerate the sidecar."
    )
}
```

#### IN-03: `SpriteModeIRTest` tests ordinal stability — this is a brittle contract for an enum that may grow

**File:** `gbkt-ir/src/test/kotlin/io/github/gbkt/core/ir/SpriteModeIRTest.kt:41-50`

**Issue:** The tests assert `spr8x8.ordinal == 0` and `spr8x16.ordinal == 1`. Enum ordinal depends on declaration order. If `SpriteMode` ever gains a third value inserted before `SPR8x16` (e.g., `SPR8x8_DOUBLE`), these tests break without any behavioral regression. Ordinal is not a meaningful semantic property of this enum — the tests add brittleness without locking a useful invariant.

**Fix:** Remove the two ordinal assertions. The name and size count tests are sufficient to lock the contract:

```kotlin
// Remove:
assertEquals(0, spr8x8.ordinal, "SPR8x8 must have ordinal 0")
assertEquals(1, spr8x16.ordinal, "SPR8x16 must have ordinal 1")
```
