## Plan 12.4-15: Anchor 4 re-shoot — PARTIAL / RED

### What landed

Two infrastructure commits cherry-picked onto `feat/d_and_d_gaps`:

1. **`4454f058` (was `1123f287`)** — `feat(12.4-15): add VisualDiff pixel-diff assertion to anchor4 test + fix HOME bank overflow`
   - `PlatformerTemplateUatTest.anchor4MetaspriteAnimation` grew the `VisualDiff.compare()` assertion (initially with the wrong tolerance — see commit 2).
   - `ConvertSpritesTask.kt` now injects `#pragma bank 1` into sprite sidecar `.c` files when `bank1.c` exists. Without this, `player_tiles[1984]` bloated HOME section and the ROM hung at boot with `EmulatorFrameHangException`. This is a real, generally-applicable fix — not specific to Plan 12.4-15.
   - `SHOW_BKG` → `DISPLAY_ON` LCD-on fix in the test path (was hanging `wait_vbl_done` forever).

2. **`61944cd2` (was `44fce068`)** — `fix(12.4-15): correct VisualDiff tolerance semantics — 0.95 → 0.05`
   - `VisualDiff.compare()` uses `isMatch = diffRatio <= tolerance`. Plan originally specified `tolerance=0.95` which meant `match=true` whenever ≤95% of pixels differ (almost always). The assertion `!match` then never fires. Corrected to `tolerance=0.05`: `match=true` only when ≤5% differ; the assertion fires when >5% differ, which is the SPEC REQ-6 contract.

### Why the duck still doesn't render

Investigation traced through `gbkt-examples/platformer-template/build/gbkt/generated/main.c` and `build/gbkt/generated/sprites/player.c`:

- `player_tiles[1984]` is real png2asset output (124 8×8 tiles, 62 8×16 pairs) — NOT a stub.
- `sprite_player_frame_0[]` has 6 `metasprite_t` entries with `{dy=-12,dx=-6,dtile=0}, {dy=8,dx=0,dtile=2}, {dy=8,dx=0,dtile=4}, {dy=-16,dx=16,dtile=6}, {dy=8,dx=0,dtile=8}, {dy=8,dx=0,dtile=10}, {metasprite_end}` — geometrically a 2-column × 3-row layout (16×48 pixels), NOT the 3-column × 2-row 24×32 layout that `-sw 24 -sh 32 -spr8x16` should produce.

Comparison against `evidence/png2asset-first-run/player_character_gbapduck_sprites.c` (the captured reference from Plan 12.4-08) shows the gbkt codegen reproduces the png2asset reference output byte-identically. **The bug is therefore upstream of the gbkt port** — it is in either:
(a) png2asset flag set (pivot `-px 12 -py 6` may be incompatible with desired anchor),
(b) the PNG asset itself (the source `player-character-gbapduck-sprites.png` may not have the expected 3×4-tile-per-frame layout that the flags assume), or
(c) a misunderstanding of how `png2asset` emits column-major-vs-row-major metasprite_t layouts in SPR8x16 mode.

All three diagnoses cross-cut asset semantics, png2asset configuration, and DSL interpretation — blast-radius wider than Plan 12.4-15's scope, wider than Phase 12.4's `MetaspriteVisitor/MetaspriteIR keep stable` constraint, and per `feedback_route_to_proper_phase_when_blast_radius_is_wide` they belong in their own phase.
