## Deviation: Rule 1 Bug Fix Applied During Sweep

**Finding:** Phase 12.4-03 (ConvertSpritesTask sidecar refactor) introduced a regression —
actor sprites were dropped from the `sprites[]` sidecar manifest when the task was refactored
from scanning `main.c` to reading `game_metadata.json`. This caused pong, breakout, and
simple-physics to fail with "No such file or directory" for their sprite headers.

A secondary issue: platformer-template's metasprite uses `sprite(asset("graphics/player-character-gbapduck-sprites.png"))`
but `metaspriteSpriteIncludes` generates `#include "sprites/player.h"` (using the metasprite id).
The sidecar lacked an `includePath` field, so ConvertSpritesTask derived the output path from
`spritePath` and placed the header at `sprites/player-character-gbapduck-sprites.h` instead of
`sprites/player.h`.

**Fix applied (commit 562ced65):**
1. `GBDKPipelineV2.buildMetadataFile()` — add actor sprites to `sprites[]` array + add
   `"includePath"` field to each entry (metasprites use `"sprites/<id>.h"`, actor sprites
   use path-derived include path)
2. `ConvertSpritesTask.convertSprites()` — read `"includePath"` from sidecar to determine
   output file location; use `includePath` stem for output `.c/.h` filenames (not `pngFile.nameWithoutExtension`)

**Root cause:** Phase 12.4-03 refactored ConvertSpritesTask to read from `sprites[]` metadata
(sidecar approach) replacing the old `parseSpriteIncludes(mainC)` main.c scanner. The old
scanner found ALL sprite includes (actor + metasprite). The new sidecar only had metasprites.
Actor sprites generate `#include "sprites/<stem>.h"` in main.c but were never added to the
sidecar until this fix.
