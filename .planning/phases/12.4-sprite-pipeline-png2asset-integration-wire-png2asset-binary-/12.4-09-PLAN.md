<objective>
Edit `PlatformerTemplate.kt`'s `val player by metasprite { }` block to (a) bind the explicit PNG
path via `sprite(asset("graphics/player-character-gbapduck-sprites.png"))` per D-05, and (b) expand
each of the 6 frames from a single-tile placeholder (`tile(0, 0, N)`) to a multi-tile composition
(~6 `tile()` calls per frame, ~36 total) per D-03 + D-14.

Covers SPEC REQ-2 (multi-tile metasprite composition), REQ-3 (`sprite()` DSL adoption), and REQ-4
(asset path convention applied).

Purpose: This is the deliverable that closes the visual gap. After this plan + Plan 12.4-13's ROM
smoke + Plan 12.4-15's anchor 4 re-shoot, the platformer-template ROM renders the duck art in 24×32
pixels per frame instead of a 64-byte checkerboard square.

Per CONTEXT D-03, the DSL `tile()` calls are authoritative for frame layout — png2asset only
provides the `_tiles[]` byte array. baseId values flow from the captured Plan 12.4-08 evidence
table (`player-tiles-ordering.md`).

This is the most artful plan in the phase: the executor must read the evidence table carefully,
respect the 8×16 sprite mode (each `tile(x, y, baseId)` in SPR8x16 represents an 8×16 pixel tile-pair),
and produce a `metasprite_t` layout that matches the duck art frames visually.

Output: One edit to PlatformerTemplate.kt — sprite binder + 36 tile() calls + obsolete-comment cleanup.
