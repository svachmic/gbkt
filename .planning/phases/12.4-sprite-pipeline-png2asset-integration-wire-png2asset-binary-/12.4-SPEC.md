# Phase 12.4: sprite-pipeline-png2asset-integration — Specification

**Created:** 2026-05-24
**Ambiguity score:** 0.14 (gate: ≤ 0.20)
**Requirements:** 6 locked

## Goal

The sprite asset pipeline (`ConvertSpritesTask` + DSL surface + metasprite composition) renders authored sprite art end-to-end for the platformer-template ROM so Phase 12.3 anchor 4 visible hflip closes; the existing metasprites / metasprites-stress / pong / breakout / banks / simple-physics ROMs keep building and rendering byte-identically; and the preventive `SEED-PHASE-12-CONVERTSPRITESTASK-AUDIT` is resolved by removing any synthesis-fallback antipatterns found during the audit.

## Background

Phase 12.3-15 anchor 4 re-shoot surfaced a confirmed defect: the platformer-template ROM renders the player metasprite as a uniform dark checkerboard square instead of the authored duck art. Investigation found:

1. **`ConvertSpritesTask` DOES invoke `png2asset`** (`gbkt-gradle-plugin/.../ConvertSpritesTask.kt:230`). The stub data is NOT a missing-toolchain failure.
2. **PNG path resolution mismatch:** Generated `main.c` emits `#include "sprites/player.h"`. The task looks for the PNG at `{assetDir}/sprites/player.png`. The actual asset is at `gbkt-examples/platformer-template/res/graphics/player-character-gbapduck-sprites.png` — different directory AND different filename stem. Mismatch → fallback path at `ConvertSpritesTask.kt:119` emits the 64-byte checkerboard stub (`generateStubCFile`).
3. **Metasprite composition is single-tile-per-frame:** Per `PlatformerTemplate.kt:333-343`, each frame currently declares one placeholder `tile(0, 0, N)`. Comments mark this as "deferred until Plan 12-18 wires the png2asset invocation". Even with correct path resolution, the metasprite would render as a single 8x16 tile sliver — not the 24×32 duck.
4. **No `sprite()` DSL exists:** Per `PlatformerTemplate.kt:313-316`, `MetaspriteBuilder.sprite()` is not yet implemented ("Phase 13 D-13 territory"). The asset PNG is loaded by id matching at the pipeline level.
5. **Preventive audit unresolved:** `SEED-PHASE-12-CONVERTSPRITESTASK-AUDIT` (created 2026-05-23 at Phase 12.2 close) flagged that `ConvertSpritesTask` may carry a synthesis-fallback antipattern similar to Phase 12.2's Defect 7 (`ConvertZoneTilesetsTask` synthetic-tilemap emission). No end-to-end audit has been performed.

Phase 12.3's emission work (PlatformerVisitor walk-cycle + cameraOffsetX + Phase 10.1-05 hflip) is correct (variable trace: walkFrameIdx cycles {1,2,0}, facingRot=3 triggers OAMF_HFLIP). Visible animation is blocked entirely downstream in the sprite pipeline.

## Requirements

1. **PNG path resolution**: `ConvertSpritesTask` discovers the platformer-template's player sprite PNG asset that drives the `sprites/player.h` include.
   - Current: `ConvertSpritesTask.kt:119` returns the missing-PNG fallback (`generateStubCFile`) because the include stem `player` doesn't match the actual file `player-character-gbapduck-sprites.png`, and the search root is `assetDir/sprites/` while the asset lives in `res/graphics/`.
   - Target: Either (a) the PNG is renamed/moved to a discoverable canonical location, OR (b) the task knows how to resolve the include's `<stem>` to the actual file via a documented convention. After this phase, `gbkt-examples/platformer-template/build/gbkt/generated/sprites/player.c` contains real png2asset output (multi-byte tile data derived from the duck sprite sheet), NOT the 64-byte stub.
   - Acceptance: After `./gradlew :gbkt-examples:platformer-template:clean :gbkt-examples:platformer-template:buildRom`, the file `build/gbkt/generated/sprites/player.c` does NOT contain the string "Stub sprite data" or "Replace with a valid PNG"; `wc -c` returns > 200 bytes.

2. **Multi-tile metasprite composition**: A metasprite frame can declare multiple `tile(relX, relY, baseId)` calls so a frame is composed of multiple 8×8 tiles (8×16 in 8x16 mode).
   - Current: `MetaspriteFrameBuilder` already accepts multiple `tile()` calls per `frame { }` block (DSL surface supports it); `PlatformerTemplate.kt:333-343` does not use this — each frame is single-tile.
   - Target: `PlatformerTemplate.kt`'s `val player by metasprite { }` block composes each of the 6 frames as a multi-tile arrangement that matches the duck sprite-sheet layout (the png2asset `-spr8x16 -px 12 -py 6 -sw 24 -sh 32` flags from `res/README.md` imply 24×32 sprite frames = 3 columns × 4 rows of 8×8 tiles = 6 tile pairs per frame in 8×16 mode).
   - Acceptance: Generated `bank1.c` `move_metasprite_*` calls reference a `metasprite_t` table with > 1 tile entry per frame (verifiable via `grep "{.*,.*,.*}" build/gbkt/generated/main.c | wc -l` on the `sprite_player_frame_0` table).

3. **`sprite()` DSL**: A standalone `sprite()` DSL block exists for binding metasprite frames to a specific asset PNG by explicit path.
   - Current: `MetaspriteBuilder.sprite()` is not implemented (`PlatformerTemplate.kt:313-316` comment). Asset PNGs are matched by id at the pipeline level, requiring naming-convention alignment.
   - Target: A `sprite(asset("graphics/player-character-gbapduck-sprites.png"))` builder call (or equivalent) inside `metasprite { }` binds the metasprite tile data to that explicit PNG path; the build pipeline routes the explicit path to `ConvertSpritesTask` regardless of include-name stem.
   - Acceptance: A unit test asserts `MetaspriteBuilder.sprite(AssetRef)` exists and that an IR walk recovers the bound asset path; the platformer-template's `val player by metasprite { ... sprite(asset("graphics/player-character-gbapduck-sprites.png")) ... }` builds successfully and the generated `player.c` contains real duck pixel data (Requirement 1 acceptance check).

4. **Asset path convention**: A documented convention exists for how DSL asset paths map to `res/` filesystem layout, and to the include name that `MetaspriteVisitor` emits.
   - Current: Convention is implicit / unspecified — `MetaspriteVisitor` emits `#include "sprites/<stem>.h"`; `ConvertSpritesTask` looks at `{assetDir}/sprites/<stem>.png`; assets actually live under arbitrary subdirs (`res/graphics/...`).
   - Target: Either (a) all sprite assets MUST live under `res/sprites/` with stem matching the metasprite name (codified in `res/README.md` + CLAUDE.md), OR (b) the include stem flows from the `sprite(asset(path))` binding and is decoupled from the metasprite name. Plus: existing games (pong/breakout/banks/simple-physics/metasprites/metasprites-stress) either already comply or are migrated.
   - Acceptance: `res/README.md` or `context/TOOLING.md` documents the convention; all 6 sprite-using games comply (no fallback-stub emission for any of them in clean buildRom output).

5. **Synthesis-fallback audit + removal**: `ConvertSpritesTask` is audited end-to-end; any synthesis-fallback antipattern (modulo tiling, hardcoded grids that fabricate byte data when asset is missing, silent placeholder emission paths beyond the `generateStubCFile` already documented) is either removed or has documented rationale + sentinel test.
   - Current: `SEED-PHASE-12-CONVERTSPRITESTASK-AUDIT` flagged the audit as preventive (no concrete defect known at that time). The 2026-05-24 finding confirms one synthesis path (`generateStubCFile` 64-byte checkerboard) exists but does NOT silently produce wrong output — it's gated on missing-PNG fallback and emits a comment marker.
   - Target: Audit complete. Any silent synthesis paths are removed or fail-fast. Documented synthesis paths (like the missing-PNG stub) either stay with a sentinel test OR escalate to a Gradle exception. The seed is marked resolved.
   - Acceptance: A test (e.g., `ConvertSpritesTaskSynthesisAuditTest`) asserts that ConvertSpritesTask either succeeds with real png2asset output OR throws a clear Gradle exception with the PNG path; no silent stub-then-pass path remains for in-scope games. `SEED-PHASE-12-CONVERTSPRITESTASK-AUDIT.md` frontmatter status updated to `resolved`.

6. **Phase 12.3 anchor 4 visible hflip closure**: The Phase 12.3 anchor 4 UAT re-runs against the post-12.4 ROM and produces visually-distinguishable left-facing vs right-facing player frames.
   - Current: Phase 12.3-15 anchor 4 PNGs show identical checkerboard placeholder in both facing-right and facing-left captures (variable trace passes; visual indistinguishable).
   - Target: After Phase 12.4 ships, a clean `:gbkt-examples:platformer-template:buildRom` + re-run of `PlatformerTemplateUatTest.anchor4MetaspriteAnimation` produces fresh anchor 4 PNGs in which the facing-left frame differs from any facing-right frame by more than a pixel-difference threshold.
   - Acceptance: A test or scripted check captures `anchor4-walk-frame-0.png` (facingRot=0) and `anchor4-facing-left.png` (facingRot=3), computes per-pixel diff in the metasprite-occupied region (player metasprite bounding box centered around the player position, ~24×32 px), and asserts > 5% of pixels differ. The fresh PNGs are committed to `.planning/phases/12.3-.../evidence/uat-screenshots/`, and Plan 12.3-15 SUMMARY.md is written + committed under the Phase 12.3 directory to close Plan 12.3-15 → close Phase 12.3.

## Boundaries

**In scope:**
- `ConvertSpritesTask.kt` PNG path resolution + audit + any fallback removal
- `MetaspriteBuilder.sprite()` DSL implementation (small new builder method + IR field)
- `PlatformerTemplate.kt` metasprite definition update (multi-tile composition + `sprite()` binding)
- Asset path / naming convention documentation (in `res/README.md` + `context/TOOLING.md`)
- `SEED-PHASE-12-CONVERTSPRITESTASK-AUDIT.md` status update to `resolved`
- Phase 12.3 anchor 4 re-shoot + visible-hflip acceptance + Plan 12.3-15 SUMMARY.md + Phase 12.3 close
- Asset file rename / move under `gbkt-examples/platformer-template/res/` if required to satisfy the convention
- Possible new tests: `ConvertSpritesTaskSynthesisAuditTest`, `MetaspriteSpriteDslTest`

**Out of scope:**
- Changes to the `png2asset` binary itself — it's GBDK toolchain; use as-is
- MetaspriteVisitor / MetaspriteIR rewrites — keep IR shape stable; only additive `sprite()` binding field if required
- Phase 13 framework primitives unrelated to sprites (entity pooling, smooth movement, etc.) — only `sprite()` DSL crosses into Phase 13 territory because it directly unblocks this phase
- Other archived sprite-using games (`shmup`, `racer`, `platformer`, `platformer-gbc`, `dungeon`, `explorer`, `rpg-lite`) — they're in `.archive/` per Phase 11.3 and out of the active matrix
- ConvertZoneTilesetsTask — sister task, already closed at Phase 12.2; no re-audit needed
- Visible WALK-cycle pose changes (separate from hflip) — frames 0/1/2 may visually animate as a byproduct of multi-tile composition, but the acceptance gate is hflip-only (right vs left); walk-cycle pose change is a "nice to have"

**Hard scope cap:** Terminal phase per `feedback_many_small_plans_terminal_subphase.md`. If discovered work has wider blast radius than fits in 12.4 (e.g., MetaspriteVisitor rewrites turn out to be required), escalate to a new sibling phase (12.5) — DO NOT create 12.4.1.

## Constraints

- **Back-compat (must not regress):** `pong`, `breakout`, `banks`, `simple-physics`, `metasprites`, `metasprites-stress` — all 6 sprite-using ROMs must build clean (`./gradlew :gbkt-examples:<game>:buildRom`) AND their existing UAT tests must stay GREEN. For `metasprites` + `metasprites-stress` specifically, the generated sprite C files must be byte-identical (or functionally equivalent — same `_tiles` array contents) to the pre-12.4 baseline so Phase 10/10.1 UAT GREEN screenshots reproduce.
- **png2asset binary:** Use as-is; no patches or forks. If the binary is missing the existing warn-and-skip path stays (already in `ConvertSpritesTask.kt:92-97`).
- **D-09 ROM smoke (per memory rule `rom_build_smoke_test_for_codegen_phases`):** Phase 12.4 terminal gate MUST include a clean `:gbkt-examples:platformer-template:buildRom` smoke test before declaring complete.
- **Visual Evidence Rule (per CLAUDE.md):** Requirement 6 acceptance MUST capture runtime screenshots, not just variable assertions (Requirement 6 already enforces this via the pixel-diff check).
