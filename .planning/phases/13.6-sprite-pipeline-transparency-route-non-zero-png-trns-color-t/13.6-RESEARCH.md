## Summary

The central research question was whether Mechanism A (pre-permute the PNG palette in-memory,
then pass `-keep_palette_order` as before) or Mechanism B (use a png2asset transparent-color
flag alongside or instead of `-keep_palette_order`) is the correct approach.

**Finding:** Mechanism A is correct. Mechanism B is not viable because png2asset has no
transparent-color flag in its CLI. The full `png2asset --help` output (verified against
the installed binary at `/Users/michalsvacha/gbdk/bin/png2asset`) lists only
`-keep_palette_order` and `-repair_indexed_pal` as palette-order flags — there is no
`-spr_color`, `-transparent`, or similar transparent-color argument.

Mechanism A is fully viable on the JVM: `javax.imageio.ImageIO.read()` on an indexed PNG
returns a `BufferedImage` with an `IndexColorModel` whose `getTransparentPixel()` method
returns the fully-transparent palette index directly (confirmed: returns 4 for `elephant.png`,
-1 for sprites with no tRNS chunk). Pixel-level reindexing uses `getRaster().getSample(x,y,0)`
to count usage per index and build a compact remap that skips unused (0-pixel) entries. The
pre-permuted PNG is written to a temp file or ByteArrayOutputStream, passed to png2asset with
`-keep_palette_order`, then the temp file deleted.

A live verification run confirmed the correct 2bpp output: after pre-permutation, the
elephant tile distribution shows 40.7% transparent (index 0), 17.9% outline at index 1,
14.6% green midtone at index 2, and 26.8% near-white body at index 3 — exactly matching
the seed's proven reorder experiment.

**Primary recommendation:** Use Mechanism A — pre-permute the PNG palette in-memory (or via
temp file) so that the tRNS-transparent color lands at index 0, then pass the permuted PNG
to png2asset with `-keep_palette_order` unchanged.

### Pattern 1: IndexColorModel tRNS Detection

**What:** Use `ImageIO.read()` + `IndexColorModel.getTransparentPixel()` to get the tRNS
transparent palette index.

**When to use:** In `PngUtils.kt` as `getTransparentIndexShared(file: File): Int?`

```kotlin
// Returns the palette index of the fully-transparent color (tRNS chunk), or null
// if the PNG is not indexed or has no tRNS chunk.
// Sentinel: null means "none" (non-indexed, no tRNS, or ImageIO read failure).
internal fun getTransparentIndexShared(file: File): Int? {
    if (!file.isFile) return null
    return try {
        val img = javax.imageio.ImageIO.read(file) ?: return null
        val cm = img.colorModel as? java.awt.image.IndexColorModel ?: return null
        val tidx = cm.transparentPixel
        if (tidx < 0) null else tidx
    } catch (_: Exception) {
        null
    }
}
```

**Key findings from Java test:**
- `elephant.png` (tRNS=4): `getTransparentPixel()` = 4  [VERIFIED: Java test run]
- `player-character-gbapduck-sprites.png` (no tRNS): `getTransparentPixel()` = -1  [VERIFIED]
- `tiger.png` (tRNS=4): `getTransparentPixel()` = 4  [VERIFIED]
- `track.png`, `car.png` (no tRNS): -1  [VERIFIED]
- Non-indexed PNGs (pong ball, breakout paddle): `IndexColorModel` cast returns null  [VERIFIED]

### Pattern 2: Pre-Permute PNG Palette (Mechanism A)

**What:** Build a compact remap (transparent→0, used visible→1..N, skip 0-pixel entries),
rewrite PLTE + tRNS + pixel data in-memory, write to a `File.createTempFile()` alongside
the original (so relative paths and GBDK detection still work), pass temp file to png2asset,
delete temp file after execution.

**When to use:** In `ConvertSpritesTask.convertSprite()` before the `buildPng2AssetArgs()`
call, when `getTransparentIndexShared(pngFile) > 0`.

```kotlin
// In ConvertSpritesTask.convertSprite() — before buildPng2AssetArgs():
val transparentIdx = getTransparentIndexShared(pngFile)
val pngToConvert: File
val tempFile: File?

if (transparentIdx != null && transparentIdx > 0) {
    if (strictTransparency) {
        throw GradleException(
            "sprite ${pngFile.name} declares transparent color at palette index " +
                "$transparentIdx≠0 (strict mode enabled — fix the source PNG or disable strict mode)"
        )
    }
    // Overflow guard: count used (non-zero-pixel) visible colors
    val usedVisibleCount = countUsedVisibleColors(pngFile, transparentIdx)
    if (usedVisibleCount > 3) {
        throw GradleException(
            "sprite ${pngFile.name}: transparent + $usedVisibleCount used visible colors " +
                "exceeds GB OBJ palette limit (max 3 visible)"
        )
    }
    logger.warn(
        "sprite ${pngFile.name} declares transparent color at palette index " +
            "$transparentIdx≠0; framework routed it to GB OBJ index 0 " +
            "(enable strict mode to fail instead)"
    )
    tempFile = prePermuteIndexedPng(pngFile, transparentIdx)
    pngToConvert = tempFile
} else {
    tempFile = null
    pngToConvert = pngFile
}

// ... build args, exec png2asset, then:
tempFile?.delete()
```

**Critical algorithm for pre-permutation (verified by Python simulation + live png2asset run):**
1. `ImageIO.read(file)` → `IndexColorModel` for palette, `Raster` for pixel counts
2. Count pixel usage: `raster.getSample(x, y, 0)` per pixel → `pixelCounts[paletteIdx]++`
3. Build compact remap: `transparentIdx → 0`; for each `old` in order (0..mapSize-1) where
   `old != transparentIdx && pixelCounts[old] > 0`: `old → nextNew++`
4. **Must skip 0-pixel entries** (e.g. elephant's bright-green at idx 2). If kept, body color
   ends up at palette index 4 which 2bpp cannot encode → body pixels bleed into transparent
   slot. [VERIFIED by live test — simple reorder without skipping fails.]
5. Rewrite the raw PNG bytes: new PLTE (compact-ordered), new tRNS (index 0 = alpha 0),
   new IDAT (decompress, remap each pixel byte, recompress)
6. Alternative: can build a new `BufferedImage` with `IndexColorModel` from compact palette
   and copy remapped pixels — then `ImageIO.write()`. Either raw-chunk or ImageIO approach works.

**Verified result (live run on elephant.png with compact remap → png2asset -keep_palette_order):**

| 2bpp idx | Color | BROKEN (current) | FIXED (pre-permuted) |
|---:|---|---:|---:|
| 0 | transparent BG | 54.8% (bg+outline merged) | 40.7% (bg only) |
| 1 | outline (7,24,33) | 15.9% | 17.9% (visible slot) |
| 2 | green midtone | 0.0% (wasted) | 14.6% |
| 3 | near-white body | 29.2% | 26.8% |

[VERIFIED: Python simulation + Java test + live png2asset run 2026-06-05]

### Anti-Patterns to Avoid

- **Simple palette reorder without compacting unused entries:** If you just swap transparent
  to index 0 in a 256-entry PLTE without skipping 0-pixel entries, body color falls at
  palette index 4+, which 2bpp cannot represent (only 0-3) → body pixels merge into index 0
  (transparent). VERIFIED FAILURE. [VERIFIED: live test 2026-06-05]
- **Using png2asset transparent-color flag (Mechanism B):** No such flag exists in png2asset.
  The full `--help` output was verified against the installed binary. Flags are limited to
  `-keep_palette_order` and `-repair_indexed_pal` for palette control. [VERIFIED: binary run]
- **Using `-repair_indexed_pal`:** This flag implies `-keep_palette_order` but its behavior
  is for "repairing" broken indexed palettes — not for transparent-slot routing. Its semantics
  are not specified precisely and may not guarantee transparent→index 0. Mechanism A is safer
  and deterministic. [ASSUMED based on flag name and help text; no authoritative docs]
- **Passing the original PNG to png2asset and hoping auto-sort handles it:** Phase 12.9
  explicitly documented that png2asset's default auto-sort is unreliable (moved platformer
  player's orange bg off index 0). Never remove `-keep_palette_order`. [CITED: SPEC.md § Background]
- **Modifying the source PNG asset on disk:** Out of scope per SPEC.md § Boundaries.

## Common Pitfalls

### Pitfall 1: Simple Palette Reorder Without Compact Remapping

**What goes wrong:** If you swap transparent to index 0 in a 256-entry PLTE but don't skip
unused (0-pixel) entries, the body color ends up at 2bpp index 4 — which exceeds the 2-bit
range. 2bpp encodes only values 0-3; index 4 wraps to index 0 (transparent). Body pixels
become invisible. [VERIFIED: live test with simple reorder → elephant body vanished at 67.5% idx0]

**Why it happens:** The elephant has 5 unique palette entries but only 4 used. The unused
bright-green at source index 2 must be skipped in the remap to keep body at index ≤ 3.

**How to avoid:** Build a compact remap: `{transparentIdx→0, used-visible-colors→1,2,3}`.
Only palette entries with pixel_count > 0 AND not transparent get a new index.

**Warning signs:** Generated 2bpp tiles show >60% at index 0 (body merging into transparent slot).

### Pitfall 2: Leaving Temp File if png2asset Fails

**What goes wrong:** If png2asset exits non-zero, the temp file leaks to disk.

**How to avoid:** Use try/finally: `tempFile?.delete()` in a `finally` block.

### Pitfall 3: `ImageIO.read()` on a Large PNG is Not Fast

**What goes wrong:** `elephant.png` is 64×240 = 15360 pixels; ImageIO reads + decompresses
all pixel data even just to count usage. For very large sprite sheets, this could be slow.

**How to avoid:** The pixel-count pass and the remap pass can be combined into one ImageIO
read (not two). Store the pixel count array alongside the remap. For typical GB sprites
(≤256×256), this is negligible.

### Pitfall 4: tRNS Detection on Non-Indexed PNG Returns Wrong Type

**What goes wrong:** `ImageIO.read()` on a non-indexed PNG may return a `BufferedImage`
whose `ColorModel` is not an `IndexColorModel`. Casting fails with ClassCastException.

**How to avoid:** Check `img.colorModel is IndexColorModel` before casting. If not
IndexColorModel, return null (the "none" sentinel). [VERIFIED: Java test confirmed
`ComponentColorModel` for RGBA PNGs]

### Pitfall 5: Re-pinning Baselines Without Running `convertSprites` First

**What goes wrong:** If baselines are re-pinned before 13.6 code lands (i.e., the old
broken elephant.c is captured as the new baseline), the byte-identity test becomes a
regression oracle for the WRONG output.

**How to avoid:** The baseline re-pin task must run AFTER the 13.6 mechanism is implemented
and the permutation produces the correct 2bpp output. Capture order: implement → run
`convertSprites` → verify 2bpp distribution → re-pin baselines → commit.

### Pitfall 6: Strict Mode Must NOT Fire for No-tRNS Sprites

**What goes wrong:** A strict mode check that fires on `isIndexedPng && !isIndex0Transparent`
would fail for sprites with no tRNS chunk at all (e.g. platformer player with
`getTransparentPixel() = -1`).

**How to avoid:** Strict mode fires ONLY when `tRNS index != null && tRNS index > 0`.
No tRNS chunk (null/sentinel) → no check, no warning, no failure.

### Pitfall 7: Silent `S_PAL` Descriptor Regression After Permutation

**What goes wrong:** The pre-permutation reshapes the PNG palette before png2asset runs. If
png2asset emits a different number of metasprite frame descriptors (or a different `S_PAL(n)`
distribution) from the permuted PNG vs the original, the `remapMetaspriteSubPalette`
post-process (Phase 13.3 D-19, which rewrites `S_PAL(1)` → `S_PAL(0)`) could silently
operate on the wrong descriptor count — elephant metasprite frames would render with the
wrong sub-palette while the byte-identity baseline (re-pinned from the same permuted output)
masks the regression because it re-pins the wrong result.

**How to avoid:** Assert the post-permutation `S_PAL` descriptor count in the generated
`elephant.c` matches the pre-fix baseline descriptor count as an EXPLICIT automated grep —
the 2bpp indices change with the permuted PNG, but the metasprite frame `S_PAL` count must
NOT change. This assertion MUST run BEFORE the Plan 05 baseline re-pin (so the oracle is
validated against a known-good descriptor count, not a re-pinned-then-trusted side effect).
[Resolved by Plan 03 Task 3 — see Open Questions (RESOLVED) below.]

### tRNS Index Detection (PngUtils.kt extension)

```kotlin
// Source: verified by Java stdlib test 2026-06-05 against elephant.png
/**
 * Returns the declared transparent palette index for an indexed PNG (the index
 * referenced by the tRNS chunk), or null when:
 * - The file is not an indexed PNG (IHDR color-type != 3)
 * - The PNG has no tRNS chunk
 * - The file cannot be read or decoded
 *
 * This is the "none" sentinel per SPEC Req 1: null means no tRNS routing is needed.
 * Delegates to javax.imageio.ImageIO + IndexColorModel.getTransparentPixel().
 */
internal fun getTransparentIndexShared(file: File): Int? {
    if (!file.isFile) return null
    return try {
        val img = javax.imageio.ImageIO.read(file) ?: return null
        val cm = img.colorModel as? java.awt.image.IndexColorModel ?: return null
        val tidx = cm.transparentPixel
        if (tidx < 0) null else tidx
    } catch (_: Exception) {
        null
    }
}
```

### Pixel Count + Overflow Guard

```kotlin
// Source: Java stdlib Raster API, verified 2026-06-05
/**
 * Count used (non-zero-pixel) visible palette indices — excludes the transparent index.
 * Returns the count for the overflow guard (Req 5): if > 3, the sprite exceeds the
 * GB OBJ palette (1 transparent + 3 visible = 4 entries).
 */
internal fun countUsedVisibleColors(file: File, transparentIdx: Int): Int {
    val img = javax.imageio.ImageIO.read(file) ?: return 0
    val cm = img.colorModel as? java.awt.image.IndexColorModel ?: return 0
    val raster = img.raster
    val pixelCounts = IntArray(cm.mapSize)
    for (y in 0 until img.height) {
        for (x in 0 until img.width) {
            val idx = raster.getSample(x, y, 0)
            if (idx in pixelCounts.indices) pixelCounts[idx]++
        }
    }
    return pixelCounts.indices.count { it != transparentIdx && pixelCounts[it] > 0 }
}
```

### Pre-Permute Approach — Compact Remap

The remap algorithm (verified by live png2asset run):
```
remap[transparentIdx] = 0
nextNew = 1
for old in 0 until mapSize:
    if old != transparentIdx AND pixelCounts[old] > 0:
        remap[old] = nextNew++
```

Elephant result: `{4→0, 0→1, 1→2, 3→3}` (old index 2 / bright-green with 0 pixels is skipped).

PNG rewrite options (both stdlib, planner's choice):
- **Option i — ImageIO.write():** Create new `IndexColorModel` from compact palette, copy
  remapped pixel data into a new `BufferedImage`, write with `ImageIO.write(img, "PNG", tempFile)`.
  Simpler code; relies on ImageIO's PNG encoder faithfully preserving indexed mode.
- **Option ii — Raw chunk manipulation:** Decompress IDAT, remap bytes, recompress; rewrite
  PLTE + tRNS + IDAT chunks. More code; fully deterministic output.
  
Both options are safe. Option i is recommended for code simplicity. If ImageIO encodes a
different bit-depth or color type, Option ii is the fallback.

## Open Questions (RESOLVED)

1. **ImageIO.write() indexed PNG fidelity (A2)**
   - What we know: `ImageIO.read()` correctly decodes elephant.png as indexed mode with
     `IndexColorModel`. `ImageIO.write()` with PNG format is available in JVM stdlib.
   - What's unclear: Whether JVM's PNG encoder preserves indexed mode when writing back
     a `BufferedImage` created from an `IndexColorModel`, or upgrades to RGBA.
   - Recommendation: Wave 0 — write a unit test that round-trips a 4-color indexed PNG
     through `ImageIO.read()` → new `IndexColorModel` → `ImageIO.write()` and verify
     the output is still indexed (IHDR color-type = 3). If it fails, use raw chunk
     manipulation instead.
   - **RESOLVED:** Plan 01 Task 3 (`ImageIoIndexedRoundTripTest`) is the Wave 0 gating test
     that measures the written IHDR color-type and pins the verdict (Option i viable vs
     Option ii required). Plan 03 Task 1 reads that verdict from `13.6-01-SUMMARY` and
     selects its PNG-rewrite mechanism accordingly. A2 is no longer an assumption — it is
     answered by an executable, CI-pinned test before any production code lands.

2. **`remapMetaspriteSubPalette` interaction post-fix**
   - What we know: `remapMetaspriteSubPalette` replaces `S_PAL(1)` → `S_PAL(0)` in the
     elephant.c descriptor (Phase 13.3 D-19). After pre-permutation, the palette structure
     changes but 2bpp indices 0-3 remain the same mapping — transparent is still index 0,
     outline at 1, etc. The `S_PAL` descriptor is about OBJ sub-palette slot assignment,
     not about palette entry index. This post-process should remain valid.
   - What's unclear: Whether png2asset generates the same number of `S_PAL(1)`/`S_PAL(0)`
     entries from the pre-permuted PNG vs the original.
   - Recommendation: During Wave 1 verification, confirm `remapMetaspriteSubPalette` still
     produces a correct result on the new permuted elephant.c output.
   - **RESOLVED:** Plan 03 Task 3 adds an explicit automated assertion — after running
     `:gbkt-examples:metasprites:convertSprites`, it greps the generated `elephant.c` for the
     `S_PAL(0)` descriptor count and asserts it equals the pre-fix baseline descriptor count
     (the 2bpp indices change with the permuted PNG, but the metasprite frame `S_PAL` count
     must NOT silently regress). This assertion runs BEFORE Plan 05's baseline re-pin, so the
     re-pinned oracle is validated against a known-good descriptor count rather than blindly
     trusting whatever the permuted output produced. See Common Pitfalls § Pitfall 7.
