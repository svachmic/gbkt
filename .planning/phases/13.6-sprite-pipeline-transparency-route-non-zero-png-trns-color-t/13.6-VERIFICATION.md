## Code-Review Warning Adjudications (13.6-07-REVIEW.md)

### W1 (= REVIEW "WR-01"): countUsedVisibleColors catch over-broad — REQ-5 overflow guard silently bypassed on non-IO exceptions

**REVIEW finding:** `catch (_: Exception) { 0 }` wraps the entire pixel-scan loop. If a logic error or unexpected raster shape throws a non-IOException, the catch returns 0, making `usedVisibleCount > 3` false and silently bypassing the REQ-5 guard. The sibling `getTransparentIndexShared` uses the same broad catch, but there the failure is fail-open-to-null on an unread file; here it is fail-open-past-a-guard on a file already validated.

**Verdict: ACCEPTABLE FOLLOW-UP — does not block phase goal.**

Reasoning: The critical precondition is already established at the call site. `countUsedVisibleColors` is only reached after `getTransparentIndexShared(pngFile)` returned a non-null index — meaning `ImageIO.read(pngFile)` already succeeded and the PNG already parsed as an IndexColorModel. The pixel-scan loop itself (`raster.getSample` with bounds check `if (idx in pixelCounts.indices)`) has no plausible throw path on a well-formed indexed PNG. A catastrophic raster shape producing an unexpected exception is a programmer error, not a user-authored malformed file. The phase's primary target (elephant.png with 3 used visible colors) exercises the guard correctly and the pluginTest suite covers the overflow-guard pass/fail boundary. The robustness gap — narrowing the catch to IOException so a logic bug does not silently pass the guard — is real and worth fixing, but it does not affect any of the phase's six requirements as exercised by the test corpus. Track as a follow-up hardening item.

### W2 (= REVIEW "WR-02"): Same-basename collision — deterministic name keys on file.nameWithoutExtension, not unique stemName

**REVIEW finding:** Two sprite entries resolving to PNGs with the same basename in different directories (e.g. `sprites/a/hero.png` and `sprites/b/hero.png`) both map to `buildTempDir/gbkt_permuted_hero.png`. Processing is currently serial, so this is not a same-run data race today, but it is a latent correctness regression relative to the prior random-name scheme.

**Verdict: ACCEPTABLE FOLLOW-UP — does not block phase goal.**

Reasoning: REQ-6 requires that generated sprite C is reproducible across rebuilds for the phase's actual metasprite corpus (elephant, tiger). The collision hazard is latent: the metasprites and metasprites-stress examples have no same-basename collision, and the current serial loop ensures delete-before-write gives correct behavior for any single basename. The double-rebuild determinism proof covers the real-world corpus. The fix (key the name on `stemName` instead of `file.nameWithoutExtension`) is low-risk and straightforward, but it addresses a correctness risk for a future project configuration, not a defect in the shipped behavior. Track as a follow-up.

### W3 (= REVIEW "WR-03"): buildTempDir under @OutputDirectory — Gradle cache fingerprint pollution

**REVIEW finding:** `File(sourceDir, "sprites/tmp")` places the temp directory inside `cSourceDir`, which is declared `@get:OutputDirectory` on a `@CacheableTask`. The temp PNG files are deleted in the `finally` block, but the `sprites/tmp/` directory itself is never removed. An empty (or, on crash, non-empty) `tmp/` subdirectory becomes part of the task's declared output tree, potentially perturbing Gradle's cache fingerprinting for incremental builds. The double-rebuild proof covers only clean builds.

**Verdict: ACCEPTABLE FOLLOW-UP — does not block phase goal.**

Reasoning: REQ-6's stated goal is reproducible generated sprite C — specifically that the `png2asset "Conversion args" comment` is stable across rebuilds because it embeds the deterministic base name. The deterministic base name is a pure function of `file.nameWithoutExtension`; it does not embed the absolute directory path (png2asset echoes only the basename in the comment, as shown in the baselines). The `sprites/tmp/` directory is empty after each successful run (the `finally` deletes the temp PNG), so Gradle's up-to-date check fingerprints an empty directory — identical across runs. The residual risk is: (a) a mid-build crash leaves a non-empty tmp/ that survives into the cached output; (b) cached/incremental builds may behave differently from clean builds with respect to stale permuted PNGs. Neither scenario produces non-deterministic generated C for successful builds. The proper fix is to use `task.temporaryDir` instead of a subdirectory of @OutputDirectory, which keeps the determinism property while eliminating the output-tree pollution. Track as a follow-up.

**Follow-up tracking summary:**

All three warnings are ACCEPTABLE FOLLOW-UPS. None blocks the phase goal. Recommended next actions:
- W1: narrow `countUsedVisibleColors` catch to `IOException` in a hardening pass
- W2: key the deterministic temp name on `stemName` instead of `file.nameWithoutExtension`
- W3: replace `File(sourceDir, "sprites/tmp")` with `temporaryDir` (Gradle per-task temp dir)

These three can be bundled into a single small maintenance plan.
