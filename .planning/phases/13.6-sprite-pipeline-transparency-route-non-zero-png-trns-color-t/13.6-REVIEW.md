# Phase 13.6: Code Review Report

**Reviewed:** 2026-06-05T00:00:00Z
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

Reviewed the Phase 13.6 sprite-pipeline tRNS auto-routing implementation: the
`prePermuteIndexedPng` compact remap (`PngUtils.kt`), its wiring in
`ConvertSpritesTask.convertSprite`, the `strictTransparency` opt-in knob
(`GbktExtension`/`GbktPlugin`), and the REQ-5 overflow guard. The strict-mode
path, extension wiring, and the `getTransparentIndexShared` sentinel discipline
are clean and well-tested.

The defects cluster around **exception/leak discipline in the temp-file path**.
Two functions that the KDoc/comments claim are exception-safe are not:
`prePermuteIndexedPng` leaks its temp file if `ImageIO.write` throws, and
`countUsedVisibleColors` propagates a raw `IOException` despite its KDoc
promising "0 if the file cannot be read." There is also a narrow temp-leak
window in `convertSprite` between temp creation and the guarded `try`, and the
two `error()` calls in `prePermuteIndexedPng` surface as raw
`IllegalStateException` rather than an actionable `GradleException`. No
correctness bug rises to BLOCKER — the auto-route logic itself is sound and the
strict/overflow gates fire in the correct order — but the leak/exception
findings should be fixed before this ships as a robustness guarantee.

## Warnings

### WR-01: `prePermuteIndexedPng` leaks its temp file if `ImageIO.write` throws

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/PngUtils.kt:241-243`
**Issue:** The temp file is created (`File.createTempFile`) and then written
(`ImageIO.write`). If `ImageIO.write` throws (disk full, I/O error, encoder
failure), the function exits via exception **without returning the file**, so the
caller's `finally`-block cleanup (`tempFile?.delete()`) never runs — `tempFile`
was never assigned. The result is an orphaned `gbkt_permuted_*.png` adjacent to
the source asset, contradicting the KDoc's "Temp-file leak (T-13.6-03b)"
mitigation claim. The caller comment at `ConvertSpritesTask.kt:318` also
attributes leak-safety entirely to the caller's `finally`, which does not cover
this window.
**Fix:**
```kotlin
val temp = File.createTempFile("gbkt_permuted_", ".png", file.parentFile)
try {
    ImageIO.write(newImg, "PNG", temp)
} catch (e: Exception) {
    temp.delete()
    throw e
}
return temp
```

### WR-02: `countUsedVisibleColors` propagates raw exceptions despite KDoc promising "0 if unreadable"

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/PngUtils.kt:130-142`
**Issue:** The KDoc states the function returns "0 if the file cannot be read or
is not an indexed PNG," and the sibling `getTransparentIndexShared` (lines
97-107) wraps its body in `try { ... } catch (_: Exception) { null }`. But
`countUsedVisibleColors` has **no try/catch**: `ImageIO.read(file)` can throw
`IOException` on a malformed/truncated PNG (exactly the T-13.6-02b malformed-PNG
threat the function is meant to mitigate). On the strict-off overflow-guard path
(`ConvertSpritesTask.kt:338`) this raw exception escapes the guard as an
unwrapped `IOException`, not the intended fail-fast `GradleException`, and the
behavior diverges from the documented contract.
**Fix:** Wrap the body to honor the documented sentinel:
```kotlin
internal fun countUsedVisibleColors(file: File, transparentIdx: Int): Int {
    return try {
        val img = ImageIO.read(file) ?: return 0
        val cm = img.colorModel as? IndexColorModel ?: return 0
        // ... existing body ...
        pixelCounts.indices.count { it != transparentIdx && pixelCounts[it] > 0 }
    } catch (_: Exception) {
        0
    }
}
```

### WR-03: `prePermuteIndexedPng` throws raw `IllegalStateException` via `error()` instead of an actionable `GradleException`

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/PngUtils.kt:178-180`
**Issue:** Both failure paths use `error(...)`, which throws `IllegalStateException`.
This function is called from `convertSprite` **outside** the `try` block (line
352), so the exception propagates unwrapped to Gradle as a stack-trace-style
`IllegalStateException`, not the actionable, file-named `GradleException`
pattern that the rest of this task uses (cf. the malformed-sidecar and
invalid-spriteMode handlers at `ConvertSpritesTask.kt:117` and `:166`, and the
project's WR-02/WR-04 conventions). A developer with a corrupt PNG gets a
cryptic internal error rather than "which sprite, what to do." The
preconditions should not normally fail (caller already verified `transparentIdx
>= 0` and indexed-ness), but the asymmetry with the established error-handling
convention is a real maintainability/UX defect.
**Fix:** Either wrap the `prePermuteIndexedPng` call at the call site in a
`try/catch` that rethrows a `GradleException` naming `pngFile.name`, or change
the `error()` calls to throw a typed exception the caller maps. Prefer the
call-site wrap so `PngUtils` stays Gradle-agnostic.

### WR-04: Temp-file leak window between `prePermuteIndexedPng` and the guarded `try` in `convertSprite`

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt:352-396`
**Issue:** `tempFile` is assigned at line 352-353, but the `try/finally` that
deletes it does not begin until line 376. Between those points,
`buildPng2AssetArgs(pngFile = pngToConvert, ...)` runs (line 362-372), which
calls `isIndexedPngShared(pngToConvert)` reading the temp PNG. If anything in
that window throws (e.g., an `IndexColorModel` cast or read failure surfaced by
a future change, or an OOM building the args), the temp file leaks because the
`finally` is not yet in scope. The window is small today but the cleanup
guarantee is structurally incomplete.
**Fix:** Move the temp-file lifetime into a single `try { ... } finally {
tempFile?.delete() }` that wraps everything from immediately after
`prePermuteIndexedPng` returns through the png2asset exec, so no statement that
can throw sits outside the cleanup scope.

### WR-05: Non-ASCII `≠` character embedded in `GradleException` / warning messages

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt:329, 349`
**Issue:** The strict-mode exception (`"...palette index $transparentIdx≠0..."`,
line 329) and the auto-route warning (`"...palette index $transparentIdx≠0..."`,
line 349) embed a literal U+2260 (`≠`) in user-facing build output. Console
encodings that are not UTF-8 (common on Windows `cp1252`/`cp437` terminals, and
some CI log collectors) render this as mojibake (e.g. `â‰ `), degrading an
error message whose whole purpose is to be read and acted on. The codebase
elsewhere deliberately uses ASCII in build messages.
**Fix:** Replace `≠0` with ASCII, e.g. `"... at palette index $transparentIdx
(expected 0) ..."` or `"...index $transparentIdx != 0..."`.

### WR-06: Strict-mode default flip in `platformer-template` is an unverified behavioral change with no asset guarantee

**File:** `gbkt-examples/platformer-template/build.gradle.kts:42-44`
**Issue:** `platformer-template` opts into `sprites { strictTransparency.set(true) }`.
Strict mode hard-fails `:convertSprites` (and therefore `:buildRom`) for **any**
indexed sprite PNG whose tRNS sits at a non-zero index. This example is the
GBC-target platformer reference port and is exercised by `:buildRom` smoke tests
(per the project's ROM-build-smoke-test rule for codegen phases). If any sprite
asset under `res/` — now or after a future art update — has a non-zero tRNS
index, the build now fails where it previously auto-corrected. The diff turns on
a fail-closed gate for a shipped example without an accompanying assertion that
all its current assets satisfy index-0 tRNS. (The phase's own
`player-character-gbapduck-sprites.png` is no-tRNS per `PngUtilsTest`, so it is
safe today, but nothing pins this invariant for the rest of the asset set.)
**Fix:** Confirm via a clean `./gradlew :gbkt-examples:platformer-template:buildRom`
that strict mode passes for the full current asset set (visual-evidence /
ROM-build-smoke rule), and add a short comment in the build file documenting why
strict is appropriate here (all source PNGs are authored with transparent at
index 0). If any asset relies on auto-correct, this flag will silently break the
example.

## Info

### IN-01: `getTransparentIndexShared` and `countUsedVisibleColors` each re-decode the PNG independently

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/PngUtils.kt:97, 130, 177`
**Issue:** On the auto-route path, the same PNG is decoded by `ImageIO.read`
three times: once in `getTransparentIndexShared` (line 100), once in
`countUsedVisibleColors` (line 131), and once in `prePermuteIndexedPng` (line
178). This is a (out-of-v1-scope) performance note, but it is also a
correctness-adjacent smell: three independent decodes assume the file is stable
between reads. Noting for awareness; not actionable for v1.
**Fix:** (Optional) decode once and pass the `BufferedImage`/`IndexColorModel`
into the helpers.

### IN-02: Dead/duplicated overflow-fixture generator in test helpers

**File:** `gbkt-gradle-plugin/src/test/kotlin/io/github/gbkt/gradle/tasks/PngUtilsTest.kt:140-195`
**Issue:** `writeIndexedSpritePng` (PngUtilsTest) and `writeIndexedPngWithTrns`
(ConvertSpritesTaskSidecarTest) are near-identical indexed-PNG fixture builders
with the same ImageIO round-trip caveat documented in both. Duplication invites
drift. Not a defect.
**Fix:** (Optional) extract a single shared test fixture helper.

### IN-03: Test 15 is largely narrative comment with conditional early-returns that can no-op the assertion

**File:** `gbkt-gradle-plugin/src/test/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTaskSidecarTest.kt:916-1089`
**Issue:** `overflow_fixture_with_4_used_visible_throws_gradle_exception` contains
~60 lines of exploratory comments and multiple `return` early-exits (no GBDK,
no unused slot, `ovTrnsIdx <= 0` after ImageIO round-trip). The end-to-end
overflow `GradleException` assertion (lines 1071-1088) only runs when the
synthetic PNG happens to preserve a non-zero `transparentPixel` after round-trip
— which the file itself documents as unreliable. On most JVMs this test
silently degrades to only the primitive `countUsedVisibleColors > 3` check and
never exercises the guard in `convertSprite`. The guard is covered indirectly,
but the test's headline behavior is frequently skipped without signal.
**Fix:** (Optional) split into a pure-primitive test (always runs) and a
GBDK/real-asset end-to-end test that uses a committed fixture PNG with a known,
round-trip-stable non-zero tRNS index, so the guard path is deterministically
exercised.

### IN-04: `isIndexed` parameter on `generateSpriteHeader` is retained but no longer used
