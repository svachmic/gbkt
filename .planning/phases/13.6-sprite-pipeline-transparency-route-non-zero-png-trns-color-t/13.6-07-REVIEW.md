# Phase 13.6 Plan 07: Gap-Closure Code Review Report

**Reviewed:** 2026-06-05
**Depth:** standard (per-file Kotlin analysis)
**Scope:** commits `2571cd28..3807e61b` (13.6-07 deterministic-permute-name + WR-01/02/04/05)
**Status:** issues_found (0 Critical, 3 Warning, 2 Info)

## Summary

The gap-closure replaces the random `File.createTempFile("gbkt_permuted_", ".png", file.parentFile)`
with a deterministic `File(buildTempDir, "gbkt_permuted_<nameWithoutExtension>.png")`, threads a new
`buildTempDir` parameter into `prePermuteIndexedPng`, and lands the four same-path warning fixes
(WR-01 write guard, WR-02 try/catch sentinel, WR-04 single try/finally, WR-05 ASCII messages).

The core determinism mechanism is sound: the temp filename is now a pure function of the source PNG
base name, so the png2asset "Conversion args" comment is reproducible across rebuilds. WR-01 and WR-04
are correctly implemented — there is **no remaining temp-leak window** and **no unsafe double-delete**
(File.delete is idempotent on a missing file). Path-traversal posture is unchanged and safe:
`buildTempDir` is derived from `cSourceDir` (the task `@OutputDirectory`, a trusted build location),
not from any user-controlled string — no new escape vector was introduced.

Three Warnings remain, the most important being that **WR-02's `catch (_: Exception) { 0 }` silently
disables the REQ-5 overflow guard** on a non-IO exception path, and a **narrow but real collision
regression** the random-name scheme previously avoided.

## Warnings

### WR-01: WR-02 catch is over-broad and silently disables the REQ-5 overflow guard

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/PngUtils.kt:131-148`
**Issue:** `countUsedVisibleColors` now wraps its entire body in `catch (_: Exception) { 0 }`. The
KDoc sentinel contract is "0 if the file cannot be read or is not an indexed PNG" — i.e. an
**IOException / not-indexed** sentinel. But the only caller reaches this function *after*
`getTransparentIndexShared(pngFile)` has already returned a non-null index, which means
`ImageIO.read(pngFile)` **already succeeded** and the file **already parsed as an IndexColorModel**
moments earlier (ConvertSpritesTask.kt:322 → 340). At that point an exception inside the
pixel-scan loop is far more likely to be a programmer error (logic bug, unexpected raster shape)
than an unreadable file. Swallowing it to `0` makes `usedVisibleCount > 3` evaluate false, which
**silently bypasses the REQ-5 overflow guard** (ConvertSpritesTask.kt:341) — exactly the safety
check this function feeds. A sprite that should hard-fail on "too many visible colors" would instead
sail through to png2asset. The sibling `getTransparentIndexShared` uses the same broad catch, but
there the failure is fail-*open-to-null* on a file the caller has not yet read; here it is
fail-*open-past-a-guard* on a file the caller already validated.
**Fix:** Narrow the catch to the documented IO/decoding failure, and let unexpected exceptions
propagate so a real defect is not masked as "0 visible colors":
```kotlin
return try {
    // ... scan loop ...
    pixelCounts.indices.count { it != transparentIdx && pixelCounts[it] > 0 }
} catch (e: java.io.IOException) {
    0
}
```
If the intent is genuinely to tolerate any malformed raster, document that the overflow guard is
best-effort and add a comment at the call site noting that a swallowed exception disables the guard.

### WR-02: Deterministic-name scheme reintroduces a same-basename collision the random name avoided

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt:356-360`
and `PngUtils.kt:259` (`gbkt_permuted_${file.nameWithoutExtension}.png`)
**Issue:** The temp name keys on `file.nameWithoutExtension` of the **source PNG**, not on the unique
sprite `id` / `stemName`. The output `.c`/`.h` are keyed on `stemName` (the includePath stem,
ConvertSpritesTask.kt:281-283), which is guaranteed unique per sprite; the temp name is not. Two
sidecar entries that resolve to source PNGs sharing the same basename in different subdirectories
(e.g. `sprites/a/hero.png` and `sprites/b/hero.png`) both map to
`buildTempDir/gbkt_permuted_hero.png`. The old random suffix made every temp path unique and could
never collide. Within a single `convertSprites` run the sprites are processed **serially**
(ConvertSpritesTask.kt:151 for-loop, each temp created → consumed by exec → deleted in `finally`
before the next iteration), so this is not a same-run data race today. The hazard is: (a) if sprite
processing is ever parallelized, two entries with colliding basenames would clobber each other's
permuted PNG mid-exec; (b) the temp name no longer reflects the unique identity the rest of the
pipeline uses. This is a latent correctness regression relative to the random scheme, not a current
data-loss bug.
**Fix:** Key the deterministic name on the unique sprite identity rather than the source basename —
pass `stemName` (or the sprite `id`) through to `prePermuteIndexedPng` and name the temp
`gbkt_permuted_<stemName>.png`. This preserves determinism AND uniqueness, restoring the
collision-freedom the random name provided:
```kotlin
// ConvertSpritesTask: pass stemName so the temp name matches the unique output identity
tempFile = prePermuteIndexedPng(pngFile, transparentIdx, buildTempDir, baseName = stemName)
```
At minimum, add an assertion/comment documenting that `convertSprites` must remain serial because the
temp name is no longer collision-proof.

### WR-03: `sprites/tmp` directory is created under @OutputDirectory and never cleaned up

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt:358-359`
**Issue:** `buildTempDir = File(sourceDir, "sprites/tmp")` places the temp directory **inside**
`cSourceDir`, which is declared `@get:OutputDirectory` on a `@CacheableTask` (ConvertSpritesTask.kt:54,
96). The temp PNG files are deleted in the `finally` (good), but the `sprites/tmp/` directory itself
is `mkdirs()`-created and never removed. An empty (or, on a crash mid-write, non-empty) `tmp/`
subdirectory therefore becomes part of the task's declared output tree. This can perturb Gradle
build-cache fingerprinting / up-to-date checks for `convertSprites`, and a stray permuted PNG left by
an aborted build would be cached and potentially re-packaged as an output artifact alongside the real
`.c`/`.h` files. The previous scheme wrote next to the source asset (outside the output dir), so the
output tree only ever contained `.c`/`.h`.
**Fix:** Place the temp dir outside the declared `@OutputDirectory` — e.g. under
`project.layout.buildDirectory` in a dedicated `tmp/gbkt-permute/` path threaded in as its own task
property, or under the task's `temporaryDir` (Gradle gives every task a clean per-task temp dir
exactly for this). Using `temporaryDir` also keeps determinism (stable path per task) while keeping
the byte output of png2asset reproducible, since only the basename — not the absolute dir — is echoed
into the C comment.

## Info

### IN-01: Temp basename diverges from output identity for path-stem-renamed sprites

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/PngUtils.kt:259`
**Issue:** For metasprites whose source PNG basename differs from their `includePath` stem (e.g. source
`player-character-gbapduck-sprites.png` mapping to `sprites/player.h`), the permuted temp — and thus
the "Conversion args" comment — reads `gbkt_permuted_player-character-gbapduck-sprites.png` while the
generated artifact is `player.c`. This is still fully deterministic (so REQ-6 holds), but the comment
no longer reflects the logical sprite name, which can confuse anyone diffing baselines. Tied to WR-02:
keying the temp name on `stemName` would also resolve this cosmetic mismatch.
**Fix:** Same as WR-02 — derive the temp basename from `stemName`.

### IN-02: WR-05 ASCII rewording drops the literal D-06 `N≠0` glyph the CONTEXT doc references

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt:330-331, 351-354`
**Issue:** The U+2260 (`≠`) removal is correct and the messages remain semantically faithful (sprite
name + detected index + "enable strict mode to fail instead"). Note only that 13.6-CONTEXT.md documents
the canonical D-06 wording as `N≠0`; the ASCII `index N != 0` / `index N (index != 0, strict mode
enabled)` forms are a wording-only swap, so any doc/test that greps for the literal `≠` glyph (or for
the exact prior phrase) must be updated in lockstep. No functional defect — the strict-mode and
auto-route tests assert structural substrings, not the glyph.
**Fix:** None required; optionally add a one-line note in 13.6-CONTEXT.md that the runtime message uses
ASCII `!=`.

## Verified Clean (focus items with no finding)

- **WR-01 write guard** — `temp.delete()` + guarded `ImageIO.write` that deletes-on-throw-and-rethrows
  (PngUtils.kt:257-265). No swallow, no orphan on encode failure.
- **WR-04 single try/finally** — `buildPng2AssetArgs`, arg build, and `exec` are all inside the one
  `try { ... } finally { tempFile?.delete() }`; the only statements between `prePermuteIndexedPng`
  returning and the try block are non-throwing variable initializations (`var lastArgs = emptyList()`).
  No leak window. `lastArgs` correctly preserves `Flags:` for the exit-nonzero message
  (ConvertSpritesTask.kt:407).
- **Double-delete safety** — the inner WR-01 delete and the outer `finally` delete can both fire; both
  rely on idempotent `File.delete()` returning false on a missing file. Correct, no exception.
- **Path traversal** — `buildTempDir` is `File(cSourceDir, "sprites/tmp")`; `cSourceDir` is the trusted
  `@OutputDirectory`, not user input. No new traversal/escape. The pre-existing canonical-path guard on
  `pngFile` (ConvertSpritesTask.kt:194-202) is untouched.
- **Test call-site updates** — PngUtilsTest's three `prePermuteIndexedPng(..., buildTempDir = ...)`
