# Phase 11.2: tileset-pipeline-set-bkg-data-emission - Context

**Gathered:** 2026-05-20
**Status:** Ready for research + planning

<domain>
## Phase Boundary

Phase 11.2 closes the SEED-014 visual gap surfaced by Phase 11.1 plan 08: the generated bank file must emit `set_bkg_data(0, N, _zone_<id>_tileset)` alongside the existing `_bkg_tiles_load_banked(...)` so VRAM tile slots receive real pixel data instead of staying zero-initialized. The pixel bytes are produced by a new `ConvertZoneTilesetsTask` Gradle task that invokes GBDK's `png2asset` (mirroring the existing `ConvertSpritesTask` pattern). After this phase ships, `/gsd-execute-phase 11.1` resumes — anchor 1+2 PNGs re-shoot with real-pixel content, then 11.1 wave 6 + phase close run normally.

</domain>

## Implementation Decisions

### Inherited from earlier phases (re-emphasized for 11.2)

- **D-overfitting-1/2/3 (inherited from 9/10/11/11.1):** Pipeline must work for any zone-having game, not just banks. Sport's hand-coded byte path is NOT the template. The new tileset pipeline is gbkt's own internal coupling, not a mirror of GBDK-reference style.
- **D-03-inherited (from 11.1):** Two-path coexistence. Games WITH `ExplorationSystem` stay on `GBDKSystemVisitor.visitExplorationSystem` (existing path). 11.2 ONLY extends the new SceneVisitor zone-load path added by 11.1-05. Do NOT touch `visitExplorationSystem` or its `zone_load_X` / `zone_transition_X` emissions.
- **D-08-inherited (from 11.1):** Regression set is 4 zone-having games (banks + dungeon + explorer + racer). Phase-close BLOCKING smoke test runs `./gradlew :gbkt-examples:banks:buildRom :gbkt-examples:dungeon:buildRom :gbkt-examples:explorer:buildRom :gbkt-examples:racer:buildRom` and all four must succeed.
- **D-10-inherited (from 11.1):** Cross-phase write boundary preserved. The anchor 1+2 PNG re-shoot (which actually happens during the resumed `/gsd-execute-phase 11.1` after 11.2 ships, NOT during 11.2 itself) writes ONLY to `.planning/phases/11-port-banks-gbdk-example-to-gbkt/evidence/uat-screenshots/`. NO Phase 11 .md edits.

### Area 1 — Gradle task placement & build-graph wiring

- **D-A1:** `ConvertZoneTilesetsTask` lives in `gbkt-gradle-plugin/`, sibling to `ConvertSpritesTask`. No base-class extraction in 11.2 — a future phase can refactor a shared `Png2AssetInvocation` parent if a third consumer appears. Reuses the existing GBDK_HOME discovery + error-enhancement layer.
- **D-A2:** Task runs AFTER `:generateC`, BEFORE `:buildRom`. Sequence: `:generateC` (Kotlin→C, includes SceneVisitor's `set_bkg_data` call) → `:convertZoneTilesets` (reads game_metadata.json + writes per-zone .h/.c into `build/gbkt/generated/`) → `:buildRom` (lcc on the now-complete generated/ tree). Task dependency edges: `:convertZoneTilesets dependsOn :generateC`; `:buildRom dependsOn :convertZoneTilesets`.
- **D-A3:** SceneVisitor emits a symbolic constant `_zone_<sanitized-id>_tileset_count` reference rather than a literal tile count. ConvertZoneTilesetsTask emits `#define _zone_<id>_tileset_count <N>` in the generated header alongside the byte array. SceneVisitor emits `set_bkg_data(0, _zone_<id>_tileset_count, _zone_<id>_tileset);`. Decouples Gradle task ordering from the literal-value flow into the codegen layer.
- **D-A4:** Input discovery via extending `game_metadata.json` (emitted by `GBDKPipelineV2.buildMetadataFile()`). Add a `zoneTilesets: [{id, path, sanitizedSymbol}]` field. ConvertZoneTilesetsTask reads that single artifact — no IR re-traversal, no Gradle-plugin→gbkt-ir dependency edge. Single source of truth.

### Area 2 — `#include` site & translation-unit ownership

- **D-B1:** `#include "_zone_<id>_tileset.h"` lives ONLY in the bank file that consumes it (banks: bank1.c, where `play_enter()` lives). Headers are header-guarded, so a future game with the same tileset in two banks adds two `#include` lines without conflict.
- **D-B2:** The `_zone_<id>_tileset[N]` byte array (.c file) lives in bank 0 / HOME. `const UINT8 X[]` without a bank directive defaults to HOME in GBDK. set_bkg_data is HOME-resident; calling it on HOME-resident data is always safe. HOME bank-0 pressure mitigation: the SPEC's >192-tile cap (Area 3, D-C3) keeps each tileset under 16 KB — small.
- **D-B3:** SceneVisitor emits the `#include` directive adjacent to its set_bkg_data call (locality wins over centralisation). When SceneVisitor emits the zone-load block for a scene with `zoneRefs`, it ALSO emits the `#include` line at the top of the target translation unit. INV-7 asserts both the `#include` and the call in the same TU.
- **D-B4:** Header path is flat: `build/gbkt/generated/_zone_<id>_tileset.h` (sibling to bank1.c, main.c, etc.). `#include "_zone_<id>_tileset.h"` resolves with no `-I` flag changes — lcc's default include path already covers the generated/ directory.

### Area 3 — Build-time failure-mode policy

- **D-C1:** png2asset binary not found → fail-fast loud. ConvertZoneTilesetsTask delegates GBDK_HOME detection to the same helper `ConvertSpritesTask` uses today (e.g., `GbdkToolchain` / equivalent). Error message shape matches the existing sprite-task error so users see symmetric UX across sprites and zone tilesets.
- **D-C2:** Tileset PNG missing or unreadable → fail-fast at `:convertZoneTilesets` with message `Zone <id> tileset PNG not found at <resolved-path>`. Path resolver matches `ConvertSpritesTask`'s convention.
- **D-C3:** PNG exceeds the >192-tile cap (the SPEC out-of-scope frontier) → fail-fast with `tileset > 192 tiles unsupported in phase 11.2; deferred to a future multi-bank-tile-data phase`. Cap value lives as a Kotlin const so a future phase can lift it cleanly. No silent truncation.
- **D-C4:** PNG dimensions not a multiple of 8 → fail-fast at `:convertZoneTilesets` via Kotlin-side validation (read PNG header bytes, check W % 8 == 0 && H % 8 == 0). Error message: `PNG width/height must be a multiple of 8 (Game Boy tile size); got <W>x<H> at <path>`. Do NOT depend on png2asset's stderr — its diagnostics may be opaque.

### Area 4 — Sport-pattern vs new-pattern boundary discipline

- **D-D1:** Inline KDoc at BOTH emission sites + new section in `.planning/codebase/CONVENTIONS.md`. The new SceneVisitor zone-load block gets a KDoc identifying it as `NEW path = Gradle png2asset pipeline (zones, post-11.2)`. SportVisitor.buildBuiltinTrackTilesetVarDecl() gets a KDoc identifying it as `LEGACY path = hand-coded inline bytes (sport genre racing tracks)`. Both KDocs cross-reference each other AND point to a new CONVENTIONS.md section "Tile pixel data emission: two paths, when to use which".
- **D-D2:** Drop a seed file `.planning/seeds/SEED-017-sport-zone-tileset-pipeline-unification.md` describing the deferred unification. The seed captures: (a) the two parallel patterns, (b) why they diverged (sport ships hand-coded racing tracks because it doesn't carry user-supplied PNGs; zones ship user-supplied PNGs via png2asset), (c) potential unification options for a future phase. Lives in `.planning/seeds/` so `/gsd:audit-open` and milestone summaries pick it up — survives across milestones.
- **D-D3:** Two named sentinels — INV-7 + INV-8. **INV-7** locks the NEW path (banks emission) per SPEC requirement 4: presence + ordering of `set_bkg_data(0, _zone_<id>_tileset_count, _zone_<id>_tileset)` followed by `_bkg_tiles_load_banked(...)`, AND the `#include "_zone_<id>_tileset.h"` in the same TU. **INV-8** locks the LEGACY path (sport racing unchanged): asserts `SportVisitor`'s emission still contains the inline `_racing_<id>_tileset` const-array declaration. Two clear failure messages — a future change that accidentally rewires racing through the new pipeline trips INV-8, not INV-7.
- **D-D4:** Sport-genre KDoc placement: on `SportVisitor.buildBuiltinTrackTilesetVarDecl()` (the data-source function, NOT on `buildRaceEnterOps()` which is the orchestrator). The data-source function is the unambiguous LEGACY pattern marker — any maintainer looking at how sport gets its tile data lands here first.

### Claude's Discretion (planner picks)

- **D-claude-1:** Exact png2asset CLI flag combination for tileset mode (vs sprite mode). The planner researches png2asset's flag surface (`-b bank`, `-tw/-th tile dims`, `-bpp 2`, `-bin` vs `-c`, etc.) and picks the minimal flag set that produces the `const UINT8 _zone_<id>_tileset[N] = { ... }` shape we need.
- **D-claude-2:** Exact sanitization rule for `_zone_<id>_tileset` symbol name. Must match the sanitization already used by `_zone_<id>_tiles` (the existing map-indices array) so the two arrays share a sanitized stem. Planner inspects the existing sanitizer in `GBDKPipelineV2.buildZoneData()` and reuses it verbatim.
- **D-claude-3:** Test utility for INV-7/INV-8. The planner picks between `verifyGeneratedCFor(...)` (existing pattern in BanksEmissionTest) or a new shared helper for cross-genre invariants. Whichever produces the cleanest failure message.
- **D-claude-4:** Order of operations when `set_bkg_data` AND `_bkg_tiles_load_banked` both need to run in the same `play_enter()` body. SPEC requirement 3 says `set_bkg_data` precedes `_bkg_tiles_load_banked`. Planner verifies this is also the ordering the `play_enter` test expects (yes — pixel data must reach VRAM before the map indices reference it).

</decisions>

## Existing Code Insights

### Reusable Assets

- `ConvertSpritesTask` GBDK_HOME detection logic — reuse verbatim in `ConvertZoneTilesetsTask`.
- `ConvertSpritesTask` error-enhancement layer (probably wraps `lcc not found` / `png2asset not found` with framework-specific guidance) — same wrapper for zone tilesets per D-C1.
- `GBDKPipelineV2.buildMetadataFile()` — already emits `game_metadata.json`. Extend rather than create a sibling artifact per D-A4.
- Existing sanitized-symbol helper in `GBDKPipelineV2.buildZoneData()` — reuse for the `_zone_<id>_tileset` symbol name per D-claude-2.

### Established Patterns

- **Visitor emits its own includes.** When a codegen visitor needs an external symbol, it emits the `#include` line itself rather than asking a centralised header-aggregator. Per D-B3, this convention applies to the new zone-load block.
- **Asset pipeline tasks live in `gbkt-gradle-plugin/`.** Per D-A1, no new module is created — the existing plugin module hosts the new task.
- **`game_metadata.json` is the canonical Gradle ↔ Kotlin bridge.** Per D-A4, new fields go here rather than spawning sibling JSON artifacts.

### Integration Points

- **`SceneVisitor.visit()` (lines 85–187):** Where the new `set_bkg_data` call + `#include` directive land per D-B3 and SPEC requirement 3.
- **`GBDKPipelineV2.buildMetadataFile()`:** Where the new `zoneTilesets` array gets serialised into `game_metadata.json` per D-A4.
- **`build.gradle.kts` of the gbkt Gradle plugin:** Where the new `:convertZoneTilesets` task is registered + wired into the build graph per D-A2.
- **`gbkt-examples/banks/build.gradle.kts`:** Existing example consumer — its `:buildRom` task already depends on `:generateC`; adding the `:convertZoneTilesets` step in between is the test case for the new wiring.

<specifics>
## Specific Ideas

- **png2asset symmetry doctrine:** "Whatever ConvertSpritesTask does for sprites, ConvertZoneTilesetsTask does for zone tilesets" — guides any planner choice that doesn't have an explicit decision above. Symmetric UX is the default.
- **Test naming:** INV-7 / INV-8 follow the existing INV-1..INV-6 convention in BanksEmissionTest. INV-8 may live in a separate test module if the SportVisitor genre has its own emission tests — planner decides the exact home per D-claude-3.
- **Sanitized symbol stem:** Both `_zone_<id>_tiles` (existing map-indices array) and `_zone_<id>_tileset` (new pixel-bytes array) MUST share the same `<id>` sanitization. The two arrays are referenced from the same generated code; mismatched sanitization would break the link.

</specifics>

## Deferred Ideas

- **Unify sport's hand-coded byte pattern with the new zone pipeline.** Captured in SEED-017 per D-D2. Out of scope for 11.2; a future phase with bandwidth tackles it.
- **Runtime tileset switching mid-scene.** Out of scope per SPEC. If/when a future game needs to swap tilesets without a scene change, a new phase generalises the emission to support multiple `set_bkg_data` calls within `scene_frame`.
- **Multi-bank tile data for tilesets > 192 tiles.** Out of scope per SPEC + D-C3. Future phase introduces a `_bkg_data_load_banked` helper (mirror of `_bkg_tiles_load_banked`) and the codegen logic to invoke it.
- **GBC-mode per-tile palette attributes.** Out of scope per SPEC; Phase 13 covers explicit-slot palette DSL.
- **Shared `Png2AssetInvocation` base class between sprite and zone tasks.** Refactor opportunity — explicitly deferred per D-A1 ("no base-class extraction in 11.2; a future phase can refactor a shared parent if a third consumer appears").
