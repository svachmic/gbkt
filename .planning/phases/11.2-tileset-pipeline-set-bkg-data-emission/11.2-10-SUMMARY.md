# Phase 11.2 Plan 10: Two-Path Doctrine in CONVENTIONS.md Summary

D-D1 prose-doc landing site + D-D2 SEED-017 on-disk verification — pure documentation
append that locks the boundary discipline between the NEW Gradle png2asset zone-tileset
pipeline and the LEGACY SportVisitor hand-coded racing-track byte path.

## What Shipped

A new ~70-line top-level section `## Tile Pixel Data Emission: Two Paths, When to Use
Which` appended to the end of `.planning/codebase/CONVENTIONS.md` (after the previously
final `## Detekt Rule Justifications` section). The section contains four sub-sections:

1. **`### NEW path — Gradle png2asset pipeline (zones, post-Phase-11.2)`** — when to use
   it (DSL declares `zone(id) { tileset(asset(...)) }`), the 5-step flow from PNG drop
   to `set_bkg_data` emission, code-finder pointers (`ConvertZoneTilesetsTask.kt`,
   `SceneVisitor.kt`, `GBDKPipelineV2.buildMetadataFile`,
   `GBDKPipelineV2.buildSceneFile`), and cross-reference to `BanksEmissionTest.INV-7`.
2. **`### LEGACY path — Hand-coded inline bytes (sport-genre racing tracks)`** — when
   to use it (procedural sport-genre tracks, not user PNGs), the 2-step author flow,
   code-finder pointers (`SportVisitor.buildBuiltinTrackTilesetVarDecl`,
   `buildRaceEnterOps`), and cross-reference to
   `SportLegacyTilesetPathInvariantTest.INV-8`.
3. **`### Decision tree`** — ASCII flowchart disambiguating which path applies for a
   given game DSL declaration (zone-with-tileset → NEW; racing-only → LEGACY; neither →
   no tile pixel data emitted).
4. **`### Future unification`** — explicit cross-reference to
   `.planning/seeds/SEED-017-sport-zone-tileset-pipeline-unification.md` documenting
   that Phase 11.2 chose NOT to retrofit sport onto the new pipeline.

## How Plan 10 Composes with Plan 09

Plan 09 landed the **in-code KDoc half** of D-D1 — `KDoc tag: NEW path` annotations on
`SceneVisitor.kt`'s zone-load block and `KDoc tag: LEGACY path` annotations on
`SportVisitor.buildBuiltinTrackTilesetVarDecl`. Plan 10 lands the **prose-doc half** of
D-D1 — the CONVENTIONS.md section that explains the doctrine in one canonical place
that the KDocs point back to (via the code-finder pointers in this section).

Together, the in-code KDocs + the CONVENTIONS.md section + the SEED-017 deferred-work
record form the boundary discipline that prevents the NEW and LEGACY paths from
accidentally drifting into each other in future phases.
