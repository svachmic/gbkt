## Decisions Made

1. **D-D4 placement: data-source over orchestrator.** The plan author's preference (per D-D4 in 11.2-CONTEXT.md) is that boundary-discipline markers attach to the function that owns the byte-source, not the function that orchestrates the lifecycle. Implementation followed this — the LEGACY-path KDoc went on `buildBuiltinTrackTilesetVarDecl` (returns the `CVarDecl` carrying the 48 bytes), not on `buildRaceEnterOps` (just emits the `set_bkg_data` call). This optimizes for the maintainer query "show me where sport's tile bytes come from".

2. **Single merged KDoc on buildBuiltinTrackTilesetVarDecl (not adjacent twin blocks).** The plan's `<interfaces>` template implicitly suggested adding the D-D1/D-D4 KDoc above the function signature. The function already had a multi-paragraph Plan 07.4-17 docblock occupying that slot. Two adjacent `/** ... */` blocks would orphan the first one from the function signature (Kotlin/Dokka binds only the LAST KDoc above a declaration to it). The chosen solution merges the two: the D-D1/D-D4 marker leads (since it's the first thing a "LEGACY path" search lands on), followed by a clearly-labeled `--- Original docblock (preserved verbatim from Plan 07.4-17): ---` divider, then the original content unchanged. KDoc binds correctly; both audiences (boundary-discipline navigators and tile-semantics readers) get their content.
