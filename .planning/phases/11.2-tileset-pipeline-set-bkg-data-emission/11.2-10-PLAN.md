```markdown
## Tile Pixel Data Emission: Two Paths, When to Use Which

The gbkt codegen layer ships TWO coexisting patterns for emitting tile pixel data
into generated C. Both produce `set_bkg_data(0, N, _<id>_tileset)`-shape calls;
they differ in WHERE the byte array comes from.

### NEW path — Gradle png2asset pipeline (zones, post-Phase-11.2)

**When:** A game declares `zone(id) { tileset(asset("path/to/foo.png")) ... }` and
binds the zone to a scene via `zone(zoneRef)`.

**How:**
1. Game author drops `foo.png` under `res/` (any subdirectory).
2. `GBDKPipelineV2.buildMetadataFile()` emits `zoneTilesets` manifest in
   `game_metadata.json`.
3. `ConvertZoneTilesetsTask` (in `gbkt-gradle-plugin/`) reads the manifest,
   invokes GBDK's `png2asset` for each zone tileset PNG, emits
   `_zone_<sanitized>_tileset.{c,h}` into `build/gbkt/generated/`.
4. `SceneVisitor` zone-load block emits
   `set_bkg_data(0, _zone_<id>_tileset_count, _zone_<id>_tileset);`
   before `_bkg_tiles_load_banked(...)` in the bound scene's `*_enter` function.
5. `GBDKPipelineV2.buildSceneFile()` adds the
   `#include "_zone_<sanitized>_tileset.h"` directive to the consuming bank file.

**Find it in code:**
- `gbkt-gradle-plugin/.../ConvertZoneTilesetsTask.kt`
- `gbkt-backend-gbdk/.../SceneVisitor.kt` — zone-load block (KDoc tag: NEW path)
- `gbkt-backend-gbdk/.../GBDKPipelineV2.kt:buildMetadataFile` — `zoneTilesets` manifest
- `gbkt-backend-gbdk/.../GBDKPipelineV2.kt:buildSceneFile` — `#include` thread

**Invariant:** `BanksEmissionTest.INV-7` locks the emission shape + ordering +
the consuming bank file's `#include`.

### LEGACY path — Hand-coded inline bytes (sport-genre racing tracks)

**When:** Procedurally-generated track tilesets that ship with the sport genre —
not user-supplied PNGs.

**How:**
1. `SportVisitor.buildBuiltinTrackTilesetVarDecl()` authors a 48-byte
   `const UINT8 _racing_<id>_tileset[48]` declaration with hand-coded 2bpp
   bytes derived from `tilePatternToBytes()` palette-index matrices.
2. `SportVisitor.buildRaceEnterOps()` emits
   `set_bkg_data(0, 3, _racing_<id>_tileset);` inline in the race-scene enter ops.

**Find it in code:**
- `gbkt-genre-sport/.../SportVisitor.kt:buildBuiltinTrackTilesetVarDecl` (KDoc tag: LEGACY path)
- `gbkt-genre-sport/.../SportVisitor.kt:buildRaceEnterOps`

**Invariant:** `SportLegacyTilesetPathInvariantTest.INV-8` locks the emission
shape unchanged AND asserts sport-racing is NOT retrofitted onto the NEW path
(no `#include "_zone_<...>_tileset.h"` in racing main.c).

### Decision tree

```
Does the game DSL declare zone(...) with tileset(asset(...))?
├── YES → NEW path (it happens automatically; nothing extra to author).
└── NO  → is this a racing genre track from racing { }?
         ├── YES → LEGACY path (SportVisitor authors the bytes; nothing extra to author).
         └── NO  → neither path applies; tile pixel data is not emitted for
                   this game (e.g. games with only sprites and a default BG).
```

### Future unification

See `.planning/seeds/SEED-017-sport-zone-tileset-pipeline-unification.md` for the
deferred unification work. Phase 11.2 explicitly chose NOT to retrofit sport onto
the new pipeline; a dedicated future phase will pick from the options enumerated
in SEED-017.
```
