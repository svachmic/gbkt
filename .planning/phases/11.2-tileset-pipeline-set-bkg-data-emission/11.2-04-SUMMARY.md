# Phase 11.2 Plan 04: GbktPlugin Wiring for ConvertZoneTilesetsTask Summary

One-liner: Wired `ConvertZoneTilesetsTask` (plan 11.2-03) into GbktPlugin's build graph with the two D-A2 dependency edges (`dependsOn(generateC)` + `compileRom.dependsOn(convertZoneTilesets)`) plus a `mustRunAfter(convertSprites)` sibling-ordering edge (Gradle 9 input/output overlap), and surfaced + Rule-1-fixed a Plan 03 codegen bug (png2asset native stem mis-derivation) that the buildRom smoke check exposed once Plan 05's consumer code became reachable.

## What Shipped

A 17-line additive block in `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/GbktPlugin.kt`:

1. **Import** (1 line, alphabetically placed after `ConvertSpritesTask`):
   ```kotlin
   import io.github.gbkt.gradle.tasks.ConvertZoneTilesetsTask
   ```
2. **Task registration** (14-line block, immediately after the existing `convertSprites` registration):
   ```kotlin
   // Phase 11.2 (D-A2): convertZoneTilesets — png2asset for zone tileset PNGs (sibling to convertSprites)
   val convertZoneTilesets =
       project.tasks.register<ConvertZoneTilesetsTask>("convertZoneTilesets") {
           dependsOn(generateC)
           // convertSprites and convertZoneTilesets share cSourceDir = build/gbkt/generated as
           // an @OutputDirectory. Gradle 9 fails fast when one task's input directory overlaps
           // another's output without an explicit ordering edge. mustRunAfter (not dependsOn)
           // is correct here — the two tasks are independent in purpose; they only share the
           // output dir for lcc include resolution.
           mustRunAfter(convertSprites)
           gbdkHome.set(
               extension.gbdkHome.orElse(
                   project.provider { GbdkToolchain.find(null).absolutePath }
               )
           )
           assetDirectory.set(extension.assetDirectory)
           metadataFile.set(
               generateC.flatMap { it.outputDir }.map { it.file("game_metadata.json") }
           )
           cSourceDir.set(generateC.flatMap { it.outputDir })
       }
   ```
3. **compileRom dependsOn edge** (1 line, between `dependsOn(convertSprites)` and `dependsOn(copyResources)`):
   ```kotlin
   dependsOn(convertZoneTilesets)
   ```

Three new RED-then-GREEN tests in `GbktPluginTest.kt` lock the wiring:

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] mustRunAfter(convertSprites) added to resolve Gradle 9 input/output overlap**

- **Found during:** Task 1 GREEN-state verification (`./gradlew :gbkt-gradle-plugin:test` after the initial 24-line GbktPlugin.kt addition).
- **Issue:** The IntegrationTest `simple-physics fixture builds ROM end-to-end without staleness errors` failed with:
  ```
  org.gradle.internal.execution.WorkValidationException: Some problems were found
  with the configuration of task ':convertZoneTilesets' (type 'ConvertZoneTilesetsTask').
    - Reason: Task ':convertZoneTilesets' uses this output of task ':convertSprites'
      without declaring an explicit or implicit dependency.
    - Reason: Task ':convertSprites' uses this output of task ':convertZoneTilesets'
      without declaring an explicit or implicit dependency.
  ```
  Both tasks declare `cSourceDir = build/gbkt/generated` as their `@OutputDirectory`, and convertZoneTilesets's `metadataFile` (an `@InputFile`) lives inside that same directory. Gradle 9 fails fast on the bidirectional overlap.
- **Fix:** Added `mustRunAfter(convertSprites)` to the new `convertZoneTilesets` registration. `mustRunAfter` (not `dependsOn`) is semantically correct — the two tasks are independent in purpose; they share `cSourceDir` only because lcc expects all generated artifacts in one directory. The plan author could not have anticipated this Gradle 9 validation behavior because plan 03 added the task class but not the registration; the overlap is only realized when both tasks are wired.
- **Files modified:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/GbktPlugin.kt` (1-line addition + 5-line comment).
- **Commit:** `8a204ea1` (subsumed into the GREEN commit because the issue was caught during the GREEN-state verification before the GREEN commit was written; the GREEN commit message documents the addition explicitly).

**2. [Rule 1 - Bug] png2asset native stem mis-derivation in plan 11.2-03 ConvertZoneTilesetsTask.synthesizeHeader**

- **Found during:** Plan 11.2-04 buildRom acceptance criterion #6 check (`./gradlew :gbkt-examples:banks:clean :gbkt-examples:banks:buildRom`).
- **Issue:** lcc link step failed:
  ```
  ?ASlink-Warning-Undefined Global '_checker_tiles' referenced by module 'bank1'
  ```
  Trace:
  1. Plan 11.2-03's `synthesizeHeader` used `nativeStem = pngFile.nameWithoutExtension` → `checker` (from `checker.png`) → emitted `#define _zone_play_zone_tileset checker_tiles`.
  2. png2asset, invoked with `-o /tmp/_zone_play_zone_tileset.c`, actually derives symbol names from the OUTPUT-FILE basename → emits `_zone_play_zone_tileset_tiles[]`.
  3. Plan 11.2-05's SceneVisitor (already merged in spawn base) emits `set_bkg_data(0, _zone_play_zone_tileset_count, _zone_play_zone_tileset);` in bank1.c. The macro expands to `... checker_tiles` per the (wrong) header.
  4. The `checker_tiles` symbol does not exist anywhere in the compiled object set → linker error.
  The bug was masked until Plan 04 wired the consumer chain end-to-end; Plan 11.2-03's own test (`ConvertZoneTilesetsTaskTest.kt` line 116) had hard-coded the WRONG assertion (`#define _zone_play_zone_tileset checker_tiles`), locking the bug rather than catching it.
- **Fix:** One-line correction in `ConvertZoneTilesetsTask.kt`: `nativeStem = pngFile.nameWithoutExtension` → `nativeStem = outputC.nameWithoutExtension`. With the existing `outputC = File(outputDir, "_zone_${sanitized}_tileset.c")`, the alias now correctly resolves to `_zone_play_zone_tileset_tiles` for the banks fixture (and to `_zone_<sanitized>_tileset_tiles` in general). Also corrected the corresponding Plan 03 test assertion in `ConvertZoneTilesetsTaskTest.kt` line 116 to match the actual png2asset behavior.
- **Rule-4 escalation considered:** No — the fix is a one-token logic correction (`pngFile` → `outputC`) in a single function, not an architectural change. Per Rule 1 ("Wrong queries, logic errors, type errors") and the project-feedback rule "Quality over shortcuts — every fix must be provably correct", the fix is in-scope. Per "Route to proper new phase when blast radius is wide", the blast radius here is one symbol-name derivation in one synthesis function — narrow, not wide.
- **Scope justification:** Plan 04's acceptance criterion #6 explicitly requires `./gradlew :gbkt-examples:banks:clean :gbkt-examples:banks:buildRom` to BUILD SUCCESSFUL. The plan was authored under the assumption "pre-plan-05 buildRom should still succeed because nothing references the new symbols yet" — but plan 05 already landed in the spawn base (commit `0922ba82 feat(11.2-05): prepend set_bkg_data CCall in SceneVisitor zone-load block`). Once plan 05's consumer was reachable, the plan 03 alias bug became a Plan 04 blocker. Either fix it here or fail acceptance criterion #6.
- **Files modified:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertZoneTilesetsTask.kt` (lines 246-253: comment + 1-token), `gbkt-gradle-plugin/src/test/kotlin/io/github/gbkt/gradle/tasks/ConvertZoneTilesetsTaskTest.kt` (line 115-118: corrected assertion + note pointing to plan 04).
- **Commit:** `71038a49`.

## Deferred Issues

**Sport-genre racing zones with `tilesetPath = null`:** Plan 01's manifest emission filtered these out via `?: continue`, so convertZoneTilesets receives an empty zoneTilesets array for those games and returns gracefully via the early-return path in `TaskAction.convertZoneTilesets()`. This is intentional per CONVENTIONS.md §"Tile pixel data emission: two paths, when to use which" and SEED-017 (deferred unification). Not a defect for Plan 04 — explicitly out of scope for the NEW path.

**png2asset's dedup-vs-visual count semantics:** Plan 03's KDoc + Plan 04's smoke both confirm the synthesized header carries the VISUAL tile count (e.g. 4 for banks's 16×16 checker.png) per plan 03 behavior viii. The actual `_zone_play_zone_tileset_tiles[]` array may be SHORTER than `count * 16` bytes because png2asset dedupes identical tiles in `-map` mode. For banks's solid checker pattern, the actual array is 64 bytes (4 unique tiles × 16) so count and array length match. For tilesets with duplicate tiles, `set_bkg_data(0, count, array)` may read beyond the array bounds. The spike-log §"Critical: tile dedup" flagged this for SceneVisitor's plan 05/06 — Plan 04 does not address it; tracked as forward-looking semantics work for plan 11.2-05/06 (which are already merged in spawn base; a follow-up SEED entry may be needed if a downstream consumer surfaces a runtime bug).
