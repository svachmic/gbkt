```kotlin
private fun generateTilesetHeader(sanitized: String, tileCount: Int, outputH: File) {
    val guard = "_ZONE_${sanitized.uppercase()}_TILESET_H"
    val byteCount = tileCount * 16  // 2bpp: 16 bytes per 8x8 tile
    outputH.writeText(buildString {
        appendLine("/* Auto-generated by gbkt ConvertZoneTilesetsTask — DO NOT EDIT */")
        appendLine("#ifndef $guard")
        appendLine("#define $guard")
        appendLine()
        appendLine("#include <stdint.h>")
        appendLine("#include <gbdk/platform.h>")
        appendLine()
        appendLine("extern const uint8_t _zone_${sanitized}_tileset[$byteCount];")
        appendLine("#define _zone_${sanitized}_tileset_count ${tileCount}")
        appendLine()
        appendLine("#endif /* $guard */")
    })
}
```

### §A3. png2asset flag selection (D-claude-1) — CONFIDENCE: MEDIUM-HIGH

**Verified facts (from official GBDK docs `[CITED: gbdk.org/docs/api/docs_toolchain.html]` and source repo `[CITED: github.com/LaroldsJubilantJunkyard/png2asset]`):**
- `-map` → background/window map mode (NOT sprite mode). Default WITHOUT `-map` = metasprite mode.
- `-c <file>` → output C file path. (Output extension also configurable via `-o` in the sprite path; codebase uses `-o` for sprites — see `ConvertSpritesTask.kt:199`. The flag set is interchangeable; **use `-o` for symmetry** with the existing sprite invocation.)
- `-spr8x8` / `-spr8x16` → sprite tile dimensions (8×8 vs 8×16). For background tiles we still want 8×8 (DMG hardware native).
- `-bpp 2` → 2 bits per pixel (DMG/GBC standard; explicit setting avoids any future png2asset default drift).
- `-keep_palette_order` → preserve indexed PNG palette order for deterministic byte output.
- `-noflip` → disable mirror-deduplication. **Recommended ON** for tilemaps so each PNG tile gets a unique tile-id slot — otherwise tile indices in the future tilemap-export pipeline would be off-by-one.
- png2asset emits ONLY a `.c` file; we hand-synthesize the `.h` (mirrors the sprite path — see `ConvertSpritesTask.generateSpriteHeader()`).

**Recommended flag set:**
```
<png> -o <outputC> -map -spr8x8 -bpp 2 -keep_palette_order -noflip
```

**Symbol name shape produced by png2asset:** From the existing breakout sprite output `[VERIFIED: breakout/build/gbkt/generated/sprites/paddle.c]`, png2asset emits `const uint8_t <stem>_tiles[N] = { ... };` where `<stem>` is the input file basename (no extension). To get `_zone_<sanitized>_tileset` we have two options:

**Option A (recommended): rename in-task post-processing.** Run png2asset to produce `<stem>_tiles[N]`, then post-process the C file to rename `<stem>_tiles` → `_zone_<sanitized>_tileset` (regex substitution). This is the pattern `ConvertSpritesTask.fixZeroSizeArrays` (line 358) already uses — post-processing png2asset output.

**Option B:** Symlink/rename input PNG to a canonical name like `_zone_play_zone.png` before invoking png2asset, then `<stem>` matches. Brittle — leaves a temp file around. Reject.

**Option C:** Use png2asset's `-source_tileset` flag — but this is for sharing a tileset across multiple maps, not naming. Not applicable here.

**Planner directive:** Use Option A. Post-process `<stem>_tiles[` → `_zone_<sanitized>_tileset[` via `outputC.readText().replace(...)`. Single-line edit.

**`[CITED: ConvertSpritesTask.kt:358-372 fixZeroSizeArrays]`** — Existing precedent for post-processing png2asset C output.

**`[ASSUMED]`** that png2asset's `-bpp 2` is the default for `-spr8x8` mode but we're being explicit. If png2asset rejects `-bpp 2` in `-map` mode, drop the flag. Plan 2 should keep this as a Wave-0 spike: run `png2asset checker.png -map -spr8x8 -bpp 2` manually against `gbkt-examples/banks/res/tiles/checker.png` (16×16 = 4 tiles) and confirm a `checker.c` with `checker_tiles[64]` is produced.

#### §A6.1. Ordering rationale (D-claude-4)

GBDK helper internals `[VERIFIED: gbkt-genre-sport/.../SportVisitor.kt:460-465 comment]`:
> GBDK's `_set_bkg_data` / `_set_bkg_tiles` call `display_off()` internally, leaving LCDC.7=0 after the VRAM writes.

`set_bkg_data` writes pixel bytes to VRAM tile-data area (0x8000-0x97FF). `_bkg_tiles_load_banked` writes tile-index bytes to VRAM tile-map area (0x9800-0x9BFF or 0x9C00-0x9FFF). The map indices reference the tile-data slots by index. If the indices arrive BEFORE the pixels, the visible frame between the two writes shows garbled data (no symptom for our static `set_bkg_data` ⊕ `set_bkg_tiles` sequence at scene enter — but the correct dataflow ordering is data-first-then-references-data).

Per `SportVisitor.kt:460-463`, the LEGACY sport path uses the same ordering:
```
set_bkg_data(0, 3, _racing_<id>_tileset);     // pixels first
set_bkg_tiles(0, 0, w, h, _zone_<id>_tiles);  // then indices
DISPLAY_ON;                                    // then LCD re-enable
```

Phase 11.2 mirrors the same ordering pattern. The existing `SHOW_BKG;` after `_bkg_tiles_load_banked` already re-enables BG (added in 11.1-05).

#### §A6.3. Bank residency of `_zone_<id>_tileset[N]` (D-B2)

png2asset emits a top-level `const uint8_t <stem>_tiles[N] = { ... };` declaration with no bank annotation. In GBDK, top-level `const` arrays default to HOME bank (bank 0) when no `BANKREF` / `__at()` directive specifies otherwise. `[VERIFIED: breakout/build/gbkt/generated/sprites/paddle.c line 14]` — sprites also live in HOME this way.

Per D-B2, this is correct. `set_bkg_data` is a HOME-resident GBDK function; calling it on HOME-resident data is always safe (no `SWITCH_ROM` wrapper required). HOME-bank pressure mitigation: the >192-tile cap (D-C3) keeps each tileset under 16 KB (192 × 16 = 3072 bytes ≪ ~14 KB HOME free for typical games).

### §A9. PNG header parser for D-C4

The PNG file format `[CITED: w3.org/TR/PNG/]`:
1. Byte signature: `89 50 4E 47 0D 0A 1A 0A` (8 bytes)
2. Chunks follow. First chunk MUST be IHDR with:
   - 4 bytes chunk length (big-endian) = `13`
   - 4 bytes chunk type = `49 48 44 52` ("IHDR")
   - 13 bytes chunk data:
     - **width: 4 bytes big-endian uint32** (offset 16 from file start)
     - **height: 4 bytes big-endian uint32** (offset 20)
     - bit depth, color type, etc.
   - 4 bytes CRC

**Pure-Kotlin parser (no external dep):**
```kotlin
private data class PngDims(val width: Int, val height: Int)

private fun readPngDims(file: File): PngDims {
    val bytes = file.readBytes()
    require(bytes.size >= 24) { "PNG too small: ${file.absolutePath}" }
    val sig = byteArrayOf(0x89.toByte(), 'P'.code.toByte(), 'N'.code.toByte(), 'G'.code.toByte(),
                          0x0D, 0x0A, 0x1A, 0x0A)
    require(bytes.copyOfRange(0, 8).contentEquals(sig)) {
        "Not a valid PNG: ${file.absolutePath}"
    }
    val w = ((bytes[16].toInt() and 0xFF) shl 24) or
            ((bytes[17].toInt() and 0xFF) shl 16) or
            ((bytes[18].toInt() and 0xFF) shl 8)  or
             (bytes[19].toInt() and 0xFF)
    val h = ((bytes[20].toInt() and 0xFF) shl 24) or
            ((bytes[21].toInt() and 0xFF) shl 16) or
            ((bytes[22].toInt() and 0xFF) shl 8)  or
             (bytes[23].toInt() and 0xFF)
    return PngDims(w, h)
}
```

**Alternative — reuse `javax.imageio.ImageIO`:** `ConvertSpritesTask` already uses ImageIO at line 476-490 to read sprite PNG height. The same call works for width. Either approach is fine; the byte-level parser has zero ImageIO dependencies and faster cold-start. The planner picks based on consistency preference. **Recommendation:** mirror the ImageIO approach for symmetry with `ConvertSpritesTask`.

**Validation:**
```kotlin

require(w % 8 == 0 && h % 8 == 0) {
    "PNG width/height must be a multiple of 8 (Game Boy tile size); got ${w}x${h} " +
        "at ${pngFile.absolutePath}"
}
val tileCount = (w / 8) * (h / 8)

    "tileset > $MAX_ZONE_TILESET_TILES tiles unsupported in phase 11.2; deferred to a " +
        "future multi-bank-tile-data phase. Got $tileCount tiles at ${pngFile.absolutePath}"
}
```

## Common Pitfalls

### Pitfall 1: Forgetting the symbolic count `_zone_<id>_tileset_count` (D-A3)
**What goes wrong:** Emit `set_bkg_data(0, 4, _zone_play_zone_tileset)` with a literal `4` instead of `_zone_play_zone_tileset_count`.
**Why it happens:** Easier to write; literal feels obvious.
**How to avoid:** D-A3 mandates symbolic. The header `#define _zone_<id>_tileset_count <N>` is what couples the literal-value flow back to the Gradle task. If SceneVisitor uses a literal, the Gradle task and codegen become tightly coupled — change one tileset size, must regenerate codegen.
**Warning signs:** INV-7 asserts `_zone_play_zone_tileset_count` literally in the body. Fails immediately if a literal is used.

### Pitfall 2: Wrong ordering (data before indices)
**What goes wrong:** `_bkg_tiles_load_banked(...)` emitted before `set_bkg_data(...)`. Indices reference zero-initialized VRAM tile slots; first frame after scene_enter shows garbled BG.
**Why it happens:** SceneVisitor.kt:122-151 currently builds the list with `_bkg_tiles_load_banked` first; naïve append puts `set_bkg_data` AFTER instead of BEFORE.
**How to avoid:** Edit at line 134 must PREPEND, not append. INV-7 ordering assertion catches this.
**Warning signs:** INV-7 fails with `setBkgDataIdx > loadBankedIdx`.

### Pitfall 3: png2asset symbol name doesn't match expected
**What goes wrong:** png2asset emits `checker_tiles[64]` but SceneVisitor calls `_zone_play_zone_tileset`. lcc: `undefined identifier '_zone_play_zone_tileset'`.
**Why it happens:** png2asset names the array after the PNG filename stem (`checker_tiles`), not after the zone id.
**How to avoid:** Either (a) post-process C output with regex substitution `<stem>_tiles\b` → `_zone_<sanitized>_tileset` per §A3 Option A, OR (b) emit `#define _zone_<sanitized>_tileset <stem>_tiles` in the synthesized header (alias the pipeline name to the native name — exactly what `ConvertSpritesTask.generateSpriteHeader()` does at line 282-285 for `#define sprites_paddle_tiles paddle_tiles`).
**Recommendation:** Option (b) — `#define` alias. It's exactly the sprite-pipeline pattern (no smoke and mirrors). The header looks like:
```c
extern const uint8_t checker_tiles[64];  /* from png2asset, name preserved */
#define _zone_play_zone_tileset checker_tiles
#define _zone_play_zone_tileset_count 4
```
Cleaner than Option (a) — no source-file mutation.
**Warning signs:** `:compileRom` fails with `undefined identifier '_zone_play_zone_tileset'`.

### Pitfall 4: Forgetting to dependsOn the new task
**What goes wrong:** `:compileRom` runs `lcc` before `:convertZoneTilesets` has produced the header — `#include "_zone_play_zone_tileset.h"` fails with "no such file or directory".
**Why it happens:** `GbktPlugin.kt:382-384` currently has `dependsOn(convertSprites)` only. The new task needs an explicit `dependsOn(convertZoneTilesets)` line.
**How to avoid:** Plan 2's acceptance criterion includes the `dependsOn` edge. The cross-genre regression sweep at phase close (D-08) catches this — any of the 4 games' `buildRom` failing means the dependency edge is missing or the task is broken.
**Warning signs:** `:gbkt-examples:banks:buildRom` fails at `lcc` stage with missing header.

### Pitfall 5: SportVisitor accidentally retrofitted
**What goes wrong:** A well-meaning future change applies `set_bkg_data(0, _<id>_tileset_count, _<id>_tileset)` symbolic-count pattern to SportVisitor too — but SportVisitor's `_racing_<id>_tileset[48]` is hand-coded inline, NOT emitted as a separate header. `_racing_<id>_tileset_count` is never `#define`d → linker error.
**Why it happens:** Pattern-matching from the NEW path back onto the LEGACY path.
**How to avoid:** D-D1 KDocs at both emission sites. INV-8 fails loud if SportVisitor stops emitting the inline `_racing_<id>_tileset[48]` declaration.
**Warning signs:** INV-8 RED.

### Pitfall 6: Zone with no `tilesetPath` still gets `set_bkg_data`
**What goes wrong:** A test fixture or future game declares `zone("test") { size(10, 10) }` with no `tileset(...)` — `tilesetPath` is null. SceneVisitor blindly emits `set_bkg_data(0, _zone_test_tileset_count, _zone_test_tileset)` referencing symbols that the Gradle task never produced.
**How to avoid:** §A6 filter — emit the `set_bkg_data` triple only when `zone.tilesetPath != null`. The `#include` filter in `buildSceneFile` (§A6.2) uses the same predicate.
**Warning signs:** lcc undefined-identifier error in a test fixture that doesn't use the pipeline.

### Pitfall 7: Cross-phase .md edits during 11.2
**What goes wrong:** A plan author edits `.planning/phases/11-port-banks-gbdk-example-to-gbkt/11-UAT.md` or similar to record 11.2's findings.
**How to avoid:** D-10-inherited boundary. Phase 11.2's writes go ONLY to `.planning/phases/11.2-tileset-pipeline-set-bkg-data-emission/`. The anchor 1+2 PNG re-shoot happens during the RESUMED `/gsd-execute-phase 11.1`, not during 11.2.

### Example 2: Header synthesis (§A2)

```kotlin
// Inside ConvertZoneTilesetsTask
private fun synthesizeHeader(
    sanitized: String,
    nativeStem: String,    // png2asset's chosen array stem (PNG filename basename)
    tileCount: Int,
    outputH: File,
) {
    val guard = "_ZONE_${sanitized.uppercase()}_TILESET_H"
    val byteCount = tileCount * 16  // 2bpp: 16 bytes per 8x8 tile
    outputH.writeText(buildString {
        appendLine("/* Auto-generated by gbkt ConvertZoneTilesetsTask — DO NOT EDIT */")
        appendLine("#ifndef $guard")
        appendLine("#define $guard")
        appendLine()
        appendLine("#include <stdint.h>")
        appendLine("#include <gbdk/platform.h>")
        appendLine()
        appendLine("/* Native tile data array from png2asset output */")
        appendLine("extern const uint8_t ${nativeStem}_tiles[$byteCount];")
        appendLine()
        appendLine("/* gbkt zone-pipeline aliases (Phase 11.2) */")
        appendLine("#define _zone_${sanitized}_tileset ${nativeStem}_tiles")
        appendLine("#define _zone_${sanitized}_tileset_count $tileCount")
        appendLine()
        appendLine("#endif /* $guard */")
    })
}
```

`[CITED: ConvertSpritesTask.kt:264-290]` for the structural pattern. The `#define` alias avoids post-processing png2asset's C output.

## Open Questions

1. **Should Plan 2's task post-process the png2asset C output, or rely solely on header aliases (Pitfall 3)?**
   - What we know: Sprite pipeline uses BOTH — `fixZeroSizeArrays` post-processes the .c, AND `generateSpriteHeader` emits a `#define sprites_paddle_tiles paddle_tiles` alias.
   - What's unclear: For zones we can do "alias only" (no .c mutation) because png2asset's array shape is fine — we just need a different external name. Or we can also rename in the .c for cleaner generated output.
   - Recommendation: **Alias only.** Simpler, less to test, mirrors the cleanest part of the sprite pattern. The planner ships this in Plan 2 and revisits only if INV-7 surfaces an issue.

2. **Does png2asset preserve a deterministic output ordering across runs / platforms (for ROM-size invariance)?**
   - What we know: `ConvertSpritesTask` doesn't add `--seed` flags; output appears deterministic for the cases banks/breakout exercise today.
   - What's unclear: If a future PNG triggers a tile-dedup heuristic that's order-sensitive, ROM bytes could shift.
   - Recommendation: Out of scope for 11.2 (no known evidence of non-determinism). Plan 7's smoke sweep + the existing ROM size cap catch this if it ever manifests.

3. **`-noflip` for zones — yes or no?**
   - What we know: Sprites pipeline conditionally adds `-noflip` for metasprite-bound PNGs only (`ConvertSpritesTask.kt:224-227`) to lock the tile id space.
   - What's unclear: For zones, the tilemap-export pipeline (not in 11.2 scope — tile data is currently hand-authored via `tileData = listOf(...)` in DSL or synthesized) doesn't yet need a locked tile id space.
   - Recommendation: **Add `-noflip` defensively** to keep the tile id space stable across runs. Cheap insurance. If future tilemap-export work needs it OFF for some reason, lift it then.
