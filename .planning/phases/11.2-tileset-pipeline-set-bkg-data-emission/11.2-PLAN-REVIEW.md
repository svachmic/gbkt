### MEDIUM (should fix; executor can compensate)

**MEDIUM-1 — Plan 12 omits explicit lcc-warnings audit on dungeon/explorer/racer**

Plan 11 captures `evidence/banks-smoke/lcc-warnings.txt` via narrow-pattern grep (per AC-8). Plan 12's 4-game `--parallel` sweep tees the combined output to `sweep.log` but does NOT run the same narrow-pattern grep against the dungeon/explorer/racer compile stages. AC-8 says "Generated C compiles under lcc with no implicit-int / const-mismatch / missing-declaration warnings" — that's an AC for the phase, not just banks. SceneVisitor + buildSceneFile changes touch ALL bank files in ALL games, so a non-banks regression is plausible (e.g., if dungeon's zone declares a tilesetPath via some path the planner missed, or if metaspriteInclude+zoneTilesetIncludes ordering in CFile triggers a new warning in dungeon).

**Fix hint:** Plan 12 Step 2 should append a per-game `grep -E 'warning:|implicit declaration|incompatible pointer|assignment makes|passing argument' <per-game-section-of-sweep.log>` and capture results to `evidence/cross-genre-sweep/lcc-warnings-<game>.txt`. The executor can do this inline by parsing sweep.log post-build, OR by running each `:buildRom` separately and teeing per-game logs first. Acceptable executor compensation: detect the gap during Plan 12 execution and inline the per-game audit.

**MEDIUM-2 — Plan 02 spike does NOT explicitly close one of the two stated assumptions**

Plan 02's `<resume-signal>` says "Type 'spike captured' once spike-log.md / checker.c / png2asset-help.txt all exist." But the must_haves truths list closure for A1 (`-bpp 2` valid) and A2 (`<stem>_tiles[N]` shape) AND tile count (`N=4` per checker.png at 16×16). The plan's how-to-verify step 7 says spike-log must capture "Byte count in the array (should be 4 tiles × 16 bytes = 64; verify)" — that's a real check, but it's narrative prose inside a checklist, not a structured assertion the executor MUST surface to the resume-signal.

The actual checker.png is 16×16 = 4 tiles → 64 bytes (confirmed: `identify` shows `16x16, 8-bit/color RGB`). Plan 11's acceptance criterion (`#define _zone_play_zone_tileset_count 4`) hard-codes 4. Plan 04 also hard-codes 4 in its acceptance criterion ("checker.png is 16×16 = 4 tiles"). If the spike reveals the locked flag set actually produces a different N (e.g., if `-spr8x8 -map` interprets 16×16 differently than expected), every downstream plan's hard-coded `4` breaks.

**Fix hint:** Plan 02 resume-signal should require the user (or autonomous spike) to explicitly state: "checker.c contains `<stem>_tiles[N]` with N = ___ bytes corresponding to ___ tiles." If N != 64 (or tile count != 4), plans 04 and 11's acceptance criteria need adjustment. This is a known-and-flagged risk per RESEARCH §A1+A2 — the spike is the safety valve — but the resume-signal could be tighter. Acceptable executor compensation: during plan 02 execution, capture the actual N and tile count, then when plan 04/11 execute, the acceptance-criteria checks compare against the spike-determined value (not the hard-coded 4) if there's drift. The plan-driven hard-coding of 4 is reasonable as the expected value because checker.png IS 16×16 → 4 tiles → 64 bytes (confirmed independently), but the executor should validate this against the spike output rather than trust the plan's hard-coding.

**MEDIUM-3 — ROM-size cap (SPEC Constraints "within 2× reference") has no concrete numeric reference**

Plan 12 Step 3 writes per-game ROM sizes to `rom-sizes.txt` and notes: "Compute the banks ROM size delta from any pre-Phase-11.2 baseline if a reference value is available in `gbkt-examples/banks/gbkt-build.properties`". My check shows `gbkt-build.properties` exists only as a build OUTPUT (containing `cartridge=MBC5_RAM_BATTERY`, `gbcMode=DISABLED`, `mbcType=0x1B`) — NO ROM_SIZE_CAP or REFERENCE_ROM_SIZE field. So plan 12's check degenerates to "observational only" per its own clause.

Adding 32 bytes (4 tiles × 8 bytes 2bpp; or 64 bytes per RESEARCH §A1) plus the set_bkg_data call + #include header should leave banks well under any reasonable 2× cap, but with no numerical anchor the SPEC Constraint is unfalsifiable.

**Fix hint:** Either (a) accept the observational-only stance explicitly in plan 12 SUMMARY (current plan does this — acceptable), or (b) plan 12 should additionally capture `git show <baseline>:gbkt-examples/banks/build/gbkt/output/banks.gb | wc -c` if a baseline commit hash is reasonably discoverable, computing the delta in bytes/% and asserting `<2x` directly. Acceptable executor compensation: if no baseline-properties anchor exists at run time, plan 12 SUMMARY should document the bare ROM byte counts so a future regression has a comparison point even if this phase couldn't make it pass/fail.

### LOW (nit / future improvement)

**LOW-1 — Plan 03's synthesized header uses `#define` alias instead of `extern const UINT8 _zone_<id>_tileset[N]`**

SPEC AC-1 says the header should declare `extern const UINT8 _zone_play_zone_tileset[];` (or "sized equivalent"). Plan 03's design (per RESEARCH §A2 Example 2 + Pitfall 3 — alias header is sufficient) emits `#define _zone_play_zone_tileset <native>_tiles` instead of a direct extern. Functionally equivalent at link time (the macro expands at every reference), but a maintainer grepping `extern const UINT8 _zone_` will NOT find the symbol in the header. This is a (likely deliberate) trade-off for avoiding source-file mutation per Pitfall 3.

**Fix hint:** Either accept the alias-only form (current plan), or have plan 03 emit BOTH a `#define` alias AND a forwarding `extern const UINT8 _zone_<id>_tileset[];` declaration (linker will resolve to the same symbol because the `#define` is textual; the extern is technically redundant but improves grep-ability). LOW because it's a polish issue.

**LOW-2 — Plan 09's KDoc cross-references CONVENTIONS.md before Plan 10 lands**

Plan 09 (wave 2) lands the KDocs referencing `.planning/codebase/CONVENTIONS.md §"Tile pixel data emission: two paths, when to use which"`. Plan 10 (wave 1) appends that section to CONVENTIONS.md. Since plan 10 is wave 1 and plan 09 is wave 2, in practice plan 10 will likely land FIRST and the cross-reference will be valid by the time plan 09's KDoc reads. However, the formal dependency is not declared in plan 09's `depends_on` (plan 09 depends only on 11.2-05). If plans run strictly per wave structure, plan 09 might land BEFORE plan 10 → KDoc references a section that doesn't exist yet.

**Fix hint:** Either (a) add `11.2-10` to plan 09's `depends_on` so the cross-reference is honored, OR (b) accept the eventual-consistency model (both ship in the same phase, so end-state has the cross-reference resolved). LOW because both KDoc + CONVENTIONS.md ship together at phase close, but future readers of the diff in commit-by-commit history might land on an inconsistent intermediate state. Acceptable executor compensation: run plan 10 before plan 09 (both wave 1/2; reorder is trivial).
