# Phase 13.2: Code Review Report

**Reviewed:** 2026-06-03
**Depth:** standard

## Summary

Phase 13.2 ships five requirements: file-level `@Suppress` migration (Req #12), `runIf`/`unless`/`orElse` single-frame conditionals (Req #2), `i16FixedVar`/`toPixel()` fixed-point abstraction (Req #3), `easeToZero()` decay primitive (Req #8), and `u8Var(wrapAt = N)` wrap-cycle primitive (Req #9), plus the single-use guard for all delegates (WR-06).

The core logic for `wrapAt` power-of-two detection, wrap guard emission, and `easeToZero` two-IfOp emission is correct for all current example usage. The delegate guards (VarDelegate, ActorDelegate, MetaspriteDelegate, SaveDataDelegate, ArrayDelegate) are correctly implemented and uniform. The examples (`SimplePhysics`, `Metasprites`, `MetaspritesStress`, `Banks`, `PlatformerTemplate`) are correctly migrated.

One BLOCKER is found: the `I16FixedVarDelegate.fractionalBits` parameter is accepted and silently discarded — it never flows to the returned `AssignableVar`, meaning `toPixel()` always uses its own default `fractionalBits = 4` regardless of what the delegate was constructed with.

Four warnings cover: `wrapAt = 0` producing silent always-reset behavior (no validation), asymmetric subtract semantics between the power-of-two and non-power-of-two `wrapAt` paths, `orElse` silently attaching to a wrap guard's IfOp if increment-with-wrap is the last statement, and `easeToZero(by)` oscillating when `by > 1` for small values.

## Critical Issues

### CR-01: `I16FixedVarDelegate.fractionalBits` never flows to `toPixel()` — RESOLVED

**Status:** Fixed in plan 13.2-08.
RED test commit: `e24fc345` (`test(13.2-08): RED — fractionalBits must flow from i16FixedVar to toPixel`)
Fix commit: `c205be1b` (`fix(13.2-08): flow fractionalBits from I16FixedVarDelegate to toPixel`)

**File:** `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/VariableBuilders.kt:475-479`

**Issue:** `I16FixedVarDelegate` accepts `fractionalBits` as a constructor parameter and uses it only to compute the initial stored value (`initialPixels shl fractionalBits`). It does NOT override `getValue`, so it inherits `VarDelegate.getValue` which returns `AssignableVar(resolvedName ?: property.name)` with no `fractionalBits` attached. When the user later calls `posX.toPixel()`, they are calling `AssignableVar.toPixel(fractionalBits: Int = 4)` (defined in ExprBuilder.kt:278) which uses its own default `4`, not the value the delegate was constructed with.

For the default `fractionalBits = 4`, the two defaults coincide and no bug surfaces. But for any non-default value (e.g. `i16FixedVar(80, fractionalBits = 8)` for 8.8 fixed-point), `toPixel()` silently emits `shr 4` instead of the intended `shr 8`. The user must remember to pass the same `fractionalBits` explicitly to `toPixel(fractionalBits = 8)` — no compile or runtime error alerts them to the mismatch.

The parameter creates a false promise: the delegate advertises that `fractionalBits` is a declaration-site configuration, but the call-site must be independently configured with the same value.

**Fix:** Either (a) make `I16FixedVarDelegate` propagate `fractionalBits` into the returned `AssignableVar` by overriding `getValue` and returning an extended wrapper, or (b) remove the `fractionalBits` parameter from `I16FixedVarDelegate` entirely (since the only currently used value is 4) and document that `.toPixel()` always requires the same fractional bits as the declaration. Option (a) is the correct fix:

```kotlin
// VariableBuilders.kt — add a fractional-bits-aware subtype of AssignableVar
data class FixedAssignableVar(
    override val name: String,
    val fractionalBits: Int,
) : AssignableVar(name) // or store fractionalBits in AssignableVar directly
```

Or more simply, store `fractionalBits` in `AssignableVar` and have `toPixel()` use it when non-null:

```kotlin
data class AssignableVar(val name: String, val wrapAt: Int? = null, val fractionalBits: Int? = null) {
    ...
}

// I16FixedVarDelegate.getValue:
override fun getValue(thisRef: Any?, property: KProperty<*>): AssignableVar =
    AssignableVar(resolvedName ?: property.name, fractionalBits = fractionalBits)

// ExprBuilder.kt toPixel — use stored value when available:
fun AssignableVar.toPixel(fractionalBits: Int = this.fractionalBits ?: 4): Expr =
    BinaryExpr(VarRef(name), BinaryOp.SHR, Literal(fractionalBits))
```

## Warnings

### WR-01: `wrapAt = 0` is silently accepted and produces always-reset behavior

**File:** `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/VariableBuilders.kt:135-155`

**Issue:** `isPowerOfTwo(0)` returns `false` (correct), so `emitWrapGuard(sb, name, 0)` takes the compare-reset path and emits `if (varName >= 0) { varName = 0 }`. For a `UINT8` variable, which is always >= 0, this guard fires unconditionally after every mutation, permanently locking the variable to 0. The same broken behavior occurs for `wrapAt < 0` (e.g. `wrapAt = -1` → `if (v >= -1)` which is always true for unsigned types). No validation prevents `u8Var(0, wrapAt = 0)` from compiling.

**Fix:** Add a `require` check in `U8VarDelegate` (or in `emitWrapGuard`) to reject non-positive `wrapAt` values at delegate construction time:

```kotlin
class U8VarDelegate(initialValue: Int, val wrapAt: Int? = null, transient: Boolean = false) :
    VarDelegate(VarType.U8, initialValue, transient) {
    init {
        require(wrapAt == null || wrapAt >= 2) {
            "wrapAt must be >= 2 (got $wrapAt); wrapAt = 0 or 1 produces degenerate behavior."
        }
    }
    ...
}
```

### WR-02: Asymmetric subtract behavior between power-of-two and non-power-of-two `wrapAt` paths

**File:** `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/VariableBuilders.kt:144-155`

**Issue:** `emitWrapGuard` is called after both `plusAssign`/`inc` (addition) AND `minusAssign`/`dec` (subtraction). The two paths behave differently for underflow on a `u8Var`:

- **Non-power-of-two** (e.g. `wrapAt = 5`): emits `if (v >= 5) { v = 0 }`. After `v` underflows from 0 to 255 (UINT8 wrap): `255 >= 5` is true → resets to 0.
- **Power-of-two** (e.g. `wrapAt = 16`): emits `v = v & 15`. After UINT8 underflow to 255: `255 & 15 = 15` → wraps to N-1, not 0.

The result: decrementing a power-of-two-wrapped variable from 0 wraps to N-1 (circular), while decrementing a non-power-of-two-wrapped variable from 0 resets to 0. This is an undocumented behavioral difference that can produce incorrect results if subtraction on a `wrapAt` variable is ever used. The KDoc says the guard fires after "++, --, +=, -=" so users can reasonably expect consistent behavior.

No current example subtracts from a `wrapAt` variable, so no regression exists today, but this is a subtle correctness trap. Additionally, the guard emitted after subtraction for the non-power-of-two case is semantically backwards: after `v -= 1` on a value of 3, `v` becomes 2, and `if (2 >= 5)` is false — no wrap fires (correct). Only the underflow case is affected.

**Fix:** Either restrict `wrapAt` to addition/increment ops only (remove the `wrapAt?.let { emitWrapGuard(...) }` calls from `minusAssign` and `dec`, and document this), or make the subtract path emit a proper underflow check: `if (v >= N && v > (N - by)) { v = N - 1 }` (circular decrement). Given current usage is increment-only, restricting is the simpler path:

```kotlin
operator fun AssignableVar.minusAssign(value: Expr) {
    val sb = ScriptBuilderContext.current ?: error("-= called outside a ScriptBuilder block")
    sb.assign(name, value, AssignOp.SUB)
    // NOTE: wrapAt guard intentionally not emitted for subtraction (see doc)
}
```

If circular decrement semantics are desired in future, a separate `wrapDec()` method is cleaner than overloading the existing operator.

### WR-03: `orElse` silently attaches to the wrap guard's IfOp if a `wrapAt` increment is the last statement before `orElse`

**File:** `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/ScriptBuilder.kt:240-242` and `VariableBuilders.kt:144-155`

**Issue:** `orElse` (aliasing `elseOp`) attaches an else branch to `ops.lastOrNull() as? IfOp`. For a non-power-of-two `wrapAt` variable, `inc()` emits two ops: the increment assign, then the wrap guard IfOp. If the user writes:

```kotlin
runIf(someCondition) {
    idx++       // idx has wrapAt = 5
}
orElse { navigate("gameover") }  // <-- attaches to wrap guard, not to runIf
```

Wait — in this case `idx++` is INSIDE the `runIf` body (its own `bodyBuilder`), so the outer `ops` only sees the outer IfOp from `runIf`. This is fine.

The actual problem surfaces when:

```kotlin
idx++          // emits: Assign(idx = idx+1) then IfOp(idx >= 5, [idx=0]) into outer ops
orElse { ... } // ops.lastOrNull() is now the wrap guard IfOp, not a user ifOp
```

Here `orElse` silently attaches to the wrap guard's IfOp, mutating `idx >= 5 → idx = 0 ELSE { ... }` — wrong semantics, no error thrown. The user intended `orElse` to follow some preceding `runIf`/`ifOp`, but the wrap guard slipped in between and `elseOp` doesn't distinguish between user-authored and framework-emitted IfOps.

The scenario requires careless code (calling `orElse` after an increment rather than after an explicit `runIf`), but the failure is silent and produces no diagnostic.

**Fix:** Tag wrap-guard IfOp nodes as internal (e.g. via a boolean property on IfOp IR node, or by checking that the last IfOp is a simple `v >= N → v = 0` pattern before allowing `elseOp` to attach). Alternatively, document that `orElse` must immediately follow `runIf`/`ifOp`/`unless` and add a more robust check:

```kotlin
// In elseOp — add a heuristic or tag check:
fun elseOp(block: ScriptBuilder.() -> Unit) {
    val lastIf = ops.lastOrNull() as? IfOp
        ?: throw DSLValidationError("error: elseOp() must immediately follow ifOp()")
    // Guard: wrap-guard IfOps always have a single-assign body with Literal(0).
    // If the else logic is critical, add an IR-level annotation instead.
    ...
}
```

In practice the safest fix is an IfOp `isWrapGuard: Boolean` field set to `true` by `emitWrapGuard` and checked by `elseOp`.

### WR-04: `easeToZero(by)` oscillates for `by > 1` when the variable value is less than `by`

**File:** `gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/ExprBuilder.kt:294-305`

**Issue:** The `easeToZero` implementation emits:

```
if (v < 0) { v += by }
if (v > 0) { v -= by }
```

When `by > 1`, these two branches can overshoot zero. Example: `v = 1`, `by = 2`. Frame 1: `v > 0` fires, `v -= 2` → `v = -1`. Frame 2: `v < 0` fires, `v += 2` → `v = 1`. The variable oscillates between `1` and `-1` forever and never reaches 0.

The documentation acknowledges this for `by = 1`: "the only value used in current example ports". The parameter `by: Int = 1` gives the impression that custom decay steps are supported. No guard prevents `easeToZero(by = 5)` from being called on a variable whose value is `< 5`.

**Fix:** Either remove the `by` parameter (making the method always use 1), or add a warning and a note in KDoc that `by` must not exceed the minimum absolute value the variable can have:

```kotlin
/**
 * ...
 * WARNING: [by] must be <= the minimum absolute value the variable can reach.
 * If [by] > 1 and the variable reaches a value between 0 and [by], the two
 * guards will oscillate. Default [by] = 1 is safe for all int types.
 */
fun AssignableVar.easeToZero(by: Int = 1) {
    require(by >= 1) { "easeToZero: by must be >= 1, got $by" }
    ...
}
```

### IN-01: Zone IDs in `PlatformerTemplate.kt` duplicate property names as magic strings

**File:** `gbkt-examples/platformer-template/src/main/kotlin/io/github/gbkt/examples/platformer_template/PlatformerTemplate.kt:261-307`

**Issue:** Zone declarations use the `zone("world1Area1Zone") { }` string-arg form, which duplicates the Kotlin property name as a magic string argument — a violation of Project Rule #1 ("no magic strings"). Examples:

```kotlin
val world1Area1Zone = zone("world1Area1Zone") { ... }  // "world1Area1Zone" duplicated
val world1Area2Zone = zone("world1Area2Zone") { ... }  // "world1Area2Zone" duplicated
val world2Area1Zone = zone("world2Area1Zone") { ... }  // "world2Area1Zone" duplicated
val titleZone = zone("titleZone") { ... }              // "titleZone" duplicated
val nextLevelZone = zone("nextLevelZone") { ... }      // "nextLevelZone" duplicated
```

The file itself documents this as "PHASE-12 FRAMEWORK GAP" and cites the absence of a `ZoneDelegate` as the root cause, with Phase 13 cleanup planned. This is a carried-over acknowledged deviation, not a regression introduced in Phase 13.2. Recorded here for tracking completeness.

**Fix:** Implement a `ZoneDelegate` with `provideDelegate` for name inference (parallel to `MetaspriteDelegate`, `ActorDelegate`), then migrate all `zone(id) { }` call sites to `val x by zone { }`. Tracked as Phase 13 cleanup per SEED-PHASE-12-SHARED-TILESET / PlatformerTemplate.kt comments.
