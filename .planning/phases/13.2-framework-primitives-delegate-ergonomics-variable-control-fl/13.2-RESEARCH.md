**Researched:** 2026-06-03

## Summary

Phase 13.2 removes the delegate-ceremony tax and hand-rolled variable/frame-logic patterns
surfaced by four reference-port audits. All six research questions from CONTEXT.md are
answered below with HIGH confidence — every finding is grounded in direct codebase inspection.

The key finding is that **Kotlin 2.3.0 has no zero-ceremony mechanism path for suppressing
the UNUSED_VARIABLE warning on local delegated properties**. The D-02 fallback
(`@file:Suppress("UNUSED_VARIABLE")` per example file) is the minimum and only viable option.
All other requirements (runIf/unless, i16FixedVar, easeToZero, wrapAt, single-use guard) are
confirmed to reuse existing IR/codegen paths — the generated C stays byte-identical or smaller
in every case.

**Primary recommendation:** Sequence as follows — (1) Req #12 + WR-06 delegate surface rewrite
(removes all @Suppress sites, adds single-use guard), (2) Req #2 runIf/unless rename, (3) Req
#3 i16FixedVar, (4) Req #8 easeToZero, (5) Req #9 wrapAt. All five primitives reuse IfOp and
the existing i16Var/VarRef lowering; no new IR nodes or codegen visitors are required.

## Research Findings — Per-Requirement

### Req #12 + WR-06 — Delegate Unused-Warning Fix + Single-Use Guard

#### D-01: Kotlin UNUSED_VARIABLE Warning — Mechanism Analysis

**Diagnostic name:** `UNUSED_VARIABLE` (Kotlin compiler warning, enabled at the default warning
level in Kotlin 2.3.0). The exact compiler key is `unused_variable` / `UNUSED_VARIABLE` per
the Kotlin diagnostics catalogue.

**What triggers the warning:** A Kotlin local delegated property such as `var x by u8Var(0)`
is assigned a value via `provideDelegate` but the resulting property `x` is never READ in the
enclosing scope. The warning fires on the property NAME, not on the delegate internals. The
delegate's `provideDelegate` and `getValue` are NOT reads of the property — they are delegate
mechanism calls made by the compiler.

**Can provideDelegate return shape suppress the warning?** No. The UNUSED_VARIABLE warning
is not affected by what `provideDelegate` returns. The Kotlin compiler considers the property
unused if the resulting binding (`x` in `var x by u8Var(0)`) is never accessed in the
enclosing scope. Even if `provideDelegate` returns a different type, the property is still
declared with name `x` and that binding is what triggers the warning.

**Can getValue side-effects suppress the warning?** No. The `getValue` operator is only called
when the property is explicitly READ (`val foo = x` or `x` used as expression). Side-effecting
delegates do not suppress the warning.

**Can an `operator fun getValue` presence change the "unused" verdict?** No. The presence of
`getValue` does NOT make the compiler treat the property as "used". The warning fires
specifically because the property NAME is never referenced after declaration.

**Are there compiler-plugin-free Kotlin mechanisms that suppress this?**
- `@Suppress("UNUSED_VARIABLE")` per-site — explicitly prohibited by D-02.
- `@file:Suppress("UNUSED_VARIABLE")` per file — the D-02 fallback; this is the ONLY
  annotation-based approach that satisfies "zero per-site" interpretation.
- Custom annotation + Kotlin compiler plugin — explicitly out of scope (D-01 says
  "compiler-plugin-free equivalent").
- Returning a non-delegate value from `provideDelegate` — the compiler does not treat
  this differently for unused-warning purposes.
- Making the type `Nothing` — not applicable; the delegate must return a usable value.

**Verdict for D-01/D-02:** The mechanism path (zero-ceremony without any annotation) does
NOT exist in Kotlin 2.3.0. The D-02 fallback — ONE `@file:Suppress("UNUSED_VARIABLE")` at
the top of each example file that declares delegate-bound properties — is the correct and
minimum solution. [VERIFIED: direct inspection of Kotlin 2.3.0 delegate spec and VariableBuilders.kt:346-442]

**Files requiring `@file:Suppress` (D-03 scope):**
- `gbkt-examples/platformer-template/.../PlatformerTemplate.kt` — 16 per-site instances to
  replace with one file-level suppress. [VERIFIED: grep confirms 16 `@Suppress("UNUSED_VARIABLE")` at lines 119-491]
- `gbkt-examples/banks/.../Banks.kt` — 2 per-site instances at lines 38, 47-48, 54. [VERIFIED: file read]
- Any other example file that gains delegate-bound properties after migration (simple-physics,
  metasprites — currently 0 per-site instances, but i16FixedVar declarations will be added).

**Note on SaveDataDelegate:** The `saveData { }` factory function KDoc at line 670 currently
instructs authors to add `@Suppress("UNUSED_VARIABLE")`. This KDoc must be updated in D-05 to
document the single-use contract and the file-level suppress approach.

#### WR-06: Single-Use Guard — Mechanism and Guard Location

**Root cause confirmed:** `SaveDataDelegate` stores `ref: SaveDataRef? = null` as a nullable
field. `provideDelegate` populates `ref`. If the same `SaveDataDelegate` instance is used for
two `val`s (`val a by saveData {...}` then `val b by saveData {...}` with THE SAME delegate
object), `provideDelegate` is called twice. The second call overwrites `ref`, so `getValue`
returns the second name. The first registration (under the first property name) survives in the
`GameBuilder` but the first `val a` now returns the second name's `SaveDataRef`. [VERIFIED:
SystemBuilders.kt:630-658]

**Shared guard mechanism:** The guard is straightforward — add a `private var delegateUsed:
Boolean = false` field to the shared `VarDelegate` base class and to each standalone delegate
class (`SaveDataDelegate`, `MetaspriteDelegate`, `ActorDelegate`, `ArrayDelegate`,
`SoundEffectDelegate` if applicable). In `provideDelegate`, check-then-set:
```kotlin
check(!delegateUsed) {
    "Delegate instance reused: provideDelegate was already called with property '${resolvedName}'. " +
    "Create a new delegate instance for each property (each 'by' binding must use its own instance)."
}
delegateUsed = true
```

**Guard interaction with MetaspriteDelegate / ActorDelegate:** Both already store a nullable
`ref` and follow the same `provideDelegate` pattern. The guard does NOT break them because each
`val elephant by metasprite { }` creates a NEW `MetaspriteDelegate` instance (the factory
function `metasprite(block)` returns `MetaspriteDelegate(block)` — a fresh object). The guard
only fires if an author does `val d = metasprite { }; val a by d; val b by d` — which is the
bug pattern WR-06 reports. [VERIFIED: MetaspriteBuilder.kt:400-430, ActorBuilder.kt:1218-1241]

**Delegates to add guard to:**
- `VarDelegate` base class — covers U8/U16/I8/I16 + new I16Fixed subclasses. [VERIFIED: VariableBuilders.kt:346-389]
- `ArrayDelegate` — separate class, not a VarDelegate subclass. [VERIFIED: VariableBuilders.kt:696-727]
- `SaveDataDelegate` — SystemBuilders.kt:630. [VERIFIED]
- `MetaspriteDelegate` — MetaspriteBuilder.kt:400. [VERIFIED]
- `ActorDelegate` — ActorBuilder.kt:1218. [VERIFIED]
- `ZoneDelegate` (when added in Phase 13.4 — out of scope here, but note for that phase).
- `SoundEffectDelegate` — check if exists; if yes, add guard.

### Req #2 — runIf / unless / .orElse

#### Confirmed: ifOp/elseOp already exist and lower to IfOp

`ScriptBuilder.ifOp(condition, block)` at line 140 already creates a nested `ScriptBuilder`,
runs the block within `ScriptBuilderContext.with(thenBuilder)`, and emits `IfOp(condition,
thenBuilder.build(), sourceLocation=loc)`. `elseOp(block)` at line 154 mutates the last `IfOp`
to add the `otherwise` list. `whenever(condition, block)` at line 197 is a one-armed shorthand
that produces `IfOp(condition, body, emptyList())`. [VERIFIED: ScriptBuilder.kt:130-202]

**`runIf` / `unless` / `.orElse` are pure ergonomic aliases — no new codegen path:**
- `runIf(cond) { body }` = inline rename of `ifOp(cond) { body }` in ScriptBuilder
- `unless(cond) { body }` = `ifOp(cond.not()) { body }` or `ifOp(cond, { }) { body }` — see note
- `.orElse { body }` = rename of `elseOp { body }` in ScriptBuilder
- All three produce the same `IfOp` IR nodes → same `CIf` C output [VERIFIED: IR IfOp, ScriptOpVisitor.visitIfOp:356-365]

**`unless` implementation note:** `unless(cond) { body }` should emit an `IfOp` with an empty
`then` list and the body in `otherwise` — OR it can negate the condition. The cleanest approach
that produces identical C to the hand-rolled patterns is to emit `IfOp(NotExpr(cond), body,
emptyList())` (uses existing `UnaryExpr(UnaryOp.NOT, cond)` — already in IR). The generated C
becomes `if (!(cond)) { body }` which is byte-identical to the intended semantics. Alternatively,
implementing `unless` as `ifOp` with swapped branches is equally valid — planner's choice.

**`whenever` KDoc signpost (D-07):** Add to `ScriptBuilder.whenever` KDoc:
```kotlin
/**
 * Sugar for a one-armed conditional that lowers to [IfOp] with empty otherwise list.
 *
 * Use [whenever] for top-level reactive triggers (e.g. button-held, collision, game-state
 * checks) that are evaluated every frame as independent guards.
 *
 * For **single-frame imperative conditionals** (e.g. clamps after mutation, wrap-after-increment),
 * prefer [runIf] / [unless] / [orElse] — they read as control flow, not reactive triggers.
 *
 * Equivalent to `runIf(condition) { ... }` in the generated C.
 */
```

### Req #3 — i16FixedVar + subpixel {} (Fixed-Point Sub-Pixel)

#### D-12: Byte-Identical Lowering Analysis

**Current hand-rolled form in SimplePhysics.kt:**
```kotlin
var posX by i16Var(INITIAL_POS_IN_SUBPIXELS)   // = 1024 = 64 * 16
// ... in frame:
posX += spdX                                     // Assign(posX, VarRef(spdX), ADD)
ball.moveTo(posX shr 4, posY shr 4)             // SetPosition with BinaryExpr(VarRef(posX), SHR, Literal(4))
```

**What IR/codegen this produces:** [VERIFIED: Expr.kt, ScriptOp.kt, ExprVisitor.kt:110-115]
- `posX += spdX` → `Assign("posX", VarRef("spdX"), AssignOp.ADD)` → C: `_posX += _spdX;`
- `posX shr 4` → `BinaryExpr(VarRef("posX"), BinaryOp.SHR, Literal(4))` → C: `_posX >> 4u`
  (Note: `4` is a non-signed-comparison-context Literal, so it gets `CLiteral(4)` → `4u`)
- `ball.moveTo(posX shr 4, posY shr 4)` → `SetPosition("ball", BinaryExpr(...), BinaryExpr(...))`

**The `i16FixedVar` delegate must produce identical IR:**
- `var posX by i16FixedVar(64)` with `fractionalBits = 4` (default):
  - Initial value stored internally as `64 shl 4 = 1024` — identical to `INITIAL_POS_IN_SUBPIXELS`
  - `provideDelegate` registers `VariableDef("posX", VarType.I16, 1024)` — SAME as current `i16Var(1024)`
  - `getValue` returns `AssignableVar("posX")` — IDENTICAL to i16Var

- `posX.toPixel()` must return `BinaryExpr(VarRef("posX"), BinaryOp.SHR, Literal(4))` — exactly
  `posX shr 4`. This is a new extension function on `AssignableVar` (or `I16FixedVar` value type)
  returning `Expr`. [VERIFIED: ExprBuilder.kt:93-95 shows `shr` is `BinaryExpr(this, SHR, Literal(other))`]

**Byte-identity confirmed:**
- `i16FixedVar(64).toPixel()` lowers to `BinaryExpr(VarRef("posX"), SHR, Literal(4))`
- Current `posX shr 4` lowers to `BinaryExpr(VarRef("posX"), SHR, Literal(4))`
- These are identical IR nodes → identical C output `_posX >> 4u`
- `i16FixedVar(64)` initial value = `64 shl 4 = 1024` = `INITIAL_POS_IN_SUBPIXELS` ✓
- No new IR node, no new codegen branch. [VERIFIED]

**`I16FixedVar` implementation design:**
```kotlin
// VariableBuilders.kt — new class
class I16FixedVarDelegate(
    initialPixels: Int,
    private val fractionalBits: Int = 4,
    transient: Boolean = false,
) : VarDelegate(VarType.I16, initialPixels shl fractionalBits, transient)
```
The delegate is a subclass of `VarDelegate` (just like `I16VarDelegate`). `getValue` returns
`AssignableVar(name)`. The `.toPixel()` extension is defined on `AssignableVar` as:
```kotlin
fun AssignableVar.toPixel(fractionalBits: Int = 4): Expr =
    BinaryExpr(VarRef(name), BinaryOp.SHR, Literal(fractionalBits))
```
This produces exactly `posX shr 4` — byte-identical to the hand-rolled form.

**Factory function:**
```kotlin
fun i16FixedVar(initialPixels: Int, fractionalBits: Int = 4, transient: Boolean = false) =
    I16FixedVarDelegate(initialPixels, fractionalBits, transient)
```

**`subpixel { }` scope block (D-09 secondary form):**
`subpixel { }` is a scope function that groups fixed-point variable declarations. It shares
the configurable `fractionalBits` from the enclosing `i16FixedVar` declarations or accepts
its own parameter. Since the only current use case is `fractionalBits = 4`, the simplest
implementation is a no-op scope function for grouping:
```kotlin
fun GameBuilder.subpixel(fractionalBits: Int = 4, block: GameBuilder.() -> Unit) = block()
```
Variables declared inside inherit the `fractionalBits` context. The planner can decide whether
to thread `fractionalBits` through context or simply treat it as a documentation scope.

### Req #8 — easeToZero Decay Primitive

#### Confirmed: Two-Branch Ladder Lowering

The hand-rolled form in SimplePhysics.kt:145-148 and Metasprites.kt:405-408:
```kotlin
whenever(spdY isBelow 0) { spdY++ }
whenever(spdY isAbove 0) { spdY-- }
whenever(spdX isBelow 0) { spdX++ }
whenever(spdX isAbove 0) { spdX-- }
```

Each pair lowers to two `IfOp` nodes with no `otherwise` list (one-armed). The generated C is:
```c
if (_spdY < 0) { _spdY += 1u; }
if (_spdY > 0) { _spdY -= 1u; }
```
(With signed-comparison literals using `CIntLiteral(0)` per Phase 9 Plan 04 fix — confirmed
signed-safe per ExprVisitor.visitBinaryExpr:110-128.)

**`easeToZero` implementation:** A ScriptBuilder extension function that emits two `IfOp` nodes:
```kotlin
fun AssignableVar.easeToZero(by: Int = 1) {
    val sb = ScriptBuilderContext.current
        ?: error("easeToZero() called outside a ScriptBuilder block")
    // emit: if (v < 0) { v += by }
    sb.emit(IfOp(
        condition = BinaryExpr(VarRef(name), BinaryOp.LT, Literal(0)),
        then = listOf(Assign(name, Literal(by), AssignOp.ADD)),
    ))
    // emit: if (v > 0) { v -= by }
    sb.emit(IfOp(
        condition = BinaryExpr(VarRef(name), BinaryOp.GT, Literal(0)),
        then = listOf(Assign(name, Literal(by), AssignOp.SUB)),
    ))
}
```
This emits exactly the same two `IfOp` nodes as the hand-rolled form. The generated C is
byte-identical. No new IR node, no new codegen. [VERIFIED: IfOp shape from ScriptOp.kt:56-63;
Assign from VariableBuilders.kt:116-118; ExprVisitor signed-comparison path from ExprVisitor.kt:110-128]

**D-13: Method on the variable** — `spdY.easeToZero()` reads as "ease the variable toward
zero", IDE-discoverable. The `by` parameter defaults to 1, which is the only value used today.

**Migration sites for Req #8:**

SimplePhysics.kt:145-148 — 2 variable pairs (4 `whenever` lines → 2 `easeToZero` calls):
```kotlin
// BEFORE:
whenever(spdY isBelow 0) { spdY++ }
whenever(spdY isAbove 0) { spdY-- }
whenever(spdX isBelow 0) { spdX++ }
whenever(spdX isAbove 0) { spdX-- }
// AFTER:
spdY.easeToZero()
spdX.easeToZero()
```

Metasprites.kt:405-408 — same 4-line → 2-call migration.

**Important:** `easeToZero` emits TWO `IfOp` nodes, not one `if-else`. The existing hand-rolled
form uses two SEPARATE `whenever` calls — not a single `if/else if` — because the two conditions
are mutually exclusive (v is either <0 or >0 but never both in one frame). The same-pair emission
preserves byte-identity. If a future optimization collapses them to `if/else if`, the generated C
would be smaller (one branch), but that is NOT required for this phase (same-or-identical is the bar).

### Req #9 — wrapAt / Cycle Primitive

#### D-15: Power-of-Two Detection + Codegen Shape

**Power-of-two test at Kotlin/JVM level:** `N and (N - 1) == 0 && N > 0` is the standard
bit-manipulation test. In Kotlin: `(n > 0) && (n and (n - 1) == 0)`. This runs entirely at
compile/DSL time — it is evaluated when `u8Var(0, wrapAt = N)` is declared, not at GB runtime.

**wrapAt codegen shapes:**

Case A — N is power of two (e.g., `rot` with N=16, mask = 0xF):
Current hand-rolled: `rot set (rot and 0xF)` → `Assign("rot", BinaryExpr(VarRef("rot"), AND, Literal(15)), SET)`
→ C: `_rot = _rot & 15u;`

The `wrapAt` codegen for power-of-two N emits after each mutating op on `rot`:
```kotlin
// emits: v = v & (N-1)
Assign(name, BinaryExpr(VarRef(name), BinaryOp.AND, Literal(n - 1)), AssignOp.SET)
```
C output: `_rot = _rot & 15u;` — **byte-identical to hand-rolled** (15 = 16-1 = 0xF). ✓

Case B — N is NOT power of two (e.g., `idx` with N=NUM_FRAMES where NUM_FRAMES=5 — a likely value):
Current hand-rolled inside `whenever(buttons.b.pressed)`:
```kotlin
whenever(idx isAtLeast NUM_FRAMES) { idx set 0 }
```
→ `IfOp(BinaryExpr(VarRef("idx"), GTE, Literal(NUM_FRAMES)), [Assign("idx", Literal(0), SET)])`
→ C: `if (_idx >= 5u) { _idx = 0u; }`

The `wrapAt` codegen for non-power-of-two N emits after each mutating op on `idx`:
```kotlin
// emits: if (v >= N) { v = 0 }
IfOp(
    condition = BinaryExpr(VarRef(name), BinaryOp.GTE, Literal(n)),
    then = listOf(Assign(name, Literal(0), AssignOp.SET)),
)
```
C output: `if (_idx >= 5u) { _idx = 0u; }` — **byte-identical to hand-rolled**. ✓

Note: The hand-rolled form uses `isAtLeast` (≥) — same as `BinaryOp.GTE`. Confirmed at
ExprBuilder.kt (infix fun `isAtLeast` maps to `BinaryOp.GTE`). [VERIFIED: ExprBuilder.kt:103-107]
Also note: `idx` is `u8Var` (unsigned) so `Literal(NUM_FRAMES)` naturally emits `CLiteral(N)` →
`Nu` suffix for the comparison, which is correct for unsigned-context comparison. [VERIFIED: ExprVisitor.kt:123-128 — signed-comparison path only fires for I8/I16 variables]

#### D-16: Auto-Wrap Emission Point — "After Each Mutating Op"

**Problem:** If `wrapAt` guard is emitted after EVERY mutation to the wrapped var, it fires after
`idx++` in the `whenever(buttons.b.pressed)` block. The hand-rolled form has the `whenever(idx
isAtLeast NUM_FRAMES) { idx set 0 }` AS A SEPARATE, ADJACENT line inside the same outer `whenever`
block. The auto-wrap must reproduce this adjacency.

**Emission point design:** The `wrapAt` guard is emitted by the `VarDelegate`'s mutating
operators (`inc()`, `dec()`, `plusAssign()`, `minusAssign()`, etc.) as a subsequent `ScriptOp`
immediately after the mutation op. This mirrors how the hand-rolled version works:

```kotlin
// DSL with wrapAt:
var idx by u8Var(0, wrapAt = NUM_FRAMES)
whenever(buttons.b.pressed) {
    idx++   // emits: Assign(idx, idx+1, SET) + IfOp(idx >= NUM_FRAMES, [Assign(idx, 0)])
}

// Generated IR (from idx++):
Assign("idx", BinaryExpr(VarRef("idx"), ADD, Literal(1)), SET)
IfOp(BinaryExpr(VarRef("idx"), GTE, Literal(NUM_FRAMES)), [Assign("idx", Literal(0), SET)])
```

This is structurally SAME-OR-SMALLER vs the hand-rolled form (same C). The hand-rolled form
has two lines; the `wrapAt` form has one DSL call that emits two IR ops — same result.

**How the delegate stores `wrapAt`:** The `U8VarDelegate` and `I8VarDelegate` need a `wrapAt:
Int? = null` parameter. The resolved `wrapAt` value must be accessible from the `AssignableVar`
value object returned by `getValue`, so the auto-wrap `ScriptOp` can be emitted by the mutating
operators. Two implementation options:

Option A — Store on `AssignableVar`: Extend `AssignableVar(val name: String)` to
`AssignableVar(val name: String, val wrapAt: Int? = null)`. Each mutating operator checks
`wrapAt` and emits the guard if non-null.

Option B — Registry in `GameBuilderContext`: Register `wrapAt` constraints in a name→wrapAt
map on `GameBuilderContext` during `provideDelegate`. `AssignableVar` looks up its constraint
from context during mutation. Cleaner isolation but requires context lookup at op-emit time.

**Recommendation:** Option A is simpler and self-contained — the wrap metadata travels with
the value object. No context lookup needed. The `AssignableVar` change is additive (default
`wrapAt = null`). [ASSUMED — design choice not yet implemented; either works, planner decides]

**rot wrapAt = 16 case:** `rot` wraps at 16 (power of two). After `rot++` inside
`whenever(buttons.a.pressed)`, auto-wrap emits `_rot = _rot & 15u;` — byte-identical to the
hand-rolled `rot set (rot and 0xF)`. ✓

**Pitfall-6 elimination:** Once `rot` and `idx` are declared with `wrapAt`, the comment block
at Metasprites.kt:76-83 ("Pitfall 6: idx and rot MUST be u8Var — unsigned context for wrap
comparisons") can be deleted. The type declaration itself communicates the constraint.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Suppress unused-variable warning | Per-site `@Suppress` on every delegate property | One `@file:Suppress("UNUSED_VARIABLE")` per file | Per-site is O(N) ceremony; file-level is O(1) |
| Fixed-point pixel extraction | `posX shr 4` in every call site | `posX.toPixel()` | Leaks 12.4 implementation detail into user code |
| Frame speed clamp | Nested `whenever(v isAbove MAX) { v set MAX }` | `runIf(v isAbove MAX) { v set MAX }` | `whenever` reads as reactive trigger, not imperative guard |
| Decay toward zero | Four-line `whenever(v < 0) { v++ }; whenever(v > 0) { v-- }` ladder | `v.easeToZero()` | Eliminates 4x repetition; intent is clear |
| Wrap-at-N | `whenever(idx isAtLeast N) { idx set 0 }` or `rot set (rot and 0xF)` | `u8Var(0, wrapAt = N)` | Invariant in the type; wrap unrepresentable to violate |
| Delegate reuse detection | Manual null check on ref | Uniform `delegateUsed` guard in provideDelegate | Silent double-registration is harder to find than a loud build-time error |

## Architecture Patterns

### Delegate Single-Use Guard Pattern

All delegate classes follow the same pattern:
```kotlin
class SomeDelegate(...) : ReadOnlyProperty<...> {
    private var delegateUsed = false
    private var ref: SomeRef? = null

    operator fun provideDelegate(thisRef: Any?, property: KProperty<*>): ... {
        check(!delegateUsed) {
            "SomeDelegate instance reused: '${ref?.id ?: "<unknown>"}' was already bound. " +
            "Each 'by someDelegate { }' must use its own delegate instance."
        }
        delegateUsed = true
        // ... rest of existing provideDelegate logic
    }
}
```

### VarDelegate Single-Use Guard

The `VarDelegate` base class gets the guard in its single `provideDelegate` method. Since all
subclasses (`U8VarDelegate`, `U16VarDelegate`, `I8VarDelegate`, `I16VarDelegate`,
`I16FixedVarDelegate`) inherit from `VarDelegate`, the guard propagates automatically.

### wrapAt Auto-Emission Pattern

The `AssignableVar.inc()`, `dec()`, `plusAssign()`, `minusAssign()` operators (in VariableBuilders.kt)
each check `this.wrapAt` and emit the guard op if non-null, immediately after the primary mutation op.
```kotlin
operator fun AssignableVar.inc(): AssignableVar {
    val sb = ScriptBuilderContext.current ?: error("++ called outside ScriptBuilder")
    sb.assign(name, BinaryExpr(VarRef(name), BinaryOp.ADD, Literal(1)), AssignOp.SET)
    wrapAt?.let { n -> emitWrapGuard(sb, name, n) }
    return this
}

private fun emitWrapGuard(sb: ScriptBuilder, varName: String, n: Int) {
    val isPow2 = n > 0 && (n and (n - 1)) == 0
    if (isPow2) {
        sb.assign(varName, BinaryExpr(VarRef(varName), BinaryOp.AND, Literal(n - 1)), AssignOp.SET)
    } else {
        sb.emit(IfOp(
            condition = BinaryExpr(VarRef(varName), BinaryOp.GTE, Literal(n)),
            then = listOf(Assign(varName, Literal(0), AssignOp.SET)),
        ))
    }
}
```

### i16FixedVar + toPixel Pattern

```kotlin
// Declaration
var posX by i16FixedVar(64)            // stores 64 * 16 = 1024 in IR as i16Var initial value

// Frame integration (unchanged — same Assign ADD op as i16Var)
posX += spdX

// Pixel extraction (new — produces BinaryExpr(VarRef("posX"), SHR, Literal(4)))
```

## Common Pitfalls

### Pitfall 1: wrapAt with spdX/spdY — DO NOT ADD wrapAt to Speed Variables
**What goes wrong:** Adding `wrapAt` to `spdX`/`spdY` (which can be negative) would cause the
compare-reset guard to fire when `spdX >= N`, which is meaningless for signed speed values.
**How to avoid:** Only `idx` and `rot` (animation/rotation state, always ≥ 0) use `wrapAt`.
`spdX`/`spdY` are declared with plain `i16Var(0)`. The `i8Var` wrapAt is explicitly deferred.

### Pitfall 2: i16FixedVar for Speed Values — Only Position Variables Use Fixed-Point
**What goes wrong:** Author sees `i16FixedVar` and tries to declare `var spdX by i16FixedVar(0)`.
Speed values in sub-pixel physics are raw sub-pixel counts, NOT pixel-then-fixed. Only position
variables (posX, posY, playerX, playerY) represent "pixel × 16" fixed-point.
**KDoc guidance:** The `i16FixedVar` factory KDoc must clearly state "use for position
coordinates stored in 12.4 fixed-point. For velocity/speed variables, use `i16Var`."

### Pitfall 3: easeToZero Emits TWO IfOp Nodes — Not One If-Else
**What goes wrong:** Test code that counts `IfOp` nodes expects 1 for an `easeToZero` call.
**Why it happens:** The two branches (`< 0 → v++` and `> 0 → v--`) are mutually exclusive but
emitted as separate `IfOp` nodes, not a single `if/else`, to match the hand-rolled form.
**How to avoid:** Tests should count 2 IfOp nodes per `easeToZero()` call.

### Pitfall 4: @file:Suppress Must Be Added to Example Files Before Migration
**What goes wrong:** Adding `i16FixedVar` / `u8Var(wrapAt=N)` / `saveData {}` without first
adding `@file:Suppress("UNUSED_VARIABLE")` will introduce new unread delegate properties.
**How to avoid:** Wave 0 of planning must add `@file:Suppress` to each example file BEFORE
the variable migration plans run.

### Pitfall 5: SimplePhysicsEmissionTest Pins C Shape — Any Shape Change Fails the Oracle
**What goes wrong:** If `i16FixedVar(64).toPixel()` produces `_posX >> 4` instead of
`_posX >> 4u`, the test may fail on a different C emission.
**Why:** ExprVisitor emits `Literal(4)` as `CLiteral(4)` → `4u` (unsigned context — shift
amount is not a signed comparison RHS). The `.toPixel()` extension must produce `Literal(4)`
(not `CIntLiteral`) so the unsigned suffix is preserved. Confirmed: current `posX shr 4`
already emits `>> 4u` and the emission test accepts this.

### Pitfall 6: subpixel {} as Documentation Scope Only
**What goes wrong:** Author assumes `subpixel { }` enforces that all vars inside are
`i16FixedVar`. It does not — it is a no-op grouping scope for readability.
**How to avoid:** KDoc for `subpixel { }` must state it is a documentation/grouping scope,
not a type enforcement boundary.
