## Summary

Phase 06.9 addresses 10 accumulated infrastructure gaps (J1–J10) from earlier phases. The good news: more work is already done than the deferred items suggest. Constant folding (`ConstantFoldingPass`), dead code elimination (`DeadCodeEliminationPass`), and bitwise optimization (`BitwiseOptimizationPass`) are fully implemented in `gbkt-analysis` and wired into `DefaultPipeline`. The module decomposition is substantially complete — `gbkt-core` has been reduced to an aggregator `build.gradle.kts` that re-exports `gbkt-ir`, `gbkt-lang`, `gbkt-engine`, and `gbkt-world` as `api` dependencies. The Detekt baseline in `gbkt-core` contains only 24 items (all legitimate suppressions), and `./gradlew detekt` passes clean across all modules.

The genuine remaining work: HRAM/SRAM allocation are hard-coded to zero (confirmed in `RAMPlanningPass.run()`), `estimateBgTiles()` returns a constant 256 heuristic instead of reading from `AssetManifest`, collection operations (`ht_*`, `pool_*`, `ring_*`) in `ScriptOpInterpreter.evaluateCallExpr()` return 0 stubs, and IR serialization to JSON does not yet exist for `GameIR`. SameBoy's `Tester` build target is a headless binary that runs a ROM and produces screenshot output — it requires building from source with `make tester`.

**Primary recommendation:** Tackle items in dependency order: fix `estimateBgTiles()` first (requires `AssetManifest.TilemapEntry` to gain a `uniqueTileCount` field), then HRAM/SRAM, then collection simulation, then IR JSON serialization. The headless emulator task is the most novel work and should be scoped conservatively (boot smoke test only — not scripted scenario replay).

## Architecture Patterns

### Pattern 1: Existing JSON Serialization Pattern (AssetManifest)

The codebase already has an established pattern for JSON serialization — use it for IR serialization:

```kotlin
// Source: gbkt-core/src/main/kotlin/io/github/gbkt/core/AssetManifest.kt
data class AssetManifest(val version: Int = 1, val assets: List<AssetManifestEntry>) {
    fun toJson(): String {
        val root = JSONObject()
        root.put("version", version)
        // ...
        return root.toString(2)
    }
    companion object {
        fun fromJson(content: String): AssetManifest { ... }
    }
}
```

**Apply to IR serialization:** Create `GameIRSerializer` following this pattern:

```kotlin
// New file: gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/GameIRSerializer.kt
object GameIRSerializer {
    const val SCHEMA_VERSION = 1

    fun toJson(game: GameIR): String { ... }   // returns JSON string
    fun fromJson(json: String): GameIR { ... }  // parses back to live IR
}
```

**Version field behavior:** On deserialization, if `schemaVersion` != `SCHEMA_VERSION`, emit a warning (stderr or Diagnostic) but attempt to parse anyway (best-effort backward compatibility).

### Pattern 2: Existing Analysis Pass Pattern (for HRAM/SRAM fix)

The HRAM and SRAM fields exist in `RAMLayout` and `AnalysisConfig`. The `RAMPlanningPass` currently hardcodes them to 0:

```kotlin
// gbkt-analysis/src/main/kotlin/io/github/gbkt/analysis/passes/RAMPlanningPass.kt (current)
// 4. HRAM and SRAM are 0 for now (no DSL constructs target them in v2 IR)
val hramUsed = 0
val sramUsed = 0
```

**Fix approach:** Scan `GameIR` for constructs that map to HRAM/SRAM. Current IR state:
- No DSL construct targets HRAM directly (confirmed — J1 remains an extension point)
- SRAM: `game.containers` (ContainerIR with save data) and RPG save configs (in `gbkt-genre-rpg`) indicate SRAM usage. The v2 save system stores: character stats, inventory, party state, flags to SRAM slots.

Recommended fix: Compute SRAM from `game.containers` (using `ContainerIR.slots * element byte size`) and from the presence of RPG save configs. HRAM can remain 0 with the comment updated to reflect no current DSL targets it.

### Pattern 3: Asset Manifest → VRAMLayoutPass Pipeline

The `estimateBgTiles()` fix requires:

1. **Add `uniqueTileCount` to `AssetManifestEntry.TilemapEntry`** (the field for unique post-deduplication BG tiles)
2. **Pass `AssetManifest` into `PassContext`** (currently PassContext has no asset manifest field)
3. **Update `estimateBgTiles()`** to look up the tileset path from `SceneIR.tilesetRef`, find the matching `TilemapEntry` in the manifest, and return its `uniqueTileCount`
4. **Fallback:** If manifest is null or the entry is not found, keep the 256 heuristic

```kotlin
// Updated VRAMLayoutPass.kt (simplified)
private fun estimateBgTiles(scene: SceneIR, game: GameIR, manifest: AssetManifest?): Int {
    val tilesetRef = scene.tilesetRef ?: return 0
    val entry = manifest?.assets
        ?.filterIsInstance<AssetManifestEntry.TilemapEntry>()
        ?.firstOrNull { it.tilesetPath == tilesetRef.path }
    return entry?.uniqueTileCount ?: BG_TILES_DEFAULT_ESTIMATE  // 256 fallback
}
```

**PassContext change:** Add `val assetManifest: AssetManifest? = null` to `PassContext`. The `GBDKPipelineV2` that calls the analysis pipeline already reads the manifest file — it must pass it into `PassContext`.

### Pattern 4: Collection Simulation in ScriptOpInterpreter

Collection operations emit `CallOp` (function calls in C like `ht_cache_insert(key, val)`, `pool_bullets_alloc()`). In `ScriptOpInterpreter`, `CallOp` is currently a no-op stub and `evaluateCallExpr` returns 0 for unknown functions.

**Simulation approach:** Add in-memory collection state (maps and lists) to `ScriptOpInterpreter`, and in `evaluateCallExpr` / the `CallOp` handler, dispatch on function name prefix:

```kotlin
// New state fields in ScriptOpInterpreter
private val hashTables: MutableMap<String, MutableMap<Long, Long>> = mutableMapOf()
private val pools: MutableMap<String, MutableList<Long?>> = mutableMapOf()

// In evaluateCallExpr:
"ht_${name}_insert" -> { hashTables.getOrPut(name) { mutableMapOf() }[args[0]] = args[1]; 0L }
"ht_${name}_get"    -> hashTables[name]?.get(args[0]) ?: 0L
"ht_${name}_contains" -> if (hashTables[name]?.containsKey(args[0]) == true) 1L else 0L
"ht_${name}_remove" -> { hashTables[name]?.remove(args[0]); 0L }
```

Pattern: parse function name to extract collection name and operation. Use `startsWith` / regex matching to identify collection-related calls.

### Pattern 5: SameBoy Headless Emulator Task

SameBoy has a `Tester` build target (`make tester` in the SameBoy source). The `Tester/main.c` is a headless binary that accepts ROM path arguments, runs the ROM for a configurable number of frames, and produces output (exit code + stdout with frame results).

**Gradle task design:**

```kotlin
// New: gbkt-gradle-plugin/.../tasks/EmulatorTestTask.kt
abstract class EmulatorTestTask : DefaultTask() {
    @get:Input @get:Optional abstract val sameboyTesterPath: Property<String>
    @get:InputFile abstract val romFile: RegularFileProperty
    @get:Input abstract val maxFrames: Property<Int>  // default 600

    @TaskAction
    fun run() {
        val tester = findSameBoyTester()  // auto-detect or use sameboyTesterPath
        val process = ProcessBuilder(tester.absolutePath, romFile.get().asFile.absolutePath)
            .redirectErrorStream(true)
            .start()
        // Parse stdout, report Gradle test results
    }
}
```

**Fallback:** If SameBoy tester binary is not found, fall back to `ValidateRomTask` with mGBA SDL — which already exists and works.

**Dependency note:** `emulatorTest` depends on `buildRom` depends on `generateC`. Already the structure in `GbktPlugin.kt`.

### Anti-Patterns to Avoid

- **Adding optimizations not yet in `DefaultPipeline`:** `DeadCodeEliminationPass`, `ConstantFoldingPass`, and `BitwiseOptimizationPass` are already implemented and wired. Do NOT add duplicate optimization logic — verify with `DefaultPipeline.kt` first.
- **Using `kotlinx.serialization` for IR JSON:** Would require `@Serializable` on all IR nodes — massive annotation churn across `gbkt-ir`. Use hand-rolled `JSONObject` consistent with `AssetManifest`.
- **Building SameBoy as part of the Gradle build:** SameBoy tester must be installed separately. The Gradle task detects it; it does not build it.
- **Hardcoding `PassContext.assetManifest` as non-null:** Manifest may not be available (unit tests, non-Gradle pipelines). Always treat as nullable with graceful fallback.

## Common Pitfalls

### Pitfall 1: PassContext.assetManifest Not Wired in GBDKPipelineV2

**What goes wrong:** The `estimateBgTiles()` fix reads the manifest from `PassContext`, but `GBDKPipelineV2` must pass the manifest in when constructing `PassContext`. If the wiring is missed, `estimateBgTiles()` silently falls back to 256 for all scenes.
**Why it happens:** `PassContext` is constructed deep in `GBDKPipelineV2` — the manifest file is read elsewhere.
**How to avoid:** Update `GBDKPipelineV2.run()` to read `asset-manifest.json` from the build directory and set `assetManifest` on `PassContext`.
**Warning signs:** VRAMLayoutPass tests still pass with 256 tile counts even when manifest is provided.

### Pitfall 2: IR JSON Serialization — Polymorphic ScriptOp Handling

**What goes wrong:** `ScriptOp` is a non-sealed interface (by design — external modules add subtypes). A `JSONObject`-based serializer must include a type discriminator field (`"type": "Assign"`) for every subtype, and the deserializer must handle unknown types gracefully (skip with warning, not crash).
**Why it happens:** External genre modules (gbkt-genre-rpg) add their own `ScriptOp` subtypes. Full round-trip requires either a registry of all known types or an extensible type discriminator mechanism.
**How to avoid:** Serialize only core IR types (defined in `gbkt-ir`). For round-trip completeness, genre-specific ops can be serialized as `RawOp` with a comment. Document this limitation.
**Warning signs:** `fromJson()` throws `IllegalArgumentException` on unknown type discriminators.

### Pitfall 3: Collection Simulation — Name Extraction from Function Names

**What goes wrong:** Collection function names encode both the collection name and the operation (e.g., `ht_tileCache_insert`). If the collection name contains underscores, simple `split("_")[1]` extraction fails (e.g., `ht_tile_cache_insert` has ambiguous parsing).
**Why it happens:** Collection names are user-defined and can contain underscores.
**How to avoid:** Use suffix matching for the operation part (`endsWith("_insert")`, `endsWith("_get")`) and derive the collection name from the infix.
**Warning signs:** `HashTableRef` operations fail to simulate for collection names with underscores.

### Pitfall 4: SameBoy Tester — CI Availability

**What goes wrong:** SameBoy tester binary is not a standard package manager installation. It requires building from source (`make tester` in the SameBoy C codebase). CI environments (GitHub Actions) will not have it installed.
**Why it happens:** SameBoy tester is a niche tool for emulator accuracy testing, not a general-purpose headless tool.
**How to avoid:** `emulatorTest` task must be `@Optional` — it skips gracefully when tester binary is not found (same pattern as `runEmulator` skipping when mGBA is absent). Add a note in CI docs that the task requires manual setup.
**Warning signs:** Task fails with "SameBoy tester not found" on CI.

### Pitfall 5: Optimization Report — PassContext Lifecycle

**What goes wrong:** `ConstantFoldingPass` and `DeadCodeEliminationPass` already run but produce no report. Adding report generation requires threading report data through `PassContext` without breaking existing pass return contracts.
**Why it happens:** `PassResult.Success` copies `PassContext` — any new report field must be `null`-safe on `PassContext` and accumulated via `copy()`.
**How to avoid:** Add `val optimizationReport: OptimizationReport? = null` to `PassContext`; each pass produces a `PassOptimizationSummary`; `BudgetAuditPass` or a new `OptimizationReportPass` aggregates them into a file.
**Warning signs:** `PassContext.copy()` calls fail to compile because `optimizationReport` field is missing.

## Open Questions

1. **SameBoy Tester binary CI distribution**
   - What we know: SameBoy has a `Tester` build target (`make tester`); it is a headless binary that processes ROMs.
   - What's unclear: Exact command-line arguments accepted by the tester binary (requires reading `Tester/main.c`); whether it exits with non-zero on ROM crash; whether it can run a fixed number of frames.
   - Recommendation: Use mGBA `ValidateRomTask` as the emulator test implementation — it already exists and is proven. Add SameBoy tester as an optional alternative. Both run a ROM for N frames and check for crash.

2. **IR JSON serialization scope for non-sealed ScriptOp**
   - What we know: `ScriptOp` is intentionally non-sealed (genre modules extend it). `Expr` similarly non-sealed.
   - What's unclear: Whether the serializer should attempt to serialize genre-specific ops (requiring service-loader-discovered serializers) or serialize core ops only.
   - Recommendation: Core ops only in first pass. Unknown `ScriptOp` subtypes serialize as `{"type": "Unknown", "class": "io.github.gbkt.rpg.domain.BattleOp"}` and deserialize as `RawOp("// unsupported: BattleOp")`. Document this clearly.

3. **Module boundary enforcement mechanism**
   - What we know: No ArchUnit or Gradle dependency constraint enforcement currently exists.
   - What's unclear: Whether Gradle module-level `compileOnly`/`api`/`implementation` restrictions are sufficient, or whether ArchUnit tests are needed.
   - Recommendation: Gradle `configurations` restrictions (prevent `gbkt-ir` from depending on `gbkt-lang`) are the lowest-cost enforcement. Add `forbids` directives in module-specific `build.gradle.kts` files.

4. **SRAM calculation for non-RPG games**
   - What we know: `game.containers` (ContainerIR) carries `slots` and `categoryFilter`. RPG save data size is in `gbkt-genre-rpg/domain/RpgSaveConfig.kt`.
   - What's unclear: Whether `ContainerIR.slots * sizeof(element)` correctly represents all SRAM-backed storage, or if RPG save configs need to contribute separately.
   - Recommendation: Implement `sramUsed` from `game.containers` size computation as a first pass; document that RPG module's SRAM contribution requires genre-aware extension.
