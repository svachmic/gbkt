<decisions>
## Implementation Decisions

### IR Serialization Format
- JSON format (not protobuf) — human-readable, wide tooling support, iteratable
- Include a schema version field with best-effort backward compatibility (readers warn on mismatch, try to parse anyway)
- Full round-trip: serialize IR → JSON → deserialize back to live IR objects
- Serves two use cases equally: enabling non-JVM frontends AND debugging/inspection during development
- Deserialization is required (not just dump) to support external frontends producing IR for the backend

### Module Reorganization
- Full scope: audit current state → complete migration out of gbkt-core → enforce boundaries
- Researcher determines the right module structure (no locked-in naming preferences)
- Keep gbkt-core if it still serves a purpose after migration
- Enforce boundaries via Gradle dependency constraints / architecture tests so new code goes to the right module
- Existing v2 modules (gbkt-ir, gbkt-lang, gbkt-engine, gbkt-world, gbkt-rpg, gbkt-analysis) are the starting point

### ROM Optimization Strategy
- All three optimization types at equal priority: dead code elimination, shared constant tables, function deduplication
- Always-on by default, but each optimization pass is individually configurable (user can disable specific passes)
- Use the right level for each: IR-level optimizations (constant folding) and C-output-level optimizations (dead function removal) as appropriate
- Detailed optimization report file written to build/ directory showing exactly what was removed/changed

### Headless Emulator Testing
- Target emulator: SameBoy (prioritize investigating its headless/scripting capabilities)
- Scope for this phase: CI boot smoke tests (ROM boots and runs N frames without crashing). Scripted gameplay scenarios (inputs, scene transitions) deferred to a future phase.
- Integration: Gradle task (`./gradlew emulatorTest`) — runs after buildRom, reports results in Gradle format
- Run against example games (pong, breakout, explorer, rpg-lite, dungeon)

### Claude's Discretion
- HRAM/SRAM allocation implementation details (removing hard-coded zeros)
- `estimateBgTiles()` fix approach (how to read actual tile count from asset pipeline)
- Collection operations simulation implementation in SimulationContext
- Constant-folding optimization pass design (which expressions to fold, how aggressive)
- Detekt violation triage — which violations to fix vs suppress with justification
- Specific Gradle task naming and configuration API for optimization toggles

</decisions>
