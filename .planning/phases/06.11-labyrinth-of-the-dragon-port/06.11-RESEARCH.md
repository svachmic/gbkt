## Summary

Phase 06.11 ports the LabyrinthOfTheDragon game (24K-line hand-written C across 56 files) into a V2 Kotlin DSL reference implementation. The existing `LabyrinthOfTheDragon-port/` directory has the build config, all assets (8 floor TMX maps, 13 monster sprites, font, tilesets, UI tilemaps), and a working en.po (356 strings across 16 namespaces), but **zero Kotlin source files**. Everything needs to be written from scratch.

The Original C game uses 19+ ROM banks (`#pragma bank 8` through bank ~21), 4 RAM banks, 8 dungeon floors, 12 monsters, 4 character classes (each with 6-7 abilities = 24+ total abilities), 8 consumable items, a textbox system, torch mechanics, and a flag-based world state (3 pages × 8 flags per page = up to 256 flags). This is significantly more complex than any Phase 06.10 example game.

The core work decomposes into: (1) **framework gap audit and fixes** (localization auto-padding, zero-magic-string APIs, font extension for Czech diacritics, compile-time language flag build support), (2) **asset audit and cleanup** (deduplicate res/ directory, verify all assets against Original), (3) **porting waves** ordered by dependency — RPG definitions first (characters, monsters, abilities, items), then scene/UI wiring (title, hero select, gameplay, battle, victory, game over), then world/floor definitions (8 floors × objects/chests/exits/encounters), then localization integration (en.po audit + cs.po creation), then testing + validation fixes.

**Primary recommendation:** Run framework gap analysis first as its own plan — every gap found blocks one or more porting plans. Start porting in this order: RPG core (character classes + monsters) → ability definitions → items → scenes → floors → localization. Use separate framework-fix plans for each gap, with explicit dependencies from port plans to fix plans.

## Architecture Patterns

### Pattern 1: Object-Based Entry Point

The CONTEXT.md specifies `object LabyrinthOfTheDragon` not a top-level function. This enables cleaner test access and multiple-language build variants:

```kotlin
// LabyrinthOfTheDragon.kt
object LabyrinthOfTheDragon {
    fun create() = game("LabyrinthDragon") {
        config {
            cartridge = "MBC5_RAM_BATTERY"
            romBanks = 32   // Original uses up to bank 21+
            ramBanks = 4
        }
        // ... game definition delegates to sub-files
    }
}
```

### Pattern 2: Zero Magic Strings (Hard Constraint)

**Current framework:** `sceneRef(id: String)`, `zone(id: String)`, `flags(id: String)`, `battleUpdate(combat)` already typed.

**Gaps to fix before porting:**
- Any API that accepts `String` where a typed ref should exist must be updated first
- Combat state names (`"COMBAT_STATE_VICTORY"`) must become typed enums or sealed classes
- Flag access (`flags.getFlag("metElder")`) must use typed `FlagRef` if not already

Research finding: `sceneRef()` and `ZoneRef` are already type-safe (`SceneRef(id)`, `ZoneRef(id)`). Need to audit combat state strings and flag string APIs.

### Pattern 3: Scene Ordering (Established Pattern)

Define scenes in reverse navigation order — later scenes defined first so they can be referenced without forward declarations. Only forward-declare for circular cycles:

```kotlin
// Example: gameover defined first, navigates to titleRef (forward-declared)
val titleRef = sceneRef("title")
val gameoverScene = scene("gameover") { ... navigate(titleRef) ... }
val gameplayScene = scene("gameplay") { ... navigate(gameoverScene) ... }
val titleScene = scene("title") { ... navigate(gameplayScene) ... }
start = titleScene.id
```

### Pattern 4: Floor Definition Pattern (from Original C)

Each Original floor C file defines:
- `maps[]` array — map ID + bank + data + dimensions
- `chests[]` array — chest flags, position, lock state, item list, callback
- `exits[]` array — bidirectional tile transitions between map regions
- `objects[]` array — interactive objects (signs, levers, sconces, NPCs)
- `encounters` — monster encounter tables with weights

The V2 equivalent uses `zone()` + `exploration {}` + `flags()`:

```kotlin
// Floor1Entrance.kt
val floor1 = zone("floor1") {
    name("Dungeon Level 1")
    tilemap(asset("tilemaps/floors/floor1.tilemap"))
    size(32, 32)
    encounters {
        safeSteps(10)
        entry("combat", weight = 40)    // kobold encounter
        entry("combat_goblin", weight = 20)
    }
    // chests, exits, objects — need DSL coverage research
}
```

**Gap:** The Original's `chests[]`, `exits[]`, and `objects[]` map data structures have complex flag-gated interactions. The V2 exploration system's `onInteract {}` callback handles this, but the full expressiveness needs verification.

```kotlin
// Characters.kt — 4 classes

    name("Fighter")

    name("Kobold")
```

### Anti-Patterns to Avoid

- **Raw string scene navigation:** `navigate("battle")` — use `navigate(battleSceneRef)` instead
- **Raw string flag access:** `flags.getFlag("bossDefeated")` string form — prefer typed FlagRef
- **Padding in PO msgstr:** `msgstr "Potion    "` — the framework should auto-pad; keep msgstr clean
- **skipValidation=true:** Remove from build.gradle.kts — fix validation root causes instead
- **Duplicate assets:** `res/monsters/` and `res/sprites/monsters/` both exist — deduplicate
- **LotD-specific framework API:** Any new DSL method written only for LotD needs; make it generic

## Common Pitfalls

### Pitfall 1: Framework Gap Discovered Mid-Porting

**What goes wrong:** Porting a floor and discovering the V2 `zone()` DSL can't express a chest with an `onOpen` scripted callback (the Original pattern). If this is discovered during porting, the plan splits awkwardly.

**Why it happens:** The framework was built from simpler examples (Pong, Breakout, Explorer). LotD has much more complex object interaction patterns.

**How to avoid:** Run a systematic gap audit plan **before** any porting plans. Document each Original C pattern (chests with scripted callbacks, exits with condition gates, boss-door-unlock logic) and verify framework coverage upfront. Create framework-fix plans for each gap.

**Warning signs:** Any time game code would need `raw()` or a hardcoded C string.

### Pitfall 2: String Padding Added to PO Then Changed

**What goes wrong:** The Original `en.po` already has padded strings like `"Ether "` and `"ATK&  "`. If these are kept padded and the framework adds auto-padding, strings will be double-padded.

**Why it happens:** The auto-padding feature is a **new framework feature** (not yet implemented). The existing en.po was written under the old convention.

**How to avoid:** The framework auto-padding plan must be implemented first. The en.po audit plan then strips trailing spaces from all strings that will be auto-padded. The auto-padding width must be configurable per context (13 chars for ability names, 6 chars for item short names, etc.).

**Warning signs:** Menu items misaligned in generated C output.

### Pitfall 3: OAM Overflow in Analysis Pass

**What goes wrong:** The Original uses 16 entity sprites for status icons (4 per combatant × 4 combatants) plus hero sprite. The analysis OAM pass flags this as overflow. The old port used `skipValidation=true` as a workaround.

**Why it happens:** The CONTEXT.md mandates removing `skipValidation=true`. Status icons require careful OAM slot planning.

**How to avoid:** Make the status icon sprite allocation a first-class plan. Either (a) reduce to max 10 OAM slots visible simultaneously, or (b) fix the analysis pass to account for battle-scene-only OAM usage, or (c) add a `maxOamSlots` override DSL for scenes that explicitly manage OAM differently.

**Warning signs:** Analysis BudgetAuditPass fails with OAM overflow error.

### Pitfall 4: Czech Font Tiles Break VRAM Budget

**What goes wrong:** Adding 14 Czech diacritic tiles to the font tileset pushes the font from 128 tiles to 142 tiles. If VRAM is already tight (dungeon tiles + font + monster tiles), the analysis VRAM planning pass fails.

**Why it happens:** Original font (128 tiles, 1KB) + Czech tiles (14 × 16 bytes = 224 bytes extra). VRAM tile limit is 256 tiles per bank.

**How to avoid:** Map the VRAM layout early (font placement, dungeon tile region, monster tile region). The Original uses FONT_OFFSET = 0x80 for font start, keeping dungeon tiles in 0x00-0x7F range. V2 must respect this layout or reconfigure VRAM regions in DSL.

**Warning signs:** VRAM budget report shows tile count > 256 for any scene.

### Pitfall 5: Compile-Time Language Flag Build Architecture

**What goes wrong:** Wanting `labyrinth_en.gb` and `labyrinth_cs.gb` as separate outputs requires the build to know which language to compile. Currently the Gradle plugin doesn't have a "language variant" concept.

**Why it happens:** This is a new feature. The PO file pipeline currently only supports one locale in `res/strings/en.po`.

**How to avoid:** This needs a framework plan before localization plans. The approach: `gbkt { locale("en") }` extension property selects which `res/strings/{locale}.po` to compile against. Two `./gradlew buildRom -Pgbkt.locale=en` and `./gradlew buildRom -Pgbkt.locale=cs` invocations produce separate ROMs.

**Warning signs:** Only one ROM produced regardless of locale configuration.

### Pitfall 6: Monster Encounter Tables Per Class

**What goes wrong:** The Original's encounter tables are level-gated — the same floor shows different enemy compositions based on player level. The simple `encounter { +kobold }` pattern in V2 doesn't capture this directly.

**Why it happens:** Simpler examples (Dungeon, Explorer) use flat encounter tables. LotD has progressive encounter difficulty.

**How to avoid:** Check if `zone.encounters` supports level-weighted entries or conditional encounter groups. If not, this is a framework gap. Research this in the gap audit plan.

### Existing en.po Coverage vs Original strings.h

The existing en.po contains 356 strings in 16 namespaces matching the Original's bank structure:

These truncated strings indicate the en.po was generated but not fully populated. The audit plan must cross-reference every `extern const char str_*[]` in strings.h against en.po entries.

## Open Questions

1. **Combat state names as typed refs**
   - What we know: The existing LotD port CLAUDE.md references `"COMBAT_STATE_VICTORY"` as raw string
   - What's unclear: Does the V2 `simpleBattle` / `CombatEngineSystem` expose typed combat state references?
   - Recommendation: Audit `CombatEngineSystem` API in `gbkt-ir` and `gbkt-genre-rpg`. If raw string, fix before porting.

2. **Level-progressive encounter tables**
   - What we know: Original floor files have level-gated encounter entries; V2 `zone.encounters { }` has `entry(battleId, weight)` flat table
   - What's unclear: Whether weight can be conditional on player level or flag state
   - Recommendation: Check `ZoneBuilder.kt` and `ExplorationSystem` codegen. This is likely a framework gap.

3. **Floor-local scripted object callbacks**
   - What we know: Original uses function pointers (`chest_add_torch`, `chest_add_magic_key`) for chest callbacks
   - What's unclear: Whether V2's `onInteract {}` in the exploration DSL can replicate per-object typed callbacks
   - Recommendation: This is the most complex gap. Investigate in gap audit plan.

4. **Multi-ROM output (per-language)**
   - What we know: Two ROMs needed (`labyrinth_en.gb`, `labyrinth_cs.gb`); GbktExtension has `outputName` property
   - What's unclear: Whether the Gradle plugin supports building two output variants from one game DSL
   - Recommendation: Needs a framework plan. Likely implemented as Gradle task variants or project properties.

5. **Framework auto-padding width specification**
   - What we know: Ability names need 13-char width, item names need 6-char width — different widths per context
   - What's unclear: How the auto-padding width is specified — per msgctxt namespace in PO? Per DSL call site?
   - Recommendation: Design this in the localization framework plan before implementation.
