# Phase 06.11: DSL Gap Audit — LotD Original vs V2 Framework

**Audited:** 2026-02-27
**Auditor:** Claude Sonnet 4.6 (plan executor)
**Confidence:** HIGH — all gaps verified by direct code inspection (Original C + V2 Kotlin sources)

## Summary

**14 categories audited. 14 gaps documented.** Of these:
- **5 BLOCKING** gaps — prevent porting without framework work
- **7 DEGRADING** gaps — can be worked around but at cost of fidelity or DSL quality
- **2 COSMETIC** gaps — minor, do not affect core gameplay

Each BLOCKING gap has its own recommended framework fix plan. This document provides the foundation for selecting which plans to create before porting begins.

## GAP-01: PO Auto-Padding

**Severity:** BLOCKING

**Original C pattern:** `tools/strings2c` generates C strings that are already padded to fixed widths. The Original `assets/strings` JS arrays contain padded strings (e.g., `"Cure Wounds  "` 13 chars for ability menu alignment). The `en.po` in the port continues this convention.

**V2 current status:** MISSING — No auto-padding support exists anywhere in the V2 pipeline.
- `gbkt-backend-gbdk` has no padding logic in the localization pipeline
- `GbktExtension.kt` has no `padWidth` or `padContext` property
- CONTEXT.md mandates: "Clean strings in PO, framework auto-pads" — contradicts current state

**Evidence:**
- `tools/strings2c` calculates max widths from parameter specs and pads all strings to that width (verified directly from the tool source)
- `en.po` currently has padded strings like `"Ether "` with trailing spaces — these will break if auto-padding is added without stripping the existing padding first
- No auto-padding code found in any V2 module (search confirmed)

**Recommended fix approach:**
- Add `padWidth` optional property to `msgctxt` namespace configuration in the PO pipeline
- When `padWidth` is set for a namespace, the backend zero-pads all strings in that namespace to exactly `padWidth` chars at codegen time (NOT at DSL time)
- The `en.po` audit plan must strip all trailing spaces from strings that will be auto-padded
- Configuration: either via a companion JSON/YAML file alongside en.po, or via a new Gradle extension property (`gbkt { localization { namespace("ability") { padWidth(13) } } }`)

**Affected porting plans:** All localization plans, all menu/UI scenes that display fixed-width strings. Especially: ability menu (13 chars), item menu (6 chars for short names), stat display.

## GAP-02: Compile-Time Locale Flag

**Severity:** BLOCKING

**Original C pattern:** None (Original has no localization beyond English). The port requires two ROMs: `labyrinth_en.gb` and `labyrinth_cs.gb`.

**V2 current status:** MISSING — `GbktExtension` has no `locale` property (confirmed by direct inspection of GbktExtension.kt). The PO pipeline loads `en.po` by convention but there is no mechanism to select a different locale at build time or via Gradle task parameter.

**Evidence:**
- `GbktExtension.kt` properties: `gbdkHome`, `target`, `game`, `assetDirectory`, `outputName`, `compilerFlags`, `debug`, `gbcMode`, `skipValidation`, `budgetReport`, `ramBanks`, `resourceDirectory` — no `locale`
- No `-Pgbkt.locale` Gradle property handling in `GbktPlugin.kt`

**Recommended fix approach:**
- Add `abstract val locale: Property<String>` to `GbktExtension` with default `"en"`
- The `generateC` task reads `locale.get()` → selects `res/strings/{locale}.po`
- Expose `-Pgbkt.locale=cs` as a Gradle project property override
- The `outputName` convention should append the locale: `outputName.set("labyrinth_${locale.get()}")` or require explicit naming by the user

**Affected porting plans:** Czech ROM build (Plan 06.11-12 or equivalent). All localization plans depend on this.

## GAP-03: Czech Font Tile Extension

**Severity:** BLOCKING

**Original C pattern:** None (Original is English-only). The port requires 14 extra Czech diacritic tiles (ě, š, č, ř, ž, ý, á, í, é, ú, ů, ď, ť, ň) added to the existing font at `FONT_OFFSET = 0x80`.

**V2 current status:** MISSING — The V2 asset pipeline has no concept of a "font extension" or "font overlay" mechanism. Fonts are single PNG files processed as tilesets.

**Evidence:**
- `FONT_OFFSET = 0x80` in Original `core.h` (128 tiles = 1KB reserved for font)
- Standard GB font covers ASCII 32-127 (96 usable chars). Czech needs 14 additional code points beyond ASCII 127
- V2 tileset pipeline: no mechanism to extend an existing tileset with supplementary tiles

**Recommended fix approach:**
- Design decision required: (a) a single extended `font_cs.png` with 142 tiles that replaces `font.png` for Czech builds, using the compile-time locale flag to select which font to load, OR (b) a font extension DSL: `font("font.png") { extend("font_cs_extra.png", at = 128) }` that composites tiles at build time
- Option (a) is simpler: Czech build uses a different font file. Requires user to create `font_cs.png` (128 base tiles + 14 Czech tiles = 142 tiles). The locale flag selects which font PNG to compile against.
- Option (b) requires new asset pipeline functionality

**Affected porting plans:** Czech localization plan. VRAM budget plan (font overlay needs 14 extra tiles).

## GAP-04: Level-Progressive Encounter Tables

**Severity:** BLOCKING

**Original C pattern:** `floor1.c` lines 264-346 define TWO encounter tables: `encounter_lv5[]` and `encounter_lv9[]`. The `on_move()` callback dispatches to one or the other based on `player.level`:

```c
if (player.level < 9)
    generate_encounter(encounter_lv5);
else
    generate_encounter(encounter_lv9);
```

Each table has entries with `ODDS_*` probabilities, `MONSTER_LAYOUT_*` (1, 2, or 3 monsters), monster type, level, and tier.

**V2 current status:** PARTIAL — `EncounterBuilder` in `WorldBuilders.kt` supports `entry(id, weight)` with optional `condition(flagId)`. It can gate entries on a story flag but NOT on player level. The `weight` is static.

**Evidence:**
```kotlin
// V2 EncounterBuilder (WorldBuilders.kt)
fun entry(id: String, weight: Int, block: EncounterEntryBuilder.() -> Unit = {})

// EncounterEntryBuilder only has:
fun condition(flagId: String)   // flag gate — not level gate
```

There is no `minLevel` / `maxLevel` property on `EncounterEntryIR`.

**Recommended fix approach:**
- Add `minLevel(n: Int)` and `maxLevel(n: Int)` methods to `EncounterEntryBuilder`
- Add `minLevel: Int?` and `maxLevel: Int?` fields to `EncounterEntryIR`
- The `ExplorationSystem` codegen (in `CombatVisitor` or equivalent) must emit a runtime level check before selecting the entry: `if (_player_level >= minLevel && _player_level < maxLevel)`
- Multiple encounter tables per floor become multiple weighted sets where each entry has a level range

**Affected porting plans:** All 8 floor definitions. Floor 1 uses 2 tables (lv1-8 vs lv9+), Floors 2-8 likely have similar progressive tables.

## GAP-05: Multi-Monster Encounter Groups

**Severity:** BLOCKING

**Original C pattern:** `floor1.c` encounter tables have `MONSTER_LAYOUT_2` and `MONSTER_LAYOUT_3S` entries with multiple monsters:

```c
{
    ODDS_35P, MONSTER_LAYOUT_2,
    MONSTER_KOBOLD, 5, C_TIER,
    MONSTER_KOBOLD, 6, C_TIER,
},
```

`encounter.c` / `monster.core.c` supports up to 3 active monsters per encounter (`encounter.monsters[0..2]`). The battle system's `roll_initiative()` handles 1–3 monster slots.

**V2 current status:** PARTIAL — `SimpleBattleBuilder.encounter {}` with `+goblin; +goblin` syntax (unary plus on `MonsterDef`) does support multi-monster encounters at the static DSL level. However, it is MISSING level-scaled and tier-scaled monster instantiation. The Original uses `monster_level` and `PowerTier` per encounter entry to generate monsters with level-appropriate stats from `tables.c` lookup tables. V2's `EncounterDef` only stores monster IDs — it cannot specify that "spawn Kobold at level 8, B_TIER" vs "spawn Kobold at level 5, C_TIER".

**Evidence:**
- `SimpleBattleBuilder.EncounterBuilder` stores `monsterIds: List<String>` — just IDs, no level/tier override per instance
- `EncounterDef(monsterIds, weight)` — no per-monster level/tier

**Recommended fix approach:**
- Extend `EncounterDef` with per-slot monster specs: `EncounterSlotDef(monsterId, level, tier)`
- Add `encounter { slot(kobold, level = 8, tier = MonsterTier.UNCOMMON); slot(kobold, level = 5) }` syntax OR
- Use the existing `+monster` syntax for static level, and add `slot(monster) { level(8); tier(UNCOMMON) }` for dynamic instances
- The `tables.c` equivalent in V2 must be invokable per-slot at encounter time

**Affected porting plans:** All 8 floor definitions, combat system plan.

## GAP-06: Per-Floor Scripted Object Callbacks (Chests, Sconces, Levers, NPCs)

**Severity:** BLOCKING

**Original C pattern:** `floor1.c` defines rich per-object scripted callbacks using function pointers:

```c
// Chests with callbacks
{ CHEST_1, MAP_A, 6, 2, false, false, NULL, NULL, chest_add_torch },
{ CHEST_3, MAP_A, 21, 10, false, false, str_chest_item_1pots, chest_item_1pot },

// Sconces with complex multi-state callbacks
static void on_lit(const Sconce* sconce) {
    switch (sconce->id) {
    case SCONCE_1: set_chest_unlocked(CHEST_4); map_textbox(str_floor_test_chest_click); break;
    case SCONCE_2:
    case SCONCE_3:
        if (is_sconce_lit(SCONCE_2) && is_sconce_lit(SCONCE_3)) open_door(DOOR_2);
        break;
    }
}

// NPCs with level-gated behavior
static bool on_npc_action(const NPC *npc) {
    if (player.level < 10) { map_textbox(str_maps_boss_not_yet); return true; }
    // ... start boss encounter
}

// Boss encounter inline
static bool boss_encounter(void) {
    reset_encounter(MONSTER_LAYOUT_1);
    goblin_generator(monster, 10, S_TIER);
    monster->id = 'A';
    set_on_victory(boss_victory);
    start_battle();
    return true;
}
```

**V2 current status:** PARTIAL — `ZoneBuilder` has `onEnter {}` and `onExit {}` callbacks using `ScriptBuilder`. The `exploration { onInteract {} }` hook exists. However, there is NO per-object typed callback system. In V2, all interactions funnel through a single `tryInteractWithObject(floor, x, y)` call — the framework does not have typed chest/sconce/lever/NPC object arrays with individual scriptable callbacks, flag tracking (CHEST_1 used-flag), or lock state.

**Evidence:**
- `WorldBuilders.kt` `ZoneBuilder`: only `onEnter`, `onExit`, `encounters`, `transition` — no `chest {}`, `sconce {}`, `npc {}`, `lever {}`, `door {}` DSL
- `SystemBuilders.kt` `ExplorationBuilder`: `onInteract {}` is a single global callback — no per-object dispatch

**Recommended fix approach:** This is the largest framework gap. Two options:
1. **Full object DSL**: Add `chest {}`, `sconce {}`, `lever {}`, `npc {}`, `door {}`, `sign {}` builders to `ZoneBuilder`. Each object has a position, type-specific properties (locked/unlocked for chest, lit/unlit for sconce), and an `onInteract {}` callback. The framework generates the interaction dispatch table in C. **Recommended for LotD quality.**
2. **Minimal escape**: Single `onInteract {}` with position-checking and flag-checking inside the callback. Loses type safety but keeps porting moving. **Anti-pattern per CONTEXT.md constraint.**

The floor objects system needs a full design + 1 framework plan. This blocks ALL 8 floor porting plans.

**Affected porting plans:** All 8 floor definitions. Every floor has chests, signs, and sconces. Floors 1, 5, 8 have NPCs.

## GAP-07: Exit Tile Transitions with Condition Gates

**Severity:** DEGRADING

**Original C pattern:** `floor1.c` `exits[]` defines bidirectional tile-based transitions. Some exits are blocked by doors which have lock states (normal door requiring key, next-level door requiring boss defeat):

```c
{ MAP_A, 12, 3, MAP_A, 10, 13, UP, EXIT_STAIRS, &bank_floor2 },   // To Floor 2
// Door definitions control exit access:
{ DOOR_3, MAP_A, 12, 3, DOOR_NEXT_LEVEL, false, false },           // locked until boss defeated
```

The transition from Floor 1 to Floor 2 goes through `DOOR_3` (DOOR_NEXT_LEVEL type), which is unlocked by `boss_victory()` via `open_door(DOOR_3)`.

**V2 current status:** PARTIAL — `ZoneBuilder.transition {}` supports directional transitions to other zones (`edge(NORTH)`, `to(floor2Ref)`). However, it has NO conditional gate mechanism. There is no `conditionFlag` or `requires(flagId)` on `TransitionBuilder`.

**Evidence:**
- `TransitionBuilder` fields: `targetZoneId`, `edge`, `entryPoint`, `entryX`, `entryY` — no condition/gate
- `ZoneTransitionIR` similarly lacks conditional field

**Recommended fix approach:**
- Add `condition(flagId: String)` to `TransitionBuilder` (mirrors `EncounterEntryBuilder.condition()`)
- The codegen checks the flag before executing the transition: `if (get_flag("bossDefeated")) { transition_to(floor2); }`
- If condition fails, the player is blocked (no movement, optional blocked sound)

**Affected porting plans:** Floor definitions (boss door on Floor 1, final stairs on Floors 1-7). Does not block if worked around with `onInteract {}` manually checking flags, but that violates zero-magic-strings constraint.

## GAP-08: Class-Based Ability Learning (Level-Gated Unlocks)

**Severity:** DEGRADING

**Original C pattern:** `player.c` `init_player()` always grants `ABILITY_0` (base attack). Abilities 1-5 are unlocked via `grant_ability(ABILITY_N)` at level milestones. The `player.ability_flags` bitmask tracks which abilities are unlocked:

```c
// player.c
void grant_ability(AbilityFlag flag) BANKED {
    player.ability_flags |= flag;
    set_player_abilities();
}
```

There is no explicit level→ability mapping in the C code — the grant happens via scripted events (level-up messages, reward scenes). But the intended game design has abilities unlock at levels: 1 (base), 5, 15, 35, 60, 90.

**V2 current status:** PARTIAL — `AbilityLearningBuilder` (in `gbkt-genre-rpg`) supports `autoLearn("ability", atLevel = 5)` which is exactly what is needed. However, it is NOT wired to `CharacterBuilder` — `CharacterDef` has no `learningConfig` field, and there is no `abilityLearning {}` block inside `character {}`.

**Evidence:**
- `CharacterBuilder` methods: `name()`, `stats()`, `level()`, `onLevelUp()` — no `learns {}` or `abilityLearning {}`
- `CharacterDef` fields: `id`, `name`, `stats`, `level`, `maxLevel`, `expCurve`, `onLevelUpOps` — no ability learning config
- `AbilityLearningBuilder` exists in `dsl/` but is only accessible via top-level `abilityLearning {}` game-level DSL, not per-character

**Recommended fix approach:**
- Add `learns(block: AbilityLearningBuilder.() -> Unit)` to `CharacterBuilder`
- Add `learningConfig: AbilityLearningConfig?` to `CharacterDef`
- The `CharacterBuilder.build()` passes `learningConfig` to `CharacterDef`
- Codegen emits the level-up unlock check in the character's level-up handler

**Affected porting plans:** Character class definitions (4 classes × 6 abilities each = 24 learning entries). Without this, abilities must be granted via manual flag checks in the level-up scene — still doable but loses declarative style.

## GAP-09: Monster AI Special Attacks (Type-Specific Behavior)

**Severity:** DEGRADING

**Original C pattern:** `player.c` handles per-monster-type special AI in `damage_monster()`:

```c
case MONSTER_DISPLACER_BEAST:
    monster->parameter--;
    if (monster->parameter != 0) break;
    // Phase at intervals — evasion
    monster->parameter = monster->exp_tier > B_TIER ? 2 : 4;
    return;  // "phased out" — damage cancelled

case MONSTER_DEATHKNIGHT:
    if (!(monster->parameter & DEATH_KNIGHT_REVIVE_USED) && d16() < 3) {
        monster->parameter |= DEATH_KNIGHT_REVIVE_USED;
        monster->target_hp = monster->max_hp / 4;
        // Revive once!
    }
```

These require per-monster-type parameter flags (`monster->parameter`, `DEATH_KNIGHT_REVIVE_USED`), persistent across turns in a combat.

**V2 current status:** PARTIAL — `BehaviorTreeBuilder` supports `hpBelow(25) { flee() }`, `cooldown("ability", turns = 3) {}`, `useAbility()`, `summon()`. However, it lacks:
1. **One-time trigger nodes** (fire once, set used flag) — needed for Death Knight revive
2. **Evasion/phase actions** (cancel incoming damage) — needed for Displacer Beast
3. **Custom parameter state per combat instance** — `monster->parameter` carries instance state

**Evidence:**
- `BehaviorTree.kt` action nodes: `UseAbility`, `BasicAttack`, `Flee`, `Summon`, `ChargeAction` — no `ReviveOnce`, `EvadeAttack`, `SetParameter`
- `MonsterDef` has no `parameters` or `instanceState` field
- `MonsterBuilder` has `cooldown(abilityId, turns)` but not one-time triggers

**Recommended fix approach:**
- Add `onHitReceived {}` hook to `MonsterBuilder` — fires when damage lands before it is applied. Allows returning `false` to cancel damage (Displacer Beast).
- Add a `oncePerBattle {}` behavior node — fires on first trigger, sets an internal flag to prevent repeat. (Death Knight revive)
- These are not strictly blocking — the AI can be expressed as `onLevelUp`-style scripting or a simpler approximation, but with loss of fidelity vs Original.

**Affected porting plans:** Monster definitions plan (12 monsters, 2-3 have special AI). Specific: Displacer Beast (phase evasion), Death Knight (revive), Will-o'-Wisp (phasing), Beholder (multi-attack), Dragon (final boss).

## GAP-11: Flag Typed Access API

**Severity:** DEGRADING

**Original C pattern:** `floor1.c` uses named CHEST_*, DOOR_*, SCONCE_*, LEVER_* constants (C preprocessor macros) as typed flag IDs.

**V2 current status:** PARTIAL — `flags {}` DSL registers named flags via `flag("metElder")`. However, there is NO `FlagRef` type for checked access. The `encounter { condition("bossDefeated") }` takes a raw `String`. The `gauge.onDepleted { setFlag("torchOut") }` documentation shows string-based `setFlag()`. There is no typed `FlagRef` that can be used as a variable in expressions.

**Evidence:**
- `EncounterEntryBuilder.condition(flagId: String)` — string
- `FlagPageBuilder.flag(flagName: String)` — registers name but returns nothing typed
- `flags("id") { page("story") { flag("metElder") } }` — no typed return value per flag

**Recommended fix approach:**
- `FlagPageBuilder.flag("name")` should return a `FlagRef`
- `FlagRef` would be usable in `whenever()` conditions, `condition()` gates, and `setFlag()`/`clearFlag()` calls
- Example: `val bossDefeated = flags { page("story") { flag("bossDefeated") } }.ref("bossDefeated")`
- Or simpler: `val bossDefeated by flag("bossDefeated")` delegate pattern
- **Zero magic strings constraint requires this before porting**

**Affected porting plans:** All floor definitions (chest flags, door flags, sconce flags, NPC visibility flags), story progression tracking.

## GAP-12: Window-Layer Text Animation System

**Severity:** COSMETIC

**Original C pattern:** `text_writer.c` implements character-by-character text animation with configurable speed, auto-paging (AUTO_PAGE_OFF/SLOW/MED/FAST), and VRAM-direct output to Window layer. Key features:
- `character_delay_frames` — configurable chars-per-frame delay
- `text_writer.auto_page` — AUTO_PAGE_OFF (wait for input), AUTO_PAGE_SLOW/MED/FAST
- `text_writer_clear()` — clears the text area before new page
- `\f` page break character support in string data

**V2 current status:** SUPPORTED — `DialogBuilder` has `textSpeed(speed: Int)` which maps to typewriter speed ("characters per frame"). `FontMode.FIXED_WIDTH` is supported. The dialog system renders on the Window layer (per CLAUDE.md: "All UI text renders on the GBDK window layer via `_win_*` helpers generated by `WindowTextCodegen`").

**Finding:** V2 dialog system covers the basic typewriter animation. However, auto-paging (the AUTO_PAGE_MED default where text pages advance automatically after a timer) is NOT explicitly surfaced in `DialogBuilder`. The Original uses different modes per scene (battle uses AUTO_PAGE_MED, exploration uses AUTO_PAGE_OFF with manual A-press advance).

**Recommended fix approach:**
- Add `autoPage(mode: AutoPageMode)` to `DialogBuilder` where `AutoPageMode` is `OFF`, `SLOW`, `MEDIUM`, `FAST`
- Default to `OFF` (wait for input) for exploration dialogs, `MEDIUM` for battle messages
- This is COSMETIC — the game works without it, but fidelity to Original timing differs

**Affected porting plans:** Battle scene text display, exploration sign/textbox display.

## GAP-13: Node.js Build Tools Coverage

**Severity:** DEGRADING

**Original tools directory contains 5 node.js build tools:**

| Tool | Purpose | V2 Coverage |
|------|---------|-------------|
| `png2bin` | Converts PNGs to 2BPP Game Boy tile format using StandardPalette (FFFFFF=0, AAAAAA=1, 555555=2, 000000=3) | COVERED — V2 Gradle plugin's `processAssets` task calls GBDK `png2asset` |
| `color2bin` | Converts PNG to binary color palette data (GBC palette extraction) | PARTIALLY COVERED — V2 has GBC palette support via `GbcColor` and `PaletteBuilder`. Binary export mechanism needs verification |
| `colorhex2c` | CLI helper that converts hex color strings to `RGB8(r, g, b)` C macro calls (utility/documentation aid) | NOT NEEDED — V2 uses `GbcColor(r, g, b)` DSL directly; no C macro generation needed |
| `strings2c` | Converts `assets/strings` JS namespace definitions to C string arrays with bank-based segmentation, special char substitution (`:arrow:`, `:regen:`, etc.), and parameter-aware `sprintf` format strings | PARTIAL — V2 uses GNU gettext PO files processed at codegen time. The special-char substitution (`:arrow:`, `:regen:` → custom font tile offsets) has NO equivalent in V2. This is a GAP. |
| `tables2c` | Generates `tables.h/c` from `assets/tables.csv`: `exp_by_level[99]`, `monster_exp[4][99]` (C/B/A/S tiers), `agl[4][99]`, `player_hp/sp/atk/def/dmg[4][99]`, `monster_hp/def/atk/dmg[4][99]`, `player_heal[4][99]` | PARTIALLY COVERED — see GAP-14 |

**Critical sub-gap: Special character font tile substitution**
`strings2c` expands `:regen:`, `:atk:`, `:arrow:`, `:elipsis:`, `:gil:` etc. to specific font tile offsets (0xFB, 0xDD, 0xA6, 0xE0, 0xA4). These appear in PO strings as visual symbols in menus. V2 has no equivalent substitution mechanism — the PO `msgstr` values would need raw hex codes or the framework needs to add substitution support.

**Recommended fix approach:**
- Add a `fontSymbols {}` DSL block in the localization config that maps symbol names to font tile offsets
- During PO processing, substitute `:symbol:` tokens with the configured tile offset
- This enables clean PO strings: `"Regen :regen: eff."` → renders with custom tile

**Affected porting plans:** String localization plan — all strings using special font tiles.

## GAP-14: tables.c Level-Scaled Data Tables

**Severity:** BLOCKING

**Original C pattern:** `tools/tables2c` reads `assets/tables.csv` and generates `res/tables/bank05.c` containing 48 lookup tables, each with 99 entries (one per level):

```
exp_by_level[99]            — EXP required to reach each level
monster_exp_c/b/a/s[99]    — EXP awarded by C/B/A/S tier monster at each level
agl_c/b/a/s[99]            — Agility values for C/B/A/S tier at each level
player_hp/sp/atk/def/dmg[4][99]  — Player stat tables by tier and level
monster_hp/def/atk/dmg[4][99]    — Monster stat tables by tier and level
player_heal[4][99]          — Heal values by tier and level
```

Total: ~4,752 uint16_t values = ~9.5KB of static lookup data in a dedicated bank (bank 5).

These tables are the backbone of the entire combat system — `get_player_hp(level, tier)` = `player_hp_tier[level]`. Without them, no stat scaling works.

**V2 current status:** PARTIAL — `ExpCurve` enum exists (`STANDARD`, `SLOW`, `FAST`) with defined growth formulas. The codegen in `RpgVisitor` likely generates exp threshold tables from the curve formula. However, there is NO mechanism for the 47 other tables (player/monster stat growth by level and tier). V2 monsters in `MonsterBuilder` take a single fixed stat block, not a level-tier lookup.

**Critical finding:** The V2 framework has NO concept of `PowerTier` (C/B/A/S) nor level-scaled stat lookup tables. The Original's entire combat difficulty system relies on these tables — a Level 1 C-tier Kobold has vastly different stats than a Level 9 B-tier Kobold. V2's `MonsterDef.stats` is a single fixed `CombatStats` with no scaling.

**Evidence:**
- `MonsterBuilder.stats { hp(15); atk(6) }` — single fixed value, no scaling
- `CharacterBuilder` similar — fixed stats, `expCurve` only affects EXP threshold not stat growth
- `tables.csv` columns: 48 columns × 99 rows = complete stat scaling system for 4-tier × 99-level game

**Recommended fix approach:** Two options:
1. **Port tables.c as data** — Include the 9.5KB tables.c as a static data file in the port (not generated by V2 DSL). The port's Kotlin code calls wrapper functions that match the Original's API. This is a workaround (not pure DSL) but feasible given the data is stable game-design data, not implementation.
2. **Add tier-scaled stat growth to framework** — Add `MonsterTierScaling { tier(C_TIER) { stats { hp = 15 } }; tier(B_TIER) { stats { hp = 25 } } }` + level interpolation. This is a significant framework feature.

**For LotD port:** Option 1 is pragmatic. The tables are the Original author's game balance decisions — treating them as game data (not framework features) is appropriate. Add `ExpCurve.CUSTOM(tableData)` or allow raw data arrays in the DSL for level-based lookups.

**BLOCKING because:** Without combat stat scaling, all 12 monsters and 4 character classes will have wrong stats at non-base levels. Every combat encounter will be wrong.

**Affected porting plans:** Monster definitions, character definitions, combat system, all 8 floors (encounter generation uses tier to set monster stats).
