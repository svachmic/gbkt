## Decisions Made

1. **Data class containers not singleton objects:** The plan suggested `object FighterAbilities` but the StatusEffects.kt established pattern uses data classes returned from `GameBuilder` extension functions. AbilityRef instances are only created during the builder call — singletons with `lateinit var` would require reflection to assign. Using data classes (like `LabyrinthFighterAbilities`) matches the existing pattern exactly.

2. **appliesEffect() uses StatusEffectRef.id:** The `AbilityBuilder.appliesEffect()` takes a `String` (effect ID), not a `StatusEffectRef`. Using `statusEffects.blind.id` passes the typed ref's ID as a string — zero-magic-string access without requiring API changes.

3. **Trip mechanics mapped to paralyzed:** Original's `trip_turns` (prone skip-turn) and Monk's `open_palm` trip have no direct DSL equivalent. The `paralyzed` status effect (forced turn-skip) is the closest semantic match. Trip Attack applies it at 100% on hit; Open Palm at 30%.

4. **Indomitable/Diamond Body all-resist mapped to defUp:** Both abilities set `player.aspect_resist` to resist all or physical+magical damage. No DSL equivalent for per-aspect resistance — `defUp` is the closest buff approximation (increases defense stat).

5. **Sleetstorm field effect approximated as aglDown:** `SPECIAL_SLEET_STORM` flag causes per-turn ice-slip chance in the Original. No DSL equivalent for persistent field effects — `aglDown` on all enemies (slows turn order) is the closest approximation.

6. **Wild Magic modeled as confused:** The d8 randomness has 8 outcomes; confused (25% of rolls = outcomes 4-5) at 50% chance represents the chaotic behavior intent. The combat system plan can implement full random dispatch.

7. **Still Mind has no appliesEffect:** It removes all active debuffs. The `appliesEffect()` DSL applies effects, not removes them. Documented in KDoc; actual debuff-clearing behavior wired in combat system plan.

## Deviations from Plan

None — plan executed with one intentional structural adaptation:

### Structural Adaptation: Data Classes vs Object Singletons

**Plan specified:** `object FighterAbilities` with `lateinit var` fields and `all: MutableList<AbilityRef>`.

**Implemented as:** `data class LabyrinthFighterAbilities` with constructor parameters and a computed `val all` getter.

**Reason:** The `AbilityRef` instances require a `GameBuilder` context to be created (they call `GameBuilder.ability()` internally). Singleton objects can't hold references that are only available during DSL construction without reflection or mutable global state. The data class pattern (same as `LabyrinthStatusEffects`, `LabyrinthItems`) is established by plan 06 and is idiomatic.

**Impact:** Zero — downstream plans receive the same typed refs via `abilities.fighter.secondWind` syntax. The aggregator pattern (`LabyrinthAbilities.all`) is equivalent to the plan's proposed `Abilities.all`.
