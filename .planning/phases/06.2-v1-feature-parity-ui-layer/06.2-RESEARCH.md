## Summary

Phase 06.2 ports the entire V1 UI subsystem (dialog boxes, choice menus, status bars, HUD elements, and screen text helpers) to the V2 pipeline using typed DSL builders, new IR nodes, and C AST codegen with zero CRawCode. The V2 codebase already has minimal stubs for `ShowDialog` and `ShowMenu` as `ScriptOp` nodes with basic codegen in `GBDKPipelineV2.buildDialogHelpers()` and `buildMenuHelpers()`. These stubs use `gotoxy()/printf()` on the background tile layer — the wrong approach. The new implementation must use GBDK's window layer (`move_win()`, `SHOW_WIN`, `HIDE_WIN`, `set_win_tiles()`) exclusively for all UI text, consistent with the CLAUDE.md note: "Zero `gotoxy`/`printf` calls remain in UI code."

The phase splits into four tracks: (1) Dialog system — new `dialog()` GameBuilder function producing a `DialogHandle` with `.say()` and `.choice()` ops, backed by new `DialogDef` IR in `GameIR` and new `DialogShow`/`DialogSay`/`DialogChoice` ScriptOps replacing the current stub `ShowDialog`. (2) Menu system — new `menu()` GameBuilder function producing a `MenuHandle` with typed layout/cursor/SFX config, backed by new `MenuDef` IR replacing the current stub `ShowMenu`. (3) HUD/StatusBar — new `hud()` GameBuilder function producing `HudPanel` with `bar()`, `number()`, `icons()` sub-builders, change-detection codegen, and per-frame update dispatch. (4) Text rendering — extend `ScriptBuilder` with `printCentered()`, `printAligned()`, `printAt()`, `clearRegion()` and clean up `screen.clear()` / `screen.fill()` as typed ScriptOps instead of `RawOp` strings.

**Primary recommendation:** Build new IR node types in `gbkt-ir`, new DSL builders in `gbkt-lang`, and new codegen visitors/pipeline methods in `gbkt-backend-gbdk`. Replace `ShowDialog`/`ShowMenu` ScriptOp stubs with the richer IR hierarchy. Follow the exact same patterns established by Phase 06.1 (camera, save, movement, physics).

## Architecture Patterns

### Recommended Phase Structure

Based on the Phase 06.1 pattern (8 discrete plans), Phase 06.2 should decompose as:

```
Plan 01: Dialog IR + DSL (DialogDef, DialogHandle, DialogBuilder, say(), choice())
Plan 02: Dialog Codegen (GBDKPipelineV2.buildDialogFunction, ScriptOpVisitor updates)
Plan 03: Menu IR + DSL (MenuDef, MenuHandle, MenuBuilder, layouts, cursor, SFX hooks)
Plan 04: Menu Codegen (buildMenuFunction rewrite, parent/child stack, grid menus)
Plan 05: HUD IR + DSL (HudPanel, bar(), number(), icons(), Anchor enum, change-detection)
Plan 06: HUD Codegen (buildHudUpdateFunction, per-frame dispatch integration)
Plan 07: Text Helper Extensions (printCentered, printAligned, clearRegion as typed IR)
Plan 08: Tests + CRawCode audit (unit + integration tests for all UI features)
```

### Pattern 1: New IR Node in `gbkt-ir` ScriptOp.kt

The existing ScriptOp.kt in `gbkt-ir` already has `ShowDialog` and `ShowMenu` as minimal stubs. The plan is to **replace** these with richer IR nodes rather than adding parallel nodes. Context decision: "Clean break from V1 — old DSL functions removed."

Current stub (to be replaced):
```kotlin
// gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/ScriptOp.kt

data class ShowDialog(
    val lines: List<String>,
    override val sourceLocation: SourceLocation? = null,
) : ScriptOp {
    override fun <T> accept(visitor: ScriptOpVisitorI<T>): T = visitor.visitShowDialog(this)
}
```

New hierarchy (recommended shape):
```kotlin
// Replace ShowDialog with:
data class DialogShow(
    val dialogId: String,            // references DialogDef.id in GameIR.dialogs
    override val sourceLocation: SourceLocation? = null,
) : ScriptOp {
    override fun <T> accept(visitor: ScriptOpVisitorI<T>): T = visitor.visitDialogShow(this)
}

data class DialogSay(
    val dialogId: String,
    val segments: List<DialogSegment>, // String literals and Expr references interleaved
    override val sourceLocation: SourceLocation? = null,
) : ScriptOp {
    override fun <T> accept(visitor: ScriptOpVisitorI<T>): T = visitor.visitDialogSay(this)
}

sealed interface DialogSegment
data class DialogTextSegment(val text: String) : DialogSegment
data class DialogExprSegment(val expr: Expr) : DialogSegment

data class DialogChoice(
    val dialogId: String,
    val options: List<DialogOption>,
    override val sourceLocation: SourceLocation? = null,
) : ScriptOp {
    override fun <T> accept(visitor: ScriptOpVisitorI<T>): T = visitor.visitDialogChoice(this)
}

data class DialogOption(val label: String, val body: List<ScriptOp>)
```

**CRITICAL:** Adding new ScriptOp subtypes requires updating `ScriptOpVisitorI` (in `gbkt-ir`), `ScriptOpVisitor` (in backend), and `ScriptOpInterpreter` (in core) with new `visit*` methods. The interpreter gets no-op stubs as the hardware-rendering ops it cannot simulate.

### Pattern 2: New `DialogDef` and `MenuDef` in `GameIR`

Following the pattern of `SoundEffectDef` (added to `GameIR.soundEffects`), add:

```kotlin
// In GameIR.kt — new fields:
val dialogs: List<DialogDef> = emptyList(),
val menus: List<MenuDef> = emptyList(),
val huds: List<HudDef> = emptyList(),
```

`DialogDef` carries the static configuration (speaker, textSpeed, border style, portrait, box position/size). `MenuDef` carries layout, cursor config, SFX hooks, parent reference, rendering layer. `HudDef` carries the HUD panel's elements (bars, numbers, icons) and anchor.

### Pattern 3: DSL Builder → Handle Pattern (established in 06.1)

The `CameraBuilder` / `SaveDataBuilder` / `ExplorationBuilder` pattern in `SystemBuilders.kt` is the template:

```kotlin
// In GameBuilder.kt — add:
fun dialog(id: String, block: DialogBuilder.() -> Unit): DialogHandle {
    val builder = DialogBuilder(id)
    ScriptBuilderContext.with(builder) { builder.block() }
    val def = builder.build()
    // register in dialogs list
    dialogs += def
    return DialogHandle(id)
}

fun menu(id: String, block: MenuBuilder.() -> Unit): MenuHandle {
    // same pattern
}

fun hud(id: String, block: HudBuilder.() -> Unit): HudPanel {
    // same pattern
}
```

The returned handle types (`DialogHandle`, `MenuHandle`, `HudPanel`) expose operations that emit `ScriptOp` nodes when called inside scene builders. Example:

```kotlin
// DialogHandle.say() emits DialogSay into active ScriptBuilder
fun DialogHandle.say(vararg segments: Any) {
    val scriptBuilder = ScriptBuilderContext.current ?: error("say() must be called inside a script block")
    val parsed = segments.map { seg ->
        when (seg) {
            is String -> DialogTextSegment(seg)
            is Expr -> DialogExprSegment(seg)
            else -> error("say() segments must be String or Expr")
        }
    }
    scriptBuilder.ops += DialogSay(id, parsed, sourceLocation = captureV2Location())
}
```

This mirrors `ActorPropertyRef` operator extensions and `AssignableVar` from Phase 05.05.2/05.05.3.

### Pattern 4: Codegen in GBDKPipelineV2 — window layer C

The existing `buildDialogHelpers()` uses `gotoxy()/printf()` which writes to the background tile layer. The new codegen must use the GBDK window layer. Key GBDK window-layer functions:

```c
// GBDK window layer API (from <gb/gb.h>):
move_win(x, y);           // Position window at pixel coordinates (7,y for Game Boy hardware)
SHOW_WIN;                 // Enable window display (GBDK macro → hardware register write)
HIDE_WIN;                 // Disable window display (GBDK macro)
set_win_tiles(x, y, w, h, tiles); // Write tile data to window VRAM
// For text, GBDK's window uses same console functions but on window layer:
// gotoxy() and printf() work on whichever layer is active via DISPLAY context
```

**CRITICAL FINDING:** `SHOW_WIN` and `HIDE_WIN` are C preprocessor macros that expand to hardware register writes. These **must remain `CRawCode`** — they cannot be expressed as typed C AST. This is already documented in the STATE.md decisions: "GBDK hardware macros (ENABLE_RAM, DISABLE_RAM, SCX_REG, SCY_REG, SHOW_WIN, HIDE_WIN, DISPLAY_ON, SHOW_SPRITES) kept as CRawCode."

The dialog box rendering state machine:
1. `buildDialogFunction(dialogDef)` — generates `dialog_<id>_show()` in HOME bank
2. Inside: position window (`move_win`), show window (`SHOW_WIN`, CRawCode), draw border tiles, draw speaker name, typewriter loop for text, wait for A-button press, hide window (`HIDE_WIN`, CRawCode)
3. `buildChoiceFunction(dialogDef)` — generates `dialog_<id>_choice()` returning selected index
4. Per-menu: `buildMenuFunction(menuDef)` — replaces the existing stub

### Pattern 5: HUD — Change-Detection via Global State Vars

The HUD "on-change update strategy" requires tracking previous values. Codegen generates:
- `_hud_<id>_<element>_prev` global `UINT8` variables initialized to 0xFF (sentinel = "force redraw")
- `update_hud_<id>()` function: for each element, compare current vs prev, redraw only if changed
- `buildHudUpdateCalls()` in `GBDKPipelineV2` injects `update_hud_<id>()` call at start of each scene frame function (like `addMovementAndAnimationCalls()` does for movement/animation)

### Pattern 6: Text Helpers as Typed ScriptOps (not RawOp)

Currently `clear()` emits `RawOp("cls();")`. The V2 approach should use new ScriptOps:

```kotlin
// New ScriptOps (replacing RawOp string patterns):
data class ScreenClear(override val sourceLocation: SourceLocation? = null) : ScriptOp
data class ScreenFill(val tile: Int, override val sourceLocation: SourceLocation? = null) : ScriptOp
data class PrintCentered(val text: String, val row: Int, override val sourceLocation: SourceLocation? = null) : ScriptOp
data class PrintAligned(val text: String, val row: Int, val alignment: TextAlignment, ...) : ScriptOp
data class ClearRegion(val x: Int, val y: Int, val w: Int, val h: Int, ...) : ScriptOp
```

The `ScriptBuilder` extension function `printCentered("TEXT") at 6` uses Kotlin's `at` infix via a `PrintCenteredBuilder`:

```kotlin
fun ScriptBuilder.printCentered(text: String): PrintCenteredBuilder = PrintCenteredBuilder(text, this)

class PrintCenteredBuilder(val text: String, val builder: ScriptBuilder) {
    infix fun at(row: Int) { builder.ops += PrintCentered(text, row) }
}
```

**Note:** The `at` pattern is already used in the Gradle test fixtures (`printCentered("COMPLEX GAME") at 6`) — research confirms this is the expected API.

### Anti-Patterns to Avoid

- **Using `gotoxy()/printf()` for any UI text**: This writes to the background tile layer and corrupts tilemap graphics. All UI text goes through the window layer (`_win_*` helpers).
- **Building new ScriptOp types without updating ScriptOpVisitorI**: The interface must be updated for every new ScriptOp, or the visitor dispatch breaks.
- **New IR types in wrong module**: Dialog/Menu/HUD IR goes in `gbkt-ir` (ScriptOp.kt for ops, a new UITypes.kt for `DialogDef`/`MenuDef`/`HudDef`). DSL builders go in `gbkt-lang`.
- **Not updating `ScriptOpInterpreter.executeOp()`**: Every new ScriptOp type needs a branch (even if it's a no-op stub). The `else -> throw UnsupportedOperationException` will fail at test time otherwise.
- **CRawCode for dialog text rendering logic**: Only `SHOW_WIN`/`HIDE_WIN` macros stay as CRawCode. All control flow (typewriter loop, cursor navigation, button wait) must use typed C AST.

## Common Pitfalls

### Pitfall 1: Wrong Layer for UI Text
**What goes wrong:** Using `gotoxy()/printf()` or `cls()` for dialog/menu text corrupts the background tilemap.
**Why it happens:** The existing stub `buildDialogHelpers()` already does this — it's the V1 mistake being replicated.
**How to avoid:** All dialog/menu text generation uses `move_win()`, `SHOW_WIN`/`HIDE_WIN`, and window-layer tile writes. The codegen must NOT emit `printf()` for UI text rendering.
**Warning signs:** `gotoxy` appearing in `buildDialogFunction()` output.

### Pitfall 2: Forgetting to Update ScriptOpVisitorI
**What goes wrong:** Adding new ScriptOp subtype without adding abstract method to `ScriptOpVisitorI` causes compilation error in the visitor interface.
**Why it happens:** `ScriptOpVisitorI` in `gbkt-ir` defines the visitor contract — all subtypes must have a corresponding method.
**How to avoid:** For every new `ScriptOp` data class, add `fun visitXxx(op: Xxx): T` to `ScriptOpVisitorI`, implement it in `ScriptOpVisitor` (backend), and add a no-op stub in `ScriptOpInterpreter` (core).

### Pitfall 3: Cross-Module Smart Cast Issue
**What goes wrong:** Kotlin cannot smart cast public API properties from different modules.
**Why it happens:** Documented multiple times in STATE.md decisions (06.1-01, 06.1-03).
**How to avoid:** Capture nullable fields into local vals before branching: `val style = menuDef.layout; if (style == MenuLayout.GRID) { ... }`.

### Pitfall 4: HUD Update Every Frame vs On-Change
**What goes wrong:** Calling `update_hud_<id>()` generates VRAM writes every frame — expensive on Game Boy.
**Why it happens:** Naive implementation without change detection.
**How to avoid:** HUD update function compares current value against `_hud_<id>_<element>_prev` variable. Only writes window tiles when value changes. Initialize `_prev` to `0xFF` (sentinel) so first frame always draws.

### Pitfall 5: Menu Parent/Child Stack as CRawCode
**What goes wrong:** Implementing menu stack as global function pointer or dynamic dispatch → CRawCode.
**Why it happens:** C89 has no closures; naive approach uses function pointers.
**How to avoid:** Static parent menu ID stored in `MenuDef.parentId: String?`. Codegen for `show_menu_<id>()` checks B-button: if `parentId != null`, calls `show_menu_<parentId>()` directly. Static call graph, zero function pointers, no CRawCode.

### Pitfall 6: Variable Interpolation in say() — Type Safety
**What goes wrong:** `say("Score: ", score)` where `score` is an `AssignableVar<U8>` — need to convert to `Expr`.
**Why it happens:** Kotlin overload resolution between `String` and `Expr` segments in vararg `Any`.
**How to avoid:** `DialogHandle.say(vararg segments: Any)` pattern with `when(seg)` checking for String vs Expr vs `AssignableVar<*>` (which exposes `.ir` property). Document that only `String` and `Expr` (including `AssignableVar` which implements `Expr`) are valid.

### Pitfall 7: Border Tile Graphics
**What goes wrong:** Dialog border requires tile graphics (corner, horizontal, vertical tiles) — these must be loaded into window VRAM.
**Why it happens:** Game Boy window layer uses tile indices, not pixel drawing commands.
**How to avoid:** NONE border style (no border) is the default DMG-compatible option. SINGLE/DOUBLE borders use font tile indices that GBDK provides in its built-in font. CUSTOM border requires an asset reference. Start with NONE as implemented baseline; other styles add complexity.

## Open Questions

1. **Border tile assets for SINGLE/DOUBLE border styles**
   - What we know: NONE border style needs no tiles. SINGLE/DOUBLE need tile graphics loaded into window VRAM tile slots.
   - What's unclear: Does GBDK's built-in font tile set include box-drawing characters? Or do border tiles need a separate asset?
   - Recommendation: Implement NONE border style first (sufficient for most games). Document SINGLE/DOUBLE as "requires border tileset asset" — defer to a future phase or implement as a stretch goal.

2. **`printCentered("TEXT") at 6` infix syntax**
   - What we know: The Gradle plugin test fixtures use this exact syntax. No implementation exists.
   - What's unclear: Whether to use a `PrintCenteredBuilder` helper class with `infix fun at(row: Int)`, or a simpler `printCentered(text, row)` two-argument function.
   - Recommendation: Use the `PrintCenteredBuilder` helper to preserve the `at` infix for DSL ergonomics. It matches the established DSL style.

3. **`screen.clear()`, `screen.fill()`, `screen.showSprites()`, `screen.hideSprites()` on the `SceneBuilder`**
   - What we know: The Gradle integration test uses `screen.clear()` syntax. This isn't currently implemented — `clear()` is a bare `ScriptBuilder` function call, not a `screen.clear()` method.
   - What's unclear: Whether `screen` should be a `ScreenRef` object on `ScriptBuilder` or a top-level object.
   - Recommendation: Add a `screen` property of type `ScreenRef` to `ScriptBuilder` that delegates to the same `RawOp`/`ScriptOp` emitters. This is a DSL ergonomics addition that matches what the Gradle test fixture expects.

4. **Replacement or coexistence of `ShowDialog`/`ShowMenu` ScriptOps**
   - What we know: CONTEXT.md says "clean break from V1 — old DSL functions removed." `ShowDialog` and `ShowMenu` are referenced in `ScriptOpVisitorI` and all existing visitor implementations.
   - What's unclear: Whether to rename in-place (update `ShowDialog` struct body) or add new types and remove old.
   - Recommendation: Replace `ShowDialog` → `DialogSay` (simple case) and add `DialogShow`/`DialogChoice` as new types. Remove `ShowMenu` and replace with `MenuShow`/`MenuHide`/`MenuTick` as typed ops. Update `ScriptOpVisitorI` to add new methods and remove old ones. This is a breaking change acceptable per CONTEXT.md.
