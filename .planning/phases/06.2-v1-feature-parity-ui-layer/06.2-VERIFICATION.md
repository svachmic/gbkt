## Anti-Patterns Found

| File | Pattern | Severity | Impact |
|------|---------|----------|--------|
| None found | — | — | — |

**CRawCode Audit Result:** Only approved CRawCode present in UI codegen:
1. `SHOW_WIN` / `HIDE_WIN` — GBDK hardware macros (approved exception, documented in CLAUDE.md)
2. VWF pixel-level bit-manipulation (`tile_buf`, shift/OR composition) — C89 unsafe pointer arithmetic required for VWF rendering; cannot be expressed in typed C AST
3. Dynamic menu inline loops (`_mi` variable in for-loop string for InventoryDataSource/ArrayDataSource) — dynamic variable naming requires CRawCode
4. Horizontal cursor erase in background-layer path — `gotoxy`/`printf` (approved: only fires when `renderOnWindow=false`)
5. Sprite cursor `move_sprite` in navigation handlers — GBDK function call with computed pixel coordinates via string interpolation

All CRawCode instances are within the approved exception categories. Zero occurrences of unapproved CRawCode in dialog/menu/HUD logic.

**ShowDialog/ShowMenu Audit Result:** Zero references in source files (IR, DSL, core, backend modules). KDoc references in ScriptOpVisitor updated to use current type names (DialogSay, MenuShow).

## Human Verification Required

None. All phase success criteria are verifiable programmatically through code inspection and test execution.

Items that would benefit from eventual manual testing (not blocking this phase):

1. **VWF rendering quality** — Visual appearance of variable-width fonts requires viewing on hardware or emulator. The codegen logic is correct per test assertions, but pixel-level font quality is a human judgment.
   - Test: Run a game with `fontMode(FontMode.VARIABLE_WIDTH)` in mGBA and inspect text legibility.
   - Why human: Cannot assess font aesthetic quality from generated C code alone.

2. **Dialog typewriter feel at runtime** — The `textSpeed` codegen is correct (`delay_frames(N)` calls), but the subjective feel of different speed values requires gameplay testing.

3. **Sprite cursor visual accuracy** — The cursor sprite pixel positioning math (`(x * 8 + 8, y * 8 + 16)` OAM offsets) is correct per GBDK conventions, but alignment in actual gameplay depends on specific sprite/tileset combinations.
