## Summary

Phase 13.5 adds three typed framework primitives and migrates two carrier examples. The codebase scout confirms all three patterns exist exactly where SPEC.md cites them. All referenced hook points are live and at the exact cited lines.

**Four researcher-verify items are resolved below.** The most critical finding is a **D-07 predicate gap**: the `bank > 0` predicate in D-07 is too broad — it would cause pong/breakout (ROM_ONLY, bank=1) to gain auto-emitted `*_exit` functions, violating the "no C growth for single-bank games" gate. The correct predicate is `cartridge.maxRomBanks > 2` (genuinely uses MBC). A second critical finding is that `screen()` must be a **SceneBuilder-level primitive** (parallel to `zone()`), not a ScriptBuilder `enter {}` op, because it must both register a synthetic ZoneIR with GameBuilder AND add to SceneIR.zoneRefs — neither of which is accessible from ScriptBuilder alone.

**Primary recommendation:** Plan wave sequencing: (1) `BindCurrentLevel` IR+DSL+visitor+ScriptOpInterpreter → RED tests → fix → GREEN; (2) auto-`*_exit` predicate+hook+trampoline-pairing → RED test → fix → GREEN; (3) `screen()` SceneBuilder primitive + synthetic ZoneIR + GameBuilder registration → RED tests → fix → GREEN; (4) Banks.kt migration; (5) PlatformerTemplate + PlatformerExtensions migration; (6) regression sweep + visual evidence capture; (7) DSL_REFERENCE.md docs.

## Researcher-Verify Findings

### D-04 — `screen()` Internal Zone-ID Synthesis + Asset Discovery

**VERIFIED by codebase inspection.** [VERIFIED: codebase grep]

**Finding:** `screen()` MUST be implemented at the `SceneBuilder` level (parallel to `zone()`), NOT inside `enter { }` as a ScriptBuilder op. The reason:

1. `ScriptBuilder` does not hold a reference to `SceneBuilder`.
2. `SceneIR.zoneRefs` is set by `SceneBuilder.build()` from `SceneBuilder.zoneRefs`; a ScriptBuilder op cannot add to it.
3. `screen()` must both register a synthetic `ZoneIR` with `GameBuilder` AND add to `SceneIR.zoneRefs` so `SceneVisitor` emits the zone-load prelude.

**Concrete mechanism:**

```kotlin
// gbkt-lang/SceneBuilder.kt — new method
fun screen(assetRef: AssetRef) {
    val syntheticId = "_screen_${id}"     // deterministic from scene id
    val syntheticZone = ZoneIR(
        id = syntheticId,
        name = syntheticId,
        tilesetPath = assetRef.path,
        // mapWidth/mapHeight = null → ConvertZoneTilesetsTask derives from PNG IHDR
        // (same as titleZone/nextLevelZone after 13.4 removed explicit size())
    )
    GameBuilderContext.current?.registerZone(syntheticZone)
        ?: error("screen() must be called inside a game {} block")
    require(zoneRefs.isEmpty()) {
        "scene '$id' already binds a zone; multi-zone-per-scene deferred"
    }
    zoneRefs += syntheticId
    // D-05/D-06 superset ops (hide sprites, scroll reset, center-placement)
    // are injected by SceneVisitor via the zone-load prepend path — no extra
    // ScriptOp injection needed here IF the centered-card logic is extended
    // into SceneVisitor for screen-zones. Otherwise: add a ScreenCenterOp
    // to enterOps that ScriptOpVisitor emits as the hide+clear+center sequence.
}
```

**ID synthesis rule:** `_screen_${sceneId}` (e.g., `_screen_title`, `_screen_nextLevelScene`). The leading underscore distinguishes it from user-declared zones. This ID must NOT collide with any user-visible zone name since users cannot declare zones with leading underscores via the `by zone` delegate (which uses the Kotlin property name without prefix).

**Metadata channel:** The synthetic `ZoneIR` is registered via `GameBuilder.registerZone()` exactly like a normal zone. `GBDKPipelineV2.buildMetadataFile()` loops `gameIR.zones` (line 316 — `for (zone in gameIR.zones)`) and emits every zone with a `tilesetPath`. The synthetic zone has `tilesetPath = assetRef.path` so it appears in `zoneTilesets[]` automatically. No new metadata field or task wiring needed.

**D-05 centering — two options for the planner:**
- Option A: Keep `screen()` as a pure zone-load (SceneVisitor emits the tilemap at (0,0) per existing path); add a new `ScreenCenterOp` ScriptOp that `ScriptOpVisitor` lowers to the hide+clear+center sequence; `SceneBuilder.screen()` appends `ScreenCenterOp` to enterOps.
- Option B: Introduce a flag in `ZoneIR` or `SceneIR` (`screenMode: Boolean`) that `SceneVisitor` detects to emit the superset (hide+clear+center) instead of the (0,0) tilemap-place. SceneVisitor already has the `sceneHasCardOverdraw` detection heuristic (line 268) — a `screenMode` flag is cleaner and more explicit.

**Recommendation:** Option B (a `screenMode: Boolean` flag in `ZoneIR` or `SceneIR`), because SceneVisitor already centralizes the zone-load logic and has the `sceneHasCardOverdraw` heuristic. Adding a first-class `screenMode` flag is cleaner than a synthetic ScriptOp. The flag gates: (1) skip the (0,0) tilemap-place, (2) prepend `hide_sprites_range(0u, MAX_HARDWARE_SPRITES)`, (3) prepend `move_bkg(0u, 0u)`, (4) emit centered `fill_bkg_rect` + `_bkg_tiles_load_banked` at computed center coords. This matches what `LevelCardSceneBuilder.materialize()` does today via cEmit (lines 857-900).

**`buildSetupCurrentLevelFunctionIfNeeded` filter:** Currently filters out zones where `idLower.contains("title") || contains("nextlevel") || contains("next_level")` (line 2438-2440). The synthesized `_screen_title` zone ID contains "title" — it would be filtered correctly. `_screen_nextLevelScene` contains "nextlevel" — also filtered. This is intentional and matches today's behavior.

### D-06/D-07 — bankSlot Audit + Title-Enter Byte Budget

**VERIFIED by codebase inspection.** [VERIFIED: codebase grep]

#### Critical Finding: D-07 Predicate `bank > 0` Is Too Broad

**The predicate `scene.bankSlot?.bank != null && scene.bankSlot.bank > 0` WILL cause pong and breakout to gain new `*_exit` functions, violating the "no C growth for single-bank games" acceptance gate.**

Evidence:
- Pong: `Cartridge.ROM_ONLY`, 3 scenes (title, game, gameover), NO exit blocks anywhere [VERIFIED: Banks.kt line 30; pong grep of `exit {` returns empty]
- Breakout: `Cartridge.ROM_ONLY`, 4 scenes (title, game, gameover, win), NO exit blocks [VERIFIED: BreakoutV2.kt grep]
- `ROM_ONLY` has `maxRomBanks = 2` (only banks 0 and 1) [VERIFIED: Types.kt:148]
- `BankingAnalysisPass` FFD packer places ALL pong/breakout scenes into bank 1 (the only non-HOME bank available) [VERIFIED: BankingAnalysisPass.kt:150-168 — FFD packs into banks 1..maxBanks-1; with ROM_ONLY only bank 1 is available]
- Therefore pong/breakout scenes have `bankSlot.bank = 1 > 0` → D-07's current predicate fires → auto-emits `title_exit`, `game_exit`, etc. for pong/breakout → violation

**Correct predicate:** The auto-`*_exit` synthesis must be gated on whether the game actually uses MBC (multiple switchable banks). The discriminator is `gameIR.config.cartridge.maxRomBanks > 2`:
- `ROM_ONLY`: maxRomBanks = 2 → no auto-exit (bank 1 is just the single non-HOME bank, no MBC switching)
- `MBC1`: maxRomBanks = 32 → auto-exit enabled
- `MBC5_RAM_BATTERY` (Banks.kt): maxRomBanks = 256 → auto-exit enabled

**Where to place the check:** `SceneVisitor.visit()` currently does NOT receive `GameIR.config`. The `SceneVisitor.visit()` signature is `(scene, actors, variables, zoneBankAllocation, zones, gbcTarget)`. The check can be threaded as either:
- A new `isMbcGame: Boolean` parameter to `SceneVisitor.visit()` (additive, clean)
- Moved entirely to `GBDKPipelineV2.buildSceneFile()` which has `GameIR` access — the pipeline can call `SceneVisitor.visit()` without the auto-emit, then append the empty exit function separately

**Recommendation:** Add `isMbcGame: Boolean = false` to `SceneVisitor.visit()` (additive, backward-compat default = false, no regression). The call site in `GBDKPipelineV2.buildSceneFile()` passes `gameIR.config.cartridge.maxRomBanks > 2`.

#### Trampoline Pairing

`GBDKPipelineV2.buildTrampolinesForScene()` (line 3187) currently only emits `*_exit_trampoline` when `scene.exitOps.isNotEmpty()`. When Req #15 auto-synthesizes an empty `play_exit`, the trampoline must also be emitted. Both gates must use the same predicate. The `navigate_to_scene()` builder (line 4563) also filters `it.exitOps.isNotEmpty()` — this too must include the auto-synthesized exit case.

**Additional complexity:** `navigate_to_scene` must include an exit case for `play_exit_trampoline` even when `exitOps` is empty. A flag on `SceneIR` (e.g., `autoEmitExit: Boolean`) set by the SceneVisitor or pipeline can track which scenes got the auto-exit, so downstream pipeline methods can query it without re-deriving the predicate.

#### pong/breakout null-bankSlot check

Banks.kt uses `MBC5_RAM_BATTERY` (maxRomBanks = 256). The `play` scene in Banks.kt has 3 non-trivial op blocks (enter: `showSprites`, frame: 2 wheneverBlocks, exit: `hideSprites`). `BankingAnalysisPass` assigns `bankSlot.bank = 1` to the play scene (FFD bin-packing with 3 scenes → all in bank 1 since packing starts at bank 1). So `play.bankSlot.bank = 1 > 0` AND `cartridge.maxRomBanks = 256 > 2` → auto-emit fires. [ASSUMED based on FFD logic; exact bank assignment depends on estimated byte counts, but 3 small scenes all fit in bank 1]

No active example relies on an auto-`*_exit` for a `null`-bankSlot (BANKED-by-default) scene. The null case already produces `isBanked = true` for backward compat; the auto-emit must require a non-null bankSlot (so tests that pass no bankSlot are unaffected). [VERIFIED: SceneVisitor.kt:104-105 — `val sceneBanked = sceneBank == null || sceneBank > 0`]

#### Title-Enter Byte Budget

The title scene currently binds `titleZone` via `zone(titleZone)` at scene body level. `SceneVisitor` emits the zone-load prelude (set_bkg_data + _bkg_tiles_load_banked + DISPLAY_ON) prepended before any user enterOps. The title has no user enterOps.

After migration to `screen(asset("graphics/title-screen.png"))`:
- The zone-load prelude is identical (same PNG, same generated symbols)
- D-05/D-06 superset adds: `hide_sprites_range(0u, MAX_HARDWARE_SPRITES)` + `move_bkg(0u, 0u)` + centered `fill_bkg_rect` + centered `_bkg_tiles_load_banked` + `DISPLAY_ON`
- The non-centered `_bkg_tiles_load_banked` at (0,0) from the zone-load prelude would be SKIPPED (using the `sceneHasCardOverdraw`-equivalent signal or the `screenMode` flag)

Net C shape change for title_enter:
- REMOVE: `_bkg_tiles_load_banked(bank, 0, 0, W, H, tilemap)` at (0,0)
- ADD: `hide_sprites_range(0u, MAX_HARDWARE_SPRITES)` + `move_bkg(0u, 0u)` + `fill_bkg_rect(0u, 0u, 32u, 32u, 0u)` + `_bkg_tiles_load_banked(bank, col, row, W, H, tilemap)` at centered coords
- Net: +3 statements, -1 statement = +2 statements → SLIGHTLY LARGER in C, but the key question is ROM bytes.

For a 20×9 banner centered on 20×18 screen: `col = (20-20)/2 = 0, row = (18-9)/2 = 4`. The centered placement call is functionally identical to a (0,4) tilemap-place (col=0, row=4 per the LevelCardSceneBuilder math), replacing the (0,0) tilemap-place.

**SPEC allows same-or-smaller bytes, NOT necessarily byte-identical.** The additional `hide_sprites_range` + `move_bkg` + `fill_bkg_rect` are small GBDK calls (< 10 bytes each in SDCC output). The ROM size impact is likely +20-40 bytes for title_enter, acceptable under the functional-equivalence + same-or-smaller bar IF the overall ROM stays at or below pre-migration size.

**Actual same-or-smaller depends on the post-optimization ROM.** The planner should treat this as AMBER: capture pre-migration ROM size, verify after migration. The visual validation (MCP screenshot) is the binding gate.

## Common Pitfalls

### Pitfall 1: D-07 Predicate Bank>0 Too Broad
**What goes wrong:** Using `bank > 0` as the sole predicate for auto-`*_exit` causes pong and breakout (ROM_ONLY, 3-4 scenes all in bank 1) to gain new `*_exit` functions — violating the "no C growth for single-bank games" gate and failing the acceptance criterion.
**Why it happens:** BankingAnalysisPass places ALL scenes into bank 1+ for multi-scene games, even ROM_ONLY games. ROM_ONLY bank 1 is not a "different" bank in the MBC sense — it's just the code bank.
**How to avoid:** Gate additionally on `cartridge.maxRomBanks > 2` (the isMbcGame check). Thread this from GBDKPipelineV2 as `isMbcGame: Boolean` parameter.
**Warning signs:** If pong/breakout codegen tests fail with unexpected `title_exit`/`game_exit` functions; if `navigate_to_scene` gains new exit switch cases for previously exit-less scenes.

### Pitfall 2: `screen()` Placed in ScriptBuilder Instead of SceneBuilder
**What goes wrong:** Implementing `screen()` as a `ScriptBuilder` (enter {}) op means it cannot add to `SceneIR.zoneRefs`, so `SceneVisitor` never emits the zone-load prelude. The title scene renders a blank screen.
**Why it happens:** The CONTEXT.md D-03 description "called inside a scene's `enter { }`" is misleading. The physical placement must be at the `SceneBuilder` body level — like `zone(zoneRef)`.
**How to avoid:** Implement as `SceneBuilder.screen(assetRef)` (not `ScriptBuilder`). The resulting DSL reads `scene("title") { screen(asset("...")); frame { ... } }` — `screen()` is at the scene body level, not inside `enter { }`.
**Warning signs:** If `scene.zoneRefs` is empty after `screen()` call → `SceneVisitor` won't emit zone-load → blank display.

### Pitfall 3: Missing Trampoline Pairing for Auto-Emitted `*_exit`
**What goes wrong:** Auto-emitting `play_exit` BANKED in bank1.c without also adding a `play_exit_trampoline` in main.c causes `navigate_to_scene()` to call `play_exit_trampoline()` which doesn't exist → SDCC undefined identifier error.
**Why it happens:** `buildTrampolinesForScene()` and `buildNavigateToSceneFunction()` both currently gate on `scene.exitOps.isNotEmpty()`. They miss the auto-synthesized case.
**How to avoid:** Use a consistent predicate — the same `isMbcGame && bankSlot.bank > 0` check — in both SceneVisitor (auto-emit exit) and GBDKPipelineV2 (emit trampoline + navigate switch case).
**Warning signs:** SDCC linker error `undefined identifier 'play_exit_trampoline'` in buildRom output.

### Pitfall 4: ScriptOpInterpreter when-Block Throws on BindCurrentLevel
**What goes wrong:** Adding `BindCurrentLevel` to IR without updating `ScriptOpInterpreter`'s `when` block causes JVM simulation tests that exercise `gameplayScene.enter {}` to throw `UnsupportedOperationException: Unknown ScriptOp: BindCurrentLevel`.
**Why it happens:** `ScriptOpInterpreter` uses a `when` expression (line 283), not the ScriptOpVisitorI interface. New nodes must be added to the no-op branch.
**How to avoid:** Add `is BindCurrentLevel ->` to the hardware-no-op block in `ScriptOpInterpreter.execute()`.
**Warning signs:** `ScriptOpInterpreter` tests or `SimulationContextV2` tests fail with `UnsupportedOperationException`.

### Pitfall 5: Test ScriptOpVisitorI Implementations Fail to Compile
**What goes wrong:** Adding `visitBindCurrentLevel` to `ScriptOpVisitorI` without updating the 5 test implementations causes compile failure across `gbkt-ir:test` and `gbkt-core:test`.
**Why it happens:** Kotlin's non-sealed interface with explicit visitor contract requires ALL implementations to add the new method. The 5 test implementations (PuzzleOpDescriber, TriggerTestDescriber, ScriptOpDescriber, 2 anonymous objects) are not abstract — they must implement every interface method.
**How to avoid:** Update all 5 test implementations in Step 1 before any test can run.
**Warning signs:** Kotlin compile error `Class 'PuzzleOpDescriber' is not abstract and does not implement abstract member 'visitBindCurrentLevel'`.

### Pitfall 6: `buildSetupCurrentLevelFunctionIfNeeded` Filtering Breaks with `_screen_` Prefix
**What goes wrong:** Synthetic zone ID `_screen_title` (from `screen()`) might not match the existing title-filter in `buildSetupCurrentLevelFunctionIfNeeded` (line 2438: `!idLower.contains("title")`). `_screen_title` DOES contain "title" so it IS filtered out. But `_screen_nextLevelScene` might not contain "nextlevel" if the scene name differs.
**Why it happens:** The filter matches on zone ID substrings. Synthetic IDs must be designed to always pass the filter for non-gameplay zones.
**How to avoid:** The `_screen_` prefix plus scene-ID ensures synthetic zones use the same filter as their source zones. Test: if titleScene produces `_screen_title`, the "title" substring matches. If nextLevelScene produces `_screen_nextLevelScene`, the "nextlevel" substring matches. This holds as long as the scene names follow the conventional naming.
**Warning signs:** `setup_current_level()` switch case count grows unexpectedly to include screen zones.

### Pitfall 7: Pre-Migration Baseline Not Captured Before Migration
**What goes wrong:** Without a pre-migration ROM baseline (screenshots + byte sizes), the "same-or-smaller bytes" and "MCP visual parity" gates cannot be objectively verified.
**Why it happens:** The migration plan starts refactoring immediately, and by the time visual evidence is needed, the pre-migration ROM no longer exists cleanly.
**How to avoid:** The FIRST task of the migration wave must be: build pre-migration ROMs, capture screenshots of all 3 visual surfaces (title, gameplay-level, NextLevel-card), record byte sizes. This is D-11 binding.

## Open Questions (RESOLVED)

1. **`screen()` placement: SceneBuilder level vs ScriptBuilder enter {}`**
   - What we know: ScriptBuilder cannot add to SceneIR.zoneRefs; must be SceneBuilder level
   - What's unclear: CONTEXT.md D-03 says "called inside a scene's `enter { }`" — this may be aspirational API design that the DSL user types, but the Kotlin DSL evaluation may still execute it at the SceneBuilder level via receiver extension
   - RESOLVED: Implement as `SceneBuilder.screen(assetRef)` callable at scene body level. If the author prefers `enter { screen(...) }` syntax, implement via a ScriptBuilder wrapper that delegates back to SceneBuilder — but this is complex. The simpler and architecturally correct form is `scene("title") { screen(asset("...")); frame { ... } }`. (Planned in 13.5-02.)

2. **`navigate_to_scene()` exit-case inclusion for auto-synthesized exits**
   - What we know: `buildNavigateToSceneFunction()` filters `it.exitOps.isNotEmpty()` — auto-exit scenes with empty `exitOps` are excluded
   - What's unclear: should `navigate_to_scene()` call `play_exit_trampoline()` even when it's a no-op? YES — for the Banks trampoline convention to hold; without the exit case, old scenes that were navigating away from `play` would silently skip the exit call
   - RESOLVED: Use `SceneIR.autoEmitExit: Boolean = false` flag set during SceneVisitor processing, consumed by pipeline to include the scene in exit-switch cases and trampoline generation via a shared `shouldAutoEmitExit` predicate. (Planned in 13.5-03.)

3. **`screen()` Option A vs Option B for D-05 centering**
   - Option A: New `ScreenCenterOp` ScriptOp node added to enterOps → requires another ScriptOpVisitorI method + all implementations
   - Option B: `screenMode: Boolean` flag in `ZoneIR` → SceneVisitor reads it, no new ScriptOp interface method needed
   - RESOLVED: Option B. ZoneIR already carries zone-specific behavior flags; adding `screenMode` is cheaper than a new ScriptOp + full visitor wiring. (Planned in 13.5-02.)
