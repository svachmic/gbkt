# Phase 06.5: V1 Feature Parity Port — RPG Package - Research

**Researched:** 2026-02-23
**Domain:** RPG package expansion — gbkt-rpg DSL, IR, codegen for stats, abilities, status effects, monster AI, three combat variants, equipment, class/job, economy, save integration
**Confidence:** HIGH

## Summary

Phase 06.5 builds on the engine combat foundation from Phase 06.4. The engine (`CombatEngineSystem` IR + `CombatVisitor` codegen) is already complete and tested. Phase 06.5's job is to make `gbkt-rpg` a full RPG authoring package that wraps the engine with rich domain types: character stats, abilities, status effects, monster AI, equipment, class/job system, three combat variants (ATB, tactical grid, wave-survival), party management, economy/shops, and save integration.

The central design constraint is already established: `gbkt-rpg` uses `GenericSystem` (via `registerSystem()`) for all its systems, extends `GameBuilder` via extension functions, and does NOT introduce new sealed IR subtypes. All RPG domain data flows through `GenericSystem.config` maps. The GBDK backend (`GBDKSystemVisitor`, `buildSimpleBattleFunctions`) dispatches on `config["type"]` string keys. This pattern is proven working and is the mandatory pattern for all new RPG systems in this phase.

The phase is large but well-understood structurally. The biggest risk is scope management: 16 success criteria spanning 10+ subsystems. The recommended approach is to plan in thematic waves, mirroring the Phase 06.4 plan pattern (4 plans). Each plan delivers a coherent slice: (1) RPG character/stats/leveling DSL + codegen, (2) ability/status effect/monster AI DSL + codegen, (3) three combat variants + turn order as `CombatEngineSystem` extensions, (4) equipment/economy/save/party + `_item_names[]` + migrate `simpleBattle`, integration tests.

**Primary recommendation:** Use GenericSystem config-map pattern for all RPG systems (proven in simpleBattle); extend CombatEngineSystem for ATB/tactical/wave-survival variants (proven in 06.4 CombatType enum); all codegen in new RpgVisitor class (mirrors CombatVisitor/InventoryVisitor); zero CRawCode in new code.

## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Combat Variant Depth
- All three combat types (ATB, tactical grid, wave-survival) are full playable systems, not scaffolding
- Each variant is feature-complete enough to build a real game around
- Shared ability base with variant-specific extensions: core ability (name, cost, effect) is shared; grid adds range/AoE shape, ATB adds charge time, etc.

#### ATB (Active Time Battle)
- Two gauge models available to developer: classic FF-style fill gauge AND charge-based (actions have cast times)
- Developer selects which model via DSL
- Supports Wait mode (gauge pauses during menus), Active mode (keeps filling), and player-toggle option (in-game setting)
- Three-tier configuration: developer sets default mode, can expose toggle to player

#### Tactical Grid Combat
- Full tactical: movement range, terrain types (passable/blocked/slow/damage), elevation bonuses, line-of-sight
- Optional facing system (developer enables) — flanking/backstab bonuses when turned on
- Developer opts out of features they don't need (terrain, elevation, facing are all independent opt-ins)

#### Wave-Survival Combat
- Fully configurable between-wave behavior: pause duration, shop access, heal amount, next-wave trigger (timer vs player-ready)
- Both scripted waves (hand-authored enemy composition) and procedural waves (rules-based spawning with difficulty curves)
- Developer can mix scripted and procedural in the same game

#### Monster AI Framework
- Full behavior trees: selector/sequence/decorator nodes, not just priority lists
- Configurable awareness levels per monster: SELF_ONLY, TARGET_AWARE, FULL_CONTEXT
- Multi-phase boss AI: behavior changes at HP thresholds (Phase 1: 100-50%, Phase 2: 50-25%, etc.)
- Role-based group coordination: monsters tagged with roles (TANK, HEALER, DPS), AI can reference allies by role
- Cooldown system: both per-ability cooldowns AND global repeat prevention, developer chooses per monster
- Charge/telegraph actions: abilities can have chargeTurns(N) — monster enters charge state, player sees warning, attack fires after N turns
- Difficulty modifiers: EASY/NORMAL/HARD tiers that modify AI behavior (targeting intelligence, ability selection)
- Summon actions: AI can spawn new combatants mid-battle (boss summons adds)

#### Equipment System
- Standard slots (weapon, shield, head, body, accessory) plus developer-defined custom slots
- Slot configuration supports dual-wielding and two-handed: slot rules define whether a weapon slot accepts 1 two-handed OR 2 one-handed items
- Tiered set bonuses: 2-piece, 3-piece, 4-piece bonuses for item sets
- Stat modifiers: flat + percentage, applied in order (base → flat → percentage → final)
- Requirements (all optional per item): level requirement, stat requirement, class/job restriction
- Optional upgrade/enchant system (developer enables): +1/+2/+3 upgrades and elemental enchanting
- Optional durability: items degrade with use, at zero become ineffective
- Optional elemental affinity: equipment ties into existing Aspect system (fire sword, ice armor, etc.)

#### Status Effects
- Typed cleansing: 'cleanse all debuffs', 'remove specific effect', 'dispel all buffs from enemy'
- Dual immunity model: per-effect immunity AND per-category immunity (DEBUFF, CROWD_CONTROL, DOT, BUFF)
- Effect interaction rules: developer defines interactions — 'poison cancels regen', 'wet + fire = steam', 'frozen + physical = shatter bonus damage'
- Full event-driven triggers: onHit, onDamageTaken, onTurnStart, onTurnEnd, onDeath — enables thorns, counter, regen, etc.
- Resistance/apply-chance: both flat percentage AND stat-based contest (developer chooses per effect)
- Enhanced INTENSITY stacking: per-stack scaling + onStackApplied/onStackRemoved hooks
- Source-aware stacking: same source refreshes duration, different sources stack independently
- Presentation (icons, animations, sounds) stays in BattlePresentation layer, NOT in effect DSL

#### Class/Job System
- Class definitions with stat growth rates, equipment restrictions, learnable abilities
- All job-change modes configurable per game: locked (no switching), switchable-fresh, switchable-with-skill-retention
- Developer configures which mode their game uses

#### Ability Learning & Skill Trees
- Multiple learning methods: auto-learn at level thresholds, skill point allocation, class-gated, item/scroll teaching
- Both flat unlock lists AND prerequisite trees
- Optional mastery system: abilities gain proficiency through use
- Optional evolution chains: Fire → Fira → Firaga

#### Party Management
- Active party + optional reserve/bench
- Optional row-based formation: front/back row with configurable bonuses
- Story-driven party changes: addToParty/removeFromParty as script actions
- Optional guest flag: temporary members with locked equipment, AI-controlled in battle, auto-leave at story point

#### Economy & Shops
- Merchant DSL: define shops with inventory, pricing, stock limits
- Single currency with developer-defined name
- Both static and flag-gated dynamic stock
- Sell pricing: global sell ratio (default 50%) with per-item override
- Optional crafting module: recipe-based crafting as opt-in DSL extension
- Unified loot tables with rarity system: common/uncommon/rare/epic tiers
- Optional per-item stock limits

#### Save/Load Integration
- Full auto-serialization with exclusion list
- Developer-configurable save slot count (default 3)
- Both save-anywhere and save-point-only modes
- Developer-configured save preview fields
- Checksum validation
- Optional auto-save: trigger-based with dedicated auto-save slot
- Optional New Game+: configurable carry-over rules

#### Future-Proofing Design Principles
- General-purpose first: design for broadest RPG use cases
- Primary target styles: JRPG + SRPG (tactical). Action RPG, roguelike are secondary
- Escape hatches: combat loop hooks (onBeforeAction, onAfterDamage, etc.) + fully custom combat types
- Raw injection warning: framework warns when raw/escape-hatch code is used
- Style presets as documented examples, not first-class API

### Claude's Discretion
- C AST node design and codegen architecture for all RPG systems
- IR node structure for new combat variants
- Behavior tree node implementation details (selector/sequence/decorator internals)
- SRAM layout and memory management for save data
- Performance optimization for Game Boy hardware constraints
- Test structure and codegen assertion patterns
- Mini-example project structure for feature validation

### Deferred Ideas (OUT OF SCOPE)
- Action RPG / roguelike as first-class RPG styles — secondary for now
- Multiple currency types — single named currency covers most Game Boy RPGs
- Crafting as a deeper system with crafting stations, material gathering — current opt-in module is recipe-based only

## Architecture Patterns

### Pattern 1: GenericSystem config-map (MANDATORY for all new RPG systems)

All RPG systems in `gbkt-rpg` produce `GenericSystem` instances — no new sealed IR subtypes. The `config` map carries all domain data. The `GBDKSystemVisitor.visitGenericSystem()` dispatches on `config["type"]`.

**CRITICAL:** The test `no system in ir is an RPG-specific sealed subtype` in `RpgBuildersTest` enforces this. All new RPG systems (ATB, grid combat, wave-survival, abilities, status effects) MUST produce `GenericSystem`.

```kotlin
// Pattern: RPG extension function produces GenericSystem
fun GameBuilder.abilitySystem(id: String, block: AbilitySystemBuilder.() -> Unit) {
    val builder = AbilitySystemBuilder(id)
    builder.block()
    val def = builder.build()
    val system = GenericSystem(
        id = id,
        config = mapOf(
            "type" to "ability_system",
            "abilities" to def.abilities,
            // ...
        )
    )
    registerSystem(system)
}
```

**Backend dispatch** in `GBDKSystemVisitor.visitGenericSystem()`:
```kotlin
"ability_system" -> RpgVisitor(gameIR).generateAbilitySystemFunctions(system)
"atb_combat" -> RpgVisitor(gameIR).generateAtbCombatFunctions(system)
// etc.
```

### Pattern 2: CombatType extension for new combat variants

The existing `CombatType` enum has `TURN_BASED` and `REAL_TIME`. New variants (ATB, TACTICAL_GRID, WAVE_SURVIVAL) MUST be added to this enum in `CombatEngineIR.kt`:

```kotlin
enum class CombatType {
    TURN_BASED,
    REAL_TIME,
```

The `CombatVisitor.buildStateMachineSwitch()` already dispatches on `system.combatType == CombatType.TURN_BASED`. New branches will add variant-specific case bodies.

### Pattern 5: RpgVisitor in gbkt-backend-gbdk (NOT in gbkt-rpg)

The RPG visitor that generates C code MUST live in `gbkt-backend-gbdk`, not in `gbkt-rpg`. The dependency rule is:
- `gbkt-rpg` depends on `gbkt-core` (DSL recording)
- `gbkt-backend-gbdk` depends on `gbkt-rpg` (for codegen of RPG domain types)

This mirrors the existing pattern: `InventoryVisitor` lives in `gbkt-backend-gbdk` and is called from `GBDKPipelineV2`. A new `RpgVisitor` class follows the same structure.

### Behavior Tree IR Pattern (Claude's Discretion)

For the monster AI framework (full behavior trees), the recommended implementation is a sealed hierarchy of tree node types within `gbkt-rpg` domain (not gbkt-ir):

```kotlin
// gbkt-rpg/domain/BehaviorTree.kt
sealed interface BehaviorNode
data class SelectorNode(val children: List<BehaviorNode>) : BehaviorNode  // OR logic
data class SequenceNode(val children: List<BehaviorNode>) : BehaviorNode  // AND logic
data class ActionNode(val action: MonsterAction) : BehaviorNode
data class ConditionNode(val predicate: MonsterCondition) : BehaviorNode
data class PhaseThresholdNode(val hpPercent: Int, val tree: BehaviorNode) : BehaviorNode
```

The `RpgVisitor` translates this tree into a C switch/if structure. Each node maps to nested C conditionals. This is Claude's discretion area — the above is a recommended starting point.

## Common Pitfalls

### Pitfall 1: Creating new sealed IR subtypes in gbkt-ir for RPG systems
**What goes wrong:** Adding `RpgBattleSystem : SystemIR` or `AbilitySystem : SystemIR` to gbkt-ir forces all `when(system)` exhaustive matches in the backend to add new branches — breaks compilation.
**Why it happens:** Intuitive to model RPG systems as first-class SystemIR subtypes.
**How to avoid:** ALL RPG systems use `GenericSystem` with `config["type"]`. The test `no system in ir is an RPG-specific sealed subtype` in `RpgBuildersTest` will catch violations.
**Warning signs:** New `is RpgSystem` patterns appearing in `GBDKSystemVisitor`'s `when` blocks.

### Pitfall 2: Adding ATB/grid/wave as GenericSystem instead of CombatType extension
**What goes wrong:** If ATB combat is registered as a `GenericSystem`, it bypasses the existing `CombatVisitor` infrastructure and requires a completely separate codegen path, duplicating the state machine generation logic.
**Why it happens:** Consistent with the "use GenericSystem" rule for RPG systems. But combat variants are logically SUBTYPES of the engine combat system.
**How to avoid:** ATB/TACTICAL_GRID/WAVE_SURVIVAL extend the existing `CombatType` enum and use `CombatEngineSystem`. The `CombatVisitor` gains variant-specific branches in `buildStateMachineSwitch()`.

### Pitfall 3: C89 violations in new RPG codegen
**What goes wrong:** New RPG visitors accidentally use C99 syntax — variable declarations after statements, `//` comments, `bool` type.
**Why it happens:** Kotlin code generating C code makes it easy to forget C89 constraints.
**How to avoid:** Follow the established patterns: `CVarDecl` before `CFor` (not in `init`), use `CComment` for `/* ... */` style, use `UINT8` not `bool`, `CRawExpr("i++")` for loop increment.

### Pitfall 4: Forgetting `_item_names[]` is an InventoryVisitor extension, not a new system
**What goes wrong:** Building `_item_names[]` as a separate RPG system rather than as an extension to `InventoryVisitor.generateItemConstants()`.
**Why it happens:** It seems RPG-specific.
**How to avoid:** `_item_names[]` is inventory data — item display names live in the item catalog alongside IDs and stack counts. It belongs in `InventoryVisitor`. The inventory menu system (`InventoryDataSource`) already reads from the visitor's output.

### Pitfall 5: CombatStats backward compatibility break
**What goes wrong:** Adding new required fields to `CombatStats(hp, atk, def)` breaks all existing `CombatStats(hp=20, atk=5, def=3)` call sites in tests and examples.
**Why it happens:** Extending a data class naively.
**How to avoid:** All new stats fields on `CombatStats` MUST have default values (`val sp: Int = 0`, `val agl: Int = 0`). The `CharacterBuilder.stats {}` block adds `sp()`, `atk()`, `matk()`, etc. as optional setters.

### Pitfall 6: gbkt-rpg module depending on gbkt-backend-gbdk
**What goes wrong:** RPG domain types accidentally import C AST types from `gbkt-backend-gbdk`.
**Why it happens:** Tempting to put codegen-aware helpers in the domain module.
**How to avoid:** `gbkt-rpg/build.gradle.kts` only has `implementation(project(":gbkt-core"))`. The RPG visitor (`RpgVisitor.kt`) lives in `gbkt-backend-gbdk`, not `gbkt-rpg`.

### Pitfall 7: Behavior tree depth causing WRAM overflow
**What goes wrong:** A deep behavior tree for a boss monster generates deeply nested C if/switch code that exceeds Game Boy stack depth at runtime.
**Why it happens:** Behavior trees are recursive by nature; Game Boy stack is ~128 bytes.
**How to avoid:** Use iterative evaluation pattern for behavior tree codegen (mirrors Phase 06.1 A* decision: iterative not recursive). The tree is compiled into a flat switch/if sequence at codegen time — not evaluated recursively at runtime.

```kotlin
fun generateItemNamesTable(): CVarDecl? {
```

## Open Questions

1. **ATB gauge fields on CombatEngineSystem vs separate GenericSystem**
   - What we know: `CombatEngineSystem` is the appropriate home for ATB config (it IS a combat system). ATB fields are variant-specific — irrelevant for TURN_BASED.
   - What's unclear: Should ATB-specific fields (gaugeModel, waitMode, activeMode) be on `CombatEngineSystem` directly (cluttering it), or in a separate `AtbConfig` data class field?
   - Recommendation: Add `val atbConfig: AtbConfig? = null` as a nullable field on `CombatEngineSystem`. Null for non-ATB games (no overhead). Backend only reads it when `combatType == CombatType.ATB`.

2. **Behavior tree codegen output size**
   - What we know: Game Boy ROM banks are 16KB. Full behavior trees could generate significant C code per monster.
   - What's unclear: Maximum viable tree depth/complexity before bank overflow becomes a concern.
   - Recommendation: Each monster's behavior tree compiles to a single `update_ai_<monsterid>()` C function. The planner should add a bank assignment note for RPG AI functions (likely bank 1 or dedicated RPG bank).

3. **simpleBattle migration — backward compatibility in tests**
   - What we know: `RpgBuildersTest` tests expect `simpleBattle` to produce a `GenericSystem`. After migration to `CombatEngineSystem`, the test `simpleBattle registers a GenericSystem in game IR systems` will fail.
   - What's unclear: Should the migration update or remove those tests?
   - Recommendation: Update tests to expect `CombatEngineSystem` instead of `GenericSystem` after migration. The key constraint ("no RPG-specific sealed subtype") is still satisfied — `CombatEngineSystem` is a core IR type.

4. **SRAM layout for full RPG state**
   - What we know: `SaveSystem` IR handles slot count, checksum, version. RPG state is much larger than arcade game state (character stats, inventory, flags, equipment).
   - What's unclear: SRAM is 8KB max on MBC5 carts. Does the RPG save state fit in one slot?
   - Recommendation: Claude's discretion — implement SRAM compaction (pack stats into UINT8, use bit flags for boolean state). The planner should include a memory budget note in Plan 04.
