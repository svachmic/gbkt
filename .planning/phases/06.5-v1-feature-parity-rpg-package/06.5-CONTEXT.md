# Phase 06.5: V1 Feature Parity Port — RPG Package - Context

**Gathered:** 2026-02-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Port RPG-specific features to gbkt-rpg package: character stats and leveling, abilities with targeting and effects, status effects, monster definitions with AI, RPG-specific battle logic layered on engine combat. Includes three combat variants (ATB, tactical grid, wave-survival), equipment system, class/job system, economy/shops, save integration, and ability learning. All codegen uses typed C AST. gbkt-rpg depends on engine combat (Phase 06.4), not the reverse.

</domain>

<decisions>
## Implementation Decisions

### Combat Variant Depth
- All three combat types (ATB, tactical grid, wave-survival) are full playable systems, not scaffolding
- Each variant is feature-complete enough to build a real game around
- Shared ability base with variant-specific extensions: core ability (name, cost, effect) is shared; grid adds range/AoE shape, ATB adds charge time, etc.

### ATB (Active Time Battle)
- Two gauge models available to developer: classic FF-style fill gauge AND charge-based (actions have cast times)
- Developer selects which model via DSL
- Supports Wait mode (gauge pauses during menus), Active mode (keeps filling), and player-toggle option (in-game setting)
- Three-tier configuration: developer sets default mode, can expose toggle to player

### Tactical Grid Combat
- Full tactical: movement range, terrain types (passable/blocked/slow/damage), elevation bonuses, line-of-sight
- Optional facing system (developer enables) — flanking/backstab bonuses when turned on
- Developer opts out of features they don't need (terrain, elevation, facing are all independent opt-ins)

### Wave-Survival Combat
- Fully configurable between-wave behavior: pause duration, shop access, heal amount, next-wave trigger (timer vs player-ready)
- Both scripted waves (hand-authored enemy composition) and procedural waves (rules-based spawning with difficulty curves)
- Developer can mix scripted and procedural in the same game

### Monster AI Framework
- Full behavior trees: selector/sequence/decorator nodes, not just priority lists
- Configurable awareness levels per monster: SELF_ONLY, TARGET_AWARE, FULL_CONTEXT
- Multi-phase boss AI: behavior changes at HP thresholds (Phase 1: 100-50%, Phase 2: 50-25%, etc.)
- Role-based group coordination: monsters tagged with roles (TANK, HEALER, DPS), AI can reference allies by role
- Cooldown system: both per-ability cooldowns AND global repeat prevention, developer chooses per monster
- Charge/telegraph actions: abilities can have chargeTurns(N) — monster enters charge state, player sees warning, attack fires after N turns
- Difficulty modifiers: EASY/NORMAL/HARD tiers that modify AI behavior (targeting intelligence, ability selection)
- Summon actions: AI can spawn new combatants mid-battle (boss summons adds)

### Equipment System
- Standard slots (weapon, shield, head, body, accessory) plus developer-defined custom slots
- Slot configuration supports dual-wielding and two-handed: slot rules define whether a weapon slot accepts 1 two-handed OR 2 one-handed items
- Tiered set bonuses: 2-piece, 3-piece, 4-piece bonuses for item sets
- Stat modifiers: flat + percentage, applied in order (base → flat → percentage → final)
- Requirements (all optional per item): level requirement, stat requirement, class/job restriction
- Optional upgrade/enchant system (developer enables): +1/+2/+3 upgrades and elemental enchanting
- Optional durability: items degrade with use, at zero become ineffective
- Optional elemental affinity: equipment ties into existing Aspect system (fire sword, ice armor, etc.)

### Status Effects
- Typed cleansing: 'cleanse all debuffs', 'remove specific effect', 'dispel all buffs from enemy'
- Dual immunity model: per-effect immunity AND per-category immunity (DEBUFF, CROWD_CONTROL, DOT, BUFF)
- Effect interaction rules: developer defines interactions — 'poison cancels regen', 'wet + fire = steam', 'frozen + physical = shatter bonus damage'
- Full event-driven triggers: onHit, onDamageTaken, onTurnStart, onTurnEnd, onDeath — enables thorns, counter, regen, etc.
- Resistance/apply-chance: both flat percentage AND stat-based contest (developer chooses per effect)
- Enhanced INTENSITY stacking: per-stack scaling + onStackApplied/onStackRemoved hooks (e.g., 5 bleed stacks = hemorrhage burst)
- Source-aware stacking: same source refreshes duration, different sources stack independently
- Presentation (icons, animations, sounds) stays in BattlePresentation layer, NOT in effect DSL — clean separation

### Class/Job System
- Class definitions with stat growth rates, equipment restrictions, learnable abilities
- All job-change modes configurable per game: locked (no switching), switchable-fresh, switchable-with-skill-retention
- Developer configures which mode their game uses

### Ability Learning & Skill Trees
- Multiple learning methods available: auto-learn at level thresholds, skill point allocation, class-gated, item/scroll teaching
- Developer picks which method(s) their game uses
- Both flat unlock lists AND prerequisite trees — developer chooses per class or globally
- Optional mastery system: abilities gain proficiency through use (reduced cost, increased power, unlocks upgrade)
- Optional evolution chains: Fire → Fira → Firaga as framework concept (developer defines upgrade paths)

### Party Management
- Active party + optional reserve/bench (developer configures whether reserves exist, reserve size, EXP sharing, swap rules)
- Optional row-based formation: front/back row with configurable bonuses (damage multipliers, defense bonuses)
- Story-driven party changes: addToParty/removeFromParty as script actions (developer enables dynamic vs static party)
- Optional guest flag: temporary members with locked equipment, AI-controlled in battle, auto-leave at story point

### Economy & Shops
- Merchant DSL: define shops with inventory, pricing, stock limits
- Single currency with developer-defined name (gold, gil, zenny — not hardcoded)
- Both static and flag-gated dynamic stock: base inventory fixed, optional items appear/disappear based on game flags
- Sell pricing: global sell ratio (default 50%) with per-item override
- Optional crafting module: recipe-based crafting as opt-in DSL extension
- Unified loot tables with rarity system: common/uncommon/rare/epic tiers; shared across monster drops, chests, quest rewards
- Optional per-item stock limits: specific items can have limited quantity per shop

### Save/Load Integration
- Full auto-serialization with exclusion list: all RPG state saves by default, developer marks what to exclude (noSave)
- Developer-configurable save slot count (default 3)
- Both save-anywhere and save-point-only modes (developer picks)
- Developer-configured save preview: define which fields appear on slot selection screen (leader name, level, time, location, etc.)
- Checksum validation: protect against SRAM corruption, warn player on corrupt data
- Optional auto-save: trigger-based (scene transitions, after battles) with dedicated auto-save slot
- Optional New Game+: configurable carry-over rules (what persists, what resets)

### Future-Proofing Design Principles
- General-purpose first: design for broadest RPG use cases, not tailored to LabyrinthOfTheDragon
- Primary target styles: JRPG + SRPG (tactical). Other styles (action RPG, roguelike) are secondary
- Escape hatches: combat loop hooks (onBeforeAction, onAfterDamage, etc.) + fully custom combat types
- Raw injection warning: framework warns when raw/escape-hatch code is used — the goal is 99% framework coverage
- Style presets as documented examples, not first-class API — avoid preset maintenance burden

### Claude's Discretion
- C AST node design and codegen architecture for all RPG systems
- IR node structure for new combat variants
- Behavior tree node implementation details (selector/sequence/decorator internals)
- SRAM layout and memory management for save data
- Performance optimization for Game Boy hardware constraints
- Test structure and codegen assertion patterns
- Mini-example project structure for feature validation

</decisions>

<specifics>
## Specific Ideas

- Combat variants share a unified ability base — core ability properties are combat-type-agnostic, variants add their own extensions
- Targeted mini-example projects validate each combat variant (ATB, grid, wave-survival) — not full games, just enough for end-to-end ROM compilation
- Boss AI multi-phase pattern: distinct behavior trees per HP threshold, not just condition checks within a single tree
- Equipment slot configuration is declarative: slot rules (two-handed blocks shield, dual-wield requires trait) are defined in the DSL, not procedural code
- Loot rarity tiers affect drop rates and can optionally affect item stats (rare version of sword has better base stats)

</specifics>

<deferred>
## Deferred Ideas

- Action RPG / roguelike as first-class RPG styles — secondary for now, may be future phase
- Multiple currency types — single named currency covers most Game Boy RPGs
- Crafting as a deeper system with crafting stations, material gathering — current opt-in module is recipe-based only

</deferred>
