## Summary

Phase 12.7 fixes a single, well-isolated codegen defect: `PlatformerVisitor.buildVerticalFootProbe()` (kt:1222–1262) zeroes `_playerVy` and sets `_grounded = 1` on foot collision but never corrects `_playerY` to pin the player's foot-row to the top edge of the underlying solid tile. The over-integrated sub-pixel position from the previous frame's gravity step remains in `_playerY`, producing a stable 1–3 px visual hover observed in all three RED-baseline PNGs.

The fix is additive: append two `CVarDecl`/`CExprStatement` nodes to the existing `thenBody` list of the inner `anyHit` CIf block. One new local variable (`foot_tile_row`) plus one assignment to `posYSym`. The function signature must gain one parameter (`posYSym: String`) to expose the y-position symbol to the helper — the only structural change to `buildVerticalFootProbe`. The D-03 stuck-resolve wrap is a parallel one-liner guard (`if (!groundedSym)`) on the outer while-loop at kt:879, using a symbol already resolved in `buildTilemapPhysicsUpdateFunction` scope.

The snap formula `posYSym = ((foot_tile_row << 3) - height) << 4` is STRONGER than the reference `player.c` (which relies on the iterative stuck-resolve loop — the snap is a deterministic single-assignment). This divergence is intentional and must be documented in a `CComment` inline.

**Primary recommendation:** Additive change to `buildVerticalFootProbe` — add `posYSym: String` parameter, append `foot_tile_row` CVarDecl and snap-assignment CExprStatement to the inner `anyHit` thenBody. D-03 guard on the stuck-resolve loop. New RED-first JVM test. UAT EVIDENCE_DIR redirect to Phase 12.7 directory. Full anchor re-shoot with expanded variables.txt.

### Finding 4: The snap formula is GEOMETRICALLY CORRECT [VERIFIED: codebase + math]

Probe checks at `player_real_y + height` (the pixel immediately below the player's foot). The reference `player.c` line 265 uses the same offset:
```c
IsTileSolid(playerRealX+(HALF_WIDTH-2), playerRealY+PLAYER_CHARACTER_BOUNDING_BOX_HEIGHT)
```

When the probe fires:
- `foot_tile_row = (player_real_y + height) >> 3` — the tile row containing the probe point
- Desired position: foot's bottom pixel at `(foot_tile_row << 3) - 1` (one pixel above the solid tile's top edge, i.e., touching it)
- Player top at: `player_real_y = (foot_tile_row << 3) - height`
- Sub-pixel encoding: `posYSym = ((foot_tile_row << 3) - height) << 4`

This places the foot at `player_real_y + height - 1 = (foot_tile_row << 3) - 1`, and the probe point at `player_real_y + height = (foot_tile_row << 3)` (exactly the tile top). The snap is boundary-exact.

**Edge case check (playerHeight=24, spawn y=120):**
- `foot_tile_row = (120 + 24) >> 3 = 144 >> 3 = 18`
- `((18 << 3) - 24) << 4 = (144 - 24) << 4 = 120 << 4 = 1920` — positive, no underflow.
- General condition for non-negative: `foot_tile_row >= height / 8`. With height=24, this means `foot_tile_row >= 3` (y ≥ tile row 3 = pixel 24). At spawn y=120, this holds by a wide margin. [VERIFIED: math]
- **Planner discretion:** CONTEXT.md notes this edge case; document as a comment. Unreachable on platformer-template geometry.

### Finding 5: The 3–5 px hover is the sub-pixel remainder from probe-before-integrate ordering [VERIFIED: code analysis]

The hover mechanism:
1. Frame N: Player falling at `vy = K * 32` (K frames of gravity, `gravity * 16 = 32/frame`). Integration: `posY += vy >> 4` moves player DOWN `K * 2` pixels. Player now overlaps solid tile.
2. Frame N+1: Probe fires (section 3, BEFORE integration). `anyHit = true` → `vy = 0`, `grounded = 1`. Integration (section 6): `posY += 0 >> 4 = 0`. Player stays at over-integrated position.

Without the snap, `posY` holds the over-integrated value. With `gravity = 2`, each frame adds `32` to `vy`. After a long fall (terminal velocity not capped in tilemap path — only the rect-physics path caps at `cfg.terminalVelocity`), `vy` can be large. The hover is `(last_vy >> 4)` pixels = `(last_vy / 16)` pixels.

With `gravity * 16 = 32` and the `jumpHold` logic capping the effective integration, at equilibrium falling the player accumulates ~32 sub-pixel velocity per frame. One frame's over-integration: `32 >> 4 = 2 px`. After gravity accumulation across a jump arc (vy climbs back from -800 to positive), the hover on landing can be 3–5 px (confirmed by RED baseline PNGs). [VERIFIED: code analysis + visual evidence]

**CONTEXT.md §specifics claimed "hover ≈ vy >> 4 at terminal velocity". Confirmed — the hover IS one frame's `vy >> 4` at whatever velocity the player had on the landing frame.**

### Finding 6: Reference `player.c` does NOT have a snap-to-tile-top step [VERIFIED: codebase]

Reference at lines 261–268:
```c

    playerYVelocity=0;
    grounded=TRUE;

```

No position correction. The reference relies on the stuck-resolve while-loop (lines 226–229) to handle over-integration:
```c

    playerY -= 16;
```

**D-02's snap is the correct gbkt-specific fix** — it deterministically pins the position rather than relying on iterative pop-up that the probe-first order has already short-circuited. [VERIFIED: codebase + reference cross-check]

```kotlin
private fun extractFunctionBody(cSource: String, functionSignaturePrefix: String): String {
    val lines = cSource.lines()
    val startIdx = lines.indexOfFirst { it.startsWith(functionSignaturePrefix) }
    if (startIdx == -1) return ""
    val body = StringBuilder()
    var depth = 0
    var started = false
    for (i in startIdx until lines.size) {
        val line = lines[i]
        body.appendLine(line)
        for (ch in line) {
            if (ch == '{') { depth++; started = true }
            if (ch == '}') depth--
        }
        if (started && depth == 0) break
    }
    return body.toString()
}
```

## Common Pitfalls

### Pitfall 1: Forgetting to add `posYSym` parameter to `buildVerticalFootProbe`

**What goes wrong:** The snap formula emits `CVar(posYSym)` where `posYSym` is in scope in `buildTilemapPhysicsUpdateFunction` but NOT in `buildVerticalFootProbe`. Forgetting the parameter addition causes a Kotlin compile error (unresolved reference).

**Why it happens:** CONTEXT.md §code_context says "No new plumbing" which is technically true for `player_real_y` (a runtime C variable, not a Kotlin param) but WRONG for `posYSym` (a Kotlin string symbol that must be passed).

**How to avoid:** Always add `posYSym: String` to `buildVerticalFootProbe` FIRST, then implement the thenBody. Update the call site at kt:869.

**Warning signs:** Kotlin compiler error: "unresolved reference: posYSym" inside `buildVerticalFootProbe`.

### Pitfall 2: Using `CLiteral(0)` instead of `CIntLiteral(0)` for the `!groundedSym` guard condition

**What goes wrong:** D-03's `if (!groundedSym)` wrap emits `CBinaryExpr(CVar(groundedSym), "==", ...)`. `groundedSym` is a UINT8 global — so `CLiteral(0)` emits `0u` which is unsigned-context and correct for UINT8 comparisons. However the nearby existing jump-initiation code (kt:994) already uses `CIntLiteral(0)` for the `groundedSym == 0` comparison (see kt:996). To maintain local consistency within the function, use `CIntLiteral(0)` for the `== 0` comparison of `groundedSym`, matching the existing pattern. [VERIFIED: codebase kt:996]

**How to avoid:** Grep `groundedSym` usages in `buildTilemapPhysicsUpdateFunction` and match the literal type used there.

### Pitfall 3: Anchoring JVM test on `"void platformer_physics_update"` including `(void)` suffix

**What goes wrong:** The emission is `void platformer_physics_update(void) {`. If the anchor prefix is `"void platformer_physics_update(void)"`, it includes the parameter list which is fine. But if the implementation changes the C function signature in a future phase (unlikely), the test would silently return empty body.

**How to avoid:** Use `"void platformer_physics_update"` (without `(void)`) as the anchor — this is broader and future-proof. Confirmed: all existing sibling tests use the function-name prefix without parameters.

### Pitfall 4: snap assertion inside foot-probe IF-block vs file-level grep

**What goes wrong:** `posYSym` (e.g., `_playerY`) appears in many places in `platformer_physics_update`: the `player_real_y` CVarDecl initializer, the velocity integration at section 6, and (after the fix) the snap in section 3. A file-level `mainC.contains("_playerY = ((")` would pass even if the snap is outside the foot-probe block.

**How to avoid:** Use brace-walk to extract the `platformer_physics_update` body, then do a SUBSTRING search for a token that is UNIQUE to the foot-probe IF-block context, e.g., `"foot_tile_row"` (a new local variable that does not appear elsewhere). This is scope-sufficient.

### Pitfall 5: Running `./gradlew clean` twice in the same regression sweep

**What goes wrong:** Per `feedback_no_parallel_gradle_clean.md`, two `./gradlew clean` invocations against the same project root cause Kotlin daemon collision and corrupt both builds.

**How to avoid:** Single chained command:
```bash
./gradlew clean \
  :gbkt-examples:pong:buildRom \
  :gbkt-examples:breakout:buildRom \
  :gbkt-examples:simple-physics:buildRom \
  :gbkt-examples:metasprites:buildRom \
  :gbkt-examples:metasprites-stress:buildRom \
  :gbkt-examples:banks:buildRom \
  :gbkt-examples:racer:buildRom \
  :gbkt-examples:platformer-template:buildRom
```

### Pitfall 6: Asserting snap assignment using `physicsBody.contains("_player_y")` (legacy fallback form)

**What goes wrong:** The snap is emitted using `posYSym` which resolves to `_playerY` (user-bound) in the platformer-template integration test, but resolves to `_player_y` in the legacy-fallback (no `tilemap_collision` system) JVM test. The new emission test must be written for ONE of these cases and the test GameIR must be consistent with the assertion.

**How to avoid:** Use the legacy-fallback form in `PlatformerPhysicsSnapToTileTopEmissionTest` (no `tilemap_collision` system), asserting `_player_y` (the fallback). Alternatively, use a bound form (with `tilemap_collision` system) and assert `_playerY`. Pick ONE and document it. The legacy form is simpler (mirrors `TilemapCollisionEmissionTest.buildPlatformerGameIR`).

```kotlin
// Source: TilemapCollisionEmissionTest.kt lines 90-110 [VERIFIED: codebase]
private fun extractFunctionBody(cSource: String, functionSignaturePrefix: String): String {
    val lines = cSource.lines()
    val startIdx = lines.indexOfFirst { it.startsWith(functionSignaturePrefix) }
    if (startIdx == -1) return ""
    val body = StringBuilder()
    var depth = 0
    var started = false
    for (i in startIdx until lines.size) {
        val line = lines[i]
        body.appendLine(line)
        for (ch in line) {
            if (ch == '{') { depth++; started = true }
            if (ch == '}') depth--
        }
        if (started && depth == 0) break
    }
    return body.toString()
}
```

## Open Questions (RESOLVED)

1. **Does `player_real_y + height` overflow UINT16 for any realistic spawn?**
   - What we know: With height=24 and screen height=144, max `player_real_y` is ~120. `120 + 24 = 144 = tile row 18`. No overflow.
   - What's unclear: If a future zone has a tall level (more than 255 tiles high), `player_real_y + height` could approach UINT16 range. Irrelevant for platformer-template.
   - Recommendation: Document as a TODO comment near the snap; no guard needed for 12.7.

2. **Does the snap interact with the `grounded = 1` → gravity-off path in section 5b?**
   - What we know: After snap, `posYSym` is corrected. On the NEXT frame, the player is grounded (`groundedSym = 1`). Section 5b's gravity is gated by `groundedSym == 0`, so gravity is NOT applied when grounded. The snap doesn't change this logic.
   - What's unclear: Nothing. The snap fires inside the foot-probe block (section 3). Gravity gating (section 5b) reads `groundedSym` which was set to 1 by the same foot-probe block. Order is: snap → grounded=1 → gravity suppressed. Consistent.
   - Recommendation: No action needed. Document snap-before-grounded order in the CComment.

3. **Is the UAT test harness capture timing reliable for anchor-2 and anchor-5?**
   - What we know: Phase 12.6 debug Cycle 2 found Coffee-GB capture timing unreliable for anchor-5 scene-flip frames. Anchor-2 (jump/land on solid) has simpler timing (just a physics event, not a scene-flip) — more reliable.
   - What's unclear: Whether the snap will produce visually distinct grounded frames in Coffee-GB vs the hover frames.
   - Recommendation: W5 plan should include a direct MCP-driven capture as a fallback if the UAT harness produces ambiguous frames. Per Phase 12.6 precedent, direct MCP capture is the binding evidence when harness timing is unreliable.
