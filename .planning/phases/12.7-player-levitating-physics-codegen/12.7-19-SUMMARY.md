## Decisions Made

- **Branch A taken** per Plan 12.7-17 Round-5 verdict at line 272 (`**Verdict:** **H1 + H2 (compound)**`). Branch B/C stubs would have skipped this plan with a single-line note; H1's codegen defect determines this plan is in scope.
- **IR-driven pivot_adjust resolution, NOT a hardcoded literal in the visitor body.** Per the parallel_execution contract: "do NOT hardcode 2u literal in the visitor. The visitor must read the actor's pivot+frameSize+hitbox from the IR." The visitor's `buildTilemapPhysicsUpdateFunction` looks up the player metasprite via `gameIR.metasprites.firstOrNull { it.posYVarName == tcSystem.config["posYVar"] }` (both flow the SAME property-delegate name from `tilemapCollision { position(playerX, playerY) }` and `metasprite { posY(playerY) }`); computes `pivot_adjust = (frameHeight - pivotY - height).coerceAtLeast(0)`. The literal `2u` appears in the emitted C ONLY because the platformer-template's geometry computes to 2. A future game with `frameSize(32, 40), pivot(16, 10), hitbox(8, 24)` would emit `pivot_adjust = 6u` — the visitor body has zero hardcoded geometry.
- **Named reference-geometry fallback constants on a private companion object** when the IR is incomplete (test fixtures that build a SystemIR-only GameIR without actors or metasprites — e.g. `PlatformerPhysicsSnapToTileTopEmissionTest.buildPlatformerGameIR`). `REFERENCE_FRAME_HEIGHT = 32` and `REFERENCE_PIVOT_Y = 6` are locked to the platformer-template's reference geometry; the existing `playerHitbox = HitboxDef(0, 0, 8, 24)` fallback uses the same convention. Together they yield `pivot_adjust = 32 − 6 − 24 = 2` for minimal-IR fixtures, keeping their emission byte-identical to the platformer-template's. The constants are KDoc-cited and self-citing (they reference PlatformerTemplate.kt:328-333 and the Plan 12.7-17 diagnostic Section 2). This avoids bare magic numbers in the function body AND avoids over-engineering the IR with denormalized config the user DSL doesn't yet need.
- **Two `-` ops on the `foot_pixel_anchor` line, NOT a separate `foot_anchor_with_pivot` CVarDecl.** Plan 12.7-19's <interfaces> sketched Option A with two new CVarDecls (`pivot_adjust` + `foot_anchor_with_pivot`). I implemented `pivot_adjust` as a new CVarDecl but folded the subtract into a `(foot_pixel_top - height) - pivot_adjust` expression inside the existing `foot_pixel_anchor` CVarDecl. Rationale: C's `-` is left-associative at one precedence class (C11 §6.5.6), so `a - b - c` parses as `(a - b) - c` — precedence-immune. The Plan 12.7-11 `one binary-op CLASS per line` discipline was designed to defeat MIXED-class chains (the 12.7-04 `<< - <<` bug); SAME-class chains were never affected. A separate `foot_anchor_with_pivot` CVarDecl would be ceremony with no defect-class coverage. The trailing comment block now explicitly cites this so a future refactor doesn't re-inline a mixed-class line or re-introduce the unneeded ceremony.
- **`coerceAtLeast(0)` clamp on pivot_adjust.** A future caller binding a metasprite whose render extent fits INSIDE the hitbox (e.g. tiny sprites in a tall actor) would compute a NEGATIVE pivot_adjust. Clamping to 0 yields the Plan 12.7-11 hitbox-foot-snap behaviour as the back-compat default — the snap stays at the hitbox foot when there's no overshoot to correct. The semantic is `pivot_adjust = max(0, extra_render_pixels_below_hitbox_foot)`.
