## Issues Encountered

### Anchor-5 00-last-gameplay.png shows real player levitation — diagnosed as NEW DEFECT, NOT a regression from Round-5

**Symptom:** 00-last-gameplay.png shows the player metasprite suspended in mid-screen (~vertical-center of the 144-px screen) against a green grid-pattern background. The bottom-of-screen ground row is visible but NOT under the player. JSON sidecar at frame 1327:
- `playerY: 686` → `player_real_y = 42` (well above ground at ~120 px)
- `playerVy: 416` (positive = falling, mid-trajectory)
- `grounded: 0` (NOT grounded — player is in mid-air)
- `playerX: 7192` → `player_real_x = 449` (at right-edge trigger zone)
- `next_level: 1` (trigger has fired this frame)
- `current_level: 0` (still in level 1; main()-guard will navigate next vblank)

**False hypotheses eliminated:**

1. **NOT a snap-emission defect.** Plan 12.7-19's pivot_adjust=2 fix is confirmed in effect (anchor2-variables.txt: `playerY_grounded: 1632` — 32 subpixel = 2 px delta from Plan 12.7-12's 1664; anchor-5/03-level-2.json: `playerY: 1632, grounded: 1` — same equilibrium). The snap emission produces zero pixel gap when the player IS grounded. The snap CANNOT un-levitate a player who is genuinely airborne — it activates only inside the `if (_grounded)` branch in `platformer_physics_update`.

2. **NOT a capture-timing defect.** Plan 12.7-20's fix correctly captures the gameplay-scene framebuffer at the trigger-fire frame (verified: `scene: gameplay` variables present in JSON; perceptual.txt shows distinct_colours=4 and dominant_ratio=0.8524 — non-uniform, non-degenerate). The capture is BEFORE main()-guard navigates — exactly as designed. The capture is faithful; the underlying program state at frame 1327 is mid-air.

**True root cause (NEW DEFECT):**

The level-end trigger in `gbkt-examples/platformer-template/build/gbkt/generated/main.c:601-603`:

```c
// Level-end trigger: increment _next_level when past the right margin
if (player_real_x > _current_level_width - 32u) {
    ++_next_level;
}
```

The trigger fires PURELY on horizontal position. NO grounded check. NO vy check. So a player who is mid-jump at the right-edge crossing point triggers the level-end while airborne.

The `anchor5LevelSwitch` test harness holds RIGHT continuously + presses A periodically while waiting for the trigger to fire. One A press at frame ~1320 triggered a jump; the player took ~7 frames to reach `real_x=449` (just past the threshold at 480-32=448); at that point `real_y=42, vy=416 (falling)`. The trigger fired mid-flight.

**Possible fixes (out of scope for Plan 12.7-21; route via follow-up plan):**

- (a) **Gameplay logic fix:** Add a `_grounded` guard to the level-end trigger emission (probably in `gbkt-examples/platformer-template/src/main/kotlin/.../PlatformerTemplate.kt` near the `levelEnd` builder, or in the visitor that emits the trigger — TBD by the follow-up plan's research step). This matches the SPEC R-03 truth "player pinned to floor near right-edge trigger" most literally.
- (b) **Test harness fix:** Modify `anchor5LevelSwitch` to release A (and possibly hold the player on the ground for N frames) before reaching the trigger zone. This sidesteps the levitation in the test artifact without changing game-design intent — but only fixes the EVIDENCE; the actual game would still trigger level-end mid-jump in player-facing play.
- (c) **Both:** Pick (a) if the game-design intent is "level ends when player is on the floor at the right edge" (the SPEC literal); pick (b) if the intent is "trigger fires regardless of grounded state". The SPEC R-03 wording strongly favors (a). The follow-up plan should clarify intent before fixing.

This defect class pre-existed Plan 12.7. It was MASKED in Plan 12.7-12 by the H2 capture-timing trap (`01-near-end.png` was captured AFTER `navigate_to_scene`, so it showed the empty nextLevelScene background — making the player's pre-trigger state invisible). Plan 12.7-15's user UAT first noticed the symptom ("anchor-5 levitation"). Plan 12.7-17's diagnostic mis-attributed it to H1+H2 (codegen + capture timing). Plan 12.7-19 + 12.7-20 closed those two hypotheses cleanly. This plan's JVM-tier visual sanity confirms the symptom persists at frame 1327 and isolates the true defect class.
