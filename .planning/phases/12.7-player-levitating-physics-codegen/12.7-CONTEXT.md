## Implementation Decisions

### Probe / integration ordering (Area 1)

- **D-01:** **Keep current probe-then-integrate order.** `buildTilemapPhysicsUpdateFunction`
  sections stay as-is: read `player_real_x/y` → horizontal probes → vertical
  foot/head probes → stuck-resolve while-loop → jump initiation → gravity →
  velocity integration. The reference `platformer_template/src/player.c` is
  ALSO probe-before-integrate (lines 261–268 probe, line 321 integrate) — the
  SPEC.md §Background "ordering suspect" hypothesis is contradicted by code
  inspection. The snap-to-tile-top step lives INSIDE the existing foot-probe
  IF-block at `PlatformerVisitor.kt:1239–1261` (the `thenBody` of the
  `vySym > 0 && anyHit` block). Smallest blast radius; preserves Defect4Symbol /
  JumpHold / WalkCycle emission test contracts unchanged.

### Snap formula shape (Area 2)

- **D-02:** **Bit-shift algebraic snap.** Inside the foot-probe IF-block's
  `thenBody` (currently zeroes `vySym` and sets `groundedSym = 1`), append a
  third statement that snaps `_playerY` to the sub-pixel value placing the
  player foot directly above the hit tile-row:

  ```
  foot_tile_row = (player_real_y + height) >> 3       // tile row the foot hits
  posYSym       = ((foot_tile_row << 3) - height) << 4 // snap; sub-pixel scale
  ```

  Single deterministic assignment. Matches the `>> 3` tile-row and `>> 4`
  sub-pixel conventions used elsewhere in the function. The codegen uses
  `CBinaryExpr` / `CVarDecl` per the existing visitor patterns. Reject
  alternatives: multiplied algebraic (slower SDCC codegen), per-foot-probe
  left+right snap (unobserved — platformer-template has flat ground; deferred
  to Phase 13+ if slope support lands).

### Stuck-resolve while-loop fate (Area 2)

- **D-03:** **Keep but tighten — gate on `!grounded`.** The existing
  stuck-in-ground while-loop at `PlatformerVisitor.kt:879–911` (pops `posYSym -= 16`
  until `is_tile_solid(x, y + heightMinus1)` is false) stays — it remains
  defense-in-depth for the spawn-inside-floor edge case (e.g., `spawn(x, y)`
  with coords overlapping a solid tile) and head-probe inverse-drift cases the
  snap doesn't cover. **Wrap the while-loop in `if (!groundedSym)`** so it
  skips the redundant fall-collision case the snap now handles. Slight perf
  win; narrows the defensive scope without removing the safety net.

### JVM emission test placement (Area 3)

- **D-04:** **New file in `gbkt-genre-platformer/src/test/.../codegen/`** named
  `PlatformerPhysicsSnapToTileTopEmissionTest.kt`. Matches established
  per-feature naming convention (Defect4SymbolRewrite, JumpHold, WalkCycle,
  TilemapPhysicsPlayerSymbol). Single contract per test class — RED-isolation
  stays clean. **Copy the Kotlin awk-brace-walk mirror** from

## Deferred Ideas

### Slope / one-way platform snap support

D-02's snap formula assumes flat ground tiles (all tile rows are equally
solid at their top edge). Slopes and one-way platforms (PlatformType
SLOPE / ONE_WAY) need per-tile-type snap geometry. Out of scope —
platformer-template has only flat ground. Belongs in a future Phase 13+
platformer-genre expansion. Capture as a TODO comment near the snap if
the divergence is worth flagging.

### Per-foot-probe left+right snap (different tile heights)

If the left foot hits a tile-row at Y=N and the right foot hits a tile-row
at Y=N-1 (e.g., stepping onto an edge), the current single snap picks
ONE tile-row. Reference player.c uses the OR of two probes (same shape as
the current foot-probe), so the snap chooses based on the first probe to
succeed. Edge case unobserved on platformer-template. Belongs in a future
slope-aware snap phase.

### Removing the stuck-resolve while-loop entirely

D-03 keeps the loop as defense-in-depth. If a future audit proves the
loop is unreachable (snap fully covers all callers), it can be removed.
That's a Phase 13+ cleanup, not 12.7 work.

### Removing buildVerticalFootProbe's `vy = 0` redundancy

Once snap lands, the player's `vy` will be zeroed AND the position
snapped in the same IF-block. The two assignments are not redundant
(zeroing vy stops gravity accumulation; snap pins position), but the
snap formula assumes `vy` was zeroed first — order-dependence within the
IF-block. Document order, don't refactor.
