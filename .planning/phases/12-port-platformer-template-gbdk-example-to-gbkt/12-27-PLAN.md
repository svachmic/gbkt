    **SEED 1 — SEED-PHASE-12-ONE-WAY-TILE.md:**

    1. **Title:** "SEED-PHASE-12-ONE-WAY-TILE: oneWayThreshold(M) tile-collision extension"

    2. **Surfaced by:** "Phase 12 D-13b — explicitly deferred; future port that needs traversable-platforms (jump up through, stand on top) triggers this"

    3. **Motivation:** Many platformers (Mario, Mega Man, Castlevania) use ONE_WAY tiles — solid from above (player lands on top) but passable from below (player jumps through). Phase 12 ships solid-only via `solidThreshold(N)` (tile < N is solid).

    4. **Proposed DSL surface:**
       ```kotlin
       platformerPhysics {
           solidThreshold(17)       // tile < 17 = solid
           oneWayThreshold(40)      // 17 ≤ tile < 40 = one-way (solid from above only)
           // tile ≥ 40 = passable
       }
       ```

    5. **Codegen implications:**
       - `is_tile_solid()` HOME helper becomes `tile_classify()` returning enum {SOLID, ONE_WAY, PASSABLE}
       - 5-point AABB probe gains vertical-velocity check (one-way solid only on `_player_vy > 0` AND head-above-tile-top)
       - New global: `_current_level_one_way_threshold (UINT8)`
       - Per-level override extends to `oneWayThreshold` shadow

    6. **Blast radius:** PlatformerVisitor (tilemap-physics branch + is_tile_solid renamed/extended) + GBDKPipelineV2 (helper update) + PlatformerPhysicsConfig (new field) + PlatformerBuilders (new method). ~4 files; medium scope.

    7. **Routing recommendation:** Phase 13 IFF a future port surfaces real need (e.g. shmup with platforms, new platformer port). Pre-budgeting in Phase 13 NOT recommended (low-frequency need per CONTEXT.md).

    8. **Reference:** N/A (gbkt-original; no upstream GBDK reference for this).

    **SEED 2 — SEED-PHASE-12-SHARED-TILESET.md:**

    1. **Title:** "SEED-PHASE-12-SHARED-TILESET: ConvertZoneTilesetsTask shared-tileset deduplication"

    2. **Surfaced by:** "Phase 12 D-15 — RESEARCH §D-15 Recommendations option (a) (accept duplication) chosen for Phase 12 budget; this seed tracks the future dedup work"

    3. **Gap description:** ConvertZoneTilesetsTask processes tilesets PER ZONE. When 2+ zones reference the same PNG (e.g. world1Area1Zone and world1Area2Zone both using `res/graphics/world1-tileset.png`), the task invokes png2asset TWICE, producing two identical `_zone_<id>_tileset.c` files. ROM size grows by ~1-3KB per duplication; correctness preserved.

    4. **Proposed approach:** Introduce a `sharedTileset` concept:
       ```kotlin
       val world1Tileset = sharedTileset(asset("res/graphics/world1-tileset.png"))
       val world1Area1Zone by zone { tileset(world1Tileset); tiles(...) }
       val world1Area2Zone by zone { tileset(world1Tileset); tiles(...) }
       ```
       Or: detect duplicates automatically in ConvertZoneTilesetsTask (hash PNG paths; emit one `_shared_tileset_<hash>.c`; map zone references to the shared name).

    5. **Codegen implications:**
       - New SharedTilesetIR (or hash-based dedup in pipeline)
       - ZoneIR.tilesetPath becomes Either<Path, SharedTilesetRef>
       - allocateZoneBanks accounts for shared payloads (one bank slot for the shared tileset)

    6. **Blast radius:** ConvertZoneTilesetsTask + GBDKPipelineV2 (allocateZoneBanks + buildTilemapBankFiles) + ZoneBuilder + ZoneIR + asset metadata serialization. ~5 files; medium-high scope.

    7. **Routing recommendation:** Phase 13 — explicitly listed in RESEARCH as a Phase 13 candidate. ROM-size impact of NOT fixing: ~1-3KB per shared-tileset pair (within 2× signal threshold for Phase 12).

    8. **JVM marker:** Plan 12-15 MultiTilesetAllocationTest currently ASSERTS the duplication exists (it should fail when the gap is fixed — useful regression marker).
