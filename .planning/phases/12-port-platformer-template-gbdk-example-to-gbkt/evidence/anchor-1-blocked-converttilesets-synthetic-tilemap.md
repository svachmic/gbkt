## Root Cause

`ConvertZoneTilesetsTask.synthesizeScreenTilemap()` (introduced by Plan 11.1-17 to
satisfy the `_bkg_tiles_load_banked` call in `SceneVisitor`) synthesizes the
per-zone tile-index array by **tiling the small `png2asset` `_tileset_map`
deduplication table across a fixed `screenMapWidth × screenMapHeight` grid via
modulo**, NOT by extracting the actual tile layout from the source PNG.

The synthesis loop, verbatim from
`gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertZoneTilesetsTask.kt:432-439`:

```kotlin
// Step 4: build the tiled-repeat byte sequence.
// For each (y, x) in the screen grid, index into the source tile map via modulo.
val tiledBytes = mutableListOf<Int>()
for (y in 0 until screenMapHeight) {
    for (x in 0 until screenMapWidth) {
        tiledBytes += sourceMap[(y % mapTileH) * mapTileW + (x % mapTileW)]
    }
}
```

The companion comment block above the synthesis call confirms the design intent
(`gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertZoneTilesetsTask.kt:288-292`):

> Plan 11.1-17 (Phase B): synthesize the screen-tile-index array that tiles the
> png2asset _tileset_map across the zone's mapWidth × mapHeight screen grid.
> This is the companion to set_bkg_data (pixel bytes); it fills the tile-index
> map that _bkg_tiles_load_banked writes to the VRAM tile-map area. Without this,
> only tile slot 0 (all-white) fills the background even when VRAM has two tiles.

The 11.1-17 intent was a **stand-in** to unblock `_bkg_tiles_load_banked` codegen
when png2asset's deduplication shrank `_tileset_map` below the screen grid size.
The original assumption — "tile a small dedup map across the screen" — happens to
produce a checkerboard for Banks Phase 11 (whose source PNG actually IS a
2×2 dedup pattern), so Banks landed GREEN. The assumption breaks for any zone
whose source PNG carries a **non-trivial, non-repeating tile layout**.

The first 5 lines of the resulting `_zone_world1Area1Zone_tilemap.c` are the
verbatim symptom (no real world1-area1 data; just an 8-tile horizontal repeat by
4-tile vertical repeat):

```c
/* Auto-generated by gbkt ConvertZoneTilesetsTask (Plan 11.1-17) -- DO NOT EDIT */
/* Screen tile-index array for zone world1Area1Zone: tiles the 8x4 */
/* png2asset _tileset_map across the 32x32 screen */
/* tile grid (mapWidth * mapHeight = 1024 bytes). */
/* Consumed by SceneVisitor's _bkg_tiles_load_banked call in world1Area1Zone_enter. */
```

And the first data row of that array (line 19), showing the 0..7 ramp repeating
4× across the 32-column screen:

```c
const uint8_t _zone_world1Area1Zone_tilemap[32 * 32] = {
    0, 1, 2, 3, 4, 5, 6, 7, 0, 1, 2, 3, 4, 5, 6, 7, 0, 1, 2, 3, 4, 5, 6, 7, 0, 1, 2, 3, 4, 5, 6, 7,
    ...
```

The comment text "tiles the 8x4 png2asset _tileset_map across the 32x32 screen"
documents the bug: the 8×4 `png2asset` dedup table for world1-area1 is reused
modularly to fill a 32×32 grid, **discarding the actual platformer layout**.

## Evidence — Reference vs Generated Shape Mismatch

### Reference contract (GBDK platformer_template demo)

The reference's `World1Area1.c` (generated by upstream `png2asset` in `-map` mode
during the GBDK demo build) declares:

```c
const unsigned char World1Area1_map[1920] = {
    0x11,0x11,0x11,0x11,0x11,...   // 60 bytes per row, 32 rows
    ...
};
```

Reference dimensions (from `World1Area1.h`):

```c
#define World1Area1_WIDTH 480
#define World1Area1_HEIGHT 256
```

That is: **480×256 px = 60×32 tiles = 1920 tile indices**, sourced verbatim from
the world1-area1.png layout via png2asset's `-map` mode.

### gbkt-generated shape

`gbkt-examples/platformer-template/build/gbkt/generated/_zone_world1Area1Zone_tilemap.c`:

```c
const uint8_t _zone_world1Area1Zone_tilemap[32 * 32] = { ...8-tile-repeating-ramp... };
```

That is: **32×32 = 1024 bytes** of synthetic 0..7 / 8..15 / 16..23 / 24..31 ramp,
with the source PNG layout entirely discarded.

### Size + content delta

| metric                    | reference                       | gbkt 11.1-17 synthesis                |
| ------------------------- | ------------------------------- | ------------------------------------- |
| array length              | 1920 bytes                      | 1024 bytes (896 fewer)                |
| tilemap width             | 60 tiles                        | hard-coded 32                         |
| tilemap height            | 32 tiles                        | hard-coded 32                         |
| data source               | png2asset `-map` extraction     | `sourceMap[(y%H)*W + (x%W)]` modulo   |
| preserves source layout   | yes                             | **no** (any non-repeating PNG loses)  |

This explains the visual symptom in `02-gameplay.png` (commit e7e1bd48 re-shoot):
the gameplay tilemap loads into VRAM cleanly (the codegen + scene wiring fixes
in 12-19 work as designed), but the loaded bytes are the synthetic ramp instead
of the real world1Area1 layout. The screen shows a regular grid of platformer
tiles arranged in the 0..7 / 8..15 / 16..23 / 24..31 ramp pattern — **not** the
designed level geometry from world1-area1.png.

## Affected Zones

All 5 zones in Phase 12's platformer-template use the same synthetic-tilemap
path through ConvertZoneTilesetsTask. The dimensional mismatch ranges from
catastrophic (world1Area1 loses 896 bytes of layout) to merely cosmetic (title /
nextLevel — the 20×9 art is stretched and repeated into 32×32):

| zone           | source PNG          | source px   | reference tiles | reference len | gbkt-generated len | layout-preserved? |
| -------------- | ------------------- | ----------- | --------------- | ------------- | ------------------ | ----------------- |
| world1Area1Zone | world1-area1.png   | 480×256     | 60×32           | 1920          | 32×32 = 1024       | no — discards 896 bytes, plus 28 missing columns per row |
| world1Area2Zone | world1-area2.png   | (similar)   | (60×32)         | (1920)        | 32×32 = 1024       | no                                                       |
| world2Area1Zone | world2-area1.png   | (similar)   | (60×32)         | (1920)        | 32×32 = 1024       | no                                                       |
| titleZone       | title-screen.png   | 160×72      | 20×9            | 180           | 32×32 = 1024       | no — 20×9 stretched + vertical-repeated into 32×32 (visible artifact: "GBDK-2020 PLATFORMER TEMPLATE" stacked twice in 01-title.png) |
| nextLevelZone   | next-level.png     | 160×72      | 20×9            | 180           | 32×32 = 1024       | no — same stretching artifact as titleZone               |

The title-screen vertical-repeat artifact ("GBDK-2020 PLATFORMER TEMPLATE"
appearing twice in the visible 20×18 viewport) was previously noted as a "32×32
tilemap into 20×18 viewport" coincidence; with the defect identified, the real
cause is now clear: the 20×9 title bitmap is modulo-tiled into a 32×32 grid,
which means rows 0–8 hold the title art and rows 9–17 hold a **second copy** of
rows 0–8 (because `y % 9 = 0..8` for `y = 9..17`). That is the doubling visible
in `01-title.png`.

### Retroactive Banks Phase 11 impact

`gbkt-examples/banks` does NOT visibly regress today because its zone tilesets
(`pause-bg.png`, `play-bg.png`) are designed as small checkerboards whose 2×2 (or
similar) png2asset dedup table coincidentally aligns with the modulo-tiling
output. The bug has been latent since Plan 11.1-17 landed; Banks does not
distinguish "modulo-tiled dedup map" from "extracted source layout" at the
pixel level, so anchor 1's binding screenshot in `11-port-banks-gbdk-example-to-gbkt`
verifies (correctly) that the codegen pipeline emits a tilemap, but does NOT
verify that the tilemap matches the source PNG's actual layout.

When Phase 12.2 ships the fix, Banks' tilemap will continue to render
correctly because the real extraction produces the same checkerboard the synthetic
path happens to produce. No Banks-side rework needed.

## Why Plan 12-19 Cannot Ship

Plan 12-19's anchor 1 `must_haves` (from `12-19-PLAN.md` Task 2 §"how-to-verify")
include:

> Screenshot 02-gameplay.png visually shows the gameplay scene with tilemap +
> player metasprite visible (visual-evidence rule per D-10)
>
> world1Area1 tilemap rendered (NOT blank, NOT garbled)
>
> Player metasprite visible somewhere on screen (any pose)

The codegen + scene wiring deviations in 12-19 (commits 733770d6 and e7e1bd48)
land all three of those except the second clause: "world1Area1 tilemap
rendered". The tilemap IS rendered — but the bytes loaded are the synthetic
8-tile ramp, not the world1Area1 layout from `world1-area1.png`. Visually, the
screen shows a regular repeating grid of platformer terrain tiles. Per
CLAUDE.md §"Verification Methodology — Visual Evidence Rule" and the user-memory
rule `feedback_visual_evidence_for_visual_truths.md`, a visual truth (tilemap is
the world1Area1 layout) demands visual evidence; the current 02-gameplay.png
does not show the level layout, so the must-have is not met.

This cannot be fixed inside Plan 12-19 because:

1. The defect is in `ConvertZoneTilesetsTask` (a Gradle plugin task in
   `gbkt-gradle-plugin/`), not in any module 12-19 touches.
2. The fix requires re-routing through `png2asset -map -maps_only -source_tileset
   <tileset>` (or equivalent extraction logic), which changes the per-zone
   tilemap dimensions from a fixed 32×32 to **variable** dimensions matching the
   source PNG. That ripples through:
   - `_zone_<id>_tilemap.c` size (array length changes per zone)
   - `_zone_<id>_tileset.h` `_tilemap_WIDTH` / `_tilemap_HEIGHT` macros (currently
     hard-coded 32, must become per-zone)
   - `setup_current_level()` per-case body (correct already — uses the WIDTH /
     HEIGHT macros, so once they're per-zone the case bodies are
     auto-consistent)
   - `_bkg_tiles_load_banked` callers in `title_enter` / `nextLevel_enter`
     (currently pass literal `32u, 32u` — must become `_zone_<id>_tilemap_WIDTH,
     _zone_<id>_tilemap_HEIGHT`)
   - Banks Phase 11 regression-shield (its anchor 1 binding screenshot must be
     re-shot to lock the new shape, even though the visual is unchanged).
3. Per the user-memory rule
   `feedback_route_to_proper_phase_when_blast_radius_is_wide.md`, a fix that
   spans two modules (`gbkt-gradle-plugin` + downstream Banks regression-shield
   re-shoot) and includes a per-zone dimensional contract change is NOT a
   single-visitor / single-helper inline deviation. It belongs in a proper
   phase with research + spec + plan.
