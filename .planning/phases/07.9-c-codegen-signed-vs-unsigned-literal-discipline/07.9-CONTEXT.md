## Phase Boundary

Phase 07.9 fixes a single bug class in the GBDK backend codegen: **non-negative `CLiteral(n)` is emitted with a `u` suffix at every call site, which silently corrupts every `signedVar <|> CLiteral(n)` comparison via C's usual-arithmetic-conversion (C11 §6.3.1.8).**

The fix surface is `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/emit/CEmitter.kt` (line 421) and — depending on the chosen architecture — a subset of the 13 visitor files that construct `CLiteral` nodes.

<specifics>
## Specific Ideas

### The bug — concrete proof (from the Phase 07.4-34 evidence file 11)

`gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/emit/CEmitter.kt:421` emits every non-negative `CLiteral(n)` with a `u` suffix. Many visitors construct `CBinaryExpr(signedVar, "<", CLiteral(0))` to test whether a signed expression is negative. The emitted C reads:

```c
signedVar < 0u
```

C's usual arithmetic conversions (C11 §6.3.1.8) promote both operands of a comparison to a common type. When one side is `unsigned int` (the `0u`) and the other is a smaller signed type, the signed value is converted to `unsigned int` — turning negative values into very large positives:

```c
(INT16)-63 < 0u   →  (unsigned)-63 < 0u   →  0xFFFFFFC1 < 0    →  FALSE   (wrong)
(INT16)-63 > 8u   →  0xFFFFFFC1 > 8u                            →  TRUE    (wrong direction)
```

**Demonstrated runtime impact** in the racer ROM (post-Layer-1 fix):

```
# evidence/round-8-camera-and-track/11-runtime-green-camera-monotonic-advance-after-fix.txt
frame=baseline    _car_y=80 _camera_y=8
frame=baseline+30 _car_y=5  _camera_y=8
frame=baseline+60 _car_y=5  _camera_y=8
monotonic_advance=false
```

The camera follows the car for ~1 second (while `rawY ≥ 0`), then locks to `maxY=8` for every subsequent frame because `rawY < 0u` is always false. User's manual UAT (Racer ROM, 2026-05-12) corroborates: *"camera follows for about 1 second. Then it halts."*

### Blast surface (grep-verified)

The bug is **not** camera-specific. Approximate scale: ~17 signed-context `CLiteral` comparisons across 6 visitor files. A precise per-call-site signed/unsigned audit is a **deliverable of this phase (D-04)**, not a precondition for planning. See `<canonical_refs>` § "Confirmed bleeding sites" for the table.

### Why this didn't surface earlier

- Pong/Breakout don't use friction or deceleration — motion is bouncy reflection (`ballDx *= -1`), no negative-velocity decay.
- Pure-positive variables (UINT8 score, lives, X/Y position) compare correctly against `0u` — the unsigned-vs-unsigned case is fine.
- The bug only bites when **signed semantics matter**: velocity, deltas, signed deltas like `rawX = car_x - SCREEN_HALF`, accelerometer-style accumulation.
- Platformer is the first genre using these heavily, and Platformer hasn't had deep UAT yet (was queued for Phase 07.5, now blocked by 07.9).

### Architectural options on the table (researcher: present all four; do NOT pre-recommend one)

- **Option B — type-aware `CEmitter`.** Plumb a type-context through `emitExpr` recursion. Zero visitor changes; emitter resolves `CVar` → type. Silent-failure mode for new code paths.
- **Option C — split `CIntLiteral` / `CUIntLiteral` (or `CLiteral.signed` flag).** Visitors declare intent at construction site. Widest call-site migration (~30–50 sites). AST shows the signed/unsigned choice; intent visible at code review.
- **Option D — invert the default: bare `CLiteral(n)` emits `n` (no suffix); add `CUIntLiteral(n)` for the few cases needing `u`.** Smallest diff. **Requires SDCC validation per D-02** — the prior framing ("near-zero risk") was reasoning, not evidence.
- **Option E — always cast the literal at the visitor site** (`CCast(CI16, CLiteral(0))`). Most explicit form; uses Plan 07.4-34's `emitCastInner` to keep precedence-safe. Verbose at visitor sites.

The discussion may surface a fourth option not on this list — researcher should treat the four above as a starting frame, not a closed set.
