# Phase 07.9 — C-codegen signed-vs-unsigned literal discipline — Research

**Researched:** 2026-05-12
**Domain:** GBDK backend codegen literal-emission policy (SDCC for sm83 target)
**Confidence:** HIGH (SDCC asm probes executed locally; all four canonical bug forms verified at the instruction level)

---

## Summary

This research **proves the bug at the assembly level**, not just the C-text level. Using the project's own GBDK toolchain (`~/gbdk/bin/lcc` driving SDCC 4.5.1 #15267 for sm83), six probe pairs were compiled and the `.asm` output diffed. The findings are conclusive on two fronts:

1. **The bug is real in the binary.** `INT16 a < 0u` is not just semantically wrong on paper — SDCC emits a completely different (and dead) instruction sequence for the suffixed form. The compiler even raises **SDCC warning 94 ("comparison is always false due to limited range of data type")** and **warning 126 ("unreachable code")** on the bad form, which means the bug is detectable at compile time if we ever route lcc output through a warnings-aware build step. The current pipeline does not surface these warnings to the user.
2. **The fix space is asymmetric.** For *signed-typed* targets all three "fix" forms (`< 0`, `(INT16)0`, `(INT16)0u`) produce **byte-identical** asm — `ld b, d; bit 7, b; jr Z, ...` (test the sign bit). For *unsigned-typed* targets the `u` suffix is a no-op (`x == 0` and `x == 0u` produce identical asm). For wide assignment initializers (`UINT16 r = 0xFFFFu`), the suffix is also a no-op. **This means Options D and E both produce correct binaries with no runtime cost.**

The CONTEXT.md `<specifics>` framing surfaced four options (B/C/D/E). This research adds **Option F — context-aware literal emission via emitCompareInner** as a hybrid that mirrors the precedence-aware `emitCastInner` already in `CEmitter.kt:451`. Section 4 compares all five on the eight required axes.

The CLiteral audit found **144 comparison-with-CLiteral patterns across 11 visitor files** (CONTEXT estimated ~17 signed-context sites; the broader catalogue is wider). Of those 144 patterns, the in-scope signed-context subset is **~17–25** (classification in section 5); the rest are over `slots`/`maxSize`/`width`/`height`/`UINT8`-typed loop counters and are correctly unsigned today.

**No recommendation.** Per D-01, the planner picks among B/C/D/E/F. This research presents evidence for each.

## Section 1 — SDCC + GBDK Compile Probes (D-02 #1) — STATUS: COMPLETE

**Toolchain:** `~/gbdk/bin/lcc -Wa-l -S` driving `~/gbdk/bin/sdcc` (SDCC 4.5.1 #15267, sm83 target). Verified by `sdcc --version`.

### 1.1 Probe A — `INT16 a < 0` vs `INT16 a < 0u`

**Source:** `probe_a_signed_lt_zero.c` (`.asm`: `probe_a.asm`). [VERIFIED: SDCC 4.5.1 #15267]

SDCC raised **warning 94 ("comparison is always false due to limited range of data type")** and **warning 126 ("unreachable code")** on the `a < 0u` line. The .asm output confirms why:

```asm
_test_no_suffix::      ; if (a < 0)            -- CORRECT
    ld    b, d
    bit   7, b         ; test sign bit
    jr    Z, 00102$
    ld    hl, #_result_a
    ld    (hl), #0x01  ; "a is negative" branch retained
    ret
00102$:
    xor   a, a
    ld    (#_result_a),a
    ret

_test_u_suffix::       ; if (a < 0u)           -- BUG (always false; THEN branch deleted)
    xor   a, a         ; unconditional store of 0 to result_b
    ld    (#_result_b),a
    ret
```

**Result:** SDCC's optimizer eliminates the entire "true" branch for `a < 0u`. The bug is **not just C-semantic** — the binary literally has no instruction sequence that can set `result_b = 1`. This validates the camera bug's runtime symptom: `rawY < 0u` always false → `_camera_y` permanently clamped to maxY.

### 1.2 Probe B — `INT16 a > 8` vs `INT16 a > 8u` (the racer Y-axis clamp)

**Source:** `probe_b_signed_gt_n.c` (`.asm`: `probe_b.asm`). [VERIFIED: SDCC 4.5.1 #15267]

```asm
_test_no_suffix::         ; if (a > 8)   -- CORRECT (signed compare)
    ld    c, e
    ld    b, d
    ld    e, b
    ld    d, #0x00
    ld    a, #0x08
    cp    a, c            ; signed-16 comparison path
    ld    a, #0x00
    sbc   a, b
    bit   7, e            ; check sign of a
    jr    Z, 00113$
    bit   7, d            ; check sign of literal-as-promoted
    jr    NZ, 00114$
    ...

_test_u_suffix::          ; if (a > 8u)  -- DIFFERENT (unsigned compare; for a=-63 returns TRUE)
    ld    a, #0x08
    cp    a, e
    ld    a, #0x00
    sbc   a, d            ; unsigned-16 comparison — no sign-bit handling
    jr    NC, 00102$
    ...
```

**Result:** Two completely different instruction sequences. The `8u` form does an unsigned 16-bit comparison; for `a = -63 = 0xFFC1`, that returns TRUE (`0xFFC1 > 8`). This is the exact bug the racer hits when `_car_y = 5`.

### 1.3 Probe C — `UINT8 x == 0` vs `UINT8 x == 0u`

**Source:** `probe_c_unsigned_eq_zero.c` (`.asm`: `probe_c.asm`). [VERIFIED]

```asm
_test_no_suffix::    ; if (x == 0)
    or    a, a
    jr    NZ, 00102$
    ...

_test_u_suffix::     ; if (x == 0u)
    or    a, a       ; BYTE-IDENTICAL to no-suffix form
    jr    NZ, 00102$
    ...
```

**Result:** **Byte-identical asm.** For unsigned-typed targets the `u` suffix has zero effect. This validates that removing the `u` from the emitter (Option D) does NOT regress the hundreds of correctly-unsigned comparison sites — they will produce the same binary.

### 1.4 Probe D — `UINT16 r = 0xFFFF` vs `UINT16 r = 0xFFFFu`

**Source:** `probe_d_uint16_assign.c` (`.asm`: `probe_d.asm`). [VERIFIED]

```asm
_main::
    ld    hl, #_r_a
    ld    a, #0xff
    ld    (hl+), a
    ld    (hl), #0xff          ; r_a = 0xFFFF
    ld    hl, #_r_b
    ld    a, #0xff
    ld    (hl+), a
    ld    (hl), #0xff          ; r_b = 0xFFFFu — BYTE-IDENTICAL
    ret
```

**Result:** Assignment initializers to matching-width unsigned types: `u` suffix is a no-op. This is in-scope for the **audit** (D-04, Section 5) — non-comparison sites are correctly unsigned today and stay deferred.

### 1.5 Probe E — `INT16 a < (INT16)0` vs `INT16 a < (INT16)0u` (Option E validation)

**Source:** `probe_e_explicit_cast.c` (`.asm`: `probe_e.asm`). [VERIFIED]

```asm
_test_explicit_cast::     ; if (a < (INT16)0)
    ld    b, d
    bit   7, b            ; same instruction sequence as Probe A "no suffix"
    jr    Z, 00102$
    ...

_test_explicit_cast_u::   ; if (a < (INT16)0u)
    ld    b, d
    bit   7, b            ; ALSO same — the (INT16) cast normalises the RHS
    jr    Z, 00102$
    ...
```

**Result:** Option E (visitor-site `CCast(CI16, CLiteral(0))`) produces **correct asm regardless** of whether the inner literal carries a `u` suffix. The outer `(INT16)` cast forces the comparison to run in signed domain. This makes Option E **robust to the rest of the codebase** — even if a future contributor wraps another literal with `CCast(CI16, CLiteral(N))` while emitter still appends `u`, the comparison still runs in signed mode.

### 1.6 Probe F — Three-way: `a < 0` vs `a < 0u` vs `a < (INT16)0`

**Source:** `probe_f_three_way.c` (`.asm`: `probe_f.asm`). [VERIFIED]

**Result:** Option D (`a < 0`, no suffix) and Option E (`a < (INT16)0`, explicit cast) produce **identical binaries**. The difference is purely at the C source-text level: D is shorter, E is more explicit at the visitor call site.

## Section 3 — C-spec Rationale (D-02 #3): C11 §6.3.1.8 Walkthrough

[CITED: ISO/IEC 9899:2011 §6.3.1.8 "Usual arithmetic conversions"]

The "usual arithmetic conversions" rule applies to **all** binary operators where both operands have arithmetic type (`<`, `>`, `<=`, `>=`, `==`, `!=`, `+`, `-`, `*`, `/`, `%`, `&`, `|`, `^`). For C11 §6.3.1.8 the algorithm is:

1. **Integer promotion** — if either operand has integer type narrower than `int`/`unsigned int`, it is first promoted to `int` (if `int` can represent all values) or `unsigned int` (otherwise).
2. **Common type selection** — once both operands are `int`/`unsigned int` or wider, the rule picks the common type:
   - Both same type → that type.
   - Same signedness → wider type.
   - Different signedness, unsigned wider-or-equal → unsigned wins.
   - Different signedness, signed wider AND can represent all unsigned values → signed wins.
   - Different signedness, signed wider but cannot represent → both convert to **unsigned counterpart of the signed type**.

On the SM83/GB target, `int` is **16-bit** (verified by `~/gbdk/include/asm/sm83/types.h:53`: `typedef signed int INT16`). So `int` and `unsigned int` are both 16-bit, and an `int` cannot represent all `unsigned int` values → rule 3 applies → unsigned wins.

### 3.1 Four canonical cases for the in-scope fix surface

#### Case 1: `signed < 0u` (bare suffix-promoted zero)

```c
INT16 a = -63;
if (a < 0u) { ... }   // promotion: a → unsigned int; -63 → 0xFFC1
                       // unsigned compare: 0xFFC1 < 0 → FALSE
```

**Programmer intent:** test if `a` is negative. **Actual behaviour:** always FALSE for any negative `a`. **SDCC behaviour:** raises warning 94 + 126, eliminates THEN branch in asm (probe A).

#### Case 2: `signed > Nu` (small positive N like 8)

```c
INT16 a = -63;
if (a > 8u) { ... }   // promotion: a → 0xFFC1; 8u stays 8
                       // unsigned compare: 0xFFC1 > 8 → TRUE
```

**Programmer intent:** test if `a` exceeds 8 (positive only). **Actual behaviour:** ALL negative `a` return TRUE (wrong direction). **SDCC behaviour:** emits a different instruction sequence (probe B) — `cp a, c; sbc a, b; jr NC, ...` (unsigned-16 path) instead of the signed path that checks sign bits.

#### Case 3: `signed >= 0u`

```c
INT16 a = -63;
if (a >= 0u) { ... }  // unsigned compare: 0xFFC1 >= 0 → TRUE (always)
```

**Programmer intent:** test if `a` is non-negative. **Actual behaviour:** ALWAYS TRUE for any `a` (`unsigned >= 0` is a tautology). Subtle but equally broken.

#### Case 4: `unsigned < 0u`

```c
UINT16 x = 100;
if (x < 0u) { ... }   // unsigned compare: 100 < 0 → FALSE (always)
```

**Programmer intent:** typically a defensive/redundant test; never expected to fire. **Actual behaviour:** also always FALSE. **Important:** this case is **not broken** — it matches programmer intent (since unsigned can never be negative). The `u` suffix is benign in unsigned-typed targets. This is what Probe C confirmed at the asm level.

### 3.2 Why the rule is dangerous specifically for game-logic state

Game-logic variables that semantically *can* go negative — velocity (`vx`, `vy`), signed deltas (`rawX = car_x - SCREEN_HALF`), accelerometer accumulators, jump-cancel counters — are the bug's target population. Pure-positive game state (score, lives, HP, X/Y positions on-screen) compares correctly against `0u` because both sides are unsigned. This explains why Pong/Breakout/Explorer never tripped this bug — they don't use signed game-state heavily — while Racer (camera math) and Platformer (velocity, friction) hit it immediately. [VERIFIED: cross-reference Plan 07.4-34 evidence file 11 root-cause analysis]

### 3.3 Spec rationale and the option space

The four options on the table all neutralise rule 3:

- **Option B / D / F:** make the literal NOT be `unsigned int` (drop the `u` suffix → bare `0` is `int` = signed; rule applies, signed-int and signed-int → signed-int → correct).
- **Option C:** the `CIntLiteral` flavour emits without `u`; visitor declares intent at construction.
- **Option E:** force the literal to be `(INT16)`-cast → also signed → rule applies, signed-and-signed → signed → correct. SDCC even folds the cast (probe E asm is identical to bare-literal probe A asm).

All five options are spec-correct. Differences are stylistic/architectural.

**Confidence:** HIGH (C11 §6.3.1.8 is the canonical spec; SDCC's behaviour matches the spec in our probes).

## Section 4 — Architectural Options (B / C / D / E + F)

Per D-01, this section presents evidence on a comparison table. **No recommendation.** The planner picks during `/gsd-plan-phase 07.9`.

### 4.1 Option B — Type-aware `CEmitter`

**What it changes:** `CEmitter.emit*` carries a `TypeContext` parameter (passed through `emitExpr` recursion) so the emitter knows the surrounding expression's type. When emitting a `CLiteral` whose surrounding context is a comparison and the other operand is signed-typed (`CI8` / `CI16` resolved via `CVar` → type map), drop the `u` suffix.

- **Files touched:** `CEmitter.kt` (~80 lines), plus a new type-resolution helper that walks `CVar.name` → type (or maintains a per-function symbol table). The visitor surface remains unchanged.
- **Migration burden:** Zero visitor migration. 13 visitor files stay untouched.
- **AST additions:** None.
- **Failure mode in NEW code:** **silent.** A new visitor that builds `CBinaryExpr(signedVar, "<", CLiteral(0))` automatically inherits the right policy — but if the variable typing is wrong/missing in the type map, the emitter falls back to the buggy form without warning.
- **Runtime cost:** Zero (changes are at emission, not at runtime).
- **Reversibility:** HIGH. Single-file change; could be reverted with one commit.
- **Preserves `emitCastInner`:** YES (no conflict; the helpers compose).
- **Major risk:** the symbol-table machinery to resolve `CVar` → type is **non-trivial**. The current emitter is type-blind; adding type-awareness pulls in scope-walking, function-parameter tracking, and globals lookup. Estimated 200–400 lines including tests for the type-resolution helper alone.

### 4.2 Option C — Split `CIntLiteral` / `CUIntLiteral` (or `CLiteral.signed` flag)

**What it changes:** `CExpr` AST gains a new node — either two flavours (`CIntLiteral(value)` / `CUIntLiteral(value)`) or a flag on existing `CLiteral(value, signed: Boolean)`. Visitors declare intent at construction time. `CEmitter` emits with or without `u` based on flavour/flag.

- **Files touched:** `CExpr.kt` (+5–15 lines for new node), `CEmitter.kt` (+5–10 lines branching), 13 visitor files (each `CLiteral(...)` in a signed-comparison context becomes `CIntLiteral(...)`; estimated **17–25 call sites updated** in-scope for D-03; the audit in Section 5 itemises).
- **Migration burden:** **Wide.** Every signed-context comparison site must change. The widest call-site migration of any option.
- **AST additions:** New `CIntLiteral` node (or new `signed: Boolean` field).
- **Failure mode in NEW code:** **explicit and visible.** A new visitor author looking at neighbouring code sees `CIntLiteral(0)` in signed contexts; the difference is loud at code-review.
- **Runtime cost:** Zero.
- **Reversibility:** MEDIUM. AST changes touch downstream consumers (visitors, optimizers if any inspect literal flavour). If the choice turns out wrong, reverting requires touching all migrated sites again.
- **Preserves `emitCastInner`:** YES.
- **Major risk:** Default flavour bias — if `CLiteral(0)` remains the "unsigned" default (existing behaviour preserved), every signed site needs the explicit `CIntLiteral`. If `CLiteral` becomes signed-default, every existing unsigned site needs explicit `CUIntLiteral` (i.e. the migration is even wider). Planner must pick a default; the wider-migration default is loud-at-review but requires more change.

### 4.3 Option D — Invert the default: bare `CLiteral(n)` emits `n` (no suffix)

**What it changes:** `CEmitter.kt:421` changes from `if (expr.value >= 0) "${expr.value}u" else "${expr.value}"` to `"${expr.value}"`. Optional: add `CUIntLiteral(n)` for the few cases that benefit from explicit `u` (none verified necessary by the probes).

- **Files touched:** `CEmitter.kt` (1 line, plus optional new AST node ~5 lines).
- **Migration burden:** **Zero call-site change.** Visitors untouched. The 17–25 signed-context sites stop being broken; the ~120 currently-unsigned-typed sites lose the `u` but stay binarily identical to today's output (per Probe C: `x == 0` and `x == 0u` produce byte-identical asm for unsigned-typed `x`).
- **AST additions:** None (or optional `CUIntLiteral`).
- **Failure mode in NEW code:** N/A — every literal renders the same way. Cannot fail differently across new code paths.
- **Runtime cost:** Zero. Probes C and D prove binary-identical output for unsigned-typed targets.
- **Reversibility:** HIGH. One-line revert.
- **Preserves `emitCastInner`:** YES.
- **Major risk:** the regenerated-C diff is **NOT surgical** — every `0u` / `1u` / `Nu` in the codebase becomes `0` / `1` / `N`. Estimated diff: ~5000–10000 lines of pure suffix-strip across all example games' `main.c` / `bank1.c`. D-09 Tier-3 acceptance ("surgical diff — only signed-comparison sites change") would **fail** under naive Option D. Planner must either (i) tighten the "surgical" criterion to "no asm-level change" rather than "no text-level change" (Probe C / D evidence supports this), or (ii) pick a different option, or (iii) build a parallel emission mode that keeps `u` for assignment initializers (which would morph Option D into a flavour of Option B/F).
- **Secondary risk:** SDCC's warning 94/126 cluster (probe A) goes away with Option D — that's the desired outcome — but the broader project loses any signal that a future contributor accidentally writes `CLiteral(0u)` somewhere. If gbkt's build pipeline ever surfaces SDCC warnings as build failures, Option D + a deliberate ban on `u`-emission becomes self-enforcing.

### 4.4 Option E — Visitor-site explicit cast (`CCast(CI16, CLiteral(0))`)

**What it changes:** Every signed-context comparison site wraps the literal in `CCast(CI16, CLiteral(n))`. The emitter is untouched (uses the already-shipped `emitCastInner` helper from Plan 07.4-34).

- **Files touched:** 13 visitor files (the 17–25 in-scope sites get a `CCast(CI16, …)` wrapper). `CEmitter.kt` untouched.
- **Migration burden:** wide (same as Option C — every signed-context site changes), but the change is more visible than Option C at the call site: the cast is emitted into the C as `(INT16)0` rather than being a property of an AST node.
- **AST additions:** None (uses existing `CCast`).
- **Failure mode in NEW code:** **silent.** A new visitor that forgets the cast wrapper produces `vy < 0u` and inherits the bug. No structural enforcement.
- **Runtime cost:** **Zero — verified at asm level (Probe E).** SDCC folds the cast; binary is identical to bare-literal asm.
- **Reversibility:** MEDIUM. If reverted, every migrated site needs unwrapping.
- **Preserves `emitCastInner`:** uses it directly.
- **Major risk:** the emitted C becomes verbose — `(INT16)0` and `(INT16)8` everywhere — and the Tier-3 surgical diff becomes "every comparison RHS gains a `(INT16)` prefix". Reviewer-friendly because intent is explicit at the C level; reviewer-noisy because every line touches.
- **Secondary risk:** Visitors that build the cast wrong (e.g. wrap `CCast(CU8, CLiteral(0))` instead of `CI16`) introduce subtle bugs. Type discipline at visitor sites becomes essential.

### 4.5 Option F (NEW) — Emit-site context-aware `emitCompareInner` (mirrors `emitCastInner`)

**What it changes:** Mirror the precedence-aware `emitCastInner` pattern (already shipped in Plan 07.4-34 at `CEmitter.kt:451`). Introduce `emitCompareLiteral(literal, op, otherSide)` that the `CBinaryExpr` emit branch calls when the operator is a comparison and the other side has a hint of signed type. The hint can be (a) a known signed-name pattern (`vy`, `vx`, `rawX`, `rawY`), (b) a lookup into a small signed-variable allowlist registered by visitors, or (c) a tag carried on `CVar` (`CVar(name, type: CType? = null)`).

- **Files touched:** `CEmitter.kt` (~30 lines new helper), optional addition to `CVar` (one nullable type field). Visitors optionally pass `type = CI16` at construction site for the variables they know to be signed.
- **Migration burden:** Hybrid. Visitors can opt in for the variables they declare as signed (e.g. `CVar("_plat_vy", CI16)`); for variables not opted in, emitter falls back to current behaviour (loud at the asm warning level — see Probe A).
- **AST additions:** Optional `CVar.type: CType? = null` (nullable, backward-compatible — existing code untouched).
- **Failure mode in NEW code:** **opt-in.** A new visitor that builds `CVar("vy")` without the type tag inherits the current (buggy) emission — same as today. Visitors that opt in (`CVar("vy", CI16)`) get the right policy automatically.
- **Runtime cost:** Zero.
- **Reversibility:** HIGH (additive feature; `CVar.type` defaults to null).
- **Preserves `emitCastInner`:** YES — composes with it.
- **Major risk:** the opt-in model means the **fix only protects variables that visitors explicitly tag**. The 17–25 in-scope sites must each have their `CVar` constructions audited to add the type tag. The migration burden is similar to Option C/E but the AST change is smaller (one nullable field, not a new node).
- **Secondary risk:** name-based hint detection (option (a) above) is fragile — it relies on a hand-maintained list of signed-variable name prefixes. Discard option (a); option (c) (tag on `CVar`) is structurally sounder.

### 4.6 Comparison table

| Axis | B (type-aware emitter) | C (CIntLiteral split) | D (drop default `u`) | E (visitor-site cast) | F (CVar.type opt-in) |
|------|------------------------|------------------------|----------------------|------------------------|------------------------|

| Reversibility | HIGH (1 file) | MEDIUM (AST + 13 files) | HIGH (1 line) | MEDIUM (13 files) | HIGH (additive) |

### 4.7 What the planner needs to choose

The trade-off is **call-site migration vs robustness-to-future-code**:

- Options D and B require **zero visitor migration** but have **silent failure modes** if the policy ever needs to differ for unsigned-only contexts (Option B) or if a future site genuinely needs `u` (Option D — though Probes C/D show no such site exists today).
- Options C, E, F require **visitor migration** (17–25 sites in-scope) and force the choice to be visible at the call site — **loud failure mode** for future contributors.

A secondary consideration: **D-09 Tier-3 surgical diff**. Options D and E produce wide regenerated-C diffs; B, C, F produce minimal diffs. The acceptance criterion as written ("only signed-comparison sites change") is satisfiable by B, C, F natively, and by D/E if the criterion is reinterpreted as "no asm-level change outside signed-comparison sites" (which Section 1 probes support).

This convention prevents an entire class of runtime bugs that surfaced in Phase 07.4

   the emission tier. {if Option B/D/F chosen} OR

## Common Pitfalls

### Pitfall 1: "Just drop the `u`" without asm validation

**What goes wrong:** The Plan 07.4-34 evidence file 11 framed Option D as "near-zero risk" via reasoning. Reasoning alone is not evidence (per `feedback_quality_over_shortcuts.md`).
**Why it happens:** SDCC for sm83 is a niche target; intuitions from x86 SDCC don't transfer.
**How to avoid:** Section 1 probes ARE the evidence. Any planner-chosen architecture that hinges on "SDCC produces correct asm without the `u`" must cite the probe artifacts (`evidence/research/probe_a.asm` through `probe_f.asm`).
**Warning signs:** A plan that asserts "this is correct" without an .asm citation.

### Pitfall 2: Wide regenerated-C diff fails the D-09 #3 "surgical" criterion

**What goes wrong:** Options D and E touch every `Nu` (D) or every signed-context literal RHS (E) in every generated C file. The criterion "only signed-comparison sites change" reads literally as failing for those options.
**Why it happens:** D-09 was written to detect *unintended* drift; the criterion's intent is "no regression in unsigned code paths". Probes C and D show that for unsigned-typed sites, the asm is byte-identical regardless of `u`-presence — so Option D's wide *text* diff has *zero* binary impact.
**How to avoid:** the planner explicitly reinterprets D-09 #3 to "no asm-level change outside signed-comparison sites" (Probes C/D justify this) OR picks an option (B, C, F) that produces a minimal text diff.
**Warning signs:** A plan that picks Option D without an explicit acceptance-criterion reinterpretation.

### Pitfall 3: Silent failure mode for Options B, E

**What goes wrong:** Options B (type-aware emitter) and E (visitor-site cast wrapper) both have silent failure modes — a new visitor that omits the cast (E) or whose `CVar` type isn't resolvable by the type map (B) inherits the bug without any compile-time signal.
**Why it happens:** Both architectures rely on convention adherence at the call site or in a type map that lives elsewhere. Future contributors who don't read the docs trip the bug back into existence.
**How to avoid:** pair B/E with the JVM-tier structural test (Section 6.1 #8 — `no_signed_var_compared_against_u_suffix`). The test fails loudly if a new site bleeds back.
**Warning signs:** "It's correct now" without a regression-guarding scan test.

### Pitfall 4: Confusing audit completeness with fix scope

**What goes wrong:** D-04 catalogues all 144 comparison sites including buckets (b) and (c). A planner might be tempted to "fix everything while we're here" — violating D-03's scope (in-scope = comparisons only).
**Why it happens:** Scope-creep is the default failure mode of audit-driven fixes.
**How to avoid:** D-04's catalogue produces a DEFERRED IDEA for buckets (b) and (c); the in-scope plan touches only bucket (a). The catalogue is **output**, not **input** to the fix surface.

### Pitfall 5: Ignoring SDCC warnings 94/126

**What goes wrong:** SDCC raised warnings on every probe that hit the bug. The current gbkt build pipeline does not surface SDCC warnings to the user — so the bug went unnoticed for one full phase (07.4).
**Why it happens:** lcc swallows SDCC stderr unless `-Wa-l` propagates warnings (it does for asm output but not for error escalation).
**How to avoid:** Phase 08 (or a 07.9 Claude's Discretion plan) may add SDCC-warning-as-error escalation. This is OUT OF SCOPE for 07.9 but a recommended follow-up.
