# Phase 13.8: Code Review Report

**Reviewed:** 2026-06-06
**Depth:** standard
**Files Reviewed:** 16
**Status:** issues_found

## Summary

Phase 13.8 closes deferred WR debt across the palette/sprite codegen surface under a strict
D-03 byte-identity contract. The implementation is high quality: the new IR fields
(`MetaspriteIR.initialSubPaletteSlot`, `MetaspriteIR.sceneId`, `SceneIR.allocatedZoneBank`)
are nullable-with-null-default with correct `?:` fallbacks, `SceneIR.equals()`/`hashCode()`
correctly include the new field (guarded by `SceneIRTest`), the serializer correctly omits the
pipeline-transient `allocatedZoneBank` and conditionally serializes the metasprite fields, and
the byte-identity contract holds for all currently-buildable example games.

I verified the byte-identity-critical claims:
- `buildMetaspriteSpritePaletteStatements` (`GBDKPipelineV2.kt:5076-5121`): both arms fall back to
  list-index / `proceduralCount + idx` when slots are null → zero delta for shipped single-metasprite games.
- `checkPalettePolarity` (`PngUtils.kt:271-348`): the `to5()` RGB555 quantization is arithmetically
  correct (`to5(100) == to5(103) == 98`), the Spearman tie-averaging `(i+1+j)/2.0` is correct, and
  the per-sub-palette windowing (`base until n step 4`, `subList(base, base+4)`) is off-by-one-free.
- `parsePaletteRgb555Values` (`PngUtils.kt:374-405`): uniform null-for-empty contract; both call
  sites (`ConvertSpritesTask.kt:461`, `ConvertZoneTilesetsTask.kt:359`) delegate correctly.
- `prePermuteIndexedPng` determinism: `gbkt_permuted_${stemName}.png` is stable across rebuilds;
  `temporaryDir` relocation moves temp files out of `@OutputDirectory` (cacheability fix is sound).

The findings below are NOT byte-identity violations for shipped games. The most significant is a
**latent correctness regression** introduced by the `SceneIR.allocatedZoneBank` "field-over-lookup"
refactor: it is correct for the single-zone scenes the DSL allows today, but it silently breaks the
moment the deferred multi-zone-per-scene feature lands — and a misleading comment claims the
opposite, which will cause the future implementer to trust broken code.

No Critical issues. Three Warnings, three Info.

## Warnings

### WR-01: `allocatedZoneBank` field-over-lookup silently emits the wrong bank for multi-zone scenes (latent regression + misleading comment)

**File:** `gbkt-backend-gbdk/.../codegen/visitor/SceneVisitor.kt:191-197`,
`gbkt-backend-gbdk/.../codegen/pipeline/GBDKPipelineV2.kt:642-650`

**Issue:**
Before 13.8, `SceneVisitor` resolved the `_bkg_tiles_load_banked(bank, ...)` literal *per zone* via
`zoneBankAllocation[zoneId]`. The 13.8 refactor populates a single `SceneIR.allocatedZoneBank` with
only the FIRST zone's bank:

```kotlin
// GBDKPipelineV2.buildCFiles
val zoneBank = scene.zoneRefs.firstNotNullOfOrNull { bankAllocation[it] }
if (zoneBank != null) scene.copy(allocatedZoneBank = zoneBank) else scene
```

and `SceneVisitor` reads it INSIDE the per-zone `flatMap` with a `?:` that short-circuits the
per-zone lookup:

```kotlin
scene.zoneRefs.flatMap { zoneId ->
    ...
    val bank =
        scene.allocatedZoneBank        // <-- non-null short-circuits for EVERY zone
            ?: zoneBankAllocation[zoneId]
            ?: error(...)
```

For a scene with two zone refs whose zones `allocateZoneBanks` placed in *different* banks (the
auto-allocator at `GBDKPipelineV2.kt:766-780` opens new banks via bin-packing, so this is reachable),
every zone in the scene now emits the FIRST zone's bank. The non-first zones get a wrong
`SWITCH_ROM`/`_bkg_tiles_load_banked` bank → reads tile data from the wrong ROM bank.

This is currently *latent* (not a byte-identity violation for shipped games) only because the DSL
hard-limits scenes to one zone: `SceneBuilder.kt:152` `require(zoneRefs.isEmpty()) { "... multi-zone-per-scene deferred to Phase 13 ..." }`. The fallback CANNOT fire for the case it claims to cover.

Worse, the comment at `SceneVisitor.kt:188-191` and the field KDoc at `SceneIR.kt:54-56` explicitly
claim the fallback handles "Multi-zone scenes where allocatedZoneBank stores only the first zone's
bank" — but the `?:` operator means `zoneBankAllocation[zoneId]` is *never consulted* once
`allocatedZoneBank` is non-null. A future Phase-13 implementer enabling multi-zone-per-scene will
read this comment, trust it, and ship a wrong-bank bug. This is the exact class of "structural
single-source guarantee" the refactor was meant to *prevent*.

**Fix:** Either (a) make the field a per-zone map, or (b) keep the per-zone lookup authoritative and
only use the field when the scene has exactly one zone ref, and correct the comments:

```kotlin
// SceneVisitor — read per-zone authoritatively; field is a single-zone convenience only
val bank =
    zoneBankAllocation[zoneId]
        ?: scene.allocatedZoneBank   // fall back to the field only when the map lacks the zone
        ?: error("Zone '$zoneId' bound to scene '${scene.id}' has no bank allocation.")
```

and fix the KDoc/comment to state plainly that `allocatedZoneBank` is a single-zone-scene field and
does NOT carry per-zone banks for multi-zone scenes. Add a `ZoneBankFieldTest` case with a
two-zone scene whose zones land in banks 2 and 3, asserting BOTH literals are emitted (currently it
would emit `2u` twice).

### WR-02: No collision guard when multiple metasprites declare the same `initialSubPaletteSlot`

**File:** `gbkt-backend-gbdk/.../codegen/pipeline/GBDKPipelineV2.kt:5076-5121`

**Issue:**
The new `initialSubPaletteSlot` path lets each metasprite name its own OBJ sub-palette slot:

```kotlin
val slot = ms.initialSubPaletteSlot ?: listIdx                  // procedural arm
val slot = ms.initialSubPaletteSlot ?: (proceduralCount + idx)  // asset-driven arm
```

There is no validation that two metasprites do not declare the same slot, and no validation that an
asset-driven `initialSubPaletteSlot` does not collide with a procedural one (the two arms are
computed independently and concatenated at line 5121). If two metasprites declare slot 2, the
pipeline silently emits two `set_sprite_palette(2u, 1u, ...)` calls — the second overwrites the
first's OBJ palette RAM, producing wrong colors at runtime with no diagnostic. The whole point of
the feature (per-13.7-DIAGNOSTIC) is to make the upload slot match the draw-path slot; a silent
collision defeats that and is hard to debug because both calls "look" correct.

Because the field is opt-in and null-default, this does not affect byte-identity, but a duplicate
slot is a plausible authoring mistake that the codegen should reject loudly rather than emit broken C.

**Fix:** After computing both arms, detect duplicate slots and fail fast (or warn) before returning:

```kotlin
val all = proceduralStatements + assetDrivenStatements
val slots = (proceduralMetasprites.mapIndexed { i, ms -> ms.initialSubPaletteSlot ?: i } +
    assetDrivenMetasprites.mapIndexedNotNull { i, ms -> /* mirror the suppression filter */ })
val dupes = slots.groupingBy { it }.eachCount().filter { it.value > 1 }.keys
require(dupes.isEmpty()) {
    "Metasprite OBJ sub-palette slot collision on slot(s) $dupes — two metasprites upload to the " +
        "same set_sprite_palette slot; the later upload overwrites the earlier (declare distinct " +
        "initialSubPaletteSlot values)."
}
```

### WR-03: `parsePaletteRgb555Values` integer-fallback parses out-of-range RGB555 tokens silently

**File:** `gbkt-gradle-plugin/.../tasks/PngUtils.kt:396-404`

**Issue:**
The raw-integer fallback in the consolidated parser accepts any int/hex token without validating it
is a legal 15-bit RGB555 value (0..0x7FFF):

```kotlin
body.split(",").forEach { token ->
    val trimmed = token.trim()
    val v = trimmed.toIntOrNull()
        ?: trimmed.removePrefix("0x").toLongOrNull(16)?.toInt()
        ...
    if (v != null) result.add(v)
}
```

`checkPalettePolarity` then decomposes each value via `v and 0x1F`, `(v shr 5) and 0x1F`,
`(v shr 10) and 0x1F`. A token with bits above bit 14 (e.g. an accidental 32-bit constant or a value
> 0x7FFF) is silently truncated by the masks, producing a wrong luminance and potentially a spurious
or missed inversion WARNING. Since the parser is now the single source of truth for two call sites,
the lenient contract is a drift hazard exactly like the one IN-02 in the KDoc claims to have fixed.
The consequence is bounded (this only feeds a non-fatal WARNING), so it is a Warning, not a Blocker.

**Fix:** Clamp/validate in the fallback, or document that the masks intentionally ignore high bits.
Minimal robustness:

```kotlin
if (v != null && v in 0..0x7FFF) result.add(v)
```

(or log a debug message and skip tokens outside the RGB555 range rather than feeding garbage into the
polarity comparator).

## Info

### IN-01: `MetaspriteIR` serializer round-trip drops most fields (pre-existing, now adjacent to new fields)

**File:** `gbkt-ir/.../GameIRSerializer.kt:336-359`

**Issue:** `serializeMetaspriteIR`/`deserializeMetaspriteIR` only persist `id`, `frames`,
`sourceLocation`, `initialSubPaletteSlot`, and `sceneId`. The other `MetaspriteIR` fields
(`posXVarName`, `posYVarName`, `idxVarName`, `rotVarName`, `mirrorDedup`, `spritePath`,
`frameCount`, the `spriteMode`/pivot/frame cutting flags) are NOT round-tripped — a deserialized
`MetaspriteIR` loses them. This pre-dates 13.8, but 13.8 added two of the five serialized fields, so
it is worth flagging: if any consumer relies on `GameIRSerializer` round-tripping metasprites
(e.g. a future cache layer), the new `sceneId`/`initialSubPaletteSlot` survive while `spritePath`
does not, which is an inconsistent and surprising partial serialization.

**Fix:** Out of scope for 13.8, but track: either serialize all `MetaspriteIR` fields or document
why the serializer intentionally persists only a subset (the codegen path uses the in-memory IR, not
the JSON, so this may be deliberately partial — say so in the KDoc).

### IN-02: `checkPalettePolarity` requires emitted size to be a multiple of 4, silently returning false otherwise

**File:** `gbkt-gradle-plugin/.../tasks/PngUtils.kt:288-290`

**Issue:** The guard `if (n % subPaletteSize != 0) return false` treats a non-multiple-of-4 emitted
palette as "not invertible" and skips the check entirely. png2asset normally emits multiples of 4,
but if a future png2asset version emits a 3- or 5-entry palette, the polarity WARNING silently goes
dark with no diagnostic — the guard is indistinguishable from a genuine "not inverted" result. This
is acceptable for a non-fatal advisory, but a one-line `logger`/debug note (the function has no
logger today) or a doc note that this path is a silent skip would prevent a confusing
"why did the WARNING stop firing" investigation later.

**Fix:** Documentation-only; note in the KDoc that a non-multiple-of-4 emitted palette is a silent
skip (already partially covered in the degenerate-guards list, but the consequence — silent loss of
the advisory — is not called out).

### IN-03: `firstNotNullOfOrNull` populates the field from the first *allocated* zone, not the first *referenced* zone

**File:** `gbkt-backend-gbdk/.../codegen/pipeline/GBDKPipelineV2.kt:644`

**Issue:** The comment at line 638 says "Each scene gets the bank of its **first** resolved zone
ref", but `scene.zoneRefs.firstNotNullOfOrNull { bankAllocation[it] }` returns the bank of the first
zone ref that *has an allocation entry*, which is not necessarily `zoneRefs[0]` if `zoneRefs[0]` is
absent from `bankAllocation`. With today's single-zone DSL this is moot, but combined with WR-01 it
compounds the confusion for the future multi-zone implementer. Tighten the comment to match the code
(or vice versa) when WR-01 is addressed.

**Fix:** Align comment and code; fold into the WR-01 fix.
