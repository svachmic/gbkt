## Summary

Phase 13.8 is a debt-closure phase with zero net-new DSL/runtime behavior. It addresses three clusters: (1) a pure-function rewrite of the `PngUtils.checkPalettePolarity` comparator plus consolidation of duplicated RGB parse/pack logic across two Gradle tasks; (2) three architectural latents in `GBDKPipelineV2` that create silent correctness hazards for multi-scene/multi-metasprite games; and (3) a set of advisory cleanups from post-phase code reviews. The hardest constraint is byte-identity: all architectural changes MUST preserve generated-C output for the two shipped ROMs (platformer-template, metasprites) exactly.

**Key finding (Req 6 — hardcoded 2u):** Phase 13.5 already migrated `PlatformerExtensions.kt` away from raw `cEmit("_bkg_tiles_load_banked(2u, ...")`. The current code at `SceneVisitor.kt:328` uses `CLiteral(bank)` where `bank = zoneBankAllocation[zoneId]` (from `allocateZoneBanks`). The `2u` literal visible in tests and evidence files is the *generated C output value* for the current single-zone layout, not a hardcoded literal in Kotlin source. Req 6 therefore is a **structural improvement**: add a `SceneIR.allocatedZoneBank: Int?` field populated by `allocateZoneBanks` so the IR itself carries the single-source truth, preventing future divergence if `allocateZoneBanks` were called with inconsistent inputs at different pipeline stages.

**Key finding (Req 5 — sub-palette slot):** `MetaspriteIR` has no `initialSubPaletteSlot` or equivalent field. The `_<id>_subPalette` is a pure runtime variable (initialized to 0). Implementing Req 5 as "slot derived from declared sub-palette" requires adding an `initialSubPaletteSlot: Int?` field to `MetaspriteIR` (default null → falls back to list-index, preserving byte-identity for shipped cases).

**Key finding (Req 4 — scene-scoped suppression):** `GBCPalette` has no scene binding. The `hasSpritePalette` predicate is game-global. A scene-scoped predicate must be derived from a different linkage: which `SceneIR` contains the `MoveMetasprite` ops that reference the asset-driven metasprite. This linkage exists at runtime in `scene.enterOps`/`scene.frameOps` but requires iterating scenes to determine which scene "owns" a metasprite. The planner must choose between (a) scene-scoped predicate via ops inspection, or (b) a `sceneId: String?` field on `MetaspriteIR` (simpler, explicit binding). The CONTEXT does not lock this sub-decision.

**Primary recommendation:** Execute risk-ascending per D-06. Pure-function fixes (Req 1/2/3/7 + W1/W2/W3) first — they have no IR coupling and the tests are straightforward RED→GREEN. The three architectural latents (Req 4/5/6) require IR changes with constructor ripple; write the byte-identity oracle gate BEFORE implementing them so any unintended C delta is caught immediately.

## Diagnose-First Targets — Grounded Source Analysis

### Diagnose-First Target 1: SceneIR bank field (Req 6, D-01)

**Current shape of SceneIR** (`SceneIR.kt:33`):
```kotlin
data class SceneIR(
    val id: String,
    val enterOps: List<ScriptOp> = emptyList(),
    val frameOps: List<ScriptOp> = emptyList(),
    val exitOps: List<ScriptOp> = emptyList(),
    val actorIds: List<String> = emptyList(),
    val tilesetRef: AssetRef? = null,
    val collisionData: ByteArray? = null,
    val mapWidth: Int? = null,
    val zoneRefs: List<String> = emptyList(),
    val sourceLocation: SourceLocation? = null,
    override val bankSlot: BankSlot? = null,      // PlatformAnnotatable field (scene code bank)
    override val vramRange: VRAMRange? = null,
    override val oamSlot: OAMSlot? = null,
) : PlatformAnnotatable
```

`SceneIR` is a **data class** with a **custom `equals`/`hashCode`** (because `collisionData: ByteArray?` needs `contentEquals`). It does NOT use the generated `copy()` semantics — it has a handwritten `equals` at lines 50-66 and `hashCode` at lines 68-83. Any new field **must** be added to both `equals` and `hashCode` manually.

**Existing nullable-field pattern:** All existing optional fields have null defaults: `tilesetRef: AssetRef? = null`, `collisionData: ByteArray? = null`, etc. The new `allocatedZoneBank: Int?` follows the same nullable-with-null-default pattern.

**Where `allocateZoneBanks` is computed and available:**
- `GBDKPipelineV2.allocateZoneBanks(gameIR): Map<String, Int>` (pipeline method, `internal`)
- Called in `GBDKPipelineV2.buildCFiles()` at line 634: `val bankAllocation = allocateZoneBanks(gameIR)`
- The `bankAllocation` map is threaded into `buildSceneFile()` and `buildHomeFile()` within the same invocation.

**Proposed population site:** After `allocateZoneBanks(gameIR)` returns in `buildCFiles()`, populate `scene.allocatedZoneBank` by rebuilding the scene list:
```kotlin
val scenesWithBanks = gameIR.scenes.map { scene ->
    val zoneBank = scene.zoneRefs.firstNotNullOfOrNull { bankAllocation[it] }
    scene.copy(allocatedZoneBank = zoneBank)
}
```
Then pass `scenesWithBanks` to `buildSceneFile` and `buildHomeFile` instead of `gameIR.scenes`.

**However:** Since `SceneIR` is a data class with custom `equals`/`hashCode`, `copy()` IS available (the generated one) — the custom methods are handwritten but `copy()` is still generated for data classes. Planner should use `scene.copy(allocatedZoneBank = zoneBank)` and add the new field to `equals`/`hashCode`.

**The TWO emission sites that read the bank:**
1. **SceneVisitor.kt:187** — `val bank = zoneBankAllocation[zoneId] ?: error(...)` — after the fix, reads `scene.allocatedZoneBank ?: zoneBankAllocation[zoneId]` (fallback for backward compat) or simply `scene.allocatedZoneBank ?: error(...)`
2. **GBDKPipelineV2.kt:2473** — `val bank = bankAllocation[zone.id] ?: 1` in `buildSetupCurrentLevelFunctionIfNeeded()` — this reads from the `bankAllocation` map directly (not SceneVisitor). This site does NOT need to change for Req 6 — it already reads from `allocateZoneBanks`. The "dual-literal" in the generated C (`_current_area_bank = 2u`) is correct because it's computed from the same `bankAllocation` map.

**Constructor call ripple:** `SceneIR` is constructed in ~366 places (many are tests, the rest are in GameIRSerializer and DSL builders). With a **nullable field with a null default**, all existing call sites compile without changes. Only `GameIRSerializer.kt` needs `allocatedZoneBank` added to serialize/deserialize (optional: the field is pipeline-transient and could be omitted from serialization — the planner must decide).

**`equals`/`hashCode` ripple:** The custom `equals` at lines 50-66 and `hashCode` at lines 68-83 must each add one line for the new field. This is a 2-line IR-module edit.

**Byte-identity preservation argument:** The new field defaults to `null`. For the shipped platformer-template and metasprites shapes, the population logic sets `allocatedZoneBank` from `allocateZoneBanks(gameIR)` — the same value the SceneVisitor already uses. The `CLiteral(bank)` value in generated C is unchanged. Zero-delta confirmed structurally.

**Test fixture ripple:** All test constructors that use `SceneIR(id = "...")` compile unchanged (new field has default = null). No test changes needed for existing test fixtures.

### Diagnose-First Target 2: Scene-scoped sprite-palette suppression (Req 4, 13.7 WR-05)

**Current shape** (`GBDKPipelineV2.kt:5048-5075`, method `buildMetaspriteSpritePaletteStatements`):

```kotlin
private fun buildMetaspriteSpritePaletteStatements(gameIR: GameIR): List<CStatement> {
    if (gameIR.config.gbcTarget == GbcTarget.DMG) return emptyList()
    if (gameIR.metasprites.isEmpty()) return emptyList()
    val proceduralMetasprites = gameIR.metasprites.filter { it.spritePath == null }
    val proceduralStatements = proceduralMetasprites.mapIndexed { slot, ms ->
        CRawCode("set_sprite_palette(${slot}u, 1u, ${ms.id}_palettes);")
    }
    // Asset-driven fallback arm (Phase 13.7-03):
    val hasSpritePalette = gameIR.palettes.any { it.type == PaletteType.SPRITE }  // ← GAME-GLOBAL
    val assetDrivenStatements = if (!hasSpritePalette) {
        val proceduralCount = proceduralMetasprites.size
        val assetDrivenMetasprites = gameIR.metasprites.filter { it.spritePath != null }
        assetDrivenMetasprites.mapIndexed { idx, ms ->
            CRawCode("set_sprite_palette(${proceduralCount + idx}u, 1u, ${ms.id}_palettes);")
        }
    } else {
        emptyList()
    }
    return proceduralStatements + assetDrivenStatements
}
```

**The suppression question:** "Is this metasprite's scene the OBJ-palette authority?" In a game where `spritePalette{}` is declared for scene A and an asset-driven metasprite lives in scene B, scene A's palette should not suppress scene B's asset-driven upload.

**Available data for a scene-scoped predicate:**
- `gameIR.scenes` — each `SceneIR` has `enterOps`, `frameOps`, `exitOps`
- `ScriptOp.MoveMetasprite` in scene ops identifies which scene uses which metasprite
- `gameIR.palettes` — `GBCPalette` has `type: PaletteType` but NO scene binding field

**There is no scene-id on GBCPalette.** The `spritePalette{}` DSL registers at game level (`GameBuilder`), not scene level. The SPEC says "scene-scoped predicate" but the IR currently does not support attaching a palette to a specific scene.

**Two implementation options for the planner:**

**Option A (IR extension):** Add `sceneId: String? = null` to `GBCPalette` — the `spritePalette{}` DSL would need to be called inside a scene builder and capture the enclosing scene ID. This is a DSL surface change and is wide-blast-radius. Not recommended for a debt-closure phase.

**Option B (metasprite scene linkage):** Add `sceneId: String? = null` to `MetaspriteIR`, populated by the DSL when `moveMetasprite(ms)` is called in a scene. The pipeline's suppression predicate becomes: "does the metasprite's declared scene have a SPRITE palette?" This is simpler and stays within the `MetaspriteIR` blast-radius of Req 5.

**Option C (ops-based detection):** Derive which scene contains `MoveMetasprite(metaspriteId)` by scanning `gameIR.scenes[*].frameOps`. No IR change needed — purely a pipeline logic change. The predicate becomes: "does the scene that contains `MoveMetasprite(<id>)` have a SPRITE palette in any of its `enterOps` `SetPalette` ops?" This is the minimal-blast-radius option but requires careful ops scanning.

**Option D (narrow KDoc + test, defer architectural fix):** Add a KDoc that documents the game-global scope explicitly, add a JVM codegen-shape test for the mixed case (synthetic GameIR with non-owning spritePalette + asset-driven metasprite in another scene), and confirm the test FAILS (proving the bug exists) — then implement Option B or C to make it GREEN. This satisfies the SPEC's RED→GREEN acceptance criterion.

**Byte-identity preservation for shipped shapes:**
- Platformer-template: `hasSpritePalette = false` → new predicate must also yield false (no SPRITE palettes anywhere) → asset-driven upload is emitted → same as now. PASS.
- Metasprites example: has one `GBCPalette(type=SPRITE, name="gray_pal")` → `hasSpritePalette = true` → suppressed → same as now. PASS.
- Any new predicate MUST produce the same boolean result for both shipped shapes.

**Recommendation for planner:** Use **Option B** (add `sceneId: String?` to `MetaspriteIR`) combined with Option D (RED test first). This keeps the fix contained to the same IR layer as Req 5's `initialSubPaletteSlot`. The planner should fold Options B + D together since `MetaspriteIR` is already being touched for Req 5.

### Diagnose-First Target 3: Slot from sub-palette (Req 5, 12.9 WR-05)

**Current shape** (`GBDKPipelineV2.kt:5054-5056`):
```kotlin
val proceduralMetasprites = gameIR.metasprites.filter { it.spritePath == null }
val proceduralStatements = proceduralMetasprites.mapIndexed { slot, ms ->
    CRawCode("set_sprite_palette(${slot}u, 1u, ${ms.id}_palettes);")
}
```
And for asset-driven (`GBDKPipelineV2.kt:5067-5071`):
```kotlin
assetDrivenMetasprites.mapIndexed { idx, ms ->
    CRawCode("set_sprite_palette(${proceduralCount + idx}u, 1u, ${ms.id}_palettes);")
}
```

**The `_<id>_subPalette` runtime variable** is declared at `GBDKPipelineV2.kt:951`:
```kotlin
CVarDecl(name = "_${ms.id}_subPalette", type = CU8, initializer = CLiteral(0)),
```
This is a runtime UINT8, initialized to 0, changed at runtime by `ms.subPalette set expr`. There is NO compile-time declaration of which OBJ slot a metasprite's draw path targets.

**The problem:** For `N ≥ 2` metasprites, `mapIndexed` assigns OBJ slot by list position. If the metasprite's draw path uses `_<id>_subPalette` to select its sub-palette at runtime (via `rot >> 2` in the metasprites example), the initial value of `_<id>_subPalette` (0) determines which slot is used on the first frame. The upload at slot `proceduralCount + idx` may not match slot 0.

**IR field needed:** Add `initialSubPaletteSlot: Int? = null` to `MetaspriteIR`. When non-null, the pipeline uses this value as the OBJ slot for `set_sprite_palette(...)`. When null (default), fall back to list index — preserving byte-identity for all existing metasprites (which have no declared slot).

**Shipped single-metasprite case (metasprites example):**
- One asset-driven metasprite (`elephant`, `spritePath != null`), `proceduralCount = 0`, `idx = 0`
- Emits: `set_sprite_palette(0u, 1u, elephant_palettes);`
- With `initialSubPaletteSlot = null` default, list-index fallback → slot 0 → same output. BYTE-IDENTICAL.

**Constructor ripple:** `MetaspriteIR` is a data class (all fields have defaults except `id` and `frames`). Adding `initialSubPaletteSlot: Int? = null` compiles all existing call sites without changes.

**GameIRSerializer:** Add `initialSubPaletteSlot` to `serializeMetaspriteIR` / `deserializeMetaspriteIR`. This is additive and backward-compatible (default null on deserialize).

## Common Pitfalls

### Pitfall 1: Custom `equals`/`hashCode` in SceneIR — adding a field without updating both methods
**What goes wrong:** Adding `allocatedZoneBank: Int?` to the constructor but not to `equals` (lines 50-66) or `hashCode` (lines 68-83) causes two SceneIR instances with different bank values to compare equal, silently hiding test failures.
**Why it happens:** `SceneIR` is a `data class` with handwritten `equals`/`hashCode` overrides (required because `collisionData: ByteArray?` needs `contentEquals`). The generated `equals` is overridden — new fields are NOT automatically included.
**How to avoid:** After adding the field, immediately add `&& allocatedZoneBank == other.allocatedZoneBank` to `equals` and `result = 31 * result + (allocatedZoneBank ?: 0)` to `hashCode`.
**Warning signs:** A test with two SceneIR instances differing only in `allocatedZoneBank` asserts `a != b` but gets `a == b`.

### Pitfall 2: `allocatedZoneBank` serialization decision
**What goes wrong:** Including `allocatedZoneBank` in `GameIRSerializer` means serialized GameIR JSON carries this pipeline-transient field. Deserializing an old JSON without this field sets it null (fine). But serializing WITH the field could break downstream consumers that don't expect it.
**Why it happens:** The field is a pipeline annotation (computed from `allocateZoneBanks`), not a DSL-authored value. It should arguably be omitted from serialization.
**How to avoid:** Treat `allocatedZoneBank` like `bankSlot`/`vramRange`/`oamSlot` — these ARE serialized in `GameIRSerializer`. Look at how `BankSlot` is serialized to determine if `allocatedZoneBank` should be nullable-and-skipped or nullable-and-included. Simplest approach: omit it from serialization (not needed for persistence; recomputed every codegen run).
**Warning signs:** `GameIRSerializerTest` fails because round-trip JSON doesn't match.

### Pitfall 3: Byte-identity regression from RGB555 quantization change (Req 3)
**What goes wrong:** The `to5()` quantization on the source PLTE side changes the luminance values used for Spearman ranking. For cases where the emitted palette was ALREADY byte-identical, this could change the Spearman result from `false` to `true` (or vice versa), altering the WARNING output at build time — which is not a generated-C regression but is a behavioral change.
**Why it happens:** The quantization is specifically designed to change the comparator's behavior for near-tie luminance values. For the shipped assets (world1-tileset.png BG, elephant.png OBJ), the guard returns `false` in both old and new code because the existing polarity is CORRECT (not inverted). No WARNING fires in either case. PASS.
**How to avoid:** Confirm the shipped assets pass both the old and new comparators without WARNING. The RED→GREEN test for Req 3 proves the new behavior is correct; the buildRom smoke test + byte-identity oracles prove no C-code regression.
**Warning signs:** A WARNING is emitted at buildRom time that was not present before. Investigate which asset it fires on before treating it as a blocker.

### Pitfall 4: `getTemporaryDir()` vs `File(sourceDir, "sprites/tmp")` for W3
**What goes wrong:** Moving `buildTempDir` from inside `cSourceDir` (the `@OutputDirectory`) to `getTemporaryDir()` changes the path of temp files. If `prePermuteIndexedPng` generates a deterministic name based on `file.nameWithoutExtension` (current W2 bug), changing the directory alone doesn't fix the cache fingerprint issue — Gradle may still scan it.
**Why it happens:** W2 and W3 are coupled. W2 keys the temp name on `stemName` (fixing same-basename collision). W3 moves the directory out of `@OutputDirectory` (fixing build-cache pollution). Both must be done together.
**How to avoid:** Implement W2 and W3 in the same task: pass `stemName` to `prePermuteIndexedPng` (or have the caller rename the result) AND move the temp dir to `getTemporaryDir()`.
**Warning signs:** After W3 alone, Gradle still fingerprints temp files; or, after W2 alone, the old path still lives in `@OutputDirectory`.

### Pitfall 5: `MetaspriteIR.initialSubPaletteSlot` vs runtime `_<id>_subPalette`
**What goes wrong:** Confusing the compile-time slot (which OBJ palette slot the hardware texture references) with the runtime sub-palette variable (which slot is selected per-frame via `rot >> 2`). The Req 5 fix is about the UPLOAD slot — matching the initial hardware slot so the upload and the draw-path agree at first frame.
**Why it happens:** The `_<id>_subPalette` variable (initialized to 0) drives the runtime OAM attribute in `move_metasprite`. The `set_sprite_palette(slot, ...)` at startup uploads the palette to a specific hardware OBJ palette RAM slot. These two must agree.
**How to avoid:** The `initialSubPaletteSlot` field represents "which OBJ palette slot should `set_sprite_palette` upload to at startup." For single-metasprite games with no explicit declaration, slot 0 is correct (default null → list index → 0). The new field is only needed when a game author explicitly declares a different slot.

### Pitfall 6: SceneIR.copy() — data class copies DO work
**What goes wrong:** Thinking that because `SceneIR` has custom `equals`/`hashCode` it cannot use generated `copy()`.
**Why it happens:** `data class` generates `copy()` regardless of whether `equals`/`hashCode` are overridden.
**How to avoid:** Use `scene.copy(allocatedZoneBank = bank)` freely in the pipeline. The custom `equals`/`hashCode` affect comparison, not copying.

### Pattern 1: Per-sub-palette Spearman ranking (Req 1 + Req 3)

```kotlin
// Source: 13.7-REVIEW.md WR-01 recommendation + Req 3 quantization fix
internal fun checkPalettePolarity(sourcePng: File, emittedRgb555Values: List<Int>): Boolean {
    return try {
        val img = ImageIO.read(sourcePng) ?: return false
        val cm = img.colorModel as? IndexColorModel ?: return false
        val mapSize = cm.mapSize
        val n = emittedRgb555Values.size
        if (n < 2) return false
        if (n > mapSize) return false

        val srcReds   = ByteArray(mapSize).also { cm.getReds(it) }
        val srcGreens = ByteArray(mapSize).also { cm.getGreens(it) }
        val srcBlues  = ByteArray(mapSize).also { cm.getBlues(it) }

        // Req 3: quantize source PLTE to RGB555 before computing luminance (same grid as emitted)
        fun to5(c: Int): Int = (c * 31 / 255) * 255 / 31
        val sourceLum = (0 until n).map { i ->
            0.299 * to5(srcReds[i].toInt() and 0xFF) +
                0.587 * to5(srcGreens[i].toInt() and 0xFF) +
                0.114 * to5(srcBlues[i].toInt() and 0xFF)
        }

        val emittedLum = emittedRgb555Values.map { v ->
            val r5 = v and 0x1F; val g5 = (v shr 5) and 0x1F; val b5 = (v shr 10) and 0x1F
            0.299 * (r5 * 255 / 31) + 0.587 * (g5 * 255 / 31) + 0.114 * (b5 * 255 / 31)
        }

        // Req 1: rank per 4-entry GBC sub-palette, return true if ANY sub-palette is strictly inverted
        val subPaletteSize = 4
        if (n % subPaletteSize != 0) return false  // not a valid GBC palette
        (0 until n step subPaletteSize).any { base ->
            val srcGroup = sourceLum.subList(base, base + subPaletteSize)
            val emGroup  = emittedLum.subList(base, base + subPaletteSize)
            val minLum = srcGroup.min(); val maxLum = srcGroup.max()
            if (maxLum - minLum < SPEARMAN_EPSILON) return@any false
            spearmanCorrelation(spearmanRanks(srcGroup), spearmanRanks(emGroup)) < -1.0 + SPEARMAN_EPSILON
        }
    } catch (_: Exception) {
        false
    }
}
```

### Pattern 2: Consolidated PngUtils parse helper (Req 2)

```kotlin
// Single source of truth for palette parse + RGB555 packing
internal fun parsePaletteRgb555Values(file: File, symbol: String): List<Int>? {
    val text = file.readText()
    val headerPattern = Regex(
        """const\s+palette_color_t\s+${Regex.escape(symbol)}\s*\[\s*\d+\s*\]\s*=\s*\{([^}]*)\}""",
        RegexOption.DOT_MATCHES_ALL,
    )
    val match = headerPattern.find(text) ?: return null
    val body = match.groupValues[1]
    val rgb8Pattern = Regex("""RGB8\(\s*(\d+)\s*,\s*(\d+)\s*,\s*(\d+)\s*\)""")
    val result = mutableListOf<Int>()
    var foundRgb8 = false
    for (m in rgb8Pattern.findAll(body)) {
        val r8 = m.groupValues[1].toInt(); val g8 = m.groupValues[2].toInt(); val b8 = m.groupValues[3].toInt()
        val r5 = r8 * 31 / 255; val g5 = g8 * 31 / 255; val b5 = b8 * 31 / 255
        result.add((b5 shl 10) or (g5 shl 5) or r5)
        foundRgb8 = true
    }
    if (foundRgb8) return if (result.isEmpty()) null else result
    // Fallback: raw decimal/hex integers
    body.split(",").forEach { token ->
        val trimmed = token.trim()
        val v = trimmed.toIntOrNull()
            ?: trimmed.removePrefix("0x").toLongOrNull(16)?.toInt()
            ?: trimmed.removePrefix("0X").toLongOrNull(16)?.toInt()
        if (v != null) result.add(v)
    }
    return if (result.isEmpty()) null else result
}
```
