## Summary

The v2 source map implementation connects two already-present systems that are not yet wired together for v2 games. On one side: `ScriptOp` IR nodes already carry a `sourceLocation: SourceLocation?` field (defined in `gbkt-core/src/main/kotlin/io/github/gbkt/core/ir/v2/ScriptOp.kt`), though all current DSL builder methods (in `ScriptBuilder.kt`) create ops WITHOUT populating that field — they pass `sourceLocation = null` by default. On the other side: the full source map infrastructure (SourceMap, SourceMapBuilder, SourceMapLoader, ErrorEnhancer, CompileRomTask.enhanceErrorMessage, IntelliJ GbktCodegenService) already exists and is tested and working for v1 games.

The gap is purely in the pipeline: (1) DSL builders must capture caller stack frames and attach them as `SourceLocation` when constructing `ScriptOp` nodes, (2) `CEmitter` must track which output line it is currently on so that `ScriptOpVisitor` can record C-line → `SourceLocation` mappings during emission, (3) `GBDKPipelineV2.generate()` must produce source maps (one per C file) alongside the C strings, and (4) `executeV2Path()` in `GenerateCTask` must write those maps to disk and remove the WARNING about source maps being unavailable.

The v2 JSON format extends the existing format by adding `irNodeType` and `bankNumber` fields. The existing `SourceMapLoader` (used by `CompileRomTask`) and `GbktCodegenService` (used by IntelliJ) both need to be updated to (a) parse the new fields and (b) load maps for multiple C files instead of only `main.c.gbkt.map`.

**Primary recommendation:** Wire `sourceLocation` capture into every `ScriptBuilder` method, thread it through `ScriptOpVisitor` → `CEmitter` with a line counter, and surface source maps per C file from `GBDKPipelineV2`. Update loaders and the IntelliJ plugin last.

### Pattern 1: SourceLocation Capture in ScriptBuilder

Every `ScriptBuilder` method currently creates IR ops without source location. The fix is a single helper at the top of each builder method:

```kotlin
// In ScriptBuilder — BEFORE (current)
fun assign(target: String, value: Expr, op: AssignOp = AssignOp.SET) {
    ops += Assign(target, value, op)
}

// AFTER — capture caller stack frame
fun assign(target: String, value: Expr, op: AssignOp = AssignOp.SET) {
    ops += Assign(target, value, op, sourceLocation = captureV2Location())
}

// Helper (private) — reuse same stack-walking logic as captureSourceLocation() in SourceMap.kt
// but returns ir.v2.SourceLocation instead of core.SourceLocation
private fun captureV2Location(): io.github.gbkt.core.ir.v2.SourceLocation? {
    val stackTrace = Thread.currentThread().stackTrace
    for (frame in stackTrace) {
        val className = frame.className
        if (className.startsWith("java.") || className.startsWith("jdk.")) continue
        if (className.startsWith("io.github.gbkt.core.dsl.")) continue  // skip DSL internals
        if (className.startsWith("kotlin.")) continue
        val fileName = frame.fileName ?: continue
        val lineNumber = frame.lineNumber
        if (lineNumber <= 0) continue
        return io.github.gbkt.core.ir.v2.SourceLocation(fileName, lineNumber, 0)
    }
    return null
}
```

**Note:** There are currently TWO `SourceLocation` types: `io.github.gbkt.core.SourceLocation` (v1, used by `SourceMapBuilder`) and `io.github.gbkt.core.ir.v2.SourceLocation` (v2 IR, `data class SourceLocation(val file: String, val line: Int, val col: Int)`). `ScriptOp.sourceLocation` uses the v2 type. The v2 source map pipeline will work with v2 `SourceLocation` throughout.

### Pattern 2: Line-Tracking CEmitter

`CEmitter` currently builds a String via `buildString { appendLine(...) }` without knowing which output line it is on. For source map generation, it needs a line counter that increments with each appended line.

Option A — Instrument CEmitter directly (two-pass): Call `CEmitter.emit()` first to get the full string, then count lines to reconstruct which lines correspond to which AST nodes. This is fragile.

Option B — SourceMapCollector callback (recommended): Add an optional `onLine: (lineNumber: Int, sourceLocation: SourceLocation?) -> Unit` callback to `CEmitter.emit()`. The `ScriptOpVisitor` annotates `CStatement` nodes (or passes locations separately), and the emitter fires the callback as it writes each line.

The cleanest approach given the typed AST: add `sourceLocation: SourceLocation?` to `CStatement` subtypes that originate from `ScriptOp` (specifically `CExprStatement`, `CIf`, `CBlock`, `CRawCode`), or alternatively add a lightweight `SourceAnnotation` wrapper class. The emitter records the line number when emitting any annotated statement.

Concrete approach: Add `sourceLocation` to `CStatement` as an interface property defaulting to null (like `ScriptOp`):

```kotlin
// In CStatement.kt — ADD source location to key statement types
data class CExprStatement(
    val expr: CExpr,
    val sourceLocation: io.github.gbkt.core.ir.v2.SourceLocation? = null
) : CStatement

data class CRawCode(
    val code: String,
    val sourceLocation: io.github.gbkt.core.ir.v2.SourceLocation? = null
) : CStatement
```

Then in `ScriptOpVisitor.visit()`:

```kotlin
fun visit(op: ScriptOp): CStatement {
    val stmt = when (op) { ... /* existing logic */ }
    return stmt.withSourceLocation(op.sourceLocation)
}
```

And `CEmitter.emitStatement()` fires a line-mapping callback before emitting each annotated statement.

### Pattern 3: GBDKPipelineV2 Source Map Output

`GBDKPipelineV2.generate()` currently returns `Map<String, String>` (filename → C content). It must be changed to also return source maps.

The cleanest API change: return a new data class `PipelineV2Output` from `GBDKPipelineV2.generate()`:

```kotlin
data class PipelineV2Output(
    val files: Map<String, String>,                     // filename → C content
    val sourceMaps: Map<String, SourceMap>              // filename → source map
)
```

`GBDKBackend.generateV2()` then packages both into `GenerationResult`. The `GenerationResult.sourceMap` field (currently single) either becomes a `Map<String, SourceMap>` or the existing single field stores the main.c map while others are attached to `GeneratedFile`.

Given the locked decision (one map per C file), the simplest path: add `sourceMap: SourceMap?` to `GeneratedFile` (currently it only has `path`, `content`, `description`).

### Pattern 4: v2 JSON Format

The existing v1 JSON format (from `SourceMap.toJson()` in `gbkt-core/.../core/SourceMap.kt`):

```json
{
  "version": "1.0",
  "gameName": "MyGame",
  "cFile": "main.c",
  "mappings": [
    { "cLine": 10, "kotlinFile": "Game.kt", "kotlinLine": 5, "symbol": "score" }
  ]
}
```

The v2 format adds `irNodeType` and `bankNumber`:

```json
{
  "version": "2.0",
  "gameName": "MyGame",
  "cFile": "main.c",
  "bankNumber": 0,
  "mappings": [
    {
      "cLine": 42,
      "kotlinFile": "PongGame.kt",
      "kotlinLine": 18,
      "kotlinColumn": 4,
      "symbol": "score",
      "snippet": "assign(\"score\", add(varRef(\"score\"), lit(1)))",
      "irNodeType": "Assign"
    }
  ]
}
```

`SourceMap.kt` and `SourceMapping.kt` need `version = "2.0"`, `bankNumber` in `SourceMap`, and `irNodeType` in `SourceMapping`. Since no backward compatibility is needed, the class definitions can be updated in place.

### Pattern 5: Multi-File Source Map Loading

`SourceMapLoader.findSourceMapFile(cSourceFile)` currently returns a single file `{name}.gbkt.map`. `CompileRomTask.enhanceErrorMessage()` loads one map for the one C file it's compiling.

For multi-file support: `SourceMapLoader` gains a method to find all `.gbkt.map` files in a directory and merge their mappings. The key for each mapping becomes `(cFile, cLine)` rather than just `cLine`.

`GbdkErrorParser.GbdkError` already captures `file: String?` (the C source file that lcc reported), so multi-file lookup is straightforward once the loader supports it.

### Pattern 6: Rust-Style Error Formatting

The locked decision requires:
```
MyGame.kt:42 | assign("score", ...)
              ^ Error: undefined reference to '_score'
```

This format needs: (a) the DSL snippet stored in `SourceMapping.snippet`, and (b) `ErrorEnhancer.formatEnhancedErrors()` updated to produce this two-line format per error, grouping multiple C errors by DSL line.

**Grouping logic:** After `enhanceErrors()`, group `EnhancedError` list by `kotlinLocation?.let { "${it.kotlinFile}:${it.kotlinLine}" }`. Errors with the same DSL line appear together in one block. Errors with `kotlinLocation = null` (boilerplate) get `(no DSL mapping — generated scaffolding)` suffix.

### Anti-Patterns to Avoid

- **Do not capture source location at ScriptOp construction time by calling `captureSourceLocation()` from inside `ScriptOp` data class constructors.** Source location must be captured at the DSL layer (in `ScriptBuilder` methods), not in the IR layer. The IR nodes are data containers.
- **Do not add line tracking to `CEmitter` via mutable state that persists between files.** The emitter is an object (singleton); any mutable state added must be reset between calls or passed via parameter.
- **Do not keep the IntelliJ plugin parsing only `main.c.gbkt.map`.** `readCachedSourceMap()` hardcodes this path. After this phase, bank1.c errors will also map to DSL.
- **Do not use `SourceMapBuilder` (v1) for v2 source maps.** Create a v2-specific builder that produces the v2 JSON format. The v1 builder's `gameName`+`cFile` constructor signature doesn't fit multi-file output well.

## Common Pitfalls

### Pitfall 1: Two SourceLocation Types

**What goes wrong:** The codebase has two `SourceLocation` types: `io.github.gbkt.core.SourceLocation` (v1, in `SourceMap.kt`) and `io.github.gbkt.core.ir.v2.SourceLocation` (v2 IR, in `Types.kt`). They have slightly different field names: v1 has `(file, line, column, snippet)` and v2 IR has `(file, line, col)`. Mixing them without conversion will cause type errors.

**Why it happens:** The v2 IR type was defined independently from the v1 type; both were needed at different phases.

**How to avoid:** In `GBDKPipelineV2`, work exclusively with `io.github.gbkt.core.ir.v2.SourceLocation` internally. When writing source maps to JSON, convert to the `SourceMapping` data class (v1 core) or define a v2-specific serialization directly. The cleanest approach: define a separate `V2SourceMap` / `V2SourceMapping` data class in `gbkt-backend-gbdk` that owns v2-specific serialization, rather than modifying the v1 `SourceMap`.

**Warning signs:** Import conflicts between `io.github.gbkt.core.SourceLocation` and `io.github.gbkt.core.ir.v2.SourceLocation` in visitor or pipeline files.

### Pitfall 2: CEmitter Object State

**What goes wrong:** `CEmitter` is a Kotlin `object` (singleton). If line tracking is added as mutable var, concurrent or sequential calls from tests or from multiple CFile emissions will see stale line counts.

**Why it happens:** The existing `CEmitter.emit(file: CFile)` is designed as a pure function; adding mutable state breaks this.

**How to avoid:** Pass an optional `SourceMapCollector` (or use a local counter per `emit()` call). A closure or data class passed as a parameter to `emit()` that accumulates mappings keeps the function pure. The collector can be `null` for non-source-map code paths (e.g., game.h header file).

**Warning signs:** Source map line numbers are off by the line count of previously emitted files.

### Pitfall 3: ScriptBuilder Methods Without Source Location

**What goes wrong:** There are 30+ methods in `ScriptBuilder.kt`, several in `SceneBuilder.kt`, and helpers in `GameBuilder.kt`. Missing even one `captureV2Location()` call means some DSL constructs produce unmapped C lines.

**Why it happens:** Manual method-by-method update is error-prone.

**How to avoid:** After implementing the capture mechanism, write a test that creates a game with one of each ScriptOp type and asserts that `sourceLocation != null` on every op. This acts as a regression guard.

**Warning signs:** Test failures where specific ScriptOp subtypes always produce `null` source locations.

### Pitfall 4: Stack Depth at Capture Time

**What goes wrong:** `captureV2Location()` in `ScriptBuilder` skips frames from `io.github.gbkt.core.dsl.*`. If the user calls a DSL helper that internally calls another helper (nesting), the skip logic may land on the wrong frame (the inner helper's caller rather than the user's game file).

**Why it happens:** Stack trace filtering relies on package prefix matching. Lambdas compiled by Kotlin may appear with unusual class names.

**How to avoid:** The existing `captureSourceLocation()` (used by v1) already handles this correctly by skipping `io.github.gbkt.core.*`. Use the same logic, just extend the skip list to cover `io.github.gbkt.core.dsl.*` specifically. Run end-to-end tests to confirm the captured file name is the user's game file (e.g., `PongGame.kt`), not an internal file.

**Warning signs:** `kotlinFile` in source map entries showing `ScriptBuilder.kt` or `GameBuilder.kt` instead of the user's game file.

### Pitfall 5: executeV2Path Reflection Chain

**What goes wrong:** `executeV2Path()` currently calls `generateV2` via reflection and extracts files via `GenerationResultWrapper`. If `GBDKPipelineV2.generate()` signature changes to return `PipelineV2Output`, the reflection call chain must be updated in the Gradle plugin.

**Why it happens:** The Gradle plugin runs in an isolated classloader; it can only access backend classes via reflection. Any signature change in the pipeline requires a matching reflection update.

**How to avoid:** The source maps should be returned as part of `GenerationResult` (already in the backend-api contract). `GenerationResultWrapper` already extracts files; it needs to also extract source maps. Keep the public API surface minimal — add source maps to `GeneratedFile.sourceMap` rather than adding a new field to `GenerationResult`.

**Warning signs:** `GenerationResultWrapper.getFilesOrThrow()` succeeds but source maps are never extracted.

### Pitfall 6: IntelliJ Plugin Hardcoded Path

**What goes wrong:** `readCachedSourceMap()` in `GbktCodegenService.kt` explicitly looks for `build/gbkt/generated/main.c.gbkt.map`. After this phase, there are also `bank1.c.gbkt.map` files. The plugin will silently miss bank1.c mappings.

**Why it happens:** The v1 pipeline only produced one C file, so one map sufficed.

**How to avoid:** Change `readCachedSourceMap()` to scan the `build/gbkt/generated/` directory for all `*.gbkt.map` files and merge their mappings into a unified lookup. The key becomes `(cFile, cLine)` → `SourceLocation`.

### Pitfall 7: Boilerplate Lines and "Closest Previous" Fallback

**What goes wrong:** `ParsedSourceMap.findKotlinLocation()` already has a "closest previous mapping" fallback (returns the most recent mapping before the queried line). Boilerplate C lines (function signatures, `#include`, `#pragma bank`) will map to whatever DSL line precedes them. This produces misleading error locations.

**Why it happens:** The fallback was designed for approximate error mapping before statement-level granularity existed.

**How to avoid:** With statement-level mapping now the goal, the fallback should be used only when the error line is truly between two mappings in a dense mapping region. For boilerplate blocks at the top of each file (before any DSL-originated code), the fallback would map to the first scene's enter block — which is wrong. Consider adding explicit "unmapped sentinel" entries at the start of each boilerplate section so the loader can distinguish "no mapping before this line" from "closest mapping is from a different context."

**Warning signs:** lcc errors in includes or pragmas showing a spurious DSL location rather than "(no DSL mapping — generated scaffolding)".

// New overload alongside existing emit(CFile)
fun emit(file: CFile, collector: SourceMapCollector? = null): String = buildString {
    var lineNumber = 1
    // ... existing header lines increment lineNumber ...

    for (fn in file.functions) {
        appendLine()
        lineNumber++
        append(emitFunction(fn, lineNumber, collector))

### executeV2Path — After Source Map Wiring

```kotlin
// In GenerateCTask.kt — executeV2Path() after changes
private fun executeV2Path(rawGame: Any, outputDir: File, target: String) {
    val gameIR = rawGame.javaClass.getMethod("build").invoke(rawGame)
        ?: throw GradleException("GameBuilder.build() returned null")

    val backend = BackendReflection.findBackendForTarget(target)
        ?: throw GradleException("No backend found for target '$target'")

    val gameIrClass = Class.forName("io.github.gbkt.core.ir.v2.GameIR")
    val generateV2Method = backend.javaClass.getMethod("generateV2", gameIrClass)
    val result = generateV2Method.invoke(backend, gameIR)
        ?: throw GradleException("generateV2 returned null")

    val generationResultWrapper = GenerationResultWrapper(result)
    val files = generationResultWrapper.getFilesOrThrow()

    var totalLines = 0
    files.forEach { (filename, content) ->
        val outputFile = File(outputDir, filename)
        outputFile.writeText(content)
        totalLines += content.lines().size
        println("Generated: $filename (${content.lines().size} lines)")

        // Write source map for this C file if available
        val sourceMapJson = generationResultWrapper.getSourceMapJson(filename)
        if (sourceMapJson != null) {
            val mapFile = File(outputDir, "$filename.gbkt.map")
            mapFile.writeText(sourceMapJson)
            println("Generated source map: ${mapFile.absolutePath}")
        }
    }

    // Remove the WARNING — source maps now generated
    println("Generated ${files.size} C files ($totalLines total lines)")
    println("Output directory: ${outputDir.absolutePath}")
}
```

## Open Questions

1. **SourceMapCollector threading model in CEmitter**
   - What we know: `CEmitter` is an `object`, called sequentially from `GBDKPipelineV2.buildCFiles()`
   - What's unclear: Whether making `emit()` accept a mutable collector causes issues in tests that call `CEmitter.emit()` multiple times
   - Recommendation: Make collector a local variable constructed per `generate()` call in `GBDKPipelineV2`; pass it to each `emit()` call. Reset between files.

2. **game.h source map**
   - What we know: game.h contains only prototypes, externs, and `#define` constants — no user ScriptOp nodes
   - What's unclear: Whether the IntelliJ combined-view design requires a game.h map for completeness
   - Recommendation: Skip game.h source map (Claude's discretion from CONTEXT.md). game.h has no DSL-originated content; a map would be empty. Invest effort in main.c and bank1.c maps.

3. **IRNodeType string for CRawCode generated by hide/showSprites() etc.**
   - What we know: `ScriptBuilder.hideSprites()` and `showSprites()` emit `RawOp("HIDE_SPRITES;")` which `ScriptOpVisitor` converts to `CRawCode`. These are convenience wrappers, not raw user code.
   - What's unclear: Whether `irNodeType` should be `"RawOp"` or a more descriptive type
   - Recommendation: Use `op::class.simpleName` (returns `"RawOp"`) as `irNodeType`. Snippet can be the raw code string.

4. **SourceMapping.snippet population strategy**
   - What we know: The v2 `SourceLocation` does not carry a snippet — it only has `(file, line, col)`. To populate `snippet`, the pipeline would need to read the user's source file at the captured line, which requires file system access.
   - What's unclear: Whether snippet should be populated and whether source file access is feasible in the Gradle worker context.
   - Recommendation: Leave `snippet = null` for the v2 pipeline in this phase. The `irNodeType` and `kotlinFile:kotlinLine` alone are sufficient for the Rust-style error display. Snippet population can be added as a follow-on enhancement.

5. **Bidirectional IntelliJ navigation for multi-file output**
   - What we know: `CCodePreviewPanel.kt` currently handles one C file's text and one source map. The locked decision requires a "combined view" of all generated files.
   - What's unclear: Whether the combined view is one document (concatenated) or a tabbed pane per file, and what the click-to-navigate implementation looks like at IntelliJ API level.
   - Recommendation: The combined view can be a single `EditorTextField` with C text from all files concatenated with `// --- bank1.c ---` separators, and a merged mapping table keyed by absolute line number in the concatenated text. The file watcher monitors the `generated/` directory for `*.gbkt.map` changes.
