### Why the explicit `set_bkg_palette` is needed (per d-v3-visual-finding-v2.md)

Coffee-GB's `eu.rekawek.coffeegb.core.gpu.ColorPalette` initializes BG palette RAM to all zeros on construct (`new int[8][4]`) and never auto-fills it to the DMG default. The GBDK `cgb_compatibility()` (= `set_default_palette()`) on real hardware writes both DMG palette registers (BGP_REG, OBP0_REG, OBP1_REG) AND GBC palette RAM (BCPD slot 0, OCPD slot 0), but on Coffee-GB the sm83.lib implementation's BCPD path is not reached (only the BGP_REG path is). Result: post-`cgb_compatibility()`, BG palette RAM stays at zero → every BG pixel composites to `bgPalette[0][N] = 0x0000` = RGB(0,0,0) regardless of what BG tile data is loaded.

The explicit `set_bkg_palette(0u, 1u, _gbkt_default_bg_pal)` writes via BCPS/BCPD register pair directly (the GBC palette RAM register pair Coffee-GB DOES register in `accepts(address)`). Slot 0 is populated with the DMG-equivalent default. First composited GBC frame now has a valid BG palette to read.

### Why the bgFillCheckerboard hoist is needed (per d-v3-visual-finding-v2.md)

LCDC.4=1 (the default after cgb_compatibility + the only mode gbkt currently emits) means the BG tile-data region and the sprite tile-data region SHARE `$8000-$8FFF`. Plan 20's hoisted `set_sprite_data(0u, 48u, elephant_tiles)` writes 48 sprite tiles starting at tile 0, which OVERWRITES the BG tile-0 region with elephant-shaped bytes. Without a subsequent `set_bkg_data(0, 1, _checkerboard_bg_pattern)` pre-DISPLAY_ON, the BG composites tile 0 using the elephant bytes — not the checker pattern. Combined with the BG palette zero-init (above), the first frame is uniformly RGB(0,0,0).

By hoisting `bgFillCheckerboard` between `set_sprite_data` and `SHOW_BKG`, the checker bytes overwrite the elephant bytes at $8000 BEFORE the BG plane composites. The sprite plane composites using OAM-resolved tiles (which point to tiles 0..47 with the elephant bytes intact via the sprite tile lookup — sprites do NOT re-read the BG-overwritten region). Both planes render correctly.

## Scope decisions (NOT deviations — explicit minimal-scope choices per D-05)

**1. Did NOT replace `cgb_compatibility()` with an inline equivalent (Alternative 3 from finding).**
Out of scope per D-05. Plan 22 keeps `cgb_compatibility()` intact and adds an explicit BG palette write to compensate for its Coffee-GB-specific BCPD shortfall. If runtime UAT shows the fix is insufficient (e.g., sprite palette RAM also turns out to be zero-initialized in some other code path), Plan 23 escalates to Alternative 3.

**2. Did NOT touch the `_gbkt_default_bg_pal` colors to match user-declared palettes when present.**
The default emits unconditionally (when GBC target) regardless of whether the user has declared any `bgPalette { }` blocks. For metasprites (which uses cgb_compatibility's default appearance as the intended BG), this is correct. For games that declare their own BG palette via DSL, the user-declared palette would also emit a `set_bkg_palette(...)` call that overrides slot 0 — but the current DSL surface does not support user-declared BG palettes via `palette()` in scene scope (only sprite palettes are declared by the metasprites example). When BG palette DSL surface lands (future plan), the default would be a fallback-only emission. Documented in d-v3-visual-finding-v2.md "Scope considerations" — out of Plan 22 scope to implement.

**3. Did NOT modify `SceneVisitor` or the play_enter generation path.**
The duplication-not-relocation approach sidesteps any SceneVisitor changes — the bgFillCheckerboard RawOp is identified, copied into main(), but NOT removed from the start scene's enterOps. play_enter() is unchanged; BgCheckerboardEmissionTest stays GREEN; SceneVisitor remains untouched.
