**Phase:** 10.1-metasprites-surplus-codegen-defects-inserted

**Seed:** [SEED-004-metasprites-corrupted-tile-rendering.md](../../../seeds/SEED-004-metasprites-corrupted-tile-rendering.md)
**Authored:** 2026-05-18

## Hypothesis Tested

Two competing hypotheses from SEED-004 about the cause of the garbled elephant in the
`metasprites` example ROM:

1. **png2asset tile-data byte ordering** — port and reference consume different tile-data
   layouts.
2. **8x8/8x16 sprite mode mismatch** — port does not emit `SPRITES_8x8;` before `DISPLAY_ON;`;
   GBDK default after `cgb_compatibility()` is 8x16, so the hardware interprets pairs of
   consecutive 8x8 tiles as one 8x16 sprite.

RESEARCH §D-V1 Diagnostic Recipe (lines 765-781) expected hypothesis #1 to be REJECTED
(byte-for-byte identical hex dumps, because both port and reference were assumed to use
the same `png2asset -spr8x8` invocation), and hypothesis #2 to be CONFIRMED as the sole
root cause.

The actual evidence captured by this plan contradicts the assumption: BOTH hypotheses
are active, and they share a single underlying root cause — a **sprite-mode mismatch
across the gbkt pipeline**.

## Hypothesis #1 Verdict — ACTIVE (RESEARCH assumption did not hold)

`tile-data-diff.txt` is **non-empty** (1193 lines). The bytes differ structurally, not
trivially:

- Port `elephant_tiles[896]` — 56 entries of 16 bytes each.
- Reference `sprite_tiles[768]` — 48 entries of 16 bytes each.
- Port emits **interleaved blank tiles** between actual data rows. Concretely:
  - Port tile 0 = all zeros (16 bytes of `0x00`).
  - Port tile 1 = `0x00,0x00,0x00,0x00,0x00,0x00,0x03,0x03,0x0d,0x0e,0x1f,0x10,0x3f,0x20,0x3f,0x20`
    (this matches reference tile 0).
  - Port tile 2 = all zeros.
  - Port tile 3 = `0x00,0x00,0x03,0x03,0xfd,0xfe,0x3f,0xc0,...` (this matches reference tile 1).
  - Pattern continues — every other port tile is blank padding.

**Why this happens:** `gbkt-gradle-plugin/.../ConvertSpritesTask.kt` line 228-238
(`determineSpriteMode`) defaults to `SPR8x16` when the source PNG height ≥ 16 pixels.
The elephant PNG is 64×240, so the port invokes `png2asset -spr8x16`, which emits tile
data as top+bottom 8x8 pairs per "tile". The reference's `png2asset` invocation
(captured verbatim in the autogenerated comment at `sprite.c` line 2) was
`-sh 48 -spr8x8 -noflip -c /sprite.c`, which emits dense 8x8 tile data.

Cross-reference confirmation from `sprite.h` header `#define`s:

```
#define sprite_TILE_W 8
#define sprite_TILE_H 8     <-- reference is 8x8 mode
#define sprite_TILE_COUNT 48
extern const uint8_t sprite_tiles[768];
```

The DSL in `gbkt-examples/metasprites/src/main/kotlin/.../Metasprites.kt` transcribed
its `tile(...)` indices from the reference's `-spr8x8` numbering (per the comment at
line 127: `// Format: METASPR_ITEM(dy, dx, dtile, attr) → tile(relX=dx, relY=dy, baseId=dtile)`).
Those indices do not map to the port's `-spr8x16` interleaved layout — each DSL
tile-index ends up pointing at half-tiles + blanks.

## Hypothesis #2 Verdict — CONFIRMED

`sprite-mode-init-grep.txt` shows:

- Reference `metasprites.c`:
  - Line 164 — `cgb_compatibility();`
  - Lines 189-193 — `#if sprite_TILE_H == 16 / SPRITES_8x16; / #else / SPRITES_8x8; / #endif` — because `sprite_TILE_H == 8`, the `SPRITES_8x8;` branch is taken.
  - Line 194 — `DISPLAY_ON;`.

- Port `main.c`:
  - Line 209 — `cgb_compatibility();`
  - Line 213 — `DISPLAY_ON;`
  - **Lines 210-212 contain NO `SPRITES_8x8;` or `SPRITES_8x16;` macro.** Only audio register writes (`NR52_REG`, `NR50_REG`, `NR51_REG`).

GBDK's default sprite mode after `cgb_compatibility()` is 8x16 (`SPRITES_8x16` is the
hardware default LCDC bit). Without an explicit `SPRITES_8x8;` call, the hardware pairs
consecutive 8x8 OAM tiles into 8x16 sprites — which by itself would garble even
correctly-laid-out 8x8 tile data.

## Named Root Cause

(also: Named root cause — singular per D-05.)

**Sprite-mode mismatch across the gbkt pipeline.** The port disagrees with itself and
with the user's DSL transcription intent at three layers:

| Layer | What it expects | What it produces |
|-------|------------------|------------------|
| DSL author intent (`Metasprites.kt`) | 8x8 tile indices (per CLAUDE.md `gbkt-examples/metasprites/CLAUDE.md` "Metasprite Frame Tile Coordinates") | n/a — read-only specification |
| Asset pipeline (`ConvertSpritesTask`) | 8x16 (defaults via `determineSpriteMode` line 236 because PNG height ≥ 16) | `png2asset -spr8x16` interleaved layout |
| Runtime emission (`GBDKPipelineV2` main) | Doesn't say — leaves GBDK default | 8x16 hardware sprite mode |

All three layers must agree, and the natural fit for the metasprite primitive is 8x8
(`-spr8x8` is the GBDK metasprite reference's own choice). Per D-05 ("name the bug
after the build, then fix"), we name the bug as a singular cause — the absence of an
authoritative 8x8-vs-8x16 contract carried across asset pipeline + runtime emission +
DSL — even though fixing it requires touching two files.

## Fix Shape Proposed for Plan 11

The minimum fix that makes the port match the reference's behavior:

### Edit 1 — Force `convertSprites` to `-spr8x8` for metasprite assets

In `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt`,
`determineSpriteMode(pngFile)` (line 228-238) currently defaults to `SPR8x16` when the
PNG height ≥ 16. Either:

- **Option A (narrow):** override the default to `SPR8x8` when the PNG is consumed by a
  metasprite (the metasprite IR has access to the resolved sprite-asset path; the task
  needs to know which PNGs are metasprite-bound).
- **Option B (broad):** change the default for all sprites to `SPR8x8` (matches the
  GBDK reference's choice for the metasprite primitive); document the change and verify
  no other example regresses.

Plan 11 should pick Option A if feasible (metasprite-aware), else Option B with a
regression-test sweep. RESEARCH §Code Examples lines 1005-1031 contains the exact code
shape for the runtime emission (Edit 2 below).

### Edit 2 — Emit `SPRITES_8x8;` in main.c between `cgb_compatibility();` and `DISPLAY_ON;`

In `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt`,
inside `buildMainFunction`'s `mainBody` builder (per RESEARCH §D-V1 line 795-797: file
location is `GBDKPipelineV2.kt` line 3580-3613 in the buildMainFunction body), after
the existing `cgb_compatibility()` call and BEFORE `DISPLAY_ON;`, conditionally emit
`SPRITES_8x8;` when `gameIR.metasprites.isNotEmpty()`. Per CLAUDE.md literal convention
this is `CRawCode("SPRITES_8x8;")` — it's a GBDK macro, not a C expression.

### Why both edits are required

- **Edit 1 alone** fixes the tile-data layout but leaves the runtime in 8x16 sprite
  mode — the hardware still pairs adjacent 8x8 tiles, so the elephant would still
  appear with shifted/doubled rows.
- **Edit 2 alone** sets the runtime to 8x8 mode but the port's tile data is still laid
  out as 8x16 top+bottom pairs interleaved with blanks — the elephant would still
  appear with blanks in alternate positions.

Together, Edit 1 + Edit 2 align all three pipeline layers (DSL intent + asset pipeline
+ runtime emission) on 8x8 mode, matching the GBDK reference exactly.

### Scope caveat for Phase 11+

If a future metasprite uses an 8x16 sprite size, the IR will need to carry that bit and
the conditional emission in main.c will branch (mirroring the reference's `#if sprite_TILE_H == 16`
pattern), and ConvertSpritesTask's default will need to consider per-asset metadata
rather than a single global default. Out of scope for 10.1 — all known metasprites in
the gbkt-examples tree consume `-spr8x8`.

`Seed004ElephantTileRenderingDiagnosticTest` (in
`gbkt-backend-gbdk/src/test/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/`) is
authored in this plan and locks the runtime side of the fix (Edit 2). The test asserts
that `main.c` contains `SPRITES_8x8;` between `cgb_compatibility();` and `DISPLAY_ON;`
when the GameIR contains at least one metasprite. At this plan's close the test is RED
— the `SPRITES_8x8;` substring is not found. Plan 11's Edit 2 will turn it GREEN.

Plan 11 should also add an analogous RED→GREEN test for Edit 1 (asset pipeline
`-spr8x8` enforcement) — either a `ConvertSpritesTask` unit test or an integration test
asserting that `elephant_tiles[]` has size 768 (not 896) after a fresh build.
