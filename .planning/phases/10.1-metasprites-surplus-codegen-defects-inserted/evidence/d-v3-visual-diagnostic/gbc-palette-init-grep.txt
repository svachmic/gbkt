## Surprising Finding — DSL Comments Are Stale

The DSL file `Metasprites.kt` lines 92-94, 317-319 carry PHASE-13 TODO comments asserting that
"all palette() calls default to slot 0 until explicit-slot DSL lands" and "Will produce:
set_sprite_palette(0, 1, gray_pal) for all four palettes (incorrect for runtime)".

**This is no longer true at codegen time.** The actual emission at main.c:234-237 distributes
the 4 palettes across slots 0, 1, 2, 3 correctly (one per call, in declaration order). The
TODO comments are stale.

This means hypothesis (a) from `DEF-10.1-13-C` — "Metasprites.kt DSL doesn't declare any GBC
color palettes (so all slots are 0 = black)" — is **FALSIFIED** by this evidence:

1. The DSL declares 4 distinct `spritePalette { }` blocks with 4 distinct GBC palette colors
2. The pipeline emits 4 distinct `set_sprite_palette(slot, 1u, *_pal)` calls
3. The palette data arrays are non-zero (white/colored/dark gradients, NOT all 0x0000)

## Implications for Named Cause

Pipeline emits palette writes correctly BUT places them in `play_enter()` (post-DISPLAY_ON,
post-SHOW_SPRITES, post-set_sprite_data) rather than in `main()` BEFORE `DISPLAY_ON`. This
diverges from the reference pattern. Whether this divergence actually causes the "completely
black" GBC screenshot is the open question — see `d-v3-visual-finding.md`.
