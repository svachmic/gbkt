## Summary

Phase 10.1 closes 8 seeded defects + 3 absorbed warnings across **5 files** (`MetaspriteVisitor.kt`,
`GBDKPipelineV2.kt`, `MetaspriteBuilder.kt`, `GameBuilder.kt`, `MetaspriteIR.kt` + visitor entry on
`ScriptOp.kt`). Most defects are bounded local edits — only two substrate shifts (D-08 `VramAllocator`
class, D-10 `MoveMetasprite` IR fields) need careful planning.

**Critical D-V1 finding (HIGH confidence):** Inspection of `gbkt-examples/metasprites/build/gbkt/generated/main.c`
shows the gbkt port's `main()` calls `cgb_compatibility()`, `DISPLAY_ON`, `SHOW_SPRITES`,
`set_sprite_data(...)` — **but never calls `SPRITES_8x8` or `SPRITES_8x16`**. The reference
(`/Users/michalsvacha/gbdk/examples/cross-platform/metasprites/src/metasprites.c:188-193`)
emits `SPRITES_8x8;` before `DISPLAY_ON` based on the `sprite_TILE_H == 16` macro from `sprite.h`.
GBDK's hardware default after `cgb_compatibility()` is **8x16 mode** — the hardware interprets each
pair of tiles as one 8x16 sprite while the descriptor's `dtile` indices assume 8x8 mode, producing
the garbled output. **D-V1 root cause hypothesis #2 (8x8/8x16 mode mismatch) is the dominant bug;**
hypothesis #1 (png2asset byte-ordering) is unlikely — the reference and port consume the same
`png2asset -spr8x8` output verbatim (`elephant_tiles[]` symbol from `sprites/elephant.h`).

**Critical SceneVisitor finding (HIGH confidence):** `SceneVisitor.visit` (lines 65-114) has **no
frame_prelude/postlude hook today**. Frame body is a flat `frameOps.map { ScriptOpVisitor.visit }`.
For D-11 (WR-05) Route A, the wrap must happen in `buildSceneFile` (GBDKPipelineV2.kt:1320-1379)
between `SceneVisitor.visit` and the `addMovementAndAnimationCalls` chain, OR by extending
`SceneVisitor.visit` to accept optional prelude/postlude statement lists. Plans must pick this
seam explicitly — D-11 Route A IS viable but requires a small new structural change. No escalation
needed; the wrap is local to `buildSceneFile`.

**Critical synthetic ROM finding (HIGH confidence):** `BankingAnalysisPass.run` has a single-scene
HOME fast-path at lines 91-95 (`if (game.scenes.size == 1 && codeUnits.size == 1 && estimatedBytes
<= 4096)`). The stress ROM must declare **at least two scenes** to escape the fast-path and force a
real `bank1.c`. Single-scene + many ops triggers the second clause (bytes > 4096) but is fragile;
two scenes is the predictable route.

**Primary recommendation:** Plan in this approximate order — Wave 1 parallel file-affinity
refactors (5 plans: GameBuilder, MetaspriteBuilder, two MetaspriteVisitor plans, GBDKPipelineV2
header-include + extern); Wave 2 parallel sub-plans (`VramAllocator` class + D-11 frame-wrap +
D-10 IR-field var-refs in 3 plans, ordered by file ownership); Wave 3 D-V1 diagnostic plan; Wave 4
D-V1 fix plan; Wave 5 `metasprites-stress/` synthetic ROM plan; Wave 6 per-behavior re-shoot
(3 plans — DMG behaviors 1+2 + GBC behavior 3); Wave 7 phase close + verification gate.
Floor estimate: **13 plans**; ceiling estimate: 16. Anything under 12 violates D-03.

### Pattern 1: VramAllocator (D-08 / CR-01 — Route B class)

**What:** A per-build singleton held on pipeline-local state that returns a monotonically
increasing tile index per `reserve(tileCount)` call. Replaces two parallel `var nextTile = 0`
counters in `buildSpriteDataLoadStatements` and `buildMetaspriteTileDataLoadStatements`.

**When to use:** Inside `buildMainFunction` — instantiate once, pass to a new unified
`buildAllSpriteDataLoadStatements(gameIR, allocator): List<CStatement>`.

**Minimal API surface** (intentionally small per D-08 "no preemptive Phase 11 design"):
```kotlin
// gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/VramAllocator.kt
internal class VramAllocator {
    private var nextTile: Int = 0

    /** Reserve [tileCount] contiguous sprite-VRAM slots. Returns the start index. */
    fun reserve(tileCount: Int): Int {
        require(tileCount >= 0) { "tileCount must be >= 0, got $tileCount" }
        val start = nextTile
        nextTile += tileCount
        return start
    }

    /** Total tiles reserved so far — useful for tests/diagnostics. */
    val tilesUsed: Int get() = nextTile
}
```

**Integration site** (Plan H replaces these two methods):
```kotlin
// REPLACES buildSpriteDataLoadStatements + buildMetaspriteTileDataLoadStatements
// CALLED ONCE from buildMainFunction at GBDKPipelineV2.kt:3538
private fun buildAllSpriteDataLoadStatements(gameIR: GameIR): List<CStatement> {
    val allocator = VramAllocator()
    val statements = mutableListOf<CStatement>()

    // Actor sprites first (preserves Phase 09 emission order)
    for (actor in gameIR.actors) {
        val sprite = actor.sprite ?: continue
        val arrayName =
            sprite.assetRef.path.substringBeforeLast('.').replace('/', '_').replace('-', '_') +
                "_tiles"
        val tilesWide = (sprite.size.width + 7) / 8
        val tilesHigh = (sprite.size.height + 7) / 8
        val tileCount = tilesWide * tilesHigh
        val start = allocator.reserve(tileCount)
        statements.addAll(ActorVisitor.generateSpriteDataLoad(actor, arrayName, start))
    }
```

### Pattern 2: MoveMetasprite IR-field var-refs (D-10 / CR-03 / WR-01)

**What:** Add four nullable `String?` fields to `MoveMetasprite` IR node that name the runtime

```kotlin
    functions: List<CFunction>,
```

## Common Pitfalls

### Pitfall 1: SceneVisitor has no prelude/postlude hook today
**What goes wrong:** D-11 Route A assumes a frame_prelude/postlude emission point exists. It
doesn't.
**Why it happens:** `SceneVisitor.visit` is a flat `frameOps.map`. No middleware layer.
**How to avoid:** Wrap in `buildSceneFile` AFTER `SceneVisitor.visit` returns — see Pattern 3.
**Warning signs:** Plan I attempts to modify `SceneVisitor.visit` signature instead of wrapping
externally → expands blast radius (every scene-using-visitor test will break).

### Pitfall 2: BankingAnalysisPass single-scene fast-path masks bank1.c bugs
**What goes wrong:** Stress ROM declares one scene; CR-02 test passes spuriously because
no `bank1.c` is generated at all (functions folded into `main.c`).
**Why it happens:** `BankingAnalysisPass.kt:91-95` puts single-scene games in HOME bank 0;
`GBDKPipelineV2.kt:522-537` then omits `bank1.c` from the output file list.
**How to avoid:** Stress ROM MUST declare ≥2 scenes (title + play). The CR-02 test MUST assert
on the actual `bank1.c` text, not the merged `main.c`.
**Warning signs:** `Seed009BankIncludeTest` asserts `mainCSource.contains("<gbdk/metasprites.h>")`
instead of `bank1CSource.contains(...)` — green but useless.

### Pitfall 3: File-level grep masks per-function regression in WR-05 test
**What goes wrong:** Stress ROM has two scenes with frame functions in the same file.
`hide_sprites_range` appearing once in `title_frame` and once in `play_frame` passes a file-level
`grep -c`, but the per-function invariant (exactly once per frame, not per call) is silently
broken in `play_frame` if it contains two metasprite calls.
**Why it happens:** Same class of bug as Phase 07.4 round-2 SC-4 (CLAUDE.md "History" section
in §Verification Methodology).
**How to avoid:** Use `extractFunctionBody` brace-walk in every Phase 10.1 emission test that
checks per-function invariants. CLAUDE.md §"Scope-level grep gates" — Plan 07.4-23 Task 1 step 3
demonstrates the awk pattern; the test file pattern at `MetaspriteEmissionTest.kt:81-101` is
the canonical Kotlin shape.
**Warning signs:** Test asserts `cSource.contains("hide_sprites_range")` without slicing by
function body.

### Pitfall 4: Generated C cache staleness defeats JVM emission tests
**What goes wrong:** `./gradlew test` passes after a fix, but `./gradlew runEmulator` shows the
old broken behavior because `build/gbkt/generated/main.c` was not regenerated.
**Why it happens:** JVM-tier emission tests run the pipeline in-process; they bypass the
filesystem entirely. The on-disk generated C is from the previous build.
**How to avoid:** Verifier MUST run `./gradlew :gbkt-examples:metasprites:clean
:gbkt-examples:metasprites:buildRom` (D-21). User-memory rule
`feedback_rom_build_smoke_test_for_codegen_phases.md` explicitly mandates this.
**Warning signs:** Phase verdict flipped to passed without a buildRom evidence log under
`evidence/`.

### Pitfall 5: Re-shoot evidence written to wrong phase directory
**What goes wrong:** Re-shot screenshots land in `.planning/phases/10.1-.../evidence/uat-screenshots/`
instead of `.planning/phases/10-.../evidence/uat-screenshots/`. D-04 explicitly mandates the
latter.
**Why it happens:** Reflexive "phase 10.1's evidence" thinking.
**How to avoid:** Plan M/N/O (re-shoot plans) MUST specify the absolute output path in the plan
action; verifier MUST check `ls -la .planning/phases/10-.../evidence/uat-screenshots/*.png` mtimes
are post-Phase-10.1-fix.
**Warning signs:** Phase 10's `evidence/uat-screenshots/` PNGs have unchanged mtimes after phase
close.

### Pitfall 6: D-10 IR-field var-refs break Phase 10 Metasprites.kt
**What goes wrong:** If D-10 lands without the canonical-fallback shape, `Metasprites.kt`
(which uses `var posX by i16Var(...)` without explicit `posX(posX)` binding in metasprite{})
breaks because `MoveMetasprite.posXVar` is `null` and the visitor emits an empty variable name.
**Why it happens:** D-10 changes the visitor's variable resolution path.
**How to avoid:** `MetaspriteVisitor.generateMetaspriteFrameSwitch` MUST default `posXVar` /
`posYVar` / `idxVar` / `rotVar` parameters to `"_posX"` / `"_posY"` / `"_idx"` / `"_rot"` —
canonical fallback preserves Phase 10's existing port. The Phase 10 example also has the option
to add explicit `posX(posX); posY(posY); idx(idx); rot(rot)` calls inside the
`metasprite { }` block once the new DSL surface lands — recommended for clarity but not required.
**Warning signs:** `MetaspriteEmissionTest` (Phase 10) goes RED after D-10 lands.

### Pitfall 7: D-V2 fix accidentally breaks `bgFillCheckerboard` callers
**What goes wrong:** The byte-literal change is at `MetaspriteBuilder.kt:269-272` — but the
function is also called from `Metasprites.kt:326`. The fix changes pixel output, which the Phase
10 re-shoot WILL show; this is intended per D-04.
**Why it happens:** D-V2's whole point is the visual change.
**How to avoid:** D-V2 test asserts the byte literal contains the four `0xF0` rows + four `0x0F`
rows pattern. Re-shoot test (D-04, Plan M) asserts BG visually shows checker squares (not
diagonal lines).
**Warning signs:** D-V2 JVM test goes GREEN but re-shot screenshots still show diagonals — means
fix didn't propagate to the generated C; force `:clean` and regenerate.

### Pitfall 8: D-08 VramAllocator change breaks pong/breakout/etc. emission shape
**What goes wrong:** Replacing `buildSpriteDataLoadStatements` + `buildMetaspriteTileDataLoadStatements`
with a unified path slightly changes the order of `set_sprite_data` calls in `main.c` for any
example. Existing emission tests for pong/breakout/explorer may have brittle ordering assumptions.
**Why it happens:** Pong/breakout/explorer have actor sprites only (no metasprites) — the actor
loop runs first in BOTH the old and new code paths. As long as actors are iterated first, the
emitted byte sequence is identical.
**How to avoid:** Pattern 1's `buildAllSpriteDataLoadStatements` MUST iterate `gameIR.actors`
BEFORE `gameIR.metasprites`. Test: run full `:gbkt-backend-gbdk:test` AND
`:gbkt-examples:simple-physics:test` AND `:gbkt-examples:pong:test` after Plan H to confirm no
emission-shape regression.
**Warning signs:** Pong/breakout/simple-physics test failures after Plan H land.

## Open Questions

1. **Are `MetaspriteIR.posXVarName` / `idxVarName` etc. needed in addition to `MoveMetasprite.posXVar`?**
   - What we know: `MoveMetasprite` is the call-site op; `MetaspriteIR` is the metasprite
     declaration. If we use D-10 option (a) implicit scope-walk, the binding is on
     `MetaspriteIR`; the `moveMetasprite()` call resolves and copies onto `MoveMetasprite`.
     If we use option (b) explicit override, the binding is per-call on `MoveMetasprite` only.
   - What's unclear: option (a) needs MetaspriteIR fields; option (b) does not. Planner picks.
   - Recommendation: try (a). MetaspriteIR + MoveMetasprite both carry the four optional fields;
     `MetaspriteIR` fields are the "default" and `MoveMetasprite` fields are the "per-call override"
     that defaults to `null` (which inherits from MetaspriteIR). This gives both ergonomics for
     free at the cost of 4 extra optional fields on MetaspriteIR. The single-metasprite Phase 10
     case keeps using canonical fallback (`_posX` / `_posY` / `_idx` / `_rot`).

2. **For D-V1, should the `SPRITES_8x8;` emission also detect existing 8x16 metasprites?**
   - What we know: `png2asset -spr8x8` produces 8x8 tile data; `png2asset -spr8x16` produces
     8x16. The reference `metasprites.c:188-193` switches on `sprite_TILE_H == 16` macro.
   - What's unclear: gbkt's `MetaspriteIR` currently doesn't carry a tile-height field; all known
     metasprites are 8x8 (Phase 10 elephant + stress ROM elephant/tiger).
   - Recommendation: emit `SPRITES_8x8;` unconditionally when `gameIR.metasprites.isNotEmpty()`
     for Phase 10.1 scope. Add `MetaspriteIR.tileHeight: Int = 8` field if/when an 8x16 metasprite
     lands (Phase 13+). Document this as a deferred decision in evidence.

3. **Should the D-V2 byte-literal fix update the helper KDoc to note the intentional deviation
   from reference's `pattern[]` (which is the diagonal)?**
   - What we know: reference uses diagonal `pattern[]` literal `0x80,0x80,0x40,0x40,...` (verified
     at `metasprites.c:43`). Seed proposes checker `0xF0,0xF0,0xF0,0xF0,0x0F,0x0F,0x0F,0x0F` —
     intentional deviation.
   - What's unclear: this is a 1-line KDoc edit, not a fix-route question.
   - Recommendation: update the KDoc on `bgFillCheckerboard` to say "diverges from reference
     pattern (which is a diagonal stripe despite the name) to honor the helper's name and
     produce a true checker visual". Already implied by the seed.
