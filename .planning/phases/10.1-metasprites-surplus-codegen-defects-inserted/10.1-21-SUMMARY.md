# Phase 10.1 Plan 21: D-V3 4th-Layer Diagnostic — Summary

**Diagnosed the 4th-layer named root cause of DEF-10.1-13-C.** Plans 10.1-19 + 10.1-20 closed
the sprite-palette bootstrap-order layer (DV3GbcPaletteWriteDiagnosticTest 3/3 GREEN,

## What Was Done

### Task 1 — Post-Plan-20 main.c grep (commit `2abacf16`)

Regenerated `gbkt-examples/metasprites/build/gbkt/generated/main.c` after a clean
`./gradlew :gbkt-examples:metasprites:generateC`. Grep captures all bootstrap-relevant calls
in `main()`, `play_enter()`, and the per-frame `move_metasprite_*` block. Evidence file:
`evidence/d-v3-visual-diagnostic-v2/post-fix-main-c-grep.txt`.

**Key findings from the grep:**

1. Bootstrap order (lines 208-222) IS reference-aligned per Plan 20 fix:
   - DISPLAY_OFF → cgb_compatibility → 4× set_sprite_palette → sound init →
     set_sprite_data → SHOW_BKG → SHOW_SPRITES → SPRITES_8x8 → DISPLAY_ON.
2. **MISSING: `set_bkg_palette()` is NEVER called anywhere in main.c.** BG palette init relies
   entirely on `cgb_compatibility()`'s implicit slot-0 side-effect.
3. **MISSING: BG tile data init (`set_bkg_data` + `fill_bkg_rect`) is deferred to play_enter
   (lines 247-248) AFTER DISPLAY_ON.** Per Plan 20's explicit out-of-scope decision.
4. `move_metasprite_*` calls pass `subpal` (= `_rot >> 2`) as `base_prop` (3rd positional
   arg). Per `<gb/metasprites.h>` docs, this overwrites OAM attribute byte → bits 0-2 = subpal
   = sprite palette slot 0..3. The dynamic per-frame palette cycling pipeline is correct.

### Task 2 — OAM attribute byte trace (commit `056b8ea8`)

Compared port's `metasprite_t` descriptor table to reference's `png2asset` output
(`/Users/michalsvacha/gbdk/examples/cross-platform/metasprites/obj/gb/res/sprite.c`).
Confirmed both use `props=0` for every sub-tile entry (port via 3-field initializer + C
zero-fill; reference via explicit `S_PAL(0)` macro which expands to literal 0 on Game Boy
per `<gb/gb.h>:105`). Evidence file: `evidence/d-v3-visual-diagnostic-v2/oam-attribute-byte-trace.md`.

**Hypothesis 2 (OAM attribute hardcoded to S_PAL(0)): FALSIFIED.** The OAM attribute byte IS
hardcoded to 0 in descriptor — but this matches the reference. Runtime `move_metasprite_*`
OVERWRITES OAM attr from `base_prop` (per the `<gb/metasprites.h>` doc string). Port passes
`subpal` as `base_prop`. Runtime evidence (`_current_base_prop=2` at frame 61) confirms the
correct value reaches OAM.

**Hypothesis 3 (descriptor needs per-frame regen): FALSIFIED.** Neither reference nor port
regenerates descriptors per frame. The GBDK design pattern is "static descriptor + dynamic
base_prop"; both implementations follow it identically.

### Task 3 — cgb_compatibility behavior notes (commit `b1cb844f`)

Read `/Users/michalsvacha/gbdk/include/gb/cgb.h:176-188`. Confirmed `cgb_compatibility()`
is an obsolete alias for `set_default_palette()` with the docstring "Sets CGB palette 0 to
be compatible with the DMG/GBP" — meaning it sets palette slot 0 (BG + sprite) to the
DMG-default grayscale (White, Light Gray, Dark Gray, Black). It does NOT switch the GBC into
"DMG-compat mode"; it does NOT no-op subsequent `set_sprite_palette()` calls. Evidence file:
`evidence/d-v3-visual-diagnostic-v2/cgb-compat-mode-vs-set-palette-notes.md`.

**Hypothesis 1 (cgb_compatibility puts GBC into DMG-compat mode): FALSIFIED.**

The notes file documents the port-vs-reference side-by-side and identifies the FIRST gap
specific to the GBC path: **gbkt never explicitly initializes BG palette RAM via
`set_bkg_palette()`** — it relies on `cgb_compatibility()` to do so as a side-effect.
This sets up the 4th-layer hypothesis.

### Task 4 — Named 4th-layer cause + RED test (commit `2359f529`)

Synthesized the falsifications above with Coffee-GB internals analysis. Created:

**`evidence/d-v3-visual-diagnostic-v2/d-v3-visual-finding-v2.md`** (250 lines):
documents the named 4th-layer cause and the exact Plan 22 fix shape.

**Named cause:** The conjunction of two facts:

(a) **gbkt NEVER emits `set_bkg_palette()`** — relies entirely on `cgb_compatibility()`'s
    slot-0 side-effect for BG palette RAM initialization.

(b) **Coffee-GB's `cgb_compatibility()` implementation (in `sm83.lib`, opaque to JVM
    analysis but inferred from the literal-black pixel-decode) writes `BGP_REG` (DMG
    palette register) only, NOT `BCPD` (GBC palette RAM register).** On Coffee-GB GBC
    mode (`gbc=true` in Gpu constructor), the CGB pixel pipeline reads from BG palette
    RAM, not BGP_REG. With BG palette RAM left at its Java zero-init state (`new
    int[8][4]` = all 0x0000), every BG pixel renders RGB(0,0,0) = pure black.

This conjunction explains why behavior1 (`_cpu=1`, DMG path) shows visible green checker
(DMG renders via BGP_REG, which cgb_compatibility DID set to DMG-default 0xE4) while
behavior3 (`_cpu=17`, GBC path) shows literal RGB(0,0,0) every pixel.

**Plan 22 fix shape (3 emission changes in `GBDKPipelineV2.buildMainFunction()`):**

1. Emit `const palette_color_t _gbkt_default_bg_pal[4] = {0x7FFF, 0x56B5, 0x294A, 0x0000};`
   constant alongside the existing user-declared palette arrays.
2. Emit `set_bkg_palette(0u, 1u, _gbkt_default_bg_pal);` in main() AFTER the 4× sprite palette
   block, BEFORE DISPLAY_ON.
3. Hoist `bgFillCheckerboard` (the RawOp containing `fill_bkg_rect` + `set_bkg_data`) from
   `{start}_enter()` body into main() between `set_sprite_data` (line 218) and `SHOW_BKG`
   (line 219). Keep the same RawOp in `play_enter()` per Plan 20's duplication-not-relocation
   pattern (idempotent re-write).

**`gbkt-backend-gbdk/src/test/kotlin/io/github/gbkt/backend/gbdk/codegen/visitor/DV3VisualV2DiagnosticTest.kt`** (committed RED):
