<objective>
Per D-05 — diagnostic-first for DEF-10.1-13-B. Plan 10.1-02 replaced the original diagonal-stripe literal with `0xF0,0xF0,...,0x0F,0x0F` thinking it produces a true 4×4 checker. The UAT re-shoot at Plan 10.1-13 revealed the actual visual is "rectangles rather than squares — slightly wider than taller".

Game Boy 2-bpp planar tile encoding: each row is 2 bytes (plane 0 + plane 1). A byte `0xF0` = `11110000` = leftmost 4 pixels lit on that plane. Stacking 8 row-pairs of `0xF0,0xF0` on top and `0x0F,0x0F` on bottom produces:
- Top 4 rows: leftmost 4 pixels lit (color 3, both planes)
- Bottom 4 rows: rightmost 4 pixels lit (color 3, both planes)

That's NOT a 4×4 checker — it's 2 vertical halves of a 4-wide-by-8-tall stripe pattern. When tiled across a 20×18 BG grid, adjacent tiles produce 4-wide horizontal stripes alternating with 4-wide vertical stripes — looking like rectangles.

The correct true 4×4 checker requires alternating per row: `0xF0,0xF0` for rows 0-3, `0x0F,0x0F` for rows 4-7. That IS what Plan 02 emitted. So either the visual is actually correct and the user perceives rectangles because each tile is 8×8 (not 4×4), OR there's a different misunderstanding.

This plan resolves the ambiguity: capture actual screen pixels, compute expected vs observed, name the cause.
</objective>
