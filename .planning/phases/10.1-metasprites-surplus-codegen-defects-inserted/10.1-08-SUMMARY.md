# Phase 10.1 Plan 08: Unify actor+metasprite VRAM tile-slot allocator (CR-01) Summary

**A new `internal class VramAllocator` replaces two parallel `var nextTile = 0` counters in `GBDKPipelineV2` with a single per-build monotonic allocator — closing CR-01 / SEED-008, the latent VRAM collision that would surface in Phase 12 (platformer_template).**

## Accomplishments

- **Closed CR-01 / SEED-008.** `GBDKPipelineV2.buildMainFunction` no longer emits two `set_sprite_data(0u, …)` calls when a game has both an actor sprite and a metasprite. A single `VramAllocator` instance, scoped to one `pipeline.generate()` call, hands out monotonic start indices to both the actor loop and the metasprite loop. The pre-fix collision is structurally impossible at the IR-to-C boundary.
- **Added `internal class VramAllocator`** (74 lines in `gbkt-backend-gbdk/.../pipeline/VramAllocator.kt`). Minimal API per D-08 Claude's-discretion: `reserve(tileCount: Int): Int` (returns pre-advance cursor, advances by N, rejects negatives via `require()`) + `val tilesUsed: Int` (diagnostic). D-13b visibility — codegen-only, no DSL exposure.
- **Replaced both old helpers with a unified loader.** The new `buildAllSpriteDataLoadStatements(gameIR)` instantiates one allocator, iterates `gameIR.actors` FIRST (Pitfall 8 — preserves Pong/Breakout/SimplePhysics emission shape), then `gameIR.metasprites` (CR-01 fix — metasprite tiles continue from where actors left off). The two private helpers `buildSpriteDataLoadStatements` and `buildMetaspriteTileDataLoadStatements` are deleted outright; their names live on as historical breadcrumbs inside the unified loader's KDoc backtick spans.
- **Added 5 regression tests:**
  - `VramAllocatorTest` (3 tests): locks the allocator contract — monotonic reserve, zero-tile cursor read, negative throws.
  - `Seed008VramCollisionTest` (2 tests): locks the unified-loader emission shape. Test 1 asserts that a 1-actor (8x16 = 2 tiles) + 1-metasprite (max tileId 47 → 48 tiles) game emits `set_sprite_data(0u, 2u, sprites_player_tiles)` followed by `set_sprite_data(2u, 48u, elephant_tiles)` (NOT two `set_sprite_data(0u, …)` calls). Test 2 asserts actor-first ordering (offset of `set_sprite_data(0u, 2u, …)` < offset of `set_sprite_data(2u, 48u, …)` inside `main()` body).
- **No regressions in any actor-using example.** `:gbkt-examples:{metasprites,pong,breakout,simple-physics,explorer}:test` all GREEN — Pitfall 8 mitigation confirmed by the broader test matrix.
- **Phase 12 prerequisite unblocked.** The platformer_template port (actors + metasprites + tilemap together) can now proceed without the latent CR-01 collision corrupting actor sprite tiles in VRAM.

## Decisions Made

- **Local-scope `VramAllocator()` instantiation.** Created inside `buildAllSpriteDataLoadStatements` body — not a pipeline-instance field, not a top-level object. This makes T-10.1-08-A (allocator state leaking across `pipeline.generate()` calls) structurally impossible: every build gets a fresh allocator.
- **Both old private methods deleted outright (no `@Deprecated` stub).** They were `private fun` with one call site each (both inside `buildMainFunction`) and zero external consumers. The unified loader's KDoc preserves their names as historical breadcrumbs in backtick code spans (NOT KDoc symbol links — backticks don't produce dokka warnings).
- **KDoc cleanup in `buildOAMInitStatements`** to redirect the stale `[buildSpriteDataLoadStatements]` link to `[buildAllSpriteDataLoadStatements]`. The OAM init method retains its OWN local `nextTile` counter — OAM init only consumes actor tiles, no metasprite OAM slots, so the unified allocator does not apply there. The new KDoc note documents this scope boundary so a future refactor doesn't try to unify OAM init too.
- **Did NOT extract `ActorVisitor.generateSpriteDataLoad` / `MetaspriteVisitor.generateMetaspriteTileData`** because they already existed with the correct `(actor/ms, arrayName, startTile): List<CStatement>` signatures from earlier phases. The plan's `<interfaces>` Note (line 106-107) anticipated this. Saved ~15 minutes of unnecessary refactoring.
- **Pre-existing Seed004 RED not added to deferred-items.md** — same rationale as Plan 10.1-07 SUMMARY § Decisions Made: `Seed004ElephantTileRenderingDiagnosticTest` is the named-root-cause anchor explicitly authored by Plan 10.1-10 to drive Plan 10.1-11's D-V1 SPRITES_8x8 fix, NOT a discovered issue from this plan's execution. ## Issues Encountered

### Worktree-path-safety violation during Task 1 (recovered — see § Performance)

**Symptom:** Initial Task 1 file Writes appeared to succeed (Write tool reported "File created successfully"), but `./gradlew :gbkt-backend-gbdk:compileTestKotlin` consistently reported `UP-TO-DATE` without compiling the new files, and `./gradlew test --tests VramAllocatorTest` failed with "No tests found for given includes". The Kotlin source files list in `--info` output did not include the new tests despite their being present in the source directory.

**Root cause:** I used absolute paths via the Write tool (`/Users/michalsvacha/GitHub/personal/gbkt/gbkt-backend-gbdk/...`) that resolved to the **main repo** rather than the worktree (`/Users/michalsvacha/GitHub/personal/gbkt/.claude/worktrees/agent-a860a92a3badba0cb/gbkt-backend-gbdk/...`). Both paths exist on disk; both have a `gbkt-backend-gbdk` subtree. The main-repo paths predate the worktree creation. From inside the worktree, `./gradlew` only scans the worktree's source set — so my new test files in the main repo were invisible.

**Recovery:** Removed the misplaced files from the main repo via `rm` (after explicit verification that they were the ones I just created), then recreated them via Write using **relative paths** (`gbkt-backend-gbdk/src/test/...`). Relative paths resolve against the worktree root (because that's `pwd`), eliminating the ambiguity. Verified by `git rev-parse --show-toplevel` confirming the worktree root and `ls "$WT_ROOT/.../pipeline/"` confirming the files landed there.

**Diagnostic time:** ~50 minutes — most of which was spent ruling out Gradle daemon cache, Kotlin compiler daemon, sandbox blocking, and detekt/spotless filters before noticing the path discrepancy.

**Lesson for future plan executions (recorded for the verifier):** In a Claude Code worktree, ALWAYS use relative paths for Edit/Write tool calls. Absolute paths constructed from prior `pwd` output captured in the orchestrator context will silently target the main repo. This matches the `<absolute-path-safety>` and `<cwd-drift-assertion>` mandates in `references/worktree-path-safety.md` (which the executor instructions explicitly require — I missed applying them at the right step).
