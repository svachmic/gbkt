## Warnings

### WR-01: `resolveSpriteMode` swallows all exceptions and may leak `ImageInputStream` on the unhappy path

**File:** `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertSpritesTask.kt:464-486`

**Issue:**
```kotlin
return try {
    val stream = javax.imageio.ImageIO.createImageInputStream(pngFile)
    val reader = javax.imageio.ImageIO.getImageReaders(stream).next()
    reader.setInput(stream, true)
    val height = reader.getHeight(0)
    reader.dispose()
    stream.close()
    if (height < 16) SpriteMode.SPR8x8 else SpriteMode.SPR8x16
} catch (_: Exception) {
    SpriteMode.SPR8x16
}
```

Two latent defects:

1. `ImageIO.createImageInputStream(pngFile)` returns `null` for unrecognized files;
   `getImageReaders(null)` returns an empty iterator and `.next()` throws
   `NoSuchElementException`. Likewise if no `ImageReader` is registered for the file
   type. In both cases the exception path silently classifies the PNG as `SPR8x16` —
   which is the documented fallback, so behaviorally tolerable, but the catch is
   wider than necessary.
2. When any exception fires between `createImageInputStream` and `stream.close()`,
   neither `reader.dispose()` nor `stream.close()` runs. JVM finalizers eventually
   clean up, but on a long-running Gradle daemon with many sprites this is a slow
   file-handle leak.

Suggested fix (use `use { }` for AutoCloseable + narrower catch):
```kotlin
return try {
    javax.imageio.ImageIO.createImageInputStream(pngFile)?.use { stream ->
        val readers = javax.imageio.ImageIO.getImageReaders(stream)
        if (!readers.hasNext()) return SpriteMode.SPR8x16
        val reader = readers.next()
        try {
            reader.setInput(stream, true)
            val height = reader.getHeight(0)
            if (height < 16) SpriteMode.SPR8x8 else SpriteMode.SPR8x16
        } finally {
            reader.dispose()
        }
    } ?: SpriteMode.SPR8x16
} catch (e: java.io.IOException) {
    SpriteMode.SPR8x16
}
```

This preserves the documented fallback semantics, closes the input stream on every
exit path, narrows the catch to I/O-specific exceptions, and handles the
no-reader-registered case explicitly rather than via `NoSuchElementException`.

### IN-01: Bare `println(...)` warning logger in `allocateZoneBanks`

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:603-606`

**Issue:**
```kotlin
if (override != null) {
    // Manual override: trust developer, log warning
    println(
        "WARNING: Zone '${zone.id}': manual bank override bank($override). " +
            "Trusting developer."
    )
    ...
}
```

`println` writes directly to stdout, bypassing the Gradle logger / SLF4J the rest of
the pipeline uses (e.g. `ConvertSpritesTask.logger.lifecycle/warn`). End users
running `./gradlew generateC` will see this WARNING line mixed in with task output
unfiltered; it cannot be silenced via `--quiet` and is not captured by structured
log appenders.

This is pre-existing (not added by Phase 10.1) but surfaced by the QUICK pattern
scan as the only `println` in the touched production set. Suggest routing through a
proper logger — a Kotlin `Logger` companion or, if this class is callable from
non-Gradle contexts, a pluggable `Consumer<String>` hook the pipeline owner
configures.

### IN-02: Redundant `!!` after null guards in scene-bank routing helpers

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:2184, 2189, 3991, 3999, 4007`

**Issue:** Five sites use `scene.bankSlot!!` after an explicit `scene.bankSlot != null`
check on the same line (or one line earlier). Kotlin smart-cast doesn't fire across
`.filter { ... }` lambda boundaries (line 2184) or across helper-method boundaries
(line 2189), and the `&&` is on the same expression as the `!!` for the
`enter/frame/exitFunctionName` triple (lines 3991/3999/4007). Behaviorally safe
because of the preceding guards, but the `!!` is the kind of pattern that becomes a
real NPE the moment a refactor moves the null check.

These are pre-existing (not Phase 10.1 work) but worth a future cleanup. Suggested
shape using `let` / pattern destructuring:
```kotlin
private fun enterFunctionName(scene: SceneIR): String {
    val slot = scene.bankSlot
    return if (slot != null && slot.bank > 0) {
        "${scene.id}_enter_trampoline"
    } else {
        "${scene.id}_enter"
    }
}
```

The local-variable binding allows smart-cast and removes the `!!` without changing
semantics. Apply the same pattern to lines 2184/2189.
