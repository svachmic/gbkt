### Pattern 1: Delegate-pattern provideDelegate (`ActorDelegate` analog)

**What:** `val nextLevelScene by levelCardScene { ... }` — name inferred from Kotlin property
name via `KProperty.name` in `provideDelegate`.

**When to use:** Whenever a DSL surface needs to capture a user-defined name; mandatory per
Project Rule #1 (no magic strings).

**Example (mirror this verbatim for `LevelCardSceneDelegate`):**

```kotlin
// Source: gbkt-lang/src/main/kotlin/io/github/gbkt/core/dsl/ActorBuilder.kt:1218–1239

class ActorDelegate(private val nameOverride: String?, private val block: ActorBuilder.() -> Unit) :
    ReadOnlyProperty<Any?, ActorRef> {
    private var ref: ActorRef? = null

    operator fun provideDelegate(
        thisRef: Any?,
        property: KProperty<*>,
    ): ReadOnlyProperty<Any?, ActorRef> {
        val name = nameOverride ?: property.name
        val gameBuilder =
            GameBuilderContext.current ?: error("actor {} must be called inside a game {} block")
        ref = gameBuilder.registerActor(name, block)
        return this
    }

    override fun getValue(thisRef: Any?, property: KProperty<*>): ActorRef =
        ref ?: error("ActorDelegate not initialized — was provideDelegate called?")
}
```

The new `LevelCardSceneDelegate` lowers to `gameBuilder.scene(name) { ... }` internally —
this means the helper produces a regular `SceneRef` compatible with all existing
`navigate(sceneRef)` call sites. Critical for the `_nextLevelSceneRef` reference in
PlatformerTemplate.kt:470 to keep working.

**Critical:** the helper MUST be invoked inside `game { }` so that `GameBuilderContext.current`
is non-null — same precedent as every other delegate (`u8Var`, `actor`, `metasprite`, etc.).

### Pattern 3: Emission-invariant test with brace-walk extraction

**What:** Test asserts substrings inside a brace-walk-extracted function body, NOT at file
level. Closes the "scope-level grep gate" landmine (Plan 12-09b precedent).

**When to use:** Whenever the assertion must lock per-function shape — e.g., "main() body
contains X but NOT Y" or "setup_current_level body contains the spawn-table assignment".

### Anti-Patterns to Avoid

- **Hand-rolling a scene-block helper without `provideDelegate`** — would re-introduce
  the magic-string anti-pattern flagged in `SEED-ZONE-MAGIC-STRING-DELEGATE-MIGRATION.md`.
- **Adding a new sealed-type subtype to `SystemIR`** — breaks the leaf-module invariant
  (gbkt-ir is dep-free). Use the `GenericSystem(type="...", config=Map<String,Any>)` opaque
  payload pattern instead (mirroring `platformerInput`, `platformerPhysics`,
  `tilemap_collision`).
- **File-level `grep -c "setup_current_level" main.c` assertion** — masks D-04's per-scope
  intent. Use brace-walk extraction.
- **Removing the `gameUsesTilemapCollision` gate** — would explode the D-14 regression sweep
  (pong/breakout/etc. would gain SCENE_NEXTLEVEL emission and break byte-identity).
- **Computing spawn defaults at codegen WITHOUT emitting a warning** — D-07 requires the
  warning so users know to declare explicitly.

## Common Pitfalls

### Pitfall 1: `_next_level` re-increment same-frame after the spawn fix

**What goes wrong:** Phase 12.6 fixes DEFECT-2 by writing `_playerX` from the spawn table —
but PlatformerVisitor's level-end trigger (kt:1110–1126) reads `player_real_x` at start of
EVERY frame. If the spawn-write happens AFTER the frame-dispatch reads `_playerX` (which is
what would happen if the spawn write lives in a frame-dispatched scene), the trigger could
still re-fire one frame later.

**Why it happens:** `setup_current_level()` is called by the trimmed `levelCardScene` Start-press
handler BEFORE `navigate_to_scene(gameplay)`. The next main-loop iteration enters the gameplay
scene with `_playerX` already at the spawn position — but the level-end trigger runs INSIDE the
gameplay scene's `frame { }` block, which means it reads `_playerX` AFTER the start-of-frame
position update. Order of operations matters.

**How to avoid:** The spawn-table write inside `setup_current_level()`'s per-case body MUST come
AFTER the `_current_level_width` assignment, BEFORE the case `break`. This ensures the first
gameplay frame's level-end trigger reads `_playerX = 40 << 4` (spawn) compared against
`_current_level_width - 32u = 480 - 32 = 448` → trigger does NOT fire. The reference's
`SetupPlayer()` runs after `SetupCurrentLevel()` in main.c:60–82 — gbkt's flow with both writes
inside `setup_current_level()` is equivalent.

**Warning signs:** anchor5LevelSwitch test variables show `_current_level == 2` (re-fire) or
`_playerX >> 4 == 449` immediately after the level switch.

### Pitfall 2: `_playerX` is INT16 subpixel (shift-by-4) — not UINT8

**What goes wrong:** Naïve codegen writes `_playerX = 40u;` — but `_playerX` is declared as
`INT16` storing subpixel-shifted values (40 pixels = 40 << 4 = 640 subpixels). A direct
UINT8 write would land the player at 2.5 pixels.

**Why it happens:** The reference `SetupPlayer()` (player.c:101–103) writes `playerX = 40<<4;`
explicitly. PlatformerTemplate.kt declares `var playerX by i16Var(80 shl 4)` — the framework
expects shifted values.

**How to avoid:** The generated case body MUST emit `_playerX = ((UINT16)_level_spawn_x[N]) << 4;`
(shift-by-4 at codegen time). Mirror the reference shift exactly. The DSL surface
`spawn(40, 120)` takes UByte PIXELS; codegen applies the `<< 4` shift.

**Warning signs:** Player visually spawns at x=2 (top-left edge) on every level start; clipping
into floor tiles.

### Pitfall 3: `_playerVx` / `_playerVy` not reset → carry-over momentum

**What goes wrong:** Player retains horizontal velocity across level switches; first frame of
new level has player slamming into the left edge.

**Why it happens:** CONTEXT D-06 specifies "and `_playerVx = 0` / `_playerVy = 0` for safety"
— this is NOT optional; it's part of the fix. The visitor pattern that reads `_playerVx`
(PlatformerVisitor.kt:553) emits `_<vxVar>` which is the user-declared `_playerVx`.

**How to avoid:** Inside the same per-case body block, after `_playerX = ...` and `_playerY = ...`,
emit `_playerVx = 0;` and `_playerVy = 0;`. Use the same `vxSym`/`vySym` resolution pattern
PlatformerVisitor uses (read `tilemap_collision.vxVar` from `GenericSystem.config`).

**Warning signs:** Player teleports to spawn, then instantly moves; runtime trace shows
non-zero `_playerVx` on frame 0 of new level.

### Pitfall 4: `LevelSwitchEmissionTest` ordering assertion (lines 280–289)

**What goes wrong:** The existing test asserts `if (` < `navigate_to_scene` < `setup_current_level`
ordering. After D-04 trim, the `setup_current_level` substring should NOT appear in `main()`
body — the ordering assertion becomes invalid.

**Why it happens:** D-05 says "re-point", which the planner must implement: not just delete the
assertion, but replace it with a NEGATIVE assertion (`mainBody must NOT contain "setup_current_level"`)
AND add a new positive assertion in `LevelCardSceneEmissionTest` (or extended in the existing file)
that asserts setup_current_level appears in the NextLevel scene's emitted body.

**How to avoid:** Plan the test edit AND the new test in the same wave. Avoid leaving the old
ordering assertion in place — it will GREEN-falsely (substring absent → matches the desired
behavior, but only by accident).

**Warning signs:** Existing test passes after D-04 trim WITHOUT being edited — sign the
assertion is now meaningless, not validating anything.

### Pitfall 5: `levelCardScene { onStartPress(gameplayScene) }` requires forward-declared SceneRef

**What goes wrong:** PlatformerTemplate.kt declares `gameplayScene` AFTER `nextLevelScene`
(at lines 408 and 434). If the migrated `levelCardScene { onStartPress(gameplayScene) }` is
declared BEFORE gameplayScene, the Kotlin reference is undefined.

**Why it happens:** Scenes traditionally rely on string IDs (`navigate("gameplay")`) to defer
resolution to codegen time. The new `onStartPress(gameplayScene: SceneRef)` requires the ref
at DSL-recording time.

**How to avoid:** Either (a) re-order declarations so `gameplayScene` precedes `nextLevelScene`,
or (b) use the existing `sceneRef("gameplay")` forward-declaration helper (GameBuilder.kt:306)
inside `onStartPress(...)`. Recommend (a) for the platformer-template migration — cleaner;
no forward-declare needed.

**Warning signs:** Compile error "unresolved reference: gameplayScene" in PlatformerTemplate.kt
after migration.

### Pitfall 6: `gameUsesTilemapCollision` gate inclusion of `levelCardScene` emission

**What goes wrong:** The new `levelCardScene` Start-press path emits `setup_current_level()`.
If this lives OUTSIDE the `gameUsesTilemapCollision` gate, it would emit for non-platformer
games that happen to use `levelCardScene` — but no non-platformer game does. The risk is
INVERSE: if the gate is too tight, a future genre using `levelCardScene` would miss the
emission.

**Why it happens:** `gameUsesTilemapCollision` is a platformer-specific check. `levelCardScene`
is a platformer DSL helper. They're aligned today but coupling them tightly could create
issues.

**How to avoid:** For Phase 12.6, KEEP the gate tight. The `setup_current_level()` call only
emits when both (a) `gameUsesTilemapCollision == true` AND (b) the `levelCardScene` is
declared. This preserves D-14 byte-identity for the 7-target regression sweep. Future
cross-genre work (the deferred `gameFlow.levelCard()`) can lift the gate when it ships.

**Warning signs:** Plan 12-26's 7-target regression sweep red-lines after the fix.

internal fun buildLevelSpawnTablesIfNeeded(gameIR: GameIR): String? {
    if (!gameUsesTilemapCollision(gameIR)) return null
    val gameplayZones = gameIR.zones.filter { zone ->
        val idLower = zone.id.lowercase()
        !idLower.contains("title") && !idLower.contains("nextlevel") &&

// setup_current_level() reads these to write _playerX/_playerY on every level switch.

### `levelCardScene { onStartPress(gameplayScene) }` DSL surface (D-03)

```kotlin
// Source: gbkt-genre-platformer/.../dsl/PlatformerExtensions.kt (new code at file end)

import io.github.gbkt.core.dsl.GameBuilderContext
import io.github.gbkt.core.dsl.SceneRef
import kotlin.properties.ReadOnlyProperty
import kotlin.reflect.KProperty

/**
 * Builder for a level-card scene (mirrors GBDK platformer_template's NextLevel card flow).
 *
 * The card scene shows level-transition graphics, waits for Start press, then triggers
 * setup_current_level() + navigates to the gameplay scene. This is the OWNED LIFECYCLE
 * that closes Phase 12.6 DEFECT-1 — the show-card → wait → setup → navigate sequence
 * runs across multiple frames with vblanks between, so card art renders before the new
 * level's tilemap stomps VRAM.
 *
 * Mirrors the reference behavior at gbdk/examples/cross-platform/platformer_template/src/main.c:44–82.
 */
@GbktDsl
class LevelCardSceneBuilder(val id: String) {
    private var gameplaySceneRef: SceneRef? = null
    private val sceneBuilderBlock = mutableListOf<io.github.gbkt.core.dsl.SceneBuilder.() -> Unit>()

    /**
     * Registers the gameplay SceneRef to navigate to on Start press. The codegen
     * emits an inline `setup_current_level();` call BEFORE `navigate_to_scene(<gameplay>)`.
     */
    fun onStartPress(gameplayScene: SceneRef) {
        gameplaySceneRef = gameplayScene
    }

    /** Forwards block content to the inner SceneBuilder so users can declare zone(), etc. */
    fun scene(block: io.github.gbkt.core.dsl.SceneBuilder.() -> Unit) {
        sceneBuilderBlock += block
    }

    internal fun materialize(gb: io.github.gbkt.core.dsl.GameBuilder): SceneRef {
        val gameplay = gameplaySceneRef
            ?: error("levelCardScene '$id' must call onStartPress(gameplayScene)")
        return gb.scene(id) {
            sceneBuilderBlock.forEach { it() }
            frame {
                whenever(buttons.start.pressed) {
                    cEmit("setup_current_level();")
                    navigate(gameplay)
                }
            }
        }
    }
}

class LevelCardSceneDelegate(private val block: LevelCardSceneBuilder.() -> Unit) :
    ReadOnlyProperty<Any?, SceneRef> {
    private var ref: SceneRef? = null

    operator fun provideDelegate(
        thisRef: Any?,
        property: KProperty<*>,
    ): ReadOnlyProperty<Any?, SceneRef> {
        val name = property.name  // "nextLevelScene" → "nextLevelScene" id (lowercase("nextlevel") matches the existing gate)
        val gb = GameBuilderContext.current
            ?: error("levelCardScene {} must be called inside a game {} block")
        val builder = LevelCardSceneBuilder(name).apply(block)
        ref = builder.materialize(gb)
        return this
    }

    override fun getValue(thisRef: Any?, property: KProperty<*>): SceneRef =
        ref ?: error("LevelCardSceneDelegate not initialized — was provideDelegate called?")
}

fun GameBuilder.levelCardScene(block: LevelCardSceneBuilder.() -> Unit): LevelCardSceneDelegate =
    LevelCardSceneDelegate(block)
```

**Critical:** the property name `nextLevelScene` lowercases to `nextlevelscene` — the
`buildMainLoopLevelSwitchGuardIfNeeded` gate checks for `lower == "nextlevel" || lower == "next_level"`,
which is exact-match. The `provideDelegate` must capture the property name and pass through
unchanged so the gate continues to fire. **Recommendation:** the helper internally normalizes
the name to `"nextLevel"` (or accepts any name that lowercases to one of the gate-accepted
forms) — or the planner widens the gate to match `lower.contains("nextlevel")`. Pick the
gate-widening path; cheaper.

### Known Threat Patterns for {stack}

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Hand-rolled escape in DSL DSL → C generated code | Tampering (T) | `cEmit("setup_current_level();")` is the only raw-C injection point; locked to a literal call with no variable interpolation |
| Buffer overflow in `_level_spawn_x[]` access | Tampering (T) / Denial of Service (D) | The switch on `(_current_level % zoneCount)` guarantees index is bounded by array length; never out-of-bounds. Existing pattern from Plan 12-17; this phase preserves the modulo |
| Symbol-collision attack via property names | Tampering (T) | `provideDelegate` captures `property.name` (Kotlin compile-time-validated identifier); no user-string concatenation. The lowercase comparison in the gate is the only weakness — A3 mitigation addresses it |
