## Accomplishments

- Added `memory.writeByte(0x0000, 0x0A)` immediately before the SRAM write loop in `load()` to open the MBC5 `ramWriteEnabled` gate (ENABLE_RAM). Without this, all SRAM writes at 0xA000-0xBFFF were silently dropped by CoffeeGB's Mbc5.setByte gate whenever the game had previously run `save_game_saves` (which ends with DISABLE_RAM).
- Added `memory.writeByte(0x0000, 0x00)` immediately after the SRAM write loop to restore the canonical DISABLE_RAM state (matches what Banks.kt's `save_game_saves` routine leaves behind).
- Updated the KDoc on `load()` to document the MBC5 ENABLE_RAM/DISABLE_RAM contract, reference REVIEW CR-01 and Phase 11.1 gap-closure plan 11.1-10, and explain why the bracket is needed.
- Existing 9/9 SavestateManagerTest tests remain GREEN — the IntArray mock accepts writes to 0x0000 without issue (disjoint from all sentinel addresses at 0xA000, 0xA800, 0xBFFF, 0xC000-0xDFFF, 0xFE00-0xFE9F, 0xFF80-0xFFFE).

## Decisions Made

- Bracket only the SRAM loop — WRAM/OAM/HRAM address ranges (0xC000-0xDFFF, 0xFE00-0xFE9F, 0xFF80-0xFFFE) are not gated by the MBC5 RAM-enable mechanism; adding unnecessary writes there would be incorrect.
- Do not touch `save()` — SRAM reads do not honour the MBC5 `ramWriteEnabled` gate per CoffeeGB's Mbc5 implementation; only writes are gated.
- Use 0x00 (not another value) for DISABLE_RAM to exactly mirror the state that Banks.kt's `save_game_saves` routine leaves behind.
