### CONTINGENCY (c) Analysis

**The checker tilemap IS rendering.** Both PNGs are 524 bytes (up from 413 blank bytes)
with a different MD5 (91d31f24) and show the checker pattern clearly when visually
inspected. The `captureAndRename` call succeeded — the PNG files were overwritten with
real content before `assertScreenshotIsNonUniform` ran.

The perceptual check finds only **2 distinct colours** because:
1. `checker.png` has exactly **2 unique tiles**: tile 0 (white background) and tile 1 (checker)
2. The Coffee-GB emulator renders DMG palette in 2 visible shades for this tileset:
   white (#FFFFFF approx) and light green (#B8D8A8 approx — Coffee-GB's "light" shade)
3. The checker tiled across 20×18 produces a 50/50 split — dominant ratio ~0.50 (PASSES the
   < 0.95 test but the `colours.size >= 4` assertion fails first)

This is the plan's **CONTINGENCY (c)**:
> "The 4-distinct-colour threshold is too strict for the actual GB DMG palette in this ROM.
> If the executor observes the captured frame uses fewer than 4 distinct colours legitimately,
> adjust the Plan-14 threshold via a small follow-up edit to the helper."

Per the parallel execution instructions: "surface honestly + propose a small Plan-14 threshold
tuning (e.g. >= 2 distinct colours). DO NOT silently retune; surface for orchestrator decision."

**Proposed tuning (for orchestrator decision):**
Change `assertScreenshotIsNonUniform` line 137 from:
```kotlin
assertTrue(colours.size >= 4, ...)
```
To:
```kotlin
assertTrue(colours.size >= 2, ...)
```
Rationale: blank = 1 colour, checker with 2 tiles = 2 colours — the distinction is clear and
unambiguous. The dominant-ratio test (< 0.95) remains as-is and provides the "not near-blank"
guard. Together: `>= 2 colours` + `dominant < 0.95` reliably distinguishes real content from
a blank or near-blank frame for the banks checker use case.
