# Phase 11.1: Code Review Report

**Reviewed:** 2026-05-20T12:00:00Z
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

Phase 11.1 ships four substantive changes under review here:

1. `SavestateManager` is extended to capture/restore SRAM (0xA000-0xBFFF) and a magic bump
   (GBST -> GBS2).
2. `SceneIR.zoneRefs` adds a scene -> zone binder list with manual `equals`/`hashCode`
   updates and a single sentinel `SceneIRTest`.
3. `SceneBuilder.zone(ZoneRef)` adds the DSL surface that lowers into `SceneIR.zoneRefs`;
   `SceneVisitor` reads the field and prepends `set_bkg_data` + `_bkg_tiles_load_banked` +
   `SHOW_BKG` to the scene-enter body.
4. `FunctionDeduplicationPass` and `COutputOptimizer` add a line-prefix comment-skip filter
   to the call-site / cross-file rewriters (SEED-015 narrow fix).

Two CRITICAL defects surfaced:

- The `SavestateManager.load()` path writes to SRAM through CoffeeGB's MBC5, which honours
  `ramWriteEnabled` for writes. After any game calls `DISABLE_RAM` (as Banks.kt's
  `save_game_saves` does at its tail), all SRAM writes are silently dropped — the SRAM
  region is never restored. The companion UAT test passes only because `writeMemory()` is
  also dropped, so pre/post values trivially match. This is a Visual-Evidence-Rule-style
  false-green in test infrastructure.
- The `COutputOptimizer` cross-file rewrite pattern is `\b<dupName>\b` (no `\s*\(`
  trailer). It does match call sites but also matches string-literal occurrences, function
  pointer assignments, and forward-declaration prototypes. The line-prefix comment-skip
  only suppresses one of the over-match classes (`//`, `/*`, `*` line starts); inline
  block comments and string literals remain vulnerable.

The remaining findings cluster around brace-walk safety (string/comment-aware tracking
missing), zone-id sanitization gaps, multi-zone-per-scene VRAM correctness, line-ending
preservation in the dedup rewriter, and several test-fragility issues (>100 byte
screenshot threshold cannot distinguish a black PNG from a real one; INV-3 reads a sidecar
file written by a different task whose ordering is asserted only by comment).

## Critical Issues

### CR-01: SavestateManager.load() silently no-ops when MBC RAM is disabled

**File:** `gbkt-emulator/src/main/kotlin/io/github/gbkt/emulator/agent/SavestateManager.kt:120-122`
**Issue:** `SavestateManager.load()` calls `memory.writeByte(addr, inp.readUnsignedByte())`
for the SRAM range (`0xA000 until 0xBFFF`). `MemoryAccess.writeByte` is wired to
`addressSpace.setByte(...)`, which on MBC5 (CoffeeGB 1.6.0) gates SRAM writes on
`ramWriteEnabled`:

```
// MBC5.setByte() decompiled (lines 144-148, hand-translated):
// if address in 40960..49151:
//   if (ramWriteEnabled) ram[getRamAddress(address)] = value;
//   // else: write silently dropped
```

Real-world flow on Banks: the `save_game_saves` function emitted by `GBDKSystemVisitor.visitSaveSystem`
wraps writes in `ENABLE_RAM; ... DISABLE_RAM;` (locked by INV-4). After that runs, the MBC
state has `ramWriteEnabled = false`. Any subsequent `SavestateManager.load()` invocation
writes `0xFF` (the open-bus byte that was saved) into the MBC5's setByte path — and the
guard drops every single write. SRAM is not restored.

This silently breaks the SRAM portion of the save/load contract advertised by the new
GBS2 file format header ("SRAM (0xA000-0xBFFF, RAM bank 0)" in the KDoc, line 26). It
also makes the round-trip test (`SavestateManagerTest.round-trip restores SRAM bytes
correctly`, line 151) green only because that test uses an `IntArray`-backed mock
`MemoryAccess` that has no MBC. On a real ROM, the round-trip is a no-op.

The companion UAT test (`BanksUatTest.anchor 4 SRAM persistence via GBST round-trip`)
passes spuriously: `writeMemory(0xA000, 99)` between save and load is itself dropped by
the MBC (RAM disabled), and the subsequent `loadState()` writes are dropped too. Both
`preBytes` and `postBytes` end up reading the same untouched SRAM contents, so
`assertContentEquals(preBytes, postBytes)` is true by accident. The test cannot detect
the underlying defect — it is a false-green sentinel.

**Fix:** Either (a) bracket the SRAM read AND write loops with explicit ENABLE_RAM/restore
in SavestateManager, peeking the current MBC enable state and restoring it after the
restore; or (b) document the invariant ("emulator MUST be in ENABLE_RAM state before
load") in the SavestateManager KDoc, document it in BanksUatTest, and add an explicit
`writeMemory(0x0000, 0x0A)` before `loadState` in the UAT test (and any production
caller). The latter is the smaller surface but is fragile — callers will forget.

Concrete fix sketch for option (a):

```kotlin
fun load(emulator: GbEmulator, file: File) {
    require(emulator.isPaused()) { ... }
    val memory = emulator.getMemory()
    // Force-enable cartridge RAM so MBC writes land in SRAM. MBC5 reads do
    // not honour this gate, but writes do (CoffeeGB 1.6.0 Mbc5.setByte
    // lines 144-148). Without this, every SRAM byte we write below is
    // silently dropped by the MBC when the previous game state left RAM
    // disabled.
    memory.writeByte(0x0000, 0x0A) // MBC5 ENABLE_RAM
    DataInputStream(file.inputStream().buffered()).use { inp ->
        // ... magic check, then read + write loops as today ...
    }
    memory.writeByte(0x0000, 0x00) // MBC5 DISABLE_RAM (restore canonical disabled state)
}
```

Note: option (a) is still not perfectly faithful — it assumes the ROM authored RAM in
"disabled" state at the end of every guarded write region. If a game intentionally
leaves RAM enabled (rare but possible), the post-load `DISABLE_RAM` toggle alters that
state. For Banks.kt the trade-off is acceptable; for a generic framework helper a peek-
and-restore is safer.

The `SavestateManagerTest.round-trip restores SRAM bytes correctly` test (line 151)
also needs hardening — the current mock bypasses MBC entirely, so it cannot catch this
defect. Add a JVM-tier emulator-backed test (or an MCP-tier on-ROM probe) that mutates
SRAM via emulator memory, calls `save_game_saves` to disable RAM, then exercises the
real SavestateManager and asserts the restored value differs from the mid-mutation
sentinel.

### CR-02: COutputOptimizer cross-file rewriter regex over-matches string literals and inline block comments

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/postprocess/COutputOptimizer.kt:100-115`
**Issue:** The cross-file call-site rewriter uses `\b<dupName>\b` (line 100) — without the
trailing `\s*\(` that `FunctionDeduplicationPass` uses (line 130). The pattern matches
the function name in any position, not just at a call site. The skip-comments filter
(lines 103-107) drops only lines whose **trimmed start** begins with `//`, `/*`, or `*`.
The following over-match classes remain unprotected:

1. **String literals containing the function name.** A `PrintAt`/`PrintCentered` op whose
   text happens to mention the deduped function name would have that literal mutated in
   place inside the C source. `\b\w+\b` has no semantic awareness of `"..."` quoting.
   Probability is low in production output but the rewriter has no guard.
2. **Inline block comments.** A line like `int x = 5; /* dpad_held(x) note */ stuff;`
   does not start with `//`, `/*`, or `*` after trim, so the filter does not skip it.
   The regex rewrites the comment text in place.
3. **Block comments spanning multiple lines whose middle lines do not start with `*`.**
   A 3-line `/* ... \n   continuation \n   */` block's middle line is not filtered.
4. **Forward-declaration prototypes in `game.h`.** A dup's prototype is rewritten to the
   canonical name, producing a duplicate prototype line. C tolerates duplicate prototypes
   so this is not a compile error, but it inflates `game.h` and produces noise.

The pattern shape mismatch between FunctionDeduplicationPass (`\b<name>\s*\(`) and
COutputOptimizer (`\b<name>\b`) is itself a quiet maintenance defect — the two
rewriters have diverged on a semantic that should be identical.

**Fix:** Align the cross-file rewriter with the per-file call-site pattern. Use
`\b<dupName>\s*\(` and let the rewriter replace only the leading identifier. Concrete:

```kotlin
val pattern = Regex("""\b${Regex.escape(dupName)}\s*\(""")
// inside the line-by-line block:
pattern.replace(line) { m -> m.value.replace(dupName, canonicalName) }
```

This bounds the rewrite to actual call sites and removes the prototype / string /
inline-comment over-match without expanding the comment-skip surface.

A more comprehensive fix would tokenise the C content (string-aware, comment-aware) and
rewrite only over identifier tokens. That is more code than the SEED-015 narrow fix
warranted; the call-site-shape regex is the minimum sufficient guard.

## Warnings

### WR-01: FunctionDeduplicationPass.extractFunctions brace-walk is not string/comment aware

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/postprocess/FunctionDeduplicationPass.kt:182-198`
**Issue:** The brace-depth tracker at lines 182-198 increments/decrements depth on raw
`{` and `}` characters with no awareness of:
- string literals (`"{"`),
- character literals (`'{'`),
- single-line comments (`// {`),
- block comments (`/* { */`).

If any of these appear inside a generated function body, depth desyncs and the recorded
`declarationEnd` is wrong. The subsequent in-place substring replacement at line 124
(`result.substring(0, rep.start) + rep.replacement + result.substring(rep.end)`)
substitutes a truncated or expanded range of source — silently corrupting the C file.
In current GBDK-generated code, brace characters inside string literals are rare but
not impossible (printf format strings, `PrintAt` text emissions, raw-code shells). The
absence of any defense makes this a latent regression surface as new visitors emit
content.

**Fix:** Either (a) tokenise the C content with a tiny lexer that recognises string and
comment regions and skips them when adjusting depth, or (b) add a defence-in-depth
sanity check: after walking, re-extract the candidate body and verify the function name
appears in the signature line. The cheaper guard is (b); the structurally correct
solution is (a) and aligns with the eventual move to AST-level dedup mentioned in the
`postprocess/CLAUDE.md` design note.

### WR-02: FunctionDeduplicationPass.FUNC_DEF_PATTERN does not match function pointer parameter lists

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/postprocess/FunctionDeduplicationPass.kt:60-64`
**Issue:** The signature pattern uses `\([^)]*\)` which matches an opening paren followed
by any non-`)` content, then a closing paren. This breaks on function definitions whose
parameter list contains a nested parenthesis — most commonly **function pointer
parameters** like `void register_callback(void (*cb)(UINT8 arg))`. The regex stops
matching at the first inner `)`. The function is then skipped (no `FunctionEntry`
recorded), silently losing the dedup opportunity. Worse, the second `find()` iteration
resumes from `match.range.last + 1`, which can re-anchor on the inner paren and produce
garbage matches in pathological cases.

The same regex pattern is duplicated in `COutputOptimizer` (line 100 of postprocess
helpers); same caveat.

GBDK-generated code does not currently emit function-pointer parameters, but a future
visitor (e.g. a callback-style menu API) could. **Defensive fix:** allow balanced
parens. The simplest Kotlin regex form is to require an opening paren and let the
brace-walk extension handle the body — keep the param list out of the regex entirely:

```kotlin
private val FUNC_DEF_PATTERN =
    Regex(
        """^((?:const\s+)?[\w*]+(?:\s+[\w*]+)*\s+(\w+))\s*\(""",
        setOf(RegexOption.MULTILINE),
    )
```

…then walk paren depth to find the matching `)`, the same way the function body's
braces are walked. (Note: this also fixes WR-01 once string/comment awareness is added.)

### WR-03: FunctionDeduplicationPass body normalization replaces function name as substring (not identifier-aware)

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/postprocess/FunctionDeduplicationPass.kt:228-233`
**Issue:** `buildDeduplicationKey` normalizes the body via plain
`func.body.replace(func.name, "__FUNC__")`. `String.replace(needle, replacement)`
replaces all substring occurrences — it has no word-boundary awareness. If a function
is named `do_x` and its body contains the identifier `do_x_helper`, the substring `do_x`
in `do_x_helper` gets normalised to `__FUNC___helper`. Two functions whose bodies
differ only in which longer identifier they contain (`do_x_helper` vs `do_x_other`)
would now BOTH normalise to `__FUNC___helper`/`__FUNC___other` differently — that
specific case is fine. But the inverse — functions named with prefix overlap
(`do_x` vs `do_x_helper`) — produces aliased normalised keys that can collide with
unrelated functions' bodies and produce false-positive dedup. The risk surface is
small in current GBDK output but grows with visitor diversity.

**Fix:** Use a word-bounded regex replacement:

```kotlin
val funcNameBoundary = Regex("""\b${Regex.escape(func.name)}\b""")
val normalizedBody = func.body
    .let { funcNameBoundary.replace(it, "__FUNC__") }
    .replace(Regex("\\s+"), " ")
    .trim()
```

### WR-04: COutputOptimizer / FunctionDeduplicationPass normalise line endings (CRLF -> LF)

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/postprocess/FunctionDeduplicationPass.kt:140`
**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/postprocess/COutputOptimizer.kt:101`
**Issue:** Both passes use `result.lines().joinToString("\n")` in the comment-skip
filter. `String.lines()` splits on `\r\n`, `\r`, or `\n`, but `joinToString("\n")`
always rejoins with bare `\n`. If `CEmitter.emit()` ever produces CRLF output (e.g.
on Windows, with a future generator change, or with a user's custom emitter), the
post-process step silently downgrades all line endings to LF.

This is benign for SDCC/lcc on Unix, but on Windows toolchains the source maps emitted
by `SourceMapCollector` carry C line numbers — if the dedup post-process changes line
counts (because the joined output is shorter than the multi-line input by a single
`\r`), the source map is wrong by one byte per line.

**Fix:** Preserve the input line separator. Detect it before split and rejoin with the
same separator, or skip the split/join when no rewrite occurs on the line:

```kotlin
val sep = if (cContent.contains("\r\n")) "\r\n" else "\n"
result = result.split(sep).joinToString(sep) { line -> ... }
```

### WR-05: SceneVisitor multi-zone-per-scene emission produces broken VRAM state

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/visitor/SceneVisitor.kt:151-202`
**Issue:** The zone-load block iterates `scene.zoneRefs.flatMap { zoneId -> ... }`. For
each zone, it emits the triple `set_bkg_data(0u, count_N, tileset_N); _bkg_tiles_load_banked(bank_N, 0, 0, w_N, h_N, _zone_N_tiles); SHOW_BKG;`.

If a scene binds **two zones**, the second zone's `set_bkg_data(0u, ...)` overwrites the
first zone's VRAM tile data at offset 0 — but the first zone's tile-map (already written
by `_bkg_tiles_load_banked`) now indexes into the second zone's tile data. The first
zone is visually corrupted. Additionally, both `_bkg_tiles_load_banked` calls use
hardcoded `(0u, 0u)` origin, so the second zone's map overwrites the first zone's map in
the same BG region.

`SceneBuilder.zone(ZoneRef)` does guard against multi-zone-per-scene at the DSL surface
(line 151 `require(zoneRefs.isEmpty()) { "scene '$id' already binds a zone; ..."}`), but
**`SceneIR.zoneRefs` is `List<String>`** — anyone constructing an IR directly
(test fixtures, JSON deserialisation via `GameIRSerializer`, future genre visitors that
synthesize SceneIR) can bypass the DSL guard and reach the visitor with multiple zone
refs. The visitor then emits structurally broken codegen with no warning.

**Fix:** Add a defensive `check(scene.zoneRefs.size <= 1) { ... }` inside
`SceneVisitor.visit` (or downgrade `SceneIR.zoneRefs` to a nullable `String?` until
Phase 13 lifts the single-zone limit). The latter aligns the IR shape with the DSL
contract; the former is the smaller diff.

### WR-06: Zone-ID sanitization is incomplete in SceneVisitor and GBDKPipelineV2

**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/visitor/SceneVisitor.kt:162`
**File:** `gbkt-backend-gbdk/src/main/kotlin/io/github/gbkt/backend/gbdk/codegen/pipeline/GBDKPipelineV2.kt:299, 682, 720, 743, 1485`
**Issue:** Every call site applies `zoneId.replace('-', '_').replace(' ', '_')` to derive
a C identifier from the zone ID. This handles `-` and ` ` but **does not handle**:
- `.` (dot — e.g. `zone.v2` becomes `zone.v2_tiles`, invalid C),
- `/`, `\` (path separators),
- digits leading (a zone named `1st-floor` becomes `1st_floor_tiles`, leading digit makes
  the C identifier invalid),
- non-ASCII characters,
- the empty string.

The sanitization is also duplicated across at least 5 call sites with no central helper —
adding a new sanitization rule requires touching every site.

**Fix:** Extract a `sanitizeZoneId(rawId: String): String` helper (placed in the
emitter/codegen utility module) that escapes all non-`[a-zA-Z0-9_]` characters and
prefixes leading digits with `_`. Replace every duplicate inline expression with the
helper call. The current narrow set of zone IDs in example games does not exercise this
defect, but a user-authored game with a zone ID like `floor.1` will get a linker
error or, worse, silent identifier clash.

### WR-07: BanksUatTest screenshot length thresholds are too lax to satisfy the Visual Evidence Rule

**File:** `gbkt-examples/banks/src/test/kotlin/io/github/gbkt/examples/banks/BanksUatTest.kt:137-139, 256-260`
**Issue:** Anchor 1 asserts `screenshotPath.length() > 100` and anchor 2 asserts
`screenshotPath.length() > 200`. Both checks only verify that a PNG exists with a
non-trivially-small byte count. A solid-black PNG of 160x144 pixels compresses well
below typical real-content PNGs but still easily exceeds these thresholds (a 160x144
all-zero PNG is roughly ~150-300 bytes depending on encoder).

Phase 11.1's own tracking commit `ef888d80` confirms this: "anchor 1+2 reshoot attempt
— tests PASS, PNGs still blank (set_bkg_data missing)". The test passed while the
binding visual evidence was blank. This is the exact failure mode CLAUDE.md's "Visual
Evidence Rule" (lines 84-119) was added to prevent — variable assertions backed by
weak file-size sentinels rather than perceptual checks.

**Fix:** Either (a) compare against a golden screenshot via `VisualDiff.compare()` (the
existing helper in `AgentDebugSession`) with a tight tolerance, or (b) decode the PNG
and assert that at least N% of pixels differ from a uniform colour (e.g. SSIM, average
non-background pixel count, palette histogram). Option (a) is the cheapest to bolt on
because the helper exists; the golden PNG must itself be regenerated whenever the
checker tileset changes.

### IN-01: SavestateManagerTest `load throws on invalid magic bytes` uses pre-fix file size (8483 bytes)

**File:** `gbkt-emulator/src/test/kotlin/io/github/gbkt/emulator/agent/SavestateManagerTest.kt:189-193`
**Issue:** The fixture writes `ByteArray(8483)` — the pre-fix savestate file size. After
the Phase 11.1 size bump (4 + 8192 + 8192 + 160 + 127 = 16675 bytes), this fixture is
no longer representative of a realistic-shaped invalid file. The test still passes
because the magic check fires before the read loops, but a future reader will assume
the constant 8483 matches the file format. It does not.

**Fix:** Either use a small fixture sized to just fail the magic check (e.g.
`ByteArray(4) { 0 }`), or use the new total size (`16675`) to mirror a structurally
correct but magically wrong file.

### IN-02: BanksEmissionTest `INV-3` depends on Gradle task ordering via comment, not via test wiring

**File:** `gbkt-examples/banks/src/test/kotlin/io/github/gbkt/examples/banks/BanksEmissionTest.kt:204-253`
**Issue:** The test reads `build/gbkt/generated/gbkt-build.properties` from disk and
asserts via `check(propsFile.exists())` with a comment that "the Gradle test task depends
on `generateC`, so the file exists before this test runs". The dependency is implicit —
there is no explicit `dependsOn(":gbkt-examples:banks:generateC")` declaration in this
file, nor a `@Test`-level assumption that the task ran. A reordered Gradle wiring (or
running this test class via JUnit directly outside Gradle) will surface a misleading
`check(...)` failure that points the user at "ensure `:gbkt-examples:banks:test` ran
`:generateC` first" without a way to enforce it.

**Fix:** Either materialise the properties file from the in-memory pipeline output in
the test itself (move the writer logic from `GenerateCTask.writeBuildMetadata` into a
shared helper), or invoke the property emission directly so the test is self-contained.
The current path conflates "test" and "post-task integration check".
