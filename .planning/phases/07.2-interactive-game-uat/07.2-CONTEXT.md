# Phase 07.2: Interactive Game UAT - Context

**Gathered:** 2026-03-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Interactively play-test all 9 example games (+ platformer-gbc GBC variant) using Claude-driven MCP emulator tools from Phases 07.1/07.1.1. Claude plays via MCP, user confirms visual correctness at checkpoints. Verify gameplay correctness, find and fix bugs inline, capture golden screenshots, produce per-game sign-off reports.

**Scope includes:**
- Claude-driven MCP play-testing of all 10 game targets
- Per-game structured sign-off reports (UAT-{game}.md)
- Golden screenshots (3-5 per game) for regression baselines + documentation
- Inline bug fixing with regression tests and atomic commits
- Automated test suite validation after each framework fix

**Scope excludes:**
- LotD play-testing (remains deferred)
- Real hardware testing
- New game content or mechanics
- Automated screenshot diff test infrastructure (golden shots captured, diff tooling is future work)

</domain>

<decisions>
## Implementation Decisions

### Session Workflow
- **Claude drives via MCP**: Claude uses emulator_start/emulator_press/emulator_assert/emulator_save_state to play-test. User watches and confirms visual correctness at checkpoints
- **One game per conversation**: Fresh context per game with /clear between. Keeps sessions focused, avoids context bloat from MCP output
- **Simple → complex ordering**: Pong → Breakout → Racer → Shmup → Platformer → Platformer-GBC → Explorer → Dungeon → RPG-Lite. Framework bugs surface early in simple games
- **Checkpoint after each game area**: Claude plays through a section (title, gameplay, game over), reports findings + screenshots. User confirms or flags issues before Claude moves to next section

### Bug Handling
- **Fix immediately**: Same as Phase 07 policy. Stop play-testing, fix the bug, add regression test, atomic commit, then resume
- **Fix autonomously, report after**: Claude diagnoses, fixes, tests, and commits. Reports the fix with before/after evidence. User reviews the commit
- **Generic framework fixes only**: No game-specific workarounds (carried forward from Phase 07)
- **Run automated tests for all games after framework fix**: `./gradlew test` after each fix to catch regressions. Only re-play-test if automated tests fail

### Coverage Depth
- **Playbook-driven**: Claude follows each game's PLAYBOOK.md as the testing guide. Every section in the playbook is exercised via MCP tools
- **Acceptance = playbook sections pass**: Every playbook section exercised, all assertions pass, user confirms visual correctness at checkpoints, no known bugs remaining
- **Per-game sign-off report**: Structured pass/fail UAT-{game}.md with evidence (variable states, assertion results)
- **Reports in phase directory**: `.planning/phases/07.2-interactive-game-uat/UAT-{game}.md`

### Golden Screenshots
- **Dual purpose**: Regression baselines AND documentation/showcase
- **3-5 key moments per game**: Title screen, main gameplay, game over/win, plus 1-2 game-specific highlights (battle screen, dungeon exploration, etc.)
- **Per-game test resources**: `gbkt-examples/{game}/src/test/resources/golden/` — co-located with tests, git-tracked
- **Curated**: Must look good (documentation) while being deterministic enough for future diffing (regression)

### Scope
- **All 10 targets**: Pong, Breakout, Racer, Shmup, Platformer, Platformer-GBC, Explorer, Dungeon, RPG-Lite (9 games + 1 GBC variant)
- **10 sessions**: One conversation per game
- **Phase exit criteria**: All 10 games have (1) UAT sign-off report, (2) 3-5 golden screenshots in test resources, (3) all automated tests passing, (4) user explicit sign-off at each checkpoint

### Claude's Discretion
- Exact MCP tool sequences for each game section
- Which playbook sections map to which MCP assertion patterns
- Screenshot timing (which exact frame to capture for golden shots)
- Sign-off report structure and level of detail
- How to name golden screenshot files

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **17 MCP tools** (emulator_start, emulator_step, emulator_press, emulator_assert, emulator_save_state, emulator_load_state, emulator_get_playbook, emulator_list_games, etc.) — full agent debugging suite ready
- **PLAYBOOK.md** for all 9 games — natural-language test guides
- **GbktTestExtension** — JUnit5 extension with convention-based ROM discovery, fluent assertions
- **GameConstants** per game — type-safe scene/variable/actor references (no magic strings)
- **StepAgent** — full emulator control (step, press, readVariable, writeVariable, captureScreenshot, save/load state)
- **VramTextVerifier** — text detection with TileDecoder support for custom tilesets
- **VariableInspector** — type-aware variable reading (8-bit and 16-bit, signed/unsigned)

### Established Patterns
- MCP play-through pattern established in `PongMcpPlaythroughTest.kt` — start, press buttons, assert state
- Screenshot capture via `emulator_screenshot` MCP tool — returns base64 PNG
- Save/load state for checkpoint-based testing
- Batch assertions via `emulator_assert` with multiple check types

### Integration Points
- Golden screenshots saved to `gbkt-examples/{game}/src/test/resources/golden/`
- UAT reports saved to `.planning/phases/07.2-interactive-game-uat/UAT-{game}.md`
- Bug fixes go through standard `./gradlew test` validation
- Each game session uses `/gbkt-play-game {game}` skill or direct MCP tool calls

</code_context>

<specifics>
## Specific Ideas

- Claude drives the emulator via MCP tools — this is a showcase of the agent debugging DX built in 07.1/07.1.1
- Golden screenshots should be curated to look good enough for a project README while being deterministic for future regression diffing
- Sign-off reports provide an audit trail — "we tested this, here's the evidence, here's what passed"
- Simple → complex ordering means Pong catches basic framework issues before we hit the complexity of Dungeon/RPG-Lite

</specifics>
