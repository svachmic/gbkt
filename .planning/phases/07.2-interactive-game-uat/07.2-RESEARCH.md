## Summary

Phase 07.2 is an operational UAT phase, not a code-construction phase. The primary work is executing 10 structured play-test sessions (one per game), each using the MCP emulator tools built in Phases 07.1 and 07.1.1. Claude drives the emulator via 16 MCP tools; the user provides visual confirmation at checkpoints.

All infrastructure is fully ready: ROMs are built for all 10 targets, PLAYBOOKs exist for all 9 games (+ platformer-gbc variant), the MCP server JAR is configured in `.claude/mcp_servers.json`, and both `/gbkt-play-game` and `/gbkt-test-game` skills are installed. The golden screenshot directories do not yet exist and must be created during each session.

The primary deliverable per session is a UAT sign-off report (`UAT-{game}.md`) in the phase directory, 3-5 golden screenshots in `gbkt-examples/{game}/src/test/resources/golden/`, and all automated tests passing. Bugs found during play-testing are fixed inline with regression tests and atomic commits.

**Primary recommendation:** Structure each session as a linear playbook walk with save-state checkpoints at scene boundaries. Use `emulator_assert` batch checks at each checkpoint to minimize round-trips. Capture golden screenshots at title, first-gameplay-frame, and terminal-state (win/gameover). Follow the session template documented in the Architecture Patterns section.

## Architecture Patterns

### Session Template (per game)

Each of the 10 sessions follows this structure:

```
1. /clear (fresh context)
2. emulator_start(game = "<name>")
3. emulator_get_playbook()
4. emulator_describe_game()
5. Walk each playbook section:
   a. Navigate to section start state
   b. emulator_save_state(label = "<section>-entry")
   c. Perform actions (emulator_press / emulator_step)
   d. emulator_assert with batch checks
   e. emulator_screenshot(label = "<game>-<moment>")
   f. Report findings to user → user confirms
6. Write UAT-{game}.md report
7. Move golden screenshots to gbkt-examples/{game}/src/test/resources/golden/
```

### Pattern 1: Scene Navigation with Wait-Gate

```json
// Source: context/UAT_GUIDE.md, gbkt-play-game.md skill
// Title → gameplay transition
{"tool": "emulator_press", "arguments": {"button": "start"}}
{"tool": "emulator_wait_for_scene", "arguments": {"scene": "gameplay", "maxFrames": 120}}
{"tool": "emulator_assert", "arguments": {
  "checks": [
    {"type": "scene_is", "scene": "gameplay"},
    {"type": "variable_equals", "name": "score", "expected": 0}
  ]
}}
```

### Pattern 2: Golden Screenshot Capture

Screenshots from `emulator_screenshot` land in `build/gbkt/screenshots/`. The planner must include a step to manually copy/move curated shots to `gbkt-examples/{game}/src/test/resources/golden/` after the session.

```
emulator_screenshot(label = "pong-title")
  → build/gbkt/screenshots/pong-title-frame-NNN.png

Copy to:
  gbkt-examples/pong/src/test/resources/golden/pong-title.png
```

**Naming convention (Claude's discretion):** `{game}-{moment}.png`
Examples: `pong-title.png`, `pong-gameplay.png`, `pong-gameover.png`

The `golden/` subdirectory must be created during the session (`mkdir -p`). It does not pre-exist for any game.

### Pattern 3: Checkpoint Assertion (Batch)

```json
// Source: context/UAT_GUIDE.md
// Minimize round-trips by batching multiple checks
{"tool": "emulator_assert", "arguments": {
  "checks": [
    {"type": "scene_is", "scene": "game"},
    {"type": "variable_equals", "name": "p1Score", "expected": 0},
    {"type": "variable_equals", "name": "p2Score", "expected": 0},
    {"type": "actor_visible", "name": "ball"},
    {"type": "sprite_count", "expected": 5}
  ]
}}
```

### Pattern 4: savestate-Based Bug Bisection

```json
// Source: context/UAT_GUIDE.md walkthrough 3
emulator_save_state(label = "pre-encounter")
// ... advance game state ...
// Bug found → restore
emulator_load_state(label = "pre-encounter")
// Retry with different assertion
```

### Pattern 5: emulator_press vs emulator_step

Use `emulator_press` for single button taps (standard input). Use `emulator_step` with `buttons` array for multi-button simultaneous presses or for holding a button for bulk movement.

```json
// Single press (edge-triggered, START/A/B buttons)
{"tool": "emulator_press", "arguments": {"button": "start"}}

// Hold direction for movement (N held + 1 release = N+1 total frames)
{"tool": "emulator_press", "arguments": {"button": "right", "frames": 30}}

// Simultaneous buttons (use emulator_step)
{"tool": "emulator_step", "arguments": {"frames": 1, "buttons": ["left", "b"]}}
```

### Pattern 6: Text Assertions and scrollAware

```json
// WIN layer UI text (score, HUD, dialogs) — default, no scrollAware needed
{"type": "text_on_screen", "text": "PRESS START"}

// BG layer text in scrolling games (platformer, explorer, dungeon)
{"type": "text_on_screen", "text": "LEVEL 1", "scrollAware": true}
```

### Anti-Patterns to Avoid

- **Testing without reading the playbook first:** The playbook contains critical quirks (e.g., Dungeon's 120-step encounter threshold). Always call `emulator_get_playbook` and read Known Quirks before testing.
- **Eyeballing instead of asserting:** All claims about game state must go through `emulator_assert`. Observations can be misleading.
- **Forgetting to create `golden/` directory:** The directory does not pre-exist. All 10 games need `mkdir -p gbkt-examples/{game}/src/test/resources/golden/` before saving screenshots.
- **Context bloat from multiple games per session:** The CONTEXT.md decision is firm: one game per conversation with `/clear` between.
- **Game-specific workarounds in bug fixes:** If a game-specific behavior must change to fix a bug, fix the framework instead. Per Phase 07 policy.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Screenshot saving | Manual file copy via Bash | `emulator_screenshot(label)` | MCP tool handles path, frame number, PNG format |
| Variable inspection | Parse WRAM manually | `emulator_read_variable` or `variables` in Observation | Type-correct (INT8 returns -1, not 255) |
| Scene waiting | Busy-loop step calls | `emulator_wait_for_scene(maxFrames)` | Handles timeout, returns `{met, framesElapsed}` |
| Text checking | Read bgText/winText manually | `text_on_screen` assert | Handles both layers + scrollAware |
| State restoration | Replay the entire game | `emulator_save_state` / `emulator_load_state` | Binary state dump, frame-perfect |
| Batch checks | Multiple sequential assert calls | `emulator_assert` with `checks` array | Fewer round-trips, single result object |

**Key insight:** All 16 MCP tools were built specifically to make UAT sessions efficient. Every manual workaround trades tool reliability for complexity.

### Pong (Session 1 — simplest)

**Pre-existing UAT test:** `PongUatTest.kt` covers 20 scenarios using `UatRunner`. Use this as the reference for what the MCP session should verify.

**Key variables:** `p1Score`, `p2Score` (UINT8), `ballDx`, `ballDy` (INT8)
**Scene order:** `title` → `game` → `gameover` → `title`
**Sprite count in gameplay:** 5 (paddle1=2, paddle2=2, ball=1)
**Golden shots:** title ("PONG"), gameplay (ball in motion), gameover ("GAME OVER")

**Known quirks to test:**
- Ball clipping at screen edge at high speeds (per playbook)
- AI paddle center-tracking (`paddle2.y + 8` vs `ball.y`)
- Score displayed via `print("P1:%d    P2:%d")` — note the spaces in the format string matter for text assertion

### Breakout (Session 2)

**Key variables:** `score`, `lives`, `bricksLeft` (UINT8), `ballDx`, `ballDy` (INT8)
**Scene order:** `title` → `game` → `gameover` / `win` → `title`
**Unique behavior:** Both `gameover` (lives=0) and `win` (bricksLeft=0) terminal scenes exist
**Golden shots:** title, gameplay (bricks visible), either win or gameover screen

**Known quirks to test:**
- Brick display uses `#` character on BG layer (text assertion may fail — this is BG-layer text, not WIN-layer)
- HUD uses BOTH `gotoxy/print` on BG layer AND `hud()` DSL on WIN layer — dual rendering
- Brick collision is tile-based: `col = (ball.x - 40) >> 3`

### Racer (Session 3 — first GBC game)

**Key variables:** `lap` (UINT8), `raceTime` (UINT8), `position` (UINT8)
**Scene order:** `title` → `race` → `results` → `title`
**Target:** `GBC_COMPATIBLE` — runs in GBC color mode
**Golden shots:** title, race (car on track), results (3 laps complete)

**Known quirks to test:**
- `raceTime` is raw frame count (NOT seconds)
- `position` starts at 1 and is NOT dynamically updated by AI in this example
- Lap detection zone: `car.x < 50 AND car.y in [95, 115)`

### Shmup (Session 4)

**Key variables:** `score`, `lives`, `scrollY`, `shootCooldown`, `waveTimer` (all UINT8)
**Scene order:** `title` → `gameplay` → `gameover` → `title`
**Unique behavior:** Entity pools (`bulletPool` max 8, `enemyPool` max 4) — no win condition
**Golden shots:** title, gameplay with active bullets and enemies, gameover

**Known quirks to test:**
- `destroyAll()` on gameplay enter prevents stale pools from previous run
- Fire cooldown: `shootCooldown` counts down from 8, must be 0 to fire
- Enemy wave timer: spawns every 60 frames

### Platformer (Session 5)

**Key variables:** `lives` (UINT8)
**Scene order:** `title` → `gameplay` → `win` / `title`
**Unique behavior:** Physics-based movement (gravity, coyote time, jump buffer)
**Golden shots:** title, mid-jump gameplay, win screen

**Known quirks to test:**
- Goal zone is a coordinate check, NOT a named collision zone actor
- `lives` resets to 3 on every gameplay enter (fresh start each run)
- Camera scrolls horizontally — `scrollAware: true` needed for BG text

### Platformer-GBC (Session 6)

**Nearly identical to Platformer.** Only differences:
- Config: `GBC_COMPATIBLE` target
- Title text: "PLATFORMER GBC" (not "PLATFORMER")
**Golden shots:** Must visually confirm GBC color mode active (platform colors differ from DMG grey)

### Explorer (Session 7 — first RPG-genre game)

**Key variables:** `hp`, `stepCount`, `keys`, `torchLevel`, `level` (all UINT8)
**Scene order:** `title` → `gameplay` → `pause` / `combat_scene` / `gameover`
**Unique behavior:** Two zones (floor1, floor2), HUD (HP bar, torch, keys), save/load, flags
**Golden shots:** title, gameplay with HUD visible, combat_scene, pause menu, gameover

**Known quirks to test:**
- Encounter every 120 steps (not 60 like RPG-Lite)
- Torch warning at 50 → gameover (warning IS the gameover trigger)
- Pause menu items: "Resume" and "Quit to Title"
- Zone transition: east edge of floor1 → floor2

### Dungeon (Session 8 — torch crawler)

**Key variables:** `torchLevel`, `keys`, `steps` (all UINT8)
**Scene order:** `title` → `gameplay` → `battle` → `gameplay` / `gameover`
**Unique behavior:** Grid-based movement (8px per step, vs Explorer's 2px smooth)
**Golden shots:** title, gameplay (dungeon tiles), battle scene, gameover

**Known quirks to test:**
- Torch-low threshold (50) is FATAL — triggers `navigate(gameoverRef)` immediately
- Torch starts at 255 (not 100 like Explorer)
- Grid movement — need to hold direction for enough frames for one step

### RPG-Lite (Session 9 — full RPG flow)

**Key variables:** `hp`, `gold`, `dungeonLevel`, `stepCount` (all UINT8)
**Scene order:** `title` → `town` → `dungeon` → `combat` / `gameover`
**Unique behavior:** Town → Dungeon → Town loop, heal mechanic, `fireball` ability declared but unused
**Golden shots:** title, town (press A to enter dungeon), dungeon gameplay, combat/battle, gameover

**Known quirks to test:**
- Town heal requires `gold >= 5 AND hp < 30`
- Encounter at `stepCount >= 60` (faster than Explorer's 120)
- Dungeon exit at `x >= 152` increments `dungeonLevel` and resets position

## Common Pitfalls

### Pitfall 1: Text Layer Confusion

**What goes wrong:** `text_on_screen` assertion fails for text that IS visually on screen.
**Why it happens:** Some games use both BG layer (gotoxy/print) and WIN layer (hud/dialog). The assertion searches both, but scrolling games need `scrollAware: true` for BG layer.
**How to avoid:** Check `bgText` and `winText` fields in `emulator_observe` response to understand which layer the text is on. Add `scrollAware: true` for platformer, explorer, dungeon, racer.
**Warning signs:** Text assertion fails but visual screenshot shows the text clearly.

### Pitfall 2: Variable Type Misreading

**What goes wrong:** A direction variable like `ballDx` returns a large positive number (e.g., 255).
**Why it happens:** If the metadata file was not loaded (ROM started without metadata), INT8 variables return unsigned byte values.
**How to avoid:** Always start with `game` name parameter (not `romFile`) — convention-based discovery auto-loads metadata. Verify `emulator_describe_game()` returns variable types.
**Warning signs:** `ballDx` showing 255 instead of -1; any "velocity" variable showing > 127.

### Pitfall 3: Scene Transition Timeout

**What goes wrong:** `emulator_wait_for_scene` returns `{met: false}` when it should succeed.
**Why it happens:** The game has preconditions before a transition (e.g., Dungeon needs `stepCount >= 120` before battle triggers; RPG-Lite needs `stepCount >= 60`). Or the wrong button was pressed.
**How to avoid:** Read the playbook's Known Quirks. Use `emulator_write_variable` to set precondition variables before testing transitions (e.g., set `stepCount` to 119 then walk one step).
**Warning signs:** `emulator_assert(scene_is: "battle")` fails after pressing the expected button.

### Pitfall 4: Golden Directory Does Not Exist

**What goes wrong:** Screenshot save fails or `mv`/`cp` command fails.
**Why it happens:** `gbkt-examples/{game}/src/test/resources/golden/` does not pre-exist for any game.
**How to avoid:** Create the directory before the session: `mkdir -p gbkt-examples/{game}/src/test/resources/golden/`
**Warning signs:** Shell commands fail with "no such file or directory".

### Pitfall 5: Context Bloat

**What goes wrong:** Late in a session (after ~5 games), MCP responses become unreliable or context fills up.
**Why it happens:** MCP tool responses (especially `emulator_describe_game` and `emulator_step` with many sprites) can be verbose.
**How to avoid:** Strictly one game per conversation. Use `/clear` between games.

### Pitfall 6: Emulator Left Running

**What goes wrong:** Next session fails to start because `emulator_stop` was not called.
**Why it happens:** Session ended mid-flow (crash, `/clear` without stop).
**How to avoid:** Each session plan must end with `emulator_stop`. The MCP server is single-session; starting a new game auto-replaces the previous session, but explicit stop is cleaner.
