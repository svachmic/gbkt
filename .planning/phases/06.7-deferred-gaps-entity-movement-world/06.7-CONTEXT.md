<decisions>
## Implementation Decisions

### Entity Pooling DSL

- **Separate pool block** — pools declared separately from actors: `val bulletPool by pool(bullet, max = 8)`. Decouples entity definition from pooling concerns.
- **Pool overflow is developer-configurable** — both "silent no-op" and "oldest recycled" strategies available. Developer picks per pool.
- **Homogeneous pools** — one entity type per pool. Fire bullets and ice bullets need separate pools. Maps cleanly to GBDK sprite allocation.
- **Destroy with optional death callback** — `destroy(entity)` is immediate by default; `destroy(entity) { playAnim("explode"); wait(8) }` runs a death sequence before pool return.
- **`forEachActive` iteration** — `bulletPool.forEachActive { bullet -> ... }` generates a for-loop over active entities. Body must remain declarative (use `whenever` conditions, not imperative mutation).
- **`activeCount` as Expr** — `whenever(brickPool.activeCount isEqualTo 0) { navigate(winScene) }` — runtime counter usable in DSL conditions.
- **Bulk operations** — `destroyAll()` and all standard pool patterns. Scene cleanup, game-over clearing, etc.
- **Per-instance properties** — pool entities support custom properties via `u8Prop()` / `i8Prop()` inside the actor block. Stored as parallel arrays in codegen. E.g., each brick has its own `hp` and `color`.

### NPC-NPC Collision

- **Per-actor opt-in flag** — `collidesWithNpcs(true)` for simple cases.
- **Type-safe collision groups** — `val projectiles by collisionGroup()` for fine-grained pair control. No magic strings.
- **`collisionRule()` with built-in responses** — `CollisionResponse.BLOCK`, `CollisionResponse.BOUNCE`, `CollisionResponse.OVERLAP`, `CollisionResponse.PUSH` plus custom `onCollide { }` callback.
- **PUSH response with mass** — entities declare `mass(N)`. On PUSH collision, heavier entities displace lighter ones more. Enables crate-pushing, NPC bumping.
- **Configurable check interval** — `collisionRule(a, b, interval = 2)` checks every N frames. Saves CPU on Game Boy.
- **Type-safe group references** — collision groups are val declarations, consistent with the no-magic-strings principle.

### SMOOTH Movement

- **Acceleration + friction model** — `speed(16)`, `acceleration(4)`, `friction(2)`. D-pad applies acceleration, release = decelerate via friction. Momentum feel.
- **Diagonal normalization is developer's choice** — both normalized (same speed diagonally) and raw (faster diagonal) available. Developer picks knowing the trade-offs (CPU cost vs correctness).

### PHYSICS Movement

- **Both platformer and top-down** — `PhysicsConfig` selects between platformer mode (gravity axis) and top-down mode (friction-based). Not limited to one genre.
- **Variable-height jump** — hold button = higher jump, release early = cut velocity. The Mario/Celeste feel. `variableJump(true)`, `jumpCutMultiplier(2)`.
- **Coyote time** — configurable grace frames after walking off a ledge: `coyoteFrames(4)`.
- **Wall response** — configurable via `WallResponse.SLIDE` (preserve vertical velocity, slide along walls) or `WallResponse.STOP` (zero velocity on contact).
- **Wall-jump** — opt-in extension of wall slide. `wallJump(true)`, `wallJumpVelocityX(24)`, `wallJumpVelocityY(28)`. Press jump while sliding on a wall to kick off in the opposite direction.
- **Per-actor physics config** — each actor can have its own `PhysicsConfig` (gravity, jump velocity, etc.). Player floaty, enemies heavy.

### Fixed-Point System

- **Developer-selectable format** — default to 4.4 (fits UINT8, 16 sub-pixels/pixel), opt-in to 8.8 (UINT16, 256 sub-pixels/pixel). Developer chooses knowing the memory trade-off.
- **Both formats available** — not a global choice. Different actors could theoretically use different precision if needed.

### Puzzle Mechanics

- **World object types** — switches, pressure plates, timed blocks as first-class `ObjectType` values in the floor/zone builder. Discoverable, not generic.
- **Delegate pattern for puzzle objects** — `val sw1 by switch(x=5, y=3) { onActivate { openDoor(door1) } }`. Name inferred from Kotlin property. Consistent with actor/variable delegates.
- **Built-in `requires()` chaining** — `val bossDoor by door(...) { requires(sw1, sw2, sw3) }`. Direct object references, not string IDs.
- **Configurable pressure plate responders** — `respondTo(player)` (default) or `respondTo(player, enemies)`. Enables "push enemy onto plate" puzzles.
- **Built-in tile swap for timed blocks** — `solidTile(0x15)`, `emptyTile(0x00)`, `interval(60)`. Automatic visual feedback.
- **Generic trigger type** — 4th type beyond the 3 named ones. Covers custom puzzle behavior.
- **Full event set** — Interact, StepOn, StepOff, Timer, FlagChanged. Enables reactive puzzle logic without polling.
- **Hidden/reveal support** — objects can be `hidden = true`, revealed via `reveal(obj)` action. Enables secret puzzles.

### Zone Tilemap Banking

- **Auto-assigned by default** — codegen auto-allocates tilemap data across banks based on size. Developer doesn't think about banks.
- **Manual override available** — `bank(N)` override for advanced users. **Override logs a warning** — we want developers to trust auto-banking but have flexibility if they "know what they are doing."

<specifics>
## Specific Ideas

### No Magic Strings (CRITICAL)

The only magic string allowed is a path to a sprite or file asset. Everything else must be a type-safe object in the DSL:
- Puzzle object references: `requires(sw1, sw2)` not `requires("sw1", "sw2")`
- Collision groups: `val projectiles by collisionGroup()` not `collisionGroup("projectiles")`
- Floor references: type-safe val, not `floor("dungeon_1")`
- Scene navigation: `navigate(winScene)` not `navigate("win")`

### Declarative Over Imperative

`forEachActive` body should use `whenever` conditions, not raw imperative mutation. The DSL stays declarative — it describes what should happen, not how.

### Quality Over Speed (CRITICAL)

At the end of execution: **NO STUBS, NO TODOs, NO SHORTCUTS, NO DEFERRED TASKS** that were not agreed in this context. Every feature fully implemented. The planner must internalize: completeness and quality, not speed, no compromises.
