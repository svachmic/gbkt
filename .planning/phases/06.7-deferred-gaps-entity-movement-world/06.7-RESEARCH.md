## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Entity Pooling DSL
- **Separate pool block** — `val bulletPool by pool(bullet, max = 8)`. Decouples entity definition from pooling.
- **Pool overflow is developer-configurable** — "silent no-op" and "oldest recycled" strategies available per pool.
- **Homogeneous pools** — one entity type per pool.
- **Destroy with optional death callback** — `destroy(entity)` is immediate; `destroy(entity) { ... }` runs death sequence before pool return.
- **`forEachActive` iteration** — `bulletPool.forEachActive { bullet -> ... }` generates a for-loop. Body must remain declarative (`whenever` conditions).
- **`activeCount` as Expr** — runtime counter usable in DSL conditions.
- **Bulk operations** — `destroyAll()` and other standard patterns.
- **Per-instance properties** — pool entities support `u8Prop()` / `i8Prop()` stored as parallel arrays in codegen.

#### NPC-NPC Collision
- **Per-actor opt-in flag** — `collidesWithNpcs(true)`.
- **Type-safe collision groups** — `val projectiles by collisionGroup()`. No magic strings.
- **`collisionRule()` with built-in responses** — `CollisionResponse.BLOCK`, `CollisionResponse.BOUNCE`, `CollisionResponse.OVERLAP`, `CollisionResponse.PUSH` plus custom `onCollide {}` callback.
- **PUSH response with mass** — `mass(N)` on entity; heavier entities displace lighter ones more.
- **Configurable check interval** — `collisionRule(a, b, interval = 2)`.

#### SMOOTH Movement
- **Acceleration + friction model** — `speed(16)`, `acceleration(4)`, `friction(2)`.
- **Diagonal normalization is developer's choice** — both normalized and raw available.

#### PHYSICS Movement
- **Both platformer and top-down** — `PhysicsConfig` selects mode via gravity axis.
- **Variable-height jump** — `variableJump(true)`, `jumpCutMultiplier(2)`.
- **Coyote time** — `coyoteFrames(4)`.
- **Wall response** — `WallResponse.SLIDE` or `WallResponse.STOP`.
- **Wall-jump** — `wallJump(true)`, `wallJumpVelocityX(24)`, `wallJumpVelocityY(28)`.
- **Per-actor physics config**.

#### Fixed-Point System
- **Developer-selectable format** — default 4.4 (UINT8), opt-in 8.8 (UINT16).
- **Both formats available** — not a global choice.

#### Puzzle Mechanics
- **World object types** — switches, pressure plates, timed blocks as first-class `ObjectType` in floor/zone builder.
- **Delegate pattern** — `val sw1 by switch(x=5, y=3) { onActivate { openDoor(door1) } }`.
- **Built-in `requires()` chaining** — direct object references.
- **Configurable pressure plate responders** — `respondTo(player)` or `respondTo(player, enemies)`.
- **Built-in tile swap for timed blocks** — `solidTile(0x15)`, `emptyTile(0x00)`, `interval(60)`.
- **Generic trigger type** — 4th type.
- **Full event set** — Interact, StepOn, StepOff, Timer, FlagChanged.
- **Hidden/reveal support**.

#### Zone Tilemap Banking
- **Auto-assigned by default** — codegen auto-allocates tilemap data across banks.
- **Manual override available** — `bank(N)` with warning log.

## Summary

Phase 06.7 closes 7 deferred gaps (D1, D2, E1, E2, E3, F1, F2) across entity pooling, collision, movement, and world subsystems. The codebase currently has solid IR and codegen infrastructure for basic features; phase 06.7 extends these with new IR nodes, DSL builders, and codegen handlers.

The most significant new work is: (1) actor-centric entity pools (D1) — separate from the existing generic `IRCollPool` data structure; (2) NPC-NPC collision groups (D2) — entirely new IR/DSL/codegen separate from existing player-entity `EntityCollisionIR`; (3) SMOOTH movement upgrade (E1) — the existing SMOOTH codegen is pixel-perfect but lacks acceleration/friction/diagonal normalization; (4) PHYSICS movement extensions (E2) — the existing PHYSICS codegen handles d-pad→velocity→position with gravity/clamp, but lacks variable-height jump, coyote time, wall-jump, and wall-slide; (5) fixed-point types (E3) — no fixed-point IR exists yet; (6) puzzle world objects (F1) — no WorldObject/PuzzleObject IR exists; (7) zone tilemap banking (F2) — zone tile arrays currently hardcoded to HOME bank (bank 0).

**Primary recommendation:** Work vertical-slice per the CONTEXT's 10-plan structure. Each plan should deliver IR + DSL + codegen + tests as a complete unit — no stubs left open across plans.

## Architecture Patterns

### Pattern 1: New IR nodes in gbkt-ir

New IR nodes live in `gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/`. There is no sealed constraint between `.kt` files in the same package — new `data class` / `enum class` types are added directly. `ScriptOp` interface (in `ScriptOp.kt`) is open (non-sealed per BOM-01 requirement), so new ScriptOp subtypes can be added by appending to `ScriptOp.kt` or a new file.

**Example pattern (entity pool ScriptOp):**
```kotlin
// In gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/ScriptOp.kt or new ActorPoolIR.kt
data class PoolSpawnActor(
    val poolId: String,
    val actorId: String,
    val x: Expr,
    val y: Expr,
    override val sourceLocation: SourceLocation? = null,
) : ScriptOp {
    override fun <T> accept(visitor: ScriptOpVisitorI<T>): T = visitor.visitPoolSpawnActor(this)
}
```

New `visitPoolSpawnActor()` must be added to `ScriptOpVisitorI` interface and all implementing classes (`ScriptOpVisitor` in gbdk backend, `ScriptOpInterpreter` in gbkt-core test).

### Pattern 2: New IR data types in CoreTypes.kt

Non-ScriptOp types (configs, enums) go in `gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/CoreTypes.kt`:

```kotlin
// Existing PhysicsConfig extended with new fields
data class PhysicsConfig(
    // ... existing fields ...
    val platformerMode: Boolean = false,    // NEW — gravity axis mode
    val variableJump: Boolean = false,      // NEW

    val wallJumpVelocityX: Int = 0,         // NEW
    val wallJumpVelocityY: Int = 0,         // NEW

enum class WallResponse { SLIDE, STOP }
```

`ActorIR` (in `gbkt-ir/src/main/kotlin/io/github/gbkt/core/ir/ActorIR.kt`) is a `data class` — add nullable fields for new capabilities:

### Anti-Patterns to Avoid

- **Adding fields to ScriptOpVisitorI without implementing in ALL visitors**: `ScriptOpInterpreter` in `gbkt-core` and `ScriptOpVisitor` in `gbkt-backend-gbdk` both implement `ScriptOpVisitorI`. Missing an override causes a compile error — Kotlin's `override` requirement catches this.
- **Putting actor pool logic in existing `IRCollPool`**: `IRCollPool` is a generic data structure (element type + free list). Actor pools are sprite-lifecycle-aware and require OAM slot management, parallel property arrays, and death callbacks. They are architecturally distinct.
- **Putting zone tilemap arrays in bank 0 for large games**: `buildZoneData()` currently puts all tile arrays in `main.c`. For many zones this overflows bank 0. The fix is to create new `CFile(bank = N, ...)` entries.
- **Adding friction/acceleration to `MovementConfig.speed`**: SMOOTH needs a new `SmoothMovementConfig` or extended `MovementConfig` fields — don't repurpose `speed` for velocity.
- **Putting fixed-point sub-pixel state in UINT8 position vars**: Fixed-point needs separate `_vx_frac` / `_vy_frac` variables alongside existing `_actorId_x`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead |
|---------|-------------|-------------|
| Collision detection math | Custom AABB from scratch | Extend existing AABB patterns from `EntityCollisionIR` / `CollisionDetection.kt` |
| Pool free-list | Custom linked-list allocator | Extend existing `IRCollPool` bitmap pattern — reuse `pool_alloc` / `pool_free` codegen |
| Bank switching in C output | Custom MBC state machine | GBDK's `SWITCH_TO_ROM_BANK(N)` macro — already used in other codegen |
| Physics variable declarations | New codegen path | Extend `ActorVisitor.generatePhysicsVars()` and `generatePhysicsDefines()` |
| Fixed-point arithmetic | IEEE float emulation | 4.4 fixed-point = 4 integer bits + 4 fractional bits in UINT8; 8.8 = UINT16 |

## Current State Assessment (What Exists vs. What's Needed)

### D1 — Entity Pooling

**What exists:**
- `IRCollPool` in `gbkt-ir/.../CollectionsIR.kt` — generic data-structure pool (element type = `CollElementType`)
- `PoolRef` in `gbkt-lang/.../CollectionBuilders.kt` — DSL ref with `acquire()`, `free()`, `forEach()`, `activeCount`
- `SpawnActor` / `DestroyActor` in `ScriptOp.kt` — OAM slot claim/release ScriptOps
- `visitSpawnActor` / `visitDestroyActor` in `ScriptOpVisitor.kt` — real OAM free-list codegen (not no-op)
- `GBDKSystemVisitor.buildSpawnActorFunction()` — generates `spawn_actor()` / `destroy_actor()` C functions with OAM free stack

**What's missing:**
- Actor-centric pool IR: `ActorPoolIR` with `actorTemplate: ActorIR`, `maxSize: Int`, `overflowStrategy`
- Actor-centric pool DSL: `val bulletPool by pool(bullet, max = 8)` where `bullet` is an `ActorDelegate`
- Pool-level spawn/destroy ScriptOps with position args and death callbacks
- `forEachActive` ScriptOp iterating over active pool slots
- Per-instance property arrays (parallel arrays: `_pool_<id>_<prop>[capacity]`)
- `destroyAll()` bulk operation
- Codegen: `pool_<id>_spawn(x, y)` / `pool_<id>_destroy(slot)` / `foreach_pool_<id>(callback)`
- Interpreter simulation of pool entity lifecycle

**Key insight:** The existing `SpawnActor(actorId: String)` handles individual named actors. The new system is pool-based: `SpawnPoolActor(poolId, x, y)` returns a slot index, and `DestroyPoolActor(poolId, slot)` releases it.

### D2 — NPC-NPC Collision

**What exists:**
- `EntityCollisionIR.kt` with `EntityCollisionConfig` — this is player-to-entity collision in the exploration system (grid-based tile collision)
- `buildEntityCollisionFunctions()` in `GBDKSystemVisitor` — generates grid-based entity tracking

**What's missing (entirely new):**
- `CollisionGroupIR` — named collision group that actors can belong to
- `CollisionRuleIR` — rule between two groups: `(groupA, groupB, response, interval)`
- `CollisionGroupConfig` on `ActorIR` — which group(s) an actor belongs to
- DSL: `val projectiles by collisionGroup()`, `collisionRule(bullets, enemies, CollisionResponse.OVERLAP) { ... }`
- `ActorBuilder.collidesWithNpcs(true)` — simple shorthand
- `ActorBuilder.mass(n)` — for PUSH response
- Codegen: per-rule AABB pair checks, emitted per-frame check functions with interval counters

### E1 — SMOOTH Movement

**What exists:**
- `MovementStyle.SMOOTH` enum value
- `generateMovementFunction()` SMOOTH branch: 4 `if (dpad_held(...)) {x/y += speed}` statements — pixel-level, no bounds checking, no velocity

**What's missing:**
- `SmoothMovementConfig` data class with `acceleration: Int`, `friction: Int`, `diagonal: DiagonalMode`
- Or extend `MovementConfig` with these fields (discretion)
- `_actorId_vx` / `_actorId_vy` velocity variables for SMOOTH (currently only for PHYSICS)
- SMOOTH codegen: d-pad applies acceleration to velocity, friction decelerates when not pressing, clamp to `speed` max, diagonal normalization (optional)
- `MovementBuilder.acceleration(n)`, `MovementBuilder.friction(n)`, `MovementBuilder.diagonal(DiagonalMode.NORMALIZED)`

### E2 — PHYSICS Movement (advanced features)

**What exists:**
- `MovementStyle.PHYSICS` with d-pad→acceleration→velocity→position
- `PhysicsConfig` with `gravity`, `maxFallSpeed`, `bounce`, `accelerationX/Y`, `velocityX/Y`
- `generatePhysicsVars()` / `generatePhysicsDefines()` in `ActorVisitor`
- `PhysicsStep` ScriptOp + `visitPhysicsStep()` codegen in `ScriptOpVisitor`

**What's missing from CONTEXT.md decisions:**
- `variableJump` field on `PhysicsConfig` + `jumpCutMultiplier` — variable-height jump: cut `vy` when button released early
- `coyoteFrames` field — grace frames counter after walking off ledge: `_actorId_coyote` UINT8 variable
- `WallResponse` enum (`SLIDE`, `STOP`) + `wallJump` flag
- `wallJumpVelocityX/Y` — kick velocity when jumping off wall
- `platformerMode` boolean — selects whether gravity is vertical-axis (platformer) vs. friction-based (top-down)
- Codegen for coyote time: decrement counter each frame, allow jump if `_coyote > 0`
- Codegen for wall slide: detect wall contact, preserve vertical velocity
- Codegen for wall jump: detect wall+jump pressed, kick velocity in opposite direction
- `PhysicsBuilder.variableJump(Boolean)`, `.coyoteFrames(Int)`, `.wallResponse(WallResponse)`, `.wallJump(Boolean)`, `.wallJumpVelocityX/Y(Int)`

### E3 — Fixed-Point System

**What exists:**
- `PhysicsConfig.velocityX/Y` as `Int` (integer pixels/frame) — no sub-pixel precision
- `_actorId_vx` / `_actorId_vy` declared as `INT8` (signed)

**What's missing:**
- No `FixedPoint44` / `FixedPoint88` types in IR
- No sub-pixel position variables (e.g., `_actorId_x_frac: UINT8`)
- `FixedPointMode` enum: `INTEGER` (current), `FP44` (UINT8, 16 sub-pixels), `FP88` (UINT16, 256 sub-pixels)
- `PhysicsConfig.fixedPointMode: FixedPointMode = FixedPointMode.INTEGER`
- Codegen: when `FP44`, position math uses high nibble as pixels; velocity accumulated in low nibble
- When position increments, shift: `x = (x_frac + vx) >> 4` for integer part
- DSL: `PhysicsBuilder.fixedPoint(FixedPointMode.FP44)` or `PhysicsBuilder.fixedPoint88()`
- `ActorIR` gets `fixedPointMode: FixedPointMode = FixedPointMode.INTEGER`

**4.4 fixed-point arithmetic pattern (for codegen):**
```c
// UINT8: upper 4 bits = integer pixels, lower 4 bits = fractional
// Velocity stored as INT8 in fixed-point (e.g., 16 = 1 pixel/frame)
_player_x_frac += _player_vx;           // accumulate sub-pixel
_player_x = _player_x_frac >> 4;        // integer part
// Gravity in FP44: gravity = 4 means 0.25 pixels/frame²
_player_vy_frac += GRAVITY_PLAYER_FP;   // accumulate sub-pixel velocity
_player_vy = _player_vy_frac >> 4;      // integer part of velocity
```

- Each object type: `id`, `x`, `y`, `hidden`, event handlers (`onActivate`, `onDeactivate`, etc.)

### F2 — Zone Tilemap Banking

**What exists:**
- `buildZoneData()` in `GBDKPipelineV2` — generates `const UINT8 _zone_{id}_tiles[]` into HOME bank (bank 0 `main.c`)
- `buildCFiles()` returns exactly 3 files: home, scene, header
- `CFile` has typed `bank: Int` field (defaults to 0)

**What's missing:**
- Bank size estimation per zone: `zone.tileData.size` bytes
- Auto-allocator: bin-pack zones into bank files, starting from a "tilemap bank" (e.g., bank 2 or configurable)
- `buildTilemapBankFiles(gameIR)` — returns List<CFile> with zone arrays distributed across banks
- `ZoneIR.bank: Int?` optional field for manual override (`bank(N)` with warning)
- Bank-aware zone load: `zone_load_X()` must `SWITCH_TO_ROM_BANK(N)` before accessing tilemap data
- Warning log when manual `bank(N)` override is used
- Update `buildCFiles()` to include generated tilemap bank files

**Auto-allocation algorithm (discretion):**
```kotlin
// Simple first-fit bin-packing
val TILEMAP_BANK_START = 2  // or configurable
val BANK_MAX_BYTES = 16384  // 16KB per GBDK ROM bank
var currentBank = TILEMAP_BANK_START
var currentBankSize = 0
val zoneToBank = mutableMapOf<String, Int>()
for (zone in gameIR.zones) {
    val zoneSize = zone.tileData.size
    if (currentBankSize + zoneSize > BANK_MAX_BYTES) {
        currentBank++
        currentBankSize = 0
    }
    zoneToBank[zone.id] = currentBank
    currentBankSize += zoneSize
}
```

## Common Pitfalls

### Pitfall 1: Adding ScriptOpVisitorI method without updating all implementations
**What goes wrong:** New `visitPoolSpawnActor` added to `ScriptOpVisitorI` but `ScriptOpInterpreter` (in `gbkt-core`) not updated. Build fails.
**Why it happens:** Two separate implementations across two modules.
**How to avoid:** Always grep both `ScriptOpVisitor.kt` (gbdk backend) and `ScriptOpInterpreter.kt` (gbkt-core test) when adding new ScriptOp visitors. Both must be updated.
**Files to update:** `gbkt-backend-gbdk/.../visitor/ScriptOpVisitor.kt` AND `gbkt-core/.../test/ScriptOpInterpreter.kt`

### Pitfall 2: Actor pool vs. generic IRCollPool confusion
**What goes wrong:** Using `IRCollPool` for actor pools when it doesn't support sprite lifecycle.
**Why it happens:** `IRCollPool` already exists and looks right for pooling.
**How to avoid:** `IRCollPool` is for generic data (bytes, structs). Actor pools need OAM slot tracking, parallel property arrays, and death callbacks. Create `ActorPoolIR` as a distinct IR node in `GameIR`.

### Pitfall 3: Fixed-point without companion fractional variable
**What goes wrong:** Using regular `_actorId_vx` (INT8) for fixed-point velocity, losing precision.
**Why it happens:** Tempting to just shift existing velocity.
**How to avoid:** FP44 needs a separate `_actorId_vx_frac: UINT8` (or encode as INT16) to accumulate fractional bits across frames. The integer part `_actorId_vx` is then `frac >> 4`.

### Pitfall 4: Zone tilemap banking breaks zone_load references
**What goes wrong:** Zone tile arrays moved to bank N, but `zone_load_X()` reads them without switching banks → corrupt tile data.
**Why it happens:** Moving data to a new bank requires updating all callers.
**How to avoid:** When generating `zone_load_X()`, check `zoneToBank[zone.id]` and emit `SWITCH_TO_ROM_BANK(N)` before the tilemap copy and `SWITCH_TO_HOME_BANK()` after. This pattern is used in existing GBDK code (see project memory notes about bank overflow).

### Pitfall 5: SMOOTH velocity variables not declared at game init
**What goes wrong:** `_actorId_vx` used in SMOOTH mode but not declared → C compile error.
**Why it happens:** Physics var declaration in `generatePhysicsVars()` only triggers for `physicsConfig != null`. SMOOTH mode needs its own velocity variables.
**How to avoid:** SMOOTH acceleration mode needs a new declaration path in `GBDKPipelineV2` — either extend `generatePhysicsVars()` to also check for SMOOTH+acceleration config, or create a separate `generateSmoothVelocityVars()`.

### Pitfall 6: Coyote time counter not reset on landing
**What goes wrong:** Coyote time counter persists after landing → player gets infinite coyote frames.
**Why it happens:** Coyote counter decrements each frame but isn't reset to `coyoteFrames` on ground contact.
**How to avoid:** Codegen must reset `_actorId_coyote = coyoteFrames` whenever the actor is confirmed on ground. Requires a ground detection check (tilemap collision below actor) in the physics update function.

### Pitfall 7: NPC-NPC collision O(n²) with large groups
**What goes wrong:** N actors in a collision group → N² pair checks per frame → too slow on GB (4MHz).
**Why it happens:** Naive pair checking.
**How to avoid:** Limit group sizes (validation pass: warn if group >8 entities). Use `interval = 2` or higher for expensive pairs. The constraint is hardware — document the expected limits.

### Fixed-point 4.4 codegen pattern

In GBDK C, 4.4 fixed-point: UINT8 where upper 4 bits = integer, lower 4 bits = fraction:
```c
// _player_vx_frac: UINT8 (4.4 fixed-point velocity accumulator)
// _player_vx: INT8 (integer pixels/frame)
_player_vx_frac += ACCEL_X_PLAYER_FP;     // accumulate (FP units)
_player_vx = (INT8)(_player_vx_frac >> 4); // extract integer part
_player_x += (UINT8)_player_vx;           // apply to position
```

### Zone tilemap banking

```kotlin
// In GBDKPipelineV2.kt
private data class ZoneBankAllocation(val zoneId: String, val bank: Int)

private fun allocateZoneBanks(gameIR: GameIR): Map<String, Int> {
    val result = mutableMapOf<String, Int>()
    var bank = TILEMAP_BANK_START
    var bankUsed = 0
    for (zone in gameIR.zones) {
        val override = zone.bankOverride  // Int? — null = auto
        if (override != null) {
            logger.warn("Zone ${zone.id}: manual bank override bank($override). Trusting developer.")
            result[zone.id] = override
        } else {
            val size = maxOf(1, zone.tileData.size)
            if (bankUsed + size > BANK_MAX_BYTES) { bank++; bankUsed = 0 }
            result[zone.id] = bank
            bankUsed += size
        }
    }
    return result
}
```

## Open Questions

1. **Actor pool + OAM slot management integration**
   - What we know: `SpawnActor(actorId)` claims an OAM slot via `spawn_actor(hash)`. Actor pools need many slots simultaneously.
   - What's unclear: Should pool entities each claim OAM slots independently, or should pools have a pre-reserved OAM range?
   - Recommendation: Pool pre-allocates OAM slots at init time based on `max` size. `pool_<id>_init()` reserves `max` consecutive slots. Cleaner and avoids hash collision.

2. **Per-instance property arrays and actor identity**
   - What we know: CONTEXT.md says parallel arrays, e.g., `UINT8 _bulletPool_hp[8]`
   - What's unclear: When `forEachActive` iterates, the loop variable is a slot index (0..max-1). How do property accesses look in DSL?
   - Recommendation: `u8Prop("hp")` inside actor block creates `_<poolId>_hp[<slot>]` with slot index passed as implicit loop variable. Slot index is an `Expr` (IR variable) available in `forEachActive` body.

3. **Smooth movement velocity variable naming conflict**
   - What we know: PHYSICS uses `_actorId_vx` / `_actorId_vy` as INT8. SMOOTH with acceleration would also need velocity variables.
   - What's unclear: Can the same variable declarations be shared?
   - Recommendation: Share `_actorId_vx` / `_actorId_vy` for both SMOOTH-with-acceleration and PHYSICS. The `generatePhysicsVars()` should trigger on SMOOTH+acceleration config too.

4. **NPC-NPC collision and exploration system interaction**
   - What we know: `EntityCollisionIR` is for player-entity grid collision in exploration. NPC-NPC is for action/platformer games.
   - What's unclear: Can they coexist? Are they orthogonal?
   - Recommendation: Treat as orthogonal. `EntityCollisionIR` is exploration-scoped. `CollisionGroupIR` / `CollisionRuleIR` is game-wide AABB pair checking. They don't share infrastructure.

5. **Tilemap bank start number**
   - What we know: Home bank (0) has zones currently. Bank 1 is used for banked scene functions. Bank 2+ would be natural for tilemap data.
   - What's unclear: Is bank 2 always safe to start?
   - Recommendation: Make TILEMAP_BANK_START configurable via `CartridgeConfig` with default = 2. Log the allocation during build.
