## Decisions Made

### G3 BLOCKED rationale
The W3 conditional flag-pin (Plan 12.8-03) was production-correct at the asset-pipeline boundary: `-keep_palette_order` is now conditionally applied only to indexed PNGs (verified via `isIndexedPng()` IHDR-color-type guard); W5 7-target sweep confirmed 6/6 strict targets byte-identical AND platformer-template INTENTIONALLY-CHANGED with the cream→near-black palette-index-0 shift correctly captured.

However, the W2 ABSORB rationale acknowledged the A6-CONFIRMED palette-wiring risk: at runtime, the BG palette RAM is populated by `_gbkt_default_bg_pal` at `main.c:698` (GBC-gated), NOT by the emitted per-zone `_zone_<id>_tileset_palettes[16]` arrays. After W3, the tilemap indices correctly reference index 0 = near-black per the source PLTE — but the BG palette RAM still holds the auto-sorted cream→dark gradient from `_gbkt_default_bg_pal`. The visual result is **color inversion**: what should render as near-black grass outlines now renders as cream, and vice versa.

This is exactly the multi-file palette-wiring scenario W2 deferred when the user chose ABSORB on the D-05 1-file heuristic. The W6 binding gate caught it as designed.
