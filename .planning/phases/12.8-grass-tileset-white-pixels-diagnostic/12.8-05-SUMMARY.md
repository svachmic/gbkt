## Pre/post byte-diff — D-14 ROOT-CAUSE-EVIDENCE

Diff command: `diff -u evidence/pre-fix-baseline/_zone_world1Area1Zone_tileset.c evidence/post-fix-baseline/_zone_world1Area1Zone_tileset.c` (output: 80 lines).

**File-size delta:** 2,919 → 3,171 bytes (+252 bytes).

**Sections that changed (4 categories):**

1. **Conversion-args header gains `-keep_palette_order` token** (textual confirmation the flag is being plumbed through ConvertZoneTilesetsTask → png2asset).
2. **Palette array shape:** `[4]` → `[16]` entries; index-0 shifts from `RGB8(224,248,207)` (cream, auto-sorted position 0) to `RGB8(8,24,32)` (near-black, PNG's actual PLTE index 0); indices 4-15 padded with `RGB8(0,0,0)`.
3. **All 27 tile bitplane rows re-permuted** — every byte of `_zone_world1Area1Zone_tileset_tiles[432]` changed because the palette-index-to-pixel-byte mapping now follows the source PLTE order instead of the auto-sorted (light→dark) order.
4. **Sections that did NOT change:** banking, BANKREF macro, include order, file structure, function declarations, sprite metadata, tile-count constants — proving the flag-pin is scoped exclusively to the png2asset asset-pipeline boundary and does NOT leak into downstream codegen.

**Why this is ROOT-CAUSE-EVIDENCE for D-14:**

D-14 asks "did the W3 fix change the bytes we expected, in the files we expected, in the way we expected?" The byte-diff answers YES on all four sub-questions:

- Expected file changed: `_zone_world1Area1Zone_tileset.c` (✓).
- Expected sections changed: palette array shape + tile bitplane bytes (✓).
- Expected direction: palette index 0 shifts from cream-sort-result to PNG-PLTE-source-result (✓); tile bytes re-permute coherently to maintain the source PNG's intended pixel-to-index mapping (✓).
- No unexpected sections changed: no leakage into banking / function signatures / sprite metadata (✓).

**Downstream risk acknowledged (W6 visual-evidence question, NOT a W5 question):** The byte-diff is necessary-but-not-sufficient for visual G3 closure. The A6-CONFIRMED palette-wiring gap (§"Palette wiring audit" in DIAGNOSTIC.md) still applies on CGB: even with correct tile bytes and correct palette-array contents emitted to ROM, the runtime never calls `set_bkg_palette` on the per-zone arrays — so CGB BG palette RAM contains `_gbkt_default_bg_pal`, not the emitted `_zone_world1Area1Zone_tileset_palettes`. Whether `_gbkt_default_bg_pal` happens to align RGB-for-RGB with the source PLTE is the W6 verdict question. If it does NOT align, a sibling phase per D-16 HARD-terminal contract will need to wire the per-zone palette into BCPS/BCPD.
