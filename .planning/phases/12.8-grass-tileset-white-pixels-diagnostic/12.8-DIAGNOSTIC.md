**Observation:** Tiles 1-2 contain `0xff` bytes in their first byte-of-row pair (`0xff,0xff,...`). In the 2bpp planar encoding (low-plane,high-plane interleaved), a row whose plane bytes are both `0xff` paints all 8 pixels as palette index 3 (binary `11`). Since palette index 3 in the emitted array is `RGB8(8,24,32)` (black), these rows render as solid black on CGB; on DMG with the default BGP register they render as the darkest shade. This is not "white pixels" per se — the white-pixel symptom likely comes from index-0 cells (palette[0] = `RGB8(224,248,207)` cream/white) appearing where the source grass intent was a green/mid-shade index. ### Verdict — A6-CONFIRMED

The arrays are unused. The runtime BG palette is whatever `_gbkt_default_bg_pal` resolves to (set at main.c:698 on non-DMG; nothing explicit on DMG, relying on `cgb_compatibility()` + hardware default BGP).

**Load-bearing input for the W2 fix-vs-route checkpoint (D-05/D-06):**

- The flag-fix alone (`-keep_palette_order` ADD per D-02) changes the **byte ORDER of palette indices** in `_zone_*_tileset_tiles[]`. It re-permutes which index a given source-PNG pixel maps to.
- On DMG, this is sufficient ONLY IF the source PNG's color-0 happens to be the cream/white shade that DMG's default BGP register renders as shade-0. From the baseline's emitted palette array `RGB8(224,248,207), RGB8(136,192,112), RGB8( 48,104, 80), RGB8(  8, 24, 32)`, the auto-sorted order already puts cream at index 0 — so the DMG-default-BGP outcome MAY visually close G3 even without palette wiring, IF the source PLTE matches that sort.
- On CGB (the platformer-template target per `gbcTarget=GBC_COMPATIBLE` in the buildRom log above), the BG palette RAM is dominated by `_gbkt_default_bg_pal` (set at main.c:698) — NOT the emitted `_zone_*_tileset_palettes`. So even with `-keep_palette_order`, the rendered RGB values come from `_gbkt_default_bg_pal`, not the source PNG's PLTE. If `_gbkt_default_bg_pal` happens to mirror the source PNG's intended palette, flag-fix-alone suffices; if not, the actual fix requires WIRING the emitted array via a per-scene/per-zone `set_bkg_palette(0u, 1u, _zone_<id>_tileset_palettes)` call — **multi-file scope** (touches SceneVisitor + GBDKPipelineV2 + zone-load codegen ordering).

The W2 fix-vs-route checkpoint MUST surface this dichotomy to the user. If the buildRom log shows `gbcTarget=GBC_COMPATIBLE` (it does — see Task 2 Step 1 above) AND the user confirms the white-pixel symptom is observed on CGB (not just DMG), the fix likely routes to 12.9 per D-05 multi-file heuristic. If the symptom is DMG-only AND the source PLTE happens to be light→dark, flag-fix-alone may close G3.

**Interpretation — which tiles changed and how this maps to the flag-pin effect:**

The diff shows the W3 conditional `-keep_palette_order` flag is doing exactly what
RESEARCH §"png2asset palette behavior" predicted, with no spillover into unrelated
codegen paths:

1. **Conversion-args header (line 2):** The auto-conversion args string emitted by
   png2asset gains the `-keep_palette_order` token. This is the visible 1-token textual
   confirmation that the flag is being plumbed through the Gradle task and into the
   external png2asset invocation. The token's presence is the upstream cause of all
   other differences below.

2. **Palette array shape (`_zone_world1Area1Zone_tileset_palettes`):** Grows from `[4]`
   (the auto-sorted 4-color emission png2asset produces WITHOUT `-keep_palette_order`)
   to `[16]` (the full 16-entry PLTE table png2asset emits WITH the flag, padded with
   `RGB8(0,0,0)` for unused indices). Critically, the FIRST entry shifts from
   `RGB8(224,248,207)` (cream — sort-ascending position 0) to `RGB8(8,24,32)` (near-
   black — the PNG's actual PLTE index 0). This is the PNG-side cause of the white-
   pixel symptom on DMG default-BGP: pre-fix, index-0 maps to cream/white; post-fix,
   index-0 maps to near-black. On a DMG using default BGP (which renders shade-0 as
   white), an index-0 tile pixel pre-fix renders as cream-on-white (invisible/white);
   post-fix that same pixel renders as the source PNG's intended index-0 color
   semantically — which the GBC palette wiring must then reflect to be visually
   correct.

3. **Tile bitplane array (`_zone_world1Area1Zone_tileset_tiles[432]`):** All 27 tiles

   bitplane bytes. This is expected: when png2asset re-permutes which palette index

   tile row change. The byte values themselves do NOT correspond to the same visual
   shades — they correspond to different palette-index ROUTES that, combined with the
   new palette ordering, should produce the SAME visual shades the source PNG author
