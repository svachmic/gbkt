# Phase 12.8 Plan 04: W4 JVM Emission-Invariant Test — World1TilesetGrassEncodingTest

W4 (D-13) lands the JVM-tier regression guard for the W3 conditional `-keep_palette_order` fix that closes G3. The new test class stages the **real** `gbkt-examples/platformer-template/res/graphics/world1-tileset.png` into a per-test TempDir, runs `ConvertZoneTilesetsTask.convertZoneTilesets()` via the same `ProjectBuilder`-driven in-process harness used by `ConvertZoneTilesetsTaskTest`, parses the emitted `_zone_world1Area1Zone_tileset_tiles[432]` byte array via an inline `parseTileBytes` helper (dual-token regex), and locks 4 representative grass-tone byte values against future png2asset version drift OR accidental removal of the W3 conditional flag.

The test is **green-locked against the post-W3 output** — byte values were captured during this plan from a fresh `convertZoneTilesets` run after the W3 fix landed at commit `13037c9b`. Any future regression (palette auto-sort returning, flag removal, png2asset format change) will surface at JVM test time with a precise byte-mismatch message rather than waiting for a visual UAT cycle.

**Step 1.** Ran `./gradlew clean :gbkt-examples:platformer-template:generateC` (succeeded, but produced only main.c / bank1.c / zone_bank2.c / game.h — the `_zone_*_tileset.c` files are NOT a `generateC` output). ```


The trailing `-keep_palette_order` token confirms the W3 conditional flag fired on the indexed PNG (`file(1)` reports `PNG image data, 64 x 32, 8-bit colormap, non-interlaced`).

**Step 2.** Read the post-fix snapshot. The palette block at lines 10-15 shows the correct GB grass palette in source order: `RGB8(8,24,32)` (slot 0, near-black outline), `RGB8(224,248,207)` (slot 1, light-green highlight), `RGB8(136,192,112)` (slot 2, mid-green grass), `RGB8(48,104,80)` (slot 3, dark-green shadow). The pre-W3 auto-sort would have re-ordered these light-to-dark, breaking the grass encoding.

Picked two grass-tone tiles for the lock:
- **Tile index 0** (bytes [0..15]): first png2asset-emitted tile from world1-tileset.png — first two 2bpp bytes `0x80, 0x80` encode the top edge of a grass-edge tile.
- **Tile index 6** (bytes [96..111]): RESEARCH-suggested grass tile (matches the left-edge ground-shape tile per RESEARCH Example 5 hint) — first two 2bpp bytes also `0x80, 0x80`.

Both tiles share the `0x80,0x80` prefix under the keep-palette-order encoding — uniquely tied to slot-0 being the near-black outline. A regression to auto-sort would shift these bytes (slot 0 would become the lightest color, breaking the grass-edge encoding contract).

## Deviations from Plan

### 1. [Rule 2 — Auto-add missing critical functionality] Dual-token regex (uint8_t support)

- **Found during:** Step 4 (focused-test green confirmation).
- **Issue:** PATTERNS.md §"Byte-parse helper pattern" (lines 196-214) specified a regex starting with `const\s+(?:unsigned\s+char|uint8_t)\s+...` — the dual-token form. The production `ConvertZoneTilesetsTask.parseMapArrayBytes` (kt:507-530) uses single-token `const\s+unsigned\s+char\s+...` because it parses `_tileset_map[]` and `_tilemap_raw_map[]` arrays (which png2asset emits as `unsigned char`).
- **Why it matters:** The `_tileset_tiles[]` array — the array this test asserts against — is emitted as `const uint8_t` (post-12.2 png2asset format; verified in captured snapshot at line 17 of `_zone_world1Area1Zone_tileset.c`). A single-token regex would silently return `null`, then `error("Could not parse...")` would fire, then the test would surface as a confusing parse-failure rather than a byte-mismatch.
- **Fix applied:** Used the PATTERNS-specified dual-token regex `(?:unsigned\s+char|uint8_t)`. Inline docblock comment cites both forms with rationale.
- **Files modified:** `gbkt-gradle-plugin/src/test/kotlin/io/github/gbkt/gradle/tasks/World1TilesetGrassEncodingTest.kt` (parseTileBytes helper).
- **Commit:** `976ce98a` (single Task 1 commit).
