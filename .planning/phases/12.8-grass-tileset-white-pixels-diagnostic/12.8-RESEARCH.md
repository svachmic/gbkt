## Summary

The Plan 12-23 SEED Hypothesis H1 (palette/index mismatch) is **confirmed before W1** by direct inspection: the reference Makefile (`/Users/michalsvacha/gbdk/examples/cross-platform/platformer_template/Makefile` lines 82-86) passes `-keep_palette_order` to every BG tileset/tilemap png2asset invocation; our `ConvertZoneTilesetsTask.kt:288-298` does NOT. The Plan 11.2-02 spike comment at `ConvertZoneTilesetsTask.kt:51-57` justifies the omission with "png2asset rejects `-keep_palette_order` on RGB (non-indexed) PNGs" — but `file(1)` reports `world1-tileset.png` and `world2-tileset.png` are **8-bit colormap (indexed)** PNGs while `title-screen.png` and `next-level.png` are **RGB**. The spike's blanket-reject conclusion was over-zealous: the flag IS valid on the indexed tileset PNGs and was removed from a code path that needed it.

Additionally, the reference Makefile passes `-b 255` (fixed-bank assignment) on every invocation; we omit this. `-b` is documented in `png2asset --help` as "Bank number (default: fixed bank)" — our zone tileset emission relies on `#pragma bank N` injection downstream, so `-b 255` is likely a no-op for our pipeline (low-risk follow-up to verify in W1). The decision-relevant delta is `-keep_palette_order` and possibly `-repair_indexed_pal` (which implies `-keep_palette_order` per the help text).

**Primary recommendation:** W1 plan reads the reference Makefile + diffs against our `args` list + confirms `world1-tileset.png` is indexed via `file(1)` (already done in this research — both findings logged in 12.8-DIAGNOSTIC.md). W2 fix is a 1-line addition of `-keep_palette_order` to the FIRST `args` list at `ConvertZoneTilesetsTask.kt:288-298` (tileset invocation). The second-invocation `tilemapArgs` at lines 343-402 uses `-maps_only -source_tileset` and reads the tile indices the first invocation produced — it inherits palette ordering through `-source_tileset` and does NOT need the flag. JVM-tier `World1TilesetGrassEncodingTest` (D-13) locks the post-fix byte pattern; D-14 7-target sweep guards regression; D-11/D-12 visual binding gates close G3 + G4 in series.

**Open question on absorb-vs-route (D-05/D-06 W2 checkpoint):** Even with `-keep_palette_order`, DMG palette index 0 is rendered "white" by the default BGP register. The fix may need a SECOND step — wiring `set_bkg_palette()` calls in scene-enter codegen to actually apply the emitted `_zone_*_tileset_palettes[4]` arrays. If that wiring touches multiple modules (SceneVisitor + GBDKPipelineV2 + scene-enter codegen ordering), the W2 checkpoint MUST route to Phase 12.9 per D-05 multi-file heuristic. The diagnostic must therefore include a post-fix `set_bkg_palette` audit — if the emitted palette already matches the DMG default BGP intent, the flag fix alone closes G3; if not, route.

### Pattern 2: Brace-walk byte-pattern assertion (D-13 test pattern)

**What:** Parse the generated `.c` byte-array initializer with a Regex that handles BOTH decimal and hex tokens (per `ConvertZoneTilesetsTask.kt:445-468` `parseMapArrayBytes` precedent); assert specific bytes at specific tile-index offsets.
**When to use:** Locking the post-fix 2bpp byte pattern as the regression guard. Mirrors the existing `parseMapArrayBytes` helper — REUSE that helper from the task or copy the Regex.
**Example:**
```kotlin
// Source: derived from ConvertZoneTilesetsTask.kt:445-468 + LevelEndTriggerGroundedGuardEmissionTest.kt:120-140
// Phase 12.8 D-13 — locks specific 2bpp grass-tile bytes that should NOT be 0xFF
// after the -keep_palette_order fix.
private fun parseTileBytes(file: File, symbol: String): List<Int>? {
    val text = file.readText()
    val pattern = Regex(
        """const\s+uint8_t\s+${Regex.escape(symbol)}\s*\[\s*\d+\s*\]\s*=\s*\{([^}]*)\}""",
        RegexOption.DOT_MATCHES_ALL,
    )
    val match = pattern.find(text) ?: return null
    return match.groupValues[1]
        .split(',')
        .map { it.trim() }
        .filter { it.isNotEmpty() }
        .map { token ->
            if (token.startsWith("0x") || token.startsWith("0X")) token.substring(2).toInt(16)
            else token.toInt()
        }
}
```

## Common Pitfalls

### Pitfall 1: Removing the `-keep_palette_order` flag globally based on a single PNG color-mode mismatch

**What goes wrong:** The Plan 11.2-02 spike found `png2asset: keep_palette_order only works with indexed png images` on a non-indexed test PNG and removed the flag from all png2asset invocations.
**Why it happens:** The spike test PNG was an RGB sprite or color-checker, not an indexed BG tileset. Generalizing the rejection from one PNG to the entire flag set is the over-zealous-fix anti-pattern.
**How to avoid:** Always classify the target PNG's color mode (`file(1)` returns "8-bit colormap" for indexed, "RGBA" / "RGB" for non-indexed). For the BG tileset path specifically, ONLY indexed PNGs are passed; the flag is universally valid here.
**Warning signs:** A blanket-remove comment ("rejected on RGB PNGs") in a code path that operates exclusively on indexed PNGs is a signal that the rejection was over-applied.

### Pitfall 2: Assuming the flag fix alone closes G3 without verifying runtime palette wiring

**What goes wrong:** Even with `-keep_palette_order`, the emitted `_zone_*_tileset_palettes[4]` array is NOT applied unless our codegen calls `set_bkg_palette()` (CGB) or sets the DMG BGP register. The reference platformer_template/src/common.c:24-37 calls `setBKGPalettes()`; our SceneVisitor zone-load codegen needs to do the same on DMG. If our codegen omits this call entirely AND the source PNG's color order conveniently matches the default DMG BGP shade-mapping (cream→white at index 0), the flag fix may still help — because `-keep_palette_order` keeps the source's color-0 in slot-0, which DMG renders as the lightest shade by default. But if the source PNG puts grass at color-0, the flag fix alone changes nothing.
**Why it happens:** Two-layer mismatch: png2asset emits palette data, but our codegen never wires it to hardware.
**How to avoid:** Inspect the current generated zone-load code for `set_bkg_palette` calls (W1 diagnostic step). Inspect the source PNG's palette ordering (e.g., via `convert world1-tileset.png -unique-colors txt:-` or by reading the emitted `_zone_*_tileset_palettes[4]` array — already done in this research: index 0 = `RGB8(224,248,207)` cream/white, index 3 = `RGB8(8,24,32)` black — order is already light→dark). If the cream-color is at index 0, the flag fix should suffice. If not, route to 12.9.
**Warning signs:** Post-fix byte-diff in `_zone_world1Area1Zone_tileset_tiles[]` shows NO change, OR shows change but the visual still has white pixels.

### Pitfall 3: Adding the flag to the SECOND (`tilemapArgs`) invocation as well

**What goes wrong:** `tilemapArgs` uses `-maps_only -source_tileset <tileset>.png` (kt:352-362). Adding `-keep_palette_order` here may either be a no-op or trigger a png2asset version-specific edge case where the flag interacts with the `-source_tileset` palette inheritance.
**Why it happens:** Over-cautious copy-paste — "if the first invocation needs it, the second probably does too."
**How to avoid:** The second invocation reads tile INDICES from the source tileset; palette ordering is already locked by the first invocation. Documented at `ConvertZoneTilesetsTask.kt:347-350`. ONLY add the flag to the first `args` list.
**Warning signs:** If you find yourself adding the flag in two places, stop and re-read the two-path semantics.

### Pitfall 4: Treating anchor-5/02 0F/F text corruption (D-10) as the same root cause

**What goes wrong:** Conflating BG tile rendering (grass white-pixels) with text rendering (0F/F nextlevel-card corruption). The text on next-level.png comes from a DIFFERENT PNG (RGB, not indexed) processed through a DIFFERENT pipeline path (not `ConvertZoneTilesetsTask`).
**Why it happens:** Both manifest as "wrong pixels in BG layer" — visual similarity invites premature unification.
**How to avoid:** W1 diagnostic explicitly tests: is `next-level.png` indexed? (Already answered: NO — it's RGB.) If non-indexed, `-keep_palette_order` is INVALID for it and cannot be the fix. The 0F/F bug routes to 12.9 (palette inversion) per D-10 conditional.
**Warning signs:** If the diagnostic finds the 0F/F bug uses the same code path as world1-tileset (e.g., title-screen also routes through ConvertZoneTilesetsTask somehow), revisit. Otherwise route.

### Pitfall 5: `phase.complete 12` invocation timing

**What goes wrong:** Invoking `phase.complete 12` BEFORE the 12-27-SUMMARY.md `status: partial → complete` flip lands → the ROADMAP gets marked checked while the SUMMARY still says partial → ledger split-brain.
**Why it happens:** Order-of-operations confusion in W8.
**How to avoid:** Write all admin edits (SUMMARY frontmatter flip + Round-N append + SEED RESOLVED stamp + STATE.md update) IN A SINGLE COMMIT FIRST, then invoke `phase.complete 12` AFTER. The handler is idempotent (re-derives `completed_phases` from ROADMAP table), so running it twice is safe, but the SUMMARY flip is NOT idempotent across commits — keep it atomic.
**Warning signs:** `gsd-sdk query phase.complete 12` exits 0 but STATE.md and 12-27-SUMMARY disagree on Phase 12 status.

### Pitfall 6: Worktree drift during execution

**What goes wrong:** Per `feedback_claude_code_worktree_drift_quirks`, parallel-agent worktree isolation can leak commits to the parent branch unintentionally.
**Why it happens:** `isolation="worktree"` mode has known quirks.
**How to avoid:** For W8 terminal close (admin-only, single-commit ledger update), prefer non-worktree execution. For W3-W6 (codegen + tests + anchor capture), worktrees are fine but verify with `git reflog` + hash-compare before merge.
**Warning signs:** Untracked files in the main checkout after a worktree merge; orphaned branches `worktree-agent-*` that don't appear in `git branch`.
