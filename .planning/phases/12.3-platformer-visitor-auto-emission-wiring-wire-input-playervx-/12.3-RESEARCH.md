### Pattern 1: AssignableVar binder (D-03 — no magic strings)
**What:** Capture `AssignableVar.name` (from Kotlin property delegate) into `String?` fields in the builder, then put them in the `GenericSystem.config` map; visitor reads them back via `config["xxxVar"] as? String`.

**When to use:** Any DSL where a builder needs to reference a user-declared variable by its property name, not by a string literal.

**Example (verbatim template from `TilemapCollisionBuilder.kt`):**
```kotlin
// Source: gbkt-genre-platformer/src/main/kotlin/.../dsl/PlatformerExtensions.kt:455-485
@GbktDsl
class PlatformerInputBuilder(val id: String) {
    private var walkSpeed: Int = 128
    private var friction: Int = 8
    private var airFriction: Int = 0
    private var walkFrameCount: Int = 3
    private var cyclePeriod: Int = 6
    private var walkFrameIdxVar: String? = null
    private var threeFrameCounterVar: String? = null

    open fun walkSpeed(value: Int) { walkSpeed = value }
    open fun friction(value: Int) { friction = value }
    open fun airFriction(value: Int) { airFriction = value }
    open fun walkFrameCount(value: Int) { walkFrameCount = value }
    open fun cyclePeriod(value: Int) { cyclePeriod = value }

    /** Captures `AssignableVar.name` (inferred from the Kotlin property delegate). */
    fun walkFrameIdx(v: AssignableVar) { walkFrameIdxVar = v.name }
    fun threeFrameCounter(v: AssignableVar) { threeFrameCounterVar = v.name }

    fun build(): GenericSystem {
        val cfg = mutableMapOf<String, Any>(
            "type" to "platformer_input",
            "walkSpeed" to walkSpeed,
            "friction" to friction,
            "airFriction" to airFriction,
            "walkFrameCount" to walkFrameCount,
            "cyclePeriod" to cyclePeriod,
        )
        walkFrameIdxVar?.let { cfg["walkFrameIdxVar"] = it }
        threeFrameCounterVar?.let { cfg["threeFrameCounterVar"] = it }
        return GenericSystem(id = id, config = cfg.toMap())
    }
}
```

### Pattern 2: Override-tracking builder (D-01 — per-zone shadow)
**What:** Subclass the base builder, override each setter to record which fields were SET, expose `toOverrideMap()` for unset-vs-set distinction.

**When to use:** Per-zone override of a game-level config where unset fields fall through to game-level defaults.

**Example (verbatim template):**
```kotlin
// Source: gbkt-genre-platformer/.../PlatformerExtensions.kt:302-332
internal class OverrideTrackingInputBuilder : PlatformerInputBuilder("input-override") {
    private val setFields = mutableMapOf<String, Any>()

    override fun walkSpeed(value: Int) { super.walkSpeed(value); setFields["walkSpeed"] = value }
    override fun friction(value: Int) { super.friction(value); setFields["friction"] = value }
    override fun airFriction(value: Int) { super.airFriction(value); setFields["airFriction"] = value }
    override fun walkFrameCount(value: Int) { super.walkFrameCount(value); setFields["walkFrameCount"] = value }
    override fun cyclePeriod(value: Int) { super.cyclePeriod(value); setFields["cyclePeriod"] = value }
    // AssignableVar binders intentionally NOT overridden — they only make sense at game-level.

    fun toOverrideMap(): Map<String, Any> = setFields.toMap()
}

fun ZoneBuilder.platformerInput(block: PlatformerInputBuilder.() -> Unit) {
    val builder = OverrideTrackingInputBuilder()
    builder.block()
    setPlatformerInputOverride(builder.toOverrideMap())  // ← needs public setter on ZoneBuilder, mirrors setPlatformerPhysicsOverride
}
```

### Pattern 3: frameOps splice (D-05 — call-site emission)
**What:** Visitor returns `GenreVisitorResult(frameOps = mapOf(sceneId to listOf(RawOp("xxx();"))))`. The backend pipeline appends these ops to the named scene's frame block. Result: the C call appears inside the scene's `gameplay_frame` body at codegen time.

**When to use:** A visitor needs to trigger a runtime call from a specific scene's frame block without modifying user DSL.

**Example (verbatim template — PlatformerVisitor.kt:199-206):**
```kotlin
// Source: gbkt-genre-platformer/.../codegen/PlatformerVisitor.kt:179-206
val gameplaySceneId: String? =
    gameIR.scenes
        .firstOrNull { scene -> scene.actorIds.any { id -> id in physicsActorIds } }
        ?.id
        ?: findFirstNavigateTarget(gameIR)
        ?: gameIR.startScene
        ?: gameIR.scenes.firstOrNull()?.id

val frameOps: Map<String, List<ScriptOp>> =
    if (gameplaySceneId != null) {
        mapOf(gameplaySceneId to listOf(RawOp("platformer_camera_update();")))  // NEW (gap #2)
    } else {
        emptyMap()
    }

return GenreVisitorResult(functions = functions, varDecls = varDecls, frameOps = frameOps)
```

Note: `visitPhysics` already returns `frameOps` for `platformer_physics_update();`. To get the D-05 emission order (input → physics → camera_update → metasprite render), the planner can either:

1. (Preferred — D-05 alignment) Prepend the input + walk-cycle statements INSIDE `buildTilemapPhysicsUpdateFunction` body (before the existing physics integration), so a single `platformer_physics_update();` call still appears once in `frameOps`. The camera-update call enters via `visitCamera.frameOps`. The pipeline merges `frameOps` across visitors — order is determined by the order the visitors are invoked in `GBDKPipelineV2`, which is deterministic (physics before camera per the existing pipeline flow).
2. (Alternate) Emit a new `_platformer_input_update()` function and add it to `frameOps` separately. Adds a function but separates concerns.

### Pattern 4: Per-function awk brace-walk emission test (CLAUDE.md §"Scope-level grep gates")
**What:** Read the generated C source as a string, find a function signature line that starts at column 0 (`"^void platformer_physics_update"`), walk braces until depth returns to 0, return the function body blob, then run `.contains()` checks against the blob — not the file.

**When to use:** Every JVM emission test in this phase. File-level grep is FORBIDDEN.

**Example (verbatim — all 4 sibling tests use this helper):**
```kotlin
// Source: gbkt-genre-platformer/src/test/.../codegen/{TilemapCollision,JumpHold,HorizontalScroll,Defect4SymbolRewrite}EmissionTest.kt
private fun extractFunctionBody(cSource: String, functionSignaturePrefix: String): String {
    val lines = cSource.lines()
    val startIdx = lines.indexOfFirst { it.startsWith(functionSignaturePrefix) }
    if (startIdx == -1) return ""
    val body = StringBuilder()
    var depth = 0
    var started = false
    for (i in startIdx until lines.size) {
        val line = lines[i]
        body.appendLine(line)
        for (ch in line) {
            if (ch == '{') { depth++; started = true }
            if (ch == '}') depth--
        }
        if (started && depth == 0) break
    }
    return body.toString()
}
```

**What:** Each emission test writes its extracted function body to `evidence/tier1-shape/<name>.c` BEFORE any assertion fires. Result: a RED run still produces a reviewable artifact on disk. (Plan 12-09 / 12-13 / 12-14 / 12.1-06 all follow this.)

### Anti-Patterns to Avoid

- **Magic strings for player symbols** (e.g., emitting `_walkFrameIdx` directly without a binder): violates `feedback_no_magic_strings.md`. **Instead:** use AssignableVar binders, skip emission if unset.
- **File-level grep in emission tests** (e.g., `mainC.contains("button_held(J_RIGHT)")`): the token appears in unrelated functions (existing rect-physics path) and false-positives. **Instead:** awk brace-walk to the target function body.
- **CLiteral on signed-context comparisons** (e.g., `CBinaryExpr(CVar("_playerVx"), ">", CLiteral(0))`): would emit `_playerVx > 0u` — promotion bug per Phase 07.9. **Instead:** `CIntLiteral(0)`.
- **Implicit `cameraOffsetX` activation** (e.g., MetaspriteVisitor querying GameIR systems internally): couples MetaspriteVisitor to platformer genre. **Instead:** thread the param through `ScriptOpVisitor.visitMoveMetasprite` per D-07 option A.
- **Auto-emitting walk-cycle when binders unset** (silently picking the magic `_walkFrameIdx`): violates D-03 fallback-shape contract. **Instead:** SKIP emission entirely; visitor's job is to be a no-op when the contract isn't satisfied.

## Common Pitfalls

### Pitfall 1: SDCC promotes signed/unsigned comparisons silently (Phase 07.9)
**What goes wrong:** `_playerVx > 0u` becomes `unsigned > unsigned`; the test never fires when `_playerVx` is negative.
**Why it happens:** C11 §6.3.1.8 "usual arithmetic conversions" promote signed to unsigned in mixed-signedness comparisons.
**How to avoid:** All new comparisons of `_playerVx`/`_playerVy` (signed INT8/INT16) against literals MUST use `CIntLiteral(N)`, NOT `CLiteral(N)`. The D-04 emission shape `if (_playerVx > 0) _playerVx -= friction` MUST emit as `CBinaryExpr(CVar(vxSym), ">", CIntLiteral(0))`. Reference: gbkt-backend-gbdk/CLAUDE.md §"Literal Emission Convention".
**Warning signs:** SDCC warning 94 "comparison is always false due to limited range of data type" — but gbkt doesn't currently escalate this; check generated C by eye if input wiring "doesn't fire".

### Pitfall 2: Bare `_grounded` symbol resolution
**What goes wrong:** PlatformerVisitor references bare `_grounded` (groundedSym fallback) at lines 610/631/672/918 BUT the user DSL must declare `var grounded by u8Var(0)` to provide the symbol. Without it, lcc fails with "undefined identifier `_grounded`".
**Why it happens:** PlatformerVisitor's tilemap-physics path treats `_grounded` as a contract symbol; it doesn't emit a CVarDecl for it (vs rect-physics' `_plat_grounded`).
**How to avoid:** D-04's input friction emission reads `_grounded` from the `tilemap_collision` system's `groundedVar` binder; PlatformerTemplate.kt already has `var grounded by u8Var(0)` (line 154). Verify the platformer-template DSL doesn't lose this declaration during the cEmit cleanup.
**Warning signs:** lcc error "Symbol `_grounded` not defined" on ROM build.

### Pitfall 3: i8Var → i16Var widening doesn't break horizontal AABB probes
**What goes wrong (potential):** The horizontal AABB probes in `buildTilemapPhysicsUpdateFunction` (`buildHorizontalProbe`) compare `_playerVx` against literal `0`. If a probe site uses `CLiteral(0)` rather than `CIntLiteral(0)`, the SDCC-promotion bug fires.
**Why it happens:** Probe code uses signed-velocity LHS but historically may not have been audited against the signed-literal discipline.
**How to avoid:** Plan 12.3-11 (req 6) MUST audit `buildHorizontalProbe` for `CLiteral`-on-signed-RHS sites and convert them to `CIntLiteral` where applicable. Probe sites: `vxSym` comparison entries in `buildHorizontalProbe` (PlatformerVisitor.kt:900-963). The widening from INT8 to INT16 changes the type but not the comparison contract — IF the existing code emits `CIntLiteral`, no change needed. Verify in the Plan 12.3-11 emission-test diff.
**Warning signs:** `:gbkt-examples:platformer-template:buildRom` produces SDCC warning 94 on the probe site; or anchor 3 silently regresses (camera doesn't scroll because `_playerVx > 0` never fires for the widened type).

### Pitfall 4: cEmit removal changes generated-C function discovery
**What goes wrong (potential):** Removing the 3 inline cEmits removes implicit symbol references. If any visitor or pipeline analysis pass relies on "saw `platformer_camera_update();` in scene frame ops, therefore camera-update wiring is needed", removing the cEmit silently drops that path.
**Why it happens:** Pipeline-emitted globals like `_current_level_map` are gated on `gameUsesTilemapCollision`, NOT on the presence of `cEmit("platformer_camera_update();")`. So this is unlikely. But verify Plan 12.3 §cleanup task lists which visitors/passes feed off the gameplay-scene's RawOp content.
**How to avoid:** When Plan 12.3-12 (cleanup) lands, immediately run the full JVM test suite + a clean `:buildRom` to confirm no implicit dependency was severed.

### Pitfall 5: Metasprite camera-offset formula integer-promotion warnings
**What goes wrong (potential):** SDCC's `(UINT8)(((INT16)(_playerX >> 4)) - (INT16)_camera_x)` emission may produce warnings about signed/unsigned mixing or cast-to-smaller-type truncation when `_camera_x` exceeds 255 (UINT16 → INT16 conversion of value > 32767, or eventual UINT8 cast).
**Why it happens:** `_camera_x` is declared `UINT16` (PlatformerVisitor.kt:1195); the formula casts via `(INT16)` for signed subtraction, then truncates to UINT8 for the metasprite call. With `_camera_x` values < 8192 and `_playerX >> 4 < 8192`, the math is safe in practice — but SDCC may still emit warnings.
**How to avoid:** Plan 12.3 metasprite-offset task should verify the emission's SDCC output (CI build log). If warnings appear, switch to `(UINT8)((_playerX >> 4) - _camera_x)` (drop the explicit INT16 casts) — the subtraction of two UINT16s produces UINT16, the UINT8 cast is well-defined for the screen-visible range (0..255).
**Warning signs:** Build log contains SDCC warning 158 or 207; UAT shows player metasprite at wrong screen X.

### Pitfall 6: Walk-cycle binders unset → silent skip vs configurable default
**What goes wrong:** If the user calls `platformerInput { walkSpeed(64) }` without `walkFrameIdx(...)` or `threeFrameCounter(...)`, the visitor SKIPS walk-cycle emission per D-03. But anchor 4 (Plan 12-22) WILL fail because `_walkFrameIdx` stays at 0.
**Why it happens:** D-03's "no magic-string fallback" decision is correct (avoids generating `_walkFrameIdx` references when the variable doesn't exist), but the platformer-template DSL must declare the binders or anchor 4 stays RED.
**How to avoid:** PlatformerTemplate.kt's NEW `platformerInput { }` block (added per D-16) MUST include the two AssignableVar binders. Plan 12.3 metasprite-walk-cycle task and Plan 12.3 PlatformerTemplate cleanup task are COUPLED: cleanup must add `walkFrameIdx(walkFrameIdx); threeFrameCounter(threeFrameCounter)` to the new `platformerInput { }` block.
**Warning signs:** Anchor 4 re-shoot stays RED.

1. **Walk-cycle skip semantics — what happens at runtime when the binders are unset but the metasprite render still indexes `_walkFrameIdx`?**
   - What we know: D-03 says visitor SKIPS emission when binders unset. The DSL still declares `_walkFrameIdx` in the metasprite block via `idx(walkFrameIdx)`. So the variable exists but never gets incremented — player stuck on frame 0 (which is the current Phase 12 Plan 12-22 RED state).

2. **Order of GenreVisitorResult.frameOps merging — does `visitCamera`'s splice land AFTER `visitPhysics`'s splice in the final scene-frame body?**
   - What we know: `GBDKPipelineV2` invokes genre visitors in registration order (ServiceLoader). The `frameOps: Map<String, List<ScriptOp>>` from each visitor is concatenated into the scene's frame block.
   - What's unclear: Whether the existing pipeline guarantees `visitPhysics` runs BEFORE `visitCamera` (D-05 emission order). The order matters only if the input emission lives in `frameOps` rather than inline in `buildTilemapPhysicsUpdateFunction`.
   - Recommendation: Prepend input emission INSIDE `buildTilemapPhysicsUpdateFunction` body (so the order is settled at function build time), THEN let `visitCamera.frameOps` add the `platformer_camera_update();` call to the scene frame. The merged frame block becomes: `[input is INSIDE physics_update()]; platformer_physics_update(); platformer_camera_update(); /* user moveMetasprite + dpad ops */`. This honors D-05 by construction.

3. **Should `gameUsesPlatformerInput` predicate participate in the camera-update-call gating?**
   - What we know: `buildTilemapCameraUpdateFunction` is gated on `gameUsesTilemapCollision`. The new `frameOps` call splice can use the same gate.
   - What's unclear: Whether games could in theory have `platformer_input` registered WITHOUT `tilemap_collision` (e.g., abstract-physics platformer using input only).
   - Recommendation: Gate the `platformer_camera_update();` call on `gameUsesTilemapCollision` (matches the function-body gate). The input emission gates on `gameUsesPlatformerInput`. The two predicates can fire independently — no cross-coupling.
