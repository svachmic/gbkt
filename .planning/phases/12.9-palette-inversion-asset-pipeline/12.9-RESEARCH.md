## png2asset Palette Emission Shape (D-02/D-03)

### Reference confirmation

From `/Users/michalsvacha/gbdk/examples/cross-platform/platformer_template/gen/gb/src/World1Tileset.h`:
```c
#define World1Tileset_PALETTE_COUNT 4        // 4 sub-palettes
#define World1Tileset_COLORS_PER_PALETTE 4   // 4 colors per sub-palette
#define World1Tileset_TOTAL_COLORS 16        // 4×4=16 total
extern const palette_color_t World1Tileset_palettes[16];  // array of 16 entries
```

`set_bkg_palette(first, nb_palettes, data)` — `nb_palettes` = 4 (sub-palette count), NOT 16 (array length).

### For D-02 macro emission

The `_zone_<id>_tileset_PALETTE_COUNT` macro must equal the number of SUB-PALETTES (e.g., 4), not the array length (16). The `extern` declaration must use the array length (16). Both values are present in png2asset's emitted C header OR can be derived:
- Array length: parse `[N]` from `const palette_color_t _zone_<id>_tileset_palettes[N]` in the emitted `.c`.
- Sub-palette count: `N / 4` (GBC hardware constant: 4 colors per sub-palette).

OR: parse png2asset's `PALETTE_COUNT` define directly from the emitted `.h` if png2asset also writes an `.h` (the reference `World1Tileset.h` is png2asset-emitted, but gbkt uses `synthesizeHeader()` to write its own custom `.h`). Since gbkt does NOT use png2asset's native `.h` (it synthesizes its own), the value must be derived from the emitted `.c`.

**Recommended implementation for D-03**: Parse `paletteCount` from the png2asset `.c` output:
```kotlin
val paletteArrayDim = parsePaletteArrayDim(outputC, "_zone_${sanitized}_tileset_palettes")
val subPaletteCount = paletteArrayDim / 4  // GBC: 4 colors per sub-palette
```
Pass both to `synthesizeHeader(... paletteArrayDim, subPaletteCount)`.

The current `_zone_world1Area1Zone_tileset.c` (at HEAD, without flag) shows:
```c

```
Array dim = 4. With `-keep_palette_order` active: array dim = 16 (matches reference). This confirms the flag changes the emission shape.

## `<gb/cgb.h>` Include Availability — D-01 Landmine Resolution

**Critical finding (confirmed at HEAD — NOT mentioned in CONTEXT.md):**

`SceneVisitor`'s D-01 `set_bkg_palette(...)` call will be emitted as `CRawCode` into `bank1.c`. The `set_bkg_palette` function is declared in `<gb/cgb.h>`. The `bank1.c` include logic in `GBDKPipelineV2.buildSceneFile()` adds `<gb/cgb.h>` only when `gameIR.hasPaletteOps()` returns true — which checks for `SetPalette` IR ops in scene scripts.

The platformer-template game has NO `SetPalette` IR ops → `hasPaletteOps()` returns `false` → `<gb/cgb.h>` is NOT included in `bank1.c`.

**Resolution**: `<gbdk/platform.h>` (included by `<gb/cgb.h>` is transitively available because the zone tileset headers `_zone_<id>_tileset.h` include `<gbdk/platform.h>`, and `platform.h` includes `<gb/cgb.h>` (confirmed in `/Users/michalsvacha/gbdk/include/gbdk/platform.h:6`). Since `bank1.c` always includes zone tileset headers when zones are present, `set_bkg_palette` and `palette_color_t` are ALREADY available via the transitive chain:

`bank1.c` → `_zone_<id>_tileset.h` → `<gbdk/platform.h>` → `<gb/cgb.h>`

**Conclusion**: NO changes to `buildSceneFile()` include logic are needed for the D-01 codegen change. The `set_bkg_palette` call compiles without additional include directives.

## Common Pitfalls

### Pitfall 1: `PALETTE_COUNT` macro = sub-palette count, NOT array length
**What goes wrong**: Emitting `#define _zone_<id>_tileset_PALETTE_COUNT 16` (array length) instead of `4` (sub-palette count) causes `set_bkg_palette(0u, 16u, data)` to try uploading 16 sub-palettes (64 colors) from a 16-entry array — reads OOB palette RAM, producing garbage colors.
**Prevention**: Parse `N` from `_tileset_palettes[N]` in emitted C, then set `PALETTE_COUNT = N / 4`.

### Pitfall 2: 32×32 fill_bkg_rect rationale must be commented
**What goes wrong**: Future reader sees `32u, 32u` hardcoded and changes it to match the reference `ShowCentered` which uses `DEVICE_SCREEN_WIDTH, DEVICE_SCREEN_HEIGHT`. This reintroduces the 0F artifact.
**Prevention**: Inline comment: `// GBC BG plane = 32x32 tiles (LCDC.3); camera scroll exposes columns 20-31`.
**Warning sign**: Reference `ShowCentered` uses `DEVICE_SCREEN_WIDTH` — different game (no camera scroll). Do NOT follow the reference for this change.

### Pitfall 3: W3 re-enable `World1TilesetGrassEncodingTest` while assertions are still RED
**What goes wrong**: If W3 removes `@Disabled` before W4 lands `-keep_palette_order`, the test fails on CI and blocks subsequent plans.
**Prevention**: W3 commits the test with `@Disabled` REMOVED. The test FAILS (RED) against current codegen by design (per `feedback_quality_over_shortcuts` + established RED→GREEN cadence). W4 landing the flag makes it GREEN. This is the intended RED→GREEN proof sequence.

### Pitfall 4: ZoneLoadSetBkgPaletteEmissionTest requires zone IR fixture with tilesetPath
**What goes wrong**: A test using `zone("play")` without `tilesetPath` (LEGACY path) gets no `set_bkg_palette` emission (by design), and the test passes vacuously.
**Prevention**: The synthetic `ZoneIR` fixture must have `tilesetPath = "some/path.png"` (not null) to trigger the NEW-path branch in SceneVisitor.

### Pitfall 5: Parallel `./gradlew clean` invocations
**What goes wrong**: D-15 sweep runs as two separate `clean` commands → Kotlin daemon collision corrupts both builds.
**Prevention**: Single chained command per `feedback_no_parallel_gradle_clean`: `./gradlew clean :breakout:buildRom :simple-physics:buildRom :metasprites:buildRom :metasprites-stress:buildRom :banks:buildRom :pong:buildRom :platformer-template:buildRom`.

### Pitfall 6: `gameIR` not accessible in SceneVisitor for GBC-gating
**What goes wrong**: `SceneVisitor.visit()` may not have `gameIR` in scope; adding `CRawCode("set_bkg_palette...")` as a simple string with `GbcTarget` gating requires `gameIR` in the visitor call site.
**Prevention**: Check `SceneVisitor.visit()` signature before coding. If `gameIR` is not a parameter, thread it through or access `gameIR.config.gbcTarget` at the call site in `GBDKPipelineV2.buildSceneFile()` (which already has `gameIR` in scope) and pass the GBC flag as a new parameter.

#### Finding RC-1c: The inversion color chain (why title renders clean but gameplay inverts)

**Confidence:** HIGH — confirmed by reading palette values in generated `.c` files.

Execution sequence at runtime:
1. `main()` line 698: `set_bkg_palette(0u, 1u, _gbkt_default_bg_pal)` — uploads 4 DMG-gray shades `{0x7FFF, 0x56B5, 0x294A, 0x0000}` (white→dark) to BG palette RAM slot 0.

### New Common Pitfalls (Round 2)

#### Pitfall 7: Confusing `SceneVisitor` zone-load path with `setup_current_level()` path
**What goes wrong**: Planner adds palette upload to `SceneVisitor` and declares fix complete, but gameplay zones go through `setup_current_level()` (not SceneVisitor), so the gameplay inversion persists.
**Prevention**: The 08b fix is in `GBDKPipelineV2.buildSetupCurrentLevelFunctionIfNeeded()`, NOT in `SceneVisitor`. W5's `SceneVisitor` fix was correct for title/nextLevel but BLIND to gameplay.
**Warning sign**: If `gameplay_enter()` in `bank1.c` is still just `{ setup_current_level(); }` after the 08b fix, the palette upload is NOT happening via SceneVisitor. Verify `main.c` per-zone cases instead.

#### Pitfall 8: Testing jump with J_B (wrong button)
**What goes wrong**: Jump uses `J_A` and `J_UP`. Pressing `J_B` does nothing for jump. MCP agent may repeat the same mistake as the G3 gate.
**Prevention**: In 08a and 08c, explicitly use `emulator_step(frames=1, buttons=["A"])` or `buttons=["UP"]`. Do NOT use `buttons=["B"]`. The metadata controls for gameplay list only LEFT/RIGHT — do not infer jump is broken from the metadata.

#### Pitfall 9: Jump assertion needs rising-edge sequencing
**What goes wrong**: `button_pressed(J_A)` returns true ONLY on the frame J_A transitions from not-held to held. If the MCP agent sends A every frame continuously, `button_pressed` is true only on frame 1; the grounded guard may not pass on frame 1 (player may still be in the air from spawn). By frame 2+ when grounded, `button_pressed` is false.
**Prevention**: Sequence: N frames of no-A to ensure previous state is clean, then 1 frame of A. Specifically: `emulator_step(60, [])` to settle player on ground, then `emulator_step(1, [])` (no-A, clears prev), then `emulator_step(1, ["A"])` (rising edge while grounded).

#### Pitfall 10: `SetupCurrentLevelPaletteEmissionTest` needs `tilesetPath != null` on zones
**What goes wrong**: The palette fix is gated on `zone.tilesetPath != null` (NEW-path predicate). A synthetic test zone with `tilesetPath = null` will not emit `set_bkg_palette` even after the fix.
**Prevention**: The test fixture must create a `ZoneIR` with `tilesetPath = "some/path.png"` (non-null), identical to the `ZoneLoadSetBkgPaletteEmissionTest` fixture constraint.

- Result: the composited frame shows gameplay BG at scroll offset `_camera_x` — world1 tiles in the off-screen columns become visible, including the `0F` tile.

This is the frame the user captures as "01-nextlevel-flip."

#### Finding D1-c: The SceneVisitor's DISPLAY_ON is the architectural culprit

**Confidence:** HIGH — confirmed by reading `SceneVisitor.kt` lines 292-299.

```
[SceneVisitor zone-load block] = set_bkg_data + _bkg_tiles_load_banked + set_bkg_palette + DISPLAY_ON
[User-authored enter ops]      = hide_sprites + move_bkg + fill_bkg_rect + centered_load + DISPLAY_ON
```

The first `DISPLAY_ON` creates a visible frame before the `fill_bkg_rect` clear. The 32×32 clear from W6 is correct in COVERAGE but runs in the WRONG POSITION — after LCD is already on.

### New Common Pitfalls (Round 3)

#### Pitfall 11: Defect 1 fix must prevent the FIRST DISPLAY_ON, not just add a second clear
**What goes wrong**: Adding another `fill_bkg_rect` call after the existing one (thinking "more coverage") doesn't fix the root cause — the first `DISPLAY_ON` from SceneVisitor fires before the clear. Adding a pre-DISPLAY_ON clear is the only solution.
**Prevention**: The fix modifies WHEN `DISPLAY_ON` fires in `nextLevelScene_enter`, not how much the clear covers.

#### Pitfall 12: Defect 2 default sprite palette has same DMG-grayscale as default BG palette
**What goes wrong**: Using the same 4-entry grayscale array for both BG and sprite palettes may look incorrect if the spritesheet uses a different authored palette. For the duck, this is acceptable (provides a visible palette); for other games, this may produce grayscale sprites that should be colored.
**Prevention**: Document `_gbkt_default_sprite_pal` as a TEMPORARY correctness fix; authored sprite palette wiring is deferred to Phase 13 (CONTEXT "Sprite-palette wiring symmetry").
**Warning sign**: If the spritesheet has `_PALETTE_COUNT > 1` (multiple sub-palettes), the default 4-entry single sub-palette will be insufficient. For the duck (single sub-palette), it's correct.

#### Pitfall 13: Defect 3 probe offset change affects ALL platforms using `buildHorizontalProbe`
**What goes wrong**: `buildHorizontalProbe` is used by `buildTilemapPhysicsUpdateFunction` which is called for ALL games that use `gameUsesTilemapCollision(gameIR) == true`. Changing `halfW` to `halfW + 1` affects all platformer games, not just platformer-template. Existing tests may assert `+ 4u` and fail.
**Prevention**: Update all affected emission tests (`TilemapCollisionEmissionTest`, any other test asserting horizontal probe offset). The change is CORRECT for all callers — the reference uses `halfW + 1` universally.

#### Pitfall 14: Defect 4 spawn_y for world2 must be determined via MCP runtime, not guessed
**What goes wrong**: Setting spawn_y = 40 (reference value) may place the player in sky for world2, causing a long fall before landing. Setting it to a value still inside underground causes the same bug.
