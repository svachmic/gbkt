## Implementation Decisions

### Area 1 — set_bkg_palette codegen contract

- **D-01: Insertion slot — AFTER `_bkg_tiles_load_banked`, BEFORE `DISPLAY_ON`.**
  Per-zoneRef emission order in `SceneVisitor.kt:185-275` becomes:
  `set_bkg_data` → `_bkg_tiles_load_banked` → `set_bkg_palette` →
  `DISPLAY_ON`. Matches reference `platformer_template/src/level.c:91-94`
  (in-level tileset-load pattern, `set_native_tile_data` → `setBKGPalettes`).
  Lowest blast radius — single statement append to the existing
  `pixelLoad + listOf(...)` flatMap. GBC-gated (mirrors existing
  `_gbkt_default_bg_pal` write at `GBDKPipelineV2.kt:4701` —
  `gameIR.config.gbcTarget != GbcTarget.DMG`).

- **D-02: Palette count argument = `_zone_<id>_tileset_PALETTE_COUNT` macro.**
  Emitted shape: `set_bkg_palette(0u, _zone_<sanitized>_tileset_PALETTE_COUNT,
  _zone_<sanitized>_tileset_palettes);`. This macro becomes the
  single-source-of-truth for the per-zone palette count, set by
  `ConvertZoneTilesetsTask` from png2asset's actual emitted palette count
  (the array dim depends on PNG PLTE — could be 1, 4, or 8 sub-palettes
  depending on the source PNG). Reject hardcoded `1u` (too narrow — only
  one sub-palette uploaded), hardcoded `8u` (reads garbage past array
  bounds when source has fewer palettes), and hardcoded `4u` (assumes
  16-color array; may not match actual emission).

- **D-03: Bundle `-keep_palette_order` re-activation + .h header additions
  into ONE W-plan in `ConvertZoneTilesetsTask`.** Single plan:
  (a) re-append `-keep_palette_order` to png2asset args list at
  `ConvertZoneTilesetsTask.kt:288-298` gated by retained `isIndexedPng()`
  helper at kt:480, (b) emit `extern const palette_color_t _zone_<id>_tileset_palettes[N];`
  in the synthesized `_zone_<id>_tileset.h` header, (c) emit
  `#define _zone_<id>_tileset_PALETTE_COUNT M` macro alongside existing
  `_zone_<id>_tileset_count` (tile count) at kt:399 region. All three
  are part of the same asset-pipeline boundary — splitting them would
  leave header gaps until both plans land.

- **D-04: JVM emission invariant in `platformer-template` scene fixture.**
  New test `ZoneLoadSetBkgPaletteEmissionTest` (or planner-picked name)
  lives in `gbkt-examples/platformer-template/src/test/...` mirroring W4
  12.8 `World1TilesetGrassEncodingTest` pattern. Pins emission against the
  actual game IR — anchors against a real scene that ships. Locks call
  shape + GBC-gating + ordering for at least one indexed-PNG zone
  (titleZone, world1Area1Zone, world1Area2Zone, world2Area1Zone, or
  nextLevelZone). Companion test re-enables `World1TilesetGrassEncodingTest`
  (currently `@Disabled`).

### Area 2 — nextLevel transition diagnostic

- **D-05: First diagnostic step is reading the generated C for
  `nextLevel_enter`.** Read `gbkt-examples/platformer-template/build/gbkt/generated/bank1.c`
  to verify the expected emission order (hide_sprites_range, move_bkg,
  fill_bkg_rect, _bkg_tiles_load_banked, DISPLAY_ON). Cheapest evidence;
  rules out codegen as defect surface before any runtime probe.

- **D-06: Second diagnostic step (if codegen is correct) is MCP runtime
  variable trace.** Boot ROM via MCP, step into nextLevel scene, capture:
  (a) BCPS/BCPD palette dump, (b) VRAM tile-data snapshot, (c) sprite
  hide state (OAM), (d) LCDC reg, (e) SCX/SCY scroll regs. Provides
  runtime evidence to distinguish "codegen ran but VRAM still stale" vs
  "codegen didn't run".

- **D-07: R-03 acceptance uses reference-screenshot comparison instead of
  programmatic pixel-diff threshold.** Reject 10% VisualDiff (12.5
  precedent) — too tolerant of palette variance. Reject distinct-tile
  count — structurally meaningful but doesn't catch palette regressions.
  Compare anchor-5 frames against a curated **reference set** at the
  binding gate.

### Area 3 — 0F artifact (reframed)

- **D-09: First step is referencing Phase 12.7 anchor-5 captures to
  establish pre-existing vs induced.** Read
  `.planning/phases/12.7-player-levitating-physics-codegen/evidence/uat-screenshots/anchor-5/*.png`.
  If "0F" appears there too → PRE-EXISTING (and predates 12.8). If absent
  → INDUCED. Free evidence — PNGs already committed.

- **D-10: REFRAME — 0F artifact + nextLevel BG-clear-defect are the SAME
  root cause.** Investigation surfaced that `0x0E` and `0x0F` are real BG
  tile indices in `_zone_world1Area1Zone_tilemap` (gameplay tilemap). The
  "0F" the user sees in anchor-5/01-02 captures is residual gameplay BG
  tilemap data persisting through the nextLevel scene transition. There is
  no runtime printf/gotoxy — those are tile cells with the wrong content
  surviving from world1Area1 because `fill_bkg_rect` doesn't cover the
  full BG plane. **R-03 (nextLevel transition) + R-04 (0F artifact)
  collapse into ONE defect class.**

- **D-11: Fix is `fill_bkg_rect(0u, 0u, 32u, 32u, 0u)` with named
  constant explaining hardware semantics.** Change
  `PlatformerExtensions.kt:860-862` from
  `fill_bkg_rect(0u, 0u, DEVICE_SCREEN_WIDTH, DEVICE_SCREEN_HEIGHT, 0u)`
  to `fill_bkg_rect(0u, 0u, 32u, 32u, 0u)`. 32×32 is the GBC BG hardware
  addressable region (LCDC.3 selects 256×256 pixel = 32×32 tile area),
  not platformer-template-specific — encode this rationale via a named
  constant or comment so future readers don't misread it as overfitting.
  Reject DSL config knob: violates declarative principle (don't surface
  low-level VRAM math); reject leaving 20×18 (insufficient coverage,
  proven by 0F evidence). Same fix resolves both R-03 + R-04.

- **D-12: If 0F is pre-existing AND in palette-wiring blast radius (per
  D-10 reframe, it IS), fix in 12.9.** SPEC R-04 said "if induced or in
  palette-wiring blast radius, fix as part of the bundle" — the reframe
  puts it in scope. NO seed file drop. R-04 acceptance becomes "anchor-5
  re-shoot shows no 0F text artifact in any quadrant after the fill_bkg_rect
  expansion".

<specifics>
## Specific Ideas

- **Reference `level.c:91-94` for D-01 ordering** — the in-level
  tileset-load flow is `set_native_tile_data → setBKGPalettes →
  set_bkg_tiles`. Gbkt's emission becomes `set_bkg_data →
  _bkg_tiles_load_banked → set_bkg_palette → DISPLAY_ON` which differs
  in that palette comes AFTER tilemap load (not between tile data and
  tilemap). The difference doesn't affect runtime semantics because
  BCPS/BCPD is independent of VRAM tile/map memory.
- **Reference `common.c:43-66` (ShowCentered) for LevelCardSceneBuilder** —
  the reference also emits `hide_sprites_range + move_bkg + setBKGPalettes
  + set_native_tile_data + fill_bkg_rect + set_bkg_tiles + DISPLAY_ON`.
  Our LevelCardSceneBuilder.materialize() relies on the SceneVisitor's
  zone-load prelude (which D-01 now adds palette to) — by the time the
  user-authored enter block runs, BCPS/BCPD is already populated. No
  additional palette upload needed inside the centered-card emission.
- **D-11 `32u, 32u` is a named hardware constant in disguise** — the GBC
  LCDC.3 register selects either `0x9800-0x9BFF` (32x32 tile map area 0)
  or `0x9C00-0x9FFF` (area 1) — both 1024 bytes = 32x32 tiles. This is
  the hardware ceiling; 32x32 cannot overflow into other VRAM regions.
- **Reference platformer_template ROM** at `/Users/michalsvacha/gbdk/examples/cross-platform/platformer_template/`
  — D-08 reference-screenshot source. If `make` succeeds + ROM boots in
  MCP, we have a known-good visual baseline. If make fails (toolchain
  drift), fall back to D-08's alternative: curated baseline PNGs from
  Phase 12.7 captures + design intent.
- **"0F" reframe was a key discovery during discussion** — initial
  hypothesis was hex-render of a runtime variable. Codebase scout
  ruled it out (no printf/gotoxy in generated C); grep of
  `_zone_world1Area1Zone_tilemap.c` showed `0x0E`/`0x0F` as actual BG
  tile indices. The visible "0F" text is BG tile artwork, not runtime
  text rendering. This reframe collapsed R-03 + R-04 into one defect
  class.
