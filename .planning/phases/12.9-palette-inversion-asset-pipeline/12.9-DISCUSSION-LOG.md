### Q4 (after reframe): Same root cause as nextLevel BG-clear?

| Option | Description | Selected |

**User's choice:** Reframe as nextLevel BG-clear gap
**Notes:** Key discovery during discussion: `0x0E`/`0x0F` are real BG tile indices in world1Area1Zone tilemap; "0F" is BG tile artwork, not runtime text. fill_bkg_rect(0,0,20,18) only covers screen viewport (DEVICE_SCREEN_WIDTH/HEIGHT), not the 32×32 GBC BG plane — residual gameplay tiles persist outside the viewport.

### Q5 (post-reframe): fill_bkg_rect coverage fix?

| Option | Description | Selected |
|--------|-------------|----------|
| Expand to 32x32 (full BG tilemap) | Hardware-addressable region. | |
| Reset SCX/SCY to 0 + clear viewport | Scroll snap + 20×18 fill. | |
| Author-side responsibility | DSL user provides custom enter. | |

**User's choice:** Other — "Expanding to 32x32 is recommended but isn't that overfitting to the source material? Shouldn't then this be somehow configurable? But then I don't want to surface too much of low level logic."
**Notes:** Thinking-partner moment. Resolved: 32×32 is the GBC BG hardware addressable region (LCDC.3 selects 256×256 pixel = 32×32 tile area), not platformer-template-specific. Filling 32×32 = filling the entire hardware-addressable BG plane. Configurable knob would violate declarative principle.
