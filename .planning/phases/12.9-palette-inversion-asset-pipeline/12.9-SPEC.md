## Background

Phase 12.8 attempted to close G3 by activating `-keep_palette_order` at the asset-pipeline boundary (`ConvertZoneTilesetsTask.kt:288-298`) but produced **worse** visual output (full color inversion) and was REVERTED post-close. The A6 audit confirmed the root cause: per-zone palette arrays are emitted by codegen but **never uploaded to BG palette RAM**.

Specifically:
- `ConvertZoneTilesetsTask` emits `const palette_color_t _zone_<id>_tileset_palettes[4]` arrays into `_zone_<id>_tileset.c` for every indexed-PNG zone tileset (confirmed in 5 generated files: titleZone, world1Area1Zone, world1Area2Zone, world2Area1Zone, nextLevelZone).
- `GBDKPipelineV2.buildHomeFile()` uploads only `_gbkt_default_bg_pal` once at main() startup via `set_bkg_palette(0u, 1u, _gbkt_default_bg_pal);` (GBC-gated).
- `SceneVisitor`'s zone-load codegen emits `set_bkg_data → _bkg_tiles_load_banked → DISPLAY_ON` per zoneRef but never `set_bkg_palette` for the per-zone palette array.
- Result: indexed tile bytes reference palette indices that resolve against stale `_gbkt_default_bg_pal` (DMG-cream) instead of the authored RGB triples in the PNG's PLTE chunk. After Phase 12.8 W3 added `-keep_palette_order` alone, indices 0-3 reference index 0 = near-black per PLTE, which the cream-loaded BG palette RAM then renders as inverted colors.
