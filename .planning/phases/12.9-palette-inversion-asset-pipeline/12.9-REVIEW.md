# Phase 12.9: Code Review Report

**Reviewed:** 2026-06-02
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

Phase 12.9 lands five defect fixes (D1–D4 + W4/W5/W6) across three modules. The fixes
themselves are correct for the path that shipped (the indexed-PNG, GBC, platformer-template
ROM that drove the G3 verdict). The CLiteral/CIntLiteral discipline is respected (D3 keeps the
`CIntLiteral(0)` velocity guard untouched; D4 is a raw assignment), the D4 grounded-symbol
resolution correctly mirrors `PlatformerVisitor`'s config-driven resolution (no magic string), and
the D2a `-keep_palette_order` gate is shared via `PngUtils.isIndexedPngShared` (no duplication).

The dominant risk is a **gate mismatch between the codegen palette-upload calls and the
asset-pipeline palette-symbol synthesis**. The `set_sprite_palette` (D2b) and per-zone
`set_bkg_palette` (W5/RC-1) calls are emitted on a *metasprite-present* / *tilesetPath-present*
gate, while the `<id>_palettes` / `_zone_<id>_tileset_palettes` symbols they reference are only
emitted when the source PNG is **indexed**. Any GBC game with a non-indexed sprite/zone PNG will
hit an SDCC "undefined identifier" link error. The platformer-template ships indexed PNGs, so
this is latent — but it is a correctness regression for the general case the framework claims to
support.

Secondary concerns: the D1 trailing-`DISPLAY_ON` heuristic is a brittle substring match, and the
D3 horizontal-probe fix is a hardcoded `halfW + 1` patch at one call site that diverges from the
foot/head probes (which still derive from the un-corrected `halfW`).

## Critical Issues

### CR-01: `set_sprite_palette` (D2b) references a symbol that does not exist for non-indexed metasprite PNGs

**Status: FIXED in gap-closure 12.9-12.**

**File:** `gbkt-backend-gbdk/.../codegen/pipeline/GBDKPipelineV2.kt:4957-4963`
(emission), `gbkt-gradle-plugin/.../ConvertSpritesTask.kt:347,392-394` (gate)

**Issue:** `buildMetaspriteSpritePaletteStatements` emits
`set_sprite_palette(${slot}u, 1u, ${ms.id}_palettes);` for **every** metasprite, gated only on
`gbcTarget != DMG` and `metasprites.isNotEmpty()`. It does **not** gate on whether the
metasprite's source PNG is indexed. However, the matching `extern const palette_color_t
${stemName}_palettes[];` declaration in `ConvertSpritesTask.generateSpriteHeader` is gated on
`isIndexed` (line 392), and png2asset only emits the `_palettes[]` array for indexed PNGs (the
author acknowledges this in `ConvertZoneTilesetsTask.kt:331`). Result: a GBC game with a
non-indexed (RGB) metasprite PNG emits a `set_sprite_palette(..., player_palettes)` call whose
`player_palettes` symbol is never declared or defined → SDCC error 20 "Undefined identifier" at
link time. The platformer-template ships an indexed PNG so the shipped ROM is unaffected, but the
two gates must agree.

**Fix:** Gate the D2b emission on the same indexed-ness signal the header uses. `MetaspriteIR`
carries no indexed flag today, so either (a) thread an `isIndexed`/`hasPalette` flag onto
`MetaspriteIR` populated at IR-build time, or (b) move the `set_sprite_palette` emission into the
asset pipeline / header where the indexed check already lives, or (c) at minimum skip the
per-metasprite emission when the PNG is not indexed. Conceptually:

```kotlin
private fun buildMetaspriteSpritePaletteStatements(gameIR: GameIR): List<CStatement> {
    if (gameIR.config.gbcTarget == GbcTarget.DMG) return emptyList()
    return gameIR.metasprites
        .filter { it.hasIndexedPalette }   // NEW: only metasprites whose PNG is indexed
        .mapIndexed { slot, ms -> CRawCode("set_sprite_palette(${slot}u, 1u, ${ms.id}_palettes);") }
}
```
Note the `slot` index must still be derived consistently (filtering changes the index — assign
slots before filtering, or key the slot on the metasprite's stable index).

### CR-02: Per-zone `set_bkg_palette` references a symbol absent for non-indexed NEW-path zone PNGs

**Status: FALSE-POSITIVE — no code change required.**

`ConvertZoneTilesetsTask.synthesizeHeader` already declares
`extern const palette_color_t _zone_<id>_tileset_palettes[paletteArrayDim]` **unconditionally**
(line 620), and png2asset always emits the `_palettes[]` array for every zone PNG — the
`-keep_palette_order` flag (gated on `isIndexedPng`) only affects palette ORDER, not whether
the array is emitted. The symbol is therefore always defined at link time; the extern is always
present; SDCC error 20 does not occur. No code change is needed.

**File:** `gbkt-backend-gbdk/.../codegen/pipeline/GBDKPipelineV2.kt:2502` and
`gbkt-backend-gbdk/.../codegen/visitor/SceneVisitor.kt:296-302` (emission);
`gbkt-gradle-plugin/.../ConvertZoneTilesetsTask.kt:305,620` (gate)

**Original issue (invalidated):** The review assumed `-keep_palette_order` controlled whether
png2asset emits the `_palettes[]` array. It does not. The array is always emitted; the flag
only controls the palette entry order. The `synthesizeHeader` unconditional extern is correct.

## Warnings

### WR-01: D1 trailing-`DISPLAY_ON` heuristic is a fragile substring match

**Status: FIXED in gap-closure 12.9-12.**

**File:** `gbkt-backend-gbdk/.../codegen/visitor/SceneVisitor.kt`

**Fix applied:** Changed `it.code.contains("DISPLAY_ON")` → `it.code.trim() == "DISPLAY_ON;"` (exact
match). A comment mentioning "DISPLAY_ON" or a macro named "DISPLAY_ONCE" can no longer accidentally
suppress the inline LCD re-enable. Additionally, when the card-overdraw signal is detected
(`fill_bkg_rect(0u, 0u, 32u, 32u, 0u)` in enterOps), the (0,0) `_bkg_tiles_load_banked` tilemap-place
is now skipped — eliminating the brief top-left flash before centering. Normal zone scenes are
byte-identical (unaffected). RED→GREEN: LevelCardSceneEmissionTest tests 8+9.

### WR-02: D3 horizontal-probe fix is a hardcoded `halfW + 1` that diverges from foot/head probes

**Status: FIXED in gap-closure 12.9-12.**

**File:** `gbkt-genre-platformer/.../codegen/PlatformerVisitor.kt`

**Fix applied:** Set `halfW = hitbox.width / 2 + 1 = 5` at the derivation site (~line 525) and
reverted `CLiteral(halfW + 1)` in `buildHorizontalProbe` back to `CLiteral(halfW)`. Now:
- horizontal probes: `player_real_x ± 5u` (unchanged — G3-approved behavior preserved)
- foot/head probes: `player_real_x ± 3u` (was 2u — now matches reference HALF_WIDTH=5, inset=3)
RED→GREEN: TilemapCollisionEmissionTest WR-02 test.

### WR-03: Zone tileset header declares `palette_color_t` without including `<gb/cgb.h>`

**Status: FIXED in gap-closure 12.9-12.**

**File:** `gbkt-gradle-plugin/.../ConvertZoneTilesetsTask.kt`

**Fix applied:** Added `appendLine("#include <gb/cgb.h>")` to `synthesizeZoneTilesetHeader` (formerly
`synthesizeHeader`, promoted to `internal` top-level for testability). The zone tileset header now
mirrors `ConvertSpritesTask.generateSpriteHeader` and is self-contained. Verified by
`ConvertZoneTilesetsHeaderCgbIncludeTest` GREEN.

### WR-04: Dual-literal bank hazard in card-scene tilemap re-place (`2u`) acknowledged but unfixed

**File:** `gbkt-genre-platformer/.../dsl/PlatformerExtensions.kt:889-896`

**Issue:** The centered-card `_bkg_tiles_load_banked(2u, ...)` hardcodes bank `2u`, duplicating
the SceneVisitor's `_bkg_tiles_load_banked(2u, ...)` literal for the same zone. The comment
(lines 882-888) explicitly flags that if `BankingAnalysisPass` repacks these tilemaps to a
different bank, the two literals silently diverge and the card scene reads code/data from the
wrong bank (hang or garbage). This is a known correctness landmine deferred to "a follow-up
phase".

**Fix:** Thread the zone's allocated bank through to this emission site (via `SceneIR` metadata or
a bank-allocation lookup) so the literal is sourced from `allocateZoneBanks`, eliminating the
dual-literal divergence. At minimum, add a build-time assertion that the two bank literals for a
given zone agree.

### WR-05: `set_sprite_palette` slot index assumes metasprite-list order equals OBJ palette layout

**File:** `gbkt-backend-gbdk/.../codegen/pipeline/GBDKPipelineV2.kt:4960-4962`

**Issue:** `mapIndexed { slot, ms -> set_sprite_palette(${slot}u, 1u, ...) }` assigns OBJ palette
slot = position in `gameIR.metasprites`. There is no cross-check that the per-metasprite
`subPalette` runtime variable (`_<id>_subPalette`, GBDKPipelineV2:928-937) or the metasprite's
OAM attribute byte actually selects the same slot. If a metasprite's draw path references a
different sub-palette index than the upload slot, the character renders with another metasprite's
palette. For a single metasprite (the shipped case) slot 0 is trivially correct, but with ≥2
metasprites the coupling is unverified.

**Fix:** Assert or document that the metasprite OAM `subPalette` attribute is bound to the same
list-order index used here, or derive the slot from the metasprite's declared sub-palette rather
than its list position.

## Info

### IN-01: `parsePaletteArrayDim` silently falls back to 4 on parse failure

**File:** `gbkt-gradle-plugin/.../ConvertZoneTilesetsTask.kt:334,528-535`

**Issue:** `parsePaletteArrayDim(outputC, paletteSymbol) ?: 4` falls back to dimension 4
(PALETTE_COUNT 1) whenever the regex fails to find the array — which is exactly the non-indexed
case where the array is absent. This silent fallback is what allows CR-02 to compile the header
(emitting a bogus `[4]` extern) instead of failing fast. Once CR-02 is fixed by gating on
indexed-ness, consider making a parse-miss on a PNG that *should* be indexed a hard error rather
than a silent 4, so a png2asset behavior change is surfaced.

### IN-02: D4 grounded reset emitted as bare `0` (consistent but unsuffixed)

**File:** `gbkt-backend-gbdk/.../codegen/pipeline/GBDKPipelineV2.kt:2543`

**Issue:** `$groundedSym = 0;` emits `_grounded = 0;` (bare literal, no `u` suffix). `_grounded`
is a UINT8 assignment target, so per the Literal Emission Convention this is an unsigned-context
site that would canonically use `0u`. It is harmless (the existing sibling `$vySym = 0;` is also
bare, so the emission is internally consistent) and these are raw template strings outside the
`CLiteral`/`CIntLiteral` AST path. Noted only for convention consistency; not a bug.

### IN-03: `isIndexedPngShared` swallows all exceptions and returns `false`

**File:** `gbkt-gradle-plugin/.../PngUtils.kt:72-74`

**Issue:** The `catch (_: Exception) { false }` treats any read error (permissions, truncated file,
I/O) as "not indexed", which silently routes the file down the non-`-keep_palette_order` path. For
a genuinely indexed PNG that momentarily fails to read, this would re-introduce the very
palette-reorder box defect D2a fixes, with no diagnostic. Acceptable as a conservative default for
a build helper, but a `logger.debug`/`warn` on the failure path would aid diagnosis. (Note: this
helper has no logger; surfacing would require threading one in.)
