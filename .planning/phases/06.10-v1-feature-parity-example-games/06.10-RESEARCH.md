        config {
            cartridge = "ROM_ONLY"
            romBanks = 2
            // For GBC: gbcTarget = GbcTarget.GBC_COMPATIBLE or GBC_ONLY

        val player by actor {
            position(80, 72)
            sprite(asset("sprites/player.png")) { size(8, 16); hitbox(0, 8, 8, 8) }

        // 5. Genre system declarations (RPG, platformer, etc.)
        // 6. UI definitions (hud, menu, dialog)
        // 7. Scenes (define leaf scenes first, root scene last — avoids circular deps)
        // 8. start = titleScene.id

### Scene Ordering Pattern (Critical — Verified)
Scenes reference each other via `navigate()`. Define them in leaf-to-root order to avoid using SceneRef before definition. Break circular cycles with forward-declared `val xRef = sceneRef("x")` at the top of the game block. **All navigate() calls should use SceneRef, not strings.**

```kotlin
// Pattern used in all 3 existing examples
val titleRef = sceneRef("title")       // Forward-declare FIRST
// ... define gameover, combat, etc (they reference titleRef)
val titleScene = scene("title") { ... }  // Define last
start = titleScene.id
```

## Common Pitfalls

### Pitfall 1: Scene Circular Navigation Without Forward Refs
**What goes wrong:** `navigate(titleScene)` called before `titleScene` is defined in a scene that appears before it in the game block.
**Why it happens:** Kotlin requires values to be defined before use. Scene navigation creates a cycle.
**How to avoid:** Always add `val titleRef = sceneRef("title")` at the very top of the `game {}` block before any variable or scene definitions. Use `navigate(titleRef)` in gameover/other scenes that need to return to title.
**Warning signs:** Compiler error "Unresolved reference: titleScene" inside a `navigate()` call.

### Pitfall 2: Genre Package Not Declared as Explicit Dependency
**What goes wrong:** `character()`, `monster()`, `platformerPhysics()`, or `racing()` functions not found at compile time.
**Why it happens:** Genre packages are in the BOM constraints but NOT automatically on the classpath. Each example must explicitly declare the genre packages it uses.
**How to avoid:** Add `implementation(project(":gbkt-genre-rpg"))` (or platformer/sport) to the example's `build.gradle.kts` before using genre DSL functions.
**Warning signs:** "Unresolved reference: character" or "Unresolved reference: platformerPhysics" compiler errors.

### Pitfall 3: Module Not in settings.gradle.kts
**What goes wrong:** New example module (platformer, shmup, racer) created as directory but `./gradlew build` ignores it.
**Why it happens:** Gradle multi-project builds only include modules listed in `settings.gradle.kts`.
**How to avoid:** Add `include("gbkt-examples:platformer")` etc. to settings.gradle.kts under the `// Example games` section before creating the build.gradle.kts.
**Warning signs:** Gradle silently ignores new module directory; `./gradlew :gbkt-examples:platformer:build` fails with "Project not found".

### Pitfall 4: gbkt{} Plugin Config References Wrong Class/Property Name
**What goes wrong:** `gbkt { game("io.github.gbkt.examples.platformer.PlatformerKt::platformer") }` fails at runtime because class or property name doesn't match.
**Why it happens:** Top-level `val` properties in Kotlin compile to a class named `{FileName}Kt` with a static getter. The reference must match exactly.
**How to avoid:** Use pattern `{fully.qualified.package}.{FileNameInPascalCase}Kt::{propertyName}`. File `Platformer.kt` with `val platformer = game(...)` → `"io.github.gbkt.examples.platformer.PlatformerKt::platformer"`.
**Warning signs:** RuntimeException "Class not found" or "Property not found" during `generateC` task.

### Pitfall 5: Pong Sound — Needs to Be Added
**What goes wrong:** Breakout has sound but Pong does not. CONTEXT.md says "all examples get at least basic sound effects."
**Why it happens:** Pong was written before the audio system was fully integrated. The DSL supports `soundEffect { preset(SoundPreset.X) }` and `playSound(sfx)` in script blocks.
**How to avoid:** Add sound effects to Pong: wall bounce (HIT), paddle bounce (BUMP), scoring (COIN), win (WIN/LOSE). Follow Breakout's pattern.

### Pitfall 6: Empty Kotlin Source Directories for rpg-lite and dungeon
**What goes wrong:** `./gradlew build` succeeds because there's nothing to compile, masking that the example is incomplete.
**Why it happens:** The modules are registered in settings.gradle.kts and have empty src/main/kotlin directories.
**How to avoid:** Create source files and tests for dungeon and rpg-lite. The build.gradle.kts already references `DungeonKt::dungeon` and `RpgLiteKt::rpgLite` but those classes don't exist yet.

### Pitfall 7: SimulationContext Doesn't Simulate Every Frame Op
**What goes wrong:** Test advances 1 frame but expects a state change that requires multiple conditions in sequence.
**Why it happens:** ScriptOpInterpreter evaluates ops in order; some conditions (e.g., brick collision in Breakout) require precise initial state for all nested `whenever()` guards to fire.
**How to avoid:** Set all relevant state variables before `advanceFrames(1)`. Check Breakout tests for the careful setup pattern (setting ballDy, ballDx, positions precisely).

## State of the Art

| Old Approach | Current Approach | Impact |
|--------------|------------------|--------|
| `dpadHeld("left")` | `dpad.left.held` | Type-safe, no magic strings |
| `buttonPressed("start")` | `buttons.start.pressed` | Type-safe |
| `assign(score, literal(0))` | `score set 0` | DSL ergonomics |
| `arrayAssign(bricks, i, literal(1))` | `bricks[idx] = 1` | Kotlin-idiomatic |
| `raw("some_c_code")` | No equivalent needed | Framework handles everything |
| String-based `navigate("title")` | `navigate(titleRef)` with SceneRef | Type-safe, compile-time validated |

**Deprecated (must not appear in examples):**
- `assign()`, `varRef()`, `literal()`, `arrayAssign()`, `arrayRef()` — use delegate operators
- `dpadHeld()`, `buttonPressed()`, `dpadAny()` — use `dpad.X.held`, `buttons.X.pressed`
- `raw()` — no raw C escape hatch in example code

## Open Questions

1. **Platformer DMG/GBC structure: two modules vs build flag**
   - What we know: CONTEXT.md says "two build targets or two separate example modules"
   - What's unclear: Whether `gbkt { }` plugin supports multiple build targets in a single module
   - Recommendation: Use two separate modules (`gbkt-examples:platformer` and `gbkt-examples:platformer-gbc`). Simpler, follows existing module-per-game convention. The GBC version just adds `gbcTarget = GbcTarget.GBC_COMPATIBLE` and a palette block.

2. **RPG-lite localization — .po file DSL support** (RESOLVED)
   - What we know: CONTEXT.md says "Explorer and RPG-lite demonstrate .po file localization"
   - Resolution: Localization is file-based, not DSL-based. Place `.po` files in `res/strings/en.po`. The asset pipeline and codegen pick up string keys as `str_{context}_{id}`. No `GameBuilder.localization()` call is needed — the integration is through the file system convention (see `context/LOCALIZATION.md`). This is a locked CONTEXT.md decision and MUST be implemented, not treated as a stretch goal.

3. **Shmup scene flow design** (RESOLVED)
   - What we know: "Vertical scrolling, enemy waves, projectiles — showcases entity system + collision in action context"
   - Resolution: CONTEXT.md explicitly locks "Vertical scrolling" as a shmup requirement. Must implement background scrolling (starfield tilemap with hardware scroll via scrollY variable incremented each frame). Static background is insufficient — scrolling is a locked requirement.

4. **Racer scene flow design**
   - What we know: "Overhead view, car on scrolling track — showcases smooth movement, camera follow, tilemap scrolling"
   - What's unclear: Whether the `racing()` DSL from gbkt-genre-sport is the right tool, or if a simpler actor-based racer would be more illustrative
