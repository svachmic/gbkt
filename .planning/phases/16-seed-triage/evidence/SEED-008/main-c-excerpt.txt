--- ANALYSIS ---

The VRAM allocator uses a shared monotonic counter across actors and metasprites:
- Player (actor) sprites: start at slot 0, use 2 slots → occupies 0..1
- Elephant metasprite: starts at slot 2 (after player) → occupies 2..(2+count-1)
- Tiger metasprite: starts at 2+elephantCount → occupies contiguously after elephant

NO two set_sprite_data calls start at slot 0. The Route A fix (shared monotonic VRAM
allocator) is implemented: GBDKPipelineV2.kt emits actor tiles first, then metasprite
tiles continuing from where actors left off.

The original defect (two independent nextTile=0 counters) would have produced:
  set_sprite_data(0u, 2u, sprites_player_tiles);         <- slot 0
  set_sprite_data(0u, <elephantCount>, elephant_tiles);  <- COLLIDES at slot 0 (BUG)

PROPOSED DISPOSITION: VERIFIED-ALREADY-FIXED
Evidence basis: scoped generated-C inspection in metasprites-stress main() (which exercises
the actor + metasprite coexistence path not present in the simpler metasprites example).
The shared monotonic VRAM allocator (Route A from seed) is confirmed present in generated C.
