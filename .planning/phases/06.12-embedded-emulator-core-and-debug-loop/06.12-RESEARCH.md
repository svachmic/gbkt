## Summary

Phase 06.12 embeds Coffee-GB (a pure-JVM Game Boy emulator written in Java/Kotlin) as a new `gbkt-emulator` module, replacing the fire-and-forget mGBA process launcher. The phase introduces three tightly-coupled deliverables: (1) a `GbEmulator` facade wrapping the Coffee-GB `Gameboy` class with a clean lifecycle API; (2) a Swing emulator window with developer controls and a LogCat-style debug log panel; (3) updated Gradle tasks (`runEmulator`, `debugEmulator`, `emulatorTest`) that use the embedded emulator instead of external processes.

The central complexity is the debug log mechanism. GBDK's `EMU_printf` macro emits a specific instruction sequence into ROM — `ld d,d` (opcode 0x52) followed by a jump and structured payload bytes — which Coffee-GB does not natively intercept (it executes `ld d,d` as a normal no-op). The phase must hook into Coffee-GB's CPU execution at the opcode level to detect this sequence and route the formatted string to the log file and LogCat panel. Source map correlation (already generated by `SourceMapCollector`) turns raw C line numbers into Kotlin DSL file:line references.

The headless mode (for CI and Claude-in-the-loop debugging) runs the emulator on a daemon thread with a null `Display`, captures `EMU_printf` output to `build/gbkt/logs/debug.log`, and exposes `getDebugLog()` on the `GbEmulator` interface. The Swing window and log viewer are optional layers on top of the same headless core.

**Primary recommendation:** Build `GbEmulator` headless-first (plain Coffee-GB `Gameboy` loop on a thread), then add Swing display and log viewer as separate plans. This ensures CI works before any GUI work begins and keeps plans small enough to complete without context truncation.

### Pattern 1: Coffee-GB Lifecycle and Threading

**What:** Coffee-GB's `Gameboy` class implements `Runnable`. The canonical integration pattern is:
1. Construct `Gameboy(configuration)` with a `GameboyConfiguration`
2. Call `gameboy.init(eventBus, serialEndpoint, console)` to inject dependencies
3. Subscribe to `DmgFrameReadyEvent` / `GbcFrameReadyEvent` on the EventBus to receive pixel data
4. Run `gameboy.run()` on a dedicated daemon thread — it blocks until `gameboy.stop()`
5. For headless: inject `EventBus.NULL_EVENT_BUS`, no-op `Display`, no-op `Console`
6. For frame stepping: call `gameboy.tick()` in a controlled loop instead of `gameboy.run()`

**Key API (verified from GitHub source):**
```kotlin
// Gameboy.java — all constructors and public methods confirmed
class Gameboy(configuration: GameboyConfiguration) : Runnable, Serializable, Closeable {
    fun init(eventBus: EventBus, serialEndpoint: SerialEndpoint, console: Console)
    fun run()            // blocks; main emulation loop
    fun tick(): Boolean  // single tick; returns true if frame completed
    fun pause()
    fun resume()
    fun isPaused(): Boolean
    fun stop()
    fun close()          // flush battery saves

    // Component access
    fun getAddressSpace(): AddressSpace
    fun getCpu(): Cpu
    fun getGpu(): Gpu
    fun getSound(): Sound
    fun getSpeedMode(): SpeedMode

    // Save states
    fun saveToMemento(): Memento<Gameboy>
    fun restoreFromMemento(memento: Memento<Gameboy>)
}
```

**Frame rendering flow (verified from SwingDisplay.java):**
- Coffee-GB's GPU calls `Display.putDmgPixel(int color)` or `Display.putColorPixel(int gbcRgb)` for each pixel
- When a complete frame is ready, `Display.frameIsReady()` posts `DmgFrameReadyEvent` or `GbcFrameReadyEvent` via EventBus
- The `SwingDisplay` subscribes to these events; convert pixel data to RGB int array, call `BufferedImage.setRGB(...)`
- The `GbDisplayPanel` implementation in this phase follows the same pattern

**Example — headless GbEmulator:**
```kotlin
class CoffeeGbEmulator(private val config: EmulatorConfig) : GbEmulator {
    private val debugLog = mutableListOf<DebugLogEntry>()
    private lateinit var gameboy: Gameboy
    private var emulatorThread: Thread? = null

    override fun start() {
        val rom = Rom.of(config.romFile)
        val gbConfig = GameboyConfiguration.Builder().rom(rom).build()
        gameboy = Gameboy(gbConfig)

        val eventBus = EventBusImpl()
        if (!config.headless) {
            // subscribe display events
        }
        gameboy.init(eventBus, NullSerialEndpoint, NullConsole)

        emulatorThread = Thread(gameboy, "gbkt-emulator").apply {
            isDaemon = true
            start()
        }
    }

    override fun stop()    = gameboy.stop()
    override fun pause()   = gameboy.pause()
    override fun resume()  = gameboy.resume()
    override fun stepFrame() { gameboy.tick() }
    override fun getDebugLog(): List<DebugLogEntry> = debugLog.toList()
    override fun getMemory(): AddressSpace = gameboy.getAddressSpace()
}
```

### Pattern 2: EMU_printf / ld d,d Interception

**What the trap is:**
GBDK's `EMU_printf` macro emits this sequence into the compiled ROM (verified via GBDK docs and gbdev.gg8.se wiki):
```assembly
ld d, d          ; opcode 0x52 — trap signal (no-op on hardware)
jr .end          ; opcode 0x18, followed by relative offset
dw $6464         ; marker bytes: 0x64, 0x64 ("dd")
dw $0200         ; marker bytes: 0x02, 0x00
; format string (null-terminated) follows
.end:
```

- Opcode `0x52` is `ld d, d` — a harmless no-op on real hardware and unhooked emulators
- The `jr` skips over the payload so execution continues normally after the debug message
- Supporting emulators detect the `ld d, d` opcode, peek at the next bytes, verify the `$6464` signature, and read the format string from memory at HL (GBDK convention: HL points to format string, DE to arguments)

**Coffee-GB does NOT natively support this.** The phase must add the hook.

**How to hook it:**
Coffee-GB's `Cpu.java` executes opcodes via an `Opcode` dispatch table. The interception point is in the CPU tick loop — after fetching opcode `0x52`, peek ahead in memory for `0x18` (JR) + `0x64, 0x64` signature:

```kotlin
// EmuPrintfInterceptor.kt
class EmuPrintfInterceptor(
    private val addressSpace: AddressSpace,
    private val onMessage: (String) -> Unit
) {
    // Called after CPU fetches opcode at current PC
    fun intercept(opcode: Int, pc: Int) {
        if (opcode != 0x52) return  // ld d,d
        // Peek at next bytes: should be 0x18 (JR), then offset, then 0x64, 0x64
        val nextByte = addressSpace.getByte(pc + 1) and 0xFF
        if (nextByte != 0x18) return
        val b2 = addressSpace.getByte(pc + 3) and 0xFF
        val b3 = addressSpace.getByte(pc + 4) and 0xFF
        if (b2 != 0x64 || b3 != 0x64) return
        // Valid EMU_printf trap — read format string from HL
        val hlAddress = readHL()  // get HL register value
        val message = readCString(addressSpace, hlAddress)
        onMessage(message)
    }
}
```

**Integration point:** The cleanest hook is CPU opcode post-dispatch. Coffee-GB's `Cpu.java` is not designed for external hooks, so the recommended approach is to call `tick()` in a controlled loop from `CoffeeGbEmulator`, reading the current PC and opcode state before/after each tick. Alternatively, patch `EmuPrintfInterceptor` into the `AddressSpace` read path — when address `0x52` is detected at PC, intercept.

**Practical implementation approach:** Since `Cpu` internals are not fully exposed, implement the interceptor by overriding `AddressSpace.getByte()` around the PC region and monitoring opcode reads, OR use a simpler approach: after each `tick()`, call a polling method that checks the last executed opcode via `gameboy.getCpu()`.

**IMPORTANT WARNING:** Coffee-GB's `Cpu.java` uses micro-operations (each opcode split into multiple micro-ops per clock cycle). The `tick()` method runs one micro-op, not one full opcode. The intercept logic must account for this — check opcode only when the full instruction is complete, not mid-instruction. Use a state machine or track instruction completion.

### Pattern 5: GbEmulator Interface (Phase 09-ready)

```kotlin
interface GbEmulator {
    fun start()
    fun stop()
    fun pause()
    fun resume()
    fun stepFrame()
    fun setSpeed(multiplier: Float)       // 1.0 = normal, 2.0 = 2x, etc.
    fun getFrameBuffer(): IntArray        // 160*144 RGB pixels
    fun getMemory(): AddressSpace         // direct memory access for inspector
    fun getDebugLog(): List<DebugLogEntry>
    fun isRunning(): Boolean
    val isHeadless: Boolean
}

data class DebugLogEntry(
    val timestampMs: Long,
    val level: LogLevel,               // GAME, EMU, WARN, ERROR
    val message: String,
    val cLine: Int?,                   // from EMU_printf hook
    val kotlinFile: String?,           // resolved via source map
    val kotlinLine: Int?,
    val context: String?               // e.g. "gameplay/frame"
) {
    fun formatted(): String {
        val ts = "[%02d:%02d.%03d]".format(
            timestampMs / 60000, (timestampMs / 1000) % 60, timestampMs % 1000
        )
        val location = if (kotlinFile != null) " $kotlinFile:$kotlinLine" else ""
        val ctx = if (context != null) " ($context)" else ""
        return "$ts$location$ctx > $message\n"
    }
}

enum class LogLevel { GAME, EMU, WARN, ERROR }
```

### Pattern 6: Source Map Resolution for Debug Log

The existing `SourceMapLoader` in `gbkt-gradle-plugin` (verified from source) parses `.gbkt.map` JSON files. The `gbkt-emulator` module needs the same logic — either copy the loader or depend on the gradle plugin (not ideal). Better: extract a shared `SourceMapParser` into `gbkt-core` that both can use, OR duplicate the small parser into `gbkt-emulator` (simpler, avoids coupling to gradle plugin).

```kotlin
// SourceMapResolver.kt in gbkt-emulator
class SourceMapResolver(sourceMapsDir: File) {
    private val maps: Map<String, ParsedSourceMap> = loadMaps(sourceMapsDir)

    fun resolve(cLine: Int): SourceLocation? {
        for (map in maps.values) {
            val mapping = map.mappings.find { it.cLine == cLine }
            if (mapping != null) {
                return SourceLocation(
                    file = mapping.kotlinFile,
                    line = mapping.kotlinLine,
                    symbol = mapping.symbol,
                    context = mapping.snippet
                )
            }
        }
        return null
    }
}
```

### Anti-Patterns to Avoid

- **Hooking deep into Coffee-GB internals:** Do not modify Coffee-GB source or fork it. Intercept at the `AddressSpace` or CPU tick boundary only.
- **Running emulator on Swing EDT:** The emulator must run on a dedicated daemon thread, never on the Swing Event Dispatch Thread. EDT is for rendering only.
- **Blocking `runEmulator` Gradle task:** The Gradle task should launch the emulator and return immediately (non-blocking). The JVM process stays alive because Swing has a non-daemon thread. Use `ProcessBuilder` pattern from the old task but via the embedded emulator.
- **Shared mutable state between emulator and log panel:** Use a thread-safe queue or `SwingUtilities.invokeLater` to pass log entries from the emulator thread to the Swing EDT.
- **Large log entries in memory:** Use a bounded circular buffer (e.g., last 10,000 entries) in memory; always write to file unbounded.

## Common Pitfalls

### Pitfall 1: Coffee-GB Micro-Operation Loop vs. Full Opcode

**What goes wrong:** `Gameboy.tick()` executes one micro-operation, not one complete instruction. Attempting to check the opcode after every `tick()` will check mid-instruction state and produce false positives.

**Why it happens:** Coffee-GB models each CPU instruction as multiple micro-ops (e.g., loading a byte from memory is a separate micro-op from storing it to a register).

**How to avoid:** Track instruction completion using a state variable. When detecting `ld d,d` (opcode `0x52`), wait until the CPU's program counter has advanced past the full instruction before treating it as complete. Alternatively, implement the intercept in `AddressSpace.getByte()` when the CPU fetches the opcode byte — this fires exactly once per instruction fetch.

**Warning signs:** Interceptor fires multiple times for a single `EMU_printf` call.

### Pitfall 2: Swing Painting on Non-EDT Thread

**What goes wrong:** Calling `repaint()` or modifying Swing components from the emulator thread causes visual corruption or deadlocks.

**Why it happens:** Swing is single-threaded; all component mutations must happen on the Event Dispatch Thread.

**How to avoid:** Always use `SwingUtilities.invokeLater { panel.repaint() }` from the emulator thread. Log entries: `SwingUtilities.invokeLater { logPanel.appendEntry(entry) }`.

**Warning signs:** `javax.swing.SwingException` or intermittent display glitches.

### Pitfall 3: Blocking Gradle Task with Blocking UI

**What goes wrong:** If `RunEmulatorTask.run()` calls `emulator.start()` and `start()` blocks waiting for the window to close, the Gradle build hangs indefinitely.

**Why it happens:** Swing's main window has a non-daemon thread keeping the JVM alive; Gradle expects task execution to return.

**How to avoid:** `start()` in `CoffeeGbEmulator` should launch the emulator thread and Swing window, then return immediately (non-blocking). The Gradle task returns; the JVM stays alive because the Swing frame's non-daemon thread is running. When the user closes the window, the emulator thread stops and the JVM exits.

**Warning signs:** `./gradlew runEmulator` never returns to the shell prompt.

### Pitfall 4: Coffee-GB Core Artifact Name

**What goes wrong:** Adding `eu.rekawek.coffeegb:coffee-gb:...` (the parent POM) to Gradle dependencies instead of `eu.rekawek.coffeegb:core:...`.

**Why it happens:** Coffee-GB is a multi-module Maven project. The parent POM `coffee-gb` is not a deployable JAR. The core logic is in the `core` submodule.

**How to avoid:** Use `implementation("eu.rekawek.coffeegb:core:1.6.0")`. Verify on Maven Central before adding.

**Warning signs:** Gradle resolves to a POM with `<packaging>pom</packaging>` and no classes.

### Pitfall 5: EMU_printf Byte Sequence Ambiguity

**What goes wrong:** `ld d,d` (opcode `0x52`) is a valid no-op instruction and appears in normal game code. The interceptor fires on non-debug instructions.

**Why it happens:** Any code that happens to load register D into itself will trigger a false positive.

**How to avoid:** After detecting opcode `0x52`, verify the full sequence: next byte must be `0x18` (JR), then at offset PC+3 and PC+4 must be `0x64, 0x64`. Only all four bytes together constitute a valid `EMU_printf` trap.

**Warning signs:** Log viewer shows garbage or too many messages.

### Pitfall 6: `gbkt-emulator` Module Placement in Build

**What goes wrong:** Adding `gbkt-emulator` to `settings.gradle.kts` but forgetting to publish it before the Gradle plugin can depend on it.

**Why it happens:** The Gradle plugin is a composite build (`includeBuild`) and resolves dependencies from `mavenLocal()`. `gbkt-emulator` must be published to `mavenLocal` before the plugin can import it.

**How to avoid:** Either (a) add `gbkt-emulator` as a direct project dependency in the Gradle plugin's classpath (not recommended for composite build), or (b) publish `gbkt-emulator` to `mavenLocal` as part of the build bootstrap, or (c) include the emulator code directly in the Gradle plugin module. Option (b) is the cleanest and follows the existing `gbkt-core` pattern.

**Warning signs:** `Could not resolve eu.rekawek.coffeegb:core` or `Could not resolve io.github.gbkt:gbkt-emulator` during plugin task execution.

### Pitfall 7: Emulator Thread Lifecycle with Gradle Worker API

**What goes wrong:** The emulator thread is not properly shut down, causing the Gradle daemon to hang after the task completes.

**Why it happens:** A non-daemon thread in the JVM prevents JVM exit. If the emulator thread is not daemon, or not properly stopped, Gradle hangs.

**How to avoid:** Mark the emulator thread as daemon (`thread.isDaemon = true`). For the `emulatorTest` task (headless, finite), ensure `emulator.stop()` is always called in a finally block.

## Code Examples

### Coffee-GB Headless Integration (verified pattern from source)

```kotlin
// Source: trekawek/coffee-gb core/src/main/java/eu/rekawek/coffeegb/core/Gameboy.java
fun runHeadless(romFile: File, maxFrames: Int): List<String> {
    val rom = Rom.of(romFile)
    val config = GameboyConfiguration.Builder().rom(rom).build()
    val gameboy = Gameboy(config)

    val capturedMessages = mutableListOf<String>()
    val eventBus = EventBusImpl()
    // NullConsole and NullSerialEndpoint = no-op implementations
    gameboy.init(eventBus, NullSerialEndpoint, NullConsole)

    val thread = Thread {
        var frames = 0
        while (frames < maxFrames) {
            val frameDone = gameboy.tick()
            if (frameDone) frames++
        }
        gameboy.stop()
    }.apply { isDaemon = true; start() }

    thread.join()
    return capturedMessages
}
```

## Open Questions

1. **Coffee-GB `core` artifact exact Maven coordinates**
   - What we know: Group `eu.rekawek.coffeegb`, submodule is `core`, latest release 1.6.0
   - What's unclear: Whether the Maven artifact is `core` or `coffeegb-core` (the pom.xml says `coffee-gb` parent with `core` submodule — typical Maven would publish as `eu.rekawek.coffeegb:core`)
   - Recommendation: Verify with `./gradlew dependencies` after adding tentative dep; if resolution fails, check https://mvnrepository.com/artifact/eu.rekawek.coffeegb

2. **CPU opcode hook integration point in Coffee-GB 1.6.0**
   - What we know: `Gameboy.tick()` executes micro-ops; `Cpu.java` has opcode dispatch table; `AddressSpace` provides `getByte()`
   - What's unclear: Whether Coffee-GB 1.6.0 exposes enough CPU state (current opcode, PC) after `tick()` to implement the intercept without modifying Coffee-GB source
   - Recommendation: First plan should prototype the intercept approach using `gameboy.getCpu()` introspection. If not sufficient, wrap `AddressSpace` with a proxy that monitors reads at PC.

3. **Speed multiplier implementation**
   - What we know: `SpeedMode` is accessible via `gameboy.getSpeedMode()`; `tick()` can be called faster or slower
   - What's unclear: Whether `SpeedMode` controls the emulator's internal speed or just GBC double-speed mode
   - Recommendation: Implement 2x/4x by calling `tick()` 2x/4x per frame interval in the emulator loop

4. **`gbkt-emulator` dependency in composite build**
   - What we know: `gbkt-gradle-plugin` is a composite build that depends on `gbkt-core` via `mavenLocal`
   - What's unclear: Whether `gbkt-emulator` should live inside the composite build or as a standard module in `settings.gradle.kts`
   - Recommendation: Standard module in `settings.gradle.kts`, published to `mavenLocal` before Gradle plugin depends on it (same pattern as `gbkt-core`)
