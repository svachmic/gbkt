# Phase 06.12: Embedded Emulator Core and Debug Loop - Context

**Gathered:** 2026-02-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Embed a Game Boy emulator as a JVM library (`gbkt-emulator` module) to close the developer debug loop. Replace external mGBA dependency with an integrated Coffee-GB emulator that captures `EMU_printf` debug output via `ld d,d` trap. Provides a Swing-based emulator window with developer controls, a LogCat-style debug log viewer, and a clean `GbEmulator` API designed for Phase 09 IntelliJ embedding.

</domain>

<decisions>
## Implementation Decisions

### Swing Emulator Window
- 4x default scale (640x576) — comfortable on modern/retina displays
- Resizable with nearest-neighbor scaling — keeps pixel art crisp at any size
- Classic keyboard mapping: arrows = D-pad, Z = A, X = B, Enter = Start, Backspace = Select
- Title bar shows: "gbkt - {rom_name} | 59.7 FPS | Frame 12345"

### Debug Log Viewer (LogCat-style)
- Separate Swing window styled like a terminal panel: monospace font, dark background, auto-scrolling
- Filterable log levels — show EMU_printf game messages + emulator events (scene transitions, warnings, illegal opcodes), user can filter down
- Structured log format with source mapping: `[00:02.341] ScriptBuilder.kt:45 (gameplay/frame) > Score: 10` — uses existing `.gbkt.map` files to correlate back to DSL code
- Log file at `build/gbkt/logs/debug.log`, overwritten each run (fresh per invocation)
- This LogCat panel migrates to an IntelliJ tool window in Phase 09

### Gradle Task Design
- `./gradlew run` = full pipeline: generateC → buildRom → launch emulator (single command)
- `runEmulator` auto-detects embedded Coffee-GB, with configurable fallback to external emulator
- No backward compatibility with old `emulator { path.set(...) }` config — embedded is the default, clean break
- All emulator tasks (runEmulator, debugEmulator, emulatorTest) use the embedded emulator consistently

### Emulator Control API
- Full developer controls: pause/resume, frame stepping, speed multiplier (2x/4x), memory inspector
- Proper toolbar with buttons — discoverable, not just keyboard shortcuts
- Memory inspector with two tabs: (1) named DSL variables via source maps, (2) raw hex memory browser
- Headless mode supported — no window, just run + capture logs (for CI, automated validation, Claude-in-the-loop debugging)

### GbEmulator Interface (Phase 09-Ready)
- Clean API from day one: `start()`, `pause()`, `resume()`, `stepFrame()`, `setSpeed()`, `getFrameBuffer()`, `getMemory()`, `getDebugLog()`
- Designed so Phase 09 IntelliJ embedding just wraps this interface in IDE panels — no refactoring needed

### Claude's Discretion
- Exact toolbar layout and button icons
- Status bar design details
- Log rotation/max size policy
- Which emulator tasks (debugEmulator, emulatorTest) benefit most from embedding vs. which can be simplified
- Speed multiplier values (2x/4x or continuous slider)
- Memory inspector hex view column layout

</decisions>

<specifics>
## Specific Ideas

- "Like LogCat from Android Studio" — the debug log viewer should feel like LogCat: live-scrolling, filterable, terminal-styled panel. Not just a file you `tail -f`.
- Memory inspector like Android Studio's variable inspector + memory view — named variables tab for quick checks, raw hex tab for deep debugging.
- `./gradlew run` should be the single command for the full dev loop: clean, compile C, build ROM, run emulator.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `RunEmulatorTask.kt`: Current external mGBA launcher — replace implementation with embedded emulator, keep task registration
- `DebugEmulatorTask.kt`: GDB server + Lua debug script launcher — adapt for embedded
- `EmulatorTestTask.kt`: Automated ROM testing — adapt for headless embedded mode
- `EmulatorExtension`: Current config (`path`, `args`, `liveReload`) — simplify for embedded-first design
- `SourceMapLoader.kt` (gbkt-gradle-plugin): Existing source map loading infrastructure — reuse for structured log output
- `SourceMapCollector` (gbkt-backend-gbdk pipeline): Generates `.gbkt.map` files during codegen — feeds the log viewer

### Established Patterns
- Gradle plugin registers tasks via `GbktPlugin.kt` with task dependencies (buildRom → runEmulator chain exists)
- Source maps are generated as `main.c.gbkt.map` alongside C output
- All emulator config flows through `GbktExtension.emulator { }` DSL block

### Integration Points
- New `gbkt-emulator` module added to multi-module build (settings.gradle.kts)
- `RunEmulatorTask` switches from ProcessBuilder(mGBA) to `GbEmulator.start()`
- `GenerateCTask` already produces source maps — debug log viewer consumes them
- Coffee-GB dependency added to `gbkt-emulator/build.gradle.kts` (Maven Central: `eu.rekawek.coffeegb:core`)

</code_context>
