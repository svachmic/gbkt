# Phase 07.1.1: agent-testing-critical-gaps - Context

**Gathered:** 2026-03-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Close 5 critical gaps blocking autonomous LLM game testing: (1) `emulator_press` MCP tool to halve button input tool calls, (2) wire custom TileDecoder through StepAgent/UatRunner/MCP so text assertions work with custom tilesets, (3) 16-bit variable support with signed interpretation through the full stack, (4) opt-in scroll-aware text reading in VramTextVerifier, (5) `context/UAT_GUIDE.md` debugging workflow documentation with real examples.

</domain>

<decisions>
## Implementation Decisions

### emulator_press MCP Tool
- Returns full Observation (same as emulator_step) — agent gets immediate feedback
- Supports hold duration: `emulator_press(button, frames=1)` — default 1 frame for tap, N frames for hold
- Single button only — no multi-button array. D-pad + button combos are sequential in GB games
- Auto-release: press for N frames, release, advance 1 more frame. Observation reflects state AFTER release
- Matches GBDK `pressed()` edge-detection semantics

### TileDecoder Wiring
- **Metadata-driven**: game_metadata.json gets tile decoder config per tilemap layer (BG vs WIN)
- **Full character map**: metadata includes complete tile→char mapping table (not just offset)
- **Per-layer decoders**: BG and WIN layers can have different decoders — window layer often uses GBDK font tiles while BG uses custom tileset
- **Auto-generated from DSL**: pipeline reads tileset declarations and auto-generates tile→char maps in game_metadata.json. Zero manual work for game authors
- StepAgent/UatRunner/MCP auto-load the right decoder from metadata. Fallback to existing GBDK_BG_DECODER/DIRECT_ASCII_DECODER defaults when no metadata present

### 16-bit Variable Support
- **Type info from IR in metadata**: game_metadata.json variable entries enriched with IR type (UINT8, INT8, UINT16, INT16)
- **Signed interpretation for all types**: INT8 reported as -128..127, INT16 as -32768..32767, unsigned types as 0..255/0..65535
- **Fix all variable types in one pass**: not just 16-bit addition — also fix INT8 signed interpretation
- **Full stack**: VariableInspector → Observation → StepAgent → UatRunner → MCP all respect variable width and signedness
- **Verified against real example game**: test with a game that uses 16-bit variables (Dungeon/RPG-Lite score counters)

### Scroll-Aware Text Reading
- **Per-read parameter**: `readText(memory, x, y, length, scrollAware=false)` — callers opt-in per call
- **Default false**: keeps existing behavior safe for non-scrolling games
- **MCP exposure**: `emulator_assert` with `text_on_screen` type gets optional `scrollAware` field. Default false
- When enabled: apply SCX/SCY register offsets to translate viewport coordinates to tilemap coordinates

### UAT Guide (context/UAT_GUIDE.md)
- **Complementary to TESTING.md**: TESTING.md covers test infrastructure (extensions, recipes, MCP tools). UAT_GUIDE.md covers the debugging WORKFLOW — how to use those tools to find and fix bugs. Cross-references between them
- **2-3 real debugging walkthroughs** from Phase 07 bugs with actual log output, source map correlation, and fix process
- **Dedicated MCP section**: how agents use emulator tools (emulator_press, emulator_assert, save/load state) for systematic debugging
- **CLAUDE.md updated**: add UAT_GUIDE.md to Documentation Index and Common Tasks Routing tables

### Testing Strategy
- **Unit + integration** for all deliverables
- Unit tests for TileDecoder logic, 16-bit read logic, scroll offset math
- Integration tests using GbktTestExtension with real ROMs (Pong for basic, Explorer/Dungeon for custom tileset)
- MCP tool test for emulator_press in PongMcpPlaythroughTest style
- 16-bit variable support verified against real example game (full pipeline: DSL → metadata → VariableInspector → MCP)

### Delivery Ordering
1. Metadata enrichment (variable types + tile maps)
2. 16-bit variable support
3. TileDecoder wiring through stack
4. Scroll-aware text reading
5. emulator_press MCP tool
6. UAT_GUIDE.md (references all new tools)

## Existing Code Insights

### Reusable Assets
- `VramTextVerifier.TileDecoder` interface: already defines `decode(tileIndex: Int): Char` — wire through stack, don't reinvent
- `VramTextVerifier.GBDK_BG_DECODER` / `DIRECT_ASCII_DECODER`: existing decoders, keep as defaults
- `VariableInspector.readNamed()`: single-byte read to extend with type-aware multi-byte reading
- `Observation` data class: `variables: Map<String, Int>` — Int already accommodates 16-bit values, just need correct reading
- `ToolHandlers.registerEmulatorTools()`: pattern for registering new MCP tools
- `GBDKPipelineV2.buildMetadataFile()`: where variable type and tile mapping metadata gets generated
- `StepAgent.step()`: builds Observation including text reads — needs TileDecoder parameter threading

### Established Patterns
- MCP tools registered in `ToolHandlers.kt` via `Server.registerEmulatorTools()` with JSON schema
- Metadata generated in pipeline, consumed by `GameMetadata` parser, exposed via `emulator_describe_game`
- `emulator_step` accepts optional `buttons` array — `emulator_press` follows same validation pattern
- Per-layer text reading already exists in VramTextVerifier (BG vs WIN with different defaults)

### Integration Points
- `GBDKPipelineV2.buildMetadataFile()` — add variable type info and tile mapping to metadata JSON
- `GameMetadata` parser — extend to parse new fields
- `VariableInspector` — type-aware reading using metadata
- `StepAgent.buildObservation()` — thread TileDecoder for text reads
- `VramTextVerifier.readText()` — add scrollAware parameter
- `ToolHandlers.kt` — new `emulator_press` tool registration
- `CLAUDE.md` — Documentation Index and Common Tasks Routing updates

</code_context>

<specifics>
## Specific Ideas

- emulator_press should feel like a natural complement to emulator_step — same Observation return type, just optimized for the common "press a button and see what happens" pattern
- TileDecoder auto-generation from DSL means game authors never need to think about tile mappings — the framework handles it, consistent with the "zero C, zero manual hardware management" philosophy
- Signed variable interpretation matches DSL declaration intent — if a developer declares `i16Var`, they expect to see negative values, not raw unsigned bytes
- UAT_GUIDE.md with real bug examples is more valuable than synthetic scenarios — shows the actual debugging process, not idealized walkthroughs

</specifics>
