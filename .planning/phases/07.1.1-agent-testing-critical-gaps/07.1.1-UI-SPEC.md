## Interaction Contract: MCP Tool API Surface

This is the primary "UI" of this phase — the JSON schema contract that AI agents
interact with when calling the new and modified MCP tools.

### emulator_press (NEW — 17th MCP tool)

**Input schema:**

| Field | Type | Required | Constraints | Description |
|-------|------|----------|-------------|-------------|
| `button` | string | yes | one of: up, down, left, right, a, b, start, select | Button to press |
| `frames` | integer | no | min 1, default 1 | How many frames to hold the button |

**Return value:** Full `Observation` JSON object — identical shape to `emulator_step` return.

**Semantic contract:**
- Advances `frames + 1` total frames: N frames held, then 1 release frame
- Observation reflects state AFTER the release frame
- Matches GBDK `pressed()` edge-detection semantics

**Error responses (string messages):**
- `button` missing: `"button is required"`
- Invalid button name: `"Invalid button '{name}'. Valid: up, down, left, right, a, b, start, select"`
- `frames` less than 1: `"frames must be positive"`
- `frames` exceeds maximum: `"frames exceeds maximum"`
- No active session: `"No active emulator session"`

**Tool description copy (used verbatim in MCP registration):**
```
Press a single button for N frames then release and advance 1 frame.
Returns full Observation after release. Matches GBDK pressed() edge semantics.
Advances frames+1 total frames (hold + release). Use instead of emulator_step
for simple button taps.
```

### emulator_assert (MODIFIED — existing tool)

The `text_on_screen` assertion type gains an optional `scrollAware` field:

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `scrollAware` | boolean | no | `false` | When true, applies SCX/SCY register offsets to translate viewport coordinates to tilemap coordinates. Only affects BG layer reads. |

**Behavioral contract:**
- `scrollAware: false` (default): existing behavior unchanged — safe for non-scrolling games
- `scrollAware: true`: viewport (x,y) mapped to tilemap (x+SCX/8, y+SCY/8) with wraparound at 32 tiles
- `scrollAware` has no effect on the WINDOW layer (window has independent WX/WY registers)

## Interaction Contract: Observation Data Shape

The `Observation` JSON object is the primary data structure agents receive. This phase
enriches its `variables` field with correct signed/16-bit values.

**Current behavior (before this phase):**
```json
{ "variables": { "ballDx": 255, "score": 42 } }
```
`ballDx` should be -1 (INT8), but reads as unsigned 255.

**Correct behavior (after this phase):**
```json
{ "variables": { "ballDx": -1, "score": 42 } }
```

**Type-to-range mapping (contract for agents reading variable values):**

| IR Type | Range | Sign |
|---------|-------|------|
| UINT8 | 0 to 255 | unsigned |
| INT8 | -128 to 127 | signed |
| UINT16 | 0 to 65535 | unsigned |
| INT16 | -32768 to 32767 | signed |

## Interaction Contract: game_metadata.json Schema Extension

The metadata file gains a `tileDecoders` section. This is machine-consumed by
`GameMetadata` parser; no human visual design required.

**Extended shape:**
```json
{
  "variables": [
    { "name": "score", "type": "U8", "semantic": "score" },
    { "name": "ballDx", "type": "I8", "semantic": "velocity" }
  ],
  "tileDecoders": {
    "bg": { "type": "gbdk_offset" },
    "win": { "type": "direct_ascii" }
  }
}
```

**Decoder type values:**

| Value | Meaning | When emitted |
|-------|---------|--------------|
| `"gbdk_offset"` | GBDK IBM font tile offset (default BG decoder) | Games without custom BG font |
| `"direct_ascii"` | Tile index == ASCII code point | Window layer (always) |
| `"custom"` | Full tile→char mapping table in `mapping` field | Reserved for future custom font DSL |

All new metadata fields are optional. Games without `tileDecoders` key fall back
to existing `GBDK_BG_DECODER` / `DIRECT_ASCII_DECODER` defaults. No breaking change.

## Documentation Contract: UAT_GUIDE.md

The UAT guide is a Markdown document. Its structural contract:

**File location:** `context/UAT_GUIDE.md`

**Required sections (in order):**

1. **Overview** — What UAT_GUIDE.md covers vs. TESTING.md. One paragraph distinguishing
   workflow (this doc) from infrastructure (TESTING.md). Cross-reference to TESTING.md.

2. **Prerequisites** — ROM must be built, MCP server must be running, PLAYBOOK.md must exist.
   3-5 bullet points. No prose paragraphs.

3. **Debugging Workflow** — Step-by-step process: start session → read playbook → step through
   gameplay → assert state → save/load states for bisect → correlate with source maps.

4. **Real Debugging Walkthroughs** — 2-3 walkthroughs from Phase 07 bugs. Each walkthrough
   must include:
   - Problem description (what was observed)
   - Actual tool call sequence (using real MCP tool names)
   - Actual log output (not synthetic)
   - Root cause and fix

5. **Using emulator_press** — When to use `emulator_press` vs. `emulator_step`. Show both
   patterns side-by-side. Emphasize `frames+1` total frame advance.

6. **Text Assertions** — How text assertions work (WIN vs BG layer), when to use
   `scrollAware: true`, tile decoder configuration.

7. **Variable Inspection** — How to read signed/16-bit variables. Type range reference.
   Common pitfall: expecting positive value from INT8.

8. **Cross-references** — Links to `context/TESTING.md`, `gbkt-emulator/CLAUDE.md`,
   `gbkt-mcp-server/CLAUDE.md`.

**Tone and style:**
- Imperative voice: "Run", "Call", "Assert" — not "You should run"
- Code blocks for all MCP tool calls and JSON payloads
- No emojis
- Line length: 100 characters max per line in Markdown prose
