## Summary

Phase 07.1.1 closes 5 critical gaps in the autonomous LLM game testing infrastructure. All work lives in two modules (`gbkt-emulator` and `gbkt-mcp-server`) plus the codegen pipeline (`gbkt-backend-gbdk`). The codebase is already well-structured with clean extension points at every target location.

The metadata pipeline (`GBDKPipelineV2.buildMetadataFile`) already emits variable types (from `VariableDef.type: VarType`) but stores them as the enum `.name` (`"U8"`, `"I8"`, `"U16"`, `"I16"`). The reading layer (`VariableInspector.readNamed`) is byte-only and the `readAll()` method returns `Map<String, Int>` treating all variables as unsigned bytes. The `readNamedInt16` method already exists in `VariableInspector` but is never called automatically — it needs to be wired into type-aware reading. Fixing variable width and signedness propagates through `AgentDebugSession.readAllVariables()` → `StepAgent.buildObservation()` → `Observation.variables` → MCP layer.

The `VramTextVerifier.TileDecoder` interface is already designed for custom decoders — the gap is that the right decoder never reaches `StepAgent.buildObservation()`. The `buildObservation()` method calls `VramTextVerifier.readAllRows(memory, layer)` with no decoder argument, so it always uses the per-layer defaults. Wiring metadata-driven decoders requires: (1) emitting tile→char mappings in `game_metadata.json`, (2) parsing them into `GameMetadata`, and (3) threading them through `StepAgent.buildObservation()`.

The `emulator_press` tool is a pure addition to `ToolHandlers.kt` with a new handler in `ToolHandlerLogic` and a new method on `McpEmulatorSession`. The implementation pattern is identical to `emulator_step` — parse button name, call `StepAgent`, return observation.

**Primary recommendation:** Implement in delivery order from CONTEXT.md (metadata → 16-bit → TileDecoder → scroll-aware → emulator_press → UAT guide). Each step builds on the previous — metadata enrichment unblocks both 16-bit and TileDecoder work.

## Architecture Patterns

### Pattern 1: Adding metadata fields to game_metadata.json

**What:** Extend `GBDKPipelineV2.buildMetadataFile()` to emit new JSON fields, then extend `GameMetadata.fromJsonString()` to parse them.

**Existing shape:**
```json
{
  "variables": [
    {"name": "score", "type": "U8", "semantic": "score"},
    {"name": "ballDx", "type": "I8", "semantic": "velocity"}
  ]
}
```

**Extended shape (this phase):**
```json
{
  "variables": [
    {"name": "score", "type": "U8", "semantic": "score"},
    {"name": "dungeonScore", "type": "U16", "semantic": "score"},
    {"name": "ballDx", "type": "I8", "semantic": "velocity"}
  ],
  "tileDecoders": {
    "bg": {"type": "custom", "mapping": {"0": " ", "1": "!", "48": "0", ...}},
    "win": {"type": "direct_ascii"}
  }
}
```

**Key insight:** `VarType.name` already gives `"U8"`, `"I8"`, `"U16"`, `"I16"` — no new IR changes needed. The metadata already has the type info; `GameMetadata.VariableDef` already parses it. The gap is only in how `VariableInspector.readAll()` uses that type.

### Pattern 2: Type-aware variable reading in VariableInspector

**What:** `readAll()` currently reads one byte per symbol regardless of type. Needs to read 1 or 2 bytes and apply signed interpretation based on `SymbolEntry.type`.

**Current (byte-only):**
```kotlin
fun readAll(): Map<String, Int> =
    symbols.mapValues { (_, entry) -> memory.readByte(entry.address) }
```

**Extended (type-aware):**
```kotlin
fun readAll(): Map<String, Int> = symbols.mapValues { (_, entry) ->
    readTypedValue(entry)
}

private fun readTypedValue(entry: SymbolEntry): Int {
    val raw = memory.readByte(entry.address)
    return when (entry.type) {
        "INT8" -> if (raw > 127) raw - 256 else raw          // signed byte
        "UINT16" -> {
            val lo = memory.readByte(entry.address)
            val hi = memory.readByte(entry.address + 1)
            (hi shl 8) or lo                                  // unsigned 16-bit LE
        }
        "INT16" -> {
            val lo = memory.readByte(entry.address)
            val hi = memory.readByte(entry.address + 1)
            val raw16 = (hi shl 8) or lo
            if (raw16 > 32767) raw16 - 65536 else raw16      // signed 16-bit LE
        }
        else -> raw  // UINT8 — existing behavior
    }
}
```

**Challenge:** `SymbolEntry.type` is currently inferred by heuristics (`inferVariableType`), not from IR metadata. The fix: when `GameMetadata` is available, override the heuristic type with the authoritative IR type from `VariableDef`. This wiring happens in `StepAgent` where both `resolvedMetadata` and the session are available.

**Approach:** Pass `GameMetadata.variables` into `VariableInspector.overrideTypes(Map<String, String>)` after loading symbols. This lets the authoritative type from the pipeline override the heuristic.

### Pattern 3: TileDecoder wiring through metadata

**What:** `StepAgent.buildObservation()` calls `VramTextVerifier.readAllRows(memory, layer)` with no decoder. The decoder must flow from `GameMetadata` → `StepAgent`.

**Extension point in `StepAgent.buildObservation()`:**
```kotlin
// Before (always uses defaults):
bgText = VramTextVerifier.readAllRows(memory, TilemapLayer.BACKGROUND),
winText = VramTextVerifier.readAllRows(memory, TilemapLayer.WINDOW),

// After (uses metadata decoder if available):
val bgDecoder = resolvedMetadata?.bgDecoder()  // null → uses default
val winDecoder = resolvedMetadata?.winDecoder() // null → uses default
bgText = VramTextVerifier.readAllRows(memory, TilemapLayer.BACKGROUND, bgDecoder),
winText = VramTextVerifier.readAllRows(memory, TilemapLayer.WINDOW, winDecoder),
```

**Tile→char map generation:** The pipeline knows which PNG tilesets are loaded at each scene. Custom tilesets replace the GBDK IBM font on the BG layer. The window layer almost always uses `DIRECT_ASCII_DECODER`. The metadata should emit:
- `"bg": {"type": "custom", "mapping": {...}}` when a scene uses a custom tileset for the BG
- `"win": {"type": "direct_ascii"}` — standard for window layer
- `"bg": {"type": "gbdk_offset"}` — default for games with no custom tileset

**Tile mapping source:** For custom tilesets (PNG files), the mapping is the relationship between tile indices and ASCII characters defined by where the font tiles appear in the PNG. The simplest approach: the DSL author does NOT need to provide this — instead, for games that use the GBDK font for text on the BG layer but custom tiles for graphics, only the BG decoder for scenes with text needs to differ from the default. Research finding: the **window layer** is where all text appears in games using custom tilesets (per CLAUDE.md: "All UI text renders on the GBDK window layer"). BG decoder for custom-tileset scenes defaults to GBDK_BG_DECODER since text appears on WIN anyway. The key insight: **for current games, WIN always uses direct_ascii, BG always uses gbdk_offset** unless a game explicitly places text on BG with a custom font.

**Simplified approach (sufficient for current phase):** Metadata emits a single `"tileDecoderConfig"` object with `"bgType": "gbdk_offset"|"custom"` and `"winType": "direct_ascii"`. The mapping table is only needed for `custom` type. For the Explorer/Dungeon/RPG-lite games: text is rendered on WIN → `DIRECT_ASCII_DECODER` is correct. BG has dungeon tiles → VramTextVerifier reading BG will give garbage, but tests should assert on WIN text, not BG text.

### Pattern 4: Scroll-aware text reading

**What:** SCX/SCY hardware registers shift the background tilemap relative to the LCD viewport. Reading tile at LCD (x, y) when SCX=8 means the actual tilemap tile is at (x + SCX/8, y + SCY/8).

**GB hardware registers:**
- `SCY` = 0xFF42 — Background Y scroll position (pixels)
- `SCX` = 0xFF43 — Background X scroll position (pixels)

**Offset calculation:**
```kotlin
// Viewport tile (x, y) → tilemap tile (tileX, tileY)
val scx = memory.readByte(0xFF43)  // pixel offset, 0-255
val scy = memory.readByte(0xFF42)  // pixel offset, 0-255
val tileX = (x + scx / 8) and 31  // wraps at 32 (tilemap is 32x32)
val tileY = (y + scy / 8) and 31  // wraps at 32
```

**Extension to `VramTextVerifier.readText`:**
```kotlin
fun readText(
    memory: MemoryAccess,
    x: Int, y: Int, length: Int,
    layer: TilemapLayer = TilemapLayer.BACKGROUND,
    decoder: TileDecoder? = null,
    scrollAware: Boolean = false,  // NEW parameter, default false = safe
): String {
    val (actualX, actualY) = if (scrollAware && layer == TilemapLayer.BACKGROUND) {
        val scx = memory.readByte(0xFF43)
        val scy = memory.readByte(0xFF42)
        ((x + scx / 8) and 31) to ((y + scy / 8) and 31)
    } else {
        x to y
    }
    // ... rest of existing implementation using actualX, actualY
}
```

**Constraint change:** With scroll-aware mode, x and y can be 0..19 (viewport coords) but actual tilemap coords can be 0..31. The existing `require(x in 0 until VISIBLE_WIDTH)` check applies to viewport coords. For scroll-aware reads, the address computation uses the full 32-tile tilemap, not just the visible 20 tiles. The validation should validate viewport input (0-19) then compute tilemap address without width constraint.

**MCP schema extension:** `emulator_assert` `text_on_screen` check gains optional `scrollAware: Boolean` field.

### Pattern 5: emulator_press MCP tool

**What:** New 17th MCP tool. Single button, N frames hold, auto-release, returns Observation.

**Implementation in McpEmulatorSession:**
```kotlin
suspend fun press(button: Button, frames: Int = 1): Observation = mutex.withLock {
    val a = requireActive()
    // Press for N frames
    val holdObs = a.stepN(frames, setOf(button))
    // Release and advance 1 more frame (matches GBDK pressed() edge semantics)
    val releaseObs = a.step(emptySet())
    lastObservation = releaseObs
    releaseObs  // observation AFTER release
}
```

**ToolHandlerLogic.handlePress:**

```kotlin
    return jsonResult(obs.toJsonObject().toString())
}
```

### Anti-Patterns to Avoid

- **Overriding readAll() return type:** Keep `Map<String, Int>` — signed INT8 returns negative Kotlin Int, INT16 returns signed value within Int range. No type change needed.
- **Breaking existing behavior:** `scrollAware = false` default is critical — games without scroll use position 0 which is already correct. Changing default would break all existing scroll-unaware text assertions.
- **Metadata-required for basic games:** All new metadata fields must be optional with graceful fallback to existing decoders. Games without custom tilesets (Pong, Breakout) work unchanged.
- **Adding decoder parameter to all public APIs:** Thread decoder through internal `buildObservation()` only. Public `StepAgent.step()` signature stays unchanged.

## Common Pitfalls

### Pitfall 1: INT8 signed values in Kotlin
**What goes wrong:** `memory.readByte(addr)` returns `Int` in range 0-255. INT8 value `-1` is stored as `0xFF = 255`. Reporting `255` instead of `-1` for signed variables.
**Why it happens:** `readByte` returns unsigned byte. No automatic sign extension.
**How to avoid:** Apply sign extension: `if (raw > 127) raw - 256 else raw` for INT8.
**Warning signs:** Game shows ballDx = 255 instead of -1 in agent output.

### Pitfall 2: 16-bit variable symbol file entries
**What goes wrong:** SDCC only emits ONE symbol entry per variable, at the low byte address. The high byte is at `address + 1`. The symbol file has no width hint — only the IR metadata knows the type.
**Why it happens:** The sym file is a simple address table, not a type-annotated debug format.
**How to avoid:** Use `GameMetadata.variables` types to determine width; sym file provides only the start address.
**Warning signs:** 16-bit variable reads return only low byte (max 255 for any value).

### Pitfall 3: Scroll-aware reads breaking window layer
**What goes wrong:** Applying SCX/SCY offsets to the WINDOW layer. The window layer ignores SCX/SCY — it has its own position registers (WX, WY).
**Why it happens:** Forgetting that window and background have independent scroll registers.
**How to avoid:** Only apply SCX/SCY offset when `layer == TilemapLayer.BACKGROUND`. Document this clearly in `readText` kdoc.
**Warning signs:** WIN layer text reads return wrong characters after scroll.

### Pitfall 4: Tilemap address overflow with scroll
**What goes wrong:** Tilemap is 32x32 tiles but only 20x18 are visible. With SCX=120 (15 tiles), reading tile at viewport x=10 gives tilemap x=25 (fine). But x=19 gives tilemap x=34 — needs wrapping at 32.
**Why it happens:** Tilemap wraps around (circular buffer in hardware).
**How to avoid:** Apply `and 31` after adding scroll offset: `(x + scx/8) and 31`.
**Warning signs:** Text reads crash or return wrong values at the right edge of viewport.

### Pitfall 5: VariableInspector type override timing
**What goes wrong:** Calling `overrideTypes()` before `loadSymbols()` — symbols not yet loaded so override map is built from empty symbols.
**Why it happens:** `StepAgent` creates inspector before loading symbols (config.symFile) then later has metadata.
**How to avoid:** `overrideTypes()` must be called AFTER `loadSymbols()`. In `AgentDebugSession.start()`, the inspector is created with `symFile` immediately — so if StepAgent calls `overrideTypes` after `start()`, the symbols are loaded. Actually, in `StepAgent`, both `resolvedMetadata` and the `session` (containing the inspector) are initialized in the constructor — but `session.start()` creates the inspector. The `overrideTypes` call must happen AFTER `session.start()` in `StepAgent.start()`.
**Warning signs:** INT8/INT16 variables still read as unsigned after override.

### Pitfall 6: emulator_press hold semantics vs step semantics
**What goes wrong:** Using `step(N, setOf(button))` then `step(emptySet())` creates N+1 total frames. If the agent also steps separately, the frame count diverges from expectations.
**Why it happens:** `emulator_press` explicitly adds a release frame as part of its semantics.
**How to avoid:** Document clearly: `emulator_press(button, frames=1)` advances `frames + 1` total frames (hold + release). State this in the tool description.
**Warning signs:** Game state is `frames + 1` ahead of what agent expects.

```kotlin
const val SCY_REG_ADDR = 0xFF42  // Background Y scroll (pixels)
const val SCX_REG_ADDR = 0xFF43  // Background X scroll (pixels)

            val scx = memory.readByte(SCX_REG_ADDR)
```

```kotlin
// New data class
data class TileDecoderConfig(

    val mapping: Map<Int, Char> = emptyMap()  // only for "custom" type

    "custom" -> VramTextVerifier.TileDecoder { tile -> mapping[tile] ?: '.' }

}
```

## Open Questions

1. **Tile→char map auto-generation for custom tilesets**
   - What we know: The pipeline knows which PNG files are tilesets. The mapping of tile index → ASCII character for custom fonts embedded in PNG files is not stored anywhere in the IR.
   - What's unclear: How does the pipeline know the ASCII layout of a custom PNG font? The PNG tileset may not be a font at all (dungeon floors, walls).
   - Recommendation: For this phase, emit `"gbdk_offset"` for BG by default and `"direct_ascii"` for WIN. Only emit `"custom"` when a game explicitly declares a custom font tileset (a future DSL construct). Current Explorer/Dungeon/RPG-lite games have text on WIN only — the default WIN decoder (`DIRECT_ASCII_DECODER`) is already correct for them.

2. **Variable type override when metadata changes mid-session**
   - What we know: Types are wired once at `start()` from static metadata.
   - What's unclear: If a different ROM is loaded without restart, types could be stale.
   - Recommendation: Types are wired on `start()` and cleared on `stop()` — consistent with existing session lifecycle.

3. **WRAM address range for 16-bit variables**
   - What we know: `VariableInspector` filters to WRAM (0xC000-0xDFFF). 16-bit variables occupy 2 bytes; `address + 1` must also be in WRAM.
   - What's unclear: Could a U16 variable be placed at 0xDFFF (last WRAM byte)? The linker would normally not split a 2-byte value across boundaries.
   - Recommendation: Add WRAM boundary check when reading 16-bit: `if (entry.address + 1 <= WRAM_END)` before reading high byte; return low byte only as fallback if somehow at boundary.
