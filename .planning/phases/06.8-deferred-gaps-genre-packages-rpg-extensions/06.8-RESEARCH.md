## Summary

Phase 06.8 has two distinct workstreams. The first is creating four new Gradle modules (`gbkt-genre-rpg` via rename, `gbkt-genre-platformer`, `gbkt-genre-puzzle`, `gbkt-genre-sport`) each with domain models, DSL builders, and codegen visitors discoverable via ServiceLoader. The second is adding missing codegen test coverage for 10 existing RPG opt-in features (H1–H10) in `RpgCodegenTest.kt` — the codegen itself already exists in `RpgVisitor.kt` and `GBDKSystemVisitor.kt`, it just lacks test validation.

The codebase has a well-established pattern: domain types in `domain/` (plain Kotlin data classes), DSL builders in `dsl/` (delegate pattern, name inference), codegen visitors in `gbkt-backend-gbdk/.../visitor/` that consume `GenericSystem` with typed `config` maps. Tests exercise visitors directly by constructing `GenericSystem` instances and asserting on `CFunction`/`CVarDecl` outputs. New genre packages follow the same pattern as `gbkt-rpg` but with genre-specific domain models.

The ServiceLoader architecture for genre codegen visitors is the most architecturally novel part of this phase. The decision is that `gbkt-backend-gbdk` does NOT depend on genre modules — genre modules register codegen visitors at runtime. This requires defining a codegen visitor extension point in `gbkt-backend-api` that genre modules implement and register via ServiceLoader, and `GBDKPipelineV2` discovers and invokes those genre visitors alongside its built-in system visitors.

**Primary recommendation:** Build genre modules sequentially (platformer → puzzle → sport → action RPG/roguelike), validate each with DSL+codegen tests before moving to the next; tackle RPG H-items as a single batch since they are existing codegen needing tests only.

### Pattern 1: GenericSystem as Extension Point

All genre-specific IR information flows through `GenericSystem` with a `"type"` key in the config map:

```kotlin
// Example: how genre DSL builder emits IR
class PlatformerBuilder {
    fun build(): GenericSystem = GenericSystem(
        id = id,
        config = mapOf(
            "type" to "platformer_physics",
            "config" to PlatformerPhysicsConfig(
                gravity = 2,
                jumpForce = 10,
                coyoteFrames = 4,
                jumpBufferFrames = 6,
            )
        )
    )
}
```

Codegen visitor dispatches on `"type"`:

```kotlin
class PlatformerVisitor(gameIR: GameIR) {
    fun generatePhysicsFunctions(system: GenericSystem): List<CFunction> {
        val config = system.config["config"] as? PlatformerPhysicsConfig ?: return emptyList()
        // ... generate CFunction nodes
    }
}
```

**Confidence:** HIGH — directly observed in `RpgVisitor.generateEquipmentFunctions()` and all other RPG systems.

### Pattern 2: DSL Delegate for Name Inference

All genre DSL constructs follow the same delegate pattern as actors, scenes, sounds:

```kotlin
// CurrencyDelegate (multi-currency system)
class CurrencyDelegate(val block: CurrencyBuilder.() -> Unit) {
    operator fun provideDelegate(thisRef: GameBuilder, prop: KProperty<*>): CurrencyRef {
        val builder = CurrencyBuilder(prop.name)
        builder.block()
        thisRef.registerCurrency(builder.build())
        return CurrencyRef(prop.name)
    }
    operator fun getValue(thisRef: GameBuilder, prop: KProperty<*>): CurrencyRef =
        CurrencyRef(prop.name)
}

fun GameBuilder.currency(block: CurrencyBuilder.() -> Unit) = CurrencyDelegate(block)

// Usage — name inferred from property

```

**Confidence:** HIGH — directly observed in `ActorDelegate`, `SceneDelegate`, and `StatusEffectDelegate`.

### Pattern 4: ServiceLoader for Genre Visitor Discovery

Current `GBDKPipelineV2` has a `buildSystemFunctions` method that uses `GBDKSystemVisitor` directly. Genre visitor discovery needs to extend this. The cleanest approach (within Claude's discretion) is:

1. Define `GenreSystemVisitor` interface in `gbkt-backend-api`:

```kotlin
interface GenreSystemVisitor {
    fun canHandle(systemType: String): Boolean
    fun visitSystem(system: GenericSystem, gameIR: GameIR): List<CFunction>
    fun visitSystemVarDecls(system: GenericSystem, gameIR: GameIR): List<CVarDecl>
}
```

2. Register in `META-INF/services/io.github.gbkt.backend.api.GenreSystemVisitor` from each genre's codegen module.

3. `GBDKPipelineV2.buildSystemFunctions()` discovers all registered `GenreSystemVisitor` instances before delegating to `GBDKSystemVisitor`:

```kotlin
private fun buildSystemFunctions(gameIR: GameIR): List<CFunction> {
    val genreVisitors = ServiceLoader.load(GenreSystemVisitor::class.java).toList()
    return gameIR.systems.flatMap { system ->
        val genreVisitor = genreVisitors.find {
            it.canHandle((system as? GenericSystem)?.config?.get("type") as? String ?: "")
        }
        genreVisitor?.visitSystem(system as GenericSystem, gameIR)
            ?: system.accept(GBDKSystemVisitor(gameIR))
    }
}
```

**Confidence:** MEDIUM — ServiceLoader pattern is already used for `CodegenBackend` in `BackendRegistry`. The exact `GenreSystemVisitor` interface design is in Claude's discretion.

### Anti-Patterns to Avoid

- **Import genre types into GBDKPipelineV2**: The genre modules must not be compile-time dependencies of `gbkt-backend-gbdk`. Discovery via ServiceLoader maintains the isolation boundary.
- **Putting domain models in IR types**: Genre domain models (PlatformerPhysicsConfig, PuzzleGridConfig, etc.) are plain Kotlin data classes, NOT sealed IR nodes. They travel through `GenericSystem.config` as typed `Any` values.
- **Sealed interfaces for genre types**: Would break the module boundary (Kotlin sealed interfaces require all implementations in the same module).
- **Skipping `build.gradle.kts` detekt baseline**: New modules need a `detekt-baseline.xml` if violations exist. Run `./gradlew :gbkt-genre-xxx:detektBaseline` after adding new code.

## Common Pitfalls

### Pitfall 1: Genre Codegen Module Coupling
**What goes wrong:** Adding `implementation(project(":gbkt-genre-platformer"))` to `gbkt-backend-gbdk/build.gradle.kts` to access `PlatformerPhysicsConfig` in `PlatformerVisitor`.
**Why it happens:** Natural instinct to import types directly.
**How to avoid:** `PlatformerVisitor` lives inside `gbkt-backend-gbdk` and casts `system.config["config"]` to `PlatformerPhysicsConfig` via reflection or by making the genre module a runtime-only dependency discovered via ServiceLoader. Alternatively, `PlatformerVisitor.kt` itself lives in `gbkt-genre-platformer` and accesses `gbkt-backend-gbdk` AST types.
**Warning signs:** `gbkt-backend-gbdk/build.gradle.kts` gains `implementation(project(":gbkt-genre-XXX"))` compile-time dependencies.

**Resolution:** The genre module (`gbkt-genre-platformer`) depends on `gbkt-backend-gbdk` (for C AST types) and registers its `PlatformerVisitor` via ServiceLoader. `gbkt-backend-gbdk` does NOT depend on genre modules. The dependency graph is: `gbkt-genre-platformer → gbkt-backend-gbdk → gbkt-backend-api → gbkt-core`.

### Pitfall 2: Detekt Violations on New Modules
**What goes wrong:** First build of a new genre module fails on Detekt with LongMethod, TooManyFunctions violations.
**Why it happens:** Codegen functions are large by design (CLAUDE.md explains this).
**How to avoid:** Run `./gradlew :gbkt-genre-XXX:detektBaseline` after the module compiles. Add `detekt-baseline.xml` to the module root. Verify `detekt.yml` exclusions cover `**/codegen/**`.
**Warning signs:** `detekt` task fails on first build of new genre module.

### Pitfall 3: Spotless License Header Missing
**What goes wrong:** Build fails with Spotless formatting violation — MPL 2.0 header missing.
**Why it happens:** New files don't automatically get the license header.
**How to avoid:** Run `./gradlew :gbkt-genre-XXX:spotlessApply` after adding new Kotlin files.
**Warning signs:** `spotlessKotlinCheck` task fails.

### Pitfall 4: Module Not in settings.gradle.kts
**What goes wrong:** Gradle fails to resolve `project(":gbkt-genre-platformer")` in dependent modules.
**Why it happens:** New module directory created but not registered in `settings.gradle.kts`.
**How to avoid:** Add `include("gbkt-genre-platformer")` to `settings.gradle.kts` before any module depends on it. Do this as the FIRST step for each new module.
**Warning signs:** `Could not resolve project :gbkt-genre-platformer` build error.

### Pitfall 5: reserveExpShare Has No Var Decl in RpgVisitor
**What goes wrong:** Test for H6 (`reserveExpShare`) fails because there is no emitted global for it.
**Why it happens:** `generatePartyVarDecls` emits `_party_reserve` array and `_party_reserve_count` but may not emit a `_party_reserve_exp_share` constant.
**How to avoid:** Check `RpgVisitor.generatePartyVarDecls()` for `reserveExpShare` handling before writing the test. If missing, add the `CVarDecl` for `_party_reserve_exp_share` as a `const` UINT8.
**Warning signs:** The `reserveExpShare` field exists in `PartyConfig` but has no corresponding codegen output.

### Pitfall 6: CraftingRecipe Uses GBDKSystemVisitor, Not RpgVisitor
**What goes wrong:** H8 test targets wrong visitor.
**Why it happens:** Crafting is in `RpgVisitor.generateCraftingFunctions()` which dispatches on `system.config["type"] == "rpg_crafting"`. The system config uses `"recipes"` key. Looking at `generateCraftingFunctions`:
```kotlin
val recipes = system.config["recipes"] as? List<CraftingRecipe> ?: return emptyList()
```
**How to avoid:** Build the crafting `GenericSystem` with `"type" to "rpg_crafting", "recipes" to listOf(...)`. Test against `RpgVisitor.generateCraftingFunctions()`.
**Warning signs:** Test produces empty function list.

## Open Questions

1. **GenreSystemVisitor interface location**
   - What we know: `gbkt-backend-api` already has `CodegenBackend` as the extension interface; `GenreSystemVisitor` would be a lighter contract for fragment visitors
   - What's unclear: Should `GenreSystemVisitor` return `List<CFunction>` + `List<CVarDecl>` separately, or a combined result type?
   - Recommendation: Define `GenreSystemVisitor` interface in `gbkt-backend-api` returning a result with both functions and var decls; let `GBDKPipelineV2` merge results into the correct compilation units

2. **Where PlatformerVisitor/PuzzleVisitor/SportVisitor live**
   - What we know: The CONTEXT.md says "each genre module provides its own codegen visitors, discovered at build time via ServiceLoader" and "gbkt-backend-gbdk does not need to know about genres"
   - What's unclear: If the visitor lives in `gbkt-genre-platformer`, it needs to reference C AST types (`CFunction`, `CVarDecl`, etc.) from `gbkt-backend-gbdk` — creating a dependency `gbkt-genre-platformer → gbkt-backend-gbdk`
   - Recommendation: Accept this dependency direction; `gbkt-genre-platformer` depends on `gbkt-backend-gbdk` (runtime); `gbkt-backend-gbdk` does not depend on any genre module at compile time

3. **reserveExpShare codegen gap (H6)**
   - What we know: `PartyConfig.reserveExpShare` field exists as `Int = 50` but `generatePartyVarDecls()` does not emit a `_party_reserve_exp_share` constant (verified by code review of lines 1482–1521)
   - What's unclear: Whether this is intentional (EXP sharing is always 50%) or an oversight
   - Recommendation: Add `CVarDecl(name = "_party_reserve_exp_share", type = CU8, initializer = CLiteral(config.reserveExpShare), isConst = true)` to `generatePartyVarDecls()` when `enableReserve = true`, then write the H6 test

4. **Action RPG / Roguelike combat style IR representation**
   - What we know: These are promoted to first-class styles. The existing `CombatEngineSystem` IR type handles combat — action RPG would need real-time combat IR
   - What's unclear: Does promoting to first-class require new IR types in `gbkt-ir` module, or can it remain GenericSystem-based?
   - Recommendation: Use `GenericSystem` with `"type" to "arpg_combat"` for now; real-time combat with cooldowns fits as a system config; defer new sealed IR types unless required for type safety

5. **Roguelike run lifecycle scope**
   - What we know: permadeath + run start/end + SRAM meta-progression
   - What's unclear: How roguelike run state integrates with existing `RpgSaveConfig` — roguelite meta-progression across runs requires SRAM
   - Recommendation: Add `RoguelikeConfig` to `gbkt-genre-rpg` domain; use existing `RpgSaveConfig` for roguelite SRAM persistence; run-local state uses WRAM only (no persistence on death in pure roguelike mode)
