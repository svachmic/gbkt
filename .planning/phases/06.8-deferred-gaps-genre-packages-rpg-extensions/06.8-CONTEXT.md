# Phase 06.8: Genre Packages & RPG Extensions - Context

**Gathered:** 2026-02-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Build three new genre packages (platformer, puzzle, sport/racing) as independent Gradle modules with type-safe DSL constructs. Promote action RPG and roguelike to first-class RPG combat styles. Validate all existing RPG opt-in extensions (equipment upgrades/durability/enchanting, ability mastery/evolution, party reserve/formation, crafting, auto-save, New Game+) with codegen tests. Implement multi-currency system. Rename `gbkt-rpg` to `gbkt-genre-rpg` for naming consistency.

**Depends on Phase 06.7** — entity pooling, physics movement, and collision response primitives are prerequisites for platformer and action RPG mechanics.

</domain>

<decisions>
## Implementation Decisions

### Platformer package (`gbkt-genre-platformer`)
- Variable-height jump model (hold = higher, release = cut short)
- Full platform type set: solid, one-way, moving, crumbling
- Both scrolling camera modes selectable per scene: smooth follow with dead zone AND screen-lock (room-based)
- All scroll directions supported: horizontal, vertical, multi-directional
- Full physics config exposed in DSL: gravity, jump force, terminal velocity, coyote time, jump buffer, air control factor
- Opt-in wall-jump / wall-slide with configurable i-frame duration and cooldown
- Tile/region hazard markers — touching triggers damage/death callback
- Parallax background layers with configurable scroll speeds per layer
- Opt-in ladder/climbing tile type — player switches to climbing state when overlapping
- Goal zone / trigger regions for level completion callbacks (pairs with scene transitions)
- Collectible helpers — DSL sugar for coins, power-ups, checkpoints (built on shared pickup system in gbkt-engine)

### Puzzle package (`gbkt-genre-puzzle`)
- Grid-based system supporting both match and block-push modes via mode switch (single grid construct, not separate APIs)
- Match mode: 3+ in a row/column matching with configurable minimum match length
- Configurable gravity direction for piece falling after clears (down, up, or none)
- Built-in chain counter + score multiplier for cascading matches
- Extensible cell type system: base types (normal, empty, wall) built-in, users register custom types with behaviors (bomb, wildcard, ice, etc.)
- Block-push mode: move validation, goal tiles, full undo stack (unlimited by default, developer can limit depth)
- Opt-in timer (countdown or elapsed) and move counter for scoring

### Sport/Racing package (`gbkt-genre-sport`)
- Targets both racing and ball sport sub-genres
- Racing: tile-based track with waypoint markers for laps/checkpoints, fits existing tilemap/zone system
- Racing: both time trial mode and AI opponent mode (developer picks)
- Racing AI: waypoint-following with configurable speed/difficulty, optional rubber-banding
- Racing: vehicle stats config (speed, acceleration, handling) — different vehicles with different profiles
- Ball sport: field + ball + scoring rules abstraction (dimensions, goals/nets, ball physics, match structure)
- Match/tournament structure: match → round → season/tournament, bracket tracking (single-elim, round-robin), standings
- Pickup system for power-ups during gameplay (speed boost, shield, etc.) — uses shared pickup system from gbkt-engine

### Action RPG / Roguelike styles
- Both combat models supported, developer picks:
  - Real-time with cooldowns (attacks in real-time, abilities have cooldown timers, damage on collision/hit frames)
  - Hybrid ATB (turn-based with real-time gauges, faster ATB bar = acts sooner)
- Dodge roll with invincibility frames — configurable i-frame duration and cooldown
- Behavior preset AI for enemies: chase(range), patrol(path), attackWhenClose(range), flee(hpThreshold) — composable
- Stamina/energy system reusing existing exploration gauge infrastructure — actions consume stamina, regenerates over time
- Roguelike: permadeath + run lifecycle (start run / end run / death = wipe)
- Roguelike: seed-based RNG for reproducible procedural generation
- Roguelike: both modes supported — pure roguelike (no persistence) and roguelite (unlock-based meta-progression across runs via SRAM)
- Roguelike: daily challenge system with date-based seed for reproducible daily dungeons
- Roguelike: room-clear gating as a room/floor property — exits lock until all enemies defeated

### Multi-currency system
- Type-safe delegate pattern: `val gold by currency { max(9999) }` — CurrencyRef used everywhere, no magic strings
- Named currencies in economy block, name inferred from Kotlin property (same pattern as actors, scenes, sounds)
- Configurable exchange rates between currencies: `exchange(from = gems, to = gold, rate = 10)`
- Per-item currency pricing in shops: `buyPrice(50, currency = gems)` — different items in same shop can use different currencies
- Per-drop currency from monsters: `drops { drop(gold, amount = 50); drop(gems, amount = 1, chance = 10) }`
- Currency translations pulled from .po files during compilation (existing localization system)

### Package separation & architecture
- Rename `gbkt-rpg` → `gbkt-genre-rpg` for naming consistency across all genre packages
- Separate Gradle module per genre: `gbkt-genre-rpg`, `gbkt-genre-platformer`, `gbkt-genre-puzzle`, `gbkt-genre-sport`
- Genres are composable — a game can mix multiple genre packages (e.g. puzzle-platformer)
- Each genre module provides its own codegen visitors, discovered at build time via ServiceLoader — `gbkt-backend-gbdk` does not need to know about genres
- All genre packages included in `gbkt-bom` version constraints (genres build on top of core)
- All genre packages included in `gbkt-all` convenience meta-module
- Shared pickup/collectible system lives in `gbkt-engine` (generic actor interaction pattern, not genre-specific) — genre packages define WHAT pickups do, engine defines HOW they work

### RPG extension validation (H1–H10)
- These are existing domain models + codegen that need codegen test validation. No new design decisions needed:
  - H1: Equipment upgrade/enchant (`EquipmentConfig.enableUpgrades` / `enableEnchanting`)
  - H2: Equipment durability (`EquipmentConfig.enableDurability`)
  - H3: Equipment elemental affinity (`EquipmentDef.aspect`)
  - H4: Ability mastery (`AbilityLearningConfig.enableMastery`)
  - H5: Ability evolution chains (`AbilityLearningConfig.evolutionChains`)
  - H6: Party reserve/bench + EXP sharing (`PartyConfig.enableReserve`, `reserveExpShare`)
  - H7: Row-based formation (`PartyConfig.enableRowFormation`)
  - H8: Crafting module (`rpg_crafting` system in `GBDKSystemVisitor`)
  - H9: Auto-save triggers (`RpgSaveConfig.autoSaveEnabled`)
  - H10: New Game+ (`RpgSaveConfig.enableNewGamePlus`)

</decisions>

<specifics>
## Specific Ideas

- Currency DSL should follow the same type-safe delegate pattern as actors, scenes, and sounds — `val gold by currency { }` with name inferred from property, returning a typed CurrencyRef
- Cross-genre pickup system: platformer coins/power-ups and racing item boxes both use the same shared engine pickup construct — avoid duplication
- Puzzle undo should be "full by default, developer-limitable" — not a fixed depth
- "Both modes, developer picks" philosophy applies broadly: scroll modes, combat styles (ARPG/ATB), roguelike persistence — the DSL exposes options, the developer configures
- BoM pattern like Spring Boot starters: `platform(gbkt-bom)` for version alignment, cherry-pick genres or use `gbkt-all`

</specifics>

<deferred>
## Deferred Ideas

- Cross-genre shared module (`gbkt-genre-shared` with internal visibility) — decided against for now, shared constructs live in `gbkt-engine`. Revisit if genre packages develop more shared patterns that don't belong in engine.
- Sport-specific presets (tennis rules, soccer rules, basketball rules) — current approach is generic field + ball + scoring. Presets could be a future convenience layer.
- Procedural track generation for racing — current approach uses hand-crafted tile-based tracks with waypoints.

</deferred>
