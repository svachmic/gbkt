## Failure A — Root Cause (D-01)

### Verdict: CONFIRMED — Frame-boundary VBlank collision prevents `update_joypad()` from seeing START

**H-A1 (DISPLAY_OFF stall):** PARTIALLY SUPPORTED for Failure B, but NOT the primary cause of Failure A.  
**H-A2 (guard override):** FALSIFIED.  
**H-A3 (Coffee-GB joypad strobe):** REFINEMENT REQUIRED — the root cause is deeper than the joypad strobe but traces through the frame-boundary model.

**True Failure A root cause: Frame-boundary collision — `nextLevelScene_enter()` called by the main-loop guard AFTER `nextLevelScene_frame()` consumes the VBlank slot, so `update_joypad()` sees joypad state WITHOUT START in the frame where START is physically pressed by the harness.**

### Why `__joypad` is 0x00 after pressing START — the frame-boundary collision

The GBDK main loop in generated `main.c:760-780`:

```c
while (1) {
    update_joypad();                        // A: reads joypad → sets __joypad
    switch (current_scene) {
    case SCENE_NEXTLEVELSCENE:
        nextLevelScene_frame_trampoline();  // B: checks button_pressed(J_START)
        break;
    }
    if (_next_level != _current_level) {    // C: guard — TRUE (1 != 0)
        navigate_to_scene(SCENE_NEXTLEVELSCENE);  // D: calls nextLevelScene_enter()
    }
    update_sprites();
    sound_driver_update();
    wait_vbl_done();                        // E: VBlank sync
}
```

Coffee-GB's `stepFrame()` runs until `frameDone = true`, which occurs when VBlank fires. VBlank is a hardware interrupt that fires ~60 times/second at the end of each frame's display period. In the emulated ROM, VBlank can fire at ANY POINT during the main loop body — not just at `wait_vbl_done()`.

**The frame-boundary collision mechanism:**

During the `nextLevelScene_enter()` call at step D (invoked by the guard EVERY FRAME because `_next_level (1) != _current_level (0)`), the following VRAM operations run:

```c
// bank1.c:73-81 — nextLevelScene_enter() VERIFIED from live generated file
void nextLevelScene_enter(void) BANKED {
    set_bkg_data(0u, _zone_nextLevelZone_tileset_count, _zone_nextLevelZone_tileset);
    set_bkg_palette(0u, ...);
    hide_sprites_range(0u, MAX_HARDWARE_SPRITES);
    move_bkg(0u, 0u);
    fill_bkg_rect(0u, 0u, 32u, 32u, 0u);   // ← 1024-cell BG plane fill
    _bkg_tiles_load_banked(2u, ..., _zone_nextLevelZone_tilemap); // ← tilemap write
    DISPLAY_ON;
}
```

`fill_bkg_rect(0u, 0u, 32u, 32u, 0u)` fills all 1024 cells of the BG map. `_bkg_tiles_load_banked` calls `set_bkg_tiles()`. These are tile-map writes to VRAM area 0x9800-0x9BFF, which can only be written during H-blank or V-blank. GBDK's `set_bkg_tiles` writes tiles per H-blank slot. A 32×32 full-plane fill spans many H-blank and V-blank windows, potentially crossing the VBlank boundary of the current frame.

When VBlank fires during `nextLevelScene_enter()` (inside `fill_bkg_rect` or `_bkg_tiles_load_banked`), Coffee-GB's `gb.tick()` returns `frameDone = true`, and `stepFrame()` exits immediately. The ROM's instruction pointer is LEFT INSIDE `nextLevelScene_enter()`. The `wait_vbl_done()` at step E is NEVER REACHED in this iteration.

**Frame boundary state when `stepFrame()` returns mid-`nextLevelScene_enter()`:**
- `__joypad` = value from `update_joypad()` call at step A (no buttons, since guard-enter is before START is pressed)
- The iteration has ALREADY consumed `update_joypad()` for this frame

**StepAgent's next call — `step(setOf(Button.START))`:**
1. Registers START in `Joypad.buttons` via `executeInputScript(inputScript { hold(START) })`
2. Calls `runFrames(1)` → `stepFrame()`
3. The ROM resumes from INSIDE `nextLevelScene_enter()` (where it stopped)
4. Completes `nextLevelScene_enter()`, returns to guard check
5. `_next_level (1) != _current_level (0)` → STILL TRUE → calls `nextLevelScene_enter()` AGAIN
6. VBlank fires again during this second `nextLevelScene_enter()` → `stepFrame()` returns
7. `update_joypad()` for the frame with START pressed was NEVER called

**Result:** The frame that runs during `step(setOf(Button.START))` never calls `update_joypad()` with START held. The next frame (after START is released) does call `update_joypad()` but `Joypad.buttons` no longer contains START (heldButtons is cleared between steps). `__joypad` stays 0x00. `button_pressed(J_START)` never fires.

**This confirms the Research Finding 3 MCP-vs-harness divergence framing is correct in spirit (the VBlank model is the root), but the exact mechanism is more specific: it is the main-loop GUARD calling `nextLevelScene_enter()` after the frame function that causes the VBlank to fire mid-iteration, displacing `update_joypad()` from the frame boundary.**

## Failure B — Root Cause (D-01)

### Verdict: CONFIRMED — Missing DISPLAY_OFF/DISPLAY_ON in `setup_current_level()` + display ON during VRAM map write

**Root cause:** `setup_current_level()` emits `_bkg_set_level_submap_banked(0u, 0u, 21u, 18u)` (which calls `set_bkg_submap`) while `LCDC_REG bit7 = 1` (display ON). Writing the BG tilemap to VRAM area 0x9800-0x9BFF while the LCD is active results in silent discard or incomplete write in Coffee-GB, producing a near-blank frame (0.983 dominant ratio, 661 bytes).

No `DISPLAY_OFF` before the `switch`. No `DISPLAY_ON` at the end of the function.

`_bkg_set_level_submap_banked` (main.c:119-124):

`set_bkg_submap` writes tile-index values to the BG map area (VRAM 0x9800-0x9BFF). This area is ONLY accessible during Mode 0 (H-blank), Mode 1 (V-blank), or Mode 2. With LCDC.7=1 (display ON, confirmed by probe: `LCDC_REG @ 0xFF40 = 0xC7`) and the LCD in Mode 3 (active scanline), writes to 0x9800-0x9BFF are blocked or corrupted.

Both occurrences are inside the `void main()` startup block (lines 746-781), NOT inside `setup_current_level()`. File-level grep count alone would report 2 occurrences — but BOTH are in the wrong function (Pitfall 2 from RESEARCH).

### Why Failure B was NOT triggered in the boot path (anchor 1 passes)

The runtime probe (Phase 5) confirms `LCDC_REG = 0xC7` (display ON) when `setup_current_level()` is called from the card path. At boot (title→gameplay), `title_enter()` calls `DISPLAY_ON` and `gameplay_enter()` calls `setup_current_level()` once. The SINGLE call at boot likely completes within one VBlank window — Coffee-GB's timing model may allow this. The DOUBLE call from the card path (card START-press + gameplay_enter) stresses the timing more, but **Failure A means we never actually reach the double-call in the harness** — the harness never gets past `button_pressed(J_START)` firing.

However, Failure B is independently real: even in a single-call context, if the LCD is active during `_bkg_set_level_submap_banked`, the write can be lost. The boot path (anchor 1) "works" because either: (a) the first `setup_current_level()` at title→gameplay happens to land in a VBlank window, or (b) Coffee-GB's VRAM access simulation is permissive for the single-call case. The fix (adding DISPLAY_OFF/ON) will make BOTH paths correct regardless of timing.

### Fix Site 2 (Failure A — frame-boundary collision): Main-loop guard ordering

**Root cause confirmed:** The main-loop guard `if (_next_level != _current_level) { navigate_to_scene(SCENE_NEXTLEVELSCENE); }` fires EVERY FRAME while on the card scene, calling `nextLevelScene_enter()` which performs VRAM writes that consume the VBlank slot AFTER `nextLevelScene_frame()` runs. This displaces `update_joypad()` from the frame boundary.

**Fix approach for Failure A:** Once `DISPLAY_OFF`/`DISPLAY_ON` is added to `setup_current_level()`, the VRAM writes are serialized within VBlank windows. The critical remaining issue for Failure A is the guard-driven `nextLevelScene_enter()` consuming VBlank every frame on the card scene.

Two fix options for Failure A:
- **Option A (preferred):** Guard the main-loop `navigate_to_scene(SCENE_NEXTLEVELSCENE)` call so it does NOT re-fire on EVERY frame when already on the card scene. The guard should only fire when scene is NOT already `SCENE_NEXTLEVELSCENE`. This prevents the VBlank-consuming enter from being called redundantly. Fix in `GBDKPipelineV2.buildMainLoopLevelSwitchGuardIfNeeded`.
- **Option B:** Add `DISPLAY_OFF`/`DISPLAY_ON` around `nextLevelScene_enter()`'s `fill_bkg_rect` + `_bkg_tiles_load_banked` calls, so the VBlank-consuming writes are bounded and don't spill across the main loop iteration boundary. Fix in `GBDKPipelineV2.buildSetupCurrentLevelFunctionIfNeeded` (already the B-site) + scene-enter codegen.

**RECOMMENDATION: Option A is the correct fix.** The guard at `main.c:773-775` fires `navigate_to_scene(SCENE_NEXTLEVELSCENE)` unconditionally whenever `_next_level != _current_level`, even when `current_scene` is ALREADY `SCENE_NEXTLEVELSCENE`. This means `nextLevelScene_enter()` runs EVERY FRAME while the player is on the card scene, performing expensive VRAM writes (fill_bkg_rect 32×32 + _bkg_tiles_load_banked) 30+ times before the player can press START. The fix: change the guard to:

```c
if (_next_level != _current_level && current_scene != SCENE_NEXTLEVELSCENE) {
    navigate_to_scene(SCENE_NEXTLEVELSCENE);
}
```

This preserves the guard's purpose (navigate to card when level changes) while preventing the redundant re-entry VBlank collision. Fix site: `GBDKPipelineV2.buildMainLoopLevelSwitchGuardIfNeeded`.

### Redundant `gameplay_enter` call — benign once DISPLAY_OFF is added

The double `setup_current_level()` call (card + gameplay_enter) becomes SAFE once DISPLAY_OFF/ON is added inside `setup_current_level()`. Each call independently turns display off, writes VRAM, turns display on. The second call is redundant work but not harmful. Per Research Open Question 2 / Pitfall 3: **DO NOT remove `setup_current_level()` from `gameplay_enter()`** — it is required for the boot path (title→gameplay). Keep it; the DISPLAY_OFF/ON wrapper makes it idempotent.

## Summary — Root Cause Verdicts

### Failure A: `_current_level` stuck at 0 in harness

**Root cause: Frame-boundary VBlank collision.**

The main-loop guard calls `navigate_to_scene(SCENE_NEXTLEVELSCENE)` → `nextLevelScene_enter()` EVERY FRAME while on the card scene (because `_next_level=1 != _current_level=0`). `nextLevelScene_enter()` contains `fill_bkg_rect(32,32)` + `_bkg_tiles_load_banked(...)`, which perform tile-map writes spanning VBlank. When VBlank fires during these writes, Coffee-GB's `stepFrame()` returns with the ROM paused INSIDE `nextLevelScene_enter()`. The next `step()` call (which carries the START press) resumes from there, completes the guard enter, then returns when the NEXT VBlank fires — without ever reaching `update_joypad()` for the frame where START was pressed. `button_pressed(J_START)` evaluates to 0 every frame. Navigation to gameplay never occurs.

**Fix: Guard the main-loop `navigate_to_scene(SCENE_NEXTLEVELSCENE)` call to NOT re-fire when already on the card scene.** Corrected generated-C: `if (_next_level != _current_level && current_scene != SCENE_NEXTLEVELSCENE) { navigate_to_scene(SCENE_NEXTLEVELSCENE); }`

**Fix site: `GBDKPipelineV2.buildMainLoopLevelSwitchGuardIfNeeded`**

### Failure B: Near-blank level-2 BG in harness

**Root cause: `setup_current_level()` calls `_bkg_set_level_submap_banked()` (which calls `set_bkg_submap`) while `LCDC.7 = 1` (display ON). VRAM BG map writes while display is active are dropped or corrupted in Coffee-GB, producing a 98.3% near-blank frame.**

**Fix: Wrap `setup_current_level()` with `DISPLAY_OFF` before the switch and `DISPLAY_ON` after the switch.** This mirrors the GBDK reference contract exactly.

**Fix site: `GBDKPipelineV2.buildSetupCurrentLevelFunctionIfNeeded`**

### MCP-vs-harness divergence

Phase 12.9's G3 approval used direct MCP capture. The MCP agent either (a) started at a different scene, or (b) navigated to level-2 via a path that did not go through the card scene. In the MCP single-call path, `gameplay_enter()` → `setup_current_level()` runs once at a time when Coffee-GB's timing model allows the VRAM write to succeed (VBlank available). The harness ALWAYS goes through the card scene (D-02 ground-truth), producing the VBlank collision that prevents Failure A from resolving and the display-ON VRAM write that causes Failure B.
