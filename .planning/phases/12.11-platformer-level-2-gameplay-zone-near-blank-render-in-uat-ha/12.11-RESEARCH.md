## Summary

Phase 12.11 owns two entangled defects in the level-1 → nextLevel-card → level-2 path. Both are
codegen/runtime defects, not harness defects (Phase 12.10 proved that).

**Failure A (logic — `_current_level` stuck at 0):** The harness holds START for 4 frames on the
card scene. The generated C `nextLevelScene_frame()` checks `button_pressed(J_START)` correctly.
However, `setup_current_level()` is called twice per level-switch — once from `nextLevelScene_frame`
(the card's START-press handler) and a second time immediately after from `gameplay_enter()` (called
by `navigate_to_scene(SCENE_GAMEPLAY)`). The critical risk is whether the double VRAM-write sequence,
with the DISPLAY in an uncertain state (no DISPLAY_OFF/DISPLAY_ON wrapping in `setup_current_level`),
causes `set_bkg_data`/`set_bkg_submap` to stall or enter a wait-for-VBlank loop that never returns,
leaving `current_scene` stuck on `nextLevelScene` from the perspective of the main-loop guard. The
GBDK reference always wraps the level-load sequence in explicit `DISPLAY_OFF` / `DISPLAY_ON` around
`SetupCurrentLevel()` + `SetCurrentLevelSubmap()`. The generated `setup_current_level()` does neither.

**Failure B (render — near-blank BG):** Even when the level-2 scene IS reached, the BG is blank
(0.983 dominant ratio). The GBDK reference `SetCurrentLevelSubmap()` is called AFTER an explicit
`DISPLAY_OFF`, so the BG-submap write happens safely with the LCD off. The generated
`setup_current_level()` calls `_bkg_set_level_submap_banked()` with the display ON (LCD state from
the preceding `nextLevelScene_enter` DISPLAY_ON). Writing the tilemap to VRAM while the LCD is
active may cause the Coffee-GB emulator to discard or corrupt the VRAM write, producing a blank
frame.

**Primary recommendation:** Wrap the VRAM-write operations in `setup_current_level()` with
`DISPLAY_OFF` before and `DISPLAY_ON` after — exactly mirroring the GBDK reference. Simultaneously
remove the duplicate `setup_current_level()` call from `gameplay_enter()` (the function is already
called by the card's START-press handler; calling it again from `gameplay_enter` is redundant and
produces a double VRAM write). These two codegen changes, verified by the DIAGNOSE plan first, are
the fix candidates for both A and B.

### Pattern: Brace-Walk Scope Extraction (existing, D-04 mandatory)

The per-file `extractFunctionBody(source, signaturePrefix)` helper used in `LevelCardSceneEmissionTest`:

```kotlin
// Source: LevelCardSceneEmissionTest.kt:110-130 (VERIFIED: codebase read)
private fun extractFunctionBody(cSource: String, functionSignaturePrefix: String): String {
    val lines = cSource.lines()
    val startIdx = lines.indexOfFirst { it.startsWith(functionSignaturePrefix) }
    if (startIdx == -1) return ""
    val body = StringBuilder()
    var depth = 0
    var started = false
    for (i in startIdx until lines.size) {
        val line = lines[i]
        body.appendLine(line)
        for (ch in line) {
            if (ch == '{') { depth++; started = true }
            if (ch == '}') depth--
        }
        if (started && depth == 0) break
    }
    return body.toString()
}
```

**Per CLAUDE.md scope-grep corollary (D-04 mandate):** All D-04 emission assertions MUST use this
brace-walk helper. A file-level `grep -c DISPLAY_OFF main.c` cannot distinguish `setup_current_level`
from `nextLevelScene_enter` or `main()`.

**Key insight:** The REFERENCE's `SetupCurrentLevel()` does NOT call `set_bkg_tiles` / `set_bkg_submap`
internally. It only calls `SWITCH_ROM` + `set_native_tile_data` (tileset) + `setBKGPalettes`. The
submap write (`SetCurrentLevelSubmap`) is a SEPARATE call, protected by the explicit DISPLAY_OFF
wrapping from the caller. The gbkt `setup_current_level()` combines BOTH the tileset load AND the
submap write into one function, but does NOT emit the required DISPLAY_OFF / DISPLAY_ON around it.

### Anti-Patterns to Avoid

- **VRAM writes with display ON:** `set_bkg_data`, `set_bkg_palette`, `_bkg_set_level_submap_banked`
  all write to VRAM or palette RAM. On real GB hardware and Coffee-GB, these writes are only safe
  during VBlank or when LCDC.7=0 (display off). Writing while display is active produces blank/corrupt
  output. [VERIFIED: GBDK reference; ASSUMED: Coffee-GB specific behavior]
- **Double `setup_current_level()` call:** The card's START-press handler calls
  `setup_current_level()` then `navigate_to_scene(SCENE_GAMEPLAY)` → `gameplay_enter()` →
  `setup_current_level()` again. This is a redundant second VRAM write that doubles the risk of
  display-timing corruption and may cause stall issues in the Coffee-GB emulator.
- **File-level grep for scope-specific invariants:** Using `grep -c "DISPLAY_OFF" main.c` instead
  of brace-walking `setup_current_level` will match other functions and produce false positives.

## Diagnostic Finding 1: `button_pressed(J_START)` mechanics in the harness

**[VERIFIED: codebase read — StepAgent.kt, InputScriptPlayer.kt, EventBusImpl.java, Joypad.java]**

`StepAgent.step(setOf(Button.START))`:
1. Computes delta: `toPress = {START} - heldButtons (empty)` = `{START}`
2. `executeInputScript(inputScript { hold(START) })` → `InputScriptPlayer.play()` → `eventBus.post(ButtonPressEvent(START))`
3. `EventBusImpl.post()` is SYNCHRONOUS — calls `Joypad.onPress(START)` immediately within the `post()` call
4. `Joypad.buttons.add(START)` — START is now in the hardware joypad set
5. THEN `runFrames(1)` advances one emulator frame

Within that frame:
- `update_joypad()`: `__joypad_prev = __joypad` (was 0, no buttons previous frame), `__joypad = joypad()` (returns J_START because `Joypad.buttons` contains START with `line=0x20`)
- `button_pressed(J_START)` = `__joypad & J_START & ~(__joypad_prev & J_START)` = `J_START & J_START & ~0` = J_START ≠ 0 → **FIRES**

**Conclusion:** `button_pressed(J_START)` DOES fire on the first frame with START held, given 30+ settle frames prior with no buttons. This path is sound in isolation. Failure A does NOT stem from the harness joypad model.

**Diagnostic probe for DIAGNOSE plan:** Read `agent.readMemory(0xC0C5)` (= `__joypad`) and
`agent.readMemory(0xC0C6)` (= `__joypad_prev`) in the frame AFTER `agent.step(setOf(Button.START))`
to confirm J_START (0x08) is in `__joypad` and 0 in `__joypad_prev`. Also read `agent.readMemory(0xC0EF)`
(`_current_level`) and `agent.readMemory(0xC0E4)` (`current_scene`) at that same frame.

Memory addresses from `.noi` file [VERIFIED: live `.noi` file read]:
- `__joypad @ 0xC0C5`
- `__joypad_prev @ 0xC0C6`
- `_current_level @ 0xC0EF`
- `_next_level @ 0xC0F0`
- `current_scene @ 0xC0E4`
- `LCDC_REG @ 0xFF40` (hardware register — bit 7 = 1 when display ON)

## Diagnostic Finding 2: Double `setup_current_level()` call

**[VERIFIED: live generated bank1.c and main.c read]**

The current generated C has:

```c
// bank1.c — Scene: nextLevelScene (card scene)
void nextLevelScene_frame(void) BANKED {
    if (button_pressed(J_START)) {
        setup_current_level();           // ← CALL 1: from card START-press
        navigate_to_scene(SCENE_GAMEPLAY);
    }
}

// bank1.c — Scene: gameplay
void gameplay_enter(void) BANKED {
    setup_current_level();              // ← CALL 2: from gameplay_enter, redundant
}
```

`navigate_to_scene(SCENE_GAMEPLAY)` in main.c calls `gameplay_enter_trampoline()` → `gameplay_enter()` → CALL 2.

**Effect of double call:**
- Call 1: `_current_level = _next_level = 1`, `set_bkg_data(world2Area1Zone)`, `set_bkg_palette(...)`, `_bkg_set_level_submap_banked(0,0,21,18)` — display ON
- Call 2: same operations again immediately — display still ON

Both calls happen within the SAME emulator frame (no `wait_vbl_done()` between them). This produces two consecutive VRAM-write sequences without any synchronization. Whether the second one succeeds depends entirely on whether the first one left the hardware in a consistent state.

**Competing hypotheses for Failure A:**
- H-A1 (`display_off` stall): `set_bkg_data` or `set_bkg_submap` internally waits for VBlank before writing, and with the display ON, the wait loop blocks for a full frame. If the Coffee-GB emulator advances to the next VBlank WITHIN the frame tick budget, the call completes but the scene may transition correctly. If the VRAM write stalls and the emulator's `maxTicksPerFrame` watchdog fires, the frame hangs and Coffee-GB throws `EmulatorFrameHangException`. [ASSUMED: Coffee-GB-specific behavior; needs MCP runtime probe]
- H-A2 (guard override): `button_pressed(J_START)` fires, `setup_current_level()` and `navigate_to_scene(SCENE_GAMEPLAY)` both complete, but there's an issue with `gameplay_enter()`'s second `setup_current_level()` call that corrupts `_current_level` or the scene index. [LESS LIKELY: both calls set `_current_level = _next_level = 1` and the guard check is `_next_level != _current_level` which would be FALSE after either call]
- H-A3 (Coffee-GB joypad read boundary): The emulator's joypad hardware strobe (`p1` register) may not be set to select the action button row (line=0x20) when `joypad()` runs, causing `button_pressed(J_START)` to read 0 (J_START not reflected). This could happen if `nextLevelScene_enter()` (called by the guard EVERY FRAME before the frame function) corrupts the P1_REG state. [LOW CONFIDENCE: ASSUMED; standard GBDK `joypad()` strobes both rows]

**Most likely Failure A cause (H-A1):** The `set_bkg_data` + `_bkg_set_level_submap_banked` calls inside `setup_current_level()` perform VRAM writes while the display is ON. In Coffee-GB's emulation of the GB/GBC VRAM access window model, VRAM writes outside VBlank are blocked. The GBDK library functions `set_bkg_data` and `set_bkg_submap` do NOT internally call `display_off()` (VERIFIED: GBDK2020 reference `level.c` shows `DISPLAY_OFF` is the caller's responsibility). However, they DO use wait-for-VBlank routines internally via the DMA transfer mechanism. With the display ON, the VRAM write may complete only during VBlank. If the VRAM write for the first call consumes a VBlank slot, the second call (from `gameplay_enter`) needs another VBlank. Combined, two `setup_current_level()` calls could consume 2 VBlanks worth of time — spanning 2 emulator frames. During this stall, the scene has already been set to `SCENE_GAMEPLAY` by `navigate_to_scene`, but the guard checks AFTER the scene-frame function returns. If the stall causes the emulator to abort the frame early, `current_scene` may be reset to `SCENE_NEXTLEVELSCENE` by a partial execution.

**Diagnostic probe:** MCP `emulator_screenshot` + `emulator_assert` to read `LCDC_REG @ 0xFF40`
(bit 7 = display on/off), `__joypad @ 0xC0C5`, `current_scene @ 0xC0E4`, `_current_level @ 0xC0EF`
at the exact START-press frame. Confirm whether display is ON/OFF when `setup_current_level` runs
and whether `button_pressed` is actually firing.

## Diagnostic Finding 3: The DISPLAY_OFF/DISPLAY_ON gap — primary Failure B root cause

**[VERIFIED: GBDK2020 reference source — `/Users/michalsvacha/gbdk/examples/cross-platform/platformer_template/src/main.c`]**

The GBDK reference wraps the entire level-load sequence in explicit `DISPLAY_OFF` / `DISPLAY_ON`:

```c
// GBDK reference main.c:58-71 — VERIFIED: installed GBDK2020 source
currentLevel = nextLevel;
DISPLAY_OFF;                        // ← explicit, caller-side display management
SetupCurrentLevel();                // tileset data only; no BG map writes
camera_x = 0;
SetCurrentLevelSubmap(0,0,21,18);   // BG map write — happens AFTER display is off
DISPLAY_ON;                         // ← explicit re-enable
```

gbkt's generated `setup_current_level()` does NOT emit `DISPLAY_OFF` before or `DISPLAY_ON` after:

```c
// Generated main.c:145-406 — VERIFIED: live generated C read
void setup_current_level(void) NONBANKED {
    _current_level = _next_level;
    switch (_current_level % 3u) {
    case 2:  // zone: world2Area1Zone
        _current_area_bank = 2u;
        _current_level_map = _zone_world2Area1Zone_tilemap;
        _current_level_width_in_tiles = _zone_world2Area1Zone_tilemap_WIDTH;
        _current_level_height = _zone_world2Area1Zone_tilemap_HEIGHT * 8u;
        _current_level_width = _zone_world2Area1Zone_tilemap_WIDTH * 8u;
        _current_level_non_solid_tile_count = 68u;
        set_bkg_data(0u, _zone_world2Area1Zone_tileset_count, _zone_world2Area1Zone_tileset);
        set_bkg_palette(0u, _zone_world2Area1Zone_tileset_PALETTE_COUNT, ...);
        _bkg_set_level_submap_banked(0u, 0u, 21u, 18u);   // ← VRAM write, display ON
        _playerX = ...; _playerY = ...; _playerVx = 0; _playerVy = 0; _grounded = 0;
        _camera_x = 0; _old_camera_x = 0;
        break;
    // ... case 0, case 1 same structure
```

**There is no `DISPLAY_OFF` before the VRAM writes, no `DISPLAY_ON` after.**

**MCP-vs-harness divergence explanation (D-03):** Phase 12.9's G3 gates were approved via direct
MCP capture, not the UAT harness. In a direct MCP session, the level-2 level may have been reached
differently — e.g., by starting the game fresh at boot (where `gameplay_enter` calls
`setup_current_level` once, with the display potentially in a DIFFERENT state from the title screen
path). At boot, `title_enter` calls `DISPLAY_ON`, the display is ON. When the user presses START
on the title, `navigate_to_scene(SCENE_GAMEPLAY)` → `gameplay_enter()` → `setup_current_level()`.
At this point there's only ONE call (no prior card-scene call). This single-call path may work
because Coffee-GB's timing model handles one VRAM write per frame correctly, while two back-to-back
calls (card START-press + gameplay_enter) exceed the single-VBlank budget.

The harness goes through the card scene (anchor5 explicitly navigates via the card), producing the
double-call path. MCP direct capture may have bypassed the card entirely. This is the key
MCP-vs-harness divergence that D-03 mandates diagnosing first.

**Anchor 1 passes despite missing DISPLAY_OFF:** Anchor 1 (title→gameplay) works because:
1. Only ONE `setup_current_level()` call (from `gameplay_enter` at title→gameplay navigate)
2. Coffee-GB may complete the VRAM write successfully in the single-call case within one VBlank

This explains why the DISPLAY_OFF/ON gap is not fatal for the boot path but IS fatal for the
two-call card-scene path.

## Diagnostic Finding 4: `setup_current_level` VRAM write order vs. GBDK reference

**[VERIFIED: live generated C + GBDK reference source]**

gbkt `setup_current_level` order for case 2 (world2Area1Zone):
1. Set metadata globals (`_current_area_bank`, `_current_level_map`, etc.)
2. `set_bkg_data(...)` — uploads tileset to VRAM tile data
3. `set_bkg_palette(...)` — uploads palette
4. `_bkg_set_level_submap_banked(0u, 0u, 21u, 18u)` — writes BG tile map

GBDK reference `SetupCurrentLevel` + caller order:
1. `set_native_tile_data(...)` — tileset to VRAM tile data (with `SWITCH_ROM`)
2. `setBKGPalettes(...)` — palette
3. Set metadata globals (`currentAreaBank`, `currentLevelMap`, etc.) ← AFTER tileset in reference
4. **[Caller]** `DISPLAY_OFF`
5. **[Caller]** `SetCurrentLevelSubmap(...)` — BG map write
6. **[Caller]** `DISPLAY_ON`

The VRAM TILE data (`set_bkg_data`) write likely works even with display ON because tile data
is uploaded to VRAM CHR area (0x8000-0x97FF) which can be written during Mode 0/1/2. The BG
TILE MAP write (`set_bkg_submap`) writes to VRAM BG map area (0x9800-0x9BFF) which is ONLY
accessible during Mode 0/H-blank/V-blank — not during Mode 3 (active LCD scanline). The reference
turns display off before `SetCurrentLevelSubmap` specifically for this reason.

**Fix prescription (for DIAGNOSE plan to validate):**
- Emit `DISPLAY_OFF;` at the start of `setup_current_level()` (before the switch)
- Emit `DISPLAY_ON;` at the end of each case body (after `_camera_x = 0`)
- Alternatively: emit `DISPLAY_OFF;` before and `DISPLAY_ON;` after each case body (mirror reference)
- Also eliminate the redundant second call: remove `setup_current_level()` from `gameplay_enter`
  (the card's START-press path has already called it; `gameplay_enter` should NOT call it again)

## Diagnostic Finding 6: Main-loop guard fires EVERY frame on card scene

**[VERIFIED: live generated main.c read]**

```c
// main.c:773-775 — VERIFIED
if (_next_level != _current_level) {
    navigate_to_scene(SCENE_NEXTLEVELSCENE);  // fires EVERY frame on card scene
}
```

While on `nextLevelScene`: `_next_level=1, _current_level=0` → guard fires → `nextLevelScene_enter()`
is called EVERY FRAME. This causes 30+ repeated full scene-enter executions during the harness
settle period before the START press. Each `nextLevelScene_enter()` call runs:
`set_bkg_data` (tileset load) + `set_bkg_palette` + `hide_sprites_range` + `move_bkg` +
`fill_bkg_rect(32,32)` + `_bkg_tiles_load_banked` + `DISPLAY_ON`.

This repeated scene-enter IS expected behavior (reference's `WaitForStartOrA()` is blocking,
gbkt's model is event-driven). The repeated enter does not directly cause Failure A or B, because
after the START-press `setup_current_level()` sets `_current_level=1`, the guard condition becomes
`1 != 1` = FALSE and stops firing.

However, the repeated `nextLevelScene_enter()` calls may create a compounding context:
`fill_bkg_rect` (which DOES call some form of VRAM sync internally) is called 30+ times before the
START press. The DISPLAY_ON at the end of each enter call leaves the display ON for the next
frame's `setup_current_level()` call. This is the baseline state when START fires.

## Diagnostic Finding 7: `gameplay_enter` redundant `setup_current_level` — candidate for removal

**[VERIFIED: live generated bank1.c read]**

```c
// bank1.c:25-28 — VERIFIED
void gameplay_enter(void) BANKED {
    setup_current_level();   // ← this is redundant when called from the card path
}
```

The `gameplay_enter` was designed for the BOOT path (title→gameplay) where `setup_current_level()`
is the ONLY call. The DSL source is `gameplay = scene("gameplay") { cEmit("setup_current_level();") }`
and the scene enter generates `gameplay_enter`. When invoked from the card's START-press path, this
becomes the second call.

**Fix site:** Remove `cEmit("setup_current_level();")` from the gameplay scene's enter block in
`PlatformerTemplate.kt` — replacing it with a direct call ONLY from the levelCardScene's START-press
handler. The levelCardScene path calls `setup_current_level()` THEN `navigate(gameplay)`. Since
`gameplay_enter` is called by `navigate_to_scene(SCENE_GAMEPLAY)`, eliminating the
`cEmit("setup_current_level();")` from the gameplay scene removes the redundant call.

BUT — this must be validated in the DIAGNOSE plan: the boot path (title→gameplay, no card) ALSO
calls `gameplay_enter`, and that path needs `setup_current_level()` to fire. Without it, the boot
path would skip level setup.

**Alternative fix:** Keep `setup_current_level()` in `gameplay_enter` but add `DISPLAY_OFF` before
and `DISPLAY_ON` after it (inside `setup_current_level()` or wrapping `gameplay_enter`). This works
for BOTH the boot path and the card path.

**Preferred fix (consistent with reference):** Add `DISPLAY_OFF` at the start of
`setup_current_level()` (before the switch statement) and `DISPLAY_ON` after the switch (once, at
the end of the function). This mirrors the reference's wrapping pattern and works regardless of
whether `setup_current_level` is called once (boot) or twice (card path). The double call becomes
benign because each call turns display off, writes, turns display on.

## Diagnostic Finding 8: GBDK `set_bkg_data` / `set_bkg_submap` do NOT call `display_off()` internally

**[VERIFIED: GBDK2020 installed source assembly — `platformer_template/obj/gb/level.asm` and `common.asm`]**

The GBDK library functions `set_bkg_data`, `set_bkg_tiles`, `fill_bkg_rect`, and `set_bkg_submap`
do NOT call `display_off()` internally. They write to VRAM directly. The `display_off()` is always
called EXPLICITLY by the programmer before VRAM writes. Confirmed by:
1. Reference `main.c:58` calls `display_off()` BEFORE `SetupCurrentLevel()`
2. Reference `common.c:43 (ShowCentered)` calls `DISPLAY_OFF` before `fill_bkg_rect` + `set_bkg_tiles`
3. The GBDKPipelineV2.kt comment at line 2729 claims "`set_bkg_tiles calls display_off() internally`"
   — this appears to be an INCORRECT comment from an earlier understanding; it is NOT confirmed by
   the GBDK source

**Corrected model:** `set_bkg_data`, `set_bkg_palette`, `set_bkg_submap`, and `fill_bkg_rect` all
write directly to VRAM/BCPD registers. They do NOT call `display_off()`. The responsibility to
call `DISPLAY_OFF` before VRAM writes lies with the caller.

This explains why `fill_bkg_rect(0u, 0u, 32u, 32u, 0u)` in `nextLevelScene_enter()` works without
an explicit `DISPLAY_OFF` in the generated enter function — the `DISPLAY_ON` at the end of the
preceding enter sets the LCD, but `fill_bkg_rect` writes BG tile map cells which are accessible
during HBlank. The key constraint is: BG tile MAP writes require either display-off or HBlank
timing. Coffee-GB's VBlank simulation may allow these writes to succeed in some cases.

`set_bkg_data` writes to VRAM chr data area (0x8000-0x97FF) which is accessible during Mode 0/1/2
(display on). `set_bkg_submap` / `fill_bkg_rect` write to BG map area (0x9800-0x9BFF) which
requires Mode 0/1/2 (H-blank/V-blank) — NOT Mode 3 (active LCD line). This distinction matters:

- `set_bkg_data` may work with display ON (accessible outside Mode 3)
- `set_bkg_submap` is risky with display ON (needs H/V-blank timing)

The fact that level-1 works at boot while level-2 fails at the card-path may relate to timing
differences in how many VRAM write opportunities exist per frame with one vs. two `setup_current_level`
calls.

## Common Pitfalls

### Pitfall 1: Diagnosing B before A is fully understood
**What goes wrong:** Fixing the DISPLAY_OFF/ON gap may make the BG render correctly but NOT fix
the case where `button_pressed(J_START)` never fires (different root cause).
**Why it happens:** A and B are entangled — the SEED says "disabling one reveals the other."
**How to avoid:** Per D-01, DIAGNOSE PLAN must root-cause BOTH A and B before any fix lands.
Use MCP to probe `__joypad`, `_current_level`, `current_scene`, and `LCDC_REG @ 0xFF40`
in the same diagnostic session.

### Pitfall 2: File-level grep for DISPLAY_OFF/ON
**What goes wrong:** `grep "DISPLAY_OFF" main.c` finds the occurrence in `void main(void)` (the
startup `DISPLAY_OFF;` at line 747) and returns a false positive.
**Why it happens:** `main()` has its own `DISPLAY_OFF` at boot.
**How to avoid:** Always brace-walk to extract `setup_current_level` scope before grepping.

### Pitfall 3: Removing `setup_current_level()` from `gameplay_enter` breaks the boot path
**What goes wrong:** The title→gameplay path relies on `gameplay_enter()` → `setup_current_level()`
for the initial level setup. Removing it from `gameplay_enter` would cause level-1 to load
incorrectly at boot (anchor 1 would regress).
**Why it happens:** The fix to avoid the double call must be surgical.
**How to avoid:** Keep `setup_current_level()` in `gameplay_enter`. Add DISPLAY_OFF/DISPLAY_ON
INSIDE `setup_current_level()` so both the boot call and the card-path call are safe.
The DIAGNOSE plan should confirm whether the double call (with correct DISPLAY_OFF/ON wrapping)
causes any issue or becomes harmless.

### Pitfall 4: Asserting DISPLAY_OFF presence in `nextLevelScene_enter` body
**What goes wrong:** Searching for `DISPLAY_OFF` in `nextLevelScene_enter` — it has none (the
reference `ShowCentered` has `DISPLAY_OFF` but the gbkt card-enter doesn't). The 0F-artifact fix
(Phase 12.9) removed the zone-load inline `DISPLAY_ON` via the card-overdraw signal.
**Why it happens:** The card-scene enter sequence was designed differently from `setup_current_level`.
**How to avoid:** DISPLAY_OFF/ON belong in `setup_current_level()`, not in `nextLevelScene_enter`.

### Pitfall 5: The `world2Area1Zone` tilemap HEIGHT=32 is NOT a bug
**What goes wrong:** Seeing `HEIGHT=32` (32 tiles tall, 256 pixels) for `world2Area1Zone` when
the screen is only 18 tiles tall might look like a bug.
**Why it happens:** All three zones are 32 tiles tall (png2asset output matches the source PNG
dimensions which include full-world height). The `_bkg_set_level_submap_banked(0,0,21,18)` call
correctly passes the SCREEN window (21×18), not the full tilemap dimensions. This is correct
behavior (same as the reference `SetCurrentLevelSubmap(0,0,DEVICE_SCREEN_WIDTH+1,DEVICE_SCREEN_HEIGHT)`).

### Pitfall 6: Parallel `./gradlew clean` — hard rule violation
**What goes wrong:** Fanning out `./gradlew clean` for multiple projects in parallel corrupts the
Kotlin daemon and both builds fail.
**Why it happens:** Kotlin daemon is single-process per project root; concurrent clean operations
collide.
**How to avoid:** Per `feedback_no_parallel_gradle_clean`, chain all builds into ONE `./gradlew`
invocation. `./gradlew clean :gbkt-examples:platformer-template:buildRom` is fine. Never two
concurrent `clean` calls.
