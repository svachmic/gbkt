# Phase 12.2 Plan 02: PlatformerTemplate DSL consumer edits — tilemap(asset(...)) for 3 world zones

## Objective recap

Add `tilemap(asset("graphics/<zone>.png"))` calls to exactly 3 zones
(`world1Area1Zone`, `world1Area2Zone`, `world2Area1Zone`) in
`PlatformerTemplate.kt`. Leave `titleZone` and `nextLevelZone` unchanged —
they use the D-01 Path A one-PNG-both-roles form.

Plan 02 is the user-facing surface for REQ-1. Without these DSL invocations,
ConvertZoneTilesetsTask (Plan 12.2-03) has no way to know which zones need
the second `png2asset -map -maps_only -source_tileset` invocation. The
plan is also a smoke test for Plan 01's builder shape — post-merge, if
`:generateC` exits 0 then Plan 01 wired its DSL builder correctly.

## What shipped

## REQ-1 consumer-side coverage

REQ-1 is the spine of Phase 12.2: real per-zone tilemap PNG paths flow from
the DSL → `ZoneIR.tilemapPath` (Plan 01) → `game_metadata.json` (Plan 03 in
its wave) → `ConvertZoneTilesetsTask` (Plan 03) which invokes the second
`png2asset` with `-map -maps_only -source_tileset` to extract real tile
indices from each area PNG against the shared world tileset.

Plan 02's job is the consumer side: declare in the DSL **which** zones opt
into the two-invocation path. After this commit, the platformer-template
DSL surface is REQ-1-complete from the user's perspective.

## D-01 SPEC literal-text deviation (explicit re-statement)

**SPEC.md Requirement 1 literal text** says:

> "PlatformerTemplate.kt's 5 zones each call `tilemap(asset(...))`"

**D-01 (12.2-CONTEXT.md decisions section) tightens this to 3 zones.**

Rationale: `png2asset` has two real modes:

1. **One PNG, both roles** (single invocation, use emitted `<Stem>_map[]` as
   real tilemap) — applies to `titleZone` (title-screen.png) and
   `nextLevelZone` (next-level.png). The PNG itself IS the screen — its
   pixels are the tileset AND its tile layout is the tilemap. Forcing
   `tilemap(asset("graphics/title-screen.png"))` here would be redundant
   self-reference and add no information.
2. **Two PNGs, distinct roles** (two invocations: tileset then
   tilemap with `-source_tileset`) — applies to `world1Area1Zone`,
   `world1Area2Zone`, `world2Area1Zone`. The world tileset PNG holds the
   shared tile palette; each per-area PNG holds the actual level layout
   that references those tiles.

Observable behavior is identical to the SPEC literal text — Defect 7
(synthetic modulo-tile ramp) is closed for all 5 zones, real tile layouts
flow through codegen, WIDTH/HEIGHT constants reflect each PNG's true
dimensions — but the DSL is semantically clearer because each
`tilemap(asset(...))` invocation now carries information not already
implied by `tileset(asset(...))`.

This deviation MUST be recorded in `12.2-VERIFICATION.md` by Plan 10
(verifier sweep) per CONTEXT.md D-01 guidance.
