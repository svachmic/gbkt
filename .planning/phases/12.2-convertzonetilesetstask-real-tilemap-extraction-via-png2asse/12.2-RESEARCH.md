## png2asset -maps_only CLI Reference

**Source:** GBDK reference Makefile at `/Users/michalsvacha/gbdk/examples/cross-platform/platformer_template/Makefile` lines 82-88. [VERIFIED: codebase read]

### Two-invocation pattern (for world*-area* zones)

```make
# First invocation — tileset (no -maps_only; emits <Stem>_tiles[] + <Stem>_map[])
$(PNG2ASSET) res/graphics/world1-tileset.png \
    -c $(GENDIR)/World1Tileset.c \
    -keep_palette_order -noflip -map \
    $(PNG2ASSET_BKG_SETTINGS_$(EXT)) -b 255

# Second invocation — tilemap only (-maps_only -source_tileset <tileset.png>)
$(PNG2ASSET) res/graphics/world1-area1.png \
    -c $(GENDIR)/World1Area1.c \
    -noflip -map -maps_only \
    -source_tileset res/graphics/world1-tileset.png \
    $(PNG2ASSET_BKG_SETTINGS_$(EXT)) -b 255
```

For `gb` target: `PNG2ASSET_BKG_SETTINGS_gb=` (empty) — no extra flags. [VERIFIED: codebase read]

### Single-invocation pattern (for titleZone, nextLevelZone — D-01 Path A one-PNG case)

```make
$(PNG2ASSET) res/graphics/title-screen.png \
    -c $(GENDIR)/TitleScreen.c \
    -noflip -map \
    $(PNG2ASSET_BKG_SETTINGS_$(EXT)) -b 255
```

No `-maps_only` and no `-source_tileset`. The emitted `.c` contains BOTH
`<Stem>_tiles[]` (pixel data) AND `<Stem>_map[]` (tile-index array). The existing
`ConvertZoneTilesetsTask` first-invocation parser at lines 393-430 already reads
`<Stem>_map[]` from this output — D-02's one-invocation path reuses that parser
verbatim (straight copy, no modulo). [VERIFIED: codebase read]

### Key observations from Makefile

1. **`-keep_palette_order` is ABSENT from all `-maps_only` invocations** (lines 84-86).
   Plan 11.2-04 confirmed png2asset rejects this flag on non-indexed RGB PNGs. The second
   invocation MUST NOT include `-keep_palette_order`. [VERIFIED: codebase read + CONTEXT.md D-02]

2. **`-source_tileset` takes the tileset PNG path**, not the generated `.c` file path.
   Exact form: `-source_tileset res/graphics/world1-tileset.png`. [VERIFIED: codebase read]

3. **`-b 255`** is present in the reference but is a bank hint for png2asset's internal
   output format, NOT the GBDK `#pragma bank N`. Our task writes its own `#pragma bank N`
   after parsing. The existing first-invocation passes `-b` already; the second invocation
   can omit or include it — it has no effect on the parsed `_map[]` bytes. [ASSUMED]

4. **Auxiliary symbols in `-maps_only` mode:** The second invocation emits ONLY the
   `<Stem>_map[]` array (no `_tiles[]`, no palette, no attribute arrays). The output `.c`
   is smaller than the first-invocation output. The parse-and-re-emit approach (D-02)
   extracts only the `_map[]` array and discards the rest, so any future auxiliary symbol
   additions would be silently ignored — exactly what we want. [ASSUMED from "maps_only"
   semantics + Makefile evidence; HIGH confidence]

5. **Stem rule for second invocation (D-claude-5):** Plan 11.2-04 confirmed that
   png2asset names the emitted array after the OUTPUT-FILE basename (the `-c <output>.c`
   argument), NOT the input PNG basename. For the second invocation with
   `-c <tmpdir>/_zone_<sanitized>_tilemap_raw.c`, png2asset will emit
   `_zone_<sanitized>_tilemap_raw_map[]`. The parser regex must use the temp-output
   basename (`_zone_<sanitized>_tilemap_raw`) as the stem. [VERIFIED: CONTEXT.md + Plan 11.2-04]

## Risk Notes

### R-01: png2asset version drift (MEDIUM)

The `-maps_only -source_tileset` flags are present in the reference Makefile but their
exact behavior has only been validated via the reference's generated output (the evidence
file shows `World1Area1_map[1920]` = 1920 bytes). If the local GBDK installation has a
different png2asset version than the one used to generate the reference output, the byte
values might differ. **Mitigation:** Plan 5's emission invariant tests use structural
assertions (byte[0..59] all `0x11`, row-31 contains ground-tile values) rather than full
1920-byte equality. The SPEC-locked approach is correct for this reason.

### R-02: `_tileset_map[]` stem in one-invocation path (LOW)

The existing parser (line 397) uses pattern:
`_zone_${sanitized}_tileset_map` to find the array. For the one-invocation path (D-01),
this is correct: the first png2asset invocation emits `_zone_<sanitized>_tileset_map[]`
because the output file is named `_zone_<sanitized>_tileset.c`. No change needed.
For the two-invocation path, the second invocation output is named
`_zone_<sanitized>_tilemap_raw.c`, so png2asset emits `_zone_<sanitized>_tilemap_raw_map[]`.
The regex for the second invocation needs a DIFFERENT stem. Both stems are derived
deterministically from the output filename — no ambiguity. **No risk if stems are tracked carefully.**

### R-03: BankingAnalysisPass filesystem access novelty (LOW)

D-04 introduces the first filesystem read in any analysis pass. The analysis passes
currently run in a JVM test context without a real filesystem. The overflow guard test
(`BankingAnalysisPassTilemapOverflowTest.kt`) must pass a real `java.io.File` as
`assetRoot` with a synthetic PNG file to trigger the guard. The `@TempDir` JUnit 5
annotation (already used in `ConvertZoneTilesetsTaskTest.kt`) handles this cleanly.
**No risk beyond the implementation detail that the test creates synthetic PNG fixtures.**

### R-04: `game_metadata.json` `zoneTilesets` lacks `tilemapPath` field (LOW)

`buildMetadataFile` currently emits only `id`, `path` (tilesetPath), `sanitizedSymbol`,
`mapWidth`, `mapHeight`, and `bank` for each zone. It does NOT emit `tilemapPath`. The
`ConvertZoneTilesetsTask` reads this JSON and needs to know `tilemapPath` per zone to
decide which invocation path to use.

**Resolution:** `ConvertZoneTilesetsTask` receives the `ZoneIR`-derived metadata at task
execution time. Looking at `ConvertZoneTilesetsTask.kt` lines 191+, the task is invoked
with `zoneId` and `pngFile` (tileset PNG). The `tilemapPath` needs to be added to
`game_metadata.json`'s `zoneTilesets` entries so `ConvertZoneTilesetsTask` can read it
at task time. This is a REQUIRED addition to `buildMetadataFile` in GBDKPipelineV2.

**Planner action:** Add Plan 2 or Plan 3 (whichever handles the tilemap path wiring)
a step to update `buildMetadataFile` to include `"tilemapPath": zone.tilemapPath` (or
`null` if absent) in each `zoneTilesets` entry. `ConvertZoneTilesetsTask` then reads
this field to decide the invocation path. This is a small addition to GBDKPipelineV2
and to the task's metadata-reading loop. Consider making it part of Plan 1 (IR layer)
since it flows naturally from adding `tilemapPath` to `ZoneIR`.

### R-05: `GameIRSerializer` round-trip for new `tilemapPath` field (LOW)

`ZoneIR` is serializable via `GameIRSerializer.kt` (referenced in `gbkt-ir/CLAUDE.md`).
Adding `tilemapPath` to `ZoneIR` requires updating the serializer to emit and parse
the new field. If not updated, round-trip tests will fail. **Planner verifies the
