# Phase 12.2: ConvertZoneTilesetsTask real-tilemap extraction via png2asset -map mode (close Defect 7) — Specification

**Created:** 2026-05-22
**Ambiguity score:** 0.18 (gate: ≤ 0.20)
**Requirements:** 6 locked

## Goal

Replace `ConvertZoneTilesetsTask`'s synthesized 32×32 modulo-tiled ramp with real per-zone tilemap data extracted via a second png2asset invocation (`-maps_only -source_tileset <tileset>`), and emit variable per-zone `_tilemap_WIDTH/_HEIGHT` constants derived from the source PNG dimensions, so the platformer-template ROM renders the world1Area1 layout instead of a 5×4 grid of identical blocks.

## Background

Phase 12 Plan 12-19 (UAT Anchor 1: title → gameplay scene transition) surfaced **Defect 7**: ConvertZoneTilesetsTask emits a synthetic tilemap by modulo-tiling the png2asset `_tileset_map` deduplication table across a hardcoded 32×32 grid. The synthesis lives at `gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertZoneTilesetsTask.kt:432-439`:

```kotlin
for (y in 0 until screenMapHeight) {
    for (x in 0 until screenMapWidth) {
        tiledBytes += sourceMap[(y % mapTileH) * mapTileW + (x % mapTileW)]
    }
}
```

This was introduced by Plan 11.1-17 as a placeholder so `_bkg_tiles_load_banked` in `SceneVisitor` had something to consume. The defect was latent for three phases because Banks Phase 11 — the only prior consumer — never actually calls `_bkg_tiles_load_banked` from `setup_current_level` (verified: Banks's `main.c` has no such call).

Plan 12-19 made the defect visible: `02-gameplay.png` shows a 5×4 grid of repeating block patterns instead of the world1Area1 layout (sky rows + scattered platforms + ground row). The title screen also doubles vertically because title-screen.png is 20×18 tiles loaded as 32×32 with wrap.

The reference GBDK Makefile (`/Users/michalsvacha/gbdk/examples/cross-platform/platformer_template/Makefile`) uses **two png2asset invocations** per gameplay zone — one for the tileset, one for the tilemap with `-maps_only -source_tileset <tileset>` — producing `World1Area1_map[1920]` (60×32 bytes) with the actual playable layout. The gbkt DSL today only carries one PNG per zone (`tileset(asset(...))`), so a new DSL field is required to surface the tilemap PNG to the task.

Affected zones in Phase 12: world1Area1Zone, world1Area2Zone, world2Area1Zone, titleZone, nextLevelZone (5 zones). Banks Phase 11 is unaffected (different codepath).

## Requirements

1. **DSL `tilemap()` field**: ZoneBuilder exposes a new builder method that registers a tilemap PNG path on `ZoneIR`.
   - Current: `ZoneBuilder` has `tileset(asset(...))` only; no way to specify a separate tilemap source PNG. `ZoneIR` has no `tilemapPath` field.
   - Target: `ZoneBuilder.tilemap(asset: AssetRef)` adds a `tilemapPath: String?` field to `ZoneIR`; PlatformerTemplate.kt's 5 zones each call `tilemap(asset("graphics/<zone>.png"))`.
   - Acceptance: JVM test `ZoneBuilderTilemapTest.kt` asserts both `tileset()` and `tilemap()` invocations land in the IR; a second test asserts a zone without `tilemap()` retains `tilemapPath == null`.

2. **Real-tilemap extraction**: ConvertZoneTilesetsTask runs the second png2asset invocation per zone when `tilemapPath` is set.
   - Current: Task runs png2asset once per zone (tileset) and then calls `synthesizeScreenTilemap()` to emit a 32×32 modulo-tiled ramp of the dedup table.
   - Target: When `tilemapPath` is set, Task runs png2asset a second time with the reference flag pattern: `<tilemap.png> -c <output>.c -noflip -map -maps_only -source_tileset <tileset.png>` plus the standard background flag set (`PNG2ASSET_BKG_SETTINGS_gb=` — empty for Game Boy gb target — and `-b 2` to land in bank 2). Emit the resulting byte array verbatim into `_zone_<id>_tilemap.c`.
   - Acceptance: For platformer-template, `_zone_world1Area1Zone_tilemap[]` is 1920 bytes and matches the reference `gen/gb/src/World1Area1.c`'s `World1Area1_map[1920]` byte-for-byte. JVM emission invariant test asserts: byte[0..59] all equal `0x11` (row 0 = sky), AND row 31 (bytes 1860..1919) contains values in {0x00..0x05, 0x16, 0x17} (ground tiles).

3. **Variable WIDTH/HEIGHT constants**: `_zone_<id>_tileset.h` declares per-zone tilemap dimensions derived from the source PNG.
   - Current: Header emits `#define _zone_<id>_tilemap_WIDTH 32` and `#define _zone_<id>_tilemap_HEIGHT 32` regardless of source PNG dimensions.
   - Target: Constants derive from `tilemap.png` pixel dimensions divided by 8. world1-area1.png (480×256) → `WIDTH 60 / HEIGHT 32`. title-screen.png (160×144) → `WIDTH 20 / HEIGHT 18`.
   - Acceptance: Inspect generated `_zone_world1Area1Zone_tileset.h` — `_zone_world1Area1Zone_tilemap_WIDTH == 60` AND `_zone_world1Area1Zone_tilemap_HEIGHT == 32`. Inspect `_zone_titleZone_tileset.h` — `_zone_titleZone_tilemap_WIDTH == 20` AND `_zone_titleZone_tilemap_HEIGHT == 18`. JVM test parses both headers and asserts the values.

4. **Synthesizer removed**: `ConvertZoneTilesetsTask.synthesizeScreenTilemap()` and its callers are deleted.
   - Current: `synthesizeScreenTilemap()` at lines 432-439 emits modulo-tiled dummy data. It is called when no real tilemap source exists.
   - Target: Function is deleted along with its single call site. When a zone has no `tilemap()` and no opt-in fallback, the task fails with a Gradle exception naming the zone ID and recommending adding `tilemap(asset(...))` to the DSL.
   - Acceptance: `grep -n "synthesizeScreenTilemap\|sourceMap\[(y % mapTileH)" gbkt-gradle-plugin/src/main/kotlin/io/github/gbkt/gradle/tasks/ConvertZoneTilesetsTask.kt` returns 0 matches. A JVM test `ConvertZoneTilesetsTaskMissingTilemapTest.kt` asserts task throws `GradleException` with diagnostic message when given a zone with `tilesetPath` set but `tilemapPath == null`.

5. **Banking overflow guard**: BankingAnalysisPass adds a cumulative-tilemap-size check.
   - Current: All `_zone_<id>_tilemap.c` files emit with `#pragma bank 2`. With dummy 32×32 data (1024 bytes/zone), 5 zones use ~5120 bytes — no overflow risk. With real data, sizes vary (1920 / 1920 / 1920 / 360 / 360 = ~6480 bytes total for Phase 12), still safe. But adding a 6th zone or a single 14 KB zone could overflow.
   - Target: BankingAnalysisPass sums all zones' `tilemapPath` PNG sizes (`PNG.width * PNG.height / 64` = tile count = byte count). If cumulative > 14336 bytes (16 KB bank size minus 2 KB safety margin for headers/prologue), build fails with a clear error naming each zone's contribution and recommending per-zone tilemap banks (out-of-scope; see SEED-PHASE-12-PER-ZONE-TILEMAP-BANKS).
   - Acceptance: Phase 12's 5 zones sum to ~6480 bytes (under threshold); platformer-template build passes. A synthetic JVM test `BankingAnalysisPassTilemapOverflowTest.kt` injects a hypothetical 6th 8192-byte zone, sums to 14672 bytes, exceeds 14336 threshold, asserts `BankingAnalysisPass.validate()` returns a failure with the expected error string.

6. **Plan 12-19 anchor 1 UAT GREEN (terminal acceptance)**: After 12.2 ships, re-running Plan 12-19's UAT test captures gameplay screenshots that visually match the reference world1Area1 layout.
   - Current: Plan 12-19's `02-gameplay.png` shows a 5×4 grid of repeating block patterns; `01-title.png` shows "GBDK-2020 PLATFORMER TEMPLATE" doubled vertically. Plan 12-19 is `blocked-pending-escalation`.
   - Target: After 12.2 ships, re-running `./gradlew :gbkt-examples:platformer-template:test --tests "PlatformerTemplateUatTest.anchor1Title_to_Gameplay"` exits 0. `01-title.png` shows the title art rendered as a single full-screen frame (no vertical doubling). `02-gameplay.png` shows the world1Area1 layout: sky rows at the top, ~3-5 floating platform blocks visible in the upper third, ground row at the bottom (matching the upper-left 20×18 viewport into the 60×32 reference tilemap).
   - Acceptance: Human visual inspection of both PNGs at `.planning/phases/12-port-platformer-template-gbdk-example-to-gbkt/evidence/uat-screenshots/anchor-1/` confirms they match the expected reference layout (compared against `gbkt-examples/platformer-template/res/graphics/title-screen.png` and the upper-left 160×144 region of `world1-area1.png`).

## Constraints

- **png2asset binary path**: must use `${GBDK_HOME}/bin/png2asset` resolved via the existing `GbdkToolchain.getPng2asset(gbdkDir)` helper (Phase 11.2 D-C1).
- **Reference flag pattern**: second png2asset invocation MUST use `-noflip -map -maps_only -source_tileset <tileset.png>` exactly as the reference Makefile does. No experimentation with `-pack_mode` / `-bpp` / `-keep_palette_order` beyond what reference uses (out-of-scope).
- **0-on-decoder-error guard**: png2asset exits 0 even when it failed (Plan 11.2-02 spike finding). Task MUST inspect the `.c` output existence after each invocation and treat absence as failure with diagnostic message (same pattern as the existing tileset invocation guard).
- **Asset immutability**: All 5 zone PNGs in `gbkt-examples/platformer-template/res/graphics/` are byte-identical to the GBDK reference and remain unchanged.
- **Banking threshold**: BankingAnalysisPass overflow guard at 14336 bytes (16 KB minus 2 KB safety margin).
- **Terminal phase**: Phase 12.2 MUST close all 6 requirements with no 12.2.1 / 12.2.2 follow-ups. Route excess via `/gsd-phase 12 --insert` for Phase 12.3.
- **Cross-phase impact**: changes to ZoneIR + ZoneBuilder MUST NOT break Banks Phase 11 or Pong/Breakout/Explorer (whose zones don't use the new `tilemap()` field). Existing zones MUST keep working with `tilemapPath == null` and the synthesizer-removal must route to a clear DSL-migration error (not silent break).

- **SEED-PHASE-12-CONVERTSPRITESTASK-AUDIT**: ConvertSpritesTask is the sister class to ConvertZoneTilesetsTask and mirrors its structure. No known defect, but the parallel synthesis-fallback antipattern (if present) would be a similar latent bug.
