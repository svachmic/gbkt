<decisions>
## Implementation Decisions

### Back-compat surface for zones without `tilemap()`

- **D-01: `tilemap()` defaults to `tileset()` PNG when absent — Path A.** The
  DSL maps 1:1 to `png2asset`'s two real modes:

  - **One PNG, both roles** — single `png2asset` invocation, use the emitted
    `<Stem>_map[]` byte array as the real tilemap, derive WIDTH/HEIGHT from
    the source PNG dimensions ÷ 8. Applies to Banks (`checker.png`),
    platformer-template's `titleZone` (`title-screen.png`), and
    platformer-template's `nextLevelZone` (`next-level.png`).
  - **Two PNGs, distinct roles** — two `png2asset` invocations: first for the
    tileset (no `-maps_only`), second for the tilemap with
    `-map -maps_only -source_tileset <tileset>.png`. The user opts into this
    by adding an explicit `tilemap(asset(...))` to the zone builder. Applies
    to platformer-template's `world1Area1Zone`, `world1Area2Zone`, and
    `world2Area1Zone`.

  **Why this is the right answer (engineering rationale captured during
  discussion):**

  1. Maps 1:1 to png2asset's two real modes — the DSL becomes a thin, faithful
     surface over the underlying tool.
  2. Defect 7 cannot recur — the synthesized modulo-tile code path is
     DELETED, not reached-but-empty. No fallback to the broken pattern.
  3. Banks gets correct output with zero DSL edits. `checker.png` (16×16 = 2×2
     tiles) produces a real 2×2 tilemap with `WIDTH=2`, `HEIGHT=2`. The
     vestigial `size(20, 18)` becomes harmless (it never was a tilemap
     dimension; it's a separate viewport concept).
  4. Backward compat is real, not a stub. Existing `tileset()`-only zones get
     structurally identical png2asset output to GBDK's reference
     `TitleScreen.c`/`NextLevel.c` outputs.
  5. No SPEC migration error needed. The "absent `tilemap()`" case has a real,
     correct semantic. Hard-fail still applies for the genuinely-broken case:
     `tilemap()` set but file missing/invalid.
  6. WIDTH/HEIGHT always derive from real PNG dimensions. SPEC Requirement 3
     satisfied without special-casing.

  - **Rejected (skip tilemap emission entirely):** breaks every consumer that
    references `_zone_<id>_tilemap` at link time; requires invasive changes
    to GBDKPipelineV2's setup_current_level emission.
  - **Rejected (1-byte stub tilemap):** dead bytes; weird semantics if any
    future code does read the symbol; communicates "missing" via magic data.
  - **Rejected (hard-fail with DSL-migration diagnostic — SPEC literal text
    of Requirement 4):** forces edits to Banks.kt despite SPEC out-of-scope
    clause. D-01 resolves the SPEC tension by giving the absent-`tilemap()`
    case a real semantic; the diagnostic still fires when a zone's `tilemap()`
    PNG is set but the file is missing/invalid (genuine error case).

  **SPEC literal-text deviation flagged for verifier:** SPEC Requirement 1's
  acceptance criterion says "PlatformerTemplate.kt's 5 zones each call
  `tilemap(asset("graphics/<zone>.png"))`". D-01 tightens this to 3 zones
  (the `world*-area*` ones). `titleZone` and `nextLevelZone` remain
  `tileset()`-only because their tileset PNG is also their tilemap PNG. The
  observable behavior (real tilemap, correct WIDTH/HEIGHT, defect 7 closed)
  is identical; the DSL is semantically clearer. Verifier MUST accept this
  tighter design; planner records the deviation in the per-plan SUMMARY.md
  and in 12.2-VERIFICATION.md.

### png2asset output processing strategy

- **D-02: Parse-and-re-emit (matches Phase 11.2 pattern).** For the
  `tilemap()`-explicit case (Path A's two-invocation path), the task runs
  `png2asset <tilemap>.png -c <tmp>.c -noflip -map -maps_only -source_tileset
  <tileset>.png` (no `-keep_palette_order` on the second invocation per SPEC
  Constraint — Plan 11.2-04 confirmed png2asset rejects this flag on
  non-indexed RGB PNGs). It then reads the emitted `.c`, regex-parses the
  `const unsigned char <Stem>_map[N] = { ... };` array (same parser shape
  ConvertZoneTilesetsTask already uses for `_zone_<sanitized>_tileset_map` at
  line 396-399), and re-emits `_zone_<sanitized>_tilemap.c` with:
  - Our auto-generated header comment block
  - `#pragma bank N` (N from the zone's allocated bank, propagated via
    `game_metadata.json`'s `bank` field per 12.1 D-01)
  - `#include <stdint.h>` and `#include "_zone_<sanitized>_tileset.h"`
  - `const uint8_t _zone_<sanitized>_tilemap[<size>] = { ... };`

  For the `tilemap()`-absent case (Path A's single-invocation path), the
  task uses the EXISTING first png2asset invocation's `.c` output, regex-parses
  the same `_zone_<sanitized>_tileset_map` array (already implemented at
  ConvertZoneTilesetsTask.kt:393-430), and re-emits `_zone_<sanitized>_tilemap.c`
  using those bytes verbatim (no modulo-tiling — straight copy).

  - **Rejected (-bin mode + emit ourselves):** would require verifying
    png2asset's `-bin` shape (file extension, byte ordering) and writing a
    new code path; the existing parse-and-re-emit pattern is proven.
  - **Rejected (in-place pragma injection + symbol rename):** auxiliary symbols
    png2asset may emit in `-map -maps_only` mode flow through verbatim into
    our output without inspection — fragile.
  - **Rejected (accept .c file as-is + alias via header):** symbol indirection
    obscures the actual byte array from grep-based emission tests.

  **Composition with D-01:** the two paths (one-invocation vs two-invocation)
  share the parse-and-re-emit step. The only difference is which png2asset
  invocation's output gets parsed. The synthesized modulo-tile loop at
  lines 432-439 is DELETED.

### DSL signature for `tilemap()`

- **D-03: `fun tilemap(ref: AssetRef)` — AssetRef-only.** Matches the
  project's no-magic-strings rule (`feedback_no_magic_strings.md`) and the
  modern typed-ref convention. Diverges from `tileset()`'s dual surface
  (`tileset(path: String)` + `tileset(ref: AssetRef)`) — that dual surface
  is itself a candidate for cleanup someday (SEED, not in 12.2 scope).

  - **Rejected (both String and AssetRef):** larger API surface to maintain;
    encourages divergence over time.
  - **Rejected (AssetRef only + later add String if asked):** YAGNI-equivalent
    — same outcome as D-03 with a hypothetical future expansion. D-03 is the
    canonical form.

  **Implementation note for planner:** Add `tilemapPath: String?` to
  `ZoneIR` (mirrors `tilesetPath: String?`). Add `fun tilemap(ref: AssetRef)`
  to `ZoneBuilder` that sets `tilemapPath = ref.path`. ZoneBuilder's
  `build()` passes both fields to the `ZoneIR` constructor.

### BankingAnalysisPass timing & data source

- **D-04: Read PNG IHDR from disk during analysis time.**
  `BankingAnalysisPass.validate(game)` iterates zones; for each zone with
  `tilesetPath != null`, opens the file via `ImageIO.read(File(assetRoot,
  zone.tilemapPath ?: zone.tilesetPath))`, reads `image.width *
  image.height / 64` to get the tile-byte count, and sums across zones. If
  cumulative > 14336 bytes (16 KB bank minus 2 KB safety margin per SPEC
  Constraint), returns a failure naming each zone's contribution and
  recommending per-zone tilemap banks (deferred via
  SEED-PHASE-12-PER-ZONE-TILEMAP-BANKS).

  **New dependency:** `BankingAnalysisPass` gains filesystem access during
  analysis (was previously pure-IR). Mirrors the same `ImageIO.read` approach
  ConvertZoneTilesetsTask already uses (ConvertZoneTilesetsTask.kt:210-218);
  reuse the helper or extract a shared utility into `gbkt-analysis` or
  `gbkt-core`. Planner picks the residence.

  **assetRoot resolution:** `BankingAnalysisPass` does not currently know
  the asset directory; it lives in `gbkt-analysis` which is pre-Gradle.
  Options the planner picks from: (a) plumb `assetRoot` into the
  `AnalysisContext` (or equivalent) at validate-time; (b) defer the PNG
  read to a lazy file-resolver injected by the Gradle plugin via the
  backend reflection layer; (c) BankingAnalysisPass reads PNG dims from a
  pre-computed metadata file emitted earlier in the pipeline. D-claude-2
  below tracks this.

  - **Rejected (add IR field for tilemap dimensions):** drifts from
    reality if user mis-declares; build-time PNG read shifts the
    filesystem dependency from analysis to DSL-build (worse, because DSL
    build is more sensitive to test isolation).
  - **Rejected (defer overflow guard to Gradle-task time):** loses the
    early-fail JVM-test guard SPEC Requirement 5 explicitly wants. SPEC
    acceptance criterion 9 is a JVM-test invariant.
  - **Rejected (hybrid: analysis + task confirmation):** two-tier safety net
    is over-engineered for the ~14 KB threshold; single-tier at analysis
    time is sufficient.

### Claude's Discretion

- **D-claude-1: Synthesizer-removal blast radius.** SPEC Requirement 4
  says `grep -n "synthesizeScreenTilemap\|sourceMap\[(y % mapTileH)"
  ConvertZoneTilesetsTask.kt` returns 0 matches after the fix. With D-01's
  one-invocation fallback path, the FUNCTION `synthesizeScreenTilemap` is
  STILL CALLED for tileset()-only zones, but its BODY changes — the
  modulo-tile loop is replaced with a straight-copy of the
  `_tileset_map[]` bytes. Two refactor shapes the planner picks from:
  (a) rename `synthesizeScreenTilemap` to `extractScreenTilemap`,
  re-implement the body, satisfies SPEC AC1 grep; (b) delete
  `synthesizeScreenTilemap` entirely and inline the parse-and-re-emit logic
  in `convertOneTileset`. Default: (b) cleaner separation of concerns.

- **D-claude-2: assetRoot plumbing into BankingAnalysisPass.** Per D-04's
  open question. Default: (a) — plumb `assetRoot` into the
  `AnalysisContext`, mirroring how the Gradle plugin already passes
  paths to the backend. Planner verifies the existing analysis-context
  shape and picks the smallest-surface integration.

- **D-claude-3: Reference helper extraction.** ImageIO-based PNG-dim
  reading lives in both `ConvertZoneTilesetsTask` (lines 210-218) AND will
  live in `BankingAnalysisPass` after this phase. Planner decides:
  (a) duplicate inline (acceptable for two call sites; trivial code);
  (b) extract a shared helper into `gbkt-core`'s asset pipeline package
  (more reusable but adds a small surface). Default: (a) duplicate inline,
  with a code comment in each call site pointing to the other; if a third
  call site appears in a future phase, extract then.

- **D-claude-4: Per-zone bank metadata propagation for the new path.**
  Phase 12.1 D-01 added `bank` to `game_metadata.json`'s `zoneTilesets`
  entries. The new tilemap invocation still uses the same `bank` value
  for the emitted `_zone_<id>_tilemap.c`'s `#pragma bank N`. Verify the
  field is populated for zones with `tilemapPath != null` AND for zones
  with `tilemapPath == null` (Path A's one-invocation case still emits
  `_zone_<id>_tilemap.c` and still needs a bank). Planner checks
  `GBDKPipelineV2.allocateZoneBanks` and `buildMetadataFile` and confirms
  the bank is propagated regardless of tilemap presence.

- **D-claude-5: png2asset-version stem behavior for the second
  invocation.** Plan 11.2-04 learned that png2asset names emitted arrays
  after the OUTPUT-FILE basename. For the second invocation with
  `-c <tmp_output>.c`, the array will be named after `<tmp_output>`'s
  basename. Planner picks a stable temp-output naming scheme (e.g.,
  `_zone_<sanitized>_tilemap_raw.c` in a scratch subdir) and uses the
  same naming convention to drive the regex parse. Mirrors the existing
  pattern at line 273-278.

- **D-claude-6: Plan decomposition (~10 plans).** Per
  `feedback_many_small_plans_terminal_subphase.md` err small; terminal
  subphase rule means no 12.2.1 follow-up. Recommended skeleton
  (planner refines after research):

  1. DSL: add `tilemapPath: String?` to `ZoneIR` + `tilemap(ref: AssetRef)`
     to `ZoneBuilder` + JVM unit test (`ZoneBuilderTilemapTest.kt`)
  2. DSL: add `tilemap(asset(...))` to the 3 platformer-template world zones
     (world1Area1Zone, world1Area2Zone, world2Area1Zone)
  3. Task fix: ConvertZoneTilesetsTask runs second png2asset invocation
     when `tilemapPath != null`; parses output; re-emits
     `_zone_<id>_tilemap.c` with `#pragma bank N`
  4. Task fix: ConvertZoneTilesetsTask handles `tilemapPath == null` by
     extracting bytes from the first invocation's `_tileset_map[]` (Path A
     one-invocation case)
  5. Task fix: delete `synthesizeScreenTilemap` (or rename + re-implement
     per D-claude-1); emit variable WIDTH/HEIGHT from source PNG dims
  6. Task emission test: `_zone_world1Area1Zone_tilemap[]` is 1920 bytes,
     byte[0..59] all `0x11` (sky row), row 31 contains ground tiles per
     SPEC AC4-5
  7. Task emission test: header WIDTH/HEIGHT constants per zone (60/32
     for world1-area1, 20/18 for title-screen, 2/2 for banks checker)
     per SPEC AC6-7
  8. Task emission test: missing-tilemap diagnostic — when `tilemapPath`
     is set but file missing/invalid, task throws GradleException
     (D-01's "genuine error case")
  9. Analysis: BankingAnalysisPass cumulative tilemap-size overflow guard;
     JVM synthetic 6-zone scenario test per SPEC AC8
  10. 5-ROM regression sweep + Plan 12-19 re-shoot + human visual
      verification + 12.2-VERIFICATION.md write-up

  Could fold (3)+(4) into one plan if the two paths share enough code, or
  split (5) into "delete synthesizer" + "variable WIDTH/HEIGHT" if either
  is non-trivial. Planner picks after research; absorb surplus inline
  (insert-a-plan, NOT 12.2.1).
