# CLAUDE.md - gbkt Development Guide

## Project Overview

gbkt (Game Boy Kotlin) is a DSL framework that compiles Kotlin code to GBDK-compatible C for Game Boy development.

**Architecture:** Kotlin DSL → IR (non-sealed interfaces + visitor dispatch) → 12 analysis passes (automatic bank/VRAM/OAM/RAM allocation) → C AST → GBDK C

See [context/ARCHITECTURE.md](context/ARCHITECTURE.md) for the full pipeline, module layers, and extension guide. See [context/DSL_REFERENCE.md](context/DSL_REFERENCE.md) for all DSL syntax (variables, actors, scenes, input, RPG, exploration, game flow).

## Tech Stack

- **Kotlin**: 2.3.20
- **Gradle**: 9.5.1
- **JVM Target**: 21

## Build & Run

```bash
# Build the project
./gradlew build

# Run all tests
./gradlew test

# Run tests for a specific module
./gradlew :gbkt-ir:test
./gradlew :gbkt-lang:test
./gradlew :gbkt-engine:test
./gradlew :gbkt-core:test
./gradlew :gbkt-backend-api:test
./gradlew :gbkt-backend-gbdk:test
./gradlew :gbkt-analysis:test
./gradlew :gbkt-genre-rpg:test

# Gradle-plugin tests: use pluginTest, NOT :gbkt-gradle-plugin:test
# Its IntegrationTest TestKit sandbox resolves gbkt-core/backend-api/backend-gbdk
# (+ transitive ir/lang/engine/world) as 0.1.0-SNAPSHOT from mavenLocal(). Running
# :gbkt-gradle-plugin:test directly against a stale ~/.m2 fails to compile fixtures
# written for the current DSL. pluginTest republishes those 7 modules first.
./gradlew pluginTest
```

## GBDK Setup & ROM Building

### Prerequisites
- GBDK-2020 installed (https://github.com/gbdk-2020/gbdk-2020/releases)
- Set `GBDK_HOME` environment variable OR install to common path

### Build Commands
```bash
./gradlew buildRom      # Build ROM (uses GBDK lcc compiler)
./gradlew runEmulator   # Run in emulator (auto-detects mGBA)
./gradlew generateC     # Generate C only (no compilation)
```

### GBDK Detection
The plugin searches in order:
1. `gbkt { gbdkHome.set("/path") }` in build.gradle.kts
2. `GBDK_HOME` environment variable
3. Common paths: `/opt/gbdk-2020`, `~/gbdk-2020`, etc.

### Output Files
- ROM: `build/gbkt/output/{name}.gb`
- Generated C: `build/gbkt/generated/main.c`
- Source map: `build/gbkt/generated/main.c.gbkt.map`
- Debug: `.map` and `.sym` files

### Common Errors
| Error | Cause | Fix |
|-------|-------|-----|
| `lcc not found` | GBDK not installed/detected | Set GBDK_HOME or install to common path |
| `undefined identifier` | Missing variable/function | Check spelling, ensure DSL generates it |
| `bank overflow` | Too much code/data | Split into multiple banks |

### Framework Gotchas
- **Banking defaults**: `BankingConfig` defaults place all banked code in bank 1 — suitable for simple games (Pong, Breakout). Complex games with RPG systems should override via `config { banking { ... } }` to spread code across multiple banks.
- **Window-layer UI**: All UI text (dialogs, menus, battle UI, status bars) renders on the GBDK window layer via `_win_*` helpers generated by `WindowTextCodegen`. This prevents text from corrupting the background tile layer when using custom tilesets. Zero `gotoxy`/`printf` calls remain in UI code.
- **Battle system**: Use `simpleBattle()` (in `gbkt-genre-rpg`) for v1 turn-based combat, driven by `battleUpdate()` every frame. The lower-level `combatEngine()` is experimental and will be revised in a future release.
- **Examples**: The seven example projects (`gbkt-examples/{pong,breakout,simple-physics,metasprites,metasprites-stress,banks,platformer-template}`) use the Gradle plugin directly — no duplicated build logic.

## Multi-Module Architecture

gbkt uses a 20-module architecture (19 Gradle subprojects + the `gbkt-gradle-plugin` composite build):

```
gbkt/
├── gbkt-ir/              # IR types (Expr, ScriptOp, GameIR — zero deps, leaf module)
├── gbkt-lang/            # DSL builders (GameBuilder, ScriptBuilder, variable delegates)
├── gbkt-engine/          # Engine runtime types (combat, input, entity, scene, graphics)
├── gbkt-world/           # World & exploration types
├── gbkt-core/            # Aggregator: re-exports ir+lang+engine+world, plus asset pipeline & test infra
├── gbkt-backend-api/     # Backend contract (CodegenBackend interface, GenreSystemVisitor)
├── gbkt-backend-gbdk/    # Game Boy/GBC backend (C AST, visitor codegen, pipeline)
├── gbkt-analysis/        # 12 analysis passes (validation, optimization, resource planning)
├── gbkt-genre-rpg/       # RPG genre plugin (characters, battles, abilities, equipment)
├── gbkt-genre-platformer/# Platformer genre plugin (physics, camera, level elements)
├── gbkt-genre-puzzle/    # Puzzle genre plugin (match-3, block-push)
├── gbkt-genre-sport/     # Sport genre plugin (racing, ball sports, tournaments)
├── gbkt-emulator/        # Embedded Game Boy emulator (Coffee-GB, debug log capture, developer UI)
├── gbkt-test/            # Test infrastructure (JUnit5 extension, assertions, recipes, discovery)
├── gbkt-mcp-server/      # MCP server for AI agent game testing (wraps StepAgent for Claude Code)
├── gbkt-gradle-plugin/   # Build integration (composite build)
├── gbkt-cli/             # Command-line tool
├── gbkt-intellij-plugin/ # IDE support
├── gbkt-all/             # Convenience meta-module (aggregates all published modules)
└── gbkt-bom/             # Version coordinator
```

Dependency layering, the visitor-based IR design, and backend responsibilities are documented in [context/ARCHITECTURE.md](context/ARCHITECTURE.md).

## Claude Code Skills Setup

Run `./gradlew gbktSetupClaude` to install Claude Code skills and MCP server configuration:

```bash
# Install skills + MCP config (run from any subproject or root)
./gradlew gbktSetupClaude
```

This installs:
- `/gbkt-play-game <game>` — Interactive play session with the MCP emulator
- `/gbkt-test-game <game|all>` — Automated game verification suite

It also configures `.claude/mcp_servers.json` with the `gbkt-emulator` MCP server entry and writes a version marker (`.claude/.gbkt-version`) for staleness detection.

The task is safe to re-run — skills are always overwritten (framework-owned), MCP config is merged (preserves your other servers), and old skill names (`play.md`, `test-game.md`) are cleaned up automatically.

## Agent-Driven Testing

Four testing tiers from unit to AI agent:

1. **Unit tests** — `SimulationContext` drives game logic without an emulator
2. **Emulator tests** — `GbktTestExtension` (in `gbkt-test`) manages a real ROM via `StepAgent`, with auto-skip on missing ROM and auto-screenshot on failure
3. **UAT tests** — `UatRunner` drives a headless emulator with checkpoints and soft assertions
4. **MCP agent** — `gbkt-mcp-server` exposes the emulator as 19 MCP tools for Claude Code

See [context/TESTING.md](context/TESTING.md) for the complete guide (all tiers, `GbktTestExtension` API, recipes, GameConstants, `PLAYBOOK.md` format, MCP tool reference, and a worked MCP play session).

### MCP server setup

```bash
# Build the shadow JAR
./gradlew :gbkt-mcp-server:shadowJar

# Configure in .claude/mcp_servers.json
{
  "gbkt-emulator": {
    "type": "stdio",
    "command": "java",
    "args": ["-jar", "gbkt-mcp-server/build/libs/gbkt-mcp-server-all.jar"]
  }
}
```

The agent can then call `emulator_start`, `emulator_describe_game`, `emulator_step`, `emulator_wait_for_scene`, `emulator_assert`, `emulator_get_playbook`, etc.

## Verification Methodology

For verification truths shaped "X is visible on screen", evidence MUST include a runtime screenshot — variable-state assertions are not sufficient. The full Visual Evidence Rule (when it applies, when variable evidence suffices, scope-level grep gates) lives in [`.planning/verifier-gates.md`](.planning/verifier-gates.md).
